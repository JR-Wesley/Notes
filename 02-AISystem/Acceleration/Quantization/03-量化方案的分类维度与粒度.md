# 量化方案的分类坐标：以粒度连接数学表示与系统实现

本文承接 [[02-量化的统一数学模型]]：上一篇定义了 code、decoder、metadata 与 reconstruction error，本篇进一步说明一套量化方案必须在多个独立坐标轴上同时取值。`INT4`、symmetric、per-group、dynamic、PTQ 并不是同一级互斥选项；它们分别属于 element encoding、零与范围对齐、参数共享范围、参数生命周期和模型适应阶段。

在这些轴中，本文重点分析 **granularity（粒度）**。粒度首先属于 Tensor 组织层，因为它规定哪些元素共享一份参数；随后它又改变数学误差、metadata 数量、物理 layout 和 Kernel 分块。因此，本文不是把所有分类轴平均展开，而是先建立坐标系，再以 granularity 为主线观察一个组织选择怎样向下游传播。

## 2. 总体坐标系：一套方案是一组坐标，不是一个标签

### 2.1 用配置元组防止遗漏

沿用 [[02-量化的统一数学模型]] 的记号，一个方案可写成配置元组

$$
\mathcal{Q}=
(O,C,M,R,Z,P,T,E,L,A,J),
$$

其中 $O$ 是量化对象，$C$ 是 codebook/element format，$M$ 是 mapping，$R$ 是 range policy，$Z$ 是 zero alignment，$P$ 是 partition/granularity，$T$ 是参数产生时机，$E$ 是模型适应量化误差的阶段，$L$ 是 storage layout，$A$ 是 accumulator/compute contract，$J$ 是评价目标。这个元组不是必须写入代码的固定 schema，而是一张防止信息遗漏的检查表。

例如“W4A16 GPTQ”只提供了对象和大致位宽，并暗示某种算法，却仍未唯一确定 group size、group axis、对称性、zero-point、scale dtype、packing 顺序和执行 Kernel。反过来，一个足够明确的描述应接近：“线性层权重 $W[M,K]$，沿每行 K 轴每 128 个元素分组，4-bit affine code，FP16 scale，可选 integer zero-point，离线 PTQ，nibble-packed，运行时 fused dequantize 与 FP16 activation GEMM，FP32 accumulate”。

### 2.2 主要分类轴及其组合关系

| 所属层级 | 分类轴 | 核心问题 | 常见取值 | 不决定什么 |
| --- | --- | --- | --- | --- |
| 模型与算法层 | Object | 哪类 Tensor 被量化？ | weight、activation、KV cache、gradient、communication buffer | 位宽与粒度 |
| 数学表示层 | Element codebook | 单个 code 可重建哪些值？ | INT、FP、NF、logarithmic、learned table | 参数共享范围 |
| 数学表示层 | Mapping policy | 原值怎样投影到重建值？ | nearest、stochastic rounding、clipping、learned mapping | 参数何时产生 |
| 数学表示层 | Codebook geometry | 重建点是否等间距？ | uniform、non-uniform | 是否以零对称 |
| 数学表示层 | Range policy | 有限码字覆盖哪段实数范围？ | min-max、absmax、percentile、MSE/KL clipping | code 的物理排布 |
| 数学表示层 | Zero alignment | 零点和正负范围怎样安排？ | symmetric、asymmetric、显式/隐式 zero-point | codebook 是否均匀 |
| 数学表示层（logical-code domain） | Code domain | bit pattern 怎样解释？ | signed、unsigned、table index、FP special values | 重建范围是否对称 |
| Tensor 组织层 | Granularity | 哪些元素共享 $\theta_g$？ | per-tensor、per-axis、per-token、per-group、block | 参数何时产生 |
| Tensor 组织层 | Parameter lifecycle | scale/codebook 何时确定？ | static、dynamic、delayed、learned | 是否 PTQ/QAT |
| 模型与算法层 | Model adaptation | 模型何时适应误差？ | PTQ、QAT、quantization-aware fine-tuning | runtime 是否动态 |
| 存储与执行层 | Storage layout | code 与 metadata 如何排布？ | packed、byte-aligned、interleaved、swizzled | 数学误差目标 |
| 存储与执行层 | Compute contract | 谁解码、怎样累加？ | explicit DQ、fused DQ、integer-only、native scaled MMA | 模型精度是否可接受 |
| 评价层 | Objective | 用什么结果判断方案？ | reconstruction、layer output、task quality、latency/bytes | 具体表示怎样实现 |

这些轴大多可以组合。例如 symmetric uniform INT4 可以做 per-tensor static PTQ，也可以做 per-group static PTQ；asymmetric uniform INT8 可以做 per-tensor static activation quantization，也可以做 per-token dynamic quantization；一个 non-uniform codebook 也可以关于零对称，并按 group 配置 scale。组合并非完全没有约束：某个硬件 instruction 可能只接受指定 codebook、block shape、scale type 与 layout，某个训练算法也可能只为特定 mapping 推导。但这些是实现或算法施加的兼容性约束，不应倒推成概念定义。

### 2.3 把分类轴归入五个知识层级

为了在阅读论文或实现时快速定位问题，可以把上表归入五层。数学表示层回答“有哪些可重建值、实数怎样投影”；Tensor 组织层回答“谁共享参数、参数何时产生”；评价层回答“用什么指标判断这种选择”；存储与执行层回答“bit 怎样排列、谁负责恢复、用什么精度累加”；模型与算法层回答“量化哪类对象、模型何时适应误差”。Logical code domain 位于数学语义与物理存储之间，用于解释有限 bit pattern 本身，不应与 reconstruction codebook 的对称性混为一谈。

这些层级有依赖关系但不能相互替代。数学上定义完整的 quantizer 仍可能没有可执行 layout；一个写着 packed INT4 的文件也可能因缺失 scale shape 和 decoder 而无法恢复数值；硬件支持某条 INT4 MMA instruction，更不代表任意 INT4 codebook、group size 或 zero-point 都能直接执行；局部 reconstruction error 更小，也不自动等于 task quality 或 latency 更好。

## 3. 先澄清两组最容易混淆的分类轴

本节仍在总体坐标系内，不是在介绍四种互斥量化类型。第一组位于数学表示层，区分 codebook 几何与零点对齐；第二组位于 Tensor 组织与模型算法层，区分参数何时产生与模型何时适应误差。

### 3.1 数学表示层：uniform/non-uniform 与 symmetric/asymmetric

#### Codebook geometry：重建点怎样分布

**Uniform/non-uniform** 描述 reconstruction codebook 的几何间距。Affine integer quantization 的

$$
\hat{x}=S(q-Z)
$$

具有固定步长 $S$，所以无论 $Z$ 是否为零，它都是 uniform。NF4 或 k-means weight sharing 的 codebook 间隔不恒定，所以属于 non-uniform；若码字成正负配对，它仍可在几何上 symmetric。

#### Zero/range alignment：零与有限范围怎样对齐

**Symmetric/asymmetric** 描述零点与范围的对齐约束。工程中 symmetric 常指 $Z=0$ 且正负有限范围对称；asymmetric 常通过非零 zero-point 平移 uniform codebook。但有些 API 使用浮点 zero-point，另一些格式没有显式 $Z$，还有些论文把“正负使用相同 scale”称为 symmetric。阅读时必须回到 encode/decode 公式，不依赖标签猜测。

#### Logical-code signedness：bit pattern 如何解释

Signed/unsigned 属于 logical-code domain，而不是 symmetric/asymmetric 的同义词。`uint8` 配合 $Z=128$ 可以表达近似对称的实数范围；`int8` 配合非零 $Z$ 也可以表达偏斜范围。逻辑码字的符号解释与 reconstruction codebook 的零对齐是两层语义。

### 3.2 参数与模型层：static/dynamic 与 PTQ/QAT

#### Parameter lifecycle：metadata 何时产生

**Static/dynamic** 描述 $\theta_g$ 的 runtime lifecycle。Static quantization 在部署前或模型准备阶段固定 scale、zero-point 或 codebook，推理时复用；dynamic quantization 根据当前输入在运行时计算参数。Delayed scaling 使用历史统计更新后续 step 的参数，处于“参数会变化但不是当前值即时决定”的中间形态。Learned scale 则把参数纳入优化过程。

#### Model adaptation：模型何时接触量化误差

**PTQ/QAT** 描述模型适应量化误差的时间。PTQ 从已训练模型出发选择量化参数或修正权重；QAT 在训练或微调的前向中模拟量化，使模型参数适应离散化。一个 PTQ 方案的 activation scale 可以是 runtime dynamic；一个 QAT 模型部署后也可以使用完全 static 的 scale。因此把 dynamic quantization 当作 QAT、把 static quantization当作 PTQ，都是分类轴混淆。

#### Dynamic 的系统成本来自数据依赖

Dynamic 参数通常提高对输入分布变化的适应性，却需要 reduction 求 amax/min/max、计算 scale，并让后续 Kernel 等待 metadata。若该统计与 quantize 能融合进生产者或通信 Kernel，开销可能被隐藏；若生成独立中间 Tensor 和额外 global-memory pass，理论精度收益可能被 latency 抵消。

## 4. Tensor 组织层核心：Granularity 的一般定义

前面的分类轴回答“方案有哪些坐标”。从这里开始只沿 granularity 这一轴深入。先回到上一篇的 BF16 weight → INT4 实例，观察只改变 group size 会发生什么；再把实例抽象成 partition function。粒度的直接产物是 metadata Tensor 的逻辑 shape，误差、容量与 Kernel 后果将在第 7–9 节逐层推导。

### 4.1 回到上一篇：同一行权重采用不同 group size

[[02-量化的统一数学模型#2. 贯穿示例：把 BF16 Linear 权重量化为 group-wise INT4|上一篇的贯穿示例]] 使用同一行中的 8 个 BF16 权重：

$$
W=[-1,-0.5,-0.25,0,0.125,0.5,0.75,1],
$$

目标 mapping 固定为 symmetric INT4、RNE、FP16 scale，不改变 codebook、rounding 或 metadata dtype。现在只改变沿 K 轴的 group size $G$，就能隔离 granularity 的作用。

| $G$ | Partition | FP16 scales | Reconstruction MSE | 理想 bits/weight | 相对 BF16 理想压缩比 |
| ---: | --- | --- | ---: | ---: | ---: |
| 8 | 整行 1 组 | `[0.1428223]` | $1.6301\times10^{-3}$ | $4+16/8=6$ | $2.67\times$ |
| 4 | 前后各 4 个，共 2 组 | `[0.1428223, 0.1428223]` | $1.6301\times10^{-3}$ | $4+16/4=8$ | $2.00\times$ |
| 2 | 每 2 个一组，共 4 组 | `[0.1428223, 0.0357056, 0.0714111, 0.1428223]` | $8.3599\times10^{-4}$ | $4+16/2=12$ | $1.33\times$ |

这个结果比“group 越小越精确”更有信息。$G=4$ 虽然更细，但前后两组的最大绝对值仍然都是 1，所以得到相同 scale、codes 和 MSE，只增加了 metadata。到 $G=2$ 时，中间两组获得更小的局部 scale，MSE 才下降约一半；与此同时，每个 weight 摊销的 scale 成本从 2 bit 增至 8 bit，理想压缩比明显下降。

因此，granularity 改变的是 partition，不是直接给误差下结论。更细 partition 只提供“各组可以使用不同参数”的自由度；数据分布是否让这份自由度产生收益，还要看各组 statistics、scale 精度与评价目标。真实部署的 $G=32/64/128$ metadata 摊销远低于这个 8 元素教学例子，但同一因果关系不变。

### 4.2 Partition function：从元素坐标到参数组

对 shape 为 $(D_0,\ldots,D_{r-1})$ 的 Tensor $X$，partition function $g(i_0,\ldots,i_{r-1})$ 把元素映射到参数组。Metadata Tensor $\Theta$ 的逻辑 shape 就是不同参数组在各轴上的计数。若第 $j$ 轴按 block size $B_j$ 分块，则该轴的参数数量为

$$
S_j=\left\lceil\frac{D_j}{B_j}\right\rceil.
$$

一个一般的 rectangular block quantizer 可以令 block shape 为 $(B_0,\ldots,B_{r-1})$，metadata 的逻辑 shape 为

$$
\operatorname{shape}(\Theta)=
\left(\left\lceil\frac{D_0}{B_0}\right\rceil,\ldots,
\left\lceil\frac{D_{r-1}}{B_{r-1}}\right\rceil\right).
$$

令 $B_j=D_j$ 表示该轴不切分，令 $B_j=1$ 表示每个坐标位置分别保留参数。Per-tensor、per-axis、per-row 和二维 block 都是这个定义的特例。具体框架可能只支持沿一个 axis blocking，或者把 block size 表达成与 input rank 相同的元组，因此文件格式、API 和 Kernel 的“block”不能只靠自然语言互换。

### 4.3 逻辑分组：参数组不是数据副本

Partition 只规定哪些元素引用同一份 metadata，并不要求先把每组复制成连续的小 Tensor。实现可以通过 strides、index arithmetic 或预先 swizzle 的 layout，让逻辑上属于同一组的 code 与 scale 在加载时相遇。因此“沿 K 轴每 128 个元素一组”是逻辑关系；这些 128 个 code 是否在文件和显存中连续，还取决于 physical layout。

### 4.4 语义单元：Quantized group 必须能够被唯一恢复

对第 $g$ 个量化组，一个可恢复的逻辑单元至少可表示为

$$
\mathcal{G}_g=(Q_g,\theta_g,d_g),
$$

其中 $Q_g$ 是组内 code，$\theta_g$ 是 scale、zero-point 或 codebook 等解码参数，$d_g$ 是必要的 shape、axis、有效长度或格式描述。若这些描述已由 Tensor schema 全局固定，$d_g$ 不必为每组重复存储；但 decoder 必须能从全局 schema 和组索引恢复它。

例如 INT4 group-size 128 的一个完整逻辑组并不只是 128 个 4-bit code，还包括该组的 scale、可选 zero-point，以及最后一组不足 128 个元素时的有效长度规则。忽略其中任一项，都可能让同一 bit pattern 被恢复成不同实数。

## 5. Granularity 的常见取值及其 Tensor 语义

Per-tensor、per-axis、per-token、per-group 与 per-block 都是 partition 的命名方式。它们必须连同量化对象、逻辑轴和 shape 一起解释；名称本身不能决定参数生命周期、codebook 或物理连续性。

| 名称 | 参数共享方式 | 典型对象 | 参数量与特点 |
| --- | --- | --- | --- |
| Per-tensor | 整个 Tensor 一个 $\theta$ | 简单 activation、接口量化 | metadata 最少，最易受跨区域 range 差异影响 |
| Per-axis / per-channel | 指定轴每个 index 一个 $\theta$ | Conv/Linear weight | 参数数等于该轴长度；“channel”必须说明轴语义 |
| Per-row / per-column | 矩阵每行或每列一个 $\theta$ | Linear weight、embedding | 是二维 Tensor 上的 per-axis 特例 |
| Per-token | 每个 token 的一行/向量一个 $\theta$ | LLM activation、KV | 通常需 runtime statistics；还要说明 batch/head 轴 |
| Per-group | 某逻辑序列每连续 $G$ 个元素共享 $\theta$ | LLM weight-only | 常沿 Linear 的 reduction/K 轴；需要 group size 与 axis |
| Per-block | 一个一维或多维块共享 $\theta$ | block-scaled FP/INT、MX | 必须给 block shape、边界和 scale layout |
| Per-element | 每元素独立参数 | 理论上限、特殊 double quantization | metadata 往往抵消压缩收益 |

### 5.1 Per-tensor：最低 metadata，最高分布耦合

整个 Tensor 只共享一份参数，统计、广播与 Kernel 接口最简单。但任何局部 outlier 都可能扩大全局 range，因此它更适合分布较均一的 Tensor、位宽较高的量化，或只作为接口边界上的简单编码。

### 5.2 Per-axis/per-channel：利用稳定的结构语义

“Per-channel”最容易产生轴歧义。若线性层按 $Y=XW^\top$ 计算，权重常记作 $W[M,K]$，$M$ 是 output features，$K$ 是 reduction/input features。Per-output-channel weight quantization 通常是每一行一个 scale，metadata shape 为 $[M]$；若框架存的是 $W[K,M]$，同一语义就落在另一物理 axis。卷积权重还可能使用 OIHW、HWIO 等 layout。必须同时记录逻辑通道含义与物理 axis number。

### 5.3 Per-token：按 activation 的 token 语义分组

“Per-token”也不是独立数学原语，而是 activation Tensor 上按 token 语义选择的 partition。对于 $X[B,T,K]$，常见 per-token scale 的逻辑 shape 是 $[B,T,1]$，每个 token 的 hidden vector 共享参数；对包含 head 轴的 $[B,H,T,D]$，还需说明 scale 是 per-token、per-head-per-token，还是在 $H\times D$ 上共同统计。

上一篇的 BF16 activation → INT8 对照中，单个 token 片段 $[0.5,-1,2,0]$ 共享 scale $2/127$，这就是 per-token partition 的一个组。若另一个 token 的最大绝对值只有 0.2，per-token 允许它使用约 $0.2/127$ 的更小 scale，而 per-tensor 会让两个 token 共用 $2/127$。这里“per-token”只说明谁共享参数；示例中 scale 由当前 token 现场计算，所以它另外还属于 dynamic parameter lifecycle。Per-token 可以配 static scale，dynamic 也可以配 per-tensor，二者不是同义词。

### 5.4 Per-group 与 per-block：把局部性变成显式参数

“Per-group”与“per-block”在文献中经常重叠。实用区分是：group 往往指沿某个逻辑一维序列连续分组，block 强调一维或多维 block shape 以及与硬件/格式规定的对应关系。但这不是跨框架统一标准；可靠描述必须写 `axis + group/block shape + ordering`。

### 5.5 比较规则：粒度不是一条普适的粗细直线

在同一个确定的 axis 和 partition family 内，group size 从 128 减到 32 可以称为更细；但 per-token、per-channel 与二维 block 往往切分的是不同轴，不能仅凭名称排成统一的“粗到细”顺序。判断两种粒度谁更细，应比较其 partition：若方案 A 的每个组都完全包含在方案 B 的某个组内，A 才是 B 的 refinement。否则它们只是不同方向的切分。

## 6. 从 8 个权重推广到完整 Linear 矩阵

第 4 节只看了一行中的 8 个元素。本节把相同 partition 规则推广到完整 Linear 权重矩阵，验证 granularity 如何决定逻辑 metadata shape，尚未进入物理 packing。固定矩阵语义与分组轴之后，才能比较 per-output-channel 与沿 K 轴 per-group 的参数数量。

设 $W\in\mathbb{R}^{M\times K}$，按行存储，并采用沿 K 轴 group size $G$ 的 weight quantization。第 $m$ 行第 $g$ 组为

$$
W_{m,g}=W[m,\ gG:\min((g+1)G,K)].
$$

每组一份 scale 时，scale Tensor 的逻辑 shape 为

$$
[M,\lceil K/G\rceil].
$$

这与 per-output-channel $[M]$ 不同。若 $M=4096$、$K=11008$、$G=128$，因为 $11008/128=86$，需要 $4096\times86=352256$ 个 scale；per-output-channel 只需要 4096 个。细粒度方案的 scale 数不是“更少”，而是多 86 倍，换来每组更贴合局部分布。这个结论只有在矩阵语义、分组轴和 group size 都固定后才成立。

若 $K$ 不能被 $G$ 整除，最后一组只有 $K\bmod G$ 个有效元素。实现可以存一个短尾组、padding 到完整组，或要求 shape 预先对齐；三者的文件大小、Kernel branch 和 layout contract 不同。逻辑公式里的 $\lceil K/G\rceil$ 不代表物理存储一定没有 padding。

## 7. 第一类下游后果：Metadata 容量与带宽

粒度从 Tensor 组织层影响存储层的第一条路径，是“组越多，需要保存和加载的参数越多”。先计算不含布局约束的理想摊销，再加入 padding、alignment 与 schema，避免把数学参数量直接当成文件大小。

### 7.1 理想容量：先计算每元素摊销

设每个量化元素占 $b_q$ bit，每组 $G$ 个元素共享一份 $b_s$ bit scale 和一份 $b_z$ bit zero-point，暂不考虑 padding、alignment 与 tensor header。每个原始元素的平均存储成本为

$$
b_{\mathrm{eff}}=b_q+\frac{b_s+b_z}{G}.
$$

相对只计算 data code 的理想大小，metadata 比例为

$$
\rho_{\mathrm{meta}}=\frac{b_s+b_z}{G b_q}.
$$

以 INT4 data、FP16 scale、无 zero-point 为例：

| Group size $G$ | 有效 bits/element | Metadata 相对 data | 相对 BF16 的理想压缩比 |
| ---: | ---: | ---: | ---: |
| 256 | $4+16/256=4.0625$ | 1.5625% | $16/4.0625\approx3.94\times$ |
| 128 | 4.125 | 3.125% | $\approx3.88\times$ |
| 64 | 4.25 | 6.25% | $\approx3.76\times$ |
| 32 | 4.5 | 12.5% | $\approx3.56\times$ |
| 16 | 5 | 25% | $3.2\times$ |
| 8（教学例） | 6 | 50% | $\approx2.67\times$ |

若再加入 8-bit zero-point，$G=32$ 时有效成本为 $4+(16+8)/32=4.75$ bit/element，metadata 已相当于 data 的 18.75%。这仍未包含尾部 padding、对齐、scale Tensor 的硬件 swizzle、模型容器索引和小 Tensor 固定开销，所以文件或显存实测通常低于“BF16 到 INT4 正好压缩 4 倍”的宣传值。

Metadata overhead 不只占容量，还占 bandwidth。Weight-only GEMM 需要同时加载 packed weights 和 scales；若 scales 无法在一个 tile 内充分复用，或者布局导致非合并访存，较小 group 可能增加 scale load 与 address-generation 成本。反过来，过大的 group 虽减少 metadata，却可能被少数 outlier 拉大 $S$，使大多数权重的 rounding resolution 变差。

### 7.2 实际容量：再加入 padding、alignment 与 schema

理想公式假设每个 code bit 和 metadata bit 都能无缝拼接。实际容器还可能包含 Tensor header、shape、dtype tag、offset table，物理 Tensor 还可能按 byte、word、cache line 或 MMA tile 对齐。对大权重矩阵，这些固定开销通常较小；对大量小 Tensor，header 和 alignment 可能显著改变总压缩比。因此应分别报告理论 payload、metadata、padding 和容器开销，而不是只给一个“平均 bit 数”。

## 8. 第二类下游后果：Group/block size 的四重权衡

同一个 group size 会同时作用于四个层面。误差属于数学评价，metadata 属于表示与存储，layout 属于物理组织，compute efficiency 属于执行合同；不能只优化其中一个指标就断言方案更好。

### 8.1 数学评价：局部范围与误差

在相同 codebook 和 range policy 下，减小 group 通常让每组动态范围更局部，降低 outlier 对其他元素的影响，并允许更小的 step size。但这不是无条件的单调质量保证：第 4 节从 $G=8$ 改为 $G=4$ 后，两组 absmax 仍相同，因此 MSE 完全没有下降；只有 partition 真正隔离了不同局部范围时，更细粒度才提供更小 step。除此之外，小组统计可能更噪声化，scale 自身低精度会放大误差，算法优化目标也可能跨组耦合。最终仍需测 layer output 或 task metric。

### 8.2 表示成本：Metadata 与容量

Group 越小，scale/zero-point 数量按 $1/G$ 增长。极端 per-element scale 可能让 metadata 与 data 一样大甚至更大。若 metadata 也量化，则又引入上一级 scale，形成 hierarchical/double quantization；这会改变完整 codebook，不能只在容量公式中把 scale bit 数替换后忽略其误差。

### 8.3 存储实现：Layout 与访存

逻辑 scale shape 不等于硬件要求的物理 layout。自然布局可能是 `[outer, ceil(K/G)]` row-major；硬件 MMA 可能要求按 warp-group 和 K tile 进行 swizzle，并将 scale tile padding 到固定边界。NVIDIA CUTLASS 对 Blackwell block-scaled GEMM 的文档示例中，自然的一维 scale 数为

$$
L\times\mathrm{outer}\times\left\lceil K/V\right\rceil,
$$

而特定 `Swizzle32x4x4` 物理布局要求

$$
L\times\operatorname{round\_up}(\mathrm{outer},128)
\times\operatorname{round\_up}\!\left(\left\lceil K/V\right\rceil,4\right)
$$

个 scale slot。这里的 padding 是硬件消费布局的一部分，不能从纯数学 group 数量推出。

### 8.4 执行合同：Compute efficiency

高效 GEMM 把 $M,N,K$ 分解成 instruction、warp-group/warp、CTA 与 cluster tile。若 scale group 沿 K 轴，其边界最好与 MMA 消费的 K vector 和 data packing 对齐，使一个 scale 能在固定次数的 multiply-accumulate 中复用。任意 group size 可能需要额外 indexing、predicate、unpack 或先生成反量化 Tensor。硬件原生 block-scaled MMA 则把 scale 应用纳入指令语义，但只接受规定的 scale vector size、dtype 和 layout。

因此，算法上最优的 $G$ 不一定是系统上最快的 $G$。工程选择要同时满足：误差足够小、metadata 可接受、转换和加载可融合、目标 Kernel 有实现、shape 与 tile 对齐。框架只暴露某几个 group size，往往不是数学上只有这些可能，而是 backend 对这些组合有优化合同。

## 9. 三种不同分块：逻辑粒度、物理 packing 与计算 tile

`group`、`block`、`tile` 经常在不同资料中被宽松地混用。本节按所属层级把它们拆开：quantization group 属于 Tensor 组织层，packing group 属于存储层，MMA/CTA tile 属于执行层。三者边界对齐可以提高效率，但相等不是定义要求。

### 9.1 Quantization group：决定共享参数

Quantization group 是 partition function 的像：组内 code 共享同一份 $\theta_g$。它影响误差和 metadata shape，但不直接规定一次 load 多少 byte，也不直接规定 MMA 每次消费多少 K 元素。

### 9.2 Packing group：决定 bit 如何装入存储单元

两个 4-bit code 常被装入一个 byte。若低 nibble 存 $u_0$、高 nibble 存 $u_1$，则

$$
b=(u_0\mathbin{\&}15)\;|\;((u_1\mathbin{\&}15)\ll4).
$$

解包得到 unsigned nibble $u\in[0,15]$ 后，若逻辑 code 是 two's-complement signed INT4，则需做符号恢复

$$
q=\begin{cases}
u,&u<8,\\
u-16,&u\ge 8.
\end{cases}
$$

Nibble 顺序、byte order、是否跨行 packing、尾部半字节如何 padding 都属于 storage contract。量化数学完全相同的两个 Tensor，只要 nibble ordering 不同，原始 byte stream 就不能互换。

上一篇的 8 个 INT4 codes 在“第一个 code 放 low nibble”的约定下打包为 `0xC9 0x0E 0x41 0x75`。这里 quantization group 包含 8 个 code并共享一个 scale，而每个 packing group 只有 2 个 code、负责组成一个 byte。二者恰好存在 $8/2=4$ 的整除关系只是本例布局友好；若 quantization group、行尾或 vector-load boundary 不对齐，仍需 padding 或跨组索引。

### 9.3 Vector load 与 MMA/CTA tile：决定执行分块

Kernel 可能一次加载 16 或 32 byte，用若干线程协作 unpack，再按 instruction 要求构造寄存器 fragment；MMA 又有自己的 $M\times N\times K$ tile。这些执行分块可以包含多个 quantization group，也可以只消费一个组的一部分。只有在 group boundary、packing boundary、vector width 与 K tile 协调时，才能减少分支、重复 scale load 和地址计算。

因此至少要区分四种常被简称为 block 的对象：共享参数的 quantization block、装载 bit 的 packing block、指令消费的 MMA tile、线程块负责的 CTA tile。它们的大小相等是一种实现优化，不是定义要求。

## 10. 组合实例：Activation 与 Weight 的粒度怎样相遇

前文分别讨论单个 Tensor 的 partition，本节把上一篇的 BF16 activation → INT8 与 BF16 weight → INT4 放进同一个矩阵乘。两侧 metadata shape 与 K 轴 group boundary 会共同约束 dot-product 分解，这也是 granularity 从统计选择进入 Kernel 接口的具体位置。

对矩阵乘 $Y=XW^\top$，令 $X[B\!T,K]$ 表示展平 batch/token 后的 activation，$W[M,K]$ 表示权重。几种常见组合可写为：

| 方案 | Activation metadata shape | Weight metadata shape | 典型参数时机 | 主要优点 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| A per-tensor / W per-tensor | `[1]` | `[1]` | static 或 dynamic | metadata 与 Kernel 最简单 | 对跨行 range 差异最敏感 |
| A per-tensor / W per-channel | `[1]` | `[M]` | A 可 dynamic，W static | 权重行差异得到保护 | epilogue/scale broadcast 更复杂 |
| A per-token / W per-channel | `[BT,1]` | `[M,1]` | A 常 dynamic，W static | 适应不同 token 与输出行 | runtime reduction 与二维 scale outer product |
| A per-token-group / W per-group | `[BT,ceil(K/G_A)]` | `[M,ceil(K/G_W)]` | A dynamic，W static | 最细局部范围 | metadata、layout 和 block dot-product 最复杂 |

最后一行还隐藏着一个关键问题：若 activation 与 weight 沿 K 轴使用不同 group boundary，那么一个 dot product segment 可能同时跨越两套 scale。Kernel 需要把 K 轴切分到两者边界的公共细分，或限制 $G_A,G_W$ 与 tile 的关系。Granularity 不只是统计学选择，它直接改变计算分解。

## 11. 从术语走向可执行方案：补齐描述字段

到这里可以把各层重新接回一套方案。短标签只适合索引，不能保证数值可恢复或 Kernel 可执行；应先补齐模糊术语隐去的字段，再写完整 descriptor。

### 11.1 模糊术语必须补齐的字段

| 模糊说法 | 至少补充 |
| --- | --- |
| per-channel INT8 | 对象、logical channel、physical axis、code range、scale/zero-point dtype |
| per-token FP8 | Tensor shape、哪些轴共同统计、FP8 variant、scale timing 与 scale shape |
| group-wise INT4 | group axis、group size、尾组规则、对称性、packing 顺序、scale/zero-point layout |
| block quantization | block shape、遍历顺序、shared metadata、边界 padding、硬件是否原生消费 |
| dynamic quantization | 哪些参数动态、统计范围、更新频率、quantize 是否与生产者融合 |
| W4A16 | W 的具体 codebook/granularity，A 的 16-bit dtype，compute 与 accumulator dtype |

尤其要避免把 `block size` 当作全局唯一数字。同一个方案中可能同时存在 quantization block、packing block、MMA K tile、CTA tile 和文件容器 chunk。它们可以恰好相等，也可以完全不同；文档必须给每个 block 所属层次。

### 11.2 用格式描述符完整定义一套方案

为了让论文概念、文件格式和 Kernel 接口可以对照，可用下面的 descriptor 记录一套方案。它不是要求所有框架采用同一种配置文件，而是确保人类描述没有遗漏恢复数值所需的信息。

| 层次 | 必填问题 | 示例字段 |
| --- | --- | --- |
| Source Tensor | 原始对象是什么？ | object、logical shape、source dtype、axis semantics |
| Partition | 谁共享参数？ | axis、group/block shape、traversal order、tail rule |
| Statistics/range | 参数怎样得到？ | min/max、amax、percentile、optimization objective、update timing |
| Element encoding | 单个 code 怎样解释？ | codebook/element dtype、code range、rounding、clipping |
| Decoder metadata | 怎样恢复实数？ | scale dtype/shape、zero-point、codebook table、hierarchical scale |
| Physical storage | bit 在哪里？ | packing order、byte order、alignment、padding、metadata placement |
| Decode path | 谁在何时恢复？ | materialized DQ、fused DQ、native scaled instruction |
| Compute contract | 恢复后怎样算？ | operand dtype、multiply semantics、accumulator dtype、output dtype |

一个足以索引方案的短名称可以是 `BF16 -> INT4_K128_SYM_S16_ROW_PACKED -> fused W4A16 GEMM(FP32 accumulate)`，但名字仍不能代替 descriptor：必须说明 `ROW` 对应哪个逻辑 axis、signed INT4 的编码方式、尾组和 nibble 顺序。相同 descriptor 还可以直接驱动测试：先验证 byte-level round trip，再验证 dequantized Tensor，最后验证 fused Kernel 与参考计算的误差。

### 11.3 用三个教学名称检查坐标是否完整

下面只给教学级描述，用来验证分类方法，不把名称冒充标准类型：

| 维度 | `INT8_BLOCK128` | `FP8_BLOCK128` | `MXFP4_BLOCK32_ROW` |
| --- | --- | --- | --- |
| Partition | 每连续 128 元素一组 | 每连续 128 元素一组 | 每行沿 K 每 32 元素一块 |
| Element codebook | signed INT8 lattice | 某个待指定 FP8 variant | OCP MXFP4 element format，待规范篇精确定义 |
| Mapping | 常为 affine/uniform | 外层 scale + FP encode | 规范定义的 shared scale + FP4 encode |
| Symmetry | 需另行指定 | 不能由 FP8 名称推出外层 range policy | 由具体 MX 规范而非名称猜测 |
| Metadata | scale，可选 zero-point | 每组 scale | 每块 shared scale |
| Storage | byte code + scale layout | FP8 byte + scale layout | packed FP4 + scale layout |
| Compute | integer dot 或 fused DQ | DQ/fused/native FP8 MMA | 需硬件 block-scaled MMA 或软件展开 |

前两列名称没有指定 scale dtype、axis、布局和 FP8 variant，所以仍不是完整方案；第三列即使意图指向 OCP MX，也必须在下一篇核对标准的 element codebook、block rule、scale encoding 和运算语义。这正是多轴分类的用途：它不仅整理概念，也能暴露名称中缺失的信息。

## 12. 小结

量化 scheme 应被视为多个正交轴的组合，而不是由 `INT4`、per-group 或 PTQ 任一标签单独定义。Granularity 用 partition function 决定参数 Tensor 的逻辑 shape，它同时影响局部动态范围、metadata bits、scale bandwidth、物理布局和 Kernel 的 K 轴分解。8 元素实例表明，更细 group 只增加“可以使用不同参数”的自由度：若各组 statistics 相同，误差不会下降；若局部范围不同，误差可能下降，但 metadata 与实现成本随之上升。完整 descriptor 还必须说明 code 和 metadata 的 packing、tail、layout、decode path 与 compute contract。真正可部署的选择，是数值误差、可恢复编码和硬件合同共同约束的结果。

下一篇将在这套分类坐标上进入现代低精度格式，分别拆解 FP8 element formats、外部 block scaling、OCP MXFP8/MXFP6/MXFP4 和厂商格式。重点将是区分 element codebook、shared-scale encoding 与 hardware compute contract，而不是把所有 4-bit 浮点方案合并为“FP4”。
