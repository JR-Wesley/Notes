# 数值表示与误差基础：从 0.1 的存储误差开始

低精度 AI 的起点不是某一种量化算法，而是一个更基本的问题：把数学上的实数 `0.1` 存进有限 bit 后，机器里究竟留下了什么？本文以 `0.1` 的存储为贯穿示例，再用“给参数 1.0 加上更新量 0.0004”观察运算误差。所有概念——bit pattern、normal、subnormal、dynamic range、precision、ULP、rounding、overflow、cancellation 与 accumulator——都用于解释这两个可计算现象，而不是作为孤立术语出现。

本文是 [[00-低精度量化知识地图]] 的数值表示基础层。它先讨论单个 element format 能表示什么，再把结论交给 [[02-量化的统一数学模型]]，由后者加入 Tensor scale、zero-point、granularity 与 metadata。IEEE 754 的当前有效版本是 IEEE 754-2019，覆盖 binary 与 decimal floating-point；本文只讨论与后续 AI 量化直接相关的二进制格式。BF16、TF32、FP8、FP4 和 MX 会作为对照出现，但不把厂商或行业格式误称为 IEEE 754 标准格式。

## 1. 从一个具体问题开始：机器怎样存储 0.1

数学上的十进制数

$$
x=0.1=\frac{1}{10}
$$

在二进制中是无限循环小数：

$$
0.1_{10}=0.00011001100110011\ldots_2.
$$

原因可以从分母看出：有限二进制小数一定能写成 $k/2^n$，而 $1/10$ 的最简分母还含有因子 5，所以不可能只用有限个二进制小数位精确表示。目标格式只能在相邻两个可表示值之间选择一个，这一步就是 rounding。`0.1` 因而把“有限码字”“舍入规则”和“误差衡量”三个问题同时暴露出来。

在 round-to-nearest, ties-to-even 下，几种常用格式保存 `0.1` 的结果如下。表中的 ULP 是 `0.1` 所处 binade 内相邻浮点数的间距；ULP error 是绝对误差除以该间距。

| 格式 | 实际保存的值 | 绝对误差 | 相对误差 | `0.1` 附近的 ULP | ULP error |
| --- | ---: | ---: | ---: | ---: | ---: |
| FP64 / binary64 | $0.10000000000000000555\ldots$ | $5.5511\times10^{-18}$ | $5.5511\times10^{-17}$ | $2^{-56}\approx1.3878\times10^{-17}$ | $0.4$ |
| FP32 / binary32 | $0.10000000149011611938\ldots$ | $1.4901\times10^{-9}$ | $1.4901\times10^{-8}$ | $2^{-27}\approx7.4506\times10^{-9}$ | $0.2$ |
| FP16 / binary16 | $0.0999755859375$ | $2.4414\times10^{-5}$ | $2.4414\times10^{-4}$ | $2^{-14}\approx6.1035\times10^{-5}$ | $0.4$ |
| BF16 | $0.10009765625$ | $9.765625\times10^{-5}$ | $9.765625\times10^{-4}$ | $2^{-11}=4.8828\times10^{-4}$ | $0.2$ |

这张表先给出三个结论。第一，位数更多通常使绝对误差更小，但“误差是多少个 ULP”取决于真实值落在相邻码字之间的位置，不会随位宽单调下降。第二，RNE 对正常范围内的单次正确舍入保证误差不超过半个相邻间距；上表所有结果都满足 $0.5$ ULP 边界。第三，`0.1` 的十进制打印值不是数学真值本身；必须区分 exact target、stored value 与显示时再次进行的 binary-to-decimal conversion。

## 2. 从 0.1 推广：有限码字怎样分配到数轴

一个 $b$ bit 存储单元至多提供 $2^b$ 个不同 bit pattern。格式设计的本质，是决定这些 pattern 对应哪些数值和特殊状态。**Dynamic range** 描述可表示数值跨越多大的数量级，通常关注最小非零正数与最大有限正数；**precision** 描述某一数值附近可分辨的间隔。两者不是同义词：增加 exponent bits 可以覆盖更多数量级，但在总位宽固定时通常会减少 significand bits，使相邻可表示值变疏。

二进制整数把码字均匀放在数轴上。无符号 $b$ bit 整数的集合为 $\{0,\ldots,2^b-1\}$；二进制补码有符号整数通常为 $\{-2^{b-1},\ldots,2^{b-1}-1\}$。相邻整数始终相差 1，因此整数具有固定的绝对分辨率，但原生整数 codebook 无法同时覆盖很大的动态范围和靠近零的细小变化。量化中的 scale 会把这个整数格点映射到真实数轴；这属于下一篇的 Quantization Scheme，而不是 INT8/INT4 存储类型自身的属性。

浮点格式则近似科学计数法，把有限码字非均匀地分布在数轴上。它用 exponent 改变数量级，用 significand（常口语化称 mantissa）描述该数量级内的有效数字。因此浮点数通常保持近似恒定的相对精度，而绝对间隔随数值绝对值增大。

## 3. IEEE 二进制浮点编码：bit pattern 怎样变成数值

第 1 节只观察了 `0.1` 的结果，本节进入它所属的 **element encoding** 层，解释 sign、exponent 与 fraction 怎样定义 reconstruction codebook。先掌握 normal 的解码公式，再看 exponent 全零或全一时为什么切换到 subnormal 与特殊值。

对一个包含 1 个 sign bit、$e$ 个 exponent bits 和 $m$ 个显式 fraction bits 的 IEEE 754 风格二进制格式，正规数（normal number）的值可写为

$$
x=(-1)^s\,2^{E-\mathrm{bias}}\left(1+\frac{F}{2^m}\right),
$$

其中 $s\in\{0,1\}$，$E$ 是 exponent field 对应的无符号整数，$F$ 是 fraction field。正规数的最高有效位总为 1，所以不必显式存储，这一位称为 implicit/hidden bit；有效精度为 $p=m+1$ 个二进制位。IEEE 风格格式通常令全零 exponent 编码零和 subnormal，全一 exponent 编码无穷大或 NaN；具体低位格式可能重新利用这些码字，所以不能仅由 `ExMy` 名称推断全部特殊值语义。

Exponent bias 让无符号 exponent field 表达正、负实际指数。对 IEEE binary16/32/64/128，$\mathrm{bias}=2^{e-1}-1$。Bias 有助于编码与比较电路组织 exponent，但不能据此推出整个浮点 bit pattern 可直接按无符号整数比较，因为 sign、特殊值和符号零仍需单独处理。

先用可精确表示的 `10.5` 作为 `0.1` 的对照。它的二进制为 $1010.1_2=1.0101_2\times2^3$。在 FP32 中，sign 为 0，biased exponent 为 $3+127=130=10000010_2$，fraction 为 `0101000...0`，所以完整 bit pattern 为

```text
0 | 10000010 | 01010000000000000000000
```

即十六进制 `0x41280000`。因为 $10.5=21/2$ 的分母是 2 的幂，它能被精确表示。相比之下，FP32 中的 `0.1` 为 `0x3DCCCCCD`：最后的 `D` 体现了无限循环展开在有限 fraction 后发生了进位舍入。

再看一个较短的 FP16 例子。若 sign 为 0、$E=15$、fraction 为 `0100000000`，则其值是

$$
2^0\left(1+2^{-2}\right)=1.25.
$$

这也说明 “mantissa bits” 在工程语境中可能只指显式 fraction，也可能把 hidden bit 算在内。本文用 $m$ 表示显式 fraction bits，用 $p=m+1$ 表示正规数的 significand precision，以消除这种歧义。

## 4. 对比当前格式：哪些是 IEEE 标准，哪些是 AI 专用格式

IEEE 754-2019 当前定义的标准二进制 interchange formats 是 binary16、binary32、binary64 与 binary128。下表中的 machine epsilon 指 1 与下一个大于 1 的可表示数之间的距离，即 $2^{-m}$；它不要与后文 round-to-nearest 的 unit roundoff 混淆。

| IEEE binary format | 编码 | Significand precision $p$ | 最小正规正数 | 最小正 subnormal | 最大有限正数 | $\epsilon$ at 1 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| FP16 / binary16 | S1E5M10 | 11 bit | $2^{-14}$ | $2^{-24}$ | $65504$ | $2^{-10}$ |
| FP32 / binary32 | S1E8M23 | 24 bit | $2^{-126}$ | $2^{-149}$ | $(2-2^{-23})2^{127}$ | $2^{-23}$ |
| FP64 / binary64 | S1E11M52 | 53 bit | $2^{-1022}$ | $2^{-1074}$ | $(2-2^{-52})2^{1023}$ | $2^{-52}$ |
| FP128 / binary128 | S1E15M112 | 113 bit | $2^{-16382}$ | $2^{-16494}$ | $(2-2^{-112})2^{16383}$ | $2^{-112}$ |

现代 AI 还使用多种 IEEE 风格或专用格式。它们可以继续用 finite codebook、range、precision 与 rounding 分析，但标准身份和执行语义不同。

| 格式家族 | 在知识体系中的位置 | 与 IEEE binary formats 的关键差别 |
| --- | --- | --- |
| BF16 | 16-bit AI element format，S1E8M7 | NVIDIA 当前文档明确将其列为非 IEEE 754 格式；接近 FP32 range，但 precision 更低 |
| TF32 | NVIDIA Tensor Core 的计算精度 | 输入/存储仍以 FP32 承载，内部 layout 是 implementation-defined；不能当成普通 19-bit 文件 dtype |
| FP8 / FP6 / FP4 | 低位 element-format families | variant 会改变 exponent bias、NaN、infinity、saturation 与 subnormal 规则；[[04-FP8、FP4与Microscaling格式]] 逐一展开 |
| MX | element code 与 shared block scale 构成的复合格式 | 不只是单个浮点 element format，还规定 block scaling 关系 |
| INT8 / INT4 | 等间距整数 code domain | 原生间距为 1；放入量化 Tensor 后的真实间距由外部 scale 决定 |

FP16 与 BF16 同为 16 bit，却体现了不同选择。FP16 用 10 个 fraction bits 换取更高的局部精度，但只有 5 个 exponent bits；BF16 保留与 FP32 相同宽度的 exponent field，动态范围接近 FP32，却只有 7 个显式 fraction bits。因此 BF16 常比 FP16 更不易发生 range overflow，却会更早丢失小的相对增量。“BF16 与 FP32 动态范围相同”是实用近似；两者最大有限值和最小 subnormal 并不完全相同，因为 fraction 宽度不同。

INT8/INT4 表中的范围只是存储码字范围，并不是被量化 Tensor 的真实数值范围。例如某个对称 INT8 张量若使用 scale $S=0.01$，其重建值可能是 $\hat{x}=S q$，相邻重建值相差 0.01；更换 scale 后，有效范围和绝对分辨率都会随之变化。因此比较 FP16 与“INT8”时，必须同时给出 INT8 的 mapping、scale 和 granularity。

## 5. 回到 0.1：用绝对误差、相对误差与 ULP 衡量结果

设数学目标为 $x$，格式中保存或计算得到的近似值为 $\hat x$，有符号误差为 $e=\hat x-x$。三个常用指标回答不同问题：

$$
\text{absolute error}=|\hat x-x|,
$$

$$
\text{relative error}=\frac{|\hat x-x|}{|x|},\qquad x\ne0,
$$

$$
\text{ULP error}=\frac{|\hat x-x|}{\operatorname{ulp}(x)}.
$$

绝对误差保留原始单位，适合判断误差是否超过业务容差；相对误差按目标值的量级归一化，但在 $x=0$ 时无定义、接近零时也可能失去解释力；ULP error 则判断结果离目标相差多少个局部码字间距。三者不是互相替代的“更高级指标”。例如 FP32 保存 `0.1` 的绝对误差约为 $1.49\times10^{-9}$、相对误差约为 $1.49\times10^{-8}$，而 ULP error 是 0.2。`10.5` 可以精确表示，所以三个误差都为零。

**ULP（unit in the last place）** 用来描述某一数值附近相邻浮点数的间距，但文献对边界点处的定义可能略有不同。对处于二项区间 $[2^k,2^{k+1})$ 的正规数，常用定义为

$$
\operatorname{ulp}(x)=2^{k-m}.
$$

所以 FP16 在 $[1,2)$ 内的间距为 $2^{-10}$，在 $[1024,2048)$ 内为 1，而从 2048 开始变为 2。浮点并不是“始终保留固定小数位”；相同的绝对增量可能在小数值处可见，在大数值处完全消失。

Machine epsilon $\epsilon=2^{-m}$ 是 1 附近向上的一个 ULP。对于 round-to-nearest，在不考虑 overflow、underflow 等边界的标准误差模型中，单次正规结果常写为

$$
\operatorname{fl}(x)=x(1+\delta),\qquad |\delta|\le u,
$$

其中 unit roundoff $u=2^{-p}=2^{-(m+1)}=\epsilon/2$。一些资料也把 machine epsilon 或 unit roundoff 都简称为 epsilon，因此阅读论文时必须先检查作者的定义。

这也解释了为什么同一个绝对增量会在不同量级上表现不同。FP16 在 $[1,2)$ 内的 ULP 是 $2^{-10}$；在 $[1024,2048)$ 内是 1；从 2048 开始则变为 2。整数 2049 恰处于 2048 与 2050 的中点，在 round-to-nearest, ties-to-even 下会舍入到 2048。

### 5.1 ULP 是局部间距，但在 binade 边界不一定左右对称

把 ULP 记成“当前数值附近相邻码字的距离”很有用，但还要补上方向。对不处在 $2^k$ 边界的 normal，前驱与后继通常属于同一个 binade，左右间距相同；对恰好位于幂次边界的数，左右两侧属于不同 binade，间距会相差 2 倍。

FP32 的 `1.0` 就是最简单的边界例子：

$$
\operatorname{succ}(1)=1+2^{-23},
$$

$$
\operatorname{pred}(1)=1-2^{-24}.
$$

因此不能笼统地说 `1.0` 的两个相邻数是 $1\pm2^{-23}$。本文公式 $\operatorname{ulp}(x)=2^{k-m}$ 采用 $x\in[2^k,2^{k+1})$ 的 binade 间距约定，所以 $\operatorname{ulp}(1)=2^{-23}$，描述向上进入 $[1,2)$ 后的间距。阅读论文或库文档时仍应检查它在幂次边界、subnormal 和 infinity 附近怎样定义 ULP。

`0.1` 不在 binade 边界，左右间距都是 $2^{-27}=7.450580596923828125\times10^{-9}$。FP32 保存值与数学真值的差为 $1.4901161193847657\times10^{-9}$，所以

$$
\text{ULP error}
=\frac{1.4901161193847657\times10^{-9}}
{7.450580596923828125\times10^{-9}}
\approx0.2.
$$

这也给出一个实用检查：若十进制近似把 $2^{-27}$ 写成约 $1.19\times10^{-8}$，后续 ULP error 就会整体算错；$1.19\times10^{-7}$ 实际上更接近 FP32 在 1 附近的 $2^{-23}$。

### 5.2 Correctly rounded、faithfully rounded 与若干 ULP 误差不是一回事

这三个术语分别描述不同强度的承诺：

| 承诺 | 结果必须满足什么 | 在 RNE 下的典型局部界 | 是否唯一决定结果 |
| --- | --- | --- | --- |
| Correctly rounded | 先求无限精度结果，再严格按指定 rounding mode 舍入 | nearest 模式通常不超过 $0.5$ ULP | 是；tie 也由规则决定 |
| Faithfully rounded | 精确结果可表示时返回它；否则返回包围精确结果的两个相邻浮点数之一 | 可能选到较远一侧，通常只保证小于一个局部间距 | 否；两个邻点都可能合格 |
| $n$-ULP accuracy | 实现结果与规定参考结果相差不超过 $n$ 个局部间距 | 由文档给出的 $n$ 决定 | 不一定 |

因此，“不超过 0.5 ULP、取最近值、tie-to-even”应称为 **RNE 下的 correctly rounded**，而不是 faithfully rounded。Faithful rounding 不是 IEEE 754 的另一个 rounding-direction attribute，也不要求一定选择最近邻。很多数学库又使用“相对 correctly rounded 结果最多相差若干 ULP”的接口指标；这个指标必须连同参考结果与测试/证明范围一起读取。

基础算术与复杂函数也要分开。指定目标格式和 rounding mode 后，符合 IEEE 754 要求的加、减、乘、除、平方根与 FMA 路径可以提供正确舍入语义；`sin`、`exp` 等库函数则要看具体库的误差合同，不能因为输入输出都是 FP32 就自动声称 correctly rounded。CUDA 当前文档就为许多数学函数分别给出 1、2 或更多 ULP 的上界，有些上界还来自广泛测试而不是穷尽证明。

用 FP32 计算 `0.1 + 0.2` 时还必须明确“真实结果”指哪一层：

| 比较层次 | 精确参考值 | FP32 输出 $0.30000001192092896$ 的误差 |
| --- | ---: | ---: |
| 十进制数学输入 $1/10+1/5$ | $0.3$ | $0.4$ ULP |
| 已存 FP32 输入的精确和 | $0.30000000447034836$ | $0.25$ ULP |

FP32 加法真正接收的是已经舍入的 `0.1f` 与 `0.2f`，所以判断这次加法是否 correctly rounded，应以第二行的精确和为基准；第一行则衡量“十进制输入表示误差 + 加法舍入误差”的总效果。把 $0.1+0.2$ 的数学真值写成 $0.3000000000000000444\ldots$，实际上混入了某种 binary64 输入或打印行为；在实数算术中 $1/10+1/5$ 就是精确的 $0.3$。

### 5.3 ULP 是单个结果的局部指标，MSE 是一组结果的总体指标

对 $N$ 个输出，MSE 与 RMSE 为

$$
\operatorname{MSE}=\frac{1}{N}\sum_{i=1}^{N}(\hat y_i-y_i)^2,
\qquad
\operatorname{RMSE}=\sqrt{\operatorname{MSE}}.
$$

所以 MSE $\le10^{-6}$ 对应 RMSE $\le10^{-3}$，不是 $3\times10^{-3}$。但这仍不能直接推出“无需正确或忠实舍入”，原因有三层：

1. ULP 的绝对大小依赖输出量级。FP32 在 1 附近半个 ULP 约为 $5.96\times10^{-8}$，在约 $2^{15}$ 附近半个 ULP 已约为 $1.95\times10^{-3}$；同一个 ULP 保证不能脱离数值范围换算成固定 MSE。
2. MSE 统计的是最终输出误差，而不是把每一步局部 rounding error 平方后取平均。100 次误差若同向传播，最终偏差可能接近误差之和；若近似独立且零均值，才可能按方差累积。计算图的条件数、reduction 顺序与非线性都会改变传播。
3. Correct rounding 只约束指定 operation 相对于其已表示输入的精确结果；它不能消除输入表示误差、模型近似误差或量化误差。反过来，不满足 correct rounding 的快速实现也可能在给定数据分布上满足最终 MSE。

因此，对“MSE 目标为 $10^{-6}$，是否需要 faithfully/correctly rounded”只能给出条件化结论：**单凭 MSE 阈值无法决定。** 应先固定输出的量级与 reference，明确 MSE 作用于单个算子、Tensor 还是端到端模型，再测量候选实现的最终误差。若已知每个最终输出都满足 $|\hat y_i-y_i|\le10^{-3}$，当然可推出 MSE $\le10^{-6}$；但“每个中间操作误差为 $10^{-4}$”不能推出同样结论。

## 6. 第二个具体问题：为什么 0.0004 的参数更新会消失

设参数为 $w=1.0$，一次更新为 $\Delta w=0.0004$，数学结果应为 $1.0004$。在不同格式中先表示操作数、执行加法并舍入到目标格式，会得到不同结果：

| 目标格式 | 1 附近的 ULP | $\Delta w$/ULP | 舍入后的 $w+\Delta w$ | 结论 |
| --- | ---: | ---: | ---: | --- |
| FP64 | $2^{-52}$ | 极大 | 约 $1.0004$ | 更新保留 |
| FP32 | $2^{-23}\approx1.1921\times10^{-7}$ | 约 3355 | $1.000399947\ldots$ | 更新保留，但仍有舍入 |
| FP16 | $2^{-10}\approx9.7656\times10^{-4}$ | $0.4096$ | $1.0$ | 小于半个 ULP，更新消失 |
| BF16 | $2^{-7}=0.0078125$ | $0.0512$ | $1.0$ | 更新消失得更早 |

这不是“低精度加法算错了”，而是 $1.0004$ 在 FP16/BF16 的局部 codebook 中更接近 1。训练中保留 FP32 master weight、采用 loss scaling、stochastic rounding 或更高精度 accumulator，都是在不同位置缓解类似的信息损失；它们的机制不能只用“位宽更高”概括。

### 6.1 舍入是 mapping，不是简单截断

一个高精度结果落在两个低精度码字之间时，必须由 rounding rule 选择结果。IEEE 754-2019 的 rounding-direction attributes 包括 roundTiesToEven、roundTiesToAway、roundTowardPositive、roundTowardNegative 与 roundTowardZero；具体硬件和 API 不一定动态暴露全部模式。最常用的 **round-to-nearest, ties-to-even（RNE）** 选择最近值，恰在中点时选择最低有效位为偶数的候选，从而避免总向同一方向处理 tie 所产生的系统偏差。

低精度 AI 还常见 stochastic rounding：根据目标值到两个邻近码字的距离，以相应概率选择上下候选。它不会让单次表示更准确，但在适当条件下可使舍入误差的期望接近零，因而可能减少许多小更新累积时的偏差。是否使用 stochastic rounding 是转换或算法的 mapping policy，不是 `BF16`、`FP8` 等格式名称天然保证的属性。

“从 FP32 转 BF16 就是截掉低 16 bit”只能描述 truncation 的某种位操作，不能代表通常期望的数值转换。NVIDIA CUDA 的常见 `float`/`double` 到 `__nv_bfloat16` 构造与转换默认使用 RNE。不同 API、编译选项或硬件路径还可能采用饱和、flush-to-zero 或其他规则，分析真实系统时必须核对具体 conversion instruction 与文档。

## 7. 把实验推到边界：overflow、underflow 与特殊值

`0.1` 和 `1.0004` 都位于普通 finite range 内。要区分 exponent bits 带来的 dynamic range 与 fraction bits 带来的 precision，可以把同一组格式继续测试在 $10^5$ 与 $10^{-8}$：FP16 的最大有限值只有 65504，所以 $10^5$ 会越过其范围；$10^{-8}$ 又小于 FP16 的最小 subnormal $2^{-24}\approx5.96\times10^{-8}$，在 RNE 下会变成零。BF16 与 FP32 拥有 8-bit exponent field，这两个值仍处于 normal range，但它们在局部能保留的有效位数不同。

### 7.1 Overflow、underflow 与 subnormal

**Overflow** 表示精确结果的绝对值超过目标格式所能覆盖的有限范围。结果可能变为同号 infinity、最大有限值或其他特殊码字，取决于格式、舍入模式和 conversion 的 saturation policy。对量化而言，clipping 到 codebook 边界与浮点算术 overflow 有相似的表象，但二者应在概念上区分：前者往往是方案主动规定的 mapping，后者是数值运算或格式转换越过表示范围。

**Underflow** 发生在结果极接近零的区域。若 exponent field 为零而 fraction 非零，IEEE 风格 subnormal 的值为

$$
x=(-1)^s\,2^{1-\mathrm{bias}}\frac{F}{2^m}.
$$

这里没有 hidden 1。Subnormal 在零与最小正规数之间提供等间距码字，使数值逐渐丢失有效位，这称为 gradual underflow。代价是相对精度不再保持：越靠近零，可用的有效位越少。最小 subnormal 再向零缩小时才完全变为零。

格式定义支持 subnormal，不代表所有硬件和执行模式都会保留它。某些路径使用 **flush-to-zero（FTZ）** 把 subnormal 输入或结果当作零，以换取更简单或更快的执行。Google Cloud TPU 文档明确指出其 BF16 conversion 会将 subnormal flush to zero；CUDA 的行为还可能受数据类型、目标架构和 `-ftz` 等编译选项影响。因此“理论最小非零值”和“某条 Kernel 数据路径中实际能保留的最小非零值”必须分别记录。

### 7.2 特殊值与符号零

IEEE 风格浮点通常包含 $+0$、$-0$、$+\infty$、$-\infty$ 和 NaN。符号零在普通相等比较中相等，但可能影响倒数、符号传播或复数分支等边界行为。Infinity 表示越界结果或数学极限；NaN 表示无效运算或缺失的有序数值，并可携带部分 payload。低位浮点为了把更多 bit pattern 留给有限数值，可能减少 NaN 编码或取消 infinity。例如 NVIDIA CUDA 的 E4M3 storage type 不支持 infinity，仅保留有限的 NaN 编码。由此可见，`E4M3` 只说明字段宽度仍不够；还必须知道具体格式变体及特殊值约定。

整数本身没有 NaN、infinity 或 subnormal。若模型格式希望表示这些状态，需要额外 sentinel、metadata 或上层约定。多数神经网络整数矩阵路径选择饱和或裁剪到有限整数范围，而不是传播 IEEE 特殊值。

## 8. 从单次存储到计算图：运算误差与表示误差不同

`0.1` 的误差在写入目标格式时已经产生，属于 representation error；`w+\Delta w` 还会在加法结果写回时产生 operation rounding。进入 reduction、dot product 和 GEMM 后，每一个中间结果都可能重复经历同样的投影，因此只检查输入能否表示还不够。

将实数或高精度数转换成某格式产生 **representation/rounding error**；在该格式上执行算术又会产生新的 operation rounding。即使每个输入都可精确表示，中间精确结果也可能需要再次舍入。浮点加法因此通常不满足结合律：

$$
\operatorname{fl}(\operatorname{fl}(a+b)+c)
\ne
\operatorname{fl}(a+\operatorname{fl}(b+c)).
$$

一个 FP16 的具体反例是 $a=2048,b=1,c=-2048$。因为 2049 位于 2048 与 2050 的中点，RNE 先算 $(a+b)$ 会得到 2048，随后加 $c$ 得到 0；若先算 $(b+c)=-2047$，再加 $a$ 则得到 1：

$$
\operatorname{fl}(\operatorname{fl}(2048+1)-2048)=0,
$$

$$
\operatorname{fl}(2048+\operatorname{fl}(1-2048))=1.
$$

这就是浮点加法不满足结合律的可计算实例。大数与小数相加时，小数可能小于当前 ULP 而完全消失；两个接近的大数相减则可能发生 cancellation，使结果中保留下来的有效数字很少。长 reduction、dot product 和 GEMM 会重复暴露这些问题。AI 硬件通常允许低精度输入在更高精度 accumulator 中累加，正是为了避免每次部分和都压回狭窄 codebook。不过，高精度累加不能恢复输入量化时已经丢失的信息，也不能自动消除求和次序造成的差异。

Fused multiply-add（FMA）计算 $a\times b+c$ 时只对最终结果做一次舍入，通常比先舍入乘法再舍入加法更准确。反过来，这也意味着启用 FMA、改变 reduction tree 或更换 Kernel 后，结果可能与逐操作实现不 bitwise identical。数值验证应依据任务设置合理误差指标，而不是默认不同实现必须逐 bit 相同。

## 9. 与量化体系的接口：element format 之后还有 Tensor mapping

浮点格式本身已经可以视为一个非均匀 codebook 和 encode/decode 规则，但现代 AI 中的“量化方案”通常还会在格式外增加 Tensor 级变换。例如先按 128 个元素分块，根据局部绝对最大值产生 scale，再把归一化值编码为 INT8 或 FP8。此时整体可表示集合由 element codebook 与 scale 共同决定；误差同时来自范围估计、clipping、scale 表示、element rounding 和后续计算。

因此，从本篇进入下一篇时应保留三组区别：第一，位宽不等于精度，precision 与 dynamic range 也不是同一维度；第二，storage range 不等于 Tensor 的真实值域，后者取决于 mapping 与 metadata；第三，格式支持某种数值不等于硬件数据路径必然保留或原生计算它。下一篇将用 codebook、mapping 与 distortion 把这些事实写成统一量化数学模型。

以 `0.1` 为例，原生 INT8 code domain 的相邻整数间距是 1，因而不能直接保存 0.1；但若量化方案定义 $S=0.01,Z=0$，则 code $q=10$ 可以重建为 $\hat x=S(q-Z)=0.1$。这不是“INT8 本身突然能表示小数”，而是 Tensor mapping 用 metadata 把整数 codebook 缩放到了新的实数坐标系。这个区别正是 [[02-量化的统一数学模型]] 的起点。

## 10. 最小可复现实验

下面的 NumPy 程序直接观察 `0.1` 的 stored value、局部 ULP 与 `1.0+0.0004`。它使用 NumPy 的 FP64/FP32/FP16 dtype；BF16 的 API 与硬件行为因框架而异，所以不在代码中用位截断伪装成通用 BF16 实现。

```python
import numpy as np


for dtype in [np.float64, np.float32, np.float16]:
    x = dtype(0.1)
    next_x = np.nextafter(x, dtype(np.inf), dtype=dtype)
    ulp = float(next_x - x)
    update = dtype(dtype(1.0) + dtype(0.0004))
    print(
        dtype.__name__,
        "stored_0.1=", format(float(x), ".20g"),
        "ulp=", format(ulp, ".20g"),
        "updated_1.0=", format(float(update), ".20g"),
    )
```

本文已在 Python 3.12.14、NumPy 2.3.5 上运行同等计算，观察到 FP32 更新结果约为 `1.0003999471664429`，FP16 更新结果为 `1.0`。实验验证的是具体软件 dtype 的转换结果；它不代表所有编译器选项、GPU instruction、FTZ 模式或低精度 Tensor Core 路径都具有完全相同的运行语义。

## 11. 小结：用同一组问题比较任何格式

遇到一个新格式时，不要从名称猜精度，而应依次问：一个 bit pattern 怎样解码；normal、subnormal、zero、infinity 与 NaN 如何分配；当前数值附近的 ULP 是多少；采用什么 rounding；运算在哪里累加；格式定义与目标硬件的数据路径是否一致。`0.1` 检查有限表示和单次舍入，`1.0+0.0004` 检查局部 precision，$10^5$ 与 $10^{-8}$ 检查 range，FP16 的 $(2048+1)-2048$ 检查运算次序。四个小实验共同构成后续比较量化格式的数值基线。

## 12. 自检问题

1. 为什么 BF16 与 FP16 同为 16 bit，BF16 更不容易发生 overflow，却更容易丢失小的参数更新？
2. FP16 在 $[1,2)$、$[1024,2048)$ 和 $[2048,4096)$ 内的 ULP 分别是多少？这会怎样影响大数加小数？
3. “INT8 的精度是 1”与“某个 INT8 量化张量的分辨率是 0.01”为何可以同时成立？
4. 高精度 accumulator 能解决哪些误差，不能解决哪些误差？
5. FP32 保存 `0.1` 的误差为什么约为 0.2 ULP，而不是超过 0.5 ULP？
6. 为什么只知道 `E4M3` 仍不足以判断 infinity、NaN、overflow 和 subnormal 行为？
7. 为什么 `INT8` 本身不能表示 0.1，而 `S=0.01` 的 INT8 量化 Tensor 可以精确重建 0.1？
8. Faithfully rounded 为什么不等于 RNE 下的 correctly rounded？哪一种允许返回较远的相邻值？
9. 为什么“每个中间操作误差不超过 $10^{-4}$”不能直接证明最终 Tensor 的 MSE 不超过 $10^{-6}$？

## 13. 来源与适用边界

- [IEEE SA, IEEE 754-2019](https://standards.ieee.org/ieee/754/6210/)：截至 2026-09-15，IEEE SA 将其列为 active standard；页面说明其覆盖 binary/decimal formats、运算方法、异常条件与默认处理。IEEE 已启动 P754 修订项目，因此未来引用应继续核对标准状态。
- [NVIDIA CUDA Programming Guide：Floating-Point Computation](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html)：用于核对当前 CUDA 文档中的 IEEE binary16/32/64/128、BF16 的非 IEEE 身份、range/epsilon 表、subnormal、FMA 以及 CUDA 的 IEEE 754-2019 限制。厂商实现说明不能替代 IEEE 规范本身。
- Siegfried M. Rump, Takeshi Ogita, Shin'ichi Oishi, [Accurate Floating-Point Summation Part I: Faithful Rounding](https://epubs.siam.org/doi/10.1137/050645671), SIAM Journal on Scientific Computing, 2008：用于区分 faithful rounding 与 rounding to nearest；前者返回包围精确结果的相邻浮点数之一，不等同于 $0.5$ ULP 的正确舍入承诺。
- [NVIDIA CUDA Programming Guide：Mathematical Function Accuracy](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html)：用于说明库函数常按相对 correctly rounded reference 的 maximum ULP error 分别给出合同，且部分界来自广泛但非穷尽测试；不能从 FP32 dtype 本身推导 `sin`、`exp` 等函数都正确舍入。
- [NVIDIA CUDA Programming Guide：Alternate Floating Point](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#alternate-floating-point)：用于区分 BF16 与 TF32；尤其是 TF32 的内部 layout 为 implementation-defined，并以 FP32 element 承载 Tensor Core 输入。
- [NVIDIA CUDA Math API：`__half`](https://docs.nvidia.com/cuda/cuda-math-api/cuda_math_api/struct____half.html)：binary16 的字段宽度、有效精度和默认转换舍入。
- [NVIDIA CUDA Math API：`__nv_bfloat16`](https://docs.nvidia.com/cuda/cuda-math-api/cuda_math_api/struct____nv__bfloat16.html)：NVIDIA BF16 的字段宽度、有效精度及默认 RNE 转换。
- [Oracle Numerical Computation Guide](https://docs.oracle.com/cd/E19957-01/802-5692/802-5692.pdf)：normal/subnormal、ULP、gradual underflow 与 IEEE 二进制格式的数值背景。
- [Google Cloud TPU：bfloat16](https://docs.cloud.google.com/tpu/docs/bfloat16)：Cloud TPU BF16 数据路径及 subnormal flush-to-zero 行为；该实现事实不能外推到所有 BF16 硬件。
- [NVIDIA CUDA Math API：FP8 E4M3](https://docs.nvidia.com/cuda/cuda-math-api/cuda_math_api/struct____nv__fp8x4__e4m3.html)：用于说明字段名称不足以决定特殊值语义，以及 NVIDIA E4M3 类型的有限值饱和行为。

本文 `0.1`、`0.2` 与 `0.3` 表中的误差和 ULP 由精确有理数差值计算，并用 Python 3.12.14、NumPy 2.3.5 复核 FP64/FP32/FP16 的存储与更新结果。BF16 数值按 S1E8M7、RNE 计算，没有把某一厂商的 FTZ 或算术路径外推成通用语义。MSE 小节给出解析边界，没有把局部误差假设冒充实际模型测量；FP8、FP4 和 MX 的精确 codebook、特殊值、scale 与 block 规则将在格式专项中按具体规范分别定义。
