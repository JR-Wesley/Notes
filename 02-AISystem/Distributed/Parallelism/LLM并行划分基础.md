# 加速比

在大模型训练中，使用多卡分布式并行（Multi-GPU Distributed Parallelism）进行扩展时，“加速比”（Speedup）是用来衡量系统**计算效率和可扩展性**的核心指标。它反映了随着计算资源（如 GPU 数量）的增加，任务完成速度提升的程度。

---

## 一、加速比的定义

**加速比（Speedup）** 是指：

> 使用 N 张 GPU 并行训练时，相对于使用 1 张 GPU 训练所获得的速度提升倍数。

数学上定义为：

$$
\text{Speedup}(N) = \frac{T(1)}{T(N)}
$$

其中：

- $ T(1) $：使用 **1 张 GPU** 完成一次训练任务所需的时间（例如处理完一个 epoch 或一定量数据所需的秒数）。
- $ T(N) $：使用 **N 张 GPU** 并行完成相同任务所需的时间。

理想情况下，如果完全线性加速，则有：

$$
\text{Speedup}(N) = N
$$

即：8 卡训练是单卡的 8 倍快。

但现实中由于通信开销、负载不均、I/O 瓶颈等原因，通常：

$$
\text{Speedup}(N) < N
$$

---

## 二、实际应用中的衡量方式

在大模型训练中，我们通常不会测量整个训练周期，而是基于**吞吐量（throughput）**来间接计算加速比。

1. **以吞吐量为基础计算有效加速比**

   定义：

   $$
   \text{Throughput}(N) = \frac{\text{Processed Samples or Tokens}}{\text{Time (seconds)}}
   $$

   则相对加速比为：

   $$
   \text{Speedup}(N) = \frac{\text{Throughput}(N)}{\text{Throughput}(1)}
   $$

   > 例如：单卡每秒处理 100 tokens，8 卡并行每秒处理 720 tokens，则加速比为 7.2x。

2. **归一化到理想情况：效率（Efficiency）**

   为进一步评估并行效率，引入“**加速效率**”：

   $$
   \text{Efficiency}(N) = \frac{\text{Speedup}(N)}{N} \times 100\%
   $$

   - 理想值为 100%
   - 实际中 >90% 表示优秀，<70% 可能存在严重瓶颈

---

## 三、影响加速比的关键因素

| 因素 | 对加速比的影响 |
|------|----------------|
| **通信开销**（AllReduce, AllGather 等） | 多卡间梯度同步耗时越长，加速比越低，尤其在小批量或高带宽需求场景 |
| **并行策略**（DP, TP, PP, SP, FSDP 等） | 不同策略通信模式不同，影响扩展性。如纯数据并行适合小模型，而 TP+PP 组合更适合大模型 |
| **硬件互联**（NVLink, InfiniBand） | 高速互联可显著降低通信延迟，提高加速比 |
| **负载均衡** | 若流水线或张量切分不均，某些卡空闲等待，导致加速比下降 |
| **I/O 与数据加载** | 数据预处理慢会导致 GPU 等待，限制整体速度提升 |
| **批大小（Batch Size）** | 小 batch 下通信占比高，加速比差；增大 batch 可改善 |

---

## 四、举例说明

假设训练一个 LLM：

| GPU 数量 | 单位时间处理 token 数 | 加速比 | 理想加速比 | 效率 |
|---------|------------------------|--------|------------|------|
| 1       | 100k                   | 1.0    | 1.0        | 100% |
| 2       | 190k                   | 1.9    | 2.0        | 95%  |
| 4       | 360k                   | 3.6    | 4.0        | 90%  |
| 8       | 650k                   | 6.5    | 8.0        | 81.25% |

可以看到，随着 GPU 数量增加，虽然绝对速度上升，但**加速效率逐渐下降**，这是分布式训练的典型现象。

---

## 五、总结

✅ **加速比的本质**：衡量并行系统的**时间收益**，反映资源投入是否“物有所值”。

✅ **目标**：尽可能接近线性加速（Speedup ≈ N），保持高效率。

✅ **优化方向**：

- 选择合适的并行策略（如 Zero-DP + TP + PP）
- 优化通信（梯度累积、混合精度、通信重叠）
- 提升数据 pipeline 效率
- 使用高性能网络（如 RDMA、NVLink）

## 1. 矩阵运算基础

LLM 中线性层、Attention 等核心计算本质是矩阵乘法（C=A×B），无论输入是 2 维还是多维矩阵，都需满足两个关键规则，否则无法计算：

1. **2 维矩阵的“匹配规则”**：
   若 A 是 [M, N]（M 行、N 列），B 的**第一维度必须等于 A 的第二维度 N**（即 B 为 [N, K]），最终结果 C 的尺寸固定为 [M, K]。这是矩阵乘法的数学本质，也是并行切分的“不可破规则”。
   
2. **多维矩阵的“降维规则”**：
   当输入是 3 维及以上矩阵（如 LLM 中带批量、多头维度的张量）时，计算会先“降维”为二维矩阵乘法：
   - 只看**倒数第 2 维和倒数第 1 维**（这两维必须满足上述 2 维匹配规则）；
   - 除最后两维外，其他维度需“对齐”（要么尺寸相等，要么通过“广播”补成相等尺寸），相当于按这些维度做“批量计算”。

   比如例子中 A 是 [10, 3, 2]（可理解为 10 个批量、每个批量是 [3,2] 的矩阵），B 是 [2,4]（2 维）：

   - 先通过“广播”把 B 补成 [10, 2, 4]（和 A 的非最后两维对齐）；
   - 再按批量逐个计算：每个 [3,2] 的 A 子矩阵 × [2,4] 的 B 子矩阵，得到 [3,4] 的结果；
   - 最终合并所有批量，得到 [10, 3, 4] 的 C，本质是“批量二维矩阵乘法”。

## 2. 二维矩阵切分（并行运算的实现方式）

为了在多 GPU 上并行计算，需要将大矩阵“切分”到不同设备，核心是基于上述维度约束做“拆分 - 计算 - 合并”，文中以“二分切分”（可扩展到多份切分）为例，后续会基于这些场景衍生出 TP（张量并行）、SP（序列并行）等优化方案。

并行优化的底层是矩阵运算的拆分。文章详细分析了四种基本的二维矩阵二分切分场景及其通信和显存特点：这四个场景本质是 **LLM 推理并行优化中，通过矩阵切分实现多设备负载分摊的核心方案**，核心逻辑围绕“切分矩阵减少单设备计算量/显存占用，再通过集群通信恢复完整结果”，所有场景均基于线性运算的核心公式 **C = A × B**（A 维度 `[M, N]`；B 维度 `[N, K]`；C 维度 `[M,K]`；一般来说 A 为激活值，B 为权重），切分需满足“矩阵乘法维度匹配”，且最终通过通信操作（如 allgather/allreduce）保证结果与原始计算一致。

在 LLM 推理并行优化中，矩阵切分是适配多 GPU 硬件、降低计算/显存压力的核心手段。以下从**切分对象、操作逻辑、关键特点、通信需求、显存变化、典型应用**六个维度，对文中四种矩阵切分场景进行结构化梳理，同时明确各场景的适用边界与技术细节。

### 场景一：B 矩阵列切（Column Split on Matrix B）

![[file-20251105121317832.png]]

- **核心对象**：仅对矩阵乘法中的**权重矩阵 B**进行切分。
- **切分方式**：沿 B 的**列维度（axis=1）** 二分（或多等分），得到子矩阵 `B₁、B₂...Bₖ`，每个子矩阵维度为 `[N, K/num_splits]`（num_splits 为切分块数，文中以 2 为例）。
- **计算逻辑**：
  1. 每个 GPU 持有完整的 A 矩阵和 1 个 B 的子矩阵（如 GPU0 持 A+B₁，GPU1 持 A+B₂）；
  2. 各 GPU 并行计算局部乘积 `Cᵢ = A × Bᵢ`（局部结果维度 `[M, K/num_splits]`）；
  3. 通过**列维度拼接（concatenate(axis=1)）** 合并所有局部结果 `C₁、C₂...`，得到完整矩阵 C（维度 `[M, K]`），等价于原生 `A×B` 计算结果。
- 关键特点

| 维度            | 具体说明                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **计算量**       | 单 GPU 计算量为原生计算的 `1/num_splits`（如二分后单 GPU 计算量减半），总计算量不变（并行分摊）。                                                                                                                        |
| **通信需求**      | 需 1 次**allgather 集群通信**（收集所有 GPU 的局部 $C_i$，沿列拼接），通信量与局部结果尺寸正相关。                                                                                                                       |
| **显存变化（非原地）** | 显存变化量为 `(-N×K/num_splits + M×K/num_splits) × 元素字节数`：<br>- 节省：B 矩阵存储减少 `N×K×(num_splits-1)/num_splits`；<br>- 新增：局部结果 Cᵢ存储 `M×K/num_splits`；<br>- 最终显存变化取决于 `M` 与 `N` 的大小关系（如 M=N 时显存无净变化）。 |
| **适用场景**      | 输入激活值 A（如 token 嵌入）尺寸较小、权重矩阵 B 尺寸过大（如 LLM 中千亿参数权重），将大权重矩阵 B 按列拆分到多 GPU。                                                                                                                   |

### 场景二：A 矩阵行切（Row Split on Matrix A）

![[file-20251105121721314.png]]

- **核心对象**：仅对矩阵乘法中的**输入激活值矩阵 A**（维度 `[M, N]`）进行切分，B 为完整权重矩阵（维度 `[N, K]`）。
- **切分方式**：沿 A 的**行维度（axis=0）** 二分（或多等分），得到子矩阵 `A₁、A₂...Aₖ`，每个子矩阵维度为 `[M/num_splits, N]`。
- **计算逻辑**：
  1. 每个 GPU 持有 1 个 A 的子矩阵和完整的 B 矩阵（如 GPU0 持 $A_1+B$，GPU1 持 $A_2+B$）；
  2. 各 GPU 并行计算局部乘积 `Cᵢ = Aᵢ × B`（局部结果维度 `[M/num_splits, K]`）；
  3. 通过**行维度拼接（concatenate(axis=0)）** 合并所有局部结果 `C₁、C₂...`，得到完整矩阵 C（维度 `[M, K]`），等价于原生 `A×B`。
- 关键特点

| 维度            | 具体说明                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **计算量**       | 单 GPU 计算量为原生计算的 `1/num_splits`（如二分后减半），总计算量不变（并行分摊）。                                                                                                                            |
| **通信需求**      | 需 1 次**allgather 集群通信**（收集所有 GPU 的局部 Cᵢ，沿行拼接），通信量与局部结果尺寸正相关。                                                                                                                    |
| **显存变化（非原地）** | 显存变化量为 `(K - N) × M/(2×num_splits) × 元素字节数`（以二分为例）：<br>- 节省：A 矩阵存储减少 `M×N×(num_splits-1)/num_splits`；<br>- 新增：局部结果 Cᵢ存储 `M×K/num_splits`；<br>- 当 `K > N` 时显存占用增加，`K < N` 时显存节省。 |
| **适用场景**      | LLM 推理中**输入激活值 A 尺寸过大**的场景（如长序列 prefill 阶段，A 的行维度对应序列长度），将 A 按行拆分到多 GPU，同时利用“延迟 allgather”优化后续运算的通信效率，例如激活值序列切分 `[sequence/SP, hidden_dim]`（SP 为序列并行度）。                         |
| **独特优势**      | 若后续存在**线性运算（如 A×B×E×F）或元素行运算（如 LayerNorm、Softmax）**，可将 allgather 步骤延迟到所有运算结束后执行，仅需 1 次拼接（减少通信次数）。                                                                               |

如： A[M/2, N]  x B x E x F ...  -> allgather 与原计算得到结果一致。这就是常见的激活值进行序列切分的场景：[sequence/sp, hidden_dim] 。

Note: 这里有个值得注意的是，仅切分一个矩阵的方式，适合任何线性运算，但不一定能够带来性能/存储空间的收益。

### 场景三：A 矩阵列切 + B 矩阵行切（Column Split on A + Row Split on B）

![[file-20251105121733088.png]]

- **核心对象**：同时对输入矩阵 A（维度 `[M, N]`）和权重矩阵 B（维度 `[N, K]`）进行切分。
- **切分方式**：
  - A 沿**列维度（axis=1）** 二分，得到子矩阵 `A₁、A₂`（维度 `[M, N/2]`）；
  - B 沿**行维度（axis=0）** 二分，得到子矩阵 `B₁、B₂`（维度 `[N/2, K]`）；
  - 切分后 A 的子矩阵列数 = B 的子矩阵行数（保证局部乘法维度匹配）。
- **计算逻辑**：
  1. GPU0 持有 $A_1+B_1$，GPU1 持有 $A_2+B_2$；
  2. 各 GPU 并行计算局部乘积 `C₁ = A₁×B₁`（维度 `[M, K]`）、`C₂ = A₂×B₂`（维度 `[M, K]`）；
  3. 通过**元素级求和（sum）** 合并局部结果 `C₁ + C₂`，得到完整矩阵 C（维度 `[M, K]`），等价于原生 `A×B`。
- 关键特点

| 维度            | 具体说明                                                                                                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **计算量**       | 单 GPU 计算量为原生计算的 `1/num_splits`（如二分为例，单 GPU 计算量减半），总计算量不变。                                                                                                                               |
| **通信需求**      | 需 1 次**allreduce 集群通信**（所有 GPU 的局部 Cᵢ进行元素级求和，而非拼接），通信量与完整 C 矩阵尺寸一致（高于场景一/二的 allgather）。                                                                                                 |
| **显存变化（非原地）** | 显存占用显著降低：<br>- A 矩阵存储减少 `M×N×(num_splits-1)/num_splits`；<br>- B 矩阵存储减少 `N×K×(num_splits-1)/num_splits`；<br>- 局部结果 Cᵢ尺寸与完整 C 一致，但仅需临时存储 1 份（求和后可释放）；<br>- 输入与权重存储均减半（二分时），显存优化效果优于场景一/二。 |
| **结果等价性**     | 局部结果需求和后才与原生 `A×B` 一致，单独局部结果无意义（区别于场景一/二的“局部结果可独立拼接”）。                                                                                                                                  |
| **局限性**       | allreduce 通信量较大（需传递完整 C 矩阵数据），且适用场景狭窄（文中明确“使用场景并不多”），更多作为场景四的基础。                                                                                                                        |
| **适用场景**      | 仅适用于**A 和 B 均为超大尺寸**（无法单独在单 GPU 存储），且对显存优化需求极高的场景，但因通信成本高，实际中较少直接使用，更多作为多矩阵链式乘法（如 A×B×C）切分的基础。                                                                                          |

### 场景四：B 矩阵列切 + C 矩阵行切（Column Split on B + Row Split on C）

![[file-20251105121744041.png]]

- **核心场景**：针对**多矩阵链式乘法**（如 `D = A × B × C`，A 维度 `[M, N]`，B 维度 `[N, P]`，C 维度 `[P, K]`），需对中间权重矩阵 B 和后续矩阵 C 进行协同切分。
- **切分方式**：
  - B 沿**列维度（axis=1）** 二分，得到子矩阵 `B₁、B₂`（维度 `[N, P/2]`）；
  - C 沿**行维度（axis=0）** 二分，得到子矩阵 `C₁、C₂`（维度 `[P/2, K]`）；
  - 切分后 B 的子矩阵列数 = C 的子矩阵行数（保证 `Bᵢ×Cᵢ` 维度匹配）。
- **计算逻辑**：
  1. GPU0 持有 A+B₁+C₁，GPU1 持有 A+B₂+C₂；
  2. 各 GPU 并行计算链式局部乘积 `Dᵢ = (A × Bᵢ) × Cᵢ`（维度 `[M, K]`）；
  3. 通过**元素级求和（sum）** 合并局部结果 `D₁ + D₂`，得到完整矩阵 D（维度 `[M, K]`），等价于原生 `A×B×C`。
- 关键特点

| 维度                | 具体说明                                                                 |
|---------------------|--------------------------------------------------------------------------|
| **计算量**          | 单 GPU 计算量为原生计算的 `1/num_splits`（二分时减半），总计算量不变（并行分摊链式乘法）。     |
| **通信需求**        | 需 1 次**allreduce 集群通信**（求和局部 Dᵢ），通信量与完整 D 矩阵尺寸一致（与场景三相同）。       |
| **核心优势**        | **中间值存储减半**：<br>- 原生链式乘法需存储中间矩阵 `E = A×B`（维度 `[M, P]`）；<br>- 切分后仅需存储局部中间矩阵 `Eᵢ = A×Bᵢ`（维度 `[M, P/2]`），中间值存储量减少 `1/num_splits`（二分时减半），是场景三的核心优化点。 |
| **显存变化**        | 继承场景三“输入（A）完整存储，B 和 C 存储减半”的优势，同时减少中间值存储，显存优化效果最优。   |
| **适用场景**        | LLM 推理中**多线性层链式计算**的场景（如 Transformer 的 FFN 层：激活值×W₁×W₂），通过协同切分 B 和 C，在降低显存占用的同时避免中间值膨胀。 |

### 四种场景的核心差异对比表

| 场景        | 切分对象       | 子矩阵维度                | 关键通信操作 | 核心价值                          | 典型应用场景                  |
|-------------|----------------|---------------------------|--------------|-----------------------------------|-------------------------------|
| 场景一：B 列切 | B 矩阵（权重）  | B1/B2：[N, K/2]           | allgather（列拼接） | 拆分权重存储，适配“激活值完整、权重过大”场景 | A=输入激活值、B=模型权重，双 GPU 分摊权重计算 |
| 场景二：A 行切 | A 矩阵（激活值）| A1/A2：[M/2, N]           | allgather（行拼接） | 拆分激活值，后续线性运算可延迟拼接（减少通信次数） | A=序列激活值（[seq_len, hidden_dim]），按序列切分（SP） |
| 场景三：A 列切 +B 行切 | A（激活值）+B（权重） | A：[M, N/2]；B：[N/2, K] | allreduce（元素求和） | 同时拆分激活值与权重，显存占用更低 | 单步矩阵乘法中“激活值 + 权重均过大”场景（较少用） |
| 场景四：B 列切 +C 行切 | 多矩阵链式计算（A×B×C） | B：[N, K/2]；C：[K/2, L] | 无额外新增通信（复用中间切分） | 减少链式计算的中间结果存储（核心优化点） | 模型中多线性层串联（如 FFN 层），降低中间激活值显存占用 |

四种矩阵切分场景的设计核心是**“计算并行化”与“显存优化”的平衡**，需根据 LLM 推理的具体需求（如激活值尺寸、权重大小、计算链路长度）选择：

1. 单矩阵乘法且仅权重过大 → 场景一（B 列切）；
2. 单矩阵乘法且仅激活值过大 → 场景二（A 行切）；
3. 单矩阵乘法且 A+B 均超大 → 场景三（A 列切 +B 行切）；
4. 多矩阵链式乘法（如 FFN 层） → 场景四（B 列切 +C 行切，最优选择）。

实际应用中，这些场景常与 TP（张量并行）、SP（序列并行）等并行策略结合（如文中提到的“SP-TP-SP”组合），进一步提升 LLM 推理的效率与扩展性。

# 线性层的并行策略

线性层是 LLM（大语言模型）的核心组件（如 Transformer 的 FFN 层、Attention 投影层），其并行计算围绕 “**降低单设备计算 / 显存压力**”“**适配多 GPU / 多节点硬件**” 展开，主要分为**层内并行**、**层间并行**、**冗余参数消除**三大方向，覆盖数据并行（DP）、序列并行（SP）、张量并行（TP）、流水线并行（PP）、Zero 冗余消除等关键技术。

## 一、层内并行：单线性层的多设备拆分计算

层内并行针对**单个线性层**（如 `Y = X·W + b`，`X` 为输入激活值，`W` 为权重），通过切分输入激活值的不同维度，匹配不同并行策略，核心是“**切分维度决定并行类型**”，且需保证切分后矩阵乘法的维度一致性。

- ​**​层内并行​**​：
    - ​**​数据并行（DP）​**​：切分 batch 维度，权重无需切分。
    - ​**​序列并行（SP）​**​：切分序列维度，不影响 LayerNorm 等运算。
    - ​**​张量并行（TP）​**​：切分隐藏层维度，权重需对应切分。
    - ​**​组合优化​**​：SP 与 TP 结合（如 Megatron 中的 MLP 层），通过将 AllReduce 拆分为 ReduceScatter 和 AllGather，并调整计算顺序，降低显存和通信开销。

可根据输入激活值的切分维度对应不同并行策略，一般切 batch 为 DP、切序列为 SP、切隐藏层尺寸为 TP。

![[file-20251105132737129.png]]

### 1. 核心并行策略：按激活值切分维度分类

线性层输入激活值 `X` 的典型维度为 `[batch_size, seq_len, hidden_dim]`（batch：样本批量，seq_len：序列长度，hidden_dim：隐藏层维度），不同切分维度对应不同并行策略：

| 并行策略 | 切分维度       | 核心操作逻辑                                                                 | 关键特点                                                                 |
|----------|----------------|------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| **数据并行（DP）** | 切分 `batch_size`（批量维度） | - 切分方式：将 `X` 按 batch 拆分为 `X₁, X₂,...Xₖ`（如 `[batch/k, seq_len, hidden_dim]`）；<br>- 权重处理：所有设备持有**完整权重 `W`**（无需切分）；<br>- 计算逻辑：各设备并行计算 `Yᵢ = Xᵢ·W + b`，最终无需合并（或仅合并 loss，推理时直接输出各设备结果）。 | - 优势：不改变矩阵乘法形态（`Xᵢ` 与 `W` 维度匹配），实现简单，无额外通信（推理场景）；<br>- 局限：权重 `W` 在所有设备冗余存储（显存占用高），仅降低计算量，不降低权重存储压力。 |
| **序列并行（SP）** | 切分 `seq_len`（序列维度）   | - 切分方式：将 `X` 按序列长度拆分为 `X₁, X₂,...Xₖ`（如 `[batch, seq_len/k, hidden_dim]`）；<br>- 权重处理：所有设备持有**完整权重 `W`**（无需切分）；<br>- 计算逻辑：各设备并行计算 `Yᵢ = Xᵢ·W + b`，若后续有元素级运算（如 LayerNorm、Softmax），可延迟合并，最终通过 `allgather` 拼接 `Yᵢ` 得到完整 `Y`。 | - 优势：不影响元素级运算（LayerNorm/Softmax 依赖 `hidden_dim` 维度，与 `seq_len` 无关），可延迟通信（减少通信次数）；<br>- 局限：仅优化 `seq_len` 过大导致的激活值存储压力，权重仍冗余存储。 |
| **张量并行（TP）** | 切分 `hidden_dim`（隐藏层维度） | - 切分方式：将 `X` 按 hidden_dim 拆分为 `X₁, X₂,...Xₖ`（如 `[batch, seq_len, hidden_dim/k]`）；<br>- 权重处理：**必须对应切分权重 `W`**（按列切分 `W` 为 `W₁, W₂,...Wₖ`，如 `[hidden_dim/k, hidden_dim]`，保证 `Xᵢ·Wᵢ` 维度匹配）；<br>- 计算逻辑：各设备并行计算 `Yᵢ = Xᵢ·Wᵢ`，最终通过 `allgather`（或 `allreduce`）合并 `Yᵢ` 得到完整 `Y`。 | - 优势：同时降低激活值（`X` 拆分）和权重（`W` 拆分）的存储压力；<br>- 局限：需严格匹配 `X` 与 `W` 的切分维度（如 `X` 切 `hidden_dim`，`W` 必须切对应维度），增加权重管理复杂度。 |

总结而言：

- DP 可以看成批量矩阵乘法，不会改变二维矩阵的乘法形态，所以对应的权重不需要变化。
- SP 切分不会影响最后一维的计算，如：LayerNorm，softmax
- TP 切分激活值后，权重必须做对应的切分。

DP 与 SP/TP 可以解耦独立使用，SP 与 TP 一般可以配合使用 (在当前推理应用中一般设计成：$DP*TP=world_size，SP=DP$)。

### 2. 策略组合与通信优化

又因为：

1. allreduce 是可以被拆分为 ReduceScatter 和 AllGather 两个步骤
2. SP 不影响元素操作的运算，如 LayerNorm，softmax

所以在上面矩阵运算场景四的基础上，对于最后的集群通信操作有如下改进，将 allreduce 运算进行拆分，变为两个步骤。并且将 allgather 操作移动到 softmax 计算后：

![[file-20251105125811248.png]]

层内并行并非单一策略使用，而是通过“**策略组合**”和“**通信拆分**”进一步提升效率，核心优化围绕“**减少通信量**”“**掩盖通信延迟**”展开：

#### （1）策略组合规则

- **DP 与 SP/TP 解耦**：DP 切分 batch，SP/TP 切分激活值的 seq_len/hidden_dim，二者可独立组合（如“DP=2，TP=4”，总设备数=2×4=8）；
- **SP 与 TP 协同**：当前推理场景中常设计为“`DP×TP = world_size`（总设备数），`SP=DP`”，例如 8 设备时，DP=2、TP=4、SP=2，既优化 batch/seq_len/hidden_dim 三个维度，又平衡各设备负载。

#### （2）通信优化：allreduce 拆分与延迟 Allgather

基于“矩阵运算场景四（B 列切 +C 行切）”的思路，对层内并行的通信操作做关键改进：

- **核心原理**：
  1. `allreduce`（元素级求和）可拆分为 `ReduceScatter`（先分散求和）+ `AllGather`（再拼接）两步，减少单次通信的数据量；
  2. SP 不影响元素级运算（LayerNorm/Softmax），可将 `AllGather`（合并激活值）延迟到元素级运算后执行，避免运算前合并导致的激活值膨胀。
- **优化效果**：
  - 元素级运算的输入数据量减半（如 LayerNorm 输入从 `[batch, seq_len, hidden_dim]` 变为 `[batch, seq_len/k, hidden_dim]`）；
  - 减少激活值中间存储（仅存切分后的小尺寸激活值），同时降低通信量（拆分 `allreduce` 后单次通信数据量减少 `1/k`）。

#### （3）典型应用：Megatron 的 SP-TP-SP 组合

在 Transformer 的 MLP 层（线性层 + 激活函数 + 线性层）中，采用“**SP→TP→SP**”的组合策略：

1. 第一步 SP：切分输入激活值的 `seq_len`，执行第一层线性层计算；
2. 第二步 TP：切分激活值的 `hidden_dim`，执行激活函数（如 GeLU）和第二层线性层计算；
3. 第三步 SP：合并激活值，完成 MLP 层输出。
该组合充分利用 SP 对元素级运算的兼容性和 TP 对权重的拆分能力，平衡计算与通信效率。

![[file-20251105133417043.png]]

### 3. 层内并行适用场景

- DP：适合 `batch_size` 大（如批量推理）、`hidden_dim`/`seq_len` 较小的场景，优先降低计算压力；
- SP：适合 `seq_len` 大（如长文本推理的 prefill 阶段）的场景，优化激活值存储；
- TP：适合 `hidden_dim` 大（如千亿参数模型的 `hidden_dim` 达 4096/8192）的场景，同时降低激活值与权重存储压力；
- 组合策略：LLM 推理中主流选择（如 DP+TP+SP），适配“大 batch+ 长序列 + 高 hidden_dim”的复杂场景。

## 二、层间并行：多线性层的设备流水线调度

层间并行针对**多个线性层构成的模型块**（如 Transformer 的“Attention 层 +FFN 层”组成的 Block），将不同层分散到不同设备，通过“**激活值流水线传递**”实现并行，核心是“**按层分配设备，用流水线掩盖层间等待时间**”。

- ​**​层间并行（流水线并行 PP）​**​：将模型层分散到不同 GPU，流水线执行。推理时可异构部署（在推理中，由于特殊计算场景，比如 FFN 为稀疏的 MoE 结构时，往往 attention 与 FFN 对算力需求不同，层间并行可以变为异构模式, 如 AFD，attention 层与 MoE 分离部署到不同设备上， Attention 层与 MoE-FFN 分离）。

![[file-20251105125832954.png]]

### 1. 基础技术：流水线并行（PP）

#### （1）核心操作逻辑

- 层分配：将模型的 `L` 个层（或 Block）拆分为 `k` 段，分配给 `k` 个设备（如设备 0 负责层 1-5，设备 1 负责层 6-10）；
- 流水线调度：激活值按“生产 - 消费”模式传递——设备 0 计算完层 1-5 的激活值后，传递给设备 1 计算层 6-10，同时设备 0 开始处理下一批激活值；
- 典型参考：基于 Megatron-2 论文的 PP 实现，通过“微批次（micro-batch）”进一步提升流水线利用率（避免设备空闲）。

#### （2）关键特点

- 优势：降低单设备的层数量（如 100 层模型拆分为 10 个设备，每设备仅 10 层），大幅减少单设备的权重存储压力；
- 局限：存在“**流水线气泡**”（初始阶段部分设备等待激活值，收尾阶段部分设备提前空闲），且激活值传递需额外通信（层间数据传输）。

### 2. 推理特化优化：异构层间并行（AFD）

LLM 推理中存在“**计算异构场景**”——不同层的算力需求差异显著（如 Attention 层算力需求低，稀疏 MoE-FFN 层算力需求高），传统 PP 的“均匀层分配”会导致设备负载不均衡，因此衍生出**异构层间并行**（如 AFD 架构）：

#### （1）核心操作逻辑

- 层分类：将模型层按算力需求分为“轻量层”（如 Attention 层、线性投影层）和“重量层”（如稀疏 MoE-FFN 层，含多个专家网络）；
- 设备分配：将“轻量层”和“重量层”分别部署到不同类型的设备（如 CPU/低算力 GPU 运行 Attention 层，高算力 GPU 集群运行 MoE-FFN 层）；
- 通信调度：激活值在“轻量层设备”与“重量层设备”间定向传递，避免算力浪费。

#### （2）关键特点

- 优势：匹配层的算力需求与设备能力（如 MoE 层用多 GPU 并行，Attention 层用单 GPU），解决传统 PP 的负载不均衡问题；
- 适用场景：含稀疏 MoE 结构的 LLM（如 GPT-4、PaLM-E），推理时 MoE 层算力占比超 60%，需单独分配高算力资源。

### 3. 层间并行适用场景

- 基础 PP：适合“层数多、单层层权重小”的模型（如 100 层以上的 Transformer），优先降低单设备的层数量与权重存储；
- 异构 PP（AFD）：适合含 MoE、稀疏激活等“算力异构层”的模型，优化设备负载均衡，提升整体推理吞吐量。

## 三、冗余参数消除：降低权重的设备冗余存储

LLM 的权重参数规模极大（如千亿参数模型权重超 400GB），传统并行策略（如 DP）中“权重全量冗余存储”（所有设备存完整权重）会导致显存严重浪费，因此需通过“**权重分散存储**”消除冗余，核心技术基于 DeepSeek 的 Zero 思想，分为“**按层分散存储**”和“**按权重切片存储**”两类。

- ​**​冗余参数消除​**​：
    - ​**​层权重分片​**​：将不同层权重分到不同设备，通过预取广播减少冗余。
    - ​**​层内权重切分​**​：每层权重切分存储，计算时 AllGather 聚合（类似 Zero）。

冗余参数消除的方式，如 deepseed 的 Zero，将参数分散存储，当参数需要使用时通过集群通信将参数召回。根据 Zero 的思想，这里介绍两种消除某一层权重冗余存储的方式。

一般而言大模型由多个 blocks 构成，blocks 中有重复的层结构。当有多个设备时，可以把这些 blocks 的权重均分到各个设备中。如下图所示，以 blocks 中线性层 B 为例，每个 GPU 存储模型的两层权重，当 GPU 需要使用到某一层权重时，先对该层的权重进行广播。

由于 GPU 支持多流，所以可以做计算、广播通信的掩盖，比如计算到 x 层时，提前把 x+1 层的权重先广播出去（权重预取）。

![[file-20251105142444311.png]]

这种方式适合于模型层权重偏小的场景，模型层权重比较大时，或者说更常使用的是权重切片（shard）的场景。即将每一层的权重进行 n 等分，每个 GPU 设备上面存一份，当需计算时将其 allgather 回来。

![[file-20251105125844443.png]]

### 1. 策略一：按层分散存储（块级权重拆分）

针对“**模型由重复 Block 构成**”的特点（如 Transformer 的 100 个相同结构 Block），将 Block 的权重按“层”分散到不同设备，避免单设备存储所有 Block 的权重：

#### （1）核心操作逻辑

- 权重分配：将 `L` 个重复 Block 的权重拆分为 `k` 组（如 100 个 Block 拆分为 10 组，每组 10 个 Block），每个设备存储 1 组权重（如设备 0 存 Block1-10，设备 1 存 Block11-20）；
- 计算时权重调度：当设备需要计算某 Block（如设备 0 需计算 Block11）时，通过“**广播通信**”从对应设备（设备 1）召回该 Block 的权重；
- 优化：利用 GPU 多流技术实现“**权重预取**”——计算当前 Block（如 Block10）时，提前广播下一个 Block（Block11）的权重，掩盖通信延迟。

#### （2）关键特点

- 优势：权重存储量与设备数成反比（10 设备存储 100 个 Block，每设备仅存 10 个 Block 权重），冗余度极低；
- 局限：仅适合“**单层层权重小**”的场景（如 Block 内单线性层权重<1GB），若层权重过大，广播通信量会激增。

### 2. 策略二：按权重切片存储（层内权重拆分）

针对“**单线性层权重过大**”的场景（如 `hidden_dim=8192` 的线性层，权重尺寸=8192×8192×4Byte≈262MB），将单一层的权重按“切片（shard）”分散存储，进一步降低单设备权重存储：

#### （1）核心操作逻辑

- 权重切片：将单线性层的权重 `W`（如 `[hidden_in, hidden_out]`）按维度拆分为 `k` 个切片（如按列切分为 `W₁, W₂,...Wₖ`，每个切片尺寸 `[hidden_in, hidden_out/k]`）；
- 存储分配：每个设备存储 1 个权重切片（如设备 0 存 `W₁`，设备 1 存 `W₂`）；
- 计算时权重调度：当需要计算该线性层时，所有设备通过“**allgather 通信**”召回所有切片，拼接为完整 `W`，再执行 `Y = X·W + b`。

#### （2）关键特点

- 优势：单设备存储的权重切片尺寸与设备数成反比（10 设备存储 1 个 262MB 的权重，每设备仅存 26.2MB），适配大尺寸层权重；
- 局限：每次计算需执行 `allgather` 召回完整权重（增加通信开销），需通过“权重预取”“通信与计算重叠”优化延迟。

### 3. 冗余参数消除适用场景

- 按层分散存储：适合“模型 Block 多、单 Block 权重小”的场景（如 100 个 Block，每个 Block 权重<10GB），优先降低 Block 级别的权重冗余；
- 按权重切片存储：适合“单线性层权重过大”的场景（如 `hidden_dim>4096` 的线性层），进一步拆分层内权重，降低单设备存储压力；
- 组合使用：LLM 推理中常结合两种策略（如先按层分散存储 Block，再按切片存储 Block 内的大权重层），最大化降低权重冗余。

## 四、三大并行方向的核心差异与组合策略

### 1. 核心差异对比

| 并行方向       | 优化目标                | 操作粒度       | 关键通信类型       | 显存优化重点       |
|----------------|-------------------------|----------------|--------------------|--------------------|
| 层内并行       | 降低单层计算/激活值存储 | 单个线性层     | allgather（合并结果） | 激活值存储         |
| 层间并行       | 降低单设备层数量        | 多个线性层（Block） | 层间激活值传递     | 权重存储（层数量） |
| 冗余参数消除   | 降低权重冗余存储        | 权重（层/切片级） | 广播/allgather（召回权重） | 权重存储（冗余度） |

### 2. 典型组合策略（LLM 推理主流方案）

在实际 LLM 推理中（如千亿参数模型），单一并行策略无法满足需求，通常采用“**层内并行 + 层间并行 + 冗余参数消除**”的组合方案，例如：

1. 层间并行（PP）：将 100 层 Transformer 拆分为 10 个设备，每设备 10 层；
2. 层内并行（DP+TP+SP）：每个设备上的 10 层，通过 DP 切分 batch（2 设备）、TP 切分 hidden_dim（5 设备）、SP 切分 seq_len（2 设备），总设备数=10（PP）×2（DP）×5（TP）=100；
3. 冗余参数消除（权重切片）：每个设备上的层权重按切片存储，进一步降低单设备权重存储（如 1 个 262MB 权重拆分为 5 切片，每设备仅存 52.4MB）。

该组合方案可同时优化“计算压力”“激活值存储”“权重存储”，是当前大模型推理的标准并行范式。

## 总结

线性层并行计算的核心是“**按需拆分**”——根据激活值维度（batch/seq_len/hidden_dim）选择层内并行策略，根据层数量与算力异构性选择层间并行策略，根据权重规模选择冗余消除策略。在 LLM 推理中，需结合硬件资源（GPU 数量、显存大小）、模型结构（是否含 MoE、hidden_dim 大小）、推理场景（batch 大小、序列长度）动态调整并行组合，最终实现“高吞吐量 + 低延迟 + 低显存占用”的目标。

Attention 层的并行计算与 FFN 或者说模型中其它线性层的计算的主要不同之处：

- 在计算 attention 之前，会多一个 head 的维度，这个 head 维度是在线性映射 (投影) 运算中产生的。`[bs, seq_len,  heads * head_dim] -> [bs,  heads, seq_len,  head_dim]`
- 序列（seq_len 维度) 并行需要修正运算。

在并行维度上面，将 Head 维度的切分也算到 TP 里面，而序列维度并行上称之为 CP(context parallel) 或 SP。

![[file-20251105143018027.png]]

Attention 层因多头（Heads）和序列维度交互而复杂， Attention 的层间并行、冗余参数消除方式与线性层的方式一致，层内并行的主要差异是 TP 和 SP，所以重点关注到这两类上面。

## SP

在 LLM 推理并行中，Attention 层的序列并行（SP，Sequence Parallelism；或 CP，Context Parallelism）是解决“长序列激活值存储/计算压力”的关键技术，但因 Attention 计算的特殊性（含 Scaled Dot-Product、Softmax 等依赖全局序列的操作），其并行逻辑与 FFN 等线性层存在本质差异。以下从“**与线性层的核心差异**”“**QKV 序列切分的三大核心问题**”“**分场景优化方案**”“**关键技术细节**”四个维度展开详解，结合原文公式、代码与场景分析，厘清 Attention 序列并行的底层逻辑。

## 一、Attention 序列并行与线性层序列并行的核心差异

线性层的序列并行（如 FFN 层切分 `seq_len`）仅需“切分激活值→并行计算→拼接结果”，而 Attention 层的序列并行需额外处理“Head 维度引入”“Softmax 全局依赖”“QKV 交互逻辑”三大特殊点，具体差异如下表所示：

| 对比维度                | 线性层序列并行（如 FFN）                          | Attention 层序列并行（SP/CP）                      |
|-------------------------|---------------------------------------------------|---------------------------------------------------|
| **核心计算单元**        | 矩阵乘法（`Y = X·W + b`）+ 元素级激活（如 GeLU）   | Scaled Dot-Product（`Score=Q·Kᵀ/√dₖ`）+ Softmax + 加权求和（`O=Score·V`） |
| **新增维度影响**        | 无额外维度，激活值维度为 `[bs, seq_len, hidden_dim]` | 多“Head 维度”，QKV 维度为 `[bs, heads, seq_len, head_dim]`（Head 维度需与 TP 协同） |
| **并行关键约束**        | 仅需保证矩阵乘法维度匹配（切分 `seq_len` 不影响 `hidden_dim`） | 需满足两个约束：<br>1. QKV 切分后 `Score` 计算维度匹配；<br>2. Softmax 依赖**全局 `seq_len`**（不可直接局部计算） |
| **通信操作逻辑**        | 仅需 1 次 `allgather` 拼接切分的 `seq_len` 维度         | 需根据 QKV 切分方式动态选择通信类型（`allgather`/`allreduce`），且可能需“Softmax 修正” |
| **结果等价性保障**      | 局部计算结果独立，拼接后与原生计算完全一致         | 仅单独切分 Q 可直接拼接等价；切分 K/V 需额外处理，否则结果不等 |

核心差异的本质：**线性层的计算是“局部独立”的（每个 `seq_len` 位置的计算不依赖其他位置），而 Attention 层的计算是“全局交互”的（每个位置的 `Score` 依赖 Q 与所有 K 的交互，Softmax 依赖所有 `Score` 的全局分布）**。

## 二、QKV 序列切分的三大核心问题：能否直接拆分合并？

Attention 层序列并行的核心是“切分 QKV 的 `seq_len` 维度”，但 Q、K、V 在 `Score` 计算中扮演不同角色（Q 是“查询”，K 是“键”，V 是“值”），单独切分某一矩阵会导致结果不等。原文通过三个子问题拆解这一核心矛盾，以下结合数学推导与代码验证逐一分析：

### 问题 1：仅切分 Q 的 `seq_len`，KV 保持完整——结果是否等价？

#### 1. 切分与计算逻辑

- **切分方式**：将 Q 按 `seq_len` 维度切分为 `Q₁, Q₂, ..., Qₖ`（如二分时 `Qᵢ` 维度为 `[bs, heads, seq_len/k, head_dim]`），K、V 保持完整（维度 `[bs, heads, seq_len, head_dim]`）。
- **计算步骤**（对应原文 Step1-Step4）：
  1. **计算局部 Score**：每个 `Qᵢ` 与完整 K 计算 `Scoreᵢ = Qᵢ·Kᵀ/√dₖ`，维度为 `[bs, heads, seq_len/k, seq_len]`（左矩阵行切，符合矩阵乘法场景二）；
  2. **局部 Softmax**：Softmax 沿 `Scoreᵢ` 的最后一维（`seq_len` 维度）计算，因 K 完整，`Scoreᵢ` 的最后一维覆盖全部 `seq_len`，局部 Softmax 结果与全局计算完全一致，得到 `Weightsᵢ`；
  3. **局部加权求和**：`Weightsᵢ` 与完整 V 计算 `Oᵢ = Weightsᵢ·V`，维度为 `[bs, heads, seq_len/k, head_dim]`（仍为左矩阵行切）；
  4. **结果拼接**：通过 `allgather` 沿 `seq_len` 维度拼接 `O₁, O₂, ..., Oₖ`，得到完整输出 `O`。

#### 2. 等价性验证（原文代码解析）

原文通过 numpy 代码验证了这一结论，核心逻辑如下：

- 全局计算：`global_out = attention(Q, K, V)`（完整 QKV 参与计算）；
- 局部计算：切分 Q 为 `Q₁`（前 2 个 `seq_len`）、`Q₂`（后 2 个 `seq_len`），分别计算 `local_out1 = attention(Q₁, K, V)`、`local_out2 = attention(Q₂, K, V)`；
- 拼接验证：`local_out = np.concatenate([local_out1, local_out2], axis=2)`（axis=2 对应 `seq_len` 维度），`np.allclose(global_out, local_out)` 返回 `True`。

#### 3. 结论：仅切分 Q 的 `seq_len`，拼接后结果与原生计算完全等价——这是 Attention 序列并行的“安全切分方式”

### 问题 2：仅切分 K 的 `seq_len`，QV 保持完整——结果是否等价？

#### 1. 切分与计算逻辑

- **切分方式**：将 K 按 `seq_len` 切分为 `K₁, K₂, ..., Kₖ`（`Kᵢ` 维度 `[bs, heads, seq_len/k, head_dim]`），Q、V 保持完整（`Q` 维度 `[bs, heads, seq_len, head_dim]`）。
- **计算矛盾点**：
  1. **局部 Score 维度异常**：`Scoreᵢ = Q·Kᵢᵀ/√dₖ`，维度为 `[bs, heads, seq_len, seq_len/k]`（仅覆盖部分 K 的 `seq_len`）；
  2. **Softmax 全局依赖破坏**：Softmax 沿 `Scoreᵢ` 的最后一维（`seq_len/k` 维度）计算，仅基于部分 K 的交互结果，而非全部 `seq_len` 的 `Score`，导致 `Weightsᵢ` 与全局计算差异极大；
  3. **拼接结果无效**：即使拼接 `O₁, O₂, ..., Oₖ`，因 `Weightsᵢ` 已失真，最终结果与原生计算完全不等。

#### 2. 结论：仅切分 K 的 `seq_len`，拼接后结果不等——这是“不安全切分方式”，需避免直接使用

### 问题 3：仅切分 V 的 `seq_len`，QK 保持完整——结果是否等价？

#### 1. 切分与计算逻辑

- **切分方式**：将 V 按 `seq_len` 切分为 `V₁, V₂, ..., Vₖ`（`Vᵢ` 维度 `[bs, heads, seq_len/k, head_dim]`），Q、K 保持完整。
- **计算步骤与矛盾**：
  1. **全局 Score 与 Softmax**：Q、K 完整，`Score = Q·Kᵀ/√dₖ` 和 `Weights = Softmax(Score)` 均为全局结果（维度 `[bs, heads, seq_len, seq_len]`），无失真；
  2. **局部加权求和的维度不匹配**：`Weights` 维度为 `[bs, heads, seq_len, seq_len]`，`Vᵢ` 维度为 `[bs, heads, seq_len/k, head_dim]`，直接相乘需 `Weights` 按列切分为 `Weightsᵢ`（维度 `[bs, heads, seq_len, seq_len/k]`），符合矩阵乘法场景三（A 列切 +B 行切）；
  3. **结果求和而非拼接**：局部计算 `Oᵢ = Weightsᵢ·Vᵢ`（维度 `[bs, heads, seq_len, head_dim]`），需通过 `allreduce`（元素级求和）合并 `O₁, O₂, ..., Oₖ`，而非 `allgather` 拼接，才能得到完整 `O`。

#### 2. 结论：仅切分 V 的 `seq_len`，需用 `allreduce` 求和而非 `allgather` 拼接，结果才能等价——需调整通信类型，而非直接拆分合并

### 三大问题总结：QKV 切分的“安全边界”

| 切分对象 | 通信操作       | 结果等价性 | 核心原因                                                                 |
|----------|----------------|------------|--------------------------------------------------------------------------|
| 仅切分 Q  | `allgather` 拼接 | 是         | K/V 完整，Softmax 基于全局 Score，局部结果独立可拼接                         |
| 仅切分 K  | 无有效通信方式 | 否         | Score 仅覆盖部分 K，Softmax 全局依赖破坏，结果失真                           |
| 仅切分 V  | `allreduce` 求和 | 是         | Q/K 完整，Score/Softmax 全局有效，局部 Oᵢ需求和合并（矩阵乘法场景三）         |

核心结论：**若需同时切分 Q、K、V 的 `seq_len`（如长序列场景需最大化并行度），必须解决“切分 K 导致的 Softmax 失真”问题——这是 Attention 序列并行的核心挑战**。

## 三、分场景优化方案：从 Softmax 修正到 Prefix Cache 适配

针对“QKV 同时切分”的核心挑战，原文提出“Softmax 修正”技术，并结合 LLM 推理的两大核心场景（Prefill、Decode）与特殊优化（Prefix Cache），设计了差异化的并行方案。

### 1. 通用解决方案：QKV 同切分 +Softmax 修正

当 Q、K、V 按相同方式切分 `seq_len`（如均切分为 `k` 份），需通过“Softmax 修正”恢复全局结果，该方案广泛应用于 Blockwise Multi-Head Attention、Ring Attention 等技术中。

#### （1）核心原理

- **步骤 1：全量交互计算局部 Oᵢ**：每个切分后的 `Qᵢ` 需与**所有**切分后的 `Kⱼ`、`Vⱼ`（`j=1..k`）计算，得到 `Oᵢⱼ = Softmax(Qᵢ·Kⱼᵀ/√dₖ)·Vⱼ`；
- **步骤 2：Softmax 修正**：因 `Qᵢ·Kⱼᵀ` 仅覆盖部分 `seq_len`，需先计算全局 `Score` 的最大值（`max_score`）和全局指数和（`sum_exp`），修正局部 `Oᵢⱼ` 的数值分布；
- **步骤 3：合并结果**：对修正后的 `Oᵢⱼ` 按 `i` 维度（Q 的切分块）拼接，得到完整 `O`。

#### （2）关键技术点

- 每个 `Qᵢ` 需与所有 `Kⱼ` 交互，需通过 Ring 通信（如 Ring Attention）传递 Q/K 块，避免全量数据传输；
- Softmax 修正依赖全局统计信息（`max_score`、`sum_exp`），需通过额外通信获取，避免数值偏差。

### 2. Prefill 场景：Ring Attention 实现高效并行

Prefill 场景是 LLM 推理的“长序列阶段”（如输入 1k token 的文本），Q 的 `seq_len` 与 K/V 完全一致，需最大化并行度，原文推荐使用**Ring Attention**方案。

#### （1）核心逻辑：环形通信减少数据传输

- **切分与通信拓扑**：将 Q、K、V 均切分为 `k` 份，分配给 `k` 个 GPU（构成环形拓扑）；
- **环形交互计算**：每个 GPU 上的 `Qᵢ` 依次与环形中其他 GPU 的 `Kⱼ`、`Vⱼ` 交互计算 `Oᵢⱼ`，并通过环形通信传递 Q/K 块（而非全量广播）；
- **Softmax 修正集成**：在环形通信过程中，同步全局 `max_score` 和 `sum_exp`，实时修正局部 `Oᵢⱼ`；
- **结果合并**：环形交互结束后，每个 GPU 持有对应 `Qᵢ` 的完整 `Oᵢ`，通过 `allgather` 拼接得到全局 `O`。

#### （2）优势：通信量与 `k` 成反比（`O(seq_len²/k)`），适配长序列场景，避免单 GPU 显存溢出

### 3. Decode 场景：Q 复制 +Tree Attention 优化瓶颈

Decode 场景是 LLM 推理的“生成阶段”（如逐 token 生成文本），Q 的 `seq_len=1`（仅当前生成的 token），K/V 为历史缓存（`seq_len` 随生成过程增长），需解决“单 GPU 瓶颈”问题。

#### （1）传统方案：Q 复制 +Gather 修正

- **步骤 1：Q 复制**：将 Q（`seq_len=1`）复制 `k` 份，分配给每个持有 K/V 切分块的 GPU；
- **步骤 2：局部 Attention 计算**：每个 GPU 用复制的 Q 与本地 K/V 切分块计算 `Oᵢ`；
- **步骤 3：Gather 修正**：将所有 `Oᵢ` gather 到一个 GPU（如 GPU0），计算全局 `max_score`、`sum_exp` 修正 `O`，再广播到其他 GPU。

#### （2）瓶颈：GPU0 需承担所有修正与求和计算，成为性能瓶颈

#### （3）优化方案：Tree Attention（树形通信替代 Gather）

- **核心改进**：将“单 GPU Gather”改为“多轮 Tree-shaped allreduce”：
  1. 按树形拓扑将 GPU 分为多组，组内先通过 `allreduce` 计算局部 `max_score` 和 `sum_exp`；
  2. 逐层合并各组统计信息，最终得到全局统计量；
  3. 按树形反向传递全局统计量，每个 GPU 独立完成 `Oᵢ` 修正，无需集中到单 GPU。
- **优势**：通信量从 `O(k·seq_len)` 降至 `O(log k · seq_len)`，跨节点场景优势显著，消除单 GPU 瓶颈。

### 4. 特殊优化：Prefix Cache 适配

Prefix Cache 是 LLM 推理的“缓存复用技术”——将输入序列中“可复用的前缀部分”（如对话历史）的 K/V 缓存起来，仅计算“新增后缀部分”（如当前输入的新 token），需解决“缓存传输”与“负载均衡”问题。

#### （1）序列拆分与计算分类

- 序列拆分：`seq_len = prefix_cache_seq_len（缓存前缀） + tail_seq_len（新增后缀）`，Q 仅需计算 `tail_seq_len` 部分；
- 计算分类：
  1. Q_tail 与缓存的 K/V_prefix 计算 Attention（复用缓存，计算量小）；
  2. Q_tail 与新增的 K/V_tail 计算 Attention（需实时计算，计算量大）。

#### （2）并行方案：Q 轮转 + 本地缓存复用

- **负载均衡**：将 `prefix_cache_seq_len` 和 `tail_seq_len` 均切分为 `k` 份，每个 GPU 持有 1 份前缀缓存和 1 份后缀数据，同时轮转 Q_tail 的切分块（如 GPU0 处理 Q_tail1，GPU1 处理 Q_tail2）；
- **缓存复用**：若前缀缓存已在 GPU 本地显存，无需跨设备传输（解决“缓存传输”问题）；
- **计算效率**：若 `prefix_cache_seq_len/k = tail_seq_len/k`（切分比例一致），一次迭代仅需 2 次 Attention 计算（分别对应前缀和后缀），负载均衡且效率高。

## 总结

文章强调，LLM 推理并行需根据模型结构（如 MLA）、计算阶段（Prefill/Decode）和硬件约束，灵活组合 DP、SP、TP、PP 等策略。关键是通过矩阵切分减少计算/显存，并优化通信（如 Ring/Tree Attention）以提升效率。
