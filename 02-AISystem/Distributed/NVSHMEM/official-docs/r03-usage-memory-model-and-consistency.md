## NVSHMEM Memory Model

### Official English

> An NVSHMEM program consists of data objects that are private to each PE and data objects that are remotely accessible by all PEs. Private data objects are stored in the local memory of each PE and can only be accessed by the PE itself; these data objects cannot be accessed by other PEs through NVSHMEM routines. Private data objects follow the memory model of C. Remotely accessible objects, however, can be accessed by remote PEs using NVSHMEM routines. Remotely accessible data objects are called Symmetric Data Objects. Each symmetric data object has a corresponding object with the same name, type, and size on all PEs where that object is accessible through the NVSHMEMAPI [1].
>
> In NVSHMEM, GPU memory allocated by NVSHMEM memory management routines is symmetric. See Section Memory Management for information on allocating symmetric memory.
>
> NVSHMEM dynamic memory allocation routines (for example, nvshmem_malloc) allow collective allocation of Symmetric Data Objects on a special memory region called the Symmetric Heap. The Symmetric Heap is created during the execution of a program at a memory location determined by the NVSHMEM library. The Symmetric Heap may reside in different memory regions on different PEs. Figure NVSHMEM Memory Model shows an example NVSHMEM memory layout, illustrating the location of remotely accessible symmetric objects and private data objects.

### 中文对照

> 一个 NVSHMEM 程序包含两类数据对象：每个 PE 私有的数据对象，以及所有 PE 都可以远程访问的数据对象。私有数据对象存储在各 PE 的本地内存中，只能由该 PE 自身访问；其他 PE 不能通过 NVSHMEM 例程访问这些对象。私有数据对象遵循 C 语言内存模型。远程可访问对象则能够由远端 PE 通过 NVSHMEM 例程访问。远程可访问的数据对象称为**对称数据对象（Symmetric Data Objects）**。在可以通过 NVSHMEM API 访问该对象的所有 PE 上，每个对称数据对象都有名称、类型和大小相同的对应对象。[1]
>
> 在 NVSHMEM 中，由 NVSHMEM 内存管理例程分配的 GPU 内存是对称的。有关对称内存分配的信息，请参阅 Memory Management 一节。
>
> NVSHMEM 动态内存分配例程（例如 `nvshmem_malloc`）允许在称为**对称堆（Symmetric Heap）**的特殊内存区域中，以集合方式分配对称数据对象。对称堆在程序执行期间创建，其内存位置由 NVSHMEM 库确定。不同 PE 的对称堆可以位于不同的内存区域。NVSHMEM Memory Model 图展示了一种内存布局示例，其中区分了可远程访问的对称对象和私有数据对象。

### 技术解读：对称的是对象对应关系，不是裸地址数值

这段定义先建立对象分类，再建立远程访问资格。一个对象位于 GPU memory 并不自动意味着它是 symmetric object；它必须由相应的 NVSHMEM collective allocation 或符合规范的 symmetric registration 建立跨 PE 对应关系。反过来，对称堆可以位于不同 PE 的不同内存区域，因此“所有 PE 的虚拟地址必须完全相同”不是 API 前提。

“same name, type, and size”描述各 PE 上的逻辑对应对象。应用通过本 PE 生成的 symmetric address 加目标 PE 标识远端对应位置，runtime 再根据 transport 与注册 metadata 完成实际寻址。底层可能利用相同 offset 提高效率，但这属于实现选择，不应写成应用自行计算远端地址的保证。

## Pointers to Symmetric Objects

### Official English

> Symmetric data objects are referenced in NVSHMEM operations through the local pointer to the desired remotely accessible object. The address contained in this pointer is referred to as a symmetric address. Every symmetric address is also a local address that is valid for direct memory access; however, not all local addresses are symmetric. Manipulation of symmetric addresses passed to NVSHMEM routines—including pointer arithmetic, array indexing, and access of structure or union members—are permitted as long as the resulting local pointer remains within the same symmetric allocation or object. Symmetric addresses are only valid at the PE where they were generated; using a symmetric address generated by a different PE for direct memory access or as an argument to an NVSHMEM routine results in undefined behavior.
>
> Symmetric addresses provided to typed interfaces must be naturally aligned based on their type and any requirements of the underlying architecture. Symmetric addresses provided to fixed-size NVSHMEM interfaces (for example, nvshmem_put32) must also be aligned to the given size. Symmetric objects provided to fixed-size NVSHMEM interfaces must have storage size equal to the bit-width of the given operation. Because C/C++ structures may contain implementation-defined padding, the fixed-size interfaces should not be used with C/C++ structures. The “mem” interfaces (for example, nvshmem_putmem) have no alignment requirements.
>
> The nvshmem_ptr routine allows the programmer to query a local address to a remotely accessible data object at a specified PE. The resulting pointer is valid for direct memory access; however, providing this address as an argument of an NVSHMEM routine that requires a symmetric address results in undefined behavior.

### 中文对照

> 在 NVSHMEM 操作中，对称数据对象通过指向所需远程可访问对象的**本地指针**来引用。该指针中包含的地址称为 symmetric address。每个 symmetric address 同时也是一个可用于直接内存访问的有效本地地址；但是，并非所有本地地址都是 symmetric address。允许对传给 NVSHMEM 例程的 symmetric address 进行指针运算、数组索引以及结构体或联合体成员访问，前提是运算得到的本地指针仍位于同一次对称分配或同一个对称对象之内。Symmetric address 只在生成它的 PE 上有效；把另一个 PE 生成的 symmetric address 用于直接内存访问，或作为 NVSHMEM 例程参数，会导致未定义行为。
>
> 传给 typed interface 的 symmetric address 必须按照其类型和底层体系结构要求自然对齐。传给固定宽度 NVSHMEM 接口（例如 `nvshmem_put32`）的 symmetric address 还必须按对应宽度对齐。传给固定宽度接口的对称对象，其存储大小必须等于该操作的位宽。由于 C/C++ 结构体可能包含由实现决定的 padding，不应对 C/C++ 结构体使用固定宽度接口。“mem”接口（例如 `nvshmem_putmem`）没有对齐要求。
>
> `nvshmem_ptr` 允许程序员查询一个本地地址，用于直接访问指定 PE 上的远程可访问数据对象。返回的指针可用于直接内存访问；但是，如果把这个地址传给要求 symmetric address 的 NVSHMEM 例程，则会导致未定义行为。

### 技术解读：三类指针不能混用

这里至少要区分普通 local pointer、local symmetric address 和 `nvshmem_ptr` 返回的 peer direct pointer。Local symmetric address 既能在本 PE 直接访问，也能与目标 PE 一起作为 NVSHMEM 远端操作的对象标识；普通 local pointer 没有这种远端对象资格；peer direct pointer 是当前 PE 地址空间中对远端对象的直接映射，只用于直接 load/store，不能再作为要求 symmetric address 的 NVSHMEM 参数。

合法的对象内指针运算仍受 C/C++ 对象边界约束。起始地址位于对象内并不足够，整个传输范围也必须位于同一次 symmetric allocation 中。对结构体使用 `put32/put64` 一类固定宽度接口时，padding、对象大小和对齐都会影响合法性；若意图按字节搬运结构体的对象表示，应优先审查 `putmem/getmem` 的范围和跨平台布局，而不是因为接口接受 32/64 位宽就假定结构体匹配。

## Ordering of Operations

### Official English

> Blocking operations in NVSHMEM that read data (for example, get or atomic fetch-and-add) are expected to return data according to the order in which the operations are performed. For example, consider a program that performs atomic fetch-and-add of the value 1 to the symmetric variable x on PE 0.

```c
a = nvshmem_int_fadd(x, 1, 0);
b = nvshmem_int_fadd(x, 1, 0);
```

> In this example, the OpenSHMEM specification guarantees that b > a. However, this strong ordering can incur significant overheads on weakly ordered architectures by requiring memory barriers to be performed before any such operation returns. NVSHMEM relaxes this requirement to provide a more efficient implementation on NVIDIA GPUs. Thus, NVSHMEM does not guarantee b > a.
>
> Where such ordering is required, programmers can use an nvshmem_fence operation to enforce ordering for blocking operations (for example, between the two statements above). Non-blocking operations are not ordered by calls to nvshmem_fence. Instead, they must be completed using the nvshmem_quiet operation. The completion semantics of fetching operations remain unchanged from the OpenSHMEM specification: the result of the get or AMO is available for any dependent operation that appears after it, in program order.

### 中文对照

> OpenSHMEM 中读取数据的 blocking operation（例如 get 或 atomic fetch-and-add）预期按照操作执行顺序返回数据。以上示例连续对 PE 0 的对称变量 `x` 执行两次加 1 的 atomic fetch-and-add；OpenSHMEM 规范保证 `b > a`。但是，在弱排序体系结构上，这种强排序可能要求每个操作返回前执行 memory barrier，带来显著开销。NVSHMEM 为了在 NVIDIA GPU 上更高效而放宽了这一要求，因此不保证 `b > a`。
>
> 如果程序需要这种 ordering，可以在 blocking operations 之间使用 `nvshmem_fence` 强制排序。`nvshmem_fence` 不对 non-blocking operations 排序；这些操作必须用 `nvshmem_quiet` 完成。Fetching operation 的完成语义没有改变：get 或 AMO 的结果在程序顺序中可供其后的依赖操作使用。

### 技术解读：单次结果可用不等于两次 fetch 之间强排序

这段文字同时包含两个层次。第一，fetching call 返回后，本次返回值已经可供当前执行流中的依赖操作使用；第二，两次 blocking fetching operations 之间并不自动保留 OpenSHMEM 所要求的强顺序，所以不能仅凭源代码先后推导 `b > a`。需要跨操作 ordering 时必须使用规范指定的 `fence`；对 non-blocking operations，仅有 fence 不够，还要以 `quiet` 建立 completion。

这里的 `fence` 和 `quiet` 是 NVSHMEM API 契约，不应直接等同于某个 verbs fence bit、某个 CQE 或固定 IBGDA WQE。具体 transport 可以用不同机制实现相同上层保证。

## Atomicity Guarantees

### Official English

> NVSHMEM contains a number of routines that perform atomic operations on symmetric data objects, which are defined in Section Atomic Memory Operations. The atomic routines guarantee that concurrent accesses by any of these routines to the same location, and using the same datatype (specified in Tables Standard AMO Types and Names and Extended AMO Types and Names) will be exclusive. Exclusivity is also guaranteed when the target PE performs a wait or test operation on the same location and with the same datatype as one or more atomic operations.
>
> NVSHMEM atomic operations do not guarantee exclusivity in the following scenarios, all of which result in undefined behavior.
>
> 1. When concurrent accesses to the same location are performed using NVSHMEM atomic operations using different datatypes.
> 2. When atomic and non-atomic NVSHMEM operations are used to access the same location concurrently.
> 3. When NVSHMEM atomic operations and non-NVSHMEM operations (for example, load and store operations) are used to access the same location concurrently.

### 中文对照

> NVSHMEM 提供多种在 symmetric data object 上执行原子操作的例程。对于同一个内存位置，如果并发访问都使用这些原子例程并采用相同 datatype，则这些访问具有排他性。当目标 PE 对同一位置、使用相同 datatype 执行 wait 或 test，同时一个或多个 PE 对该位置执行原子操作时，也保证排他性。
>
> 在以下场景中，NVSHMEM atomic operation 不保证排他性，并且都会导致未定义行为：第一，对同一位置并发执行使用不同 datatype 的 NVSHMEM atomic operations；第二，对同一位置并发混用 atomic 与 non-atomic NVSHMEM operations；第三，对同一位置并发混用 NVSHMEM atomic operations 和非 NVSHMEM 操作，例如普通 load/store。

### 技术解读：原子性首先是一套访问纪律

协议必须为每个 control word 列出全部访问方式和 datatype。不能一部分 PE 使用 `uint64_t` AMO、另一部分使用不同类型的 AMO，也不能在某些路径使用 atomic add、另一些路径用普通 PUT 或 CUDA store 清零。即使硬件恰好执行单字对齐写，也不能把未定义的混合访问提升为 API 保证。

“同一位置上的排他性”也不是多字事务。对 `tail` 的 fetch-add 可以分配唯一 ticket，但不能证明 ticket 对应 payload 已写完；对 `state` 和 `owner` 分别执行 AMO，也不能保证观察者取得二者的一致快照。数据发布、容量、回收和进度仍需额外协议。

## Differences Between NVSHMEM and OpenSHMEM

### Ordering of Blocking Fetching Operations — Official English

> Blocking operations in OpenSHMEM that read data, for example, get or atomic fetch-and-add, are expected to return data based on the order in which the operations are performed. For example, consider a program that performs atomic set operations to update symmetric variables x and y on PE 0:

```c
// Let: v_N represent symmetric variable v at PE N
// Input: x_0 = 0, y_0 = 0, i = 0, j = 0

if (nvshmem_my_pe() == 0) {
    a = nvshmem_int_atomic_set(x, 1, 0);
    nvshmem_quiet();
    b = nvshmem_int_atomic_set(y, 1, 0);
}

i = nvshmem_int_atomic_fetch(y, 0);
j = nvshmem_int_atomic_fetch(x, 0);

// Allowed output: i = 1, j = 0
```

> In this example, the OpenSHMEM specification guarantees that if i == 1 then j == 1. However, this strong ordering can incur significant overheads on weakly ordered architectures by requiring memory barriers to be performed before any fetching operation returns. NVSHMEM relaxes this requirement to provide a more efficient implementation that is aligned with the NVIDIA GPU memory model. As a result, NVSHMEM does not guarantee if i == 1 then j == 1.
>
> Where this ordering is required, programmers can use an nvshmem_fence operation to enforce ordering for blocking operations (for example, between the two nvshmem_int_atomic_fetch statements above). Non-blocking operations are not ordered by calls to nvshmem_fence. Instead, these operations must be completed by using the nvshmem_quiet operation. The completion semantics of fetching operations remain unchanged from the specification, which is the result of the get or AMO is available for any dependent operation that appears after it, in program order.

### 中文对照

> OpenSHMEM 中读取数据的 blocking operations 应按照执行顺序返回数据。示例先更新 PE 0 上的 `x` 与 `y`，随后依次 fetch `y` 和 `x`。OpenSHMEM 规定，如果 `i == 1`，则 `j == 1`。这种强 ordering 在弱排序体系结构上可能要求 fetching operation 返回前执行 memory barrier。NVSHMEM 为与 NVIDIA GPU memory model 对齐并提高效率而放宽该要求，因此允许观察到 `i == 1, j == 0`。
>
> 如果需要这种 ordering，程序员可以在两个 blocking fetching operations 之间使用 `nvshmem_fence`。Non-blocking operations 不由 fence 排序，而必须使用 `nvshmem_quiet` 完成。单次 fetching operation 的完成语义仍保持不变：get 或 AMO 的结果可供程序顺序中后续依赖操作使用。

### 技术解读与原文代码注意事项

该例的意图是说明“先观察到 `y` 的新值，不推出随后一定观察到 `x` 的新值”，也就是 NVSHMEM 对 blocking fetching operations 的跨操作 ordering 比 OpenSHMEM 更弱。程序若依赖 `x→y` 的观察顺序，必须明确建立 ordering，而不能把 fetching call 返回本身当成全局 acquire。

当前官方页面原样写有 `a = nvshmem_int_atomic_set(...)` 和 `b = nvshmem_int_atomic_set(...)`。按照当前 Atomic Memory Operations API，`atomic_set` 是 non-fetching、返回 `void` 的接口，因此这两处赋值不应直接作为可编译范例；它们不影响后续 `i/j` 所表达的 ordering 场景。本文为遵守“保留官方英文原文”的要求没有静默改写代码，只在此标出接口签名与示例形式的矛盾。

### Visibility Guarantees — Official English

> On systems with both NVLink and InfiniBand, the NVSHMEM synchronization operations including nvshmem_barrier, nvshmem_barrier_all, nvshmem_quiet, nvshmem_wait_until_*, and nvshmem_test_* only guarantee visibility of updates to the local PE’s symmetric objects. However, on systems with only NVLink, these operations guarantee global visibility of updates to symmetric objects.

### 中文对照

> 在同时具有 NVLink 和 InfiniBand 的系统上，包括 `nvshmem_barrier`、`nvshmem_barrier_all`、`nvshmem_quiet`、`nvshmem_wait_until_*` 和 `nvshmem_test_*` 在内的 NVSHMEM synchronization operations，只保证对本地 PE 的 symmetric objects 的更新可见。只有 NVLink 的系统上，这些操作则保证对 symmetric objects 更新的全局可见性。

### 技术解读：可见性范围依赖系统路径

这段差异意味着不能把一次 PE 上完成的同步操作无限外推为“所有其他 PE 都已经观察到所有 symmetric objects 的新值”。在混合 NVLink 与 InfiniBand 系统中，规范明确限制了 visibility scope。正确协议应让真正消费数据的目标 PE 观察对应 signal、wait/test 或参与满足契约的同步，并只对该同步覆盖的对象和操作建立结论。

“只有 NVLink 时全局可见”同样不等于应用可以忽略参与集合和 ownership。Global visibility 描述更新可观察性，不能证明消费者已经执行、已经读完或允许生产者复用远端 slot。

## Footnote [1]

### Official English

> For efficiency reasons, the same offset (from an arbitrary memory address) for symmetric data objects might be used on all PEs. Further discussion about symmetric heap layout and implementation efficiency can be found in Section NVSHMEM_MALLOC, NVSHMEM_FREE, NVSHMEM_ALIGN.

### 中文对照与解读

> 出于效率考虑，各 PE 的 symmetric data objects 可能使用相对于某个任意内存地址的相同 offset。关于 symmetric heap 布局和实现效率的进一步讨论，可参阅 `NVSHMEM_MALLOC`、`NVSHMEM_FREE` 与 `NVSHMEM_ALIGN`。

关键词是 “might”：相同 offset 是可能采用的效率策略，不是应用可依赖的远端地址公式。应用仍应使用本 PE 的 symmetric address 和 target PE 调用 NVSHMEM，而不是读取 heap base 后自行拼接远端指针。
