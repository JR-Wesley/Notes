# 《LLM分布式训练系统：从Transformer到万卡集群》 全局结构

## 一、核心学习目标

学习的核心目标并非掌握单一深度学习框架，而是搭建一套**统一的系统抽象思维**，聚焦大模型分布式执行的底层逻辑，形成可迁移、可复用的系统分析能力。

本课程贯穿唯一核心主线：**如何将大型计算图、Transformer 模块逐步落地到单GPU、多GPU乃至GPU集群执行，并完成全链路性能优化**。

整体学习进阶链路如下：

> Transformer Block → 单GPU执行 → 多GPU执行 → 集群执行 → 性能优化

课程所有章节均围绕该主线展开，摒弃“以框架为核心”的碎片化学习模式，聚焦底层通用原理。

## 二、核心四层系统抽象体系（模型-计算-通信-硬件）

理解大模型分布式并行的核心，是建立一套**模型→计算→通信→硬件**的四层分层抽象思维。所有并行策略（张量并行、数据并行、序列并行等）的设计逻辑、通信开销、显存占用，均可通过这四层模型逐层拆解、精准解释，是跳出框架表层、吃透分布式底层原理的核心逻辑框架。

四层抽象的核心逻辑为：**模型结构决定计算拆分方式，计算拆分产生局部结果偏差，结果补全依赖特定通信逻辑，通信效率由硬件拓扑与通信库决定**。以最经典的「张量并行（Tensor Parallel）为何必须使用 AllReduce 通信」为例，逐层拆解如下：

- **1. 模型层（拆分依据）**：Transformer 线性层（Linear）的权重矩阵可横向、纵向切分，张量并行将单层权重拆分至不同GPU，单块GPU仅存储、承载部分模型参数，天然无法独立输出完整计算结果。
- **2. 计算层（执行逻辑）**：各GPU基于自身持有的局部权重，独立完成局部矩阵乘法（Local MatMul）计算，仅输出对应分片的局部特征结果，计算过程无跨设备交互。
- **3. 通信层（补全逻辑）**：单设备局部计算结果不具备完整性，无法送入下一层网络计算，因此需要通过 AllReduce 全局聚合通信，汇总所有GPU的局部结果，得到完整的全局特征输出。
- **4. 硬件层（效率支撑）**：AllReduce 通信并非简单的数据传输，而是依托 NCCL 通信库的 Ring AllReduce 环形拓扑，适配多GPU硬件组网架构，最大化利用硬件带宽、降低通信延迟，实现高效聚合计算。

基于四层抽象体系，学习分布式并行落地需重点关注三大核心细节，覆盖场景差异、分析方法论与框架底层本质，是打通理论与工程实现的关键。

#### 1. 训练与推理的核心场景差异

大模型训练与推理的核心诉求、优化目标完全不同，直接决定并行策略、显存优化、通信逻辑的设计方向，是分布式系统设计的核心依据。

**训练核心链路**：Forward 前向计算 → Backward 反向传播 → Optimizer 参数更新 → Gradient Sync 梯度同步

**推理核心链路**：Forward 前向计算 → KV Cache 缓存优化 → Paged Attention 分页注意力优化 → Continuous Batching 连续批处理优化

#### 2. 并行策略通用标准化分析维度

所有分布式并行策略（数据并行、张量并行、序列并行等）均可通过五大固定维度拆解分析，形成统一、通用的学习与落地思维，避免碎片化理解。

- 切什么？（切分对象：权重/数据/梯度/序列等）
- 谁算？（各GPU的计算分工与负载分配）
- 谁通信？（参与跨设备通信的硬件主体）
- 通信多少？（通信数据量、传输带宽与延迟开销）
- 显存减少多少？（分片与通信带来的显存优化收益）

**落地示例：Tensor Parallel 张量并行完整链路**

> 权重（Weight）→ 列切分（Column Split）→ 局部矩阵计算（Local GEMM）→ 全局聚合通信（AllReduce）→ 输出完整结果（Output）

#### 3. 分布式框架底层核心本质

主流大模型分布式框架（PyTorch Distributed、DeepSpeed、Megatron-LM 等）表层是工具封装，核心本质均为**分布式运行时（Runtime）**，核心价值是屏蔽底层硬件差异，统一封装计算、通信、显存调度逻辑。

关键底层原理：DDP 并非在每一层计算结束后被动触发通信，其异步通信、梯度聚合的核心能力完全依托 **Reducer Hook 钩子机制** 实现，这是读懂框架源码、理解分布式运行机制、突破表层工具使用的核心关键点。

## 三、贯穿全程的两大核心学习主线

多数人难以掌握分布式大模型技术的核心原因：仅碎片化学习知识点，未建立贯穿全场景的通用分析主线。以下两大主线可串联所有分布式、显存优化技术，构建完整知识体系。

### 主线一：数据流（Dataflow）

学习任意知识点，持续聚焦核心数据流问题，精准追踪张量全生命周期流转：

- 张量当前存储位置？
- 张量维度形状？
- 张量分配在哪块GPU？
- 张量何时产生、何时释放？
- 张量何时触发通信、通信形式是什么？

**示例：Tensor Parallel 数据流链路**

> 输入数据（Input）→ 分发至 GPU0、GPU1 → 各设备局部 GEMM 计算 → AllReduce 全局通信聚合 → 输出完整结果（Output）

### 主线二：生命周期（Lifecycle）

无论学习 Activation 激活值、Gradient 梯度、Parameter 参数、Optimizer 优化器等核心对象，均统一遵循「五阶段生命周期」分析模型，可串联所有显存优化技术。

> 分配（Allocate）→ 计算（Compute）→ 通信（Communicate）→ 复用（Reuse）→ 释放（Free）

依托该模型，可自然串联 Activation Checkpoint、ZeRO、FSDP、Sequence Parallel 等主流显存优化技术，打通技术底层逻辑。

## 第一篇 计算对象（Model Layer）

**核心问题**：LLM到底在计算什么？

### Chapter 1 Transformer整体结构

**1.1 大语言模型的发展与架构演进**：梳理RNN、Transformer到现代Decoder-only LLM的完整发展脉络，明晰Transformer成为当前大模型基础架构的核心原因，掌握不同模型结构对应的适用任务场景。

**1.2 Encoder、Decoder与Decoder-only**：拆解Encoder、Encoder-Decoder、Decoder-only三种经典模型结构的计算流程，解析GPT系列采用Decoder-only架构的底层逻辑，区分模型训练与推理阶段的数据流差异。

**1.3 Transformer Block整体数据流**：搭建Transformer Block整体结构认知，厘清Attention、MLP、Norm、Residual模块之间的数据流关联，为后续各类并行策略的分析建立统一核心研究对象。

### Chapter 2 Attention计算机制

**2.1 Q、K、V的数学含义**：掌握QKV的生成来源、矩阵维度变换规则，理解各类Projection矩阵在模型运算中的核心作用，建立Attention机制的基础数据表示体系。

**2.2 Scaled Dot-Product Attention**：完整推导Attention计算公式，深度拆解矩阵乘法、Softmax归一化、Value聚合的全过程，明确各环节的计算复杂度。

**2.3 Multi-Head Attention**：理解多头注意力机制提升模型特征表达能力的原理，掌握注意力头切分逻辑，及其对后续Tensor并行设计的影响。

**2.4 FlashAttention思想**：学习FlashAttention块状计算核心逻辑，掌握其减少HBM显存访问的优化原理，建立「IO复杂度优先级高于计算复杂度」的GPU优化核心思维。

**2.5 KV Cache与推理计算**：讲解推理阶段KV Cache的数据组织与存储方式，对比分析训练、推理两个阶段Attention的计算路径差异。

### Chapter 3 MLP与归一化

**3.1 Feed Forward Network**：掌握Transformer中MLP的基础结构、特征扩维比例，以及各类激活函数的功能与适用场景。

**3.2 LayerNorm与RMSNorm**：拆解两种归一化方式的计算流程、参数量差异与计算特性，理解不同归一化设计的工程优化逻辑。

**3.3 Residual Connection**：吃透残差连接的数据流逻辑，明确其对模型梯度传播、Tensor显存生命周期的关键影响。

### Chapter 4 模型资源分析

**4.1 参数量计算**：掌握基于模型配置推导总参数量的方法，建立各核心模块参数占比的直观认知。

**4.3 Memory组成**：解析参数、激活值、梯度、优化器状态四类核心显存的构成逻辑，为后续显存优化搭建统一分析模型。

## 展开 0.1 Transformer 整体结构

---

### ① 形式化定义

Transformer 是当前所有大语言模型的基础架构。其核心设计是**用自注意力机制替代循环结构，实现序列元素的并行计算**。

一个 Transformer 模型由 **L 层** 相同的 Block 堆叠而成，每个 Block 包含两个子层：

```
输入 x ∈ R^{S×d}      （S: 序列长度, d: 隐藏维度）

for layer in 1..L:
    x = x + SelfAttention(LayerNorm(x))     # 子层1
    x = x + MLP(LayerNorm(x))               # 子层2
return x
```

**0.1.1 三种架构变体**

| 类型 | 代表模型 | 自注意力方式 | 用途 |
|------|---------|-------------|------|
| Encoder-only | BERT | 双向（能看到前后所有 token） | 理解任务 |
| Decoder-only | GPT, Llama | 因果掩码（只能看到当前及之前 token） | 生成任务 |
| Encoder-Decoder | T5 | Encoder 双向 + Decoder 因果 | 翻译、摘要 |

我们后续所有的讨论都基于 **Decoder-only** 架构（GPT/Llama 类），这是当前 LLM 的主流。

**0.1.2 Block 的内部组件**

一个 Decoder Block 由以下算子组成：

```
x_norm = RMSNorm(x)                    # 1. 前置归一化
q, k, v = Linear_Q(x_norm), Linear_K(x_norm), Linear_V(x_norm)  # 2. QKV投影（三组矩阵乘）
attn_out = Attention(q, k, v, mask)    # 3. 因果自注意力
x = x + Linear_O(attn_out)            # 4. 输出投影 + 残差

x_norm2 = RMSNorm(x)
mlp_out = Linear_up(x_norm2)          # 5. MLP上投影
mlp_out = Activate(mlp_out)           # 6. 激活函数（SwiGLU/GELU）
mlp_out = Linear_down(mlp_out)        # 7. MLP下投影
x = x + mlp_out                       # 8. 残差连接
```

**关键参数**：隐藏维度 `d`，注意力头数 `h`，每头维度 `d_head = d/h`，MLP 中间维度 `d_ff`（通常是 `d` 的 2.5~4 倍）。

---

### ② 系统视角

**在整个知识树中的位置**：`0.1` 是最顶层的“模型长什么样”的描述，是所有后续并行切分的**被切分对象**。

**输入**：一个 token 序列（`[token_1, token_2, ..., token_S]`），经过 Embedding 层转为 `S×d` 的张量。

**输出**：同样形状 `S×d` 的张量，经过最后的 LM Head 投影到词表维度，产生下一个 token 的概率分布。

**数据流**（单层 Block 内）：

```
(S, d) ──QKV投影──> 3个 (S, d) 矩阵
                     │
                     ├──> 重塑为 (h, S, d_head)
                     ├──> Attention 计算 → (S, d)
                     ├──> 残差 + → (S, d)
                     └──> MLP → (S, d) → 残差 + → (S, d)
```

**训练时的依赖**：
- 前向：需要保存每一层的 **激活值** 用于反向计算（占用大量显存，参考 0.6）
- 反向：梯度从输出端向输入端逐层流回

**与并行策略的直接关系**（预览）：
- `TP`：将 QKV 的列或 Attention 的行切分到多 GPU
- `PP`：将不同层分配给不同 GPU
- `DP`：每个 GPU 持有完整模型，但处理不同数据

---

### ③ 工程映射

**PyTorch 中一个 Decoder Block 的伪代码**：

```python
class TransformerBlock(nn.Module):
    def __init__(self, d, h, d_ff):
        self.attn_norm = RMSNorm(d)
        self.q_proj = nn.Linear(d, d, bias=False)
        self.k_proj = nn.Linear(d, d, bias=False)
        self.v_proj = nn.Linear(d, d, bias=False)
        self.o_proj = nn.Linear(d, d, bias=False)
        self.mlp_norm = RMSNorm(d)
        self.up_proj = nn.Linear(d, d_ff, bias=False)
        self.down_proj = nn.Linear(d_ff, d, bias=False)
        self.act = SwiGLU()  # Llama 使用

    def forward(self, x):
        # Self-Attention 子层
        residual = x
        x = self.attn_norm(x)
        q, k, v = self.q_proj(x), self.k_proj(x), self.v_proj(x)
        attn_out = self.attention(q, k, v)  # 包含 softmax 等
        x = residual + self.o_proj(attn_out)

        # MLP 子层
        residual = x
        x = self.mlp_norm(x)
        x = self.down_proj(self.act(self.up_proj(x)))
        x = residual + x
        return x
```

**在 Megatron-LM 中**：这个 Block 会被 `TP` 改造——`q_proj` 的列被切分到不同 GPU（见 2.2.3）。

**在 DeepSpeed 中**：Block 保持不变，但它的参数和优化器状态可能被 ZeRO 分片（见 6.2）。

### ④ 复杂度分析

**参数量**（单层 Decoder Block）：

| 组件 | 参数量 | 说明 |
|------|--------|------|
| QKV 投影 | 3 × d² | 三个 d×d 矩阵 |
| 输出投影 | d² | |
| MLP 上投影 | d × d_ff | |
| MLP 下投影 | d_ff × d | |
| RMSNorm | 2d | 极小，可忽略 |
| **单层合计** | 4d² + 2·d·d_ff | |

若 d_ff = 3d（典型值），则单层参数量 ≈ 10d²。总参数量 ≈ L × 10d² + 嵌入层（V×d）。

**计算量（FLOPs）**：
- 一次矩阵乘 [S×d] × [d×d] 约需 2Sd² FLOPs
- 单层前向约需 24 S d² FLOPs（含 Attention 的 S²d 项，但大模型下 S ≪ d，S²d 项相对小）
- 反向约为前向的 2 倍

**显存占用**（训练时单层主要部分）：
- 模型参数：约 40 d² bytes（FP16）
- 优化器状态：约 120 d² bytes（Adam FP32）
- 激活值：约 S × d × layers × 2 bytes（简化估算，实际复杂）

---

### ⑤ 设计权衡

**1. d_ff 的选择**：增大 d_ff 提升模型容量但显著增加参数量。Llama 系列用了 d_ff ≈ 8/3 d ~ 3.5d，在容量与效率间平衡。

**2. 注意力头的数量**：头数多 → 每个头维度小，可能损失表示能力；头数少 → 计算效率高但多样性低。这直接影响后续 TP 的切分粒度（头数必须能被 TP 并行度整除）。

**3. 归一化位置**：Post-LN（原始 Transformer）训练不稳定，需要学习率 warmup。Pre-LN（现在主流）将归一化放在子层之前，训练更稳定，但残差累积可能稍弱。RMSNorm 是 LayerNorm 的简化版，去掉了中心化操作，更快。

**4. 这个结构为什么需要分布式**：
- 70B 参数，FP16 下权重本身占 140GB，单张 A100 (80GB) 根本放不下。
- 即使 13B 放得下，加上优化器状态和激活，显存依然不够。
- 即使单卡放得下，训练速度也无法接受（需要多卡加速）。

## 展开 0.2 Self-Attention 的计算分解

---

### ① 形式化定义

Self-Attention 是一个序列到序列的变换，它让序列中每个位置都能直接聚合其他位置的信息。对于 Decoder-only 模型，使用 **因果掩码**，即位置 i 只能看到位置 ≤ i 的信息。

给定输入 `X ∈ R^{S×d}`（S: 序列长度, d: 隐藏维度），单头注意力：

```
Q = X @ W_Q        # (S, d) × (d, d_head) → (S, d_head)
K = X @ W_K
V = X @ W_V

Scores = Q @ K^T   # (S, d_head) × (d_head, S) → (S, S)
Scores = Scores / sqrt(d_head)
Scores = softmax(Scores + causal_mask)   # mask 上三角为 -inf

Output = Scores @ V   # (S, S) × (S, d_head) → (S, d_head)
```

**多头注意力** 将 d 分割为 h 个头，每头维度 `d_head = d/h`，每个头独立执行上述过程，最后拼接：

```
MultiHead(X) = Concat(head_1, ..., head_h) @ W_O
```

其中 `W_O ∈ R^{d×d}` 为输出投影矩阵。

**因果掩码** 的数学形式：

```
causal_mask[i, j] = 0       if i >= j
causal_mask[i, j] = -inf    otherwise
```

---

### ② 系统视角

**在整个知识树中的位置**：`0.2` 深入了 `0.1` 中 Transformer Block 里最复杂的子层。它是：

- **并行切分的核心目标**：TP（2.2）正是切分这些 QKV 矩阵和注意力头
- **显存压力的主要来源**：传统注意力需要存储 `S×S` 的分数矩阵（0.2.2）
- **FlashAttention 优化的起点**（0.2.3）

**输入/输出**：

- **输入**：`X ∈ R^{S×d}`（由前置 RMSNorm 归一化后的序列表示）
- **输出**：`R^{S×d}`，与输入同形状，经过残差连接加回原始输入

**计算流在 GPU 上的映射**：

```
X (S,d) 
  ├─ QKV 投影：三个矩阵乘，每个都是 S×d × d×d_head，输出 S×d_head
  │   - 这是 BLAS GEMM，高度优化，compute-bound
  │
  ├─ Scores = Q @ K^T：S×d_head × d_head×S → S×S
  │   - 当 S 大时（如 4096），S×S 矩阵显存很大
  │
  ├─ Softmax + Mask：逐元素操作，memory-bound
  │
  ├─ Output = Scores @ V：S×S × S×d_head → S×d_head
  │   - 又是一个 GEMM，但 S×S 矩阵需从 HBM 反复读写
  │
  └─ 输出投影：S×d × d×d → S×d，compute-bound
```

**依赖关系**：需要理解 `1.0.2` 的存储层次（HBM vs SRAM）才能理解 FlashAttention 为何快。

---

### ③ 工程映射

**PyTorch 朴素实现**（训练时会直接使用，但很慢且费显存）：

```python
def self_attention(q, k, v, causal_mask):
    # q, k, v: (batch, heads, seq_len, d_head)
    scale = q.size(-1) ** -0.5
    attn_weights = torch.matmul(q, k.transpose(-2, -1)) * scale
    attn_weights = attn_weights + causal_mask
    attn_weights = torch.softmax(attn_weights, dim=-1)
    output = torch.matmul(attn_weights, v)
    return output
```

**FlashAttention**（通过 `torch.nn.functional.scaled_dot_product_attention` 调用）：

```python
# PyTorch 2.0+ 会自动启用 FlashAttention，无需修改代码
output = F.scaled_dot_product_attention(q, k, v, attn_mask=causal_mask)
```

**工程对应关系**：
- `0.2.1` QKV 投影 → `nn.Linear`，在 Megatron 中通过 `ColumnParallelLinear` 切分（2.2.3）
- `0.2.2` Attention Score + Softmax → FlashAttention kernel（避免 S×S 显存）
- `0.2.3` 块状计算思想 → 下一节展开

---

### ④ 复杂度分析

**计算量（单层，单头）**：

| 操作 | FLOPs | 备注 |
|------|-------|------|
| QKV 投影 | 3 × 2S·d·d_head | d_head = d/h，三头总计 ≈ 6Sd²/h |
| Q @ K^T | 2S²·d_head | 当 S=4096, d_head=128 → 4.3M |
| Softmax | 2S² (近似) | memory-bound |
| V 加权 | 2S²·d_head | |
| 输出投影 | 2S·d² | |
| **总计** | ≈ 4Sd²/h + 4S²d_head + 2Sd² | S 小时第一项主导，S 大时 S² 项主导 |

**显存占用（传统实现）**：

- Q, K, V：各 `S × d_head × 2 bytes` (FP16)，对 h 个头需 ×h
- 注意力分数矩阵 `S×S`：FP16 下 `S² × 2` bytes
  - S=4096 → 32 MB；S=8192 → 128 MB
  - 看起来不大？但有 batch 和多层，且反向时这个矩阵也需要存储，实际会爆显存
- **最大瓶颈**：反向传播需要保存前向的 S×S 分数矩阵用于梯度计算，多层、多 batch 累积后显存巨大

---

### ⑤ 设计权衡

**1. 多头的数学本质**
多头允许模型在不同子空间捕捉关系，但头数不是越多越好。头数多 → d_head 小，表达能力可能下降；头数少 → 注意力多样性不足。实际中 d_head 通常在 64~128 之间（Llama-7B: h=32, d=4096, d_head=128）。

**2. 因果掩码的必要性**
训练时必须使用因果掩码以保证自回归特性，但推理时如果使用 KV cache，每条新 token 只需计算与已有 cache 的注意力，不需要掩码。这是推理优化的核心。

**3. 标准实现 vs FlashAttention**
传统方法显存 `O(S²)`，FlashAttention 通过分块计算和在线 softmax，将显存降到 `O(S)`（见 0.2.3）。代价是实现复杂，需要 CUDA kernel 编写。这也是 `0.2.3` 节点的核心内容——为后续理解通信优化（通信也是分块）打基础。

**4. 序列长度 S 对并行策略的影响**
当 S 很长（如 128K），S² 项占主导，TP 切分头只能减小 d_head 相关的计算/通信量，无法解决 S² 的显存问题。此时需要 **序列并行（SP）**（1.2.5）将序列维度也切分开。

## 展开 0.3 MLP 块的计算与参数量

---

### ① 形式化定义

MLP（多层感知机）块是 Transformer Block 中的第二个子层，它独立作用于序列中每个位置（即 token-wise），不涉及 token 间交互。其标准形式为：

```
MLP(x) = DownProjection( Activation( UpProjection(x) ) )
```

具体张量变换：

```
x ∈ R^{S×d}                          # 输入，来自 Attention 子层的残差结果

h = x @ W_up^T    ∈ R^{S×d_ff}       # 上投影，W_up ∈ R^{d_ff×d}
h = σ(h)          ∈ R^{S×d_ff}       # 激活函数
out = h @ W_down^T ∈ R^{S×d}         # 下投影，W_down ∈ R^{d×d_ff}
```

其中 `d_ff` 为中间维度，通常 `d_ff = expansion_factor × d`。

**参数量**：`W_up` 和 `W_down` 各提供 `d × d_ff` 个参数，合计 `2·d·d_ff`。

---

### ② 系统视角

**在整个知识树中的位置**：`0.3` 补完了 `0.1` 中 Transformer Block 的两大核心计算模块之一。它与 `0.2` 的 Self-Attention 并列：

- Attention：**跨 token 交互**，计算量包含 `O(S²·d)`，是序列长度敏感部分
- MLP：**每 token 独立变换**，计算量 `O(S·d·d_ff)`，是模型容量敏感部分

**输入/输出**：
- **输入**：Self-Attention 子层输出加上残差连接后的 `(S, d)` 张量，已通过第二个 RMSNorm
- **输出**：同形状 `(S, d)`，再与输入做残差连接进入下一层

**在 GPU 上的映射**：

```
x (S,d) 
  ├─ Linear Up (GEMM): S×d × d×d_ff → 输出 (S, d_ff)
  │    这是大矩阵乘，compute-bound
  │    
  ├─ Activation: 逐元素操作，memory-bound
  │    常见：GELU, SiLU, SwiGLU (涉及两个上投影的逐元素乘)
  │
  └─ Linear Down (GEMM): S×d_ff × d_ff×d → (S, d)
       也是大矩阵乘，compute-bound
```

**与并行的关联**：
- TP（2.2）可将 `W_up` 按**列**切分、`W_down` 按**行**切分，中间激活在 GPU 间仅需局部计算，通信只需一次 All-Reduce（或 Reduce-Scatter）
- PP（3）可将不同层的 MLP 分布在不同 GPU
- ZeRO（4.4）可对 MLP 的权重和优化器状态进行分片

---

### ③ 工程映射

**PyTorch 中典型 MLP 实现（Llama 的 SwiGLU 变体）**：

```python
class LlamaMLP(nn.Module):
    def __init__(self, d, d_ff):
        super().__init__()
        self.gate_proj = nn.Linear(d, d_ff, bias=False)   # W_gate
        self.up_proj = nn.Linear(d, d_ff, bias=False)     # W_up
        self.down_proj = nn.Linear(d_ff, d, bias=False)   # W_down
        self.act_fn = nn.SiLU()                            # Swish

    def forward(self, x):
        # SwiGLU: element-wise gate * act(up)
        gate = self.act_fn(self.gate_proj(x))              # SiLU(W_gate @ x)
        up = self.up_proj(x)
        h = gate * up                                      # 逐元素乘，维度 d_ff
        return self.down_proj(h)
```

**参数量与原始双线性不同**：SwiGLU 需要三个投影矩阵（gate, up, down），参数量 `3·d·d_ff` 而非 `2·d·d_ff`。为了保持总参数量与传统 MLP 相近，Llama 实际将 `d_ff` 调整为 `8/3 d`，这样 `3·d·(8/3 d) = 8d²`，与标准 `2·d·4d = 8d²` 一致。

**对应到 Megatron-LM**：
- `ColumnParallelLinear` 切分 `gate_proj` 和 `up_proj` 的列（d_ff 维度）
- `RowParallelLinear` 切分 `down_proj` 的行（d_ff 维度），并在输出端 All-Reduce

**对应到 DeepSpeed**：
- ZeRO-1 对 MLP 参数的所有 reduce 梯度进行分片通信
- ZeRO-3 直接将 `gate_proj, up_proj, down_proj` 参数分布存储在不同 GPU，按需 All-Gather

---

### ④ 复杂度分析

**计算量（单层 MLP，SwiGLU 为例）**：

| 操作 | FLOPs | 备注 |
|------|-------|------|
| gate_proj (S×d × d×d_ff) | 2S d d_ff | GEMM |
| up_proj (S×d × d×d_ff) | 2S d d_ff | GEMM |
| Activation (SiLU) | ~S d_ff | memory-bound |
| Gate * Up (element-wise) | S d_ff | memory-bound |
| down_proj (S×d_ff × d_ff×d) | 2S d d_ff | GEMM |
| **总计** | ≈ 6S d d_ff | （忽略低阶项） |

以 Llama-7B 为例：d=4096, d_ff=11008, S=4096。

单层 MLP FLOPs ≈ 6 × 4096 × 4096 × 11008 ≈ 1.1 × 10^12 FLOPs = 1.1 TFLOPs。

**显存占用**：
- 权重参数：`3·d·d_ff × 2 bytes` (FP16) ≈ 3×4096×11008×2 ≈ 270 MB
- 激活：中间输出 `(S, d_ff)` 需存储 `S × d_ff × 2 bytes` ≈ 4096×11008×2 ≈ 90 MB

**对比 Attention**：当 S=4096 时，Attention 的 FLOPs ≈ 4S²d ≈ 4×16.8M×4096 ≈ 0.27 TFLOPs。MLP 的计算量（1.1T）远大于 Attention（0.27T）。因此大模型训练中 **MLP 是计算的主要瓶颈**，而 Attention 是显存的主要瓶颈（S² 矩阵）。

---

### ⑤ 设计权衡

**1. 扩维因子（expansion factor）**
标准 Transformer 使用 4×，Llama 类使用约 8/3× 但配合 SwiGLU 的 3 个矩阵，等效计算量相当。扩维因子直接决定模型容量与计算成本：增大 d_ff 提升模型能力，但参数和 FLOPs 线性增长。

**2. 激活函数选择**
- GELU：平滑，但计算稍贵
- ReLU：简单，但可能死神经元
- SiLU（Swish）：自门控，配合 SwiGLU 在开源模型中有较好表现
不同激活函数影响收敛行为，但对并行策略和通信量影响很小。

**3. MLP 是否可融合**
由于 MLP 的 GEMM 占主导，kernel 融合（如将激活函数和逐元素乘法融入一个 kernel）收益有限，主要开销仍是矩阵乘。但 NCCL 通信重叠可与 MLP 计算并行（见 5.2.4）。

**4. 对并行的启发**
MLP 的高计算量（大 GEMM）使得它在 **TP 切分** 时效率很高：每个 GPU 处理部分列/行，计算量成倍减小，而需要的通信只是一次 All-Reduce（通信量仅为输出 `S×d`）。计算 - 通信比高，适合 TP。这也是 Megatron 优先对 MLP 做 TP 的原因之一。

## 展开 0.4 层归一化与残差连接

---

### ① 形式化定义

**层归一化（LayerNorm）**

对输入 `x ∈ R^d`（d 为隐藏维度），LayerNorm 计算：

```
μ = (1/d) Σ_i x_i
σ² = (1/d) Σ_i (x_i - μ)²
y_i = γ_i * (x_i - μ) / √(σ² + ε) + β_i
```

其中 `γ, β ∈ R^d` 是可学习参数，`ε` 是防止除零的小常数（如 1e-5）。

**RMSNorm（Root Mean Square Layer Normalization）**

去除了中心化（减均值）操作，仅用均方根统计量：

```
RMS(x) = √( (1/d) Σ_i x_i² )
y_i = γ_i * x_i / RMS(x)
```

相比 LayerNorm，RMSNorm **不减去均值，不使用 β 偏移参数**，计算更简洁。Llama、Mistral 等模型使用 RMSNorm。

**残差连接（Residual Connection）**

```
output = x + F(x)
```

其中 `F(x)` 为 Attention 或 MLP 子层的输出。残差连接将输入直接加到子层输出上，是 Transformer 可堆叠深层的核心机制。

---

### ② 系统视角

**在整个知识树中的位置**：`0.4` 是 Transformer Block 中参数最少、但训练稳定性至关重要的组件。它与 `0.2`（Attention）和 `0.3`（MLP）并列，共同构成 `0.1` 的完整 Block。

**具体位置**：在每个子层**前**应用（Pre-Norm 风格）。

```
x ── Norm ── Attention ── + ── Norm ── MLP ── + ──→ 下一层
```

**输入/输出**：

- **LayerNorm/RMSNorm**：输入 `x ∈ R^{S×d}`，输出同形状。沿最后一维（d）归一化，对每个 token 独立操作。
- **残差连接**：将子层输入与子层输出按元素相加，形状不变。

**在训练流程中的角色**：

- **稳定训练**：归一化将输入限制在稳定数值范围，防止梯度爆炸/消失。
- **残差的显存代价**：残差连接需要在前向时保存**子层输入**（即 `x`），用于反向传播时的梯度计算。这是激活显存的重要组成部分（详见 0.6）。

**与并行策略的关系**：

- 归一化是 token-wise 操作，不涉及 token 间通信，因此在 TP 切分中无需额外通信。
- 残差连接产生需存储的激活，影响 ZeRO 和激活检查点的决策（6.2.3）。

---

### ③ 工程映射

**PyTorch 实现**：

```python
# LayerNorm
ln = nn.LayerNorm(d, eps=1e-5)
# 内部维护 self.weight (γ) 和 self.bias (β)

# RMSNorm (Llama 风格)
class RMSNorm(nn.Module):
    def __init__(self, d, eps=1e-6):
        super().__init__()
        self.weight = nn.Parameter(torch.ones(d))
        self.eps = eps

    def forward(self, x):
        # x: (batch, seq_len, d)
        rms = torch.sqrt(torch.mean(x ** 2, dim=-1, keepdim=True) + self.eps)
        return x / rms * self.weight
```

**在 HuggingFace Transformers 中**：
- Llama 使用 `LlamaRMSNorm`，代码同上。
- GPT-2 等使用标准 `nn.LayerNorm`。

**残差连接**：直接写 `x = x + attention_out`，PyTorch 的自动求导引擎会自动保存 `x` 用于反向。

**在 DeepSpeed 中**：归一化参数也会被 ZeRO 分片（ZeRO-3），但因其参数量极小，不分片也无妨。

---

### ④ 复杂度分析

**参数量**：

| 组件 | 参数量 | 示例（d=4096） |
|------|--------|----------------|
| LayerNorm | 2d (γ+β) | 8192 |
| RMSNorm | d (仅γ) | 4096 |
| 残差连接 | 0 | — |

与 MLP 的 `d×d_ff`（千万级）相比，归一化参数可忽略不计。

**计算量（FLOPs）**：

- LayerNorm：约 `5 S d`（统计量 + 归一化 + 仿射）
- RMSNorm：约 `3 S d`（平方求和 + 归一化 + 缩放）
- 残差连接：`S d`（逐元素加）

对比 MLP 的 `6 S d d_ff` 量级，归一化和残差的计算几乎免费。

**显存占用**：

- **参数**：归一化权重，极小，FP16 下仅 KB 级。
- **激活存储**：残差连接需保存子层输入 `x`，形状 `(S, d)`，FP16 下 `2 S d` bytes。对 L 层、batch size B，总激活中残差存储可达 `B × L × 2 S d`，成为不可忽略的显存项。

---

### ⑤ 设计权衡

**1. LayerNorm vs RMSNorm**

| 特性 | LayerNorm | RMSNorm |
|------|-----------|---------|
| 计算 | μ 和 σ 都算 | 只算 RMS |
| 参数 | γ, β | 仅 γ |
| 速度 | 较慢 | 快约 15% |
| 效果 | 经典稳定 | 实测相当，甚至更好 |

RMSNorm 因省略减均值操作，计算图和反向传播更简单，在 Llama 类模型中成为主流。

**2. Pre-Norm vs Post-Norm**

原始 Transformer（Post-Norm）：`x = Norm(x + F(x))`
现代 LLM（Pre-Norm）：`x = x + F(Norm(x))`

- **Post-Norm**：残差路径无归一化，深层梯度可能爆炸，需要学习率 warmup。
- **Pre-Norm**：归一化在子层前，残差路径纯净，训练更稳定，无需复杂 warmup。代价是残差累积可能使表示偏大，但实测影响甚微。

当前所有主流开源 LLM 均采用 Pre-Norm。

**3. 残差连接的显存代价**

残差连接虽不引入参数，但迫使存储每层的子层输入。在 80 层、S=4096、d=8192 的模型中，仅残差激活就达数十 GB。**激活检查点**（6.2.3）可重算这些中间值以换显存，但会增加计算。这是显存优化的重要权衡。

**4. 对并行的适应性**

- 归一化和残差是独立作用于每个 token 的，天然适合数据并行（DP）和张量并行（TP）——因为每个 GPU 上的 token 或部分维度可独立完成。
- 在 TP 切分中，如果输出维度被切分（如 Attention 的 head 维度），残差连接也需要在切分的维度上局部相加，通信仅在需要完整张量时发生。

## 展开 0.5 参数量与计算量估算（FLOPs）

---

### ① 形式化定义

给定一个 Decoder-only Transformer 模型配置，可以从以下公式精确估算其**总参数量**和**单次前向/反向的计算量（FLOPs）**。

**参数量公式**

设模型具有 L 层 Transformer Block，隐藏维度 d，注意力头数 h，每头维度 d_head = d/h，MLP 中间维度 d_ff，词表大小 V。忽略位置编码和 LayerNorm 的微小参数：

```
嵌入层参数 = V × d

单层 Attention 参数 = 4d²            （Q、K、V、O 四个投影矩阵，各 d×d）

单层 MLP 参数（SwiGLU）= 3·d·d_ff    （gate、up、down 三个投影）

单层参数总计 = 4d² + 3·d·d_ff

总参数 ≈ V·d + L × (4d² + 3·d·d_ff)
```

对于非 SwiGLU 的 MLP（如 GPT-2 的 GELU），单层 MLP 参数为 2·d·d_ff。

**计算量公式（FLOPs）**

一次矩阵乘法 `A ∈ R^{m×k} × B ∈ R^{k×n}` 的理论浮点运算次数为 `2·m·k·n`（一次乘加对应两个 FLOP）。

设输入序列长度为 S，则：

```
前向 FLOPs ≈ 2·S·总参数量 + 2·L·S²·d     （第一项为线性投影，第二项为注意力分数计算）
```

更精确地按子模块分解（SwiGLU）：

| 子模块 | 前向 FLOPs |
|--------|-----------|
| QKV 投影 | 3 × 2·S·d·d ≈ 6 S d² |
| 输出投影 | 2 S d² |
| Q·K^T | 2 S² d |
| Softmax·V | 2 S² d |
| MLP gate + up | 2 × 2 S d d_ff = 4 S d d_ff |
| 激活函数 | S d_ff（忽略） |
| MLP down | 2 S d d_ff |
| 嵌入层 | 2 S V d（可忽略，仅首次） |

合并：

```
单层前向 ≈ 8 S d² + 4 S² d + 6 S d d_ff

总前向 ≈ L × (8 S d² + 4 S² d + 6 S d d_ff) + 2 S V d
```

**反向传播 FLOPs**：理论上是前向的 **2 倍**（每层需计算对输入的梯度和对权重的梯度）。实践中常数因子约为 2~3。

---

### ② 系统视角

**在整个知识树中的位置**：`0.5` 是第 0 节的汇总节点，它将 0.1~0.4 的模型组件信息转化为**可用于资源规划的数量化指标**。它是连接模型结构（0.x）与并行/显存分析（1.x~4.x）的桥梁。

**输入**：
- 模型配置：d, L, d_ff, h, V, S
- 组件结构：0.1~0.4

**输出**：
- 总参数量（直接影响显存需求：模型权重 + 优化器状态）
- 总 FLOPs（直接影响训练时间：与 GPU 算力比较得到预估时间）

**在分布式训练决策中的角色**：
- **参数量** → 决定是否必须使用模型并行（TP/PP）或 ZeRO-3（单卡放不下权重）
- **总 FLOPs** → 决定需要多少 GPU 小时，以及弱扩展效率分析（7.3）
- **Attention 中的 S² 项** → 判断序列并行（SP）是否必要
- **计算 - 通信比** → 指导 TP vs DP 的策略选择（7.2）

**依赖关系**：`0.5` 是 `1.1 显存模型` 和 `7.2 计算-通信比分析` 的直接输入。

### ③ 工程映射

**在 HuggingFace Transformers 中获取参数量**：

```python
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-2-7b-hf")
print(f"参数量: {sum(p.numel() for p in model.parameters()) / 1e9:.2f}B")
```

**估算 FLOPs 的社区方法**（基于上述公式）：

```python
def estimate_flops_forward(L, d, d_ff, h, V, S):
    # 注意力部分
    flops_attn = L * (8 * S * d**2 + 4 * S**2 * d)
    # MLP 部分（SwiGLU）
    flops_mlp = L * 6 * S * d * d_ff
    # 嵌入层
    flops_emb = 2 * S * V * d
    return flops_attn + flops_mlp + flops_emb

# 示例：Llama-2-7B, S=4096
flops = estimate_flops_forward(32, 4096, 11008, 32, 32000, 4096)
print(f"前向 FLOPs: {flops / 1e12:.2f} TFLOPS")
```

- **nvidia-smi / ncu**：查看 SM 占用和计算吞吐

**注意**：理论 FLOPs 与 GPU 峰值算力的比值 ≠ 实际利用率（MFU）。MFU 受限于内存带宽、Kernel 启动开销、非矩阵乘操作（softmax, layernorm）等。

### ④ 复杂度分析

**参数量缩放**：

- 参数由 `12 d² L` 主导（当 d_ff ≈ 3.5 d 时）
- 模型规模主要靠增加 d（更深影响参数 O(d²)，更宽影响 O(d²)）和 L（线性）控制
- Llama-7B → 70B：d 从 4096 → 8192, L 从 32 → 80，参数量增加约 10×，计算量增加约 10×（同时 S 增加）

**FLOPs 缩放**：

- 当 S ≪ d（常见于短序列），主要计算来自 `L × 8 S d²` → **与 d² 成正比**
- 当 S 增长，`L × 4 S² d` 开始显著 → **超长序列下注意力成瓶颈**
- 实际 LLM 训练中 S 通常从 2048 逐步增长到 8192 或更长，后期 S² 项不可忽略

**与显存的关系**：

- 参数量 × 精度直接占据显存：FP16 模型权重占 `2×参数量` bytes，优化器状态（Adam FP32）约 `12×参数量` bytes
- 正向激活（主要由残差和注意力中间结果构成）与 S 和 L 相关，使用 FlashAttention 可大幅降低注意力中间结果
- 总显存需求 = 权重 + 优化器 + 激活，对应 `0.6` 的显存生命周期

---

### ⑤ 设计权衡

**1. d 与 L 的权衡**：扩大 d（隐藏维度）比增加 L（层数）更“昂贵”（参数量平方增长），但能更有效地提升模型容量。所以小模型往往更“窄而深”，大模型则“宽而适中深”。

**2. 序列长度的影响**：训练长上下文模型（如 S > 8192）时，FLOPs 中 S² 项显著增加，可能导致计算资源需求大幅超出预期。此时 FlashAttention 仅降低显存，不降低理论 FLOPs（略增），但通过消除 memory-bound 可大幅提升实际速度。此外，**序列并行（SP）** 可切分序列维度以分摊注意力计算。

**3. 批次大小的选择**：总 FLOPs 正比于 S 和 batch size B。增大 B 可直接提高 GPU 利用率（更高 occupancy），但会消耗更多显存，可能导致梯度累积需求变化。在 DP 场景下，B 和通信量无关；在 TP 场景下，B 不影响通信量（通信量只与 S 和 d 相关）。

**4. 精度的影响**：FP16/BP16 训练可将计算吞吐翻倍（相对 FP32），但需处理数值稳定性。混合精度训练（AMP）中，部分敏感操作仍用 FP32，实际 FLOPs 计算时需考虑精度混合。

**5. 实际 MFU 的差距**：理论计算量是硬件选型的起点，但实际训练效率（MFU）通常在 50%~60%（良好优化下）。并行策略带来的通信开销将进一步降低有效吞吐。这正是后续节点 `7.3 扩展效率` 要回答的核心问题。

## 展开 0.6 单GPU训练循环：计算图与显存生命周期

---

### ① 形式化定义

单 GPU 训练的一次迭代（一个 micro-batch step）可以分为三个阶段：**前向传播（Forward）**、**反向传播（Backward）**、**优化器更新（Optimizer Step）**。每个阶段对 GPU 显存的需求和释放模式不同。

设模型参数为 θ（总参数量 P），数据为单个 micro-batch（batch size B，序列长度 S），使用混合精度训练（AMP），优化器为 Adam。显存占用的主要项目包括：

- **模型权重（FP16）**：`B_weights = 2P` bytes
- **FP32 主权重**：`B_master = 4P` bytes（用于更新参数，避免 FP16 精度不足）
- **优化器状态**：
  - 动量 m：`4P` bytes（FP32）
  - 方差 v：`4P` bytes（FP32）
  - 合计 `8P` bytes
- **前向激活**：`B_act = f(B, S, L, d, d_ff, ...)` bytes（子层中间结果，用于反向重算梯度）
- **梯度**：`B_grad = 2P` bytes（FP16，与权重对应；但通常在反向时临时分配/累加）

**训练循环形式化表示**：

```
1. 前向: 对每个层 l=1..L:
           x = x + F_l(Norm(x))   # 生成激活 a_l，存入显存
           （若使用激活检查点，仅保存部分层的输入）
2. 计算 loss = CrossEntropy(logits, labels)
3. 反向: 对每个层 l=L..1:
           读取 a_l（或重算），计算对权重的梯度 g_l 和对输入的梯度
           将 g_l 累加到参数梯度缓冲区
4. 优化器更新:
           m_t = β₁ m_{t-1} + (1-β₁) g   （FP32）
           v_t = β₂ v_{t-1} + (1-β₂) g²
           θ_fp32 = θ_fp32 - lr * m_t / (√v_t + ε)
           θ_fp16 = cast(θ_fp32)
```

**显存生命周期**：显存占用在反向传播的某个时刻达到峰值——此时仍有未释放的前向激活，同时梯度开始产生，且参数和优化器状态恒定驻留。

---

### ② 系统视角

**在整个知识树中的位置**：`0.6` 是第 0 节的终点，将 0.1~0.5 的模型结构、算子计算、参数量和 FLOPs 知识**统一到单 GPU 训练的物理资源约束**下。它是“为什么需要分布式”的直接回答——因为单卡显存装不下完整的训练状态。

**输入**：
- 模型配置：从 0.5 获得参数量 P
- 数据形状：B, S
- 算子行为：从 0.2~0.4 了解各层产生的激活大小

**输出**：
- 显存需求峰值估算（Peak Memory）
- 给定 GPU 容量，判断是否 OOM（Out of Memory）
- 为并行策略（1.2）提供切分动机：每个并行策略的目标就是**降低这个峰值**，使其落到单卡容量内

**依赖关系**：

```
0.5 参数量/FLOPs 估算
        +
0.6 显存生命周期 ← 0.2, 0.3, 0.4 组件激活大小
        ↓
1.1 单 GPU 显存约束模型（形式化峰值估算）
        ↓
4.4 ZeRO 冗余消除（优化器、梯度、参数分片）
```

---

### ③ 工程映射

**PyTorch 中的训练循环模板**：

```python
optimizer = AdamW(model.parameters(), lr=lr)
scaler = GradScaler()  # 混合精度

for batch in dataloader:
    optimizer.zero_grad()
    with autocast(device_type='cuda', dtype=torch.float16):
        output = model(batch)
        loss = loss_fn(output, labels)
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
```

**显存分配的内部行为**：

- `autocast` 将大部分线性层和卷积转为 FP16，但归一化、softmax 等可能保持在 FP32（由框架决定）。
- `loss.backward()` 启动自动求导引擎，它按前向计算图的反序遍历，保留必要的中间张量（激活）直到对应层的梯度计算完成。
- PyTorch 的 autograd 会为每个需要梯度的张量保存 `.grad` 缓冲区。默认情况下，梯度会在反向过程中累加，`zero_grad()` 将其置零。

**激活检查点（Activation Checkpointing）**：

```python
# 使用 torch.utils.checkpoint 手动标记
def custom_block(x):
    return MLP(Attention(x))

x = checkpoint(custom_block, x)
```

反向时不再使用保存的中间激活，而是重新前向计算该 block。等效于**用计算换显存**。

**查看显存使用**：

```python
print(f"Allocated: {torch.cuda.memory_allocated()/1e9:.2f} GB")
print(f"Cached: {torch.cuda.memory_reserved()/1e9:.2f} GB")
```

或在命令行使用 `nvidia-smi` 实时监控。

---

### ④ 复杂度分析

**显存占用模型（简化）**：

设模型参数量 P（FP16 权重 2P 字节）。对于 Adam 混合精度训练，**显存下限**（不含激活）为：

```
M_min = 2P (权重 FP16) + 4P (FP32 主权重) + 4P (动量) + 4P (方差) = 14P bytes
```

加上梯度 FP16 缓冲区（2P）通常在反向时分配，但不长期驻留（取决于内存管理），实际恒常驻留约 **12P~14P**。

**激活显存**（无检查点，标准实现）：

- 每层 Attention 激活 ≈ `B × S × d × 34` bytes（包含 QKV、Scores、Attention 输出等，根据序列长度和实现波动），使用 FlashAttention 可大幅减少（O(S) 而非 O(S²)）。
- 每层 MLP 激活 ≈ `B × S × d_ff × 2` bytes（gate 和 up 输出）+ `B × S × d` bytes（down 前）。
- 残差输入 ≈ `B × S × d × 2` bytes 每层（保存 Norm 前的值）。
- 总激活 ≈ `B × L × (S × (a·d + b·d_ff))`，其中 a, b 为常数（约 15~30，取决于组件和是否使用 FlashAttention）。

**示例估算（Llama-7B 单卡，无检查点）**：

配置：B=1, S=4096, d=4096, d_ff=11008, L=32, P≈7B。

- 权重+优化器+梯度：`14 × 7 × 10^9 ≈ 98 GB`（已超 A100 80GB！）
- 激活：大约 `B × L × S × d × 30 × 2 ≈ 1 × 32 × 4096 × 4096 × 60 ≈ 32 GB`
- 峰值总显存 > 130 GB，OOM。必须使用**参数分片（ZeRO）**或**模型并行**。

---

### ⑤ 设计权衡

**1. 精度与显存**：FP32 主权重和优化器状态占据 12P 字节，是最主要显存消耗源。混合精度训练必须保留 FP32 副本以保证更新精度，不能直接移除。**ZeRO-1** 将优化器状态分片到多卡，正是针对此开销。

**2. 激活存储 vs 重计算**：激活检查点通过牺牲约 33% 的计算时间（重算前向），可将激活显存从 O(L) 降到 O(√L) 或 O(1)（取决于选择性）。对极深模型，这是训练可行的必要条件。Megatron 默认在每个 Transformer Block 边界做检查点。

**3. 梯度累积**：当单卡 batch size 受显存限制时，可通过多次前向+反向（累积梯度）模拟更大的 global batch，等效于增加 B 但无需增加显存。代价是多次反向的通信开销（在 DP 场景）。

**4. FlashAttention 的影响**：将 Attention 的 O(S²) 激活降至 O(S)，在长序列场景可节省大量显存，但模型权重+优化器瓶颈依然存在。因此 FlashAttention 常与 ZeRO/TP 协同使用。

**5. 资源感知训练**：现代训练框架（DeepSpeed, Megatron）会在启动时估算显存占用，自动选择是否启用 ZeRO 阶段、激活检查点、TP/PP。理解 0.6 的显存生命周期，你就能理解这些自动决策背后的逻辑——**所有策略都是为了让峰值显存低于硬件上限**。

## 展开 1.0 GPU 编程与计算模型

### ① 形式化定义

GPU 是一个大规模并行协处理器，其编程模型的核心抽象是：**将同一段计算程序（Kernel）组织为多层级的并行执行单元，在成千上万个独立线程上同时运行，每个线程处理不同数据分区**。

#### 1.0.1 CUDA 执行模型：Grid / Block / Thread / Warp

CUDA 的执行层级定义如下：

- **Thread**：最基本的执行单元，每个 thread 执行同一个 Kernel 函数，但拥有不同的 `threadIdx`。
- **Warp**：32 个 thread 组成的**硬件调度最小单元**。同一 warp 内的 thread 在 SM 上以 SIMT（单指令多线程）方式锁步执行。这是理解 GPU 效率的核心概念——warp 内分支发散会导致串行化。
- **Block**：一组 thread（最多 1024 个），被分配到同一个 SM 上执行。Block 内的 thread 可以通过共享内存和 `__syncthreads()` 进行协作。
- **Grid**：一组 block 组成一个 Grid，对应一次 Kernel 启动的全部并行任务。

```
一个 Kernel 启动 = 1 个 Grid
                    ├── Block 0  ── Warp 0, Warp 1, ...
                    ├── Block 1  ── Warp 0, Warp 1, ...
                    └── Block N  ── ...
```

**工程含义**：当你写 `x = torch.matmul(A, B)` 时，PyTorch 底层调用 cuBLAS，将矩阵分块映射到 Grid/Block/Thread 层级。TP（张量并行）本质上就是在额外维度上重新组织这个映射。

#### 1.0.2 GPU 存储层次

从最慢到最快，GPU 存储层次为：

| 存储层级 | 大小（典型 A100） | 带宽 | 作用域 | 关键特性 |
|----------|-------------------|------|--------|----------|
| HBM2e（全局内存） | 40GB / 80GB | ~2 TB/s | 所有 thread | 模型参数、激活、梯度存于此 |
| L2 Cache | 40 MB | ~4 TB/s | 所有 SM | 减少 HBM 访问 |
| 共享内存 (SRAM) | 每个 SM 192 KB | ~19 TB/s | Block 内 thread | FlashAttention 的核心优化场地 |
| 寄存器 | 每个 SM 64K 个 | ~8 TB/s/reg | 单 thread | 局部变量 |

**工程含义**：分布式训练中讨论的 " 显存不够 "，几乎总是指 HBM 不够（80GB 装不下 70B 模型）。ZeRO-3 的思想就是把 HBM 中的内容分散到多张卡。而 FlashAttention 的性能提升来自尽量在 SRAM 内完成计算，避免反复读写 HBM。

#### 1.0.3 流多处理器（SM）与占用率

- 每个 GPU 有多个 **SM**（A100 有 108 个 SM）。
- 每个 SM 可同时驻留多个 block，通过**上下文切换**隐藏访存延迟。
- **Occupancy（占用率）** = 每个 SM 上活跃 warp 数 / 理论最大 warp 数。高占用率意味着 SM 有足够多的 warp 去切换，从而隐藏流水线停顿。

**形式化表示**：

```
SM 上活跃 warp 数 = min(每个 SM 最大 warp 数, 
                        寄存器限制 / 每线程寄存器数,
                        共享内存限制 / 每 block 共享内存使用)
```

#### 1.0.4 异步执行与 CUDA Stream

GPU 通过 **Stream（流）** 实现任务并行：

- 同一 stream 内的操作**顺序执行**。
- 不同 stream 的操作可以**并发执行**（例如：一个 stream 做计算，另一个 stream 做 H2D/D2H 拷贝）。
- PyTorch 默认使用 `default stream`。DDP 通过创建独立 stream 实现**通信与计算重叠**（展开 5.2.4）。

#### 1.0.5 GPU 峰值算力与带宽

以 A100-80GB SXM 为例：

- **FP16 Tensor Core 峰值**：312 TFLOPS
- **HBM 带宽**：2039 GB/s
- **NVLink 带宽**：600 GB/s（单卡对单卡）

**roofline 模型的直观含义**：如果每个浮点操作只需要很少的 byte 从 HBM 读取，则受限于**算力**（compute-bound）；如果访存量很大，则受限于**带宽**（memory-bound）。大多数推理和小 batch 训练是 memory-bound 的。

### ④ 复杂度分析

这里不涉及多 GPU 通信，我们分析单 GPU 计算的时间模型。

一个 Kernel 调用的总时间：

```
T_kernel = T_compute + T_memory
         = (FLOPs / 有效算力利用率 × 峰值算力) + (访存量 / 有效带宽利用率 × HBM 带宽)
```

- **有效算力利用率**：受占用率、warp 发散、指令流水等因素影响，通常远低于 100%。
- **有效带宽利用率**：受访问模式（是否连续、对齐）影响。

**对于大模型训练**：
- MatMul 通常是 compute-bound（特别是大矩阵）
- Element-wise 操作（ReLU、Dropout、LayerNorm）是 memory-bound
- Attention（标准实现）因为 softmax 需要全局读写，是 memory-bound——FlashAttention 通过分块将其转化为更 compute-bound 的模式

---

### ⑤ 设计权衡

**1. Occupancy vs 寄存器压力**
每个 thread 使用越多寄存器，单个 SM 可驻留的 warp 越少。编译器在寄存器分配和占用率之间自动权衡，但你需要知道：过高的寄存器使用会降低隐藏延迟的能力。

**2. 显存容量 vs 带宽**
HBM 很大（80GB），但带宽有限（2TB/s）。把更多数据放在 HBM 不会让计算变快，只有把数据放入 SRAM 或寄存器才能加速。这是 FlashAttention 和 Kernel Fusion 的核心动机。

**3. 单 GPU 的硬上限**
无论怎么优化 Kernel，单 GPU 的显存和算力都有上限。`1.0` 的核心教学目的就是让你精准理解这个上限的物理本质——当我们进入 `1.2` 的并行策略时，每一步都是在**打破这个上限**：
- 模型放不下 → TP / PP / ZeRO-3（跨 GPU 分片）
- 算力不够 → DP（增加并行度）
- 通信开销 → 第 5 节（优化通信）

## 展开 1.1 单 GPU 计算与显存模型

---

### ① 形式化定义

在单 GPU 上执行一次训练步骤（一个 micro-batch），计算过程可以形式化为一个**有向无环计算图（DAG）**，节点为算子（如 MatMul、Softmax、LayerNorm），边为张量数据流。模型训练需要同时维护三种状态：

- **持久状态**：模型参数（FP16 权重）、FP32 主权重、优化器动量与方差。这些从训练开始到结束一直驻留在显存中。
- **瞬态状态**：前向传播中产生的**激活（activations）**，用于反向传播计算梯度；反向传播中产生的**梯度**，用于更新参数；以及各种临时缓冲区。
- **峰值显存**：在一次训练迭代中，显存占用的最大值，通常发生在反向传播的某些时刻，此时持久状态未释放，大量激活尚未丢弃，梯度正在产生。

设模型参数量为 `P`（总参数个数）。混合精度训练（AMP）下，各持久状态的显存占用为：

```
FP16 权重:       2P bytes
FP32 主权重:     4P bytes
Adam 动量 (m):   4P bytes
Adam 方差 (v):   4P bytes
───────────────────────
持久状态合计:   14P bytes
```

此外，优化器在更新时会临时产生 FP16 梯度（2P bytes），但通常不长期驻留（或与激活缓冲区复用）。激活显存总量记为 `A`，其大小取决于 batch size B、序列长度 S、层数 L、隐藏维度 d、MLP 中间维度 d_ff 以及是否使用 FlashAttention 和激活检查点。

**形式化显存约束**：对于给定 GPU 容量 `M_GPU`，训练必须满足：

```
14P + A_peak ≤ M_GPU
```

其中 `A_peak` 为反向传播时的激活峰值。若此式不成立，则必须借助并行策略（ZeRO、TP、PP 等）将 14P 或 A 分摊到多张 GPU。

**在整个知识树中的位置**：`1.1` 是第 1 节“分布式训练系统基础”的核心，上承 0.6 的单 GPU 训练循环，下接 1.2 的并行性抽象。它从系统层面形式化单 GPU 的内存模型，是理解**为何必须引入分布式**以及**如何定量评估显存节省**的关键。

- 训练设置：精度（FP16/FP32），优化器类型（Adam/AdamW），是否使用混合精度

**输出**：

### ③ 工程映射

**PyTorch 中的显存分配与释放**：

- 前向时，`autograd` 引擎记录每个算子的输入输出，并保存必要的张量（`ctx.save_for_backward`）供反向使用。
- 反向时，引擎沿着计算图反向遍历，计算每个算子的梯度，并在当前算子的梯度计算完成后**释放相应的激活**（如果该激活不再被其他算子需要）。
- `loss.backward()` 最终将计算出的梯度累加到各参数的 `.grad` 属性中。

**梯度累积（Gradient Accumulation）**：

```python
accumulation_steps = 4
optimizer.zero_grad()
for i in range(accumulation_steps):
    with autocast():
        loss = model(batch) / accumulation_steps
    scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()
```

这样做可以在不增加单次前向激活的情况下，模拟更大的全局 batch size。代价是每步反向都要释放梯度缓冲区再重新分配，显存波动增加。

**FP32 Master Weight 的由来**：

在 PyTorch 的 `torch.cuda.amp` 中，`GradScaler` 控制梯度缩放。参数更新时，`AdamW` 内部会维护 FP32 副本（`param_fp32`），更新操作在 FP32 下进行以保持数值精度。`optimizer.step()` 完成后，FP32 主权重被写回到 FP16 权重。

**映射到 DeepSpeed / ZeRO**：

- ZeRO-1：将优化器状态（m, v）分片到多个 GPU，每个 GPU 只存 `8P / N` 的优化器状态。
- ZeRO-2：再加上梯度分片。
- ZeRO-3：连 FP16 权重也分片。

这些策略直接针对 `1.1` 中的 `14P` 项，将其分摊到 N 张卡上。

---

### ④ 复杂度分析

**持久状态缩放**：`14P` 随模型规模线性增长。以 Llama 为例：

| 模型 | P (B) | 14P (GB) | 所需 GPU (无并行) |
|------|-------|----------|-------------------|
| 7B | 7 | 98 | 1×A100 80GB 不够 |
| 13B | 13 | 182 | 3×A100 80GB |
| 70B | 70 | 980 | 13×A100 80GB |

**激活峰值 A 的估算**（无检查点，FlashAttention）：

```
A ≈ B × L × S × (c1×d + c2×d_ff) bytes
```

其中 c1, c2 为常数，通常取 10~30。对于 Llama-7B, B=1, S=4096, L=32, d=4096, d_ff=11008，取 c1=20：

```
A ≈ 1 × 32 × 4096 × (20×4096 + 10×11008) × 2 (FP16)
  ≈ 131072 × (81920 + 110080) × 2
  ≈ 131072 × 192000 × 2 = 50.3 GB
```

因此对于 7B 模型，仅持久状态已超单卡，激活反而次要。对于 1.5B 模型，持久状态 ~21GB，激活 10~20GB，单卡可存。

**梯度累积的影响**：不改变峰值显存（反向仍只针对一个 micro-batch 激活），但增大了单次 step 的通信次数（DP 场景），可能降低吞吐。

---

### ⑤ 设计权衡

**1. FP32 主权重是否必须？**  
是的，为了稳定收敛。若直接用 FP16 更新，梯度有效位数不足，小梯度会被直接截断。混合精度通过 FP32 主权重保证更新精度，是目前的事实标准。可优化的方向是使用低精度优化器（如 8-bit Adam），但会引入收敛风险。

**2. 激活检查点的选择性**  
不需要为所有层保存激活。通常只需在 Transformer Block 边界做检查点（一个 Block 内 Attention+MLP 全部重算），就能将激活显存从 O(L) 降到 O(√L)（若隔一层存一个）或 O(1)（仅存输入）。代价是重算带来约 20%~30% 的额外计算。

**3. FlashAttention 的联动**  
FlashAttention 主要削减 A 中与序列长度平方相关的部分，在长序列下对显存节省显著，但无法解决 14P 的基础开销。因此即使有了 FlashAttention，大模型仍然必须使用 ZeRO 或 TP 来分摊参数状态。

**4. 梯度累积与通信的关系**  
在 DP 场景下，每步累积会触发多次 All-Reduce（取决于实现：DDP 通常在 `backward` 时立刻通信，而非等到 `step`）。过多累积可能使通信碎片化，降低带宽利用率。工程上常通过梯度分桶（bucketing）和延迟通信来缓解。

**5. 单 GPU 的硬约束 → 分布式必然性**  
`1.1` 得出的关键结论是：**对于超过 1.5B 的模型，单张 80GB GPU 已无法装下 FP16 训练所需的最小显存（14P）**。所有并行策略（DP、TP、PP、ZeRO）都是为了将 14P 和 A 分摊到多个 GPU 上，使每个 GPU 满足 `(14P + A)/N_effective ≤ M_GPU`。这为下一节 `1.2` 的并行性抽象提供了直接的量化动机。

## 展开 1.2 并行性抽象

---

### ① 形式化定义

并行性抽象是指：**将一个完整的模型训练任务，沿着某个维度切分为多个独立或弱依赖的子任务，分配到多个 GPU 上同时执行**。不同的并行策略对应于不同的切分维度，每种策略都旨在打破单 GPU 的显存或算力约束（`14P + A ≤ M_GPU`）。

设总 GPU 数为 `N`（World Size），模型总参数量为 `P`，单 GPU 显存容量为 `M_GPU`。六种基本并行策略的定义如下：

- **1.2.1 数据并行（Data Parallelism, DP）**  
  沿**样本维度**切分。每个 GPU 持有完整模型副本（参数 `P`），处理不同的 micro-batch 数据。反向后通过通信将梯度同步，确保所有 GPU 上的模型一致。  
  显存节省：无（每个 GPU 仍需 14P + A），但计算并行度为 N。

- **1.2.2 模型并行（Model Parallelism, MP）**  
  广义术语，指沿**模型结构维度**切分，包含 1.2.3 PP 和 1.2.4 TP。常特指较简单的按层切分或按张量切分。

- **1.2.3 流水线并行（Pipeline Parallelism, PP）**  
  沿**模型深度（层）维度**切分。将 L 层模型分为 N 个 Stage，每个 Stage 包含连续若干层，分配给一个 GPU。数据以 micro-batch 为单位依次流过各 Stage，形成流水线。  
  显存节省：每张卡仅持有约 `14P / N` 的参数（加上激活），但存在空闲 Bubble。

- **1.2.4 张量并行（Tensor Parallelism, TP）**  
  沿**单个算子的张量维度**切分。对于 MatMul 等算子，将权重矩阵切分为列块或行块，分配到不同 GPU，通过 All-Reduce 或 All-Gather 同步中间结果。  
  显存节省：每张卡仅持有 `14P / N` 的参数量（针对被切分的算子），但每次前向需要通信。

- **1.2.5 序列并行（Sequence Parallelism, SP）**  
  沿**序列长度维度 S** 切分。将输入序列 `(B, S, d)` 沿 S 维分片，每个 GPU 处理一段连续 token。需要重新设计 Attention 计算（嵌入分布式 FlashAttention），使跨序列段的信息能交互。  
  显存节省：激活减少约 `A / N`，尤其针对长序列。

- **1.2.6 专家并行（Expert Parallelism, EP）**  
  沿**专家数量维度**切分。在 MoE（Mixture of Experts）架构中，不同专家分布在不同 GPU 上，每个 token 只激活部分专家。通过 All-to-All 通信将 token 路由到对应专家。  
  显存节省：每卡仅持有 `E / N` 个专家的参数（E 为专家总数）。

---

### ② 系统视角

**在整个知识树中的位置**：`1.2` 是分布式训练系统的**策略抽象层**，将具体的工程实现（ZeRO、Megatron 调度器）概括为六种独立的维度切分方法。它位于显存约束（1.1）和具体通信机制（2.x）之间，提供问题分解的全局视图。

**输入**：
- 硬约束：`N` 张 GPU，每张容量 `M_GPU`，网络拓扑
- 模型约束：参数量 `P`，层数 `L`，序列长度 `S`，注意力机制类型

**输出**：
- 一种或多种策略的组合（混合并行），使得 `14P_effective + A_effective ≤ M_GPU`
- 预估的总通信量和计算-通信比

**在系统中的物理位置**：

```
数据加载器 → DP 切分 → TP 切分（单层内） → PP 切分（层间） → 输出
                ↑              ↑                  ↑
              样本维度      张量维度            层深度维度
```

**每种策略的通信模式**：

| 策略 | 通信原语 | 通信频率 | 通信量 |
|------|----------|----------|--------|
| DP | All-Reduce | 每个 step 一次 | 2P（梯度） |
| TP | All-Reduce / All-Gather | 每个前向多次 | 取决于算子，每层约 O(B·S·d) |
| PP | P2P Send/Recv | 每个 micro-batch 一次 | 激活尺寸 B·S·d |
| SP | All-Gather + Reduce-Scatter | 每个 Attention 块 | O(B·S·d / N) |
| EP | All-to-All | 每个 MoE 层 | 路由 token 的激活 |

**依赖关系**：`1.2` 是后续所有具体机制章节的索引。2.x 讲 DP 和 TP 的具体通信，3.x 讲 PP 调度，5.x 深入通信系统，4.x 讨论混合策略。

---

### ③ 工程映射

**PyTorch 中的策略实现映射**：

- **DP**：`torch.nn.DataParallel`（旧，单机多卡，性能差）或 `DistributedDataParallel`（DDP，生产级）。DDP 在反向时自动插入 All-Reduce 钩子。
- **TP**：无原生高级 API，需手动切分 Linear 层（如 Megatron-LM 的 `ColumnParallelLinear` / `RowParallelLinear`），或使用 `torch.distributed.tensor.parallel`（PyTorch 2.x 实验性支持）。
- **PP**：`torch.distributed.pipeline.sync`（基于 GPipe），或 DeepSpeed 的 `PipelineEngine`，或 Megatron-LM 的调度器。
- **SP**：无单一 API，通常结合 TP 实现（Megatron-LM 的序列并行，对 LayerNorm 和 Dropout 沿 S 维切分）。
- **EP**：DeepSpeed-MoE，或 FairScale 的 Mixture of Experts 实现。

**DeepSpeed 配置示例（多种策略组合）**：

```json
{
  "train_batch_size": 32,
  "data_parallel_size": 4,
  "tensor_parallel_size": 2,
  "pipeline_parallel_size": 2,
  "zero_optimization": {
    "stage": 1
  }
}
```

**Megatron-LM 中的混合并行初始化**：
- 定义 `tp_size`, `pp_size`, `dp_size`，使得 `tp_size × pp_size × dp_size = N`。
- TP 在节点内（NVLink 高带宽），PP 和 DP 可跨节点。
- 层数 L 必须能被 `pp_size` 整除（或使用交错式流水线）。

---

### ④ 复杂度分析

**显存节省效果**（简化，假设均匀分配）：

| 策略 | 每卡参数 | 每卡优化器 | 每卡激活 | 约束 |
|------|----------|------------|----------|------|
| 无并行 | P | 12P | A | 14P + A ≤ M |
| DP | P | 12P | A/N | 14P + A/N ≤ M |
| TP | P/tp | 12P/tp | ~A/tp | 需通信，计算-通信比高 |
| PP | P/pp | 12P/pp | ~A/pp | Bubble 开销，L 须整除 |
| DP+TP | P/tp | 12P/tp | A/(dp·tp) | 需三维通信 |
| ZeRO-3 | P/N | 12P/N | A/N（+参数通信） | 额外通信拉取参数 |

**通信开销概略**：

- **DP**：每 step 一次 All-Reduce，通信量 `2P`（梯度）。与模型大小成正比，与 batch size 无关。当模型很大时，DP 通信成为瓶颈。
- **TP**：每层多次 All-Reduce/All-Gather，通信量 `O(B·S·d)`。通常限制在节点内高速链路（NVLink）使用。
- **PP**：每个 micro-batch 一次 Send/Recv，通信量 `B·S·d`。异步性好，但存在 Bubble 浪费。
- **SP**：与 TP 混合时，通信量约为 `O(B·S·d)`，但将 LayerNorm/Dropout 等小操作也切分，减少了冗余存储。

**扩展行为**：

- **DP**：强扩展时，B 固定，增大 N → 每卡 B/N 减小，计算量减小但通信量不减（每卡仍传完整梯度），计算-通信比恶化。适合弱扩展（增大 B）。
- **TP**：增大 tp_size → 每卡计算量和通信量都减小，但通信延迟增加。限制在 ~8 卡（节点内 NVLink 可接受）。
- **PP**：增大 pp_size → 每卡层数减少，Bubble 比例增大（除非增加 micro-batch 数）。
- **混合**：通过平衡 DP/TP/PP 比例，可在计算-通信-显存间取得最优。

---

### ⑤ 设计权衡

**1. 通信带宽 vs 通信量**  
不同并行策略产生不同的通信模式。TP 要求极高带宽（节点内 NVLink），PP 仅需低带宽 P2P（可容忍跨节点），DP 居中。策略选择必须匹配网络拓扑。

**2. 显存 vs 计算**  
DP 不省显存，但计算效率高（无通信延迟）。TP 和 PP 省显存但引入通信和调度开销。ZeRO 介于两者之间：省显存（分片）但额外通信拉取参数，尤其 ZeRO-3 的 All-Gather 开销显著。

**3. Bubble 与利用率的取舍**  
PP 的流水线 Bubble 随 pp_size 增大和 micro-batch 数减少而恶化。通过 1F1B 调度（3.3）和交错式流水线（3.4）可减轻，但增加实现复杂度。小模型不宜用 PP，大模型 PP 几乎必须。

**4. 混合策略的必要性**  
单一策略往往不足：
- 纯 DP 对 >10B 模型显存不够。
- 纯 TP 无法跨节点（通信开销大），且最大 tp_size 受节点 GPU 数限制。
- 纯 PP 的 Bubble 和激活存储依然可观。

工业界标准组合是 **DP + TP + PP + ZeRO**：
- TP 用于节点内（8 卡 NVLink），处理大矩阵切分。
- PP 用于跨节点扩展深度（流水线），减少跨节点带宽压力。
- DP 在批大小维度扩展算力。
- ZeRO 进一步优化优化器和参数冗余（可与 DP 协同，ZeRO-1/2 等同于更高效的 DP）。

**5. 策略对训练代码的侵入性**  
DP（DDP）对模型代码几乎无侵入，只需多进程启动脚本。TP 和 PP 需要修改模型定义（替换 Linear 层，插入通信），Megatron-LM 正是为此设计。在选择策略时，还需考虑开发成本。

通过 1.2 的抽象，所有并行策略被归约为**沿某个维度分片 + 相应的通信模式**。下一层（2.x, 3.x, 4.x, 5.x）将详细展开每种策略的工程细节和通信实现。

## 深入 1.2 并行性抽象（深度展开）

上一轮我们给出了六种并行策略的概念总览，本轮进行更深入的展开，聚焦于它们的**数学化定义、内存与通信的形式化模型、以及相互作用方式**。

---

### ① 形式化定义（增强）

**数据并行（DP）**  
设全局 batch size 为 `B`，DP 组大小为 `dp`。每个 GPU 处理 `b = B/dp` 个样本。所有权重 `θ` 在每个 GPU 上完整保存。前向与反向完全独立，仅在反向结束时对梯度 `g` 执行 **All-Reduce**：

```
g_global = (1/dp) Σ_i g_i
θ ← θ - lr * g_global
```

**张量并行（TP）**  
主要针对线性层 `Y = XW` （`X ∈ R^{b×s×d_in}`, `W ∈ R^{d_in×d_out}`）。  
- **列切分**：将 `W` 沿输出维度切分为 `[W_1 | W_2 | ... | W_tp]`。各 GPU 计算 `Y_i = XW_i`，然后在最后维度拼接 `Y = [Y_1, ..., Y_tp]`。需要一次 **All-Gather** 或等效的 **Reduce-Scatter** （取决于后续操作）。
- **行切分**：将 `W` 沿输入维度切分，且 `X` 也相应切分输入维度。各 GPU 计算部分积，然后 **All-Reduce** 求和得到 `Y`。

**流水线并行（PP）**  
将模型 `f = f_L ∘ ... ∘ f_1` 划分成 `p` 个 stage，每个 stage 分配给一个 GPU。一个 micro-batch 数据依次流过 stage。  
执行时间线：若 micro-batch 数为 `m`，则完成 `m` 个 micro-batch 所需的时间为 `(p + m - 1) × (t_f + t_b + t_comm)`（简单 GPipe 调度）。空闲 Bubble 时间占比为 `(p-1)/(p+m-1)`。

**序列并行（SP）**  
将输入 `X ∈ R^{b×s×d}` 沿 `s` 维度切分为 `sp` 份，各 GPU 持有 `X_i ∈ R^{b×(s/sp)×d}`。非 attention 操作（如 LayerNorm、MLP）直接独立计算。对于 Attention，需要跨 GPU 交换 K、V 的分块（通过 All-Gather 或 Ring 通信），实现类似分布式 FlashAttention 的效果。

**专家并行（EP）**  
在 MoE 层中，有 E 个专家。每个 GPU 持有 `E/ep` 个专家。输入 token 通过门控网络被路由到不同的专家，token 通过 **All-to-All** 通信发送到对应专家所在的 GPU，计算完成后通过另一个 **All-to-All** 送回。

**形式化的内存公式**  
对于任意并行配置，单 GPU 所需显存可表示为：

```
M_needed = (W_param + W_master + W_optim) / (tp * pp * (ZeRO_factor)) 
          + Activation(b, s/sp, L/pp, d) / (dp * sp) 
          + temp_buffers
```

其中：
- `W_param` 等被 TP、PP 和 ZeRO 切分（ZeRO-3 时 `W_param` 被 dp 进一步分片）。
- 激活大小被 DP 和 SP 分片，且被 PP 切分层数减少。
- `temp_buffers` 为通信临时缓冲区。

---

### ② 系统视角（精确交互）

**并行策略的干涉**：
- DP 与 TP/PP 独立：DP 复制整个模型，其梯度通信量不受 TP/PP 切分影响（仍需 All-Reduce 完整梯度），因此在大模型时 DP 的通信成为瓶颈。
- TP 与 PP 正交：TP 在层内切分算子，PP 在层间切分。它们可以组合：先按 PP 将层分组，然后在每组内部对某些层做 TP。
- SP 常与 TP 结合（Megatron-LM 的序列并行）：当启用 TP 时，将 LayerNorm 和 Dropout 的中间结果沿序列维度分片，以降低激活存储。
- ZeRO 可视为对 DP 的内存优化：它不再复制优化器状态（和权重），而是分片，但会引入额外的参数 All-Gather 通信。

**通信拓扑匹配**：
- **节点内（高带宽 NVLink）**：TP、SP 的密集 All-Reduce/All-Gather 适合在此。
- **跨节点（较低带宽 InfiniBand/RoCE）**：DP 的 All-Reduce（一次大包）以及 PP 的 P2P 更适合跨节点，但 DP 通信量随模型增大而线性增长，需谨慎扩展。

---

### ③ 工程映射（更具体的配置）

**Megatron-LM 的混合并行**：
- 定义 `tensor_model_parallel_size`, `pipeline_model_parallel_size`, `data_parallel_size`。
- 层划分：对于 L 层，每个 PP stage 有 `L/pp_size` 层（或交错分配）。在这些层中，线性层被 TP 切分。
- 通信组：进程网格 `(dp, tp, pp)` 映射到 GPU 阵列。
- 例子：8 GPU 单节点，可配置 tp=4, pp=2, dp=1；或 tp=2, pp=1, dp=4。

**DeepSpeed 的 3D 并行**：
- 通过 `DeepSpeedStrategy` 指定 `tensor_parallel_size`, `pipeline_parallel_size`, 以及 ZeRO 阶段。
- ZeRO 的 dp 组大小默认等于剩余并行度（`world_size/(tp*pp)`）。
- 数据加载器：自动为 dp 组分配不同的 micro-batch，为 PP 插入不同 micro-batch 的流水线。

---

### ④ 复杂度分析（详细对比）

**内存节省**（以 70B 模型为例，无 ZeRO，只用 TP/PP）：

| 配置 | 每卡参数量 | 每卡激活（估计） | 总显存/卡 | 可行性（80GB） |
|------|-----------|------------------|-----------|----------------|
| 单 GPU | 70B | ~200GB | >>200GB | 否 |
| TP=8, 无 PP | 8.75B | ~200/8 = 25GB | 约 120GB | 否（参数+激活仍大） |
| PP=8, 无 TP | 8.75B | ~25GB | ~120GB | 接近极限 |
| TP=4, PP=2 | 8.75B | ~12.5GB | ~100GB | 可能，需 ZeRO-1 |

**通信带宽需求**（S=4096, d=8192, tp=4, b=1）：

- TP All-Reduce（MLP down 投影输出）：`b*s*d * 2 bytes ≈ 64 MB`，每层一次，一秒多次。要求极高带宽（NVLink 600 GB/s）。
- DP All-Reduce（梯度）： `2P bytes = 140 GB`，每步一次。若步长时间为 10 秒，需要 14 GB/s 带宽。
- PP P2P：`b*s*d * 2 bytes = 64 MB`，每 micro-batch 一次，频率较低，带宽要求低。

**Bubble 率**：对于 PP，若 `m=4, p=8`，Bubble 率 = `(8-1)/(8+4-1)=7/11≈64%`。需要增大 m 来降低 Bubble，但 m 受 batch size 和显存限制。1F1B 调度可减少激活存储，但不能消除 Bubble。

---

### ⑤ 设计权衡（系统级）

1. **TP vs PP 的选择**：  
   - TP 在节点内扩展时通信开销相对可控，但最多只能扩展到节点内的 GPU 数（通常 ≤8）。  
   - PP 可跨节点，但引入 Bubble 和调度复杂度。  
   - 两者结合：节点内用 TP，跨节点用 PP，是工业界标准（Megatron-LM）。

2. **ZeRO 与 模型并行的关系**：  
   - ZeRO-3 可替代 TP 和 PP 吗？理论上 ZeRO-3 通过参数分片可以训练任意大模型（只要总显存够），但通信开销大（需要 All-Gather 权重）。当模型超过 100B 时，纯粹 ZeRO-3 的通信压力极大，需结合 TP/PP 降低通信频率。

3. **序列并行与长上下文**：  
   当序列长度达到 32k 甚至 128k 时，即使 TP+PP 也面临激活爆炸，此时必须引入 SP 来切分激活。SP 与 FlashAttention 结合，可实现线性缩放。

4. **策略选择的决策树**：  
   - 模型能否放入单卡？ → 否 → 先尝试 ZeRO（阶段 2 或 3）。  
   - ZeRO 通信是否可接受？ → 否 → 加入 TP（节点内）。  
   - 仍需更大模型？ → 加入 PP。  
   - 序列超长？ → 加入 SP。  
   - 若为 MoE → 加入 EP。

## 展开 1.2.1 数据并行（Data Parallelism, DP）

---

### ① 形式化定义

数据并行是最基础的分布式训练策略。它将一个大的全局批次（Global Batch）沿样本维度切分为多个等大的微批次（Micro-Batch），每个 GPU 持有一份完整的模型副本，独立计算前向传播和反向传播，最后通过**集合通信**对所有 GPU 上的模型梯度进行平均，确保所有副本保持参数一致。

**数学形式**：
设全局批次为 `D = {(x_i, y_i)}_{i=1}^{B}`，有 `N` 个 GPU。将 `D` 均匀划分为 `N` 份，每份 `D_k` 大小为 `b = B/N`。每个 GPU `k` 上：
- 模型参数 `θ`（所有 GPU 初始相同）
- 计算局部损失 `L_k(θ) = (1/b) Σ_{(x,y)∈D_k} l(f_θ(x), y)`
- 计算局部梯度 `g_k = ∇_θ L_k(θ)`
- 所有 GPU 执行 **All-Reduce** 求和并平均：
  ```
  g_global = (1/N) Σ_{k=1}^{N} g_k
  ```
- 同步更新：`θ ← θ - η · g_global`

**核心通信原语**：All-Reduce（对梯度进行全局求和并广播到所有进程）。

---

### ② 系统视角

**在整个知识树中的位置**：`1.2.1` 是并行性抽象（1.2）中的第一个具体策略，是后续混合并行（4.x）和张量/流水线并行的基础参照。它直接使用 `2.0` 的分布式基础概念，其通信机制在 `5.1.2`（All-Reduce）和 `5.2`（通信算法）中深入实现。

**在训练系统中的物理位置**：

```
数据加载器 → 切分 batch → [GPU0: model replica, b samples]
                        → [GPU1: model replica, b samples]
                        → ...
                        → [GPU_N-1: model replica, b samples]
                    ↓ 各自 forward/backward
                    ↓ 梯度 All-Reduce
                    ↓ 同步更新
            所有 GPU 上的模型参数保持一致
```

**输入**：
- 全局批次大小 `B`
- GPU 数量 `N`
- 完整的模型定义（各 GPU 上结构、初始参数相同）

**输出**：
- 一次 All-Reduce 后的全局平均梯度
- 各 GPU 上更新后的相同模型参数

**依赖关系**：
- 需要 `2.0.1`（进程与通信域）提供通信组上下文
- 需要 `5.1.2` 提供 All-Reduce 操作
- 其通信成本模型是 `7.1`（α-β 模型）的直接应用

**同步约束**：DP 是**同步训练**，所有 GPU 必须在同一时刻完成反向传播并开始 All-Reduce，存在木桶效应（最慢的 GPU 拖慢整体）。

---

### ③ 工程映射

**PyTorch DistributedDataParallel (DDP)**：
- 通过 `torch.nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])` 包装模型。
- DDP 在 `backward()` 期间，为每个参数的梯度注册钩子（hook），当梯度计算完成后立即启动**异步 All-Reduce**。
- 采用**梯度分桶（Gradient Bucketing）**：将多个参数的梯度分组打包成一个桶进行通信，减少通信启动开销。
- 支持 `find_unused_parameters=True` 处理模型中部分参数未使用的情况。

**PyTorch 示例代码**：
```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

# 初始化进程组
dist.init_process_group("nccl", rank=rank, world_size=world_size)

model = MyModel().to(device)
model = DDP(model, device_ids=[local_rank])

for batch in dataloader:
    optimizer.zero_grad()
    outputs = model(batch)
    loss = loss_fn(outputs, labels)
    loss.backward()  # 此时会自动触发梯度 All-Reduce
    optimizer.step()  # 所有 GPU 上的参数更新一致
```

**All-Reduce 的触发时机**：
- 默认在反向传播过程中，DDP 会在每个参数梯度计算后立即启动通信（与计算**部分重叠**，见 `5.2.4`）。
- 等待所有参数的梯度通信完成后，`optimizer.step()` 才会真正执行。

**与 DeepSpeed 的关系**：
- DeepSpeed 的 ZeRO-1 是 DP 的增强版：DP 复制优化器状态，ZeRO-1 将优化器状态分片，但梯度通信仍使用 All-Reduce。ZeRO-2 进一步将梯度分片，但通信量不变（只是存储分片）。
- ZeRO-3 则不再有完整的模型副本，取而代之的是通过 All-Gather 获取参数，但 DP 的梯度同步思想仍在。

**完全分片数据并行（FSDP）**：
- PyTorch 的 FSDP (`torch.distributed.fsdp.FullyShardedDataParallel`) 实现了 ZeRO-3 类似功能。它将模型参数、梯度和优化器状态分片，在前向时需要 All-Gather 参数，在反向时 Reduce-Scatter 梯度。FSDP 可以看作是 DP 与模型分片的结合。

---

### ④ 复杂度分析

**通信成本**：
假设模型参数量为 `P`，FP16 梯度大小为 `2P` bytes。对于 All-Reduce（Ring 算法），通信时间为：
```
T_comm = α · logN + β · (2(N-1)/N) · 2P
```
在 N 较大时，每个 GPU 发送/接收的数据量约为 `2P` bytes。总通信量随 `P` 线性增长，与 batch size 无关。

**显存开销**：
- **模型权重**：完整副本，`2P` bytes (FP16)
- **优化器状态**：完整 `12P` bytes (FP32 动量+方差+主权重)，总计 `14P` bytes 常驻。
- **激活**：每个 GPU 处理 `b = B/N` 个样本，激活大小为 `A(b)`（大致与 batch size 成正比）。因此激活存储随 N 增加而线性下降。
- **梯度**：`2P` bytes（在反向过程中产生，更新后释放）。

**结论**：DP 不减少模型和优化器的显存占用，仅减少激活存储。对于大模型（P 很大），单卡仍可能 OOM，这是 ZeRO 和模型并行的引入动机。

**计算与通信比**：
每个 GPU 的计算时间大约为：
```
T_comp = b · FLOPs_per_sample / GPU_peak
```
通信与计算比值为：
```
R_comm/comp = T_comm / T_comp ≈ (β · 2P) / (b · FLOPs_per_sample / GPU_peak)
```
当模型 P 很大或 batch size b 很小时，比值增大，通信成为瓶颈。因此 DP 的扩展性受限于模型大小和单 GPU batch size 的下限（不能太小，否则 GPU 利用率低且通信占主导）。

---

### ⑤ 设计权衡

**1. 同步 vs. 异步 DP**
- **同步 DP**（标准）：所有 GPU 严格同步，保证模型一致性，但存在木桶效应。
- **异步 DP**（参数服务器或 Gossip）：各 GPU 独立更新，偶尔同步。可减少等待时间，但引入**梯度陈旧性**（stale gradients），可能影响收敛。现代 LLM 训练几乎清一色使用同步 DP。

**2. DP 与梯度累积的结合**
当显存无法支持足够大的 `b` 时，使用梯度累积：在多次 micro-batch 上执行前后向（不通信），累积梯度后再执行一次 All-Reduce。这样，`b` 可以很小，但每步通信的梯度仍对应全局有效 batch size。代价是多次计算后才同步，可能降低计算效率（额外的 kernel launch 开销）。

**3. DP 扩展极限**
随着 N 增大，每卡 `b` 减小，但通信量不变（2P）。当 `b` 小到一定程度，计算时间小于通信时间，GPU 利用率将下降。因此，DP 的强扩展（固定全局 B）受限于模型大小和网络带宽。通常对于 1~10B 模型，DP 在 8~64 卡内效率尚可；对于 >100B 模型，纯 DP 的通信开销不可接受，需要结合 TP/PP/ZeRO 来降低单卡参数规模，从而减少通信量（因为梯度大小 P 被切分）。

**4. DP vs. ZeRO**
- DP：每个 GPU 存完整模型和优化器，通信只有梯度（All-Reduce）。
- ZeRO-1：分片优化器状态，但通信仍是 All-Reduce 梯度（通信量相同），显存节省 `8P/N`。
- ZeRO-2：分片梯度与优化器，通信仍是 All-Reduce，但显存节省 `10P/N`。
- ZeRO-3：分片参数、梯度、优化器，通信增加参数 All-Gather 和 Reduce-Scatter，但显存节省 `14P/N`，使得极大规模模型仅靠数据并行也能跑（通信开销增大）。

选择 DP 还是 ZeRO 取决于显存余量和网络带宽。若 DP 已满足显存要求，DP 的通信更简洁；若显存不足，ZeRO-1/2 以同等的通信量换取显存，ZeRO-3 则以更多通信换显存。

**5. DP 与 TP/PP 的协同**
在混合并行中，DP 组通常跨节点放置，TP 在节点内。梯度 All-Reduce 是在 DP 组内进行，其梯度大小因 TP/PP 切分而减小（因为每个 GPU 只持有部分参数），因此通信量与 `P/(tp*pp)` 成正比。这就是为什么大模型训练必须结合模型并行来降低 DP 通信量。

## 展开 2.0 分布式训练基础概念

---

### ① 形式化定义

分布式训练的基础概念定义了一组进程如何在多 GPU 环境下组织、标识和通信。其核心包括进程与通信域、同步模式、以及集合通信原语的抽象。

**2.0.1 进程与通信域**

- **进程（Process）**：每个 GPU 由一个独立的进程控制（单进程单卡），进程数量等于总 GPU 数量。
- **World Size**：总进程数，记为 `N`。例如，4 机 32 卡则为 `N=32`。
- **Rank**：每个进程的唯一全局标识，从 `0` 到 `N-1`。Rank 用于决定数据分配和通信角色。
- **Local Rank**：节点内 GPU 的局部标识（如 `0..7`），便于设置 `CUDA_VISIBLE_DEVICES`。
- **通信域（Process Group）**：进程的一个子集，在该子集内进行通信。所有进程默认组成一个全局组 `WORLD`。并行策略会创建多个子组：
  - DP 组、TP 组、PP 组：进程按网格划分到不同维度，使通信发生在特定组内。
  - 例如，16 个 GPU 排成 2×2×4 (dp=2, tp=2, pp=4) 的网格，需要创建对应的三个通信组。

**2.0.2 同步训练与异步训练模式**

- **同步训练**：所有进程在同一逻辑步中严格同步。每个进程完成计算后，进入集合通信（如 All-Reduce），等待所有进程到达后才能继续。梯度全局一致，参数更新同步。现代 LLM 训练（DDP、Megatron、DeepSpeed）均采用同步训练以保证收敛性。
- **异步训练**：进程间不设全局同步屏障。每个进程独立计算梯度并更新参数，参数更新通过参数服务器或 Gossip 协议异步交换。优点是消除木桶效应，提高硬件利用率，但引入**梯度陈旧**（梯度的计算基于过时参数），可能损害收敛性或需要特殊修正（如梯度校正）。

**2.0.3 集合通信原语概览**

集合通信定义了多进程间标准的数据交互模式，是 DP、TP 等策略的实现基础。共分为三大类：

- **一对多**：Broadcast（广播：从根进程发送相同数据到所有进程）、Scatter（散射：从根进程将数据按块分发给各进程）。
- **多对一**：Reduce（归约：将各进程数据用指定操作（如求和）在根进程汇总）、Gather（收集：将各进程数据拼接到根进程）。
- **多对多**：All-Reduce（全归约：所有进程得到归约结果）、All-Gather（全收集：所有进程得到所有数据块的拼接）、Reduce-Scatter（先归约再散射，结果在各进程上分片）、All-to-All（全交换：每个进程发送不同数据块给每个其他进程）。

这些原语的具体算法（Ring、Tree 等）和 NCCL 实现将在 `5.1` 和 `5.2` 中详细展开。

---

### ② 系统视角

**在整个知识树中的位置**：`2.0` 是分布式训练的“语言”基础，位于并行策略（1.2）和具体通信机制（2.x、5.x）之间。它定义了各 GPU 如何标记自己、如何组织成组、以及通过哪些基本操作交换数据。后续所有并行策略的工程实现都建立在这些概念上。

**在物理系统中的映射**：

```
物理 GPU (0..N-1)   ←  每个对应一个进程，rank 从 0 到 N-1
        │
      通信组 (Process Groups)   ←  进程子集，用于 TP/PP/DP 组内通信
        │
    集合通信原语   ←  程序调用的 API，如 all_reduce, all_gather
        │
    通信算法 (Ring, Tree, ...)   ←  NCCL 实现，决定数据如何实际流动
        │
    物理互联 (NVLink, InfiniBand, ...)
```

**输入/输出**：

- **输入**：GPU 数量、网络拓扑、并行策略配置（tp_size, pp_size, dp_size）。
- **输出**：初始化完成后的通信域和通信句柄，供训练循环中的梯度同步、张量并行通信等调用。

**依赖关系**：
- `2.0` 直接衔接 `1.2.1`（DP）等策略的具体实现。
- 提供 `5.1` 中集合通信原语的“是什么”，而 `5.1` 给出具体语义和调用示例。
- `5.3`（NCCL）负责在硬件上实现这些原语。

**关键系统性质**：
- **通信域隔离**：不同通信组内的操作互不干扰，可以并发进行（如 TP 组内的 All-Reduce 与 DP 组内的 All-Reduce 可同时进行，需不同 CUDA Stream）。
- **同步的代价**：同步训练意味着每个 step 都存在一个全局栅栏，拖慢到最慢的进程。因此负载均衡（计算、通信）至关重要。

### ③ 工程映射

**PyTorch 分布式初始化**：

```python
gather_list = [torch.zeros_like(tensor) for _ in range(group_size)]

```

### ④ 复杂度分析

这里暂不涉及具体的通信算法复杂度（属于 5.2），而是分析组织概念带来的抽象开销：

- **通信组创建开销**：`O(N_group)`，可以忽略。
- **同步栅栏开销**：每次全局同步引入的延迟，若负载不均，可能导致 GPU 空闲等待（木桶效应）。负载不平衡（如 PP 中不同 stage 计算量不同）会放大该开销。
- **Rank 分配对性能的影响**：Rank 的物理位置（哪些 GPU 在相同节点）影响通信带宽。例如，TP 组最好由同一节点内的 GPU 组成，以利用 NVLink 高带宽。若随意分配，可能导致 TP 通信走 PCIe 或网络，极大降低效率。NCCL 拓扑检测会自动优化，但进程组的初始创建仍需正确规划。

---

### ⑤ 设计权衡

**1. 同步 vs. 异步**  
同步训练保证确定性梯度更新，收敛行为稳定；异步训练可能提高吞吐但收敛曲线不确定。对于 LLM 训练，同步是唯一被证明能稳定收敛到目标精度的方法，因此工业界普遍采用同步模式。

**2. 通信组设计**  
将并行策略映射到通信组时，需要平衡通信频率和带宽需求。TP 组内通信极频繁（每层多次），必须使用节点内高速链路；DP 组内通信每步一次，可跨节点；PP 组仅相邻 stage 通信，频率低，跨节点也容易接受。因此通信组创建时，进程网格的 rank 映射策略直接决定性能。

**3. 集合通信 vs. P2P**  
集合通信（All-Reduce 等）简化编程，但其算法（Ring/Tree）会自动优化带宽利用。P2P（Send/Recv）更灵活（如 PP），但需手动调度缓冲区，容易出错。大多数框架对 DP、TP 使用集合通信，PP 使用 P2P。

**4. 节点内 vs. 跨节点**  
通信域的物理布局是显式决策：通常让 TP 组限制在节点内，PP 和 DP 跨节点。这要求用户在启动分布式脚本时正确设置 rank 顺序，或依赖 NCCL 自动发现（但 NCCL 不能改变通信组划分，仅优化通信路径）。

**5. 通信与计算的异步性**  
基础概念中的同步/异步模式不要与通信-计算重叠混淆。即使采用同步训练，集合通信操作本身可以是**异步的**（如 `dist.all_reduce` 的异步版本），以便与反向计算重叠。这是优化通信延迟的关键，在 `5.2.4` 中深入。

## 展开 2.1 数据并行（DP）的通信原语

---

### ① 形式化定义

数据并行的通信原语定义了在 N 个持有完整模型副本的 GPU 之间，如何通过集合通信完成梯度平均和参数一致性维护。

**2.1.1 All-Reduce 梯度同步**

反向传播结束后，每个 GPU k 拥有局部梯度 gₖ（对全局 batch 大小的一部分计算）。全局平均梯度为：

```
g_global = (1/N) Σₖ gₖ
```

通信实现方式为 **All-Reduce(sum)**，随后各 GPU 本地除以 N（或直接在 All-Reduce 中采用 average 操作）。形式化要求：
- 所有进程提供等长的梯度张量（通常整个模型的梯度被打平为一个连续缓冲区）。
- All-Reduce 的语义保证：每个进程得到完全相同的 `Σₖ gₖ`。
- 同步屏障：所有进程必须在 All-Reduce 开始前达到该调用点。

**2.1.2 参数广播（Broadcast）**

在训练开始时，需要保证所有 GPU 上的模型初始参数一致。这是通过一次 **Broadcast** 从 rank 0 将权重张量发送到所有其他进程。此外，在某些恢复或同步场景（如部分模型并行与数据并行混用），可能也需要对特定层进行参数广播以维持一致性。

**2.1.3 异步数据并行与梯度陈旧性**

异步 DP 放松了同步约束：每个 GPU 在本地计算梯度后无需等待其他 GPU，立即更新自己的参数，同时将梯度异步发送给其他 GPU（通过参数服务器或 Gossip 协议）。此时，GPU i 在时刻 t 使用的参数可能基于过去其他 GPU 发送的陈旧梯度。形式化地，更新公式变为：

```
θ_i^{(t+1)} = θ_i^{(t)} - η · g(θ_i^{(t-τ)})
```

其中 τ 是延迟步数。梯度陈旧可能导致收敛变慢甚至不稳定，通常需要补偿算法（如梯度修正）才能用于大规模训练。

---

### ② 系统视角

**在整个知识树中的位置**：`2.1` 是分布式训练“计算并行基础模型”的核心，直接阐述了 DP 策略的通信本质。它上承 `1.2.1` 的 DP 概念，下接 `5.1.2` 的 All-Reduce 具体算法实现。`2.1.3` 的异步变体则与 `5.2.4` 通信-计算重叠形成对比。

**在训练循环中的位置**：

```
前向传播 (各 GPU 独立) → 反向传播 (各 GPU 独立) → 梯度 All-Reduce → 优化器 step
```

**通信依赖**：
- 梯度 All-Reduce 依赖于反向传播完全结束（所有参数的梯度已计算）。
- 优化器 step 依赖于 All-Reduce 完成。
- 参数广播仅在初始化或 checkpoint 恢复时执行。

**异步 DP 的系统架构**：
常采用参数服务器（Parameter Server）模式：有专门的 server 进程维护全局参数，worker GPU 异步推送梯度、拉取最新参数。这消除了 All-Reduce 的同步屏障，但引入了网络带宽竞争和全局参数一致性问题。

**输入/输出**：
- **输入**：各 GPU 上的局部梯度。
- **输出**：所有 GPU 上相同平均梯度。

---

### ③ 工程映射

**PyTorch DDP 的梯度 All-Reduce 实现**：

- 模型由 `DistributedDataParallel` 包装后，DDP 注册 **autograd hook**：每个参数的梯度计算完成后立即触发。
- DDP 维护一个**梯度分桶**（Gradient Bucketing）：将多个参数的梯度合并到一个大缓冲区，当桶满或反向传播完成，立即执行 **异步 All-Reduce**。
- 通信后端为 NCCL，调用 `ncclAllReduce`。
- `optimizer.step()` 会显式等待所有 All-Reduce 完成。

```python
# 内部等价逻辑（简化）
for param in model.parameters():
    param.register_hook(lambda grad: bucket.add(param, grad))
    if bucket.is_full():
        all_reduce(bucket.tensor, async_op=True)
```

**Broadcast 的工程调用**：

```python
# 在初始化时
dist.broadcast(model.state_dict(), src=0)
```

**异步数据并行的实现（已不常用）**：
PyTorch 没有内置异步 DP 接口，需要用户自行实现参数服务器或使用 `torch.distributed.rpc`。工业界由于收敛性问题，异步 DP 在 LLM 训练中基本被淘汰，仅限于某些稀疏或联邦学习场景。

**在 Megatron / DeepSpeed 中的对应**：
- Megatron-LM：DP 的通信完全依托 NCCL All-Reduce，由 PyTorch DDP 或自定义包装器触发。
- DeepSpeed：ZeRO-1/2 仍然使用 All-Reduce 来平均梯度（即使优化器状态分片，梯度仍需全局平均）。ZeRO-3 的梯度平均则通过 Reduce-Scatter 实现，本质是 All-Reduce 的变体，后续在 `4.4` 详述。

---

### ④ 复杂度分析

**All-Reduce 通信成本（Ring 算法，N 进程）**：

设梯度总大小为 `G` bytes（FP16 下 `G = 2P`）。对于 Ring All-Reduce，通信时间近似为：

```
T_comm = (N-1) · α + ((N-1)/N) · (G / B)
```

其中 `α` 为通信延迟（latency），`B` 为带宽。当 N 较大时，每个进程传输的数据量接近 `G`。带宽利用率为 `(N-1)/N`。

**广播通信成本**：
- Broadcast 树算法：`log₂N · (α + G / B)`，比 All-Reduce 带宽消耗小，但仅在初始化时执行一次，开销可忽略。

**异步 DP 的通信开销**：
- 每个 worker 每次更新需 push/pull，总通信量可能更大（多次小消息），且不保证同步，延迟和带宽利用不稳定。

**显存影响**：
- DP 通信本身需要临时通信缓冲区（通常在 bucket 中），大小可配置，通常占用数十 MB 到几百 MB。
- All-Reduce 可以复用梯度缓冲区，无需额外大量显存。

**计算-通信重叠**（详见 `5.2.4`）：
DDP 的反向传播可以与 All-Reduce 流水线重叠：当一个参数梯度计算完就开始异步通信，同时继续计算后续层的梯度。重叠程度取决于层的计算时间与通信时间的比值。对于大层（如大矩阵乘），通信可能完全隐藏；对于小层（如 norm），通信无法完全隐藏。

---

### ⑤ 设计权衡

**1. All-Reduce 与 Reduce-Scatter + All-Gather**

All-Reduce 可直接平均梯度，但 ZeRO-3 使用 Reduce-Scatter 将分片的梯度分散到各 GPU，随后优化器更新后通过 All-Gather 收集更新后的分片参数。这两种模式的权衡：
- All-Reduce 适合每个 GPU 都需要完整梯度的场景（如 DP）。
- Reduce-Scatter + All-Gather 适合模型状态分片的场景（ZeRO-3），以额外 All-Gather 为代价换取显存降低。

**2. 同步与异步 DP**

- 同步 DP：确定性、收敛稳定，但存在木桶效应，要求负载均衡。
- 异步 DP：提高利用率，但梯度陈旧性可能损害收敛。即使使用梯度修正，在大规模语言模型上也缺少成功案例。因此现代 LLM 训练选择同步 DP 并搭配 ZeRO 或模型并行来平衡负载。

**3. 梯度分桶大小**

桶大小影响通信效率和重叠程度：
- 桶太小：通信次数多，延迟开销大。
- 桶太大：第一桶的启动时间推迟，重叠窗口变短。
DDP 默认桶大小 25MB，可通过 `bucket_cap_mb` 参数调整。

**4. 参数广播 vs. 初始化文件**

广播需要将完整模型权重从 rank 0 一次性传输给所有 GPU，对于大模型耗时较长（数百 GB 级别）。替代方案是每个 GPU 从共享存储或独立文件加载初始权重，完全避免广播通信。但广播实现简单，适合中等规模模型（<10B）。

**5. 与 ZeRO 的关系**

- ZeRO-1/2 保留 All-Reduce 梯度同步，因为每个 GPU 仍然计算完整梯度（但只保存部分分片）。通信量不变，但显存节省显著。
- ZeRO-3 用 Reduce-Scatter 代替 All-Reduce，通信量翻倍（增加了参数 All-Gather），但显存节省最大。这是通信与显存的经典权衡。

## 展开 2.1.3 异步数据并行与梯度陈旧性

---

### ① 形式化定义

**异步数据并行（Asynchronous Data Parallelism）** 是一种弱化同步约束的分布式训练策略：各 GPU 在计算局部梯度后，立即更新本地模型参数，而不等待其他 GPU 完成梯度计算和通信。梯度信息通过异步通信（如参数服务器或 Gossip）传播，其他 GPU 在其后的某个时刻才收到该梯度并用于更新。这导致一个 GPU 在计算梯度时所看到的参数可能已经过时，即存在**梯度陈旧（Gradient Staleness）**。

设共有 N 个 worker（GPU），worker i 在全局训练步 t 的参数为 θ_i^{(t)}。Worker i 的计算流程为：

1. 使用当前本地参数 θ_i^{(t)} 计算对一个 mini-batch 的损失 L(θ_i^{(t)})。
2. 进行反向传播，得到局部梯度 g_i^{(t)} = ∇ L(θ_i^{(t)})。
3. 将 g_i^{(t)} 异步发送给所有其他 worker（或发送到参数服务器）。
4. 立即用 g_i^{(t)} 更新本地参数：θ_i^{(t+1)} ← θ_i^{(t)} - η · g_i^{(t)}。
5. 接收来自其他 worker j 的梯度 g_j^{(t-τ_j)}（τ_j ≥ 0 为延迟步数），并用它修正本地参数或仅更新全局视图。

**梯度陈旧性（Staleness）** 定义：worker i 在步 t 接收到的 worker j 的梯度，是 worker j 在步 (t - τ) 基于参数 θ_j^{(t-τ)} 计算得到的。因此，当 worker i 使用该梯度更新参数时，该梯度相对于当前参数已经“陈旧”了 τ 步。τ 越大，梯度指向的方向与当前参数的梯度方向的偏差可能越大。

**收敛影响的形式化**：在同步 SGD 中，参数更新为 `θ_{t+1} = θ_t - η·g(θ_t)`，保证了梯度是在当前参数处求得的。在异步 SGD 中，更新变为 `θ_{t+1} = θ_t - η·g(θ_{t-τ})`。该差异可视为在正确梯度上叠加了一个噪声项。分析表明，当学习率足够小、延迟 τ 有界时，异步 SGD 可以收敛，但收敛速率会因陈旧性而降低（有界延迟模型，bounded staleness）。

---

### ② 系统视角

**在整个知识树中的位置**：`2.1.3` 是 DP 通信原语下的一个变体策略节点，它与同步 DP 的 All-Reduce 同步模式形成对比。该节点位于“计算并行基础模型”（2）之下，与现代 LLM 训练中主流的同步模式形成对照，帮助理解同步设计的动机。

**系统架构**（参数服务器模式）：

```
   Worker 0          Worker 1          Worker N-1
      |                  |                  |
  计算梯度 g0        计算梯度 g1        计算梯度 gN-1
      |                  |                  |
   Push(g0)  ---------> 参数服务器 <------- Push(gN-1)
      |   Pull(最新全局参数)   |
  本地更新 θ0            本地更新 θ1       本地更新 θN-1
```

- 每个 worker 独立运行，无需相互等待。
- 参数服务器负责收集梯度、更新全局参数，并向各 worker 分发最新参数。
- 通信模式：Push（梯度）和 Pull（参数）均为异步。

**同步 DP 与异步 DP 的系统对比**：

| 特性 | 同步 DP | 异步 DP |
|------|---------|---------|
| 同步屏障 | 每个 step 存在 All-Reduce 屏障 | 无全局屏障 |
| 梯度 | 全局平均，确定性 | 可能陈旧，随机性 |
| 硬件利用率 | 受木桶效应影响，最慢者拖累整体 | 无等待，利用率高 |
| 收敛行为 | 稳定，与单机 SGD 一致 | 可能不稳定，需降低学习率或加修正 |
| 通信开销 | 每步一次大流量 All-Reduce | 每步多次小流量 Push/Pull，总带宽可能更高 |

**适用场景**：异步 DP 在以下场景有优势：
- Worker 间计算速度差异大（异构硬件）。
- 高通信延迟环境（如跨地域集群）。
- 对最终模型精度要求不极致，更注重训练吞吐。

但在大规模 LLM 训练中，由于模型对梯度精度敏感，工业界几乎全部采用同步 DP 以保证收敛稳定性。

---

### ③ 工程映射

**参数服务器实现**：
- 分布式框架如 TensorFlow 早期版本（Parameter Server 策略）、MXNet、PaddlePaddle 中均有内置支持。
- PyTorch 中无原生的异步 DP 训练高层 API，但可通过 `torch.distributed.rpc` 手动构建参数服务器或使用 `torch.distributed.optim` 中的 `DistributedOptimizer`（结合 RPC 后端）。不过该方式已非主流。

**伪代码示意（参数服务器 worker 端）**：
```python
for batch in dataloader:
    # 拉取最新全局参数（异步，可能陈旧）
    new_params = pull_params_async(param_server)
    update_local_model(new_params)
    
    loss = compute_loss(batch)
    loss.backward()
    grads = [p.grad for p in model.parameters()]
    
    # 异步推送梯度
    push_grads_async(param_server, grads)
    
    # 本地立即更新（或等待服务器返回更新信息）
    optimizer.step()
```

**梯度陈旧补偿**：
一些方法通过调整学习率或应用梯度修正来缓解陈旧影响，如：
- **梯度空转修正（Staleness-Aware）**：将陈旧梯度与当前本地模型近似梯度混合。
- **弹性 SGD（EASGD）**：Worker 在本地更新后周期性地将参数拉向全局参数中心，是一种折中。

在现代深度学习训练中，由于 NCCL 等高效通信库的优化，同步通信的开销已经大幅降低，使得异步并行在大多数 GPU 集群上的收益被弱化。

---

### ④ 复杂度分析

**通信复杂度**：
设模型参数量为 P，N 个 worker。若使用参数服务器架构：
- 每个 worker 每步通信量：Push 梯度（2P bytes）+ Pull 参数（2P bytes）= 4P bytes（如果参数服务器不进行梯度聚合，直接更新全局参数）。若参数服务器对梯度做平均后再分发，则 Pull 量仍为 2P bytes，Push 量不变。
- 总通信量 `O(N·P)`，相比同步 All-Reduce 的总量 `O(N·P)`（每个 worker 收发各约 2P bytes），网络总负载相当，但异步模式通信颗粒度更细（小消息），可能导致带宽利用率下降，且存在竞争。

**收敛速率复杂度**：
理论上，异步 SGD 的收敛界为：
```
E[ f(θ_T) - f(θ^*) ] ≤ O( 1/T + τ_max / T + ... )
```
其中 τ_max 为最大延迟。延迟越大，收敛所需的步数 T 越多，实际可能需降低学习率。

**显存开销**：
与同步 DP 相同，每个 worker 需完整模型副本，优化器状态也完整保存。无额外显存开销。

---

### ⑤ 设计权衡

**1. 同步 vs 异步的根本选择**  
- 同步：用部分硬件空闲时间（木桶）换取确定性的高精度收敛。
- 异步：用潜在的收敛不稳定性和调参难度换取硬件利用率。  
对于昂贵的 LLM 训练（单次实验数百万美元），收敛的稳定性和可复现性远比硬件利用率重要，因此工业界一致选择同步。

**2. 陈旧性的影响范围**  
陈旧性不仅影响梯度方向，还会与自适应学习率算法（如 Adam）相互作用：Adam 的动量项和历史梯度平方会使陈旧梯度的负面影响持续更久。因此，即使异步训练，通常也需要限制最大延迟 τ_max（有界陈旧性）。

**3. 硬件异构性**  
如果训练集群中 GPU 性能不一（如不同代次），同步 DP 会将所有 GPU 拖慢到最弱者。异步 DP 则可避免此问题，但需承受陈旧代价。现代数据中心通常使用同构 GPU 来避免此问题。

**4. 与通信重叠的关系**  
同步 DP 通过通信-计算重叠（5.2.4）来隐藏 All-Reduce 延迟，使得同步等待的影响减小。当通信可以完全重叠时，同步 DP 的额外开销趋近于零，此时异步并行优势不再。

**5. 现代替代方案：本地 SGD**  
一种折中方法是**本地 SGD**：在多个本地步内使用同步 DP 不通信，仅在若干步后做一次全局同步。这减少了通信频率，也能容忍一定程度的异步性，但需要在间隔步数、收敛性上仔细调优。ZeRO 和模型并行并未采用此方法，而是继续使用每步同步。

## 展开 2.2 模型并行（MP）的张量切分

---

### ① 形式化定义

模型并行的张量切分是指将单个算子的权重张量（主要是线性层的矩阵）沿输入或输出维度进行划分，分布到多个 GPU 上并行计算，从而突破单卡显存对模型大小的限制。与流水线并行（沿层深度切分）不同，张量并行（TP）作用于层内的张量运算。

以下定义针对 Transformer 中的线性层 `Y = X W`，其中 `X` 为输入激活张量（形状 `[b, s, d_in]` 或 `[b*s, d_in]`），`W` 为权重矩阵（`[d_in, d_out]`）。

**2.2.1 1D 张量并行：列切分与行切分**

- **列切分（Column-wise）**：将权重 `W` 沿输出维度 `d_out` 切分为 `tp` 份：`W = [W_1 | W_2 | ... | W_tp]`，每个 GPU i 持有 `W_i`（形状 `[d_in, d_out/tp]`）。计算时各 GPU 得到 `Y_i = X W_i`，形状 `[b*s, d_out/tp]`。如果后续操作是像 GeLU 这样的逐元素激活函数，则各 GPU 可以独立计算激活，无需通信。如果后续操作需要完整的 `Y`（例如残差相加或后续线性层的输入），则需要通过 **All-Gather** 在输出维度拼接，或通过 **Reduce-Scatter**（如果后续操作是行切分的线性层）。

  通信：通常需要一次 All-Gather（或等效的拼接），通信量为 `b*s*d_out`（FP16 下 2 字节每元素）。

- **行切分（Row-wise）**：将权重 `W` 沿输入维度 `d_in` 切分，且输入 `X` 也需对应沿 `d_in` 切分。设 `X = [X_1 | X_2 | ... | X_tp]`，GPU i 持有 `W_i`（形状 `[d_in/tp, d_out]`）和 `X_i`。计算 `Y_i = X_i W_i`，形状 `[b*s, d_out]`。由于各 GPU 的结果是部分积，需要求总和得到最终 `Y`，因此需执行一次 **All-Reduce**（求和），通信量也为 `b*s*d_out`。

- **组合**：将列切分线性层与行切分线性层相邻放置时（如 Attention 的 QKV 投影是列切分，输出投影是行切分），它们之间的中间激活无需在 GPU 间进行 All-Gather/All-Reduce，因为列切分的输出可直接作为行切分的输入（都按列/行分布）。这是 Megatron-LM 降低通信的关键设计。

**2.2.2 2D / 2.5D 张量并行**

当 TP 扩展到超过单个节点内的 GPU 数量（例如 tp=16 或 32）时，单纯的 1D 切分会导致通信开销急剧增大（All-Reduce 跨节点带宽低）。2D 和 2.5D 并行通过将进程排列成二维网格来优化通信量，使得大量通信保持在节点内高速链路上。

- **2D 张量并行**（Optimus、SUMMA 等）：假设 `tp = p × q` 个进程排列成 `p` 行 `q` 列的网格。对线性层 `Y = XW`，权重 `W` 被分割成 `p×q` 块，计算分两阶段：第一阶段在行组内进行部分矩阵乘，第二阶段在列组内进行 All-Reduce。这使得 All-Reduce 仅在规模为 `q` 的列组内执行，通信量降为 `O(b*s*d_out / p)`（如果行组内已有 reduce）。

- **2.5D 张量并行**：在 2D 基础上引入深度（depth）维度以进一步减少冗余通信，但实现复杂度更高。常见于研究系统，工业部署仍以 1D 加节点内 TP 为主。

**2.2.3 Megatron-LM 风格的 MLP 与 Self-Attention 切分**

Megatron-LM 定义了将 Transformer 层映射到 TP 组的具体模式。

- **Self-Attention 块**：
  - 将 QKV 投影视为**列切分**：`W_Q, W_K, W_V` 各自按列切分，每个 GPU 得到部分头（head）的 Q、K、V。例如，h 个头、tp 卡，每卡管理 `h/tp` 个头。
  - 每个 GPU 独立执行其头部的因果注意力计算，输出仍为部分头（`[b, s, d_head * h/tp]`）。
  - 最后的输出投影 `W_O` 视为**行切分**：其输入是各 GPU 的部分注意力输出，`W_O` 的行被切分。每个 GPU 计算 `Y_i = Output_i W_O_i`，然后执行 **All-Reduce** 求和，得到完整 `Y`。
  这个设计使得 Attention 内只有一次 All-Reduce（在输出投影之后），QKV 不需要全局通信。

- **MLP 块**（SwiGLU 版本）：
  - `gate_proj` 和 `up_proj` 视为**列切分**：将 `W_gate, W_up` 沿输出维度 `d_ff` 切分，各 GPU 计算各自的 `gate_i` 和 `up_i`（形状 `[b, s, d_ff/tp]`），然后逐元素相乘得到 `h_i`（SwiGLU）。
  - `down_proj` 视为**行切分**：其输入 `h_i` 自然分布在 GPU 上，权重 `W_down` 沿输入维切分。各 GPU 计算 `Y_i = h_i W_down_i`，然后执行 **All-Reduce** 得到完整 MLP 输出。
  因此一个 Transformer Block 内，TP 产生两次 All-Reduce：一次在 Attention 后（输出投影），一次在 MLP 后（下投影）。如果还有跨层残差和 LayerNorm，这些操作都在切分后的维度上独立进行，不产生额外通信。

### ② 系统视角

**在整个知识树中的位置**：`2.2` 是并行策略实现的核心细节层，承接 `1.2.4` 的 TP 抽象定义，并为 `4.1`（混合并行）和 `6.3`（Megatron 实现）提供具体的切分方案和通信模式。它直接依赖于 `5.1`（集合通信原语）和 `5.3`（NCCL 实现）来执行 All-Reduce/All-Gather。

**在分布式训练流水线中的物理位置**：

- TP 通常被限制在**单个节点内**的高速 NVLink/NVSwitch 域，因为其通信模式是每层多次、通信量与激活大小成正比（`b*s*d`），需要极高的带宽。
- 在 Megatron-LM 等框架中，TP 组大小通常为 1、2、4、8（节点内 GPU 数）。
- 与 PP 组合时，每个流水线 stage 内部可能再进行 TP 切分，使得单个 stage 内的层被 TP 组共同处理。

**输入/输出**：

- **输入**：前一层（或 Embedding）产生的未切分或已切分的激活。
- **输出**：经过 All-Reduce 后的完整激活（在需要时），或保持切分状态传递给下一层（若下一层兼容切分）。

**数据流**（Megatron 方式）：

```
嵌入层 → [列切分 QKV] → 各卡独立 Attention → [行切分 W_O] → All-Reduce
         → LayerNorm (独立) → [列切分 gate/up] → SwiGLU → [行切分 down] → All-Reduce
         → LayerNorm (独立) → 下一层...
```

LayerNorm 和残差连接在 TP 切分下无需通信，因为它们在每个 GPU 上的部分激活上独立执行，并且残差相加时输入和输出都是部分维度（由于 All-Reduce 已经恢复了完整维度，但在实际实现中，LayerNorm 可能也做切分以节省激活存储，即序列并行 SP 的引入，见 1.2.5）。

**Megatron-LM 源码映射**：

- 列切分线性层：`megatron.core.tensor_parallel.layers.ColumnParallelLinear`

  ```python
  class ColumnParallelLinear(nn.Module):
      def __init__(self, in_features, out_features, ...):
          self.weight = Parameter(torch.empty(out_features // tp_size, in_features))
      def forward(self, x):
          y = F.linear(x, self.weight)
          # 如果 gather_output=True，则执行 All-Gather
          if self.gather_output:
              y = gather_from_tensor_model_parallel_region(y)
          return y
  ```
  对应的通信函数 `gather_from_tensor_model_parallel_region` 调用 NCCL All-Gather。

- 行切分线性层：`megatron.core.tensor_parallel.layers.RowParallelLinear`
  ```python
  class RowParallelLinear(nn.Module):
      def __init__(self, in_features, out_features, ...):
          self.weight = Parameter(torch.empty(out_features, in_features // tp_size))
      def forward(self, x):
          # x 是来自前一层的切分输入（或者需要 scatter）
          y = F.linear(x, self.weight)
          y = reduce_from_tensor_model_parallel_region(y)  # All-Reduce
          return y
  ```

- **Self-Attention 的实现**：
  在 Megatron 的 `ParallelAttention` 中，QKV 投影是 `ColumnParallelLinear`（不做 gather），然后 `scaled_dot_product_attention` 在部分头上计算，最后 `W_O` 是 `RowParallelLinear`（做 reduce）。

- **MLP 的实现**：
  `gate_proj` 和 `up_proj` 是 `ColumnParallelLinear`（不做 gather），然后逐元素乘法，`down_proj` 是 `RowParallelLinear`（reduce）。

**PyTorch 的实验性 TP API**：

### ④ 复杂度分析

**1D TP 通信量**（一个 Transformer Block，Megatron 风格）：

设 batch size B，序列长度 S，隐藏维度 d，TP 大小为 `t`，MLP 中间维度 `d_ff`。

- Attention 内：
  - 输出投影后的 All-Reduce：通信量 = `B × S × d`（FP16 为 `2BSd` bytes）
- MLP 内：
  - down 投影后的 All-Reduce：通信量 = `B × S × d`（同上）
- 每个 Block 总通信量：`2 × B × S × d` 元素 = `4 B S d` bytes（FP16）。
- 对于 L 层，总通信量 = `L × 4 B S d` bytes。

**计算量对比**：

每个 Block 的总计算量（前向）约为 `8 B S d² + 4 B S² d + 6 B S d d_ff`（见 0.5）。通信与计算比 `R = T_comm / T_comp` 取决于 d 和 d_ff。以 Llama-7B (d=4096, d_ff=11008, S=4096) 为例，Block 计算量约 1.4 TFLOPs（前向），通信量约 `4 × 1 × 4096 × 4096 × 2 bytes ≈ 128 MB`。若 NVLink 带宽 600 GB/s，通信时间约 0.2 ms，而前向计算时间约 4.5 ms（312 TFLOPS 50% 利用率），比值 4.4%，通信开销较小。

但是，通信量随 `B, S` 线性增长，计算量随 `S, d` 平方增长，因此对于大模型（d 很大），TP 的通信开销相对较低；但对于小模型或短序列，通信占比会上升。

**2D TP 复杂度**：

若网格 `p × q = t`，则 All-Reduce 只在列组（大小 q）内执行，通信量降低为 `(q-1)/q × 数据量`，相比 1D 的 `(t-1)/t` 减小。但需要额外的行组内 Reduce 或 Broadcast。总体带宽消耗更低，但延迟可能稍增。通常仅在 t > 8 时考虑。

**显存节省**：

TP 将参数和优化器状态按 t 分片，每卡持 `1/t` 的权重和优化器。激活也大致按 t 分片（切分维度上的中间结果），但有些激活（如 Attention 的 QKV）是全量但分布在不同卡上，仍需存储对应部分。总体激活减少因子近似 t，但不完全线性。

### ⑤ 设计权衡

**1. TP 通信频率 vs 带宽需求**

TP 在每个 Transformer 层内执行两次 All-Reduce（Megatron 风格），频率极高（例如 32 层需要 64 次 All-Reduce 每步）。这要求通信延迟极低、带宽极高。因此 TP 被严格限制在节点内高速互连（NVLink/NVSwitch），跨节点 TP 几乎不可行，因为 InfiniBand 的延迟和带宽不如 NVLink，多个 All-Reduce 累积的延迟会急剧恶化性能。这也是 TP 大小通常不超过 8 的原因（单节点 8 GPU）。

**2. 列切分 + 行切分组合的通信消除**

Megatron 巧妙地通过列切分接行切分，消除了两者之间的 All-Gather 或 All-Reduce。注意：如果两个列切分层连续，则需要插入额外的通信；但 Transformer 结构自然交替了需要通信的地方（Attention 输出和 MLP 输出需要全局信息）。因此 Megatron 的方案通信量最小化。

**3. 与 ZeRO 和 DP 的协同**

- TP 减少每卡参数量，使得单卡上 DP 的梯度大小（也是 `P/t`）减小，从而降低了 DP 的 All-Reduce 通信量。因此，TP 与 DP 结合可以改善 DP 扩展性。
- ZeRO-3 通过参数分片取代了 TP 的角色？实际上 ZeRO-3 通过 All-Gather 按需获取参数，能训练任何大模型，但其通信量极大（每层需要 All-Gather 权重）。TP 只需要 All-Reduce 激活，通信量是 `O(B S d)`，而 ZeRO-3 的通信量是 `O(P)`（每步）。对于非常大的模型，ZeRO-3 的参数通信可能成为瓶颈。因此，通常结合 TP（节点内）和 ZeRO（跨节点 DP）来平衡通信。

**4. 2D/2.5D TP 的实用价值**

在 1D TP 已经足够处理单节点 8 GPU 的今天，2D TP 仅在需要跨节点 TP 或更大 TP 组（如 16 或 32）时有意义。然而，目前主流方案是使用更小的 TP + 更大的 DP 或 PP，因为 PP 通信量比跨节点 TP 更低。2D TP 更多见于 HPC 领域的研究。

**5. 对 Attention 头数的约束**

TP 要求 `h % tp == 0`，即注意力头数必须能被 TP 组大小整除。这对模型设计提出了限制，如果头数不是 TP 的倍数，需要填充或复杂的重映射。Megatron 确保这一点。

**6. 通信与计算的重叠**

TP 的 All-Reduce 发生在层的输出处，通常无法与该层的主要计算（矩阵乘）重叠，因为矩阵乘需要完整结果才能进行下一层。不过，可以通过 CUDA Stream 和分块来尝试重叠一部分，但收益有限。因此 TP 通信通常是暴露在关键路径上的，优化通信后端至关重要。

### ① 形式化定义

Megatron-LM 提出了一种针对 Transformer 层的最小通信张量并行方案。其核心思想是：通过**将连续的线性层分别采用列切分和行切分**，使得中间激活无需通信即可直接在 GPU 之间传递，从而将一个 Transformer Block 内的通信次数压缩到最少——每个子层（Self-Attention、MLP）各只需要一次 All-Reduce。

以下定义中，假设张量并行度为 `t`，模型隐藏维度为 `d`，注意力头数为 `h`（满足 `h % t == 0`），每头维度 `d_head = d/h`。

**Self-Attention 切分形式化**：

1. **QKV 投影（列切分，无通信）**  
   Q、K、V 的权重矩阵 `W_Q, W_K, W_V ∈ R^{d×d}` 分别沿列（输出维度）切分为 `t` 份。GPU `i` 持有 `W_Q^i, W_K^i, W_V^i ∈ R^{d × d/t}`。  
   输入 `X ∈ R^{B·S×d}` 对所有 GPU 相同。计算：
   ```
   Q_i = X W_Q^i ,  K_i = X W_K^i ,  V_i = X W_V^i
   ```
   得到形状 `[B·S, d/t]` 的局部 Q、K、V。由于按头组织，每个 GPU 天然拥有 `h/t` 个完整头的 QKV，无需通信即可执行后续注意力计算。

2. **局部自注意力计算（无通信）**  
   将 `Q_i, K_i, V_i` 重塑为 `[B, h/t, S, d_head]`，各 GPU 独立执行带因果掩码的多头注意力，得到输出 `O_i ∈ R^{B·S × d/t}`（重新合并头维度）。

3. **输出投影（行切分 + All-Reduce）**  
   输出权重 `W_O ∈ R^{d×d}` 沿行（输入维度）切分。GPU `i` 持有 `W_O^i ∈ R^{d/t × d}`。计算：
   ```
   Y_i = O_i W_O^i   （形状 [B·S, d]）
   ```
   各 GPU 的 `Y_i` 是部分积，需要求和得到完整输出。因此执行 **All-Reduce(sum)**：
   ```
   Y = ∑_{i} Y_i
   ```
   Self-Attention 子层总共仅需 **一次 All-Reduce**。

**MLP 切分形式化**（以 SwiGLU 为例，标准 MLP 类似）：

1. **上投影（列切分，无通信）**  
   `W_gate, W_up ∈ R^{d×d_ff}` 沿列切分为 `t` 份。GPU `i` 计算：
   ```
   gate_i = SiLU(X W_gate^i) ,  up_i = X W_up^i
   ```
   然后逐元素乘：`h_i = gate_i ⊙ up_i`（形状 `[B·S, d_ff/t]`）。

2. **下投影（行切分 + All-Reduce）**  
   `W_down ∈ R^{d_ff×d}` 沿行切分。GPU `i` 持有 `W_down^i ∈ R^{d_ff/t × d}`。计算：
   ```
   Y_i = h_i W_down^i
   ```
   再执行 **All-Reduce(sum)** 得到完整 MLP 输出。

**总通信**：一个 Transformer Block 前向共 **2 次 All-Reduce**（Self-Attention 1 次 + MLP 1 次）。LayerNorm 和残差连接直接在每个 GPU 的局部张量上执行，无通信。

### ② 系统视角

**在整个知识树中的位置**：`2.2.3` 是张量并行（2.2）的工程实例化，直接对应 Megatron-LM 代码结构。它连接了 `1.2.4`（TP 抽象）与 `6.3`（Megatron-LM 系统实现），是理解工业界 TP 实现的关键节点。

**在训练流水线中的角色**：  
当模型以 TP 方式运行时，每个 Transformer Block 的计算被切分为 `t` 个并行的 GPU 计算流。两次 All-Reduce 是 Block 内部仅有的同步点。数据流如下：

```
输入 X (完整维度)
  │
  ├─ 列切分 QKV：各 GPU 计算局部 Q,K,V
  ├─ 局部 Attention
  ├─ 行切分 O_proj + All-Reduce ──┐
  │                                 同步点
  ├─ LayerNorm (局部)
  ├─ 列切分 gate/up + SiLU
  ├─ 行切分 down_proj + All-Reduce ─┤
  │                                 同步点
  └─ LayerNorm → 下一层
```

**通信拓扑**：  
All-Reduce 发生在 **TP 进程组**内，通常对应节点内的 GPU（高速 NVLink）。这些 All-Reduce 必须由 NCCL 高效执行（Ring 或 Tree 算法），且是 Block 计算的关键路径，无法被主要矩阵计算重叠。

**与其他并行策略的接口**：

- 与 **PP** 组合：每个流水线 stage 内部可能包含多个这样的 TP 切分 Block。P2P 通信传递的激活是完整维度（在 All-Reduce 之后），因此 PP 通信量不变。
- 与 **DP** 组合：DP 组复制整个模型，其梯度 All-Reduce 只发生在对应的 DP 进程组内，且由于 TP 减少了每卡参数，DP 的梯度通信量也成比例减小。
- 与 **ZeRO** 组合：ZeRO 的分片粒度为参数级，与 TP 的张量切分正交。通常 TP 在节点内使用，ZeRO 的 dp 组跨节点。

### ④ 复杂度分析

**通信量**（一个 Block，前向）：
- Attention 输出 All-Reduce：`B × S × d` 元素（FP16 下 `2 B S d` bytes）
- MLP 输出 All-Reduce：同样 `2 B S d` bytes
- **Block 通信总量**：`4 B S d` bytes
- 反向传播时，对应两次 All-Reduce 变为两次 **Reduce-Scatter**（梯度通信），通信量相同。

**与未优化 TP 的对比**：
如果 QKV 和输出投影不是按列/行组合而是各自独立做 All-Gather/All-Reduce，则通信量可能是现在的 2~3 倍。Megatron 方案通过列切分与行切分相邻放置，消除了中间 All-Gather，达到了理论通信下界（每个子层仅需一次全局同步）。

**计算量**（单 GPU）：
参数量和计算量均分片，每 GPU 计算量 ≈ `原计算量 / t`（近似线性，忽略通信开销）。

**延迟分析**：
All-Reduce 发生在每个 Block 的关键路径末尾。对于 L 层，总通信延迟约为 `2L × T_allreduce`，其中 `T_allreduce` 与消息大小 (`2 B S d` bytes) 和 `t` 相关。当 `t` 较小时（≤8），NCCL 的 Ring All-Reduce 延迟很低（A100 NVLink 上微秒级）。若层数多，累积延迟可观，但每层通信与计算可部分重叠（由于计算时间长，通信可能被掩盖）。

**扩展极限**：
- `t` 增大 → 每卡计算量减小，但 All-Reduce 的延迟随进程数对数增长（Ring），带宽利用率略微下降。主要瓶颈在于 `B S d` 不可太小，否则通信占比升高。
- 当 `B S d` 固定时，增大 `t` 会减小每卡计算量，使通信相对开销变大。因此 TP 不适合在单卡计算量已经很小时使用（即 DP 已足够时没必要加 TP）。

---

### ⑤ 设计权衡

**1. 通信最小化与模型设计的耦合**  
Megatron 方案要求 Transformer Block 的结构满足“列切分→独立计算→行切分”的模式。幸运的是，标准 Transformer 的 Attention 和 MLP 都符合该模式。但如果模型使用非标准结构（如多个连续线性层之间不需要完整全局信息），可能需要插入额外的通信，TP 收益降低。这是 TP 对模型结构的一种隐性约束。

**2. All-Reduce 的位置与激活存储**  
All-Reduce 在输出投影和 MLP 下投影之后，意味着残差连接的输入是完整维度的。如果同时使用序列并行（SP），LayerNorm 和 Dropout 的输入可以被切分，从而节省激活存储。Megatron 序列并行正是将 LayerNorm 前的 All-Reduce 替换为 Reduce-Scatter + All-Gather，以在序列维度切分激活。这里 TP 和 SP 的协同揭示了通信模式重构的可能。

**3. 反向传播的通信**  
前向的 All-Reduce 在反向时变为 Reduce-Scatter（针对梯度）。通信量相同，但通信模式变化可能影响重叠机会。NCCL 的 Reduce-Scatter 同样高效。

**4. TP 与激活检查点的相互作用**  
启用检查点后，每个 Block 的前向会执行两次（重算），导致 All-Reduce 也执行两次。虽然通信量加倍，但显存节省通常优先。Megatron 默认在每个 Transformer Block 边界做检查点，意味着 TP 通信开销也随重算而倍增，需在总吞吐中考虑。

**5. 对未来模型设计的启示**  
Megatron 的切分方案已成为 TP 的事实标准。设计新模型时，如果希望高效使用 TP，通常会保持“列切分 + 独立计算 + 行切分”的 Block 结构。例如，一些新架构调整了 MLP 内的激活函数，但并不改变列/行切分的基本格局。
