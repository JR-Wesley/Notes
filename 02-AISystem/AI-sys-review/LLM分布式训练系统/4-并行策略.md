# 并行策略

## 展开 Chapter 10：数据并行（DP）

---

Chapter 10 是最基础也是应用最广泛的分布式并行策略。它解决的核心问题是：**当单卡算力不足以在合理时间内完成训练时，如何通过复制模型、切分数据，利用多 GPU 协同加速？**

下面给出 Chapter 10 的整体概览，它由两个紧密关联的子节点构成，建议顺序学习。

---

### ① Formal Definition（形式化定义）

**数据并行（Data Parallelism, DP）** 是一种分布式训练策略，其核心思想是：

- **模型复制**：每个 GPU 上拥有完全相同的模型副本（参数、优化器状态各自独立维护）。
- **数据切分**：将全局批次（Global Batch）按样本维度切分为多个微批（Micro Batch），每个 GPU 消费不同的微批数据独立执行前向与反向传播。
- **梯度同步**：在反向传播完成后，所有 GPU 通过集合通信操作（通常为 AllReduce）对本地计算出的梯度进行平均或求和，确保各副本的参数更新一致。

形式化表述：设全局批大小为 \(B_{global}\)，有 \(N\) 个 GPU。每个 GPU 处理的微批大小为 \(b = B_{global} / N\)。对于任意 GPU \(i\)，其本地计算流程为：

1. 前向：\( \hat{y}_i = f(x_i; W) \)
2. 损失：\( L_i = \ell(\hat{y}_i, y_i) \)
3. 反向：\( \nabla W_i = \frac{\partial L_i}{\partial W} \)
4. 同步：\( \nabla W_{sync} = \frac{1}{N} \sum_{j=1}^{N} \nabla W_j \)  (AllReduce MEAN)
5. 更新：\( W \leftarrow W - \eta \cdot \nabla W_{sync} \)

**关键约束**：所有 GPU 的模型参数在更新后**严格一致**，这由同步操作的确定性语义保障。

### ② System Design View（系统视角）

在整个并行策略体系中，数据并行是最外层、扩展性最强的策略，通常作为“基底”与其他策略混合使用：

```
                   全局批次数据
                        │
               ┌───────┼───────┐
               ▼       ▼       ▼
           GPU 0   GPU 1   ... GPU N-1
         (完整模型)(完整模型)   (完整模型)
               │       │        │
               ▼       ▼        ▼
         本地前向   本地前向   本地前向
         本地反向   本地反向   本地反向
               │       │        │
               └───────┼───────┘
                       ▼
              AllReduce 梯度同步
                       │
               ┌───────┼───────┐
               ▼       ▼       ▼
           优化器更新 优化器更新 优化器更新  (各卡独立但一致)
```

**输入**：
- 模型完整副本（各 GPU 已加载相同权重）
- 数据加载器（DistributedSampler 确保各卡数据不重叠）
- 通信域（Process Group，定义参与 AllReduce 的 GPU 集合）

**输出**：
- 各 GPU 上参数一致更新
- 全局模型等同于在 \(B_{global}\) 上训练的模型

**依赖关系**：
- 前承 8.1 显存瓶颈：DP 不减少单卡模型状态显存，因此单纯 DP 无法解决显存瓶颈（大模型仍需结合模型并行/ZeRO）。
- 前承 8.2 算力瓶颈：DP 是解决算力瓶颈的主要手段，理论上加速比可接近 N。
- 后启 10.1 数据切分、10.2 梯度同步的具体机制；与 11/12/13 章组合形成 3D 并行。

### ③ Implementation Mapping（工程映射）

**PyTorch DDP（DistributedDataParallel）**：
- `torch.nn.parallel.DistributedDataParallel` 封装模型。
- 自动注册 Autograd Hook，在反向传播过程中触发梯度 AllReduce。
- 采用 **Reducer** 进行梯度分桶（Bucket），将多个参数的梯度合并后异步通信，实现计算与通信重叠（Overlap）。
- 用法示例：

```python
model = DDP(model, device_ids=[local_rank])
# 训练循环中：loss.backward() 内部自动触发 allreduce
```

**Megatron-LM**：
- 数据并行是混合并行的最外层（DP 包裹 TP/PP）。
- 通信域构建：在全局通信组中，跨 TP/PP 组的相同位置 GPU 组成 DP 组。
- 梯度同步时，仅在 DP 组内执行 AllReduce，TP/PP 组内通过各自的通信模式完成其他同步。

**DeepSpeed**：
- DeepSpeed 的 ZeRO 是数据并行的增强版：在 DP 的基础上增加参数/梯度/优化器状态的分片（详见 13.4）。
- ZeRO-1：优化器状态分片，梯度同步仍为 AllReduce（但各卡只保存部分状态）。
- ZeRO-2：增加梯度分片，梯度同步变为 ReduceScatter，更新后 AllGather 参数。
- ZeRO-3：参数也分片，需在每次前向/反向时 AllGather 参数。

**通用启动方式**：`torchrun` 或 `mpirun` 启动多进程，每个进程对应一个 GPU，通过环境变量获取 rank 和 world_size。

### ④ Complexity Analysis（复杂度分析）

**通信量**（标准 AllReduce，每个 GPU 的发送/接收量）：
- Ring AllReduce 算法：每卡发送 \(2P\) bytes（P 为参数量），分 \(2(N-1)\) 步完成，有效带宽近似 \(B_{eff} = \frac{2B}{N}\)，通信时间 \(T_{comm} = \frac{2P}{B_{eff}} = \frac{NP}{B}\)。
- Tree AllReduce：有效带宽更高，但对大消息不友好（分块受限），实践中 NCCL 自动选择最优算法。

**计算量**（每 GPU）：
- 前向与反向 FLOPs 与微批大小 b 成正比。总计算量（全 N 卡）与单卡处理全批次相同，因此**计算总量不变，只是并行化**。

**显存占用**（每 GPU）：
- **模型状态**：完整保留，每卡 \(M_{model\_states} = 16P\) bytes（混合精度 Adam），与单卡完全一致。
- **激活值**：正比于微批大小 b（\(B_{global} / N\)），比单卡全批次小 N 倍。
- **通信缓冲区**：额外分配用于 AllReduce 的缓冲区，通常为参数量 P 的常数倍（视分桶大小而定）。

**扩展效率**：
- 理想加速比 = \(N\)（忽略通信）。
- 实际加速比因通信开销随 N 增加而递减。Amdahl 定律适用：若通信时间占比为 \(\alpha\)，加速比 = \(\frac{N}{1 + (N-1)\alpha}\)。
- 因此 DP 规模通常受限：在 8 卡 NVLink 内效率 > 95%；跨节点扩展时，受网络带宽（8.3）影响，效率逐步下降。

**DP 与显存瓶颈的关系**：
- DP 无法缩减单卡模型状态显存，因此**大模型无法仅靠 DP 训练**。必须结合模型并行（TP/PP）或 ZeRO 来分片模型状态，DP 负责解决算力瓶颈。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：全局批大小与收敛性**
- DP 增加 GPU 数，若保持每卡微批大小 b 不变，则全局批大小 \(B_{global}\) 线性增加。
- 过大的全局批大小可能导致模型收敛困难（泛化性能下降），需要调整学习率 scaling 策略（如线性 scaling rule，或更先进的 LARS/LAMB 优化器）。
- 在固定全局批大小下，增加 GPU 只能减小每卡微批（可能降至 1），导致 GPU 计算效率下降（Tensor Core 利用率低）。此时需权衡：是接受低利用率，还是增大全局批大小。

**Trade-off 2：通信与计算的 Overlap**
- DDP 通过将梯度分桶（Bucket），在最后一个反向 Kernel 完成后立即开始通信，试图将 AllReduce 与前向计算或下一轮反向重叠。
- 但这种 Overlap 需要额外的 CUDA Stream 和通信缓冲区，增加显存开销。当显存紧张时，可能被迫关闭部分 Overlap。

**Trade-off 3：DP 作为“外层”策略**
- 在 3D 并行（DP + TP + PP）中，DP 组通常跨节点构建（利用较大网络带宽），而 TP 在节点内（利用 NVLink）。DP 的通信量（每次迭代 \(2P\)）在模型很大时可能成为瓶颈，因此通常结合 ZeRO-1/2 减少通信量或使用分级通信（Hierarchical AllReduce）。

**Trade-off 4：梯度累积替代 DP**
- 如果只有单卡但想模拟大全局批次，可使用梯度累积（多个 micro batch 累加梯度后更新）。这不解决算力瓶颈，但可模拟 DP 的训练超参数。
- 梯度累积的时间与 DP 一样（总计算量不变），但无通信开销，是单卡调参的常用手段。

## 展开 10.1：数据切分

---

### ① Formal Definition（形式化定义）

**数据切分（Data Sharding / Data Partitioning）** 是数据并行（DP）中实现样本级并行的基础机制。其目标是将一个全局训练批次（Global Batch）中的样本**不重叠、不遗漏**地分配到 \(N\) 个参与 DP 的 GPU 上，每个 GPU 独立消费一个微批（Micro Batch），从而所有 GPU 在逻辑上共同完成一个全局批次的训练。

形式化定义：设全局数据集 \( \mathcal{D} \) 包含 \( |\mathcal{D}| \) 个训练样本。每个训练步骤中，全局批次 \( B_{global} \) 是 \( \mathcal{D} \) 的一个子集，包含 \( B \) 个样本。数据切分函数 \( \text{Partition}(B_{global}, N, rank) \) 返回分配给 rank 为 \( r \) 的 GPU 的本地样本索引集合 \( I_r \)，满足：

\[

\bigcup_{r=0}^{N-1} I_r = \{0, 1, \dots, B-1\} \quad \text{and} \quad I_p \cap I_q = \emptyset, \ \forall p \neq q

\]

通常采用**均匀切分**：\( |I_r| = \lfloor B/N \rfloor \) 或通过余数分配保证各卡差异不超过 1。

在多个训练 epoch 中，切分必须配合**全局 shuffle**，确保每个 epoch 的样本分配随机且无重复，以维持训练的随机性（i.i.d. 假设）。

---

### ② System Design View（系统视角）

在整个数据并行流水线中，数据切分位于数据加载器与模型前向传播之间：

```
数据集 (存储于磁盘/共享文件系统)
       │
       ▼
全局 Shuffle (每个 epoch)
       │
       ▼
DistributedSampler 分配索引 → 每个进程获得不重叠的样本索引集
       │
       ▼
DataLoader (每个 GPU 独立) → 加载本地样本 → 微批 (b = B/N)
       │
       ▼
模型前向传播 (各 GPU 并行执行)
```

**输入**：
- 全局批次大小 \(B_{global}\) 和 GPU 数量 \(N\)
- 当前 rank（进程标识）
- 随机种子（保证各 rank 的 shuffle 同步）

**输出**：
- 每个 GPU 上唯一的、确定的样本索引集
- 各 GPU 数据加载器产出的微批张量

**依赖关系**：
- 依赖 17.1（Process 与 Rank）中的 rank 标识和进程组概念。
- 向后为 10.2 梯度同步提供各 GPU 本地梯度的数据基础。
- 是 DP 策略中唯一与“数据”直接交互的组件。

**关键设计约束**：
- **不重叠**：确保每个样本在一个训练步骤中仅被一个 GPU 处理，避免数据重复导致统计偏差。
- **全局覆盖**：每个全局批次覆盖 \(B\) 个独立样本，保证梯度估计无偏。
- **确定性**：给定相同的随机种子，各 GPU 的切分必须可复现，便于调试和 checkpoint 恢复。
- **负载均衡**：各 GPU 微批大小相等（或差 1），避免计算等待，最大化并行效率。

---

### ③ Implementation Mapping（工程映射）

**PyTorch Distributed 实现**：
使用 `torch.utils.data.distributed.DistributedSampler`：

```python
from torch.utils.data import DataLoader
from torch.utils.data.distributed import DistributedSampler

dataset = ...  # 完整数据集
sampler = DistributedSampler(
    dataset,
    num_replicas=world_size,  # N, GPU总数
    rank=rank,                # 当前 GPU rank
    shuffle=True,             # 每个 epoch 全局 shuffle
    seed=0                    # 所有 rank 必须相同
)
dataloader = DataLoader(dataset, batch_size=b, sampler=sampler, ...)
```

- **Shuffle 机制**：`DistributedSampler` 在 `set_epoch(epoch)` 被调用时，使用 `seed + epoch` 生成全局随机排列。所有 rank 使用相同的 seed 和 epoch，从而生成相同的全局排列，再根据 rank 取各自的分片。这保证了各 rank 看到的数据不重叠。
- **分片逻辑**：按 rank 顺序截取连续段。例如，全局排列后，rank 0 取前 \( \lceil B/N \rceil \) 个索引，rank 1 取下一段，依此类推。余数样本分配给低 rank。
- **迭代器生成**：`DataLoader` 使用 `sampler` 生成的索引，每个 rank 只加载属于自己的样本。

**Megatron-LM 实现**：
- 采用类似机制，但数据加载常基于 `blendable_dataset` 和 `dataset_utils`，支持多数据集混合。
- 使用 `torch.distributed.broadcast` 同步某些数据集配置参数，确保各 rank 数据分布一致。

**DeepSpeed 实现**：
- DeepSpeed 沿用 PyTorch 的 `DistributedSampler` 或自定义的 `DistributedDataLoader`，但通常通过 `deepspeed.initialize()` 后模型的 `train_batch_size` 和 `gradient_accumulation_steps` 来推导微批大小，需保证全局批大小正确切分。

**关键工程细节**：
- 每个 rank 必须调用 `sampler.set_epoch(epoch)` 开始新 epoch，否则 shuffle 种子不会更新，导致不同 epoch 数据分布重复。
- 在分布式文件系统（如 Lustre）中，需注意 I/O 竞争；常通过预取（prefetching）和高速缓存优化数据加载。
- 对于不支持随机访问的数据集，切分可能复杂，需要预处理成有序索引。

---

### ④ Complexity Analysis（复杂度分析）

**切分本身的复杂性**：
- 时间：`DistributedSampler` 的 shuffle 操作在每个 epoch 开始时执行一次全局随机排列（Fisher-Yates），复杂度 \(O(B)\)（B 为总样本数）。由于仅在 epoch 开始时执行，分摊到每个 step 的 overhead 极小。
- 空间：存储全局排列需要 \(O(B)\) 索引（如 int64）。对于超大 B（数十亿），全排列内存开销高，可采用分块 shuffle 或在线算法，但实际 PyTorch 仍用全排列。

**对训练时间的影响**：
- 数据切分本身不增加计算或通信时间。真正的开销在于**数据加载 I/O**，每个 GPU 独立从存储读取本地样本。若存储带宽不足或文件系统并发性能差，数据加载可能成为瓶颈（data stall）。
- 优化手段：使用 `DataLoader(num_workers>0)` 进行多进程预取；使用高效的二进制数据格式（如 `webdataset`、`MosaicML streaming`）。

**负载均衡分析**：
- 当 B 不能被 N 整除时，低 rank 会多处理 1 个样本。在全局批大小较大（如成千上万）时，这种不平衡可忽略（<0.1%）。
- 在极小批次（如 B=2, N=4）时显著，但实际大模型训练中 B 通常远大于 N。

**与其他并行的交互**：
- 在 3D 并行中，数据切分在 DP 维度进行。若同时使用 TP/PP，每个 DP 组内的数据切分规则不变，但需保证不同 DP 组之间的数据分配也满足全局 shuffle 逻辑（通常通过将 DP rank 视为最高维度的切分维度）。Megatron 通过复杂的 `groups` 处理，使 DP 组内的 rank 共享同一份数据，而组间切分。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：全局批大小与微批大小的平衡**
- 增大 N（更多 GPU）并保持微批大小 b 不变，全局批大小 \(B\) 线性增大，可能导致收敛问题。
- 若要维持固定的 \(B_{target}\)，则增加 N 后必须减小每卡微批 b，可能导致 GPU 计算效率下降（矩阵乘法维度减小，Tensor Core 利用率降低）。
- 工程上通常先确定能高效计算的微批大小 b（如 1~8），再通过 DP 扩展至全局批大小，并配合梯度累积微调。

**Trade-off 2：Shuffle 的确定性与随机性**
- 使用固定 seed 保证可复现性，但可能无法探索足够多样的数据顺序。
- 在某些训练策略（如 curriculum learning）中，需要动态调整数据顺序，此时不能使用标准 DistributedSampler，需自定义。

**Trade-off 3：数据加载 I/O 竞争与分布式存储**
- 所有 GPU 同时从同一个文件系统读取数据，可能产生严重的 I/O 压力。可采用每个 rank 读取独立文件（数据分片存储）或使用对象存储（S3 等）缓解。
- 在大规模集群中，常采用**数据预分片**方案：数据在预处理阶段就按总 GPU 数分好 shard，每个 rank 只读自己的 shard，避免在线 shuffle 的全局排列内存和 I/O 竞争。

**Trade-off 4：动态序列长度与数据切分**
- 若样本长度动态变化，简单的均匀样本分配可能导致不同 GPU 的总 token 数不均衡，造成计算等待。此时需按 token 数进行更复杂的均衡分配（packing 策略），超越传统 DistributedSampler 的能力。
- DeepSpeed 的 curriculum learning 和 Megatron 的 dataset blending 提供了部分解决方案，但仍需额外设计。

## 展开 10.2：梯度同步

---

### ① Formal Definition（形式化定义）

**梯度同步（Gradient Synchronization）** 是数据并行（DP）中确保所有模型副本在优化器更新后保持参数严格一致的通信过程。每个 GPU 独立执行前向与反向传播，产生**本地梯度**（local gradients）。在更新参数之前，所有 GPU 必须对各自的本地梯度执行全局聚合，通常采用 **AllReduce** 集合通信操作，计算所有 GPU 上梯度的平均值（或求和）。

形式化表述：

设有 \(N\) 个 GPU，第 \(i\) 个 GPU 计算的本地梯度为 \(\nabla W_i \in \mathbb{R}^{P}\)（\(P\) 为参数量）。梯度同步操作计算：

\[

\nabla W_{sync} = \frac{1}{N} \sum_{i=0}^{N-1} \nabla W_i

\]

此结果被分发回每个 GPU，用于后续优化器更新：

\[

W^{new} = W^{old} - \eta \cdot \nabla W_{sync}

\]

该过程保证了每一次更新后，所有 GPU 上的模型权重 \(W\) 位对应完全相同（bitwise identical，依赖确定性计算和同一随机种子）。

**通信语义**：AllReduce 可分解为 ReduceScatter + AllGather，或直接由高效的环形/树形算法实现。数学上要求参与通信的张量满足求和交换律与结合律。实际浮点运算中，由于累加顺序不同可能产生微小误差（通常被忽略），但对大模型混合精度训练需注意数值一致性。

---

### ② System Design View（系统视角）

在整个数据并行执行流程中，梯度同步处于反向传播（Backward）与优化器更新（Optimizer Step）之间，是实现参数一致性的**核心同步点**：

```
 GPU 0                  GPU 1                ...        GPU N-1
   │                      │                               │
   ▼                      ▼                               ▼
 前向传播               前向传播                        前向传播
   │                      │                               │
   ▼                      ▼                               ▼
 反向传播               反向传播                        反向传播
 (本地梯度 ∇W_0)        (本地梯度 ∇W_1)                (本地梯度 ∇W_{N-1})
   │                      │                               │
   └──────────────────────┼───────────────────────────────┘
                          │
                    梯度同步 (AllReduce)
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
       ∇W_sync         ∇W_sync        ∇W_sync
          │               │               │
          ▼               ▼               ▼
     优化器更新        优化器更新       优化器更新
```

**输入**：
- 每个 GPU 上反向传播结束后的本地梯度张量集合（所有可学习参数的梯度）。
- 参与同步的进程组（DP Process Group），由 17.2 Process Group 概念定义。

**输出**：
- 每个 GPU 收到全局平均（或求和）后的梯度，张量形状与本地梯度完全一致。
- 同步后各 GPU 参数更新起点完全相同，训练逻辑等价于在全局批大小上训练。

**依赖关系**：
- 前承 10.1 数据切分（本地梯度来源不同微批）。
- 后启优化器步骤（参数更新）。
- 依赖底层 NCCL（Chapter 14）高效实现 AllReduce。
- 与 16.2 Compute-Communication Overlap 紧密相连（梯度同步可与反向传播最后阶段或下一前向重叠）。

**关键设计目标**：
- **正确性**：梯度聚合必须完成所有参数才能更新，否则会导致参数不一致。
- **低延迟**：通信时间直接影响迭代速度，需最小化。
- **带宽利用率**：最大化有效带宽，接近硬件互联上限。
- **异步与重叠**：通过分桶和 CUDA Stream 将通信与计算重叠，隐藏通信延迟。

---

### ③ Implementation Mapping（工程映射）

#### a) PyTorch DDP（DistributedDataParallel）

PyTorch DDP 是梯度同步最典型的工程实现，核心组件为 **Reducer**（位于 `torch/csrc/distributed/c10d/reducer.cpp`）。

**工作流程**：
1. **注册 Autograd Hook**：模型被 `DDP` 包装时，为每个需要梯度的参数注册 `grad_accumulator` 钩子。当参数的反向传播完成（梯度就绪）时，钩子触发。
2. **梯度分桶（Bucketing）**：Reducer 将所有参数按**逆序**分组放入多个桶（默认桶大小 25MB），使最早完成梯度的参数等待桶被填满，然后统一发起通信。这种策略将多次小消息通信合并为大消息，提升带宽利用率。
3. **异步 AllReduce**：当某个桶内所有参数的梯度都就绪后，立即将该桶的梯度张量展平（flatten）并启动 NCCL AllReduce。通信在一个独立的 CUDA Stream 上执行，不阻塞主计算流。
4. **计算 - 通信重叠**：等待桶填满期间，后续参数的反向计算可继续执行；AllReduce 完成后的梯度在优化器步骤中才被使用，从而有效掩盖了通信延迟。
5. **梯度分发**：AllReduce 完成后，将平均梯度写回到每个参数的 `.grad` 字段，供优化器使用。

**关键代码片段**：

```python
model = torch.nn.parallel.DistributedDataParallel(
    model,
    device_ids=[local_rank],
    bucket_cap_mb=25,        # 桶容量
    gradient_as_bucket_view=True  # 使用视图避免复制
)
# 训练循环：
loss.backward()  # 内部触发 reducer 的 autograd hooks
optimizer.step()
```

`loss.backward()` 内自动完成 AllReduce，用户无需手动调用。

**DDP 的启动与配置**：
- 需使用 `torch.distributed.init_process_group` 初始化 NCCL 后端。
- 支持 `find_unused_parameters=False`（默认）以跳过未参与计算参数的同步。

#### b) Megatron-LM

Megatron 采用 3D 混合并行，其梯度同步机制依赖于并行通信域（Process Groups）的精心构造。

- **DP 组**：在混合并行中，DP 是跨 PP/TP 组的外层并行。Megatron 在 `megatron/core/parallel_state.py` 中定义了各类通信组（`mpu` 模块），其中 `DATA_PARALLEL_GROUP` 专门用于梯度同步。
- **梯度同步时机**：对于 DP 组内的参数，反向传播结束后执行 AllReduce。TP 和 PP 涉及的梯度则由对应的并行策略处理（TP 组内 AllReduce、PP 通过 P2P 传递）。
- **分桶**：Megatron 也实现了类似 DDP 的分桶机制，且桶大小可由参数控制。因参数规模更大，Megatron 的桶可能更高（数百 MB）。
- **ZeRO 协作**：当与 DeepSpeed 结合时，Megatron 将梯度同步委托给 DeepSpeed 引擎。

#### c) DeepSpeed（ZeRO 模式下的梯度同步）

DeepSpeed 的 ZeRO 阶段重新定义了梯度同步的通信模式：

- **ZeRO-1（优化器状态分片）**：梯度仍通过标准 AllReduce 同步（与 DDP 相同），但在优化器更新后，每个 GPU 只保留自己分片内的优化器状态。
- **ZeRO-2（增加梯度分片）**：梯度同步不再使用 AllReduce，而是 **ReduceScatter**。每个 GPU 只接收自己负责分片参数的平均梯度，通信量从 \(2P\) 降至约 \(P + \frac{P}{N}\) 字节（每个 GPU 发送 \(P\) 字节梯度，接收 \(\frac{P}{N}\) 字节归属梯度）。
- **ZeRO-3（参数分片）**：前向/反向时需要 AllGather 收集参数；反向产生全量本地梯度（非分片），仍使用 ReduceScatter 将梯度同步并分散到各卡。

**通信原语差异**：

| 策略 | 梯度同步原语 | 每 GPU 通信量（参数 P, N 卡） |
|------|------------|---------------------------|
| DP (DDP) | AllReduce | \(2P\) |
| ZeRO-1 | AllReduce | \(2P\) |
| ZeRO-2 | ReduceScatter | \(\approx P + P/N\) |
| ZeRO-3 | ReduceScatter（分片后的部分）| 取决于分片 |

**DeepSpeed 的同步调度**：
- 利用 CUDA Stream 异步执行通信。
- 支持通过 `overlap_comm` 参数控制是否将通信与计算重叠（通常默认开启）。
- 在 `deepspeed/runtime/zero/stage2.py` 等文件中实现了梯度同步队列。

### ④ Complexity Analysis（复杂度分析）

#### 通信时间

标准 AllReduce（Ring 算法）通信时间：

\[

T_{comm} = 2(N-1) \cdot \frac{P \cdot \text{bytes\_per\_param}}{B_{link}} \approx \frac{2 \cdot N \cdot P \cdot \text{bytes\_per\_param}}{B_{link}}

\]

其中 \(B_{link}\) 为单 GPU 双向带宽（Bytes/s），实际受限于 NVLink/IB 带宽及算法效率。

- **通信量与 N 的关系**：每 GPU 发送/接收量固定（约 \(2P\) 字节），但总步数随 N 增加而增加，导致有效带宽下降（Ring AllReduce 有效带宽约 \(2B/N\)），通信时间随 N 线性增长。
- **对训练吞吐的影响**：设单卡计算时间（前向 + 反向）为 \(T_{calc}\)，总迭代时间 \(T_{iter} = T_{calc} + T_{comm}\)（若不能完全重叠）。加速比 \(S = \frac{N \cdot T_{calc}}{T_{iter}}\)，当 \(T_{comm}\) 不可忽略时，S 远小于 N。

**实际场景示例**（7B 模型，N=8，NVLink 600 GB/s，P≈13.5 GB 梯度）：
- 每卡 AllReduce 通信量 = 2 × 13.5 GB = 27 GB。
- 有效带宽（Ring）≈ 2×600/8 = 150 GB/s → 通信时间 ≈ 27/150 = 0.18 秒。
- 若单卡计算时间为 0.8 秒（s=2048），通信占比 ≈ 18%。若完全不能重叠，加速比约 8×0.8/(0.8+0.18) ≈ 6.5 倍。

#### 显存开销

梯度同步本身不显著增加显存（梯度本身就是必须存储的），但**分桶机制**需要额外**通信缓冲区**：

- PyTorch DDP 默认分配多个桶，每个桶对应一组参数的展平视图。桶的总显存等于梯度总大小（\(P\) 元素 × 2 bytes FP16），但通过视图（`gradient_as_bucket_view=True`）可避免额外复制，仅额外存储少许控制结构。
- 若使用 `gradient_as_bucket_view=False` 或通信库内部缓冲，可能额外需要 1× 梯度显存。
- ZeRO-2/3 的 ReduceScatter 需要临时缓冲区存放接收到的梯度分片，通常量级为 \(P/N\)。

因此，显存开销通常可控，约为模型参数的 1-2 倍梯度占用。

#### 扩展性（Scaling Behavior）

- **弱扩展（Weak Scaling）**：保持每卡批次大小不变，增加 GPU 数（增大全局批次），计算量 \(T_{calc}\) 基本不变（理想情况），但通信时间随 N 上升，效率递减。
- **强扩展（Strong Scaling）**：固定全局批次，增加 GPU 数，每卡批次变小，\(T_{calc}\) 下降，通信时间可能不变或略有增加，通信占比急剧上升，扩展效率更差。
- **突破扩展极限的方法**：增大每卡计算量（梯度累积）、使用更高带宽互联（NVSwitch）、采用分级通信（节点内 Reduce 后再跨节点 AllReduce，Chapter 15.3）。

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：同步频率 vs. 参数一致性**

- 标准 DP 每次迭代后同步，保证参数严格一致。
- **梯度累积（Gradient Accumulation）**：多个微批累加梯度后执行一次 AllReduce，降低通信频率，变相增大有效计算/通信比。代价：优化器更新步数减少，可能影响收敛速度，且需更大显存保留累积梯度。
- 某些场景甚至采用完全异步 SGD（Asynchronous SGD），各 GPU 独立更新参数并异步拉取最新参数，可消除通信等待，但会引入参数不一致性（stale gradients），影响最终模型质量。现代大模型训练极少使用。

**Trade-off 2：分桶大小（Bucket Size）**

- **大桶**：减少通信启动次数，提高带宽利用率，但需等待桶内所有梯度就绪，增加延迟，降低重叠机会。
- **小桶**：更快启动通信，重叠度高，但可能产生大量小消息，降低有效带宽。
- DDP 默认 25MB 是实践折衷，Megatron 根据模型大小可调整至 200MB+。

**Trade-off 3：AllReduce 算法选择（Ring vs Tree）**

- Ring AllReduce：适合大消息，带宽最优，步数多（2(N-1)），延迟随 N 线性增加。
- Tree AllReduce：延迟对数增长（\(2\log N\)），但对大消息带宽差（因数据被分段，无法填满链路）。
- NCCL 自动根据消息大小和拓扑选择最优算法，用户通常无需介入。

**Trade-off 4：重叠（Overlap）与显存**

- 将通信放入独立 Stream 实现与计算重叠，需要额外的通信缓冲区。在显存极度紧张时，可能不得不放弃部分重叠，让通信与计算串行。
- DeepSpeed 提供 `overlap_comm` 开关，允许用户在显存和速度间权衡。

**Trade-off 5：梯度剪裁（Gradient Clipping）与同步**

- 大模型训练中常对梯度进行全局范数剪裁，这需要先 AllReduce 梯度平方和得到全局梯度范数，再对本地梯度进行缩放。这额外引入一次 AllReduce 通信（用于范数）。PyTorch DDP 通过 `torch.nn.utils.clip_grad_norm_` 自动处理，但需注意这增加了通信量。

**Trade-off 6：数值确定性与性能**

- 浮点加法不满足结合律，不同数量 GPU 或不同分桶边界可能导致梯度累加顺序不同，产生微小数值差异。为获得完全确定性结果，需使用固定桶边界、固定通信算法、甚至特殊编译选项（如 `torch.use_deterministic_algorithms`），这通常会降低性能。工业界通常接受微小误差。

## 展开 11.1：Column Parallel（列并行）

---

### ① Formal Definition（形式化定义）

**Column Parallel（列并行）** 是张量并行（Tensor Parallelism, TP）的一种基本切分模式，指将线性层（或可推广到其他层）的**权重矩阵按列维度**切分到多个 GPU 上，每个 GPU 持有权重矩阵的一部分列，从而将原本完整的矩阵乘法 \(Y = X \cdot W\) 分解为多个独立的、可并行执行的子矩阵乘法。

形式化定义：

设全量线性层为：

\[

Y = X \cdot W, \quad X \in \mathbb{R}^{s \times h}, \quad W \in \mathbb{R}^{h \times h_{out}}

\]

其中 \(s\) 为序列长度，\(h\) 为输入隐藏维度，\(h_{out}\) 为输出维度。

在 Column Parallel 中，将权重 \(W\) 按列切分为 \(N\) 份（\(N\) 为 TP 组大小）：

\[

W = [W_1, W_2, \dots, W_N], \quad W_i \in \mathbb{R}^{h \times (h_{out}/N)}

\]

每个 GPU \(i\) 持有 \(W_i\)，并复制完整的输入 \(X\)（通过 AllGather 或事先持有）。计算本地输出：

\[

Y_i = X \cdot W_i, \quad Y_i \in \mathbb{R}^{s \times (h_{out}/N)}

\]

最终输出 \(Y\) 由所有 \(Y_i\) 拼接得到。当后续层需要完整的 \(Y\) 时，需执行 AllGather 将各个列块拼接恢复；若后续层也是 Column Parallel（且保持一致的分割），则无需通信，可直接将 \(Y_i\) 作为下一层的输入分片。

**关键通信原语**：
- 输入复制：若输入 \(X\) 没有分片，则各 GPU 已持有全量，无需通信。
- 输出同步：如需要完整输出，需 AllGather 拼接。
- 反向传播：对 \(X\) 的梯度需 AllReduce（各 GPU 计算出的 \(X\) 梯度部分求和），对 \(W_i\) 的梯度各自独立计算，无需通信。

---

### ② System Design View（系统视角）

在整个混合并行训练系统中，Column Parallel 通常与 Row Parallel（11.2）成对出现，用于构建完整的 Self-Attention 和 MLP 层，以减少单卡显存和计算量，同时将通信限制在机内（NVLink）高速域内。

**位置**：一般应用于 Transformer Block 中的线性层：
- Attention 中的 Q、K、V 投影（Column Parallel）及 Output 投影（Row Parallel）。
- MLP 中的第一线性层（Column Parallel）及第二线性层（Row Parallel）。

**输入/输出/依赖**：
- **输入**：隐藏状态 \(X \in \mathbb{R}^{s \times h}\)（可以是全量或已被分片）。
- **Column Parallel Linear 输出**：每个 GPU 得到部分输出 \(Y_i\)。
- **反向依赖**：在 Column Parallel 后如果跟 Row Parallel，则无需 AllGather 完整输出，直接传递分片，通信仅发生在 Row Parallel 的 AllReduce 和本 Column Parallel 反向的 AllReduce（对 X 梯度）。
- **依赖关系**：
  - 需要机内高带宽（NVLink/NVSwitch）支撑 AllGather/AllReduce。
  - 与 11.2 Row Parallel 配对使用，形成封闭 TP 块。

**系统约束**：
- TP 组大小通常 ≤ 单机 GPU 数（如 8），因为跨节点 TP 通信开销过大。
- 列切分和行切分组合保证了 Transformer Block 的 TP 正确性：Attention 和 MLP 子层块内部通信总和为 2 次 AllReduce（正向）加 2 次 AllReduce（反向），详见 11.3。

---

### ③ Implementation Mapping（工程映射）

**Megatron-LM 实现**（`megatron/core/tensor_parallel/layers.py` 中的 `ColumnParallelLinear`）：

```python
class ColumnParallelLinear(nn.Module):
    def __init__(self, input_size, output_size, 
                 gather_output=True, ...):
        # 每个 GPU 只保留 output_size / world_size 的输出维度
        self.weight = nn.Parameter(torch.empty(
            output_size // world_size, input_size))
        ...

    def forward(self, input_):
        # input_ 形状: [s, input_size] (各GPU持有全量或分片，取决于前置层)
        # 本地矩阵乘
        output = linear(input_, self.weight)  # 形状 [s, output_per_partition]
        if self.gather_output:
            # 若需要完整输出，AllGather 拼接
            output = gather_from_tensor_parallel_region(output)
        return output
```

- **`gather_output` 参数**：当 Column Parallel 用于 QKV 投影且输出直接送给 Attention 计算（需要完整 Q/K/V 时），设 `gather_output=True`；当作为 MLP 第一层且下一层是 Row Parallel 时，设 `gather_output=False`，避免多余通信。
- **反向传播中的通信**：对输入 \(X\) 的梯度，Megatron 会在 `ColumnParallelLinear` 的反向函数中自动插入 `reduce_scatter` 或 `all_reduce`（视输出是否 gather 而定），遵循 TP 的通信协议。
- **通信实现**：调用 `megatron.core.tensor_parallel.communication` 中的函数，底层基于 NCCL。

**PyTorch 原生**：无直接 Column Parallel 模块，需手动实现切分与 NCCL 通信，通常参考 Megatron 实现。

**DeepSpeed**：DeepSpeed 的 TP 实现继承自 Megatron，并提供 ZeRO 与 TP 的组合管理。

---

### ④ Complexity Analysis（复杂度分析）

#### 计算量

单 GPU 计算量降为 \( \frac{1}{N} \) 的全量计算：

\[

\text{FLOPs} = 2 \times s \times h \times \frac{h_{out}}{N}

\]

总计仍为全量 FLOPs（无冗余计算）。

#### 显存占用

- **参数显存**：每个 GPU 只持有 \(W_i\)，参数量降为 \(1/N\)。
- **激活值**：输出激活（若不 gather）降为 \(1/N\)；输入激活仍为全量（若输入未分片），但若前置 Row Parallel 产生分片，则输入也是分片大小。在最常见搭配下（Column + Row），中间激活分片，大幅节省显存。

#### 通信开销

- **正向**（若 gather_output=True）：需 AllGather 输出 \( \frac{h_{out}}{N} \times s \) 元素到每个 GPU，通信量 ≈ \(2 \times s \times h_{out} \times \frac{N-1}{N} \) bytes（AllGather 总量，平摊到单卡）。
- **正向**（若 gather_output=False）：无通信。
- **反向**：对 \(X\) 的梯度，若正向 gather_output=True，则反向需 ReduceScatter 或 AllReduce，通信量与正向相似。
- **结论**：Column Parallel 产生的通信量与输入序列长度 \(s\) 和输出维度 \(h_{out}\) 成正比，通常远小于 Row Parallel 的 AllReduce（后者通信量为 \(2 \times s \times h\)）。但在 Attention 中，Column Parallel 的通信与 Row Parallel 的通信共同构成了 TP 内部通信。

**典型通信量（单层）**：
对于 Attention 的 QKV 投影（3h 输出，gather=True），正向需 AllGather Q/K/V 的列块，反向需 AllReduce 输入梯度。配合 Row Parallel 后，总 TP 通信约为 \(4 \times 2 \times s \times h \times 2\) bytes（详见 11.3），必须在 NVLink 带宽下才能高效运行。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：gather_output 的选择**
- **gather=True**：输出完整，后续层无需感知 TP，但引入 AllGather 通信；适合后续是普通层或不方便切分的操作（如 Softmax）。
- **gather=False**：避免通信，但要求下一层也是 TP 风格（Row Parallel），可大幅减少中间激活存储和通信量。Megatron 标准的 Transformer Block 内，Attention 和 MLP 都采用 gather=False 的 Column Parallel 与 Row Parallel 配对，通信仅发生在 Row Parallel 的 AllReduce 和 Column Parallel 反向的 AllReduce。

**Trade-off 2：TP 组大小 N 的选择**
- N 越大，单卡参数和计算量越小，但通信步数增加（AllGather 参与 GPU 数增多），带宽利用率下降。
- 通常 N ≤ 8（单机 GPU 数），跨节点时不推荐 TP，改用 PP 或 DP+ZeRO。

**Trade-off 3：Column Parallel vs 纯复制**
- 若不切分，单个 GPU 无法容纳大线性层权重（如 QKV 总投影大小为 \(h \times 3h\)，h=8192 时达 201M FP16 参数 ~0.4 GB，尚可；但对于 d_ff=32768 的 MLP 第一层，参数量巨大），Column Parallel 使得各 GPU 仅需存储部分权重，显存压力减小。
- 但通信开销要求 NVLink 级别带宽。在 PCIe 环境中，Column Parallel 可能拖慢训练，宜用 PP 替代 TP。

**Trade-off 4：与序列并行（Sequence Parallel）的联合**
- Megatron 的 TP 实现了“TP+SP”：在 Transformer Block 内，将 LayerNorm 和 Dropout 的输入按序列维度切分（Sequence Parallel），以减少激活显存。此时 Column Parallel 的输入已是分片（序列维度），通信模式稍有变化，但 Column Parallel 核心权重切分逻辑不变。这进一步降低了激活存储，但需配合重计算等其他优化。

**Trade-off 5：Column Parallel 在异构设备上的适用性**
- 因为 TP 需要密集通信，仅适合具有高速互联的 GPU 同构组。在 CPU-Only 或低带宽互联场景，Column Parallel 几乎不可用，应使用 PP 或仅使用 ZeRO。

## 展开 11.2：Row Parallel（行并行）

---

### ① Formal Definition（形式化定义）

**Row Parallel（行并行）** 是张量并行（TP）的一种基本切分模式，指将线性层的**权重矩阵按行维度**切分到多个 GPU 上，每个 GPU 持有权重矩阵的一部分行，并接收已被切分（或复制后切分）的输入，计算出部分输出，最后通过 **AllReduce** 将各部分输出求和，得到完整的全量输出。

形式化定义：

设全量线性层为：

\[

Y = X \cdot W, \quad X \in \mathbb{R}^{s \times h_{in}}, \quad W \in \mathbb{R}^{h_{in} \times h}

\]

在 Row Parallel 中，将权重 \(W\) 按行切分为 \(N\) 份（\(N\) 为 TP 组大小）：

\[

W = \begin{bmatrix} W_1 \\ W_2 \\ \vdots \\ W_N \end{bmatrix}, \quad W_i \in \mathbb{R}^{(h_{in}/N) \times h}

\]

输入 \(X\) 也按列（特征维度）对应切分为 \(X_i \in \mathbb{R}^{s \times (h_{in}/N)}\)。每个 GPU \(i\) 持有 \(W_i\) 和对应的 \(X_i\)，计算本地部分输出：

\[

Y_i = X_i \cdot W_i, \quad Y_i \in \mathbb{R}^{s \times h}

\]

最终的完整输出是所有 \(Y_i\) 的逐元素求和：

\[

Y = \sum_{i=0}^{N-1} Y_i

\]

该求和通过 **AllReduce（SUM）** 完成，每个 GPU 得到完整的 \(Y\)。

**关键通信原语**：
- 正向：AllReduce（SUM）对每个 GPU 的部分输出求和，通信量为 \(2 \times s \times h \times \frac{N-1}{N}\) bytes（每个 GPU 发送 + 接收）。
- 反向：对 \(X_i\) 的梯度可直接计算（无需通信，因为 \(W_i\) 本地持有），但对 \(W_i\) 的梯度计算后，无需进一步通信（各 GPU 独立更新自己的权重分片）。注意，反向传播时，误差信号从完整的 \(Y\) 梯度传入，经过本地矩阵乘得到 \(X_i\) 的梯度，这部分是分片式的（如果前置层也是 TP，则无需额外通信）；若前置层需要完整的 \(X\) 梯度，需执行 AllGather，但在标准的 Column+Row 配对中，Row Parallel 的输出已经是全量的 \(Y\)，而其输入 \(X_i\) 的梯度保持分片，传递给 Column Parallel（Column Parallel 反向会处理）。

---

### ② System Design View（系统视角）

在混合并行训练系统中，Row Parallel 通常紧跟在 Column Parallel 之后，两者配对构成 Transformer Block 内完整的 TP 计算模式。

**位置**：
- Attention 子层：在 Q、K、V 的 Column Parallel 投影和 Attention Score 计算之后，Output 投影采用 Row Parallel（权重按行切分），将 Attention 输出的多个头结果聚合。
- MLP 子层：第一层 Column Parallel（h → 4h，输出分片），第二层 Row Parallel（4h → h，输入分片，输出求和还原）。

**输入/输出/依赖**：
- **输入**：Row Parallel 的输入 \(X_i\) 必须已按特征维度切分（通常是前置 Column Parallel 的 gather_output=False 产生的分片输出）。
- **输出**：每个 GPU 通过 AllReduce 得到完整的 \(Y\)，可作为下一个 Block 的输入（全量，或通过 Sequence Parallel 再次切分）。
- **依赖关系**：
  - 需要前置 Column Parallel 的输出分片，构成 TP 内部闭环。
  - 正向 AllReduce 是必须的通信步骤，产生全量输出。
  - 反向传播时，Row Parallel 接收完整输出的梯度，本地计算对 \(W_i\) 和输入分片的梯度，对 \(W_i\) 梯度无需通信，对输入的梯度保持分片传递给前置 Column Parallel。

**系统约束**：
- AllReduce 通信量正比于序列长度 \(s\) 和输出维度 \(h\)，在 TP 组较大时成为瓶颈。
- 必须在低延迟高带宽环境（NVLink/NVSwitch）下执行，否则 AllReduce 延迟会严重拖慢计算。

---

### ③ Implementation Mapping（工程映射）

**Megatron-LM 实现**（`megatron/core/tensor_parallel/layers.py` 中的 `RowParallelLinear`）：

```python
class RowParallelLinear(nn.Module):
    def __init__(self, input_size, output_size, 
                 input_is_parallel=True, ...):
        # 每个 GPU 只保留 input_size // world_size 的输入维度
        self.weight = nn.Parameter(torch.empty(
            output_size, input_size // world_size))
        ...

    def forward(self, input_):
        # input_ 形状: [s, input_per_partition] (分片输入)
        output_parallel = linear(input_, self.weight)  # [s, output_size]
        # AllReduce 求和，得到完整输出
        output = reduce_from_tensor_parallel_region(output_parallel)
        return output
```

- **`input_is_parallel` 参数**：标记输入是否已切分（通常设为 True，配合 Column Parallel 的分片输出）。若设为 False，输入是全量，则需先进行 scatter 或视为非典型用法。
- **`reduce_from_tensor_parallel_region`**：内部调用 `all_reduce`（SUM）将各 GPU 的部分输出相加，并广播到所有 GPU。这是 Row Parallel 的正向核心通信。
- **反向传播通信**：由于正向有 AllReduce，反向时对输入的梯度需通过 ReduceScatter 或直接将全局梯度广播到各个分片（Megatron 内部自动处理，通常通过对 `input_` 的梯度进行 `split_tensor` 操作，保持分片）。
- 具体实现位于 `megatron/core/tensor_parallel/communication.py` 中，调用 NCCL 集合操作。

**PyTorch 原生实现**：无直接封装，需手动实现权重切分和通信，利用 `torch.distributed.nn.functional.all_reduce` 或 `torch.distributed.all_reduce` 完成求和。

**DeepSpeed 张量并行**：与 Megatron 实现高度一致，DeepSpeed 将 Megatron 的 TP 代码作为其引擎一部分，同样使用 `RowParallelLinear` 进行行切分。

### ④ Complexity Analysis（复杂度分析）

#### 计算量

单 GPU 计算量降为 \( \frac{1}{N} \) 的全量计算：

\[

\text{FLOPs} = 2 \times s \times \frac{h_{in}}{N} \times h

\]

总计全 \(N\) 卡计算量等于原全量，无冗余。

#### 显存占用

- **参数显存**：每个 GPU 只持有 \(W_i \in \mathbb{R}^{h \times (h_{in}/N)}\)，参数量降为 \(1/N\)。
- **激活值**：输入激活已分片（来自前置层），为 \(s \times (h_{in}/N)\)；输出激活在 AllReduce 后为全量 \(s \times h\)，因此 Row Parallel 的**输出激活是全量**，无法节省这部分显存（除非后续采用 Sequence Parallel 切分）。这是 Row Parallel 与 Column Parallel 的一个重要区别：Column Parallel 可保持输出分片（若 gather=False），Row Parallel 则强制输出全量以恢复完整的隐藏状态。

#### 通信开销

- **正向**：AllReduce（SUM）通信量 = \(2 \times s \times h \times \frac{N-1}{N}\) bytes（每 GPU 发送 + 接收）。当 N 较大时接近 \(2 s h\)。
- **反向**：对输入梯度的通信量（若需传给前置 Column Parallel）：由于正向是 AllReduce，反向需 ReduceScatter 将完整输出梯度转化为分片输入梯度，通信量同样为 \(2 s h \times \frac{N-1}{N}\) bytes。但 Megatron 实现中，Row Parallel 反向通常不产生额外通信，因为输入梯度直接保持分片传递给 Column Parallel，Column Parallel 反向会处理自己的 AllReduce。确切通信模式取决于整个 TP Block 的设计，但可视为 Row Parallel 正向 AllReduce + Column Parallel 反向 AllReduce 联合构成一对通信。

**通信量与序列长度和隐藏维度的关系**：
通信量正比于 \(s \times h\)。对于大模型的长序列训练，这会成为显著的带宽开销。例如，h=8192, s=2048, N=4，正向 AllReduce 字节量约为 \(2 \times 2048 \times 8192 \times 3/4\) ≈ 25 MB（FP16）。若迭代有多个 Row Parallel 层，通信积累。

#### 与 Column Parallel 的通信对比

| 操作 | 正向通信 | 反向通信（对输入梯度） |
|------|---------|---------------------|
| Column Parallel (gather=True) | AllGather \(s h_{out}\) | AllReduce \(s h_{out}\) |
| Row Parallel | AllReduce \(s h\) | (隐式，由 Column Parallel 承担) |

在实际 3D 并行中，Row Parallel 的 AllReduce 与 Column Parallel 的 AllReduce 构成了 Transformer Block 内部 TP 通信的主要部分，必须通过 NVLink 高速互联提供足够带宽。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：输出必须全量 vs. 激活显存**
- Row Parallel 强制产生全量输出（还原隐藏状态），这导致激活显存中无法节省输出部分，可能成为瓶颈。
- 缓解手段：Megatron 在 TP 基础上引入 Sequence Parallel（SP），将 LayerNorm 和 Dropout 的激活按序列维度切分，Row Parallel 的输出虽为全量，但在进入下一 Block 前即被切分，大幅削减整体激活存储。

**Trade-off 2：与 Column Parallel 的配对约束**
- Row Parallel 的输入必须已经按特征维度分片，即前置必须是 Column Parallel（或等效的分片操作），否则需要在前向额外执行 Scatter 或 AllGather，增加了通信成本和实现复杂性。
- 因此 TP 设计总是成对出现：Column Parallel → Row Parallel → Column Parallel → Row Parallel …，以确保数据流动中通信合理且显存节省最大。

**Trade-off 3：TP 组大小 N 的扩展限制**
- Row Parallel 的 AllReduce 通信量随 N 增大而增大（接近 \(2sh\)），但 Ring AllReduce 有效带宽随 N 下降（约 \(2B/N\)），导致通信时间急剧上升。
- 因此，通常 TP 限制在单机 8 卡内，且 H100 等新一代 GPU 的 NVSwitch 全互联大幅提升了 AllReduce 带宽，使得 TP=8 仍可接受。

**Trade-off 4：Row Parallel 替代方案**
- 如果放弃 TP 而采用 ZeRO-3，模型参数分片同样可减小单卡参数和计算量，但通信模式变为参数 AllGather，且没有 Row/Column Parallel 的精细切分。在选择并行策略时，需权衡 TP 的通信量（机内）与 ZeRO-3 的通信量（可能跨机）。
- 实践中常采用混合：机内 TP（8 卡） + 跨机 DP（ZeRO-2），最大化利用带宽层级。

**Trade-off 5：与 Attention 并行中的特殊考量**
- 在 Attention 并行中，Q、K、V 的投影使用 Column Parallel，其输出可能被切分为多个头组直接进入 Attention 计算。随后的 Output 投影使用 Row Parallel，将多头注意力输出聚合。这种设计最小化了跨 GPU 的数据移动，使得 TP 的通信仅发生在 Column Parallel 输出（若 gather）和 Row Parallel 的 AllReduce，整体通信量可控。

## 展开 11.3：Attention Parallel（注意力并行）

---

### ① Formal Definition（形式化定义）

**Attention Parallel** 是张量并行（TP）在 Multi-Head Self-Attention 模块上的完整切分方案。它将 Attention 中的四个线性投影（Q、K、V、Output）以及 Attention 计算本身，按照头（head）的维度分配到 \(N\) 个 GPU 上，通过 Column Parallel 与 Row Parallel 的组合实现参数、计算和激活值的分布，同时最小化跨 GPU 的通信。

形式化定义（Decoder-only 因果自注意力，Pre-LN 结构）：

设输入隐藏状态 \(X \in \mathbb{R}^{s \times h}\)，有 \(n_h\) 个注意力头，每个头维度 \(d_h = h / n_h\)。TP 组大小为 \(N \leq n_h\)，每个 GPU 被分配 \(n_h / N\) 个连续的头（或按需分配）。

**权重矩阵切分**：
- \(W_Q, W_K, W_V \in \mathbb{R}^{h \times h}\) 按**列**切分（Column Parallel），每 GPU 持有 \(W_{Q,i} \in \mathbb{R}^{h \times (h/N)}\)，对应其负责的头的 Q、K、V 部分。
- \(W_O \in \mathbb{R}^{h \times h}\) 按**行**切分（Row Parallel），每 GPU 持有 \(W_{O,i} \in \mathbb{R}^{(h/N) \times h}\)，对应其负责的头的输出投影部分。

**计算流程（单 GPU i，针对所属头集合 \(\mathcal{H}_i\)）**：

1. **Q/K/V 投影（Column Parallel, gather_output=False）**
   \(Q_i = X \cdot W_{Q,i},\ K_i = X \cdot W_{K,i},\ V_i = X \cdot W_{V,i}\)
   形状均为 \(s \times (h/N)\)。由于各 GPU 持有的列块自然包含其负责头的 Q/K/V，**无需通信即可进入 Attention 计算**。

2. **Attention 计算（仅计算本地头）**
   将 \(Q_i, K_i, V_i\) 重塑为 \(s \times (n_h/N) \times d_h\) 或等价的合并表示，执行标准的 scaled dot-product attention（含因果掩码、softmax、dropout 等）。
   得到本 GPU 负责头的输出：\(\text{Attn}_i \in \mathbb{R}^{s \times (h/N)}\)。

3. **Output 投影（Row Parallel）**
   将 \(\text{Attn}_i\) 作为输入，执行本地行切分的线性变换：
   \(O_i = \text{Attn}_i \cdot W_{O,i} \in \mathbb{R}^{s \times h}\)。
   所有 GPU 的 \(O_i\) 求和得到完整 Attention 输出：
   \(O = \sum_(O = \sum_(O = \sum_{i=0}^{N-1} O_i\)。
   该求和通过 **AllReduce（SUM）** 完成，各 GPU 获得全量输出 \(O\)。

**反向传播关键点**：
- 对于 \(W_O\) 的梯度：各 GPU 独立计算，无需通信。
- 对于 \(W_Q, W_K, W_V\) 的梯度：各 GPU 独立计算，无需通信（每个 GPU 的梯度作用于自己的列块）。
- 对于输入 \(X\) 的梯度：Row Parallel 反向产生 \(\partial L / \partial O_i\)，乘 \(W_{O,i}^T\) 得到对 \(\text{Attn}_i \cdot W_{Q,i}^T, W_{K,i}^T, W_{V,i}^T\) 得到对 \(X\) 的**部分梯度**。所有 GPU 对 \(X\) 的部分梯度需 **AllReduce** 求和（与 Column Parallel 的反向通信一致）。

**通信总览**：
- 正向：一次 AllReduce（Row Parallel 输出求和）。
- 反向：一次 AllReduce（对 \(X\) 的梯度求和）。
- 无 AllGather：因为 Q/K/V 列切分后直接喂给本地注意力计算，输出投影的行切分也直接利用分片注意力输出。

---

### ② System Design View（系统视角）

在 Transformer Block 内部，Attention Parallel 是 **Self-Attention 子层的完整 TP 映射**，前后通常为 MLP 的 TP 块或 LayerNorm。它的位置与数据流如下：

```
输入 X (s × h, 全量)
       │
       ▼
  LayerNorm
       │
       ▼
 ┌─────────────────────────────────────┐
 │      Attention Parallel 子层         │
 │                                     │
 │  Column Parallel QKV 投影 (无通信)    │
 │   → 本地 Attention 计算 (头分组)      │
 │   → Row Parallel Output 投影         │
 │   → AllReduce 求和 ────────────────► 完整 Attention 输出
 └─────────────────────────────────────┘
       │
       ▼
   残差连接 + LayerNorm → MLP Block (TP)
```

**输入**：全量隐藏状态 \(X\)（或通过 Sequence Parallel 按序列维度切分的分片，若同时开启 SP，则 LayerNorm 和注意力输入均可能分片，此处仅讨论纯 TP 情形）。
**输出**：全量 Attention 输出（经 AllReduce 后），形状 \(s \times h\)。
**依赖关系**：
- 依赖 TP 通信域（NCCL 进程组），要求高速互联。
- 与 MLP 的 TP 无缝衔接：Attention 输出全量可直接作为 MLP Column Parallel 的输入（无需额外通信），MLP Row Parallel 的 AllReduce 构成第二个通信点。
- 若结合 Sequence Parallel（13.1），则 LayerNorm 前后引入序列维度的 AllGather/ReduceScatter，但 Attention Parallel 内部逻辑不变。

**设计目标**：
- 参数分片：每个 GPU 存储 \(1/N\) 的 QKV 和 Output 投影权重。
- 激活分片：Q/K/V 和注意力中间结果（Score 矩阵等）都被切分到各 GPU，大幅降低激活显存。
- 最小通信：仅需 1 次正向 AllReduce 和 1 次反向 AllReduce（对输入梯度），无冗余数据搬运。

### ③ Implementation Mapping（工程映射）

**Megatron-LM 实现**（核心位于 `megatron/core/tensor_parallel/layers.py` 和 `megatron/core/transformer/attention.py`）：

- 使用 `ColumnParallelLinear` 实现 QKV 投影（通常合并为单个 \(h \times 3h\) 矩阵，然后按头维度拆分，`gather_output=False`）。
- Attention 计算在分片后的 Q/K/V 上进行，每个 GPU 仅计算自己负责的 \(n_h/N\) 个头。核心代码片段：

```python
# 简化自 Megatron attention 实现
# QKV 投影 (ColumnParallel, output_is_parallel=True)
mixed_x_layer = ColumnParallelLinear(input, 3*h, gather_output=False)(x)
q, k, v = split_tensor_along_last_dim(mixed_x_layer, 3)

# 重塑为多头形式 [s, n_h/N, d_h] 或 [n_h/N, s, d_h]
q = q.view(s, num_heads_per_partition, head_dim)
k = k.view(s, num_heads_per_partition, head_dim)
v = v.view(s, num_heads_per_partition, head_dim)

# 标准注意力计算 (FlashAttention 或 标准)
attn_output = scaled_dot_product_attention(q, k, v, ...)  # [s, h/N]

# 输出投影 (RowParallel)
output = RowParallelLinear(h, h, input_is_parallel=True)(attn_output)
# output 已 AllReduce，形状 [s, h]
```

- **RowParallelLinear** 内部执行 `all_reduce(output_parallel)`。
- 反向传播：Megatron 的 `ColumnParallelLinear` 和 `RowParallelLinear` 的反向函数自动插入所需的 AllReduce（对输入 \(X\) 的梯度）。Column Parallel 反向执行 `reduce_scatter` 或 `all_reduce` 将各 GPU 的部分输入梯度求和，Row Parallel 反向将完整输出梯度转化为分片输入梯度（通常无需额外通信，仅通过修改梯度视图和 Column Parallel 反向的通信完成）。

**DeepSpeed 张量并行**：
- 复用 Megatron 的 TP 实现，同样提供 `Attention` 的 TP 封装，配置中将 `tensor_parallel` 大小设定后，自动切分头。

### ④ Complexity Analysis（复杂度分析）

#### 计算量

- Q/K/V 投影：每 GPU \( 2 \times s \times h \times (h/N) \times 3 \) FLOPs，总计全 N 卡为 \( 6 s h^2 \)。
- Attention Score 计算：每 GPU \( 2 \times s^2 \times (h/N) \) FLOPs，总计 \( 2 s^2 h \)。
- Attention 加权聚合：每 GPU \( 2 \times s^2 \times (h/N) \) FLOPs，总计 \( 2 s^2 h \)。
- Output 投影：每 GPU \( 2 \times s \times (h/N) \times h \) FLOPs，总计 \( 2 s h^2 \)。

总计算量与前序推导的完整 Attention 模块一致，没有冗余计算，仅分布执行。

#### 显存占用

- **参数显存**：Q、K、V、O 四个矩阵各切为 \(1/N\)，每 GPU 参数为 \(4 h^2 / N\)（合并 QKV 则 \(3 h^2 / N + h^2 / N\)）。
- **激活值**（前向，无重计算）：
  - Q/K/V 张量：各 \(s \times (h/N)\)，FP16 下共约 \(3 \times 2 \times s h / N\) bytes。
  - Attention Score 矩阵：\(n_h/N\) 个头，每个头 \(s \times s\)，总元素 \( (n_h/N) s^2 \)，FP16 下 \(2 \times (n_h/N) s^2\) bytes。这是主要激活开销，但相比非 TP 已减少 N 倍。
  - Attention 输出（Softmax 后，投影前）：\(s \times (h/N)\)，2 bytes。
  - Output 投影后：全量 \(s \times h\)，2 bytes（**无压缩**，因 AllReduce 后为全量）。

由此可见，Attention Parallel 将 Score 矩阵等主要中间激活切分 N 倍，极大缓解了长序列导致的 \(s^2\) 显存爆炸。配合 FlashAttention（消除 Score 矩阵存储）效果更佳。

#### 通信开销

- **正向**：Row Parallel 输出 AllReduce，通信量 \(2 \times s \times h \times \frac{N-1}{N}\) bytes（FP16），接近 \(2 s h\) 当 N 大时。
- **反向**：对输入 \(X\) 的梯度 AllReduce，通信量与正向类似，也为 \(2 s h \frac{N-1}{N}\) 左右（或 Column Parallel 反向中已包含）。
- 无 AllGather 需求，这对比 Column Parallel gather=True 时节省了额外的 \(s h\) 通信。

**通信时间估算示例**：h=4096, s=2048, N=4, FP16。每卡 AllReduce 通信量 \(2 \times 2048 \times 4096 \times 3/4\) ≈ 12.6 MB。在 NVLink 300 GB/s 下，理论传输时间 ~0.04 ms。正向 1 次 AllReduce，反向 1 次，合计约 0.08 ms，相比于数毫秒的计算时间占比极小，验证了 TP 在机内高效的原因。

#### 扩展性

- TP 组大小 N 受限于头数 \(n_h\)，最大 N = \(n_h\)（每个 GPU 至少负责一个头）。
- N 增大，通信量增加（接近 \(2 s h\)），且 Ring AllReduce 带宽利用率下降。实际中 N ≤ 8（单机 8 卡），使用 NVSwitch 可维持良好效率。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：头数限制 TP 规模**
- Attention Parallel 天然的并行度受注意力头数限制。若 \(n_h=32\)，最大 TP=32，但通常 TP=8 或 4 更实用，因为需保留足够头数在单 GPU 上保持计算粒度。若头数较少（如 GQA，KV 头少），Attention Parallel 依然适用，因为 Q 头仍可分配，K/V 头通过复制或广播处理（Megatron 支持 GQA TP）。

**Trade-off 2：Column Parallel QKV 是否 gather_output**
- 本方案选择 `gather_output=False`，使 Q/K/V 直接分片进入 Attention，避免 AllGather。这是 Megatron 默认行为，减少了通信和激活存储。如果某些自定义 Attention 需要全局 Q/K/V（如跨头计算），则必须 gather，会显著增加通信量。

**Trade-off 3：与 FlashAttention 的协同**
- FlashAttention 通过分块计算减少 HBM 访问，不影响 TP 逻辑。在 TP 下，FlashAttention 可在每个 GPU 上独立运行其分块，进一步降低显存和提升速度。两者叠加是当前大模型训练的标配。

**Trade-off 4：通信量与计算重叠**
- 正向的 Row Parallel AllReduce 位于 Attention 计算之后，可能与后续的残差加法或 LayerNorm 重叠。Megatron 通过 CUDA Stream 调度，将通信与计算重叠，隐藏部分延迟。但 Attention Parallel 的通信点较为集中，重叠难度大于 DDP 的梯度分桶。

**Trade-off 5：序列并行（SP）整合**
- 当 TP+SP 同时开启，Attention Parallel 的输入 X 已被序列维切分，LayerNorm 输出分片。此时 Q/K/V 投影的输入是分片的，计算仍然本地化，输出 AllReduce 保持不变。好处是 LayerNorm 和残差的激活也被切分，整体激活显存进一步降低。代价是增加了序列维度的 AllGather/ReduceScatter 通信。因此 TP+SP 需要在通信总量和显存节省之间权衡，通常适用于长序列训练。

## 展开 13.1：Sequence Parallel（序列并行）

---

### ① Formal Definition（形式化定义）

**Sequence Parallel (SP)** 是一种针对 Transformer 模型中**激活显存**进行优化的并行策略。其核心思想是将输入序列沿序列维度（sequence length dimension）切分到多个 GPU 上，使得每个 GPU 仅处理序列的一部分（子序列），从而将激活值（尤其是 Attention Score 矩阵之外的 LayerNorm、Dropout、残差等逐元素操作产生的激活）的显存占用降低 \(N\) 倍（\(N\) 为 SP 组大小）。

形式化定义（结合 Megatron-LM 的 TP+SP 方案）：

设输入张量为 \(X \in \mathbb{R}^{s \times h}\)（s 为序列长度，h 为隐藏维度），SP 组由 \(N\) 个 GPU 组成。将 \(X\) 沿第 0 维（序列维）切分为：

\[

X = \begin{bmatrix} X_1 \\ X_2 \\ \vdots \\ X_N \end{bmatrix}, \quad X_i \in \mathbb{R}^{(s/N) \times h}

\]

每个 GPU \(i\) 持有子序列 \(X_i\)。

**SP 区域内的子层**（在 Megatron 的 TP+SP 方案中）包括：
- LayerNorm / RMSNorm
- Dropout
- 残差连接中的加法

这些操作均为**逐元素**或**仅沿特征维**进行的运算，不涉及跨 token 交互，因此可以完全独立地在子序列上执行，**无需通信**。

**SP 边界处的转换**：
- 在进入需要完整序列信息的操作（如 Attention 的 QKV 投影（若未做 TP 切分）或 Attention Score 计算）之前，需要将子序列 **AllGather** 恢复为完整序列。
- 在离开需要完整序列的区域后，立即通过 **ReduceScatter**（或等同操作）将序列重新切分回子序列。

形式化，在一个 Transformer Block 内，Megatron 的 TP+SP 数据流如下：

1. **输入**：子序列 \(X_i\)（或全量序列，根据上一层输出决定）
2. LayerNorm：\( \text{LN}_i = \text{RMSNorm}(X_i) \) — 无需通信
3. **转换为全量**：AllGather → \( \text{LN} \in \mathbb{R}^{s \times h} \)
4. Attention（可采用 TP 切分头部，如 11.3）计算：输入全量，内部 TP 通信，输出全量 \(O \in \mathbb{R}^{s \times h}\)
5. **切回子序列**：ReduceScatter（或 slice）→ \(O_i \in \mathbb{R}^{(s/N) \times h}\) （实际上 Megatron 利用 Column/Row Parallel 的反向通信隐式完成切分，详见工程实现）
6. 残差加 Dropout：\( Y_i = X_i + \text{Dropout}(O_i) \) — 无需通信
7. 第二个 LayerNorm：同样在子序列上执行，然后再次 AllGather 进入 MLP TP 块。
8. MLP TP 块：输入全量，计算后通过 Row Parallel 的 AllReduce 输出全量，再切回子序列。

**关键通信原语**：
- **AllGather**：将子序列恢复成全序列（正向进入 Attention/MLP 前）。
- **ReduceScatter**：将全量序列重新切分为子序列（正向离开 Attention/MLP 后）。在 Megatron 实现中，这一对通信与 TP 内部的 AllReduce 融合，减少了独立的通信操作。

**纯 SP 与 TP+SP 的区别**：
- 若仅使用 SP（不使用 TP），则 Attention 和 MLP 中的线性层需要在完整序列上计算，SP 仅减少 LayerNorm/Dropout/残差的激活存储，收益有限。
- Megatron 将 SP 与 TP 深度绑定：**TP 负责切分参数和 Attention 头，SP 负责切分序列维度的激活**，两者通信合并，实现最大收益。本文后续如非特指，SP 均指 Megatron 式 TP+SP。

---

### ② System Design View（系统视角）

Sequence Parallel 位于 Transformer Block 内部，与 Tensor Parallel 紧密协同，构成“**TP+SP**”混合策略：

```
输入子序列 X_i (s/N × h)
       │
       ▼
 LayerNorm (本地) → X_norm_i
       │
       ▼
 AllGather → X_norm (全量 s × h) ──→ 喂给 Attention TP (Column/Row Parallel)
       │
       ▼
 Attention 输出 (全量) → 经 Row Parallel AllReduce → O (全量)
       │
       ▼
 ReduceScatter → O_i (子序列 s/N × h) (实现在反向或通过 TP 隐式完成)
       │
       ▼
 残差 + Dropout (本地) → Y_i
       │
       ▼
 LayerNorm (本地) → Y_norm_i → AllGather → 喂给 MLP TP
       │
       ▼
 MLP 输出 (全量) → Row Parallel AllReduce → 输出全量
       │
       ▼
 ReduceScatter → 输出子序列 (传递给下一 Block)
```

**在整个训练系统中的位置**：
- 位于并行策略层，通常与 TP 协同部署（在 Megatron 中 `--sequence-parallel` 是启用 TP 时的选项）。
- 主要目标：**解决长序列训练时激活显存爆炸问题**，特别是 Attention Score 矩阵之外的部分。
- 与 Activation Checkpoint（重计算）互补：SP 减少存储，重计算进一步用时间换空间。

**输入/输出/依赖关系**：
- 输入：Transformer Block 的隐藏状态（可以已经是子序列或全量）。
- 输出：相同形状的子序列（若传递到下一 Block 继续 SP）或全量（若结束 SP）。
- 依赖：
  - 需要 TP 组内的高速互联（NVLink），因为 AllGather/ReduceScatter 通信量与 \(s \times h\) 成正比，对带宽敏感。
  - 通常与 TP 组复用相同的通信域（Process Group），即 `tensor_model_parallel_group`。
  - 与 11.1 Column Parallel 和 11.2 Row Parallel 紧密耦合：SP 的 AllGather/ReduceScatter 可以与 Column/Row Parallel 的 AllReduce 合并，减少总通信次数。

**设计约束**：
- SP 的序列切分要求 `s` 能被 `N` 整除。
- 仅在 TP 启用时 SP 才高效，因为 Attention 和 MLP 内的 TP 本身需要全量序列输入，而 SP 的转换通信可与 TP 通信融合。
- 若模型使用了位置编码（如 RoPE），需注意序列切分对相对位置的影响（RoPE 基于绝对位置，子序列切分不影响其正确性，因为每个 token 的位置索引是全局唯一的，且 Attention 在 AllGather 后是全序列，因此位置信息完整）。

### ③ Implementation Mapping（工程映射）

**Megatron-LM 实现**（`megatron/core/tensor_parallel/layers.py` 及相关）：

在 Megatron 中，SP 的实现并非通过显式插入 `all_gather` 和 `reduce_scatter` 到每个 Block，而是通过以下精巧设计：

1. **LayerNorm 与 Dropout 的序列切分**：
   当启用 SP 时，`LayerNorm` 和 `Dropout` 被替换为支持序列并行的版本（`megatron/core/tensor_parallel/layers.py` 中的 `RMSNorm` 和 `Dropout` 实现会自动检测 `sequence_parallel` 设置）。它们直接在子序列上操作，不执行通信。

2. **通信融合**：
   在 Transformer Block 中，Attention 的 `RowParallelLinear` 正向原本有 AllReduce；MLP 的 `RowParallelLinear` 也有 AllReduce。启用 SP 后，这些 AllReduce **被替换为** `ReduceScatter`（或等效操作），从而将输出全量切回子序列，**同时完成 TP 的求和和 SP 的序列切分**。而进入 Attention/MLP 前的 AllGather 则由 `ColumnParallelLinear` 的输出 gather（或显式 AllGather）完成，但 Megatron 巧妙利用了 **Column Parallel 的输出并不 gather**（当 `gather_output=False` 时），而是在 Attention 计算前通过跨 GPU 的通信实现数据全量需求，实际相当于融合了 AllGather。

   具体地，Megatron 的 Block 前向流程简化如下：

   ```python
   # 输入 x: [s/N, h] (子序列)
   x_norm = RMSNorm(x)  # 本地

   # Attention 块：
   # ColumnParallel QKV: 输入需要全量 [s, h] -> 这里会执行 AllGather
   # (在 Megatron 中，ColumnParallel 的 forward 若输入是子序列会自动 all_gather)
   mixed_x_layer = ColumnParallelLinear(3*h, gather_output=False)(x_norm) 
   # 这里内部会先 all_gather 输入，再做矩阵乘
   # ... Attention 计算 ...
   # RowParallel Output 投影：
   # 原本是 AllReduce，但在 SP 下，被替换为 ReduceScatter
   attn_output = RowParallelLinear(h, input_is_parallel=True, 
                                   reduce_scatter=True)(attn)
   # attn_output 形状：[s/N, h] 子序列

   x = x + Dropout(attn_output)  # 本地残差

   # MLP 块类似，第二层 RowParallel 也使用 reduce_scatter
   ```

3. **反向传播**：
   在反向时，SP 对应的通信反向自动推导：`ReduceScatter` 的反向是 `AllGather`，`AllGather` 的反向是 `ReduceScatter`。Megatron 的自动微分机制确保梯度流向正确，无需手动处理。

4. **代码位置**：
   - `megatron/core/tensor_parallel/communication.py` 中的 `_AllReduce` 和 `_ReduceScatter` 等函数。
   - `megatron/core/tensor_parallel/layers.py` 中 `RowParallelLinear` 的 `reduce_scatter` 参数。
   - `megatron/core/transformer/transformer_block.py` 中 Block 的前向逻辑根据 `sequence_parallel` 标志调整通信调用。

**DeepSpeed 序列并行**：
- DeepSpeed 也实现了 Sequence Parallel，通常在 `deepspeed.ops.transformer.inference` 中，但训练中使用 Megatron 的 TP+SP 时，由 Megatron 管理，DeepSpeed 负责任其他部分。

### ④ Complexity Analysis（复杂度分析）

#### 显存节省

无 SP（纯 TP）时，Transformer Block 中激活显存的大头包括：

- LayerNorm 的输入/输出（\(s \times h\)）
- 残差分支中保存的隐藏状态（\(s \times h\)，用于反向）
- Dropout mask（\(s \times h\)）
- Attention 输出投影前的全量激活（\(s \times h\)）

启用 SP 后，上述张量全部变为 \(s/N \times h\) 大小，激活显存减少 N 倍。对于长序列（\(s \gg h\)），这部分节省非常可观。
例如，s=8192, h=4096, FP16，单个 Block 中上述四个张量合计约 \(4 \times 8192 \times 4096 \times 2\) ≈ 256 MB。使用 SP=4 后，降至 64 MB，节省 192 MB/Block。40 层模型总节省约 7.7 GB。

#### 通信开销

在 TP+SP 方案中，每个 Transformer Block 新增的通信量（相比纯 TP）体现在：

- 正向：进入 Attention 前需 AllGather LayerNorm 输出（\(s \times h\) 字节 → 每 GPU 发送量约 \(s h \frac{N-1}{N}\) 字节），离开 Attention 时 ReduceScatter（同量级）。
  但由于 Megatron 的融合设计，这些通信与 TP 内部的 AllReduce 部分合并，总通信次数增加很少。实际上，每个 Block 的通信量从纯 TP 的 2 次 AllReduce（正向）变为 2 次 AllGather + 2 次 ReduceScatter，总数据量类似（但 AllReduce 是双向，AllGather+ReduceScatter 组合亦是双向）。
- 因此，TP+SP 对带宽需求与纯 TP 基本在同一水平，但显存收益巨大。

**通信时间估算**：
h=4096, s=8192, N=4，AllGather \(s h\) 字节 ≈ 32 MB（FP16）。有效带宽 NVLink 300 GB/s → 约 0.1 ms。一个 Block 正向两次 AllGather+ 两次 ReduceScatter 约 0.4 ms。相比于 Attention 计算时间（s=8192 时 Score 计算耗时可观），通信占比仍可接受，且在 H100 更高带宽下更小。

#### 算术强度与计算影响

SP 本身不改变 FLOPs（计算量不变），仅改变激活存储位置。对 Kernel 的算术强度无直接影响，但减少了显存占用，允许更大的微批大小 b 或更长的序列 s，间接提升 GPU 利用率。

#### 扩展性

SP 的序列切分维度受限于序列长度 s。当 s 较小而 N 较大时，子序列过短（如 s=1024, N=8 → 128），可能导致 GPU 计算效率下降（矩阵乘维度缩小）。因此 SP 通常用于长序列场景（s ≥ 2048），且 N ≤ 8 常见。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：显存 vs. 通信**
- SP 以额外的 AllGather/ReduceScatter 通信换取激活显存大幅下降。对于通信带宽充足的机内 NVLink 环境，这是极划算的交易。
- 若通信带宽不足（如跨节点），SP 的通信开销可能超过收益，不建议跨节点使用 SP。

**Trade-off 2：SP 与 Activation Checkpoint 的互补**
- SP 主要减少 LayerNorm/Dropout/残差的激活存储；Activation Checkpoint（重计算）可以减少 Attention 和 MLP 中间结果的存储。两者组合可达最大的显存削减。
- 重计算增加计算量，SP 增加通信量；工程中可根据瓶颈选择：显存紧张时双开，通信紧张时仅用重计算。

**Trade-off 3：SP 对微批大小的间接影响**
- 通过节省激活显存，SP 允许增大微批大小 b，提升 GPU 计算效率，尤其在长序列训练中，可能抵消甚至超过因通信增加带来的时间损耗。

**Trade-off 4：序列长度限制与负载均衡**
- 序列长度必须被 N 整除，否则需要 padding，带来少量计算浪费。
- 若序列长度动态变化（packing），SP 分片可能导致不同 GPU 的 token 数不均衡，需动态重新分配或结合其他策略。

**Trade-off 5：与 FlashAttention 的协作**
- FlashAttention 消除了 Attention Score 矩阵的显存存储，但不影响 LayerNorm/Dropout 的激活。SP 正好弥补这部分，两者合力使长序列训练显存大幅降低。
- 当前大模型（如 Llama 2 70B 长上下文训练）普遍采用 FA + TP + SP + Activation Checkpoint 的组合。

**Trade-off 6：与 Context Parallel 的区别**
- Sequence Parallel（此处）是指沿序列维切分 Transformer Block 中的非注意力组件，注意力仍操作全序列。而 Context Parallel（13.3）将序列维切分扩展到注意力本身（通过环形注意力或类似机制），进一步支持超长上下文（百万 token）。两者可以结合使用，但 Context Parallel 实现更复杂，通信模式也不同。

## 展开 13.2：Expert Parallel（专家并行）

---

### ① Formal Definition（形式化定义）

**Expert Parallel (EP)** 是一种针对 **Mixture of Experts (MoE)** 模型设计的并行策略。在 MoE 层中，原本单一的 FFN 被多个并行的“专家”子网络（通常是小 FFN）取代，每个 token 根据路由决策（Routing）仅激活其中少数专家（Top-k）。Expert Parallel 将这些专家分布到不同的 GPU 上，每个 GPU 持有部分专家，令牌通过 **All-to-All** 通信发送到负责该专家的 GPU 上进行计算，结果再通信返回。

形式化定义：

设 MoE 层有 \(E\) 个专家，每个专家为一个独立的前馈网络（通常为 2 层 FFN）。TP/EP 组由 \(N_{EP}\) 个 GPU 构成（通常每个 GPU 一个专家，即 \(N_{EP} = E\)，或可按比例分配）。输入隐藏状态 \(X \in \mathbb{R}^{s \times h}\)（s 为序列长度，h 为隐藏维度）。

1. **路由（Routing/Gating）**：每个 GPU 独立对本地 token 执行路由计算（门控网络 \(G\) 通常很小，在所有 GPU 上复制），为每个 token 选择 Top-k 个专家（k 通常为 1 或 2），并计算路由权重。
2. **Token 分发（All-to-All dispatch）**：根据路由决策，每个 GPU 将本地 token 按目标专家分组，通过 **All-to-All** 通信将 token 发送到负责该专家的 GPU。此操作改变了 token 与 GPU 的映射关系。
3. **专家计算（Expert computation）**：每个 GPU 接收到来自所有 GPU 的 token，执行其本地专家的前向计算（各自独立的 FFN）。
4. **Token 收集（All-to-All combine）**：专家计算完成后，通过另一个 **All-to-All** 通信，将处理后的 token 按原始序列顺序返回其原始所在的 GPU。
5. **加权合并**：各 GPU 收到返回的 token 后，根据路由权重进行加权求和（若 k>1），并可能添加残差连接，产生 MoE 层的最终输出。

形式化表示（单层 MoE，k=1 简化）：

- 输入 tokens: \(X \in \mathbb{R}^{s \times h}\) （每个 GPU 本地持有 \(X\) 的全量或分片，取决于前置切分）。
- 门控: \(p, idx = \text{Gate}(X)\)，\(idx\) 为专家索引（size s）。
- All-to-All dispatch: 将 \(X\) 按 \(idx\) 重排并发送，目标 GPU 接收到 \(X' \in \mathbb{R}^{s' \times h}\)（s' 为发往该 GPU 的总 token 数，总和为 s）。
- 专家计算: \(Y' = \text{Expert}_{idx}(X')\)。
- All-to-All combine: 将 \(Y'\) 返回原始 GPU，得到 \(Y \in \mathbb{R}^{s \times h}\)。
- 输出: \(O = X + \text{GateWeight} \odot Y\) （残差 + 路由权重）。

**关键属性**：
- 专家参数被切分到不同 GPU，天然实现参数分片（类似模型并行）。
- token 动态调度，负载均衡是关键挑战。
- 通信原语为 All-to-All，与 DP/TP 的 AllReduce/AllGather 不同。

---

### ② System Design View（系统视角）

在混合并行训练系统中，Expert Parallel 通常与数据并行（DP）和张量并行（TP）组合使用，形成“DP+TP+EP”三维并行：

```
全局批次数据 (DP 维度切分)
       │
   ┌───┼───┐
  GPU组0 ... GPU组M  (每个 DP 组持有完整模型副本)
       │
   ┌───┼───┐
  EP 组内 (专家分布)
       │
 ┌─────┼─────┐
 TP 组 (切分单个专家内部)
```

**在整体训练中的位置**：
- MoE 层替换了标准 Transformer Block 中的 FFN 部分，成为 Attention 后的计算核心。
- EP 作用于 MoE 层，负责专家的分布与 token 的路由通信。
- 通常 EP 与 DP 组合：DP 负责非专家层（如 Attention、Embedding）和批量扩展，EP 负责 MoE 层的专家分片。

**输入/输出/依赖关系**：
- **输入**：Attention 输出（全量或经过 TP/SP 处理）进入 MoE 层的门控和 All-to-All。
- **输出**：经专家处理并重组后的 token 序列，形状与输入相同。
- **依赖关系**：
  - 需要底层高效的 All-to-All 通信实现（NCCL 提供 `ncclAllToAll`）。
  - 通常要求 MoE 层所在 GPU 间有高带宽互联（如 NVLink），因为 All-to-All 通信量较大且随序列长度和专家数量增长。
  - 专家间的负载均衡严重影响性能，需要辅助损失或动态路由策略。

**系统目标**：
- 在不大幅增加计算量（稀疏激活）的前提下，扩大模型参数总量（增加专家数 E），从而提升模型容量。
- 通过 EP 将专家分布，使得单 GPU 显存和计算仅与激活专家数 k 成正比，而非总专家数 E。

---

### ③ Implementation Mapping（工程映射）

**Megatron-LM 的 MoE 实现**（`megatron/core/transformer/moe/`）：

1. **专家层定义**：`GroupedMLP` 或 `SequentialMLP` 实现，每个专家是一个小 FFN（通常隐藏维度与标准 FFN 相同或稍小）。
2. **Token 分发与收集**：在 `moe_utils.py` 或 `token_dispatcher.py` 中实现 All-to-All。核心代码：

```python
# 简化流程
def moe_forward(self, hidden_states):
    # 门控路由
    scores, indices = self.gate(hidden_states)  # [s, E]
    
    # Token 分发 (All-to-All dispatch)
    dispatched_input = dispatch(hidden_states, indices, self.num_experts)
    
    # 专家计算 (每个GPU执行其本地专家)
    expert_output = self.experts(dispatched_input)
    
    # Token 收集 (All-to-All combine)
    combined_output = combine(expert_output, indices, self.num_experts)
    
    # 权重混合 & 残差
    output = self.apply_router_weights(combined_output, scores)
    return output
```

3. **并行域构建**：Megatron 新增了 **Expert Parallel Group** (`mpu.EXPERT_PARALLEL_GROUP`)，与 DP、TP、PP 通信域并列。在初始化模型时，根据 `--expert-model-parallel-size` 参数创建 EP 组。
4. **负载均衡**：Megatron 实现了多种辅助损失（`load_balancing_loss`），鼓励 token 均匀分布到各专家。还可使用容量因子（capacity factor）限制每个专家处理的 token 上限，丢弃溢出 token。

**DeepSpeed MoE**：
- DeepSpeed 提供了 `DeepSpeedMoE` 和 `MoE` 模块，基于 Megatron 并增加 PyTorch 层面的集成。
- 支持 **EP + DP 混合**：MoE 层的专家被复制到多个 DP 组（称为“ep_size”），通过 `groups.moe` 管理。
- All-to-All 通信可使用 NCCL 或 PyTorch 的 `dist.all_to_all`。
- 提供了 **PR-MoE** 和 **Z-code MoE** 等更高效的 token 分发策略，以及参数 ZeRO 与 EP 的结合。

**FairScale 等**：
- 也有 MoE 实现，但 Megatron/DeepSpeed 是目前工业界主流。

### ④ Complexity Analysis（复杂度分析）

#### 计算量

- 门控计算：小矩阵乘 \(s \times h \times E\)，通常忽略。
- 专家计算：每个 token 激活 k 个专家，总 FLOPs ≈ \(2 s \times k \times h \times d_{ff}\)（与传统 FFN 的 \(2 s h d_{ff}\) 相比，若 k=1 且单个专家 FFN 大小不变，则 FLOPs 不变；若专家数增多但稀疏激活，计算量仅与激活专家数相关，而非总专家数）。
- 参数量扩充但不增加计算量，这是 MoE 的核心优势。

#### 显存占用

- **参数显存**：所有专家的参数总量为 \(E \times \text{Params}_i \cdot W_{EP}\) 个 GPU，每 GPU 参数约为 \(E/N_{EP} \times \text{Params}_{expert}\)。若不使用 EP，需全量加载，单卡无法容纳大 E。
- **激活显存**：输入 \(X\) 在 All-to-All 前后均存在；All-to-All 通信需缓冲区；每 GPU 处理的 token 数受负载均衡影响，可能波动。
- 由于 token 被重新分配，本地 token 数可能增大（若该 GPU 专家热门），导致激活显存峰值增加。容量因子限制可控制上限。

#### 通信开销

- **All-to-All 通信**：前后两次 All-to-All（dispatch 和 combine）。每个 token 大小为 h 个元素，total tokens = s。
  - 理想均匀情况下，每个 GPU 发送 \(s\) tokens，接收 \(s\) tokens（若 N_EP 个 GPU 均分）。通信量约为 \(2 \times s \times h \times \text{bytes_per_element}\) （每个 GPU 发送 + 接收各一份完整序列大小），但实际总数据量 = \(2 \times s \times h\) （发送加接收），在 \(N_{EP}\) 个 GPU 上的 Ring All-to-All 实现中，每卡数据量约为 \(2 s h \times \frac{N_{EP}-1}{N_{EP}}\)，接近 \(2 s h\) 当 N_EP 较大。
- **与 TP 通信的对比**：All-to-All 通信模式与 AllReduce 不同，其有效带宽受 NCCL All-to-All 算法实现影响，通常低于 AllReduce 的带宽。因此 EP 对网络带宽要求极高，典型用于单机内 NVSwitch 环境，避免跨节点。

**通信时间估算**（h=4096, s=2048, N_EP=8, FP16）：
- 每卡通信量约 \(2 \times 2048 \times 4096 \times 2\) bytes ≈ 33.6 MB。8 GPU All-to-All 在 NVSwitch 下总带宽约 600 GB/s（双向），每个 GPU 单向可享 ~75 GB/s，发送 + 接收时间约 0.45 ms。两次 All-to-All 约 0.9 ms。若 MoE 层很多（如 10+），通信占比需重视。

#### 负载均衡

- 专家流行度不均衡导致部分 GPU 接收 token 数远大于均值，引起计算等待和显存溢出。
- 辅助损失（Load Balancing Loss）增加训练扰动，可能导致模型质量轻微下降，需权衡。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：专家数量 E 与并行度 N_EP**
- 增大 E 提高容量，但需要更多 EP 并行度来分布专家。N_EP 受限于单机 GPU 数，因为 All-to-All 对带宽敏感。若 E > 总 GPU 数，可在 EP 组内让每个 GPU 持有多个专家（`E_per_GPU = E / N_EP`），此时 EP 与 DP/TP 混合使用。

**Trade-off 2：Top-k 与计算效率**
- 增大 k（每个 token 激活更多专家）提升模型表达能力，但计算量线性增加，且 All-to-All 通信量不变（token 复制后仍为 k*s 个 token 发送），但接收 token 数增加，通信量可能上升，需要更大容量因子。

**Trade-off 3：负载均衡 vs. 模型质量**
- 强制完美均衡（较小的 capacity factor）会丢弃一些 token，损害模型效果。工程中通常使用辅助损失引导均衡，并留有一定容量裕量（如 1.25x），允许部分 token 溢出丢弃，再通过重路由或引入 Skip 连接补偿。

**Trade-off 4：EP 与 DP 的组合**
- MoE 模型通常使用 EP+DP：MoE 层使用 EP 切分专家，非 MoE 层（如 Attention、LayerNorm）则通过 DP 复制。因此需要两个不同的通信域，并在不同层间切换通信组。这增加了调度复杂性，但避免了在非专家层进行不必要的 All-to-All 通信，节省带宽。

**Trade-off 5：All-to-All 的实现与性能**
- NCCL 对 All-to-All 的支持不如 AllReduce 成熟，大消息场景下性能优化仍在持续。Megatron/DeepSpeed 有时会采用自定义的 CUDA kernel 进行 token 重排（permutation）配合通信，或使用 `torch.distributed.all_to_all_single`。选择不当可能造成性能瓶颈，需要结合 profiling 调优。

**Trade-off 6：MoE 层与普通 FFN 的混合（Dense + MoE）**
- 许多大模型（如 Mixtral 8x7B）采用每隔一层使用 MoE，而非全部替换，以平衡通信与计算。普通层使用标准 DP/TP，MoE 层加入 EP。这种异构结构要求训练框架能灵活地在不同并行配置间切换。

**Trade-off 7：显存与计算的折衷（容量因子）**
- 容量因子限制了每个专家处理的 token 上限，超过则丢弃。降低容量因子节省显存（减少最坏情况下的缓冲区大小），但丢弃 token 可能降低质量。增大容量因子保证精度，但显存和计算峰值增大。这需要针对具体模型和数据集调优。
