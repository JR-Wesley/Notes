# 集合通信

## 展开 5.1 集合通信原语（Collective Communication）

---

### ① 形式化定义

集合通信是指**一组进程（通信域）按照预定义的通信模式完成数据的重分布或全局计算**。与点对点通信（Send/Recv）不同，集合通信涉及多个发送者和接收者，且操作是原子性的：要么所有参与的进程都执行，要么都不执行。

设通信域中有 `N` 个进程，每个进程 `k` 拥有本地数据 `x_k`。根据原语类型，输出数据分布定义如下。

---

#### 5.1.1 一对多与多对一原语

**Broadcast（广播）**
- 输入：根进程 `r` 上的一个数据块 `D`；其他进程无数据。
- 输出：所有进程得到 `D` 的副本。
- 语义：`∀k: out_k = D`

**Scatter（散射）**
- 输入：根进程 `r` 上有一个长度为 `N` 的数据块列表 `[D_0, D_1, ..., D_{N-1}]`。
- 输出：进程 `k` 收到 `D_k`。
- 语义：`out_k = D_k`（根进程负责分片）

**Gather（收集）**
- 输入：每个进程 `k` 拥有一个数据块 `D_k`。
- 输出：根进程 `r` 收到所有数据块的拼接 `[D_0, ..., D_{N-1}]`；其他进程无输出。
- 语义：根进程上 `out = Concat(D_0, ..., D_{N-1})`。

**All-Gather（全收集）**
- 输入：每个进程 `k` 拥有一个数据块 `D_k`（大小相等）。
- 输出：所有进程都收到所有数据块的拼接 `[D_0, ..., D_{N-1}]`。
- 语义：`∀k: out_k = Concat(D_0, ..., D_{N-1})`。可以理解为 Gather + Broadcast。

---

#### 5.1.2 多对多归约原语

**Reduce（归约）**
- 输入：每个进程 `k` 有一个数据块 `D_k`。
- 输出：仅根进程 `r` 收到归约结果 `Red(D_0, D_1, ..., D_{N-1})`；其他进程无输出。
- 归约操作 `Red` 可以是 sum, max, min 等。最常用的是 sum。
- 语义：`out_r = Σ_k D_k`（以 sum 为例）

**All-Reduce（全归约）**
- 输入：每个进程 `k` 有一个数据块 `D_k`。
- 输出：所有进程都得到全局归约结果 `Red(D_0, ..., D_{N-1})`。
- 语义：`∀k: out_k = Σ_i D_i`。可视为 Reduce 后 Broadcast。

**Reduce-Scatter（归约 - 散射）**
- 输入：每个进程 `k` 有一个数据块列表 `[D_k^0, D_k^1, ..., D_k^{N-1}]`（即每个进程拥有同样大小的 N 个数据块）。
- 输出：进程 `k` 收到第 `k` 个归约结果 `Σ_i D_i^k`。
- 语义：先将所有进程的第 j 个数据块做全局归约，再将第 j 个结果分配给进程 j。可以看作先做 N 路 Reduce，再 Scatter。

---

#### 5.1.3 All-to-All（全交换）

**All-to-All**
- 输入：每个进程 `k` 拥有 N 个数据块 `[D_k^0, D_k^1, ..., D_k^{N-1}]`。
- 输出：进程 `k` 收到来自所有进程的第 `k` 个数据块，即 `[D_0^k, D_1^k, ..., D_{N-1}^k]`。
- 语义：`out_k = Concat(D_0^k, ..., D_{N-1}^k)`。等价于转置一个进程×数据块的矩阵。
- 常见于 MoE 中的 token 路由（把 token 发送给对应专家，并收集专家输出）。

---

### ② 系统视角

**在整个知识树中的位置**：`5.1` 是通信系统层的抽象定义，它描述了“数据需要怎样流动”，而不关心底层硬件。上层并行策略（DP、TP、PP、EP）所需的所有通信模式最终都映射到这些原语。`5.1` 是理解 NCCL（5.3）和通信算法（5.2）的前提。

**在分布式训练中的角色**：
- DP 的梯度同步 → **All-Reduce**
- TP 的列切分后拼接 → **All-Gather**；行切分后求和 → **All-Reduce**
- PP 的激活传递 → **点对点 Send/Recv**（不属于集合通信，但也可用 Broadcast 实现某些模式）
- MoE 的专家路由 → **All-to-All**
- ZeRO-3 的参数收集 → **All-Gather**；梯度分片 → **Reduce-Scatter**

**输入/输出**：
- 输入：各 GPU 上的本地张量（大小和形状由原语约定）。
- 输出：符合原语语义的重分布张量，数据可能跨 GPU 移动。

**与通信库的接口**：
集合通信原语由 NCCL（GPU 间）或 Gloo（CPU 间）等后端实现。训练框架调用 PyTorch 的 `torch.distributed` API，后者将调用转发至 NCCL 的对应函数（如 `ncclAllReduce`）。

**同步语义**：
所有集合通信操作都是**显式或隐式的同步点**：操作返回时，所有进程的通信缓冲区已可用，且全局数据已一致。NCCL 内部可能采用异步执行，但从框架角度看是同步完成的（除非使用 `async_op=True` 启动异步版本）。

---

### ③ 工程映射

**PyTorch 分布式 API 对应**：

```python
import torch.distributed as dist

# 假设 tensor 形状在进程间一致，group 指定通信域
dist.broadcast(tensor, src=0, group=group)             # Broadcast

dist.scatter(tensor, scatter_list, src=0, group=group) # Scatter

dist.gather(tensor, gather_list, dst=0, group=group)   # Gather

dist.all_gather(gather_list, tensor, group=group)      # All-Gather
# gather_list: list of N tensors，每个 tensor 与 tensor 等形状

dist.reduce(tensor, dst=0, op=dist.ReduceOp.SUM, group=group)  # Reduce

dist.all_reduce(tensor, op=dist.ReduceOp.SUM, group=group)     # All-Reduce

dist.reduce_scatter(output, input_list, op=dist.ReduceOp.SUM, group=group) # Reduce-Scatter
# input_list: list of N tensors, output: 单个 tensor

dist.all_to_all(output_tensor_list, input_tensor_list, group=group) # All-to-All
```

**在并行策略中的具体调用**：

- **DDP 的 All-Reduce**：
  PyTorch DDP 内部将参数梯度分桶后，调用 `dist.all_reduce(bucket_tensor, group=dp_pg)`。通信后端为 NCCL。

- **Megatron TP 的 All-Reduce**：
  在 `RowParallelLinear` 中调用 `dist.all_reduce(tensor, group=mpu.get_tensor_model_parallel_group())`。

- **Megatron TP 的 All-Gather**：
  在 `ColumnParallelLinear` 中 `gather_output=True` 时调用 `dist.all_gather(...)`。

- **DeepSpeed ZeRO-3 的 All-Gather**：
  当某个层的前向需要完整参数时，ZeRO-3 调用 `dist.all_gather(param_shard_list, param_shard, group=dp_group)` 重建完整参数。

- **MoE 的 All-to-All**：
  DeepSpeed-MoE 使用 `dist.all_to_all` 将 token 发送到相应的专家 GPU。

**异步版本**：

```python
handle = dist.all_reduce(tensor, async_op=True)
# 执行其他计算...
handle.wait()  # 等待通信完成
```

异步原语是实现通信 - 计算重叠（5.2.4）的关键。

### ④ 复杂度分析

以下给出各原语在典型算法（Ring）下的通信延迟模型（α-β 模型）：`T = α·log(N) + β·(data_per_proc)` 或类似形式。设消息大小为 `M` bytes（每个进程提供的数据量），带宽为 `B`，延迟为 `α`。

| 原语 | 算法（Ring） | 每个进程传输量 | 延迟（简化） |
|------|-------------|---------------|-------------|
| Broadcast | Ring 广播 | M | (N-1)·α + ((N-1)/N)·M/B |
| Scatter | Ring 散射 | M | (N-1)·α + ((N-1)/N)·M/B |
| Gather | Ring 收集 | M | (N-1)·α + ((N-1)/N)·M/B |
| All-Gather | Ring All-Gather | M | (N-1)·α + ((N-1)/N)·M/B |
| Reduce | Ring Reduce | M | (N-1)·α + ((N-1)/N)·M/B |
| All-Reduce | Ring All-Reduce | M | 2(N-1)·α + 2·((N-1)/N)·M/B |
| Reduce-Scatter | Ring Reduce-Scatter | M | (N-1)·α + ((N-1)/N)·M/B |
| All-to-All | 点对点 | M (每个进程) | (N-1)·α + (N-1)·M/B（最坏） |

**要点**：
- All-Reduce 的通信量大约是 Reduce 的两倍（因为每个进程需要同时发送和接收完整的归约结果）。
- All-Gather 每个进程收发总数据量约 `(N-1)/N * (N*M)` = `(N-1)M`，与 All-Reduce 类似但无需归约计算。
- Reduce-Scatter 在 Ring 实现下仅需 `(N-1)/N * M` 的传输量（每个进程最终只保留结果的 1/N），因此比 All-Reduce 少一半的通信量（省去了 All-Gather 部分）。
- All-to-All 在任意两进程之间都要交换数据，总通信量 `O(N·M)`，不具备良好的扩展性，但在 MoE 中 token 数量有限，可接受。

**在 TP 和 DP 中的通信量具体体现**（以 2.2.3 为例）：
- TP 中一次 All-Reduce 消息大小 `2 B S d` bytes，tp=4 时每个进程收发约 `(3/4)*2BSd` bytes。
- DP 中 All-Reduce 消息大小 `2P` bytes（P 为模型参数量），远大于 TP 单次通信量。

---

### ⑤ 设计权衡

**1. All-Reduce vs Reduce-Scatter + All-Gather**

在标准 DP 梯度同步中，All-Reduce 直接给出所有进程相同的平均梯度。ZeRO-3 则用 Reduce-Scatter 将梯度分片（每个进程只得到自己负责的那部分参数的全局梯度和），然后优化器更新分片参数，最后用 All-Gather 收集更新后的参数。其权衡：

- All-Reduce：一步完成，编程简单，每个进程得到完整梯度。
- Reduce-Scatter + All-Gather：总通信量等同 All-Reduce（Reduce-Scatter 省一半，All-Gather 加上），但允许参数和优化器状态分片存储，极大节省显存。

**2. 通信原语与网络拓扑的匹配**

广播/归约类原语可以使用 Ring 或 Tree 算法。Ring 在均匀带宽网络中（如节点内 NVLink）效果好，Tree 在延迟敏感时更优。NCCL 根据拓扑自动选择。All-to-All 需要全连接通信，跨节点时带宽压力大，因此 MoE 实现中常将专家放置限制在节点内，以减少跨节点 All-to-All。

**3. 异步原语与重叠**

所有集合通信均支持异步启动（PyTorch `async_op=True`）。通过将通信操作放入独立的 CUDA Stream，可以与计算主 Stream 上的矩阵乘等并行执行，实现通信 - 计算重叠。但并非所有原语都能同样有效地重叠：All-Reduce 需要完成全部归约才能使用结果，而 All-Gather 可逐步收集部分数据，更易重叠。

**4. 原语粒度与系统效率**

将大量小消息的通信合并为一个大的集合通信（如梯度分桶）能显著提高带宽利用率，因为集合通信的延迟 `α` 是固定的，合并后 `M` 增大，`β·M` 主导，吞吐接近峰值带宽。DDP 的梯度分桶正为此目的。

**5. 在混合并行中的通信隔离**

不同并行策略的集合通信应使用**不同的通信域**（Process Groups），以避免相互阻塞和死锁。例如，TP 的 All-Reduce 在 `tp_group` 内执行，DP 的 All-Reduce 在 `dp_group` 内执行，两者可以在不同 CUDA Stream 上并发执行，从而最大化带宽利用（前提是硬件链路不争用）。Megatron/DeepSpeed 均以此方式组织。

## 展开 5.2 通信算法与复杂度

---

### ① 形式化定义

集合通信算法定义了数据如何在 N 个进程间完成传输与归约的具体步骤，直接决定通信延迟和带宽利用率。核心度量模型为 **α-β 成本模型**：

```
T_comm = α × (steps) + β × (data_per_step)
```

其中 `α` 是每次通信启动的固定延迟，`β` 是每字节传输时间的倒数（即 `1/带宽`）。算法的设计目标是平衡 steps 和 data_per_step，使总时间最小化。以下定义四种关键算法和重叠机制。

---

#### 5.2.1 Ring All-Reduce

**算法描述**：将 N 个进程排列成逻辑环形。将每个进程的数据均分为 N 份（称为块）。算法分两个阶段：

1. **Reduce-Scatter 阶段**：执行 `N-1` 步。第 `k` 步，每个进程将其上一步收到的某个块（或自身初始块）发送给右邻居，并从左邻居接收另一块，然后将接收到的块与本地对应块进行 **归约（求和）**。经过 `N-1` 步后，每个进程持有最终归约结果的第 `i` 个块（即第 i 份全局和）。

2. **All-Gather 阶段**：再执行 `N-1` 步。每个进程将已拥有的最终块依次向右传递，同时从左侧接收缺少的最终块。经过 `N-1` 步后，所有进程拥有完整的全局归约结果。

**形式化成本**（每个进程数据量 `M`，分 N 块）：
- 每步发送/接收 `M/N` 字节。
- 总步数 `2(N-1)`。
- 总通信时间：`T_ring = 2(N-1)·α + 2·(N-1)/N · (M/β)`。
- 当 N 较大时，传输总量约 `2M`。

**关键特性**：带宽利用率高（流水线化数据传输），与进程数无关的恒定传输量 `2M`（每个进程）。是 NCCL 中大消息的主要算法。

---

#### 5.2.2 Tree All-Reduce

**算法描述**：将进程组织为二叉树（或多叉树）。通常分两个阶段：

1. **Reduce 阶段（自底向上）**：叶子节点发送数据给父节点，父节点汇总子节点的数据并进行归约，逐层向上，直到根节点得到全局归约结果。
2. **Broadcast 阶段（自顶向下）**：根节点将全局结果逐层向下广播，所有进程收到完整结果。

**形式化成本**（二叉树，深度 `⌈log₂N⌉`）：
- 每步发送/接收 `M` 字节（未分块）。
- 总步数 `2·log₂N`。
- 总通信时间：`T_tree = 2 log₂N·α + 2 log₂N · M/β`。
- 每个进程（非根）发送和接收总量均为 `M`。根节点发送 `M·log₂N`，接收 `M·log₂N`。

**关键特性**：延迟步数少（对数级），适合小消息，因为 `α` 主导时对数步数更优。但带宽利用率不如 Ring（大数据量时无法并行流水线），且根节点负载重。

---

#### 5.2.3 Recursive Halving-Doubling（递归折半加倍）

**算法描述**：一种基于进程间成对交换的 All-Reduce 算法。进程间进行多轮通信，每轮中将当前拥有的部分归约结果与特定远距离进程交换。

1. **Reduce-Scatter 阶段（递归折半）**：第 `k` 轮（从 0 开始），距离为 `2^k` 的进程对交换数据块。每个进程发送当前持有的部分数据给对端，同时接收对端数据，并在本地归约。经过 `log₂N` 轮后，每个进程拥有最终结果的一个分片（类似 Reduce-Scatter）。
2. **All-Gather 阶段（递归加倍）**：反向过程，进程将对等距离的进程交换归约结果，逐步填充完整结果。经过 `log₂N` 轮，所有进程得到完整结果。

**形式化成本**：
- 共 `2·log₂N` 步。
- 每步消息大小逐渐变化：第 `k` 步发送大小为 `M/2`（在折半阶段，每轮发送当前持有的一半数据），实际总传输量每个进程约 `M`（折半） + `M`（加倍） = `2M`（因为开始每步发半量数据，累加）。
- 延迟：`T_rhd = 2 log₂N·α + 2·(M/β)`（粗略，带宽部分接近 `2M/B`，因总传输量 `2M`）。

**关键特性**：同样具有 `log` 级步数，但总传输量与 Ring 接近（`2M`），且每个进程的通信负载对称。在节点数较多且消息中等大小时，能兼顾延迟和带宽。NCCL 将 Recursive Halving-Doubling 用于中等大小消息和某些拓扑。

---

#### 5.2.4 通信 - 计算重叠（Overlap）

**定义**：将通信操作与计算操作安排在**不同的 CUDA Stream** 上，使它们能在 GPU 上并发执行，从而将通信延迟隐藏在计算时间之内，减少训练步的整体耗时。

**实现基础**：
- GPU 支持多个**执行流**（Stream），不同流上的操作可重叠（前提是不存在数据依赖）。
- 集合通信通常由 NCCL 在内核中执行，占用 SM 或专用拷贝引擎（Copy Engine）。
- 反向传播时，依赖关系是：层的梯度计算依赖于前一层的梯度（由后向前）。但计算层 `l` 的梯度与通信层 `l+1` 的梯度可以并行，因为层 `l+1` 的梯度已经计算完毕，可以立即开始其 All-Reduce，而层 `l` 的梯度正在计算。

**典型实现（DDP 中的重叠）**：
- 梯度分桶（Bucketing）：将多个参数的梯度打包成桶。
- 当某个桶内的所有梯度计算完毕，立即将该桶的 All-Reduce 放入通信流，同时主计算流继续计算下一层的梯度。
- 这样，反向传播的**计算**与**通信**形成流水线，理想情况下通信时间全部被隐藏。

**形式化重叠条件**：
给定一层梯度计算时间 `T_comp` 和该层的 All-Reduce 时间 `T_comm`，如果 `T_comm ≤ T_comp`，则通信可以被该层计算完全隐藏。否则，只能部分隐藏，暴露的通信延迟为 `T_comm - T_comp`。整体的隐藏效果取决于计算与通信的平衡。

---

### ② 系统视角

**在整个知识树中的位置**：`5.2` 是通信系统的算法引擎层。它承接 `5.1` 的集合通信原语语义，并为其提供具体的执行步骤。这些算法直接影响 DP（All-Reduce）、TP（All-Reduce/All-Gather）、ZeRO（Reduce-Scatter + All-Gather）的通信性能。NCCL（`5.3`）正是这些算法的硬件感知实现。

**数据流与系统位置**：
- Ring/Tree/RHD 算法部署在 **NCCL 核心**，框架（PyTorch）通过 `ProcessGroup` 间接调用。
- 通信 - 计算重叠由**框架的训练循环**（DDP/DeepSpeed/Megatron）调度，通过将通信操作放入独立 CUDA Stream 实现。

**依赖关系**：
- 依赖 `5.1` 原语定义。
- 被 `5.3.3`（NCCL 的 Channel 与 Ring 构建）和 `6.1`（DDP/FSDP 实现）使用。

---

### ③ 工程映射

**NCCL 中的算法选择**：
NCCL 根据消息大小和 GPU 拓扑自动选择最优算法：
- **小消息（< 256KB）**：Tree 或 Recursive Halving-Doubling（减少延迟）。
- **大消息**：Ring（充分发挥带宽）。
- 对于 All-Reduce，NCCL 支持 `ncclAllReduce`，内部调度 Ring、Tree 或 CollNet 等。

**PyTorch DDP 的重叠实现**：
- DDP 维护一个 `bucket_cap_mb`（默认 25MB）。
- 反向时，梯度填充到桶，桶满或反向结束，调用 `dist.all_reduce(bucket_tensor, async_op=True)`。
- 异步 All-Reduce 在与计算不同的 Stream 上执行，计算无需等待。

**Megatron / DeepSpeed 的重叠**：
- Megatron 的 TP All-Reduce 通常无法重叠（在关键路径上），但 DP 的 All-Reduce 可与反向计算重叠。
- DeepSpeed ZeRO 阶段 1/2 与 DDP 类似，对梯度桶 All-Reduce 重叠。ZeRO-3 的 All-Gather（参数）可通过预取与计算重叠（DeepSpeed 实现了参数预取调度器）。

---

### ④ 复杂度分析

**算法对比**（消息大小 `M`，进程数 `N`，带宽 `B`，延迟 `α`）：

| 算法 | 步骤数 | 每进程总传输量 | 延迟开销 | 带宽开销 | 适用场景 |
|------|--------|---------------|---------|---------|----------|
| Ring All-Reduce | 2(N-1) | 2·(N-1)/N·M ≈ 2M | 高（N 大时） | 近峰值带宽 | 大消息，N 较大 |
| Tree All-Reduce | 2 log₂N | M (非根) | 低 | 低（串行） | 小消息，延迟敏感 |
| Recursive Halving-Doubling | 2 log₂N | ~2M | 低 | 高 | 中等消息，N 较大 |
| 重叠（理想） | — | — | 可能为 0 | 隐藏 | 反向传播 |

**在训练中的表现**：
- 对于 DP 的梯度同步（`M = 2P`），P 从 1B 到 100B，`M` 从 2GB 到 200GB。Ring All-Reduce 带宽接近 NVLink 600 GB/s，通信时间 ~ (200GB/600GB/s) = 0.33s 对于 100B 模型。若重叠充分，大部分可隐藏。
- 对于 TP 的小消息 All-Reduce（`M = 2 B S d`），典型 64MB，Ring 延迟约几微秒，Tree 延迟类似，选择影响不大。

**重叠效果量化**：
若反向计算时间 `T_comp`，通信时间 `T_comm`，无重叠时步长时间 `T_comp + T_comm`。完美重叠时步长 `max(T_comp, T_comm)`。因此加速比上限 `(T_comp + T_comm) / max(T_comp, T_comm)`。当 `T_comm << T_comp` 时收益小，反之收益大。实际中受限于 bucket 延迟（第一桶之前无通信）和依赖链。

---

### ⑤ 设计权衡

**1. Ring vs Tree**
- Ring：大规模数据（梯度同步）下吞吐最高，但步数多。
- Tree：小消息（如 TP 中的频繁小 All-Reduce）延迟低，但带宽利用率差。
NCCL 在内部会根据大小动态切换，用户通常无需干预。

**2. Recursive Halving-Doubling 的适用性**
在节点数较多且网络拓扑不规则时，RHD 的成对交换模式更易映射到物理拓扑（如 Fat-Tree），减少拥塞。NCCL 在特定环境使用。

**3. 重叠的代价**
重叠引入额外显存（通信缓冲区）和流管理开销。桶大小设置需权衡：
- 大桶：减少通信次数，但延迟了第一桶的通信，可能失去与计算重叠的机会。
- 小桶：更早开始通信，但大量小消息降低带宽利用率。

**4. 通信算法与并行策略的协同**
- DP 梯度同步：大消息，必须用 Ring 或 RHD 最大化带宽，重叠极其关键。
- TP All-Reduce：小消息，频繁，延迟敏感，更倾向 Tree 或小 Ring。
- ZeRO-3 All-Gather：大消息（参数大小 M=P_chunk），类似 DP 同步，用 Ring，可与计算预取重叠。

**5. 拓扑感知算法**
NCCL 的 Ring 不是任意环，而是根据 GPU 互联（NVLink 网状、PCIe 树）构建最优环，以跳数最少和带宽最大为目标。跨节点时，NCCL 使用多个 Ring 或 Tree 组合（如双层 All-Reduce）。这些将在 `5.3` 中深入。

## 展开 5.3 NCCL 实现层

---

### ① 形式化定义

**NCCL（NVIDIA Collective Communications Library）** 是 NVIDIA 为 GPU 间集合通信提供的高度优化库。它接收上层的通信请求（如 `all_reduce`），并根据物理 GPU 拓扑和消息大小，自动选择并执行最优的通信算法。其核心职责是：**将逻辑上的集合通信原语，映射为硬件上最高效的数据搬运路径与 kernel 执行序列**。

NCCL 的工作可以解构为以下四个工程单元：

- **5.3.1 拓扑检测**：扫描 PCIe、NVLink、InfiniBand 等链路，构建包含 GPU、网卡、PCI 交换机、NVSwitch 的物理连接图。
- **5.3.2 通信域**：将逻辑进程组（如 TP 组）映射到物理拓扑上，供算法选择使用。
- **5.3.3 Channel 与 Ring 构建**：在 GPU 间分配多个逻辑通道（Channel），每个通道在参与通信的 GPU 间通过拓扑路径构建一个逻辑环（Ring），用于流水线化数据传输。
- **5.3.4 PyTorch 对接**：PyTorch 通过 `ProcessGroupNCCL` 将 `torch.distributed` API 调用翻译为 NCCL 的 C 接口，并管理 CUDA Stream 的调度与同步。

**传输层硬件抽象**：
NCCL 将不同互连抽象为统一传输层，其带宽和延迟特征差异显著：

| 传输层 | 带宽（单向，A100） | 延迟 | 用途 |
|--------|-------------------|------|------|
| **NVLink** | 600 GB/s（单对单） | ~1 μs | 节点内 GPU 间通信 |
| **PCIe 4.0 x16** | 32 GB/s | ~5 μs | GPU 与网卡、CPU 通信 |
| **InfiniBand (HDR)** | 200 Gb/s ≈ 25 GB/s | ~1-2 μs | 跨节点通信 |
| **RoCE (RDMA over Converged Ethernet)** | 100-400 Gb/s | ~2-5 μs | 跨节点通信（以太网） |

---

### ② 系统视角

**在整个知识树中的位置**：`5.3` 是通信系统的**硬件感知实现层**，位于 `5.2`（通信算法）与 `6.x`（工程实现映射）之间。它是从抽象原语到具体硬件的桥梁。

**在分布式训练系统中的层次位置**：

```
训练框架 (PyTorch / DeepSpeed / Megatron)
  │
  ├─ torch.distributed API
  │     │
  │     └─ ProcessGroupNCCL  ← 本节核心
  │           │
  │           └─ libnccl.so
  │                 │
  │                 ├─ 拓扑检测 (PCIe / NVLink / InfiniBand)
  │                 ├─ Channel 管理 (多 Ring 流水线)
  │                 └─ CUDA Kernel 调用 (拷贝 / 归约)
  │
  └─ CUDA Driver / GPU 硬件
```

**输入/输出**：
- **输入**：上层的集合通信调用（`all_reduce(tensor, group)`），以及静态的进程组信息。
- **输出**：在指定 CUDA Stream 上完成数据搬运，并在操作完成后设置事件信号。

**在并行策略中的角色**：
- DP 的梯度同步、TP 的 All-Reduce/All-Gather、ZeRO-3 的参数收集，其最终的执行都由 NCCL 完成。
- NCCL 的拓扑感知能力决定了**TP 组是否应限制在节点内**（利用 NVLink）以及**跨节点 DP 梯度同步**如何利用 InfiniBand。

---

### ③ 工程映射

#### 5.3.1 NCCL 拓扑检测

NCCL 在初始化时调用 `ncclCommInitRank`，内部扫描系统：

- 通过 CUDA API 枚举所有 GPU 及其 NVLink/NVSwitch 连接。
- 通过 PCIe 拓扑发现 GPU 与网卡（NIC）的绑定关系（GPU Direct RDMA 需要 GPU 和网卡在同一 PCIe 域）。
- 构建一个带权图，权重反映带宽与跳数。

这个拓扑图决定了后续 Channel 和 Ring 的构建方式。用户可通过环境变量 `NCCL_DEBUG=INFO` 查看检测结果。

#### 5.3.2 NCCL 通信域

NCCL 中的通信域由 `ncclComm_t` 对象表示。每个通信域对应一组参与通信的 GPU（逻辑进程组）。多个通信域可以共存（如 TP 组和 DP 组），各自独立调度。

**关键环境变量**：
- `NCCL_SOCKET_IFNAME`：指定用于跨节点通信的网络接口。
- `NCCL_IB_DISABLE`：设为 1 禁用 InfiniBand，强制走 IP 网络。
- `NCCL_NET_GDR_LEVEL`：控制 GPUDirect RDMA（GPU 直接通过网卡与远程 GPU 传输数据，不经过 CPU 内存）。

#### 5.3.3 NCCL 的 Channel 与 Ring 构建

对于一次集合通信，NCCL 将数据切分为多个小块，通过多个 **Channel** 并发传输。每个 Channel 使用一个独立的 CUDA Stream 和一个逻辑 **Ring**（环）：

- **Ring** 由通信域内的 GPU 组成，顺序由拓扑图决定（最短路径或最大带宽优先）。
- 多个 Channel 的 Ring 顺序可以不同（旋转），以平衡链路利用。
- 每个 Channel 负责传输一部分数据（类似流水线分段），从而提高总体吞吐。

**Ring 构建策略**：
- 节点内（NVLink）：Ring 沿 NVSwitch 或网状连接构建，通常所有 GPU 间带宽对称。
- 跨节点（InfiniBand）：NCCL 在节点间创建多个 Ring，每个 Ring 只包含各节点的一个 GPU，通过网卡通信；节点内 Ring 独立并行。这称为**分层 All-Reduce**。

#### 5.3.4 NCCL 与 PyTorch 的对接

PyTorch 在 `torch.distributed` 中使用 `ProcessGroupNCCL` 类封装 NCCL。初始化时：

```python
import torch.distributed as dist

dist.init_process_group(backend='nccl', init_method='env://')
```

这会在每个进程创建一个全局的 `ncclComm_t`。

后续操作如：

```python
dist.all_reduce(tensor, group=tp_group)
```

内部调用：

1. 查找 `group` 对应的 `ncclComm_t`。
2. 根据 `tensor` 大小选择算法（隐含在 NCCL 内部）。
3. 将操作提交到当前 CUDA Stream（或异步指定 Stream）。

**关键细节**：
- PyTorch 自动为每个通信域维护独立的 CUDA Stream，用于异步启动 NCCL 操作。
- NCCL 操作需要显式同步：`torch.cuda.synchronize()` 或等待返回的 `WorkNCCL` 对象。

---

### ④ 复杂度分析

**拓扑检测开销**：仅在初始化时执行一次，扫描所有 GPU 和网卡，耗时通常 < 1 秒，可忽略。

**Channel 数量**：
- NCCL 默认使用 **8 个 Channel**（可配置 `NCCL_MIN_NCHANNELS` / `NCCL_MAX_NCHANNELS`）。
- 更多 Channel 增加流水线深度，可能提高带宽利用率，但占用更多 GPU 资源（SM、内存）。

**Ring All-Reduce 传输量**（每 Channel）：
- 总数据量 `M` 被切分为 `num_channels` 份，每份 `M/C`。
- 每个 Channel 的传输量：`2(N-1)/N × M/C` bytes（每个 GPU 收发各约 `2M/C`）。
- 总传输量不变（`2(N-1)/N × M`），但多个 Channel 并发使带宽利用率接近峰值。

**跨节点通信复杂度**：
- 跨节点时，NCCL 使用节点内 Ring + 跨节点 Ring 的双层结构。跨节点 Ring 的带宽受限于 InfiniBand（如 200 Gb/s），成为瓶颈。
- 对于 DP 梯度同步（`M = 2P`），跨节点带宽远低于节点内 NVLink（25 GB/s vs 600 GB/s），通信时间可能增长 20 倍以上，必须依赖通信 - 计算重叠（5.2.4）来隐藏。

**延迟分析**：
NCCL 操作的延迟包括：
- Kernel 启动延迟（几微秒）。
- 数据传输延迟（带宽倒数 × 数据量）。
- 同步延迟（等待所有进程到达集合操作点）。
NCCL 针对小消息优化了延迟（使用 Tree 算法），大消息则优先吞吐。

---

### ⑤ 设计权衡

**1. 自动化 vs 可配置性**
NCCL 高度自动化，根据拓扑和消息大小动态选择算法。但用户可通过环境变量调整（如 `NCCL_ALGO=Ring` 强制 Ring）。对大多数用户，默认配置最优；极端场景下（如自定义拓扑）可能需要微调。

**2. 节点内 vs 跨节点通信**
NCCL 自动检测 GPU 是否在同一节点，并使用不同传输层。训练框架需要**正确放置进程**，确保 TP 组在节点内（利用 NVLink），DP 组可跨节点。若 TP 跨节点，NCCL 会走 InfiniBand，性能将严重下降。这是进程映射（`2.0`）与 NCCL 拓扑检测的配合关键。

**3. GPUDirect RDMA 的影响**
启用 GPUDirect RDMA（GDR）允许 GPU 直接通过网卡与远程 GPU 通信，绕过 CPU 内存拷贝，大幅降低跨节点通信延迟。但要求 GPU 和网卡在同一 PCIe 域（拓扑上直接相连）。NCCL 自动检测是否支持 GDR。

**4. NCCL 的 Channel 数量与资源占用**
增加 Channel 数可提升带宽利用率，但每个 Channel 占用 SM 和 CUDA 核心（用于执行归约 kernel）。在计算密集的训练中，过多的通信 Channel 可能与计算 kernel 争抢资源，反而降低吞吐。默认 8 个 Channel 是经验平衡点。

**5. PyTorch ProcessGroup 的封装**
ProcessGroup 将 NCCL 通信域与 PyTorch 的 Stream 机制对接，隐藏了 NCCL 的复杂性。但它也引入了额外同步点（如 `dist.barrier()`），可能导致不必要的 GPU 空闲。高效训练需要精确控制同步时机。

**6. NCCL 的版本与兼容性**
NCCL 版本与 CUDA 驱动、PyTorch 版本强绑定。新版本 NCCL 通常带来拓扑检测和算法优化（如对 NVSwitch 的改进），升级 NCCL 是提升通信性能的有效手段之一。

## 展开 7.1 通信成本模型（α-β 模型）

---

### ① 形式化定义

通信成本模型（α-β 模型）是分析分布式系统中消息传递开销的基本数学模型。它将一次通信操作的总时间建模为**固定延迟**与**传输数据量成正比的可变成本**之和。

设一次通信传输 `M` 字节的数据，则耗费时间：

```
T_comm(M) = α + β · M
```

其中：

- **α（alpha）**：启动延迟（latency），单位秒。涵盖消息初始化、内核启动、握手、同步等与消息大小无关的固定开销。对于 GPU 通信（如 NCCL kernel），α 通常在 **1~10 微秒**量级。
- **β（beta）**：传输时间的倒数，即 `1 / 有效带宽`，单位秒/字节。有效带宽 `B` 取决于硬件链路和协议效率。β·M 是实际数据传输部分。

对于集合通信（如 All-Reduce），整个过程由多步组成，总时间可表示为：

```
T_total = s · α + total_bytes_transferred · β
```

其中 `s` 是逻辑通信步数，`total_bytes_transferred` 是每个进程总共发送和接收的字节数。例如，**Ring All-Reduce** 在 `N` 个进程中：

```
s = 2(N - 1)
total_bytes = 2 · ((N - 1) / N) · M
```

其中 `M` 是每个进程的初始数据量。当 `N` 较大时，每个进程传输量约 `2M`。

**模型的使用方式**：给定硬件参数（α，β）和通信模式（步数、传输量），可以预测通信时间，进而分析并行策略的扩展性和瓶颈。

---

### ② 系统视角

**在整个知识树中的位置**：`7.1` 是性能分析层的基石，位于通信算法（5.2）和并行策略（1~4）之上。它将抽象的“通信开销”量化为可计算的数学指标，为混合并行设计（4.1）、扩展效率分析（7.3）和瓶颈诊断（7.4）提供统一的语言。

**在训练系统中的角色**：
- **预测**：给定模型大小、并行配置，估算通信时间占比。
- **对比**：量化不同并行策略（DP vs TP vs PP）的通信开销。
- **调优**：指导梯度分桶大小、通信域划分、重叠策略的选择。

**输入/输出**：
- **输入**：通信消息大小 `M`（如梯度大小 `2P`，或 TP 激活 `2 B S d`），参与进程数 `N`，硬件参数 `α` 和 `β`。
- **输出**：预计通信时间 `T_comm`，可直接与计算时间 `T_comp` 比较，得到通信占比和理论加速比。

**与其他节点的依赖**：
- 依赖 `5.2` 的算法步数和传输量公式。
- 被 `7.2`（计算 - 通信比）和 `7.3`（扩展效率）直接引用。
- 使用 `1.0` 中的硬件带宽参数确定 β。

### ③ 工程映射

**在 PyTorch / NCCL 中的测量**：
虽然 α 和 β 通常由硬件决定，但可以通过 micro-benchmark 测量有效值。

```python
import torch.distributed as dist
import torch

def benchmark_allreduce(size_mb, group, warmup=5, repeat=10):
    tensor = torch.randn(size_mb * 1024 * 1024 // 4, dtype=torch.float32, device='cuda')
    # warmup
    for _ in range(warmup):
        dist.all_reduce(tensor, group=group)
    torch.cuda.synchronize()
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(repeat):
        dist.all_reduce(tensor, group=group)
    end.record()
    torch.cuda.synchronize()
    return start.elapsed_time(end) / repeat  # ms
```

**确定 α 和 β**：对不同大小的消息进行测试，线性回归 `T(M) = α + β·M`。实际 NCCL 内部会根据消息大小切换算法，导致分段线性（α 和 β 不同），因此需要针对特定范围建模。

**Megatron / DeepSpeed 中的使用**：
- 这些框架通常不显式计算 α-β，而是通过 heuristics 或通信时间测量来决定梯度分桶大小、TP/DP 划分。
- 在 Megatron 的 `tensor_parallel` 初始化中，会根据 `tp_size` 和网络拓扑估算通信量，但实际优化仍依赖 NCCL 自动选择。

**工程参数示例（A100 集群）**：

| 链路 | 有效带宽 B | β (s/GB) | α (μs) |
|------|-----------|----------|--------|
| NVLink (节点内) | ~550 GB/s | ~0.0018 | ~2 |
| InfiniBand HDR (跨节点) | ~22 GB/s | ~0.045 | ~5 |

*注：β = 1/B，实际有效带宽低于物理峰值。*

### ④ 复杂度分析

**通信成本缩放规律**：
- 对于 DP 梯度同步（All-Reduce，每个进程数据量 `M`）：

  ```
  T_dp(N) ≈ 2(N-1)·α + 2·((N-1)/N) · (M/β⁻¹)
  ```

  随着 `N` 增大，延迟项线性增长，带宽项趋近 `2M/β⁻¹`（接近常数，但总传输量略增）。因此，DP 通信时间主要由 `M` 决定，N 的影响在延迟项。

- 对于 TP All-Reduce（每层，`M = 2·B·S·d` bytes），通常 `N` 较小（≤8），延迟项可忽略，`T_tp ≈ 2·((N-1)/N) · M · β`。每步多次累积。
- 对于 PP P2P（Send/Recv），`T_pp = α + β·M`（一次传输），`M = B·S·d`，开销远小于 DP/TP。

**实际训练中的量级**：
- 模型 13B，FP16 梯度 26 GB。N=8 DP，节点内 NVLink：
  `T_dp ≈ 2*7*2μs + 2*(7/8)*26GB*0.0018 s/GB ≈ 28μs + 0.082 s = ~82 ms`
- 同一模型，TP=4，S=4096, d=5120：`M = 2*1*4096*5120*2 bytes = 80 MB`，
  `T_tp ≈ 2*(3/4)*80MB*0.0018 s/GB ≈ 0.00022 s = 0.22 ms`，每层 0.22 ms，32 层累积 ~7 ms。

可见 DP 通信是大模型训练的主要通信开销，而 TP 通信虽然频率高，但单次极小，总开销可控。

### ⑤ 设计权衡

**1. 使用有效带宽而非物理峰值**
物理带宽是理论最大值，有效带宽受协议开销、流控、信道利用率影响。例如，NVLink 600 GB/s 物理带宽，实际 NCCL All-Reduce 有效带宽约 550 GB/s。β 的取值必须基于实测或参考值，否则会低估通信时间。

**2. α-β 模型的局限性**
- 模型假设通信时间与消息大小呈完美线性，但实际因算法切换（Ring vs Tree）和网络拥塞，β 并非恒定。
- 未考虑通信与计算的重叠（7.2 会引入重叠因子）。
- 未量化同步等待（木桶效应）导致的空闲时间，需要结合 `7.3` 扩展效率分析。

**3. 通信粒度与延迟权衡**
将大量小消息合并为一个大消息（如梯度分桶）可以减少 `α` 项的总影响（减少通信次数），但增加了计算等待通信的延迟，可能影响重叠效果。α-β 模型可以帮助找到最优桶大小：平衡次数和单次数据量。

**4. 分层通信的建模**
跨节点通信（如 InfiniBand）β 远大于节点内（NVLink）。NCCL 的分层 All-Reduce 可建模为节点内阶段（低 β）和跨节点阶段（高 β）的组合。这解释了为什么跨节点 DP 比节点内 DP 昂贵得多，也说明了混合并行（节点内 TP + 跨节点 DP）的优势。

**5. 指导并行策略选择**
通过比较 `T_comp` 与 `T_comm`：
- 若 `T_comm >> T_comp`：通信瓶颈，需减少通信量（如增大 TP 减少 DP 梯度大小）或优化通信（如 InfiniBand 升级）。
- 若 `T_comm << T_comp`：通信可被隐藏，可放心扩展 DP。
α-β 模型提供了量化的决策依据，避免盲目调整。

## 展开 7.2 计算 - 通信比分析

---

### ① 形式化定义

**计算 - 通信比**（Compute-Communication Ratio）定义为在一个训练步（或部分计算单元）中，**有效计算时间与通信时间的比值**。它衡量并行策略中每单位通信开销能“买到”多少计算工作，是评估扩展效率的核心指标。

设对于特定的并行策略，一个训练步内：

- `T_comp`：纯计算时间（假设无限带宽下的总计算延迟）。
- `T_comm`：由通信引入的额外时间（包括数据传输与同步）。

则计算 - 通信比定义为：

```
R = T_comp / T_comm
```

**含义**：
- `R > 1`：计算时间大于通信时间，计算主导，通信开销占比较低，扩展性较好。
- `R < 1`：通信时间大于计算时间，通信瓶颈，增加 GPU 可能不带来加速。
- `R ≈ 1`：平衡点。

由于不同并行策略的通信模式不同，它们的 `R` 有不同表达形式：

**数据并行（DP）**：一次梯度同步 All-Reduce，通信发生在整个模型梯度上。

```
T_comp_dp ≈ B_global · FLOPs_per_sample / (N · GPU_peak · utilization)
T_comm_dp ≈ T_allreduce(2P) ≈ 2(N-1)/N · (2P) · β + 2(N-1)·α
R_dp = T_comp_dp / T_comm_dp
```

注意，每张 GPU 的计算量随 `N` 增大而减小（全局 batch 固定），但通信量近似常数（`2P` 字节），因此 **DP 的 R 随 N 增大而减小**。

**张量并行（TP）**：通信发生在每层的输出 All-Reduce 或 All-Gather（消息大小 `M_tp = 2·B·S·d` 字节）。

```
T_comp_tp_per_layer ≈ (单层计算量 / N) / GPU_peak
T_comm_tp_per_layer ≈ T_allreduce(2BSd) (All-Reduce 或等效)
R_tp = T_comp_per_layer / T_comm_per_layer
```

由于通信量与激活大小 `B·S·d` 成正比，而计算量近似与 `B·S·d²` 成正比（矩阵乘主导），所以 **TP 的 R 与隐藏维度 d 成正比，d 越大通信占比越低**。

**流水线并行（PP）**：通信为 P2P Send/Recv 激活（大小 `M_pp = B·S·d` 字节），频率为每个 micro-batch 一次。

```
T_comp_pp_per_stage ≈ (L/pp) · 单层计算量 / GPU_peak
T_comm_pp_per_stage ≈ (m-1) · (α + β·BSd)  （m 为 micro-batch 数，P2P 重叠好可隐藏）
R_pp 通常很高，因为激活传输量远小于计算量（尤其是大模型）。
```

### ② 系统视角

**在整个知识树中的位置**：`7.2` 是性能分析层中对并行效率的直接量化工具，居于 `7.1` 通信成本模型之上，为 `7.3` 扩展效率分析提供了核心变量。它连接了通信系统（5.x）与并行策略（1~4），回答了“为什么某种并行方式在这个规模下合理/不合理”。

**在训练系统设计中的角色**：
- **策略选择**：若 `R_dp` 过低（如 <1.5），说明 DP 通信成为瓶颈，可能需要引入 TP 或 ZeRO 来减少梯度通信量。
- **混合并行配比**：通过比较 `R_dp`, `R_tp`, `R_pp`，决定在给定硬件拓扑上如何分配 DP、TP、PP 的规模。
- **重叠潜力评估**：高 `R` 意味着计算相对通信富余，通信更容易被隐藏。

**输入/输出**：
- **输入**：模型配置（d, L, P, S），并行度（N_dp, N_tp, N_pp），硬件参数（GPU 峰值算力，α, β，有效带宽）。
- **输出**：每种策略的 `R` 值，总体的计算与通信时间占比，以及潜在瓶颈预警。

**依赖关系**：
- 依赖 `0.5` 计算 FLOPs，`1.1` 显存约束，`5.2` 通信算法复杂度，`7.1` α-β 模型。
- 为 `7.3` 强/弱扩展分析提供通信边际成本。

### ③ 工程映射

**在 PyTorch / Megatron / DeepSpeed 中的预估方法**：

1. **计算时间 `T_comp`**：通过 FLOPs 估算或 profiler 实测。
   - 理论：`T_comp ≈ B·S·(FLOPs_per_token) / (N_gpus · GPU_peak · MFU)`
   - 实测：使用 `torch.profiler.profile` 提取 CUDA kernel 耗时总和（不含通信 kernel）。

2. **通信时间 `T_comm`**：通过 α-β 模型或 NCCL profiler。
   - 理论：基于消息大小和 `N` 用 `7.1` 公式计算。
   - 实测：在 NCCL 调试模式下打印通信耗时，或使用 `nsys` 追踪。

**工程中的近似规则**：
- 对于 DP：`T_comm_dp ≈ 2·(2P) · β_effective` （忽略延迟项，大消息主导）。
- 对于 TP：`T_comm_tp ≈ (L · 2 · 2·B·S·d) · β_intra` （每层两次 All-Reduce，β 用节点内 NVLink 值）。
- Megatron 内部会基于这些估算决定 TP 大小（通常限制 tp≤8）。

**Profiling 工具**：

```python

    loss.backward()
print(prof.key_averages().table(sort_by="cuda_time_total"))
```

统计 `ncclAllReduce` 等通信 kernel 的总时间，与计算 kernel 时间对比，得到实际 `R`。

### ④ 复杂度分析

**R 的缩放行为**（固定硬件，增大模型或并行度）：

**数据并行**：

```
R_dp ∝ (B_global / N) · (FLOPs_per_token / GPU_peak) / (2P · β)
    ∝ (B_global / N) · (1 / P) · (FLOPs_per_token / GPU_peak)
```

- `P` 增大 → `R_dp` 减小（通信量正比于 P，计算量正比于 B·FLOPs_per_token，而 FLOPs_per_token 与 P 近似线性，因此 `R_dp` 大致随 `P` 缓慢下降，但当 B 固定，绝对计算时间增长不如通信量快，且 N 增加时每卡计算量下降）。
- `N` 增大（固定全局 batch） → `R_dp` 下降，因为每卡计算量减半，通信量不变。强扩展下 DP 扩展效率必然下降。
- `B_global` 增大（弱扩展） → `R_dp` 可保持恒定，因每卡计算量不变。

**张量并行**：

```
R_tp ∝ (B·S·d²/tp) / (B·S·d · β) ∝ d/tp
```

- `R_tp` 正比于隐藏维度 `d`。大模型（d 大）的 TP 通信占比小，效率高。小模型（d 小）TP 通信可能成为负担。
- `tp` 增大，每卡计算量线性减小，通信量基本不变（All-Reduce 总传输量约 2·BSd 每卡），所以 `R_tp` 随 `tp` 增大而降低，限制了 TP 的扩展。

**流水线并行**：

```
R_pp ∝ (计算量) / (BSd · β) ∝ (L/pp) · d
```

- `R_pp` 通常很大，因为 `L·d` 远大于 `1`。PP 通信开销极低，只要微批次数量 m 足够大以隐藏 Bubble。

**混合并行的整体 R**：
通常由最低的 `R` 维度主导。如果 TP 的 R 很低，即使 DP 和 PP 的 R 很高，系统也会受限于 TP 通信。因此需平衡各维度的 R 在同一数量级。

---

### ⑤ 设计权衡

**1. 通信瓶颈的识别与缓解**
当 `R < 1` 时，增加更多 GPU 甚至可能使总时间变长（通信增加的等待超过计算节省）。实践中要求 `R > 2` 以留出安全边际。若 `R` 不足：
- DP：降低 `N_dp`，或使用 ZeRO-1/2（不影响 R 计算），或引入 TP 来减小每卡参数量 P。
- TP：限制 `tp` 在节点内，增大 d（模型更宽），或使用序列并行（1.2.5）切分激活以降低通信量。
- PP：确保足够 micro-batch 数，使 Bubble 占比 <20%。

**2. 计算 - 通信比与重叠的相互作用**
高 `R` 不意味着通信能完全隐藏。重叠能力受限于依赖链（通信只能在对应梯度计算完成后开始）。实际中需结合 `5.2.4` 的重叠因子，定义**有效通信时间** `T_comm_eff = max(0, T_comm - T_comp_overlap)`。设计时应争取 `T_comm_eff ≈ 0`。

**3. 混合并行中的 R 平衡**
在三维混合并行中，通信发生在不同维度，物理链路 β 不同（节点内 NVLink β_intra 小，跨节点 β_inter 大）。通常使 TP 用低 β 链路（节点内），DP 用高 β 链路（跨节点）。通过调整 `dp × tp × pp = N`，使每个维度的 `R` 都在可接受范围（例如 >3）。Megatron/DeepSpeed 的配置经验即基于此平衡。

**4. 模型规模增长下的 R 变化**
随着模型从 7B → 70B → 175B，`P` 线性增长，`d` 也会增大（但不一定成比例）。DP 的 `R_dp` 会下降（因为梯度通信量正比于 P），而 TP 的 `R_tp` 可能因 d 增加而改善。这意味着超大模型更依赖 TP/PP，而非纯 DP+ZeRO，这也是为什么 GPT-3 的训练采用了高 TP 度（8）的原因之一。

**5. 使用 R 指导梯度累积和 micro-batch 调优**
梯度累积不改变单次通信量，但减少了通信频率（每累积步才一次 All-Reduce），等效于增大了 `T_comp`。这可以提高有效 `R`，但会延迟同步，需要更大显存保存累积梯度。PP 的 micro-batch 数增加则直接减少了 Bubble 占比，提高了 `R_pp`。

## 展开 7.3 扩展效率与强扩展 / 弱扩展

---

### ① 形式化定义

**扩展效率（Scaling Efficiency）** 衡量并行系统在增加计算资源（GPU）后，实际性能增益相对于理想线性加速的比例。它是判断并行策略在特定规模下是否可持续的核心指标。

设使用 `N` 个 GPU 训练一个任务的吞吐量为 `Throughput(N)`（samples/sec 或 tokens/sec），单 GPU 吞吐量为 `Throughput(1)`，则：

```
加速比（Speedup）: S(N) = Throughput(N) / Throughput(1)
扩展效率: E(N) = S(N) / N
```

理想线性扩展下，`S(N) = N`，`E(N) = 1`（100%）。实际系统中 `E(N) < 1`，且随 `N` 增大而衰减。

**两种扩展模式**：

**强扩展（Strong Scaling）**：固定问题规模（全局 batch size `B` 恒定），增加 GPU 数量 `N`。
- 目标：缩短完成相同工作量所需的时间。
- 理想：时间与 `N` 成反比，即 `Time(N) = Time(1) / N`。
- 实际瓶颈：每卡计算量 `b = B/N` 递减，通信量不变（DP 梯度 `2P`），导致通信占比增加。同时，过小的 `b` 降低 GPU 利用率，kernel 启动开销相对变大。

**弱扩展（Weak Scaling）**：固定每 GPU 的问题规模（`b` 恒定），随 `N` 增加同步增大全局 batch `B = N·b`。
- 目标：在更短时间内处理更多数据，或训练更大模型（模型大小随 N 线性增加）。
- 理想：吞吐量线性增长，单步时间保持恒定。
- 实际瓶颈：当模型规模也随 N 增加时，通信模式可能改变（如梯度大小 `P` 变大），单步时间可能上升。在仅增加 batch 而不增加模型时，弱扩展较易接近理想。

**扩展效率的形式化预测**：
结合 `7.1` 的通信成本模型和 `7.2` 的计算 - 通信比，带开销的加速比为：

```
S(N) = N / (1 + N·T_comm_overhead / T_comp(1))
```

其中 `T_comp(1)` 是单 GPU 的计算时间。由此：

```
E(N) = 1 / (1 + N·T_comm_overhead / T_comp(1))
```

`T_comm_overhead` 对 DP 约为 `T_allreduce(2P)`（每个 GPU 分摊的通信开销），对 TP 和 PP 有对应形式。该式揭示了：当 `N` 增大时，分母增大，扩展效率必然下降。

### ② 系统视角

**在整个知识树中的位置**：`7.3` 是性能分析层的综合度量节点，承上整合 `7.1`（通信成本）和 `7.2`（计算 - 通信比），通过扩展效率将它们与实际吞吐和资源利用率关联起来。为 `7.4` 的关键瓶颈诊断提供量化目标。

**在系统设计中的角色**：
- **资源规划**：给定扩展效率目标（如 >0.8），反推允许的最大 GPU 数量。
- **并行策略比较**：不同策略的扩展效率随 N 的衰减速度不同，可以据此选择最优策略。
- **瓶颈发现**：扩展效率低于预期时，剖析是计算、通信还是 Bubble 导致。

**输入/输出**：
- **输入**：模型的单 GPU 计算时间 `T_comp(1)`，并行度 `N_dp, N_tp, N_pp`，通信开销模型（来自 `7.1` 和 `5.2`），硬件拓扑。
- **输出**：预估加速比 `S` 和效率 `E`，以及各并行维度对效率损失的贡献。

**与硬件的依赖**：
- 节点内带宽（NVLink 高带宽）使 TP 能维持高扩展效率（上限 ~8）。
- 跨节点带宽（InfiniBand）限制了 DP 的扩展效率，尤其在强扩展下。
- 使用梯度累积可模拟弱扩展，维持效率但增加步时间。

---

### ③ 工程映射

**测量扩展效率的步骤**：

1. **单 GPU 基准**：在单 GPU 上使用最大可放入显存的 micro-batch size `b_max`，运行若干步，计算吞吐 `T_1`（tokens/sec）。
2. **多 GPU 基准**：在 N GPU 上，使用全局 batch `B = N·b`（弱扩展）或 `B = b_max`（强扩展），测量吞吐 `T_N`。
3. **计算加速比和效率**：`S = T_N / T_1`，`E = S / N`。

**Megatron-LM 中的扩展效率测试**：
Megatron 提供 `tools/checkpoint_loader_mcore.py` 等评估脚本，并在论文中报告了不同模型大小和 GPU 数的扩展效率。他们典型地使用弱扩展（增大 batch 和模型），保持每 GPU 计算量恒定。

**DeepSpeed 中的效率**：
DeepSpeed 通过 ZeRO 减少显存，允许更大的 micro-batch，从而在相同 GPU 数量下能更好地维持 GPU 利用率，提高扩展效率。ZeRO-3 的额外通信会降低效率，需权衡。

**Profiling 得到开销比例**：

```python
# 在 PyTorch Profiler 中分离计算和通信时间
with profile(...) as prof:
    for step in range(10):
        loss.backward()
        optimizer.step()

# 统计总耗时，通信 kernel 占比
total_time = prof.table()...
comm_time = sum(...) 
overhead_ratio = comm_time / total_time
E_measured = (1 - overhead_ratio) * (理想线性加速比 N)
```

**典型扩展效率值（经验）**：
- 纯 DP，节点内 8 GPU，强扩展（固定 batch）：`E ≈ 0.85 ~ 0.95`（取决于模型大小）。
- 纯 DP，跨节点 64 GPU，强扩展：`E` 可能降至 `0.5 ~ 0.7`。
- 混合 TP+PP+DP，数百 GPU，弱扩展：`E` 通常维持在 `0.7 ~ 0.9`（Megatron 论文数据）。

### ④ 复杂度分析

**强扩展下效率的衰减**：
设单 GPU 计算时间 `T_c(1)`，DP 通信时间 `T_comm = κ·P`（κ 包含 β 和 N 相关常数）。在 N 个 GPU 强扩展时，每卡计算时间 `T_c(N) = T_c(1)/N`。忽略重叠的理想加速比为：

```
S_strong(N) = N · T_c(1) / (T_c(1)/N + T_comm)
            = N² / (1 + N·T_comm / T_c(1))
```

当 `N` 较大时，`S_strong(N) ≈ N / (T_comm / T_c_per_proc)`，远小于 N。效率 `E_strong ∝ 1/N`，随 N 快速下降。

**弱扩展下效率的保持**：
若保持每卡计算量 `T_c(1)` 不变，仅增大全局 batch。在 DP 中，通信时间仍为 `T_comm = κ·P`（模型不变时 `P` 不变），总步时间 `T_total = T_c(1) + T_comm`（假设通信无法重叠或重叠不完全）。加速比：

```
S_weak(N) = N · T_c(1) / (T_c(1) + T_comm) = N / (1 + T_comm/T_c(1))
```

效率 `E_weak = 1 / (1 + T_comm/T_c(1))`，**与 N 无关**！只要 `T_comm/T_c(1)` 保持恒定，弱扩展效率不衰减。这是弱扩展在大模型训练中受欢迎的原因。

但是，当模型规模随 N 增加而增加时（如大模型需要更多卡），`P` 增大导致 `T_comm` 增加，`T_comm/T_c(1)` 可能恶化，造成效率下降。这就是为何需 TP/PP 分担参数，降低梯度通信量。

**TP/PP 的扩展特性**：
- TP：增加 `N_tp`，每卡计算减少，通信量基本不变（每层 All-Reduce `2BSd`），效率类似强扩展，快速衰减。因此 TP 限制在 8 以内。
- PP：增加 `N_pp`，每卡计算量几乎不变（层数 L/N_pp），通信量不变（P2P），但 Bubble 比例上升。扩展效率主要受 Bubble 影响，当 micro-batch 数 m 大时，Bubble 小，效率可维持较高。PP 可以扩展到较大规模（如 16~64）。
- 混合 TP+PP+DP：平衡三维度扩展，能在数百 GPU 上维持 >0.7 的弱扩展效率。

---

### ⑤ 设计权衡

**1. 强扩展 vs 弱扩展的选择**
- 强扩展适合中小规模（<32 GPU），追求更快的单步时间。
- 弱扩展是训练大模型的唯一可行方式：通过增大 batch 和模型，充分利用更多 GPU 而不过分损害效率。
- 实践中常结合两者：增大模型（弱扩展）的同时，将固定全局 batch 分摊到更多 GPU（也有强扩展成分）。

**2. 效率下降的容忍度**
扩展效率从 0.95 降到 0.7，意味着 30% 的算力被通信和同步浪费。在大规模训练（数百万美元成本）中，必须通过优化（通信重叠、ZeRO、混合并行）将效率维持在 0.8 以上，否则成本将不可接受。

**3. 模型大小与扩展效率的关联**
小模型（<1B）在数百 GPU 上训练时，每卡计算量太小，通信主导，扩展效率极低。大模型（>10B）因每卡计算量充足，更易获得高扩展效率。因此，**只有当模型大到足以“喂饱” GPU 计算时，大规模并行才有意义**。

**4. 混合并行的扩展效率调优**
- 首先确定 TP 限制（节点内，≤8）。
- 然后确定 PP 的扩展范围（受 Bubble 限制，可跨节点）。
- 剩余并行度分配给 DP（受梯度通信限制，可通过 ZeRO 降低通信）。
- 调优目标：使各维度的 `R = T_comp/T_comm > 3`，以确保扩展效率 >0.85。
- 工具：使用 Megatron 的 `parallel_state.py` 或 DeepSpeed 配置模拟扩展行为。

**5. 扩展效率的预报与实测闭环**
理论预报（基于 α-β 模型）可估算扩展效率趋势，但需实测验证（因重叠、负载均衡、网络拥塞等因素）。实践中，启动大规模训练前先用小规模（如 1/4 规模）做扩展测试，将实测效率外推到全规模，以规避风险。

## 展开 7.4 关键瓶颈：All-Reduce 带宽 vs. TP 通信量

---

### ① 形式化定义

在大规模分布式训练中，通信的两个最主要来源是 **数据并行（DP）的梯度 All-Reduce** 和 **张量并行（TP）的层内 All-Reduce/All-Gather**。它们对通信带宽的需求有本质不同，共同构成系统的关键瓶颈。

设模型参数量为 `P`，隐藏维度 `d`，序列长度 `S`，micro-batch 大小 `B`，DP 并行度 `N_dp`，TP 并行度 `N_tp`。两种通信的数据量形式化为：

**DP All-Reduce 通信量（梯度同步）**：

```
M_dp = 2P  bytes   （FP16 梯度，每个 GPU 的通信量为 ≈ 2P，Ring All-Reduce 每 GPU 收/发约 2P）
```

每个训练步（或梯度累积步）执行一次。其带宽需求 = `M_dp / T_step`，其中 `T_step` 是单步训练时间。

**TP 通信量（每层 All-Reduce）**：

```
M_tp_per_layer = 2 · B · S · d  bytes   （FP16，单次 All-Reduce 消息大小，Megatron 风格一个 Block 两次）
```

每个 Transformer Block 前向有 2 次 All-Reduce（反向对应 Reduce-Scatter，数量相同）。总 TP 通信量：

```
M_tp_total = L · 2 · M_tp_per_layer = 4 · L · B · S · d  bytes （全模型前向）
```

频率极高：每一步中，每个 Block 都会触发通信。

**瓶颈定义**：当硬件提供的通信带宽 `B_hw`（如 NVLink 600 GB/s，InfiniBand 25 GB/s）无法在给定时间窗内完成所需数据传输时，通信成为瓶颈。瓶颈可能表现为：
- DP All-Reduce 时间过长，导致梯度同步成为步长时间的主要部分。
- TP 的频繁小消息 All-Reduce 累积延迟过大，或跨节点时带宽不足无法支撑。

**瓶颈的量化对比**：定义两种通信的“通信压力”指标：

```
Pressure_dp = M_dp / (可用 DP 链路带宽)    // 单位：秒，每步同步耗时
Pressure_tp = M_tp_per_layer / (可用 TP 链路带宽)  // 单位：秒，每层通信耗时
```

若 `Pressure_tp * L` 与 `Pressure_dp` 在同一量级或更大，且无法重叠，则构成瓶颈。

---

### ② 系统视角

**在整个知识树中的位置**：`7.4` 是性能分析层的最终瓶颈诊断节点，整合了 `7.1`（通信成本）、`7.2`（计算 - 通信比）和 `7.3`（扩展效率），并直接关联到 `5.3`（NCCL 实现）和混合并行设计 `4.1`。它回答“在具体硬件上，什么通信会成为最先触及天花板的那一个”。

**在训练系统中的角色**：
- 在系统设计阶段，判断应该将高速链路（NVLink）分配给 DP 还是 TP。
- 诊断已部署系统的性能壁障：是梯度同步占太多时间，还是 TP 的频繁通信拖慢了单步？
- 决定并行度的调整方向：增大 TP 以减少 DP 梯度大小，但增加 TP 通信；或反之。

**通信拓扑与瓶颈关系**：
- **节点内**：NVLink 提供极高带宽（~600 GB/s 每对），通常 TP 通信（小消息、频繁）放在节点内，瓶颈概率低。
- **跨节点**：InfiniBand 带宽有限（~25 GB/s），主要用于 DP 梯度同步（大消息、低频）。如果 DP 梯度太大或节点数太多，跨节点带宽会率先成为瓶颈。
- **分层 All-Reduce**：NCCL 在跨节点时先做节点内 Reduce，再跨节点 All-Reduce，使得瓶颈通常落在跨节点链路上。

**与混合并行的关联**：混合并行（DP+TP+PP）通过调整比例来平衡这两类通信。例如，若 DP 梯度同步太慢，可增加 TP 来减小每卡参数 `P`，从而减小 `M_dp`；但这又增加 TP 通信频率，可能使节点内 NVLink 拥塞。反之亦然。设计时需使两方面的带宽需求均低于硬件能力。

### ③ 工程映射

**PyTorch / Megatron 中观测瓶颈**：
- 使用 `torch.profiler` 分析 `ncclAllReduce` 等 kernel 的时间，区分是来自 DP 组还是 TP 组。
- 通过 NCCL 环境变量 `NCCL_DEBUG=INFO` 查看实际通信带宽，若远低于理论峰值，则可能存在拥塞或配置问题。

**Megatron-LM 的通信隔离**：
- Megatron 明确将 TP 通信限制在节点内（`tp_group` 仅包含同一节点的 GPU）。
- DP 通信跨节点时，使用 NCCL 的分层 All-Reduce，确保节点内先聚合再跨节点。
- 在代码中，通过 `mpu.get_tensor_model_parallel_group()` 和 `mpu.get_data_parallel_group()` 获取不同的通信域，避免混乱。

**DeepSpeed 的通信调度**：
- DeepSpeed 对 ZeRO 阶段的通信有优化：ZeRO-1/2 的梯度 All-Reduce 与 DP 等同；ZeRO-3 额外参数 All-Gather 可能增加通信压力。
- 在 DeepSpeed 配置中，可通过 `communication_data_type` 控制通信精度，例如使用 FP16 通信以减少数据量（牺牲部分精度）。

**瓶颈检测的典型阈值**（经验）：
- 单步中 DP All-Reduce 时间占比 > 20% 时，DP 通信成为显著瓶颈。
- TP All-Reduce 单次延迟 > 50 μs 或累计时间 > 5% 步时，TP 通信问题需关注（通常发生在 tp>8 或跨节点 TP）。
- 若 `N_dp` 很大且模型 >10B，跨节点带宽往往是第一瓶颈。

### ④ 复杂度分析

**场景对比：DP 瓶颈 vs TP 瓶颈**

设 A100 集群，节点内 NVLink 带宽 550 GB/s（有效），跨节点 InfiniBand 25 GB/s（有效）。分析一个 70B 模型（P=70B，FP16 梯度 140 GB），d=8192，L=80，S=4096，B=1（micro-batch）。

- **DP All-Reduce（跨节点，N_dp=8）**：
  `M_dp = 140 GB`，跨节点带宽 25 GB/s → `T_dp ≈ 140 / 25 = 5.6 秒`（忽略延迟和节点内部分，实际分层会减少跨节点数据量，但跨节点部分仍传输 `2·(N_inter-1)/N_inter·M_dp` 约 140 GB per GPU）。这远超单步计算时间（通常数秒），DP 成为绝对瓶颈。实际中跨节点 DP 时，每个 GPU 的跨节点传输量约为 `2 * (N_node-1)/N_node * M_dp`，若 2 节点，每个 GPU 跨节点传输 70 GB，耗时 2.8 秒，依然很大。

- **DP All-Reduce（节点内，N_dp=8）**：
  节点内带宽 550 GB/s → `T_dp ≈ 140 / 550 ≈ 0.25 秒`。与计算时间（假设 400ms）可比，占比 ~38%，已是显著瓶颈。

- **TP All-Reduce（节点内，tp=4）**：
  `M_tp_per_layer = 2 * 1 * 4096 * 8192 * 2 = 128 MB`（FP16）。
  节点内带宽 550 GB/s → 单次 All-Reduce 约 0.23 ms。80 层，160 次 All-Reduce，总 TP 通信时间 ≈ 36.8 ms。与计算时间（假设 400ms）相比，占比 ~9%，可接受。

- **TP All-Reduce 若跨节点（tp=8 跨 2 节点）**：
  跨节点带宽 25 GB/s → 单次 All-Reduce 需 128 MB / 25 GB/s ≈ 5.1 ms，总 TP 通信 816 ms，远超计算时间，不可行。这就是 TP 不能跨节点的数学原因。

**结论**：对于大模型，DP 的跨节点梯度同步是所有通信中的最大瓶颈，因其数据量庞大且跨节点带宽有限。TP 通信虽然频繁但总数据量小得多，且被限制在节点内高速链路上，通常不构成主要瓶颈，除非 TP 度太大或序列极长。

**混合策略的作用**：
引入 TP=4 可将每卡参数量 P 减为 1/4，使 DP 梯度通信量降为 35 GB，跨节点时间降为 1.4 秒（2 节点每卡 17.5 GB），大幅缓解 DP 瓶颈。这正是混合并行的核心动机。

### ⑤ 设计权衡

**1. 带宽分配：NVLink 给 DP 还是 TP？**
- NVLink 带宽高，但资源有限。通常优先满足 TP 的低延迟频繁通信，因为 TP 通信无法轻易跨节点。
- DP 梯度同步虽然数据量大，但频率低，可以容忍跨节点较慢带宽，且可通过通信 - 计算重叠隐藏部分延迟。
- 若节点内 GPU 有多余 NVLink 带宽，也可用于加速 DP 节点内 Reduce 阶段（分层 All-Reduce），但不改变跨节点瓶颈。

**2. 增大 TP 度缓解 DP 瓶颈 vs 引入 TP 通信开销**
增大 `N_tp` 可以线性减小 `P` 和 `M_dp`，从而降低 DP 通信时间，但会增加 TP 通信总次数和总数据量（因为每层 All-Reduce 次数和单次数据量不变，但层数可能因 PP 变化？实际上 TP 通信总量 `4 L B S d` 不随 `N_tp` 变化，单个 GPU 通信量也不变（仍为 `2·((tp-1)/tp)·BSd`，略减），所以 TP 通信开销几乎恒定。因此，**只要 TP 限制在节点内且带宽充足，增大 TP 是纯收益**，可以有效减轻 DP 跨节点压力，直到 tp 达到节点 GPU 数量上限或 d 减小导致 TP 效率下降。

**3. 序列长度 S 和 Batch Size B 的影响**
TP 通信量与 `B·S·d` 成正比。当训练极长序列（如 128K）时，TP 通信量也可能膨胀到不可忽略，甚至在节点内也形成瓶颈。此时需要引入序列并行（SP）来切分 `S` 维度，降低单 GPU 上的 `S`，从而降低 TP 通信量。这是 `1.2.5` 和 `4.5` 的关键场景。

**4. 通信精度与计算精度的权衡**
为降低 DP 梯度通信量，可使用梯度压缩（如 8-bit 通信）或 PowerSGD 等有损压缩。这牺牲部分梯度精度，可能影响收敛，需谨慎。TP 通信通常不压缩，因为其数据量相对小且需要完全精度保持激活正确性。

**5. 硬件代际影响**
H100 的 NVLink 4.0 带宽提升至 900 GB/s，InfiniBand NDR 400 GB/s。跨节点带宽相对提升更多（25 → 50 GB/s），有助于缓解 DP 跨节点瓶颈。同时 H100 的 SM 计算能力更强，计算时间缩短，通信占比相对上升，需要重新平衡混合并行比例。

**6. 瓶颈诊断的实际步骤**
当扩展效率不佳时，优先检查：
- DP All-Reduce 耗时（通过 profiler 或 NCCL 日志）。
- 跨节点带宽利用率（是否达到物理极限的 80% 以上）。
- TP All-Reduce 累计延迟是否异常（可对比单层计算时间）。
根据瓶颈类型选择对策：增加 TP/PP 降低 DP 梯度大小，或升级网络，或启用通信重叠/压缩。
