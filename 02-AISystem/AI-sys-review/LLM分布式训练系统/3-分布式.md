# 展开 8.1：显存瓶颈

---

## ① Formal Definition（形式化定义）

**显存瓶颈（Memory Bottleneck）** 是指：在给定的 GPU 物理显存容量（HBM）约束下，训练一个指定规模的模型所需的最小显存超过了单张 GPU 的可用容量，导致无法完成哪怕一次前向 + 反向 + 优化器更新（即 micro batch size = 1 仍无法运行）。这是大模型必须采用分布式训练系统的最直接原因。

形式化定义如下：设单 GPU 可用显存为 \(M_{GPU}\)（如 A100-80GB SXM 为 80 GB），模型训练的最小显存需求为 \(M_{required}\)，其中：

\[

M_{required} = M_{model\_states} + M_{act} + M_{overhead}

\]

- \(M_{model\_states}\)：模型状态显存（参数、梯度、优化器状态、master weights），详见 4.3，通常 ≥ 12P bytes。
- \(M_{act}\)：最小微批大小下（b = 1）的激活值显存（可经 Activation Checkpoint 或 FlashAttention 削减）。
- \(M_{overhead}\)：框架、库与通信开销（通常占 5%~20%）。

若 \(M_{required} > M_{GPU}\)，则单卡训练不可能，系统处于显存瓶颈。瓶颈可能由模型状态主导（参数瓶颈），也可能由激活值主导（激活瓶颈），还可能二者共同作用。

---

## ② System Design View（系统视角）

在整个分布式训练决策链中，8.1 是“动机触发器”：

```
模型配置 (L, h, s, ...)
       │
       ▼
┌───────────────────┐
│   4.3 显存组成计算 │
└────────┬──────────┘
         │
         ▼
   计算 M_required
         │
         ▼
   M_required > GPU 显存? 
     │YES        │NO
     ▼            ▼
  8.1 显存瓶颈   单卡可训练（仅需 DP 扩大吞吐）
     │
     ├──→ 必须采用模型并行（TP/PP）或 ZeRO-3 将模型状态切分
     ├──→ 若激活瓶颈主导，需启用 Activation Checkpoint、Sequence Parallel
     └──→ 作为 10~13 章并行策略选择的直接驱动
```

**输入**：
- 模型参数量 P（来自 4.1）
- 激活值计算模型（来自 4.3，考虑 FlashAttention、微批大小、序列长度）
- GPU 硬件显存规格

**输出**：
- 是否必须分布式
- 瓶颈类型（参数主导、激活主导、复合型）
- 指导选择具体优化手段（ZeRO 阶段、TP 程度、是否开启重计算）

**依赖关系**：
- 上承 4.1、4.2、4.3 的资源分析
- 下启 10.1（DP 无法解决显存瓶颈）、11.1（TP 切分模型）、12.1（PP 切分层）、13.4（ZeRO 分片）、8.2（算力瓶颈往往伴随显存瓶颈）

## ③ Implementation Mapping（工程映射）

在实际训练框架中，“显存不够”通常表现为以下错误之一，工程师据此反向定位瓶颈：

- **CUDA Out of Memory (OOM)**：`RuntimeError: CUDA out of memory. Tried to allocate ...` 表明尝试分配张量失败，显存耗尽。
- **DDP 启动时 OOM**：即便只跑单卡 DDP，若模型本身大于单卡显存，初始化后第一次前向就会 OOM。证明必须引入模型并行或 ZeRO。
- **Megatron / DeepSpeed 的 check_memory_usage**：启动前框架会粗略估算所需显存，若超过设定百分比发出警告或拒绝启动。

**DeepSpeed 的显存分析工具**：

```python
# 在 deepspeed.initialize() 之后
engine.memory_breakdown()
```

输出类似：

```
Memory breakdown after initialization:
  Parameters:        xx GB
  Gradients:         xx GB
  Optimizer states:  xx GB
  Activations:       xx GB
  Total:             xx GB
```

如果 `Total` 接近或超过 80 GB，说明单卡无法承载全量模型状态，必须启用 ZeRO Stage 3（参数分片）。

**PyTorch 手动评估**：

```python
param_size = sum(p.numel() for p in model.parameters()) * 2  # FP16
optim_state_size = param_size * 4  # Adam FP32 states roughly
print(f"Min model state: {(param_size * 2 + optim_state_size) / 1e9} GB")
```

结合估算的激活值，即可预判单卡可行性。

## ④ Complexity Analysis（复杂度分析）

以 **7B 模型**（P = 6.74 × 10^9, L=32, h=4096, d_ff=11008, n_heads=32）为例，定量分析单卡 80GB A100 的可行性。

**模型状态显存**（混合精度 Adam，含 master weights）：
\[
M_{model\_states} = 16P \ \text{bytes} = 16 \times 6.74 \times 10^9 = 107.8 \ \text{GB}
\]
仅此一项已远超 80 GB 上限。因此，**即使不加载任何数据（b=1, s=1），单卡也不可能训练 7B 模型**。这是“参数瓶颈”的典型表现。

**如果采用 ZeRO-1（优化器状态分片）**：
- 单卡仍保留完整参数和梯度，仅优化器状态被分片到 DP 组。
- 模型状态显存降至 \(2P(\text{param}) + 2P(\text{grad}) + \frac{8P}{N_{DP}}\)。当 \(N_{DP}=8\) 时，单卡模型状态 = 4P + P = 5P ≈ 33.7 GB。
- 此时模型状态可装入 80GB，但还需加上激活值。

**激活值瓶颈示例**（同模型，假设 s=4096, b=1，无 FlashAttention）：
根据 4.3，单层激活主要项含 Score 矩阵 \(b n_h s^2\) = 1×32×4096² ≈ 5.37×10^8 元素，2 bytes → 约 1.0 GB/层。32 层仅 Score 矩阵即 ~32 GB。加上其他激活张量，总激活可能超过 60 GB。
- 模型状态 33.7 GB + 激活 60 GB = 93.7 GB > 80 GB，依然无法单卡训练。
此时必须开启 **FlashAttention**（消除 Score 矩阵存储）或 **Activation Checkpointing**（重计算换空间）。

**开启 FlashAttention 后**，激活显存降至 ~20 GB，总占用 33.7 + 20 = 53.7 GB，单卡 80 GB 可容纳。**这表明：对于 7B 模型，组合 ZeRO-1（需多卡）和 FlashAttention（单卡特性）才能使训练可行**（前提是多卡数据并行组存在）。若只有一张卡，ZeRO-1 无效，必须用 ZeRO-3 或张量并行 + 流水并行。

**复杂度渐近分析**：

| 瓶颈类型 | 主导项 | 代表性条件 |
|---------|--------|-----------|
| 参数瓶颈 | \(16P\) | P > 5B（80GB 单卡） |
| 激活瓶颈（长序列） | \(L \cdot b \cdot n_h \cdot s^2\) | s ≥ 4096 且无 FlashAttn |
| 复合瓶颈 | 两者量级相当 | 中大模型 + 中等序列长度 |

**Scaling 行为**：
- 参数量 P 增长导致模型状态线性突破，显存需求不可压缩（除非分片）。
- 序列长度 s 增长导致激活显存二次增长（无 FA 时），比参数增长更快造成瓶颈。
- 数据并行（DP）**不减少单卡模型状态和单样本激活量**，因此纯 DP 无法解决显存瓶颈，必须结合模型并行或 ZeRO。

---

## ⑤ Design Trade-offs（权衡）

**Trade-off 1：模型状态分片 vs. 通信开销**
- 使用 ZeRO-3 可将模型状态分片到多卡，单卡模型状态随 DP 数增加线性下降，突破显存墙。
- 代价是每次前向/反向需要 AllGather 参数，引入额外通信。若卡间带宽不足（如 PCIe），通信时间可能显著拖慢训练。在 NVLink 连接下该代价可接受。
- 决策：若单卡连参数都装不下，ZeRO-3 或 TP 是强制的，没有“是否选择”的余地。

**Trade-off 2：Activation Checkpoint vs. 重计算开销**
- 激活瓶颈可通过重计算缓解，几乎不增加通信，但增加 ~30% 的计算量。
- 若计算资源充裕而显存紧张（许多大模型训练场景），这是默认开启项。
- 若计算已处于 Compute Bound，额外重计算可能拉低吞吐，此时可结合 Sequence Parallel 来分担激活。

**Trade-off 3：FlashAttention 的重要性**
- 在长序列训练中，开启 FA 几乎成为标准，它消除了激活中的二次项，使内存复杂度从 \(O(s^2)\) 降为 \(O(s)\)。
- 但它是一种算法重写，对注意力变体有要求，在极特殊模型结构中可能无法使用。不做 FA 则序列长度严重受限。

**Trade-off 4：微批大小 b 的权衡**
- 减小 b 直接减少激活显存，但过小的 b 会导致 GPU 计算效率下降（Kernel 无法充分利用并行）。
- 通常通过梯度累积保持较大的全局批大小，用小 b 控制显存，再增大 DP 数保持吞吐。

**Trade-off 5：单卡 80GB 是硬边界，但并非不可突破**
- 通过 CPU Offload（ZeRO-Offload 或 Megatron 的 CPU Adam），可将优化器状态和部分参数暂存 CPU 内存，变相扩展存储池。代价是 PCIe 带宽极低，会严重拖慢训练。
- 这类方案通常用于微调（finetuning），在预训练中较少使用。

**结论**：
8.1 显存瓶颈是大模型必须走向分布式的第一推手。7B 模型已需至少 2 张 A100（ZeRO-3 + FA），65B 模型需数十张卡，175B 模型需数百张卡配合复杂的 3D 并行。理解这个瓶颈，才能理解后续所有并行策略的必然性。

# 展开 8.2：算力瓶颈

---

## ① Formal Definition（形式化定义）

**算力瓶颈（Compute Bottleneck）** 是指：在给定单 GPU 的理论峰值算力（Peak FLOPS）约束下，完成一次完整训练（到达目标 loss 或处理完预定数量 tokens）所需的**总浮点运算量**过大，导致即使显存充足，训练时间也远超工程可接受的范围（数月至数年）。这是推动分布式训练的第二个根本动机——**不仅需要装得下，还需要算得完**。

形式化定义如下：设单 GPU 的峰值算力为 \(C_{peak}\)（单位 FLOPS，如 A100-80GB SXM 的 FP16 Tensor Core 峰值 312 TFLOPS），模型训练所需的总浮点运算量为 \(F_{total}\)（单位 FLOPs），则单卡训练的**理论最少训练时间**（忽略通信、IO、Kernel 启动开销）为：

\[

T_{min} = \frac{F_{total}}{C_{peak}}

\]

若 \(T_{min}\) 超过工程可用时间（例如 1 年），则系统处于算力瓶颈。实际训练中，由于**实际利用率 MFU（Model FLOPs Utilization）远低于 100%**（通常 30%~60%），真实训练时间 \(T_{real}\) 会数倍于 \(T_{min}\)。

算力瓶颈与显存瓶颈常同时出现，但二者独立：即使通过 ZeRO/TP 解决了显存问题，单卡算力仍可能无法在数周内完成千亿级模型训练。

---

## ② System Design View（系统视角）

在分布式训练动机体系中，算力瓶颈处于第二层判断：

```
模型配置 + 训练数据量 (tokens)
       │
       ▼
  计算总 FLOPs (F_total)
       │
       ▼
  T_min = F_total / C_peak
       │
       ▼
  T_min > 时间预算? 
     │YES         │NO
     ▼             ▼
 8.2 算力瓶颈    单卡训练时间可接受（仅需 DP 扩大吞吐）
     │
     ├──→ 必须增加 GPU 数量，利用并行加速训练
     ├──→ 此时并行不仅为显存，更为提升总算力（线性加速期望）
     └──→ 与通信瓶颈（8.3）一起，限制了并行扩展效率
```

**输入**：
- 模型结构（L, h, s）及训练数据规模（总 tokens 数 \(D\)），来自 4.2 FLOPs 计算：\(F_{total} \approx 6 \cdot D \cdot P\)（Chinchilla 缩放定律近似，每个 token 训练需约 6×P FLOPs）。
- 单 GPU 峰值算力 \(C_{peak}\)。

**输出**：
- 单卡最少训练时间估算
- 最少所需 GPU 数量（以满足时间约束）
- 扩展驱动：走向多卡数据并行或混合并行来缩短端到端时间

**依赖关系**：
- 上承 4.2 计算 FLOPs，下接 8.3 带宽瓶颈（通信开销降低并行效率）。
- 与 8.1 显存瓶颈并列，共同决定并行规模下限。
- 引导 Chapter 9 Roofline 分析（定位 Kernel 级瓶颈）和 Chapter 25 性能建模（全局训练时间预估）。

---

## ③ Implementation Mapping（工程映射）

实际框架中，算力瓶颈的量化通常以**训练时间预估**和**吞吐量报告**体现：

**Megatron-LM**：
- 在训练启动时，会根据配置计算 total FLOPs per iteration 和 per token，并根据 GPU 数量 N 和峰值算力估算 MFU 和训练时间。
- 公式示例（在 `megatron/training/training.py` 和相关脚本中）：
  - `flops_per_token` 由模型结构导出（见 4.2）
  - 总迭代数 = 训练 tokens / (全局批大小 × 序列长度)
  - 预估训练时长 = 总迭代数 × 每迭代时间（基于 MFU 估算）。

**DeepSpeed**：
- 不直接输出全训练时间预测，但通过 `ds_report` 和日志提供每秒吞吐量（samples/sec, tokens/sec），用户可据此推算总时间。
- 结合 `train_batch_size`、`gradient_accumulation_steps`、`num_gpus`，可用 `total_tokens / (tokens_per_second_per_gpu × num_gpus)` 粗略估算。

**PyTorch 生态**：
- 常借助 `torch.profiler` 记录单迭代 Kernel 耗时，手动积分推算。
- 实践中，使用 scaling law 工具（如 `chinchilla` 公式）估算给定模型和 token 数的总 FLOPs，再除以 GPU 算力总数得出计划训练时间。

**典型示例**（手算）：
训练一个 7B 模型，处理 2T tokens，总 FLOPs ≈ 6 × 7e9 × 2e12 = 8.4e22 FLOPs。单张 A100 (312 TFLOPS) 理想时间 = 8.4e22 / 312e12 ≈ 2.69e8 秒 ≈ 8.5 年。显然不可接受。若用 1024 张 A100，假设 50% MFU，实际算力 = 1024 × 312e12 × 0.5 ≈ 1.6e17 FLOPS，时间 ≈ 8.4e22 / 1.6e17 ≈ 525,000 秒 ≈ 6 天。这才变得可行。因此算力瓶颈直接驱动了大规模集群的使用。

---

## ④ Complexity Analysis（复杂度分析）

**4.2 节已推导**：单 token 前向 FLOPs ≈ \(L \times (24 s h^2 + 4 s^2 h)\)，训练迭代（前向 + 反向）约 3 倍。总训练 FLOPs 为：

\[

F_{total} \approx 3 \times D \times \text{FLOPs\_per\_token}

\]

其中 D 为训练 token 总数。若近似为 \(6 \cdot D \cdot P\)，可得简洁估算。

**单卡训练时间**（理论下限）：
\[
T_{min} = \frac{F_{total}}{C_{peak}} = \frac{6 \cdot D \cdot P}{C_{peak}}
\]

**示例分析（7B 模型，D=1T tokens）**：
- \(F_{total} \approx 6 \times 7 \times 10^9 \times 10^{12} = 4.2 \times 10^{22} \) FLOPs。
- A100 FP16 峰值 312 TFLOPS = 3.12e14 FLOPS。
- \(T_{min} = 4.2e22 / 3.12e14 \approx 1.35 \times 10^8\) 秒 ≈ **4.3 年**。
- 若考虑实际 MFU≈50%，则需 **8.6 年**。

**Scaling 行为**：
- 算力需求随模型参数量 P 和训练数据量 D 线性增长（\(O(P \cdot D)\)）。在 Scaling Law 指导下，P 和 D 通常同步增长，因此总 FLOPs ≈ \(O(P^2)\) 或 \(O(D^2)\)。
- 单卡算力 \(C_{peak}\) 增长缓慢（受制程和功耗限制，年均 ~2-3x，远不及模型规模增长），所以**大模型训练必然需要更多 GPU**。
- 增加 GPU 数量 N 理想情况下线性缩短训练时间，但受限于通信开销（8.3）和并行效率（Amdahl's Law），实际加速比递减。

**与显存瓶颈的耦合**：
- 显存瓶颈决定了**最少 GPU 数** \(N_{mem}\)（如 7B 需 ≥2 张 A100 装下模型状态）。
- 算力瓶颈决定了**满足时间要求的最少 GPU 数** \(N_{comp}\)（如想 1 周内训练完需 1024 张卡）。
- 实际所需 GPU 数 \(N = \max(N_{mem}, N_{comp})\)，通常 \(N_{comp} \gg N_{mem}\)，即**算力是更大的规模驱动力**。

---

## ⑤ Design Trade-offs（权衡）

**Trade-off 1：训练时间 vs. 硬件成本**
- 用更多 GPU 缩短训练时间，但硬件成本和功耗线性增加。需要权衡模型能否在目标时间内完成，确定最小可行 GPU 数量。
- 通常参考同规模公开模型（如 Llama 2 70B 使用 2000 张 A100 训练 90 天）来倒推所需资源。

**Trade-off 2：MFU 与并行的矛盾**
- 增加 GPU 数 N 提高总算力，但通信开销上升，MFU 可能下降（如从 60% 降到 45%）。实际训练时间缩短倍率小于 N，甚至可能出现负加速（增加 GPU 后总时间不降反升）。
- 需要精细的混合并行设计（TP/PP/DP 的比例）来最大化 MFU，这正是 Chapter 25 性能建模的核心。

**Trade-off 3：训练数据量 D 的确定**
- 给定模型大小 P，最优训练 token 数 \(D_{opt} \approx 20 \times P\)（Chinchilla 定律）。更多的数据 D 可提升模型性能，但直接增加 \(F_{total}\)。
- 如果算力预算固定，必须在模型大小和数据量之间做 trade-off，不能两者无限扩大。

**Trade-off 4：低精度训练以提升有效算力**
- 使用 FP16/BF16 Tensor Core 可使峰值算力翻倍（相比 FP32），INT8/FP8 进一步提升。
- 但数值稳定性可能制约，尤其在大规模训练中（如 FP8 需更复杂的缩放策略）。提升有效算力也缓解了算力瓶颈。

**Trade-off 5：训练策略（Curriculum Learning, Token Dropping）**
- 通过减少有效计算量来缩短训练时间，但可能牺牲模型质量。这是较新的研究方向（如动态序列长度、MoE 稀疏激活），原理上可减少 \(F_{total}\)，但不改变单卡算力上限。

# 展开 8.3：带宽瓶颈

---

## ① Formal Definition（形式化定义）

**带宽瓶颈（Bandwidth Bottleneck）** 是指：在多 GPU 训练（包括单机多卡和跨节点）中，GPU 计算单元与显存之间（**显存带宽**），以及 GPU 之间（**互联带宽**）的数据传输速率不足以支撑计算单元的满负荷运行，导致计算资源闲置等待数据搬运，从而无法达到理论峰值算力。

形式化定义如下：设某次运算的**算术强度**（Arithmetic Intensity）为 \(I = \frac{\text{FLOPs}}{\text{Bytes Moved}}\)（即每搬运 1 字节数据能执行多少浮点运算），硬件平台的**算力/带宽比**为 \(R = \frac{C_{peak}}{B_{peak}}\)（峰值 FLOPS / 峰值带宽 Bytes/s）。

若 \(I < R\)，则该运算属于 **Memory Bound**——性能被带宽限制，GPU 算力无法用满；若 \(I > R\)，则为 **Compute Bound**。这是 **Roofline 模型**（将在 Chapter 9 展开）的核心判据。

在分布式训练上下文中，存在两层带宽瓶颈：

| 层级 | 名称 | 带宽典型值 (A100) | 对训练的影响 |
|------|------|------------------|-------------|
| **片内** | HBM 显存带宽 | ~2 TB/s (80GB) | 决定单 Kernel 是 Compute Bound 还是 Memory Bound；Attention Score 计算等低算术强度 Kernel 受限于此 |
| **片间** | GPU 互联带宽 | NVLink 600 GB/s (卡间) / InfiniBand 50~400 GB/s (节点间) | 决定 AllReduce/AllGather 等通信操作的耗时，直接影响多卡并行加速比 |

当片间互联带宽不足时，通信耗时在总迭代时间中占比上升，导致多 GPU 加速比严重偏离线性。这是**分布式扩展效率无法线性增长**的最直接物理原因。

## ② System Design View（系统视角）

在分布式训练瓶颈体系中，带宽瓶颈位于最上层（制约扩展效率）：

```

          8.2 算力瓶颈 → 单卡能否算完（时间上）

                │

                │
                ├──→ 若 B_interconnect 太小 → 多卡加速比递减，甚至比单卡更慢
                ├──→ 驱动 Overlap 技术（计算与通信重叠，16.2）
```

## ④ Complexity Analysis（复杂度分析）

### 4.1 片内带宽瓶颈：Memory Bound 分析

根据 Roofline 模型，Kernel 的算术强度 I 与硬件算力/带宽比 R 的比较：

- **典型值**：A100 FP16 峰值 312 TFLOPS，HBM 带宽 2 TB/s = 2000 GB/s
- \(R = 312 \times 10^{12} / (2000 \times 10^9) = 156\) FLOPs/Byte

即：一个 Kernel 需要每搬运 1 字节数据执行超过 156 次浮点运算，才能成为 Compute Bound。否则就是 Memory Bound。

**Transformer 中典型 Kernel 的算术强度**：

| Kernel | 算术强度 (I, FLOPs/Byte) | 瓶颈类型 |
|--------|--------------------------|---------|
| GEMM (大矩阵乘, m=n=k=4096) | ~1000~2000 | ✅ Compute Bound |
| LayerNorm / RMSNorm | ~1~5 | ❌ Memory Bound |
| Softmax | ~1~3 | ❌ Memory Bound |
| Attention Score (Q×K^T, 小 batch) | ~50~200 | 🔸 边界，s 大时可能 Memory Bound |
| Element-wise Ops (ReLU, Dropout) | ~0.5~2 | ❌ Memory Bound |

这意味着：

- **矩阵乘法**通常 Compute Bound（算术强度高），GPU 算力可被充分利用。
- **归一化、激活函数、Softmax** 等逐元素操作是典型的 Memory Bound，性能受限于 HBM 带宽。这是 **Kernel Fusion**（将多个 Memory Bound 操作融合为一个 Kernel 以减少访存）的根本动机。
- **FlashAttention** 的优化核心正是通过分块计算提高 Attention 的算术强度（减少 HBM 读写），将其从 Memory Bound 推向更接近 Compute Bound。

### 4.2 片间带宽瓶颈：通信开销分析

数据并行（DP）中，每次迭代需对梯度执行 AllReduce。每 GPU 通信量为 **\(2P\) 字节**（发送 P bytes + 接收 P bytes，来自 Ring AllReduce 算法）。通信耗时：

\[

T_{comm} = \frac{2P}{B_{eff}}

\]

其中 \(B_{eff}\) 为有效 AllReduce 带宽（考虑算法效率后）。

**具体示例（7B 模型，梯度 2P bytes = 13.5 GB）**：

| 互联方式 | 典型带宽 | 梯度同步时间 |
|---------|---------|-------------|
| PCIe Gen4 ×16 | ~32 GB/s (双向) | 13.5 / 32 ≈ 0.42 秒 |
| NVLink (A100, 卡对) | 600 GB/s | 13.5 / 600 ≈ 0.023 秒 |
| InfiniBand HDR (200 Gbps) | ~25 GB/s | 13.5 / 25 ≈ 0.54 秒 |
| InfiniBand NDR (400 Gbps) | ~50 GB/s | 13.5 / 50 ≈ 0.27 秒 |

一次迭代（前向 + 反向）的计算时间（单卡 7B, b=1, s=2048）约 0.5~1.0 秒。若用 PCIe 互联，通信时间 0.42 秒，通信占比 ~30%~45%——**带宽瓶颈显著拖慢训练**。换成 NVLink，通信占比降至 ~2%~4%，可近似忽略。

这就是为什么现代训练集群**单机内使用 NVLink/NVSwitch，跨机使用高速 InfiniBand**。

**Scaling 行为**：
- 随 GPU 数 \(N\) 增加，AllReduce 通信量固定（每卡 \(2P\) bytes），但有效带宽受拓扑影响（Ring 算法有效带宽 ≈ \(2B / N\)，导致通信时间随 N 增加而上升）。
- 因此，当 N 很大时（如 1024 卡），即使 NVLink 机内带宽充足，跨节点通信也会成为主导瓶颈。

---

## ⑤ Design Trade-offs（权衡）

**Trade-off 1：通信量 vs. 并行度**
- 张量并行（TP）通信量极大（每层需多次 AllReduce），仅在机内 NVLink 带宽下可行。
- 流水线并行（PP）通信量小（仅传递激活边界），适合跨节点低带宽环境。
- 数据并行（DP）通信量中等，配合 ZeRO 后增加 AllGather，需要大规模时采用分级通信。
- **设计选择**：机内多用 TP 利用高带宽，跨节点用 PP + DP（ZeRO）降低通信压力。

**Trade-off 2：通信重叠（Overlap）的必要性**
- 若通信是瓶颈，可通过将通信与计算放入不同 CUDA Stream，实现 Overlap（16.2）。
- 代价：增加显存（通信缓冲区）、增加调度复杂度。仅当通信占比确实高时才值得。

**Trade-off 3：梯度累积与通信频率**
- 增大梯度累积步数 → 降低通信频率（多个 micro batch 后通信一次），通信占比下降。
- 代价：更多 micro batch 增加激活显存或需要更多重计算。

**Trade-off 4：Kernel Fusion 以应对 Memory Bound**
- 将多个 Memory Bound 的逐元素 Kernel 融合为一个（如 LayerNorm + Dropout + Residual），减少 HBM 访问次数，提升有效算术强度。
- 代价：实现复杂、灵活性降低，现代编译器（TorchInductor, Triton）可自动完成部分融合。

**Trade-off 5：网络拓扑选择与成本**
- NVSwitch 全互联提供极致带宽，但仅限单机（8/16 卡）。
- Fat-Tree 拓扑（InfiniBand）提供跨节点高对分带宽，但成本随规模增大急剧上升。
- 小型集群可使用 Dragonfly 等降低布线成本，但有效带宽降低。架构选择是成本与性能的权衡。

# 展开 Chapter 9：Roofline 模型

---

Chapter 9 是连接硬件性能上限与 Kernel 级优化决策的核心分析工具。在理解了显存、算力、带宽三重瓶颈之后，Roofline 模型提供了一套**统一的量化框架**，用于精确判定任意 Kernel 在特定 GPU 上的性能瓶颈类型，并指导优化方向。

下面给出 Chapter 9 的整体概览，它由三个递进的子节点构成，建议按顺序学习。

---

## ① Formal Definition（形式化定义）

**Roofline 模型**（Roofline Model）是一种用于分析计算 Kernel 在特定硬件平台上性能上限的可视化与定量方法。它由 Samuel Williams 等人在 2009 年提出，核心思想是：

> Kernel 的实际性能（FLOPS）受限于两个“屋顶”：**峰值算力（Compute Roof）** 与 **峰值带宽（Bandwidth Roof）**，Kernel 的算术强度决定它撞在哪一个屋顶上。

形式化定义：

设硬件平台参数：

- 峰值算力 \(C_{peak}\)（FLOPS）
- 峰值显存带宽 \(B_{peak}\)（Bytes/s）
- 算力/带宽比：\(R = \frac{C_{peak}}{B_{peak}}\)（FLOPs/Byte），称为 **Ridge Point**（脊点）

对于一次 Kernel 执行：

- 总浮点运算量：\(F\)（FLOPs）
- 总数据搬运量：\(M\)（Bytes）
- 算术强度：\(I = \frac{F}{M}\)（FLOPs/Byte）

则该 Kernel 可达到的**理论上限性能**为：

\[

P_{roof} = \min\left(C_{peak},\ B_{peak} \times I\right)

\]

判别规则：

- 若 \(I < R\)：Kernel 处于 **Memory Bound** 区域，性能被带宽限制，GPU 算力闲置
- 若 \(I > R\)：Kernel 处于 **Compute Bound** 区域，性能被算力限制，带宽未打满

Roofline 图是一个以算术强度 I（对数）为横轴、可达到性能 P（对数）为纵轴的双区域图：左侧上升斜线（带宽墙），右侧水平线（算力墙）。

---

## ② System Design View（系统视角）

在整个训练系统中，Roofline 模型位于硬件层与 Kernel 实现层的交界处：

```
GPU 硬件参数 (C_peak, B_peak)
       │
       ▼
┌─────────────────────┐
│   Roofline 模型      │
│  · Ridge Point R    │
│  · Bandwidth Roof   │
│  · Compute Roof     │
└──────────┬──────────┘
           │
           ▼
  Kernel 算术强度 I (来自具体操作: GEMM, Softmax, LayerNorm...)
           │
           ▼
   判定: Compute Bound or Memory Bound?
     │                  │
     ▼                  ▼
  优化算力利用率     优化数据搬运
  (增加矩阵规模)     (Kernel Fusion, 分块计算)
```

**输入**：
- GPU 硬件峰值指标（来自 Chapter 5/22）
- 具体 Kernel 的 FLOPs 和 Bytes 搬运量（可静态分析或通过 Profiler 获取）

**输出**：
- 每个 Kernel 的瓶颈类型判定
- 优化建议：若 Memory Bound → 减少访存（融合、量化）；若 Compute Bound → 提高计算效率（Tensor Core 利用率）
- 为 FlashAttention、Kernel Fusion 等优化提供理论论证

**依赖关系**：
- 前承 4.2 FLOPs、5.2 GPU 存储体系、8.3 带宽瓶颈

## ④ Complexity Analysis（复杂度分析）

**Ridge Point 的典型值**（FP16 Tensor Core）：

| GPU | C_peak (TFLOPS) | B_peak (TB/s) | R (FLOPs/Byte) |
|-----|-----------------|---------------|-----------------|
| A100 SXM (80GB) | 312 | 2.0 | **156** |
| H100 SXM | 989 | 3.35 | **~295** |
| V100 SXM | 125 | 0.9 | **~139** |

Ridge Point 越高，意味着需要更高的算术强度才能将 Kernel 推向 Compute Bound。

**Transformer 各 Kernel 的算术强度**（回顾并补充）：

| Kernel | I (FLOPs/Byte, 典型值) | A100 上瓶颈 | H100 上瓶颈 |
|--------|-------------------------|-------------|-------------|
| 大 GEMM (m=n=k=4096) | ~1000-2000 | Compute | Compute |
| 中 GEMM (batch=64) | ~200-500 | Compute | 边界/Compute |
| Attention Score (Q×K^T, 大 s) | ~50-200 | 边界/Memory | Memory |
| LayerNorm / RMSNorm | ~1-5 | Memory | Memory |
| Softmax | ~1-3 | Memory | Memory |
| Element-wise (ReLU, Dropout) | ~0.5-2 | Memory | Memory |
| FlashAttention (分块) | 通过减少 M 提升有效 I，使其接近 Compute | 更高效 | 更高效 |

**Kernel Fusion 的有效算术强度提升**：
若将三个 Memory Bound 的 Kernel 融合（如 LayerNorm + Dropout + Add），中间数据不再写回 HBM，总 M 下降，I 上升，可能越过 Ridge Point 成为 Compute Bound，从而充分利用算力。

## ⑤ Design Trade-offs（权衡）

**Trade-off 1：通用优化方向**
- Memory Bound Kernel：目标不是提高计算效率，而是**减少数据搬运**或**提高带宽利用率**（如使用 Shared Memory、提高读取连续性）。
- Compute Bound Kernel：目标不是减少访存，而是**提高计算效率**（如使用 Tensor Core、提高 Occupancy、避免 Bank Conflict）。

**Trade-off 2：Ridge Point 随硬件变化**
- 从 A100 到 H100，算力提升（3.2x）远超带宽提升（1.7x），Ridge Point 从 156 升至 ~295。这意味着在 H100 上，更多的 Kernel 会掉入 Memory Bound 区域。
- 因此，在 H100 上，Kernel Fusion 和 FlashAttention 等减少 HBM 访存的技术变得更加关键。

**Trade-off 3：理论模型与实际行为的差距**
- Roofline 假设数据搬运都达到峰值带宽，实际中因非连续访问、Bank Conflict 等，有效带宽远低于峰值。
- 算力上限假设 100% Tensor Core 利用率，实际因 Tile Size 不匹配、Warp 调度等也很难达到。
- 因此，Roofline 给出的是**上限**，实际优化需结合 Profiler 精确定位。

**Trade-off 4：优化成本与收益**
- 对于 Memory Bound 的 Kernel，融合或重写为 Custom CUDA Kernel 成本高，但收益明显（如 FlashAttention 将 Attention 整体性能提升 2-4x）。
- 对于 Compute Bound 的大 GEMM，优化空间有限（cuBLAS 已高度优化），精力应放在通信、数据流水线等系统层面。
