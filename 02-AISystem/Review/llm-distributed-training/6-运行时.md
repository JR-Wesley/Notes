# 6 运行时

## 展开 17.1：Process 与 Rank

---

### ① Formal Definition（形式化定义）

在分布式训练中，**Process（进程）** 是操作系统层面的一个独立执行实例，拥有独立的地址空间和显存上下文。一个典型的分布式训练作业由 $N$ 个进程组成，每个进程通常独占一个 GPU 设备，独立运行模型副本的全部或部分计算逻辑，并通过进程间通信库（如 NCCL、Gloo）进行数据交换。

**Rank** 是分配给每个进程的全局唯一整数标识符，取值范围为 $0, 1, \dots, N-1$。它用于在通信操作中精确寻址：指定数据发往哪个进程（`dst=rank`），或从哪个进程接收（`src=rank`）。Rank 是整个分布式系统的最基本寻址单元。

与 Rank 相关的关键概念：

- **World Size（$W$）**：参与当前分布式训练作业的进程总数，即 $N$。
- **Local Rank**：进程在其所在计算节点（机器）内部的编号，通常等于该进程绑定的 GPU 编号（如 `local_rank=0` 表示使用本机第一块 GPU），用于在单机内定位设备。
- **Global Rank**：即 Rank，在整个作业中唯一。
- **Node Rank / Host Rank**：节点在多机集群中的编号，常通过 `GROUP_RANK` 或 `NODE_RANK` 等环境变量获取，用于构建分层通信拓扑。

形式化，分布式作业启动时，会通过外部启动器（如 `torchrun`、`mpirun`）为每个进程注入一组环境变量，进程在调用 `init_process_group()` 时使用这些变量确定自己的身份和通信后端。这些环境变量构成了 Rank 的绑定信息。

---

### ② System Design View（系统视角）

Process 与 Rank 位于 Runtime 层的最底层，是整个分布式训练系统组织计算和通信的基础，所有并行策略（DP、TP、PP）和通信域（Process Group）都建立在 Rank 的概念之上。

**在整个训练系统中的位置**：

```
硬件层 (GPU, 网络)
    │
    ▼
启动器 (torchrun / mpirun) 分配 Rank, World Size, 注入环境变量
    │
    ▼
进程初始化 (init_process_group) ──► 构建通信后端 (NCCL/Gloo)
    │
    ▼
Rank 标识建立 ──► 划分 Process Group (17.2)
    │
    ▼
并行策略寻址 (DP: 按 rank 切分数据; TP: 按 rank 切分权重; PP: 按 rank 指派层段)
```

**输入**：
- 启动命令指定的进程数（`-n` / `--nproc_per_node`）。
- 硬件拓扑：每个节点上的 GPU 数量，节点内 GPU 互联方式。
- 用户定义的初始化方法（`tcp://...` 或共享文件系统）。

**输出**：
- 每个进程确定的 `world_size`、`rank`、`local_rank`。
- 已初始化的默认 Process Group（`WORLD` 组），为后续并行通信提供默认通信域。
- 绑定到本地 GPU 的设备上下文（`torch.cuda.set_device(local_rank)`）。

**依赖关系**：
- 是所有通信操作（14.1 P2P, 14.2 Collective）的前置条件：通信必须基于 Rank 来指定源和目标。
- 是 Process Group（17.2）构建的基础：Group 就是 Rank 的子集。
- 与 17.3 CUDA Stream 协作：每个进程内独立管理 Stream，不同进程的 Stream 互不干扰。
- 上层并行策略（如 Megatron 的 `mpu.initialize_model_parallel`）会依据 Rank 和 world size 划分 TP、PP、DP 组。

**设计目标**：
- 为每个计算单元（GPU）提供一个逻辑上的独立控制流。
- 确保通信库可唯一标识每个端点，实现高效的数据交换。
- 通过 Local Rank 与 GPU 设备绑定，最大化本地显存带宽和计算资源。

### ③ Implementation Mapping（工程映射）

**PyTorch 分布式初始化**：

使用 `torch.distributed.init_process_group` 初始化默认进程组。典型流程：

1. 启动命令（`torchrun`）：

```bash
torchrun --nproc_per_node=8 --nnodes=2 train.py
```

`torchrun` 会自动设置以下环境变量：

- `LOCAL_RANK`：节点内 GPU 编号 (0–7)
- `RANK`：全局 rank (0–15)
- `WORLD_SIZE`：16
- `MASTER_ADDR`、`MASTER_PORT`：主节点通信地址

2. 训练脚本中获取这些变量并初始化：

```python
import os
import torch
import torch.distributed as dist

def setup():
    local_rank = int(os.environ['LOCAL_RANK'])
    rank = int(os.environ['RANK'])
    world_size = int(os.environ['WORLD_SIZE'])
    
    torch.cuda.set_device(local_rank)
    dist.init_process_group(
        backend='nccl',
        init_method='env://',
        world_size=world_size,
        rank=rank
    )

def cleanup():
    dist.destroy_process_group()
```

**Megatron-LM**：
- Megatron 在 `megatron/training/initialize.py` 中封装了初始化逻辑。
- 它调用 `torch.distributed.init_process_group`，并额外调用 `mpu.initialize_model_parallel` 划分 TP、PP、DP 通信组，这些划分基于 `rank` 和 `world_size` 计算。
- 例如，TP 组大小 `tensor_model_parallel_size` 将连续的 rank 组成一组。通过 `rank // tp_size` 等计算实现。

**DeepSpeed**：
- DeepSpeed 通过 `deepspeed.initialize()` 内部调用分布式初始化。用户通常先调用 `torch.distributed.init_process_group`，然后传入模型到 DeepSpeed。
- DeepSpeed 也可通过 `deepspeed.initialize` 的 `config` 自动检测 rank 和 world size。

**进程与 GPU 绑定的重要性**：
- 如果 `torch.cuda.set_device(local_rank)` 未正确调用，每个进程可能默认使用 GPU 0，导致多进程争抢同一 GPU，资源冲突且性能极差。
- `LOCAL_RANK` 与环境变量 `CUDA_VISIBLE_DEVICES` 配合，确保每个进程只能看到自己的 GPU（常见于 `mpirun` 方式）。

**替代启动方式**：
- `mpirun`（OpenMPI）：设置 `OMPI_COMM_WORLD_RANK`、`OMPI_COMM_WORLD_SIZE` 等，PyTorch 可从环境变量中自动读取。
- `SLURM`：使用 `srun`，自动设置 `SLURM_PROCID`、`SLURM_LOCALID` 等。

### ④ Complexity Analysis（复杂度分析）

Process 与 Rank 本身作为元信息，不产生显存或计算开销，但其数量（World Size）直接影响通信和调度复杂度。

**启动开销**：
- 启动 $N$ 个进程，每个进程加载 Python 环境、模型、通信库初始化。在数千卡规模下，启动时间（包括 NCCL 拓扑探测、建立连接）可能达到数分钟，成为工程问题。优化手段包括利用 `NCCL_DEBUG=INFO` 分析瓶颈，或采用持久化进程池。

**通信规模扩展**：
- 所有集合通信（AllReduce 等）的时间复杂度与 world size $N$ 相关（如 Ring AllReduce 步数为 $2(N-1)$，延迟项随 $N$ 线性增长）。因此，World Size 决定了通信域的规模，进而影响扩展效率。
- 分层通信（15.3）通过将大的 world 分组来缓解这个问题，但其分组基于 rank 的分布（如连续 rank 在同一个节点）。

**Rank 的局部性与通信带宽**：
- 相邻 rank（如 rank 0 和 rank 1）如果在同一节点，则享有机内高带宽 NVLink；若在不同节点，则使用较低带宽的 InfiniBand。因此，并行策略的通信组划分严重依赖 rank 的分配方式（连续 rank 分配在同一节点）。`torchrun` 默认就是连续分配 local rank。

**进程间负载均衡**：
- 如果某些进程的计算任务更重（如数据不均或模型分片不均），则会造成 straggler 效应，其他进程在集合通信中等待。因此，Rank 机制要求各进程的计算、通信尽量均衡。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：单进程 vs 多进程**
- 分布式训练强制每个 GPU 一个进程，利用进程隔离获得独立显存空间和 CUDA 上下文，避免 GIL（全局解释器锁）等问题。多进程模型使得每个 GPU 的计算完全并行，是当前主流。
- 单进程多线程难以在 Python 中实现高效的多 GPU 并行，因为 GIL 限制和 CUDA 上下文管理复杂，已被摒弃。

**Trade-off 2：Rank 的静态 vs 动态分配**
- 当前框架采用静态分配：训练开始前由启动器确定各进程的 rank，整个训练过程中不变。这简化了通信域管理，保证可靠性。
- 动态加入或移除进程（弹性训练）可以在节点故障时调整 world size，但需要重新初始化通信组和平衡负载，实现复杂。Pytorch Elastic (`torchrun` 的弹性模式) 支持这一功能，但会引入额外的重新划分开销。

**Trade-off 3：Local Rank 与全局 Rank 的转换**
- 通信库操作使用全局 rank，而 GPU 设备设置使用 local rank。在代码中需要不断在两者之间转换（例如 `global_rank = node_rank * nproc_per_node + local_rank`）。
- 多节点时，通过 `MASTER_ADDR` 指定的主节点 rank 必须为 0，这通常要求主节点的 global rank 0 进程充当协调者。

**Trade-off 4：进程数 vs GPU 利用率**
- 每个 GPU 一个进程是默认选择，但在某些场景（如 GPU 显存极大，需多进程共享一 GPU？极少见）或超大模型推理时，可能在一个 GPU 上运行多个进程（如 GPU 切分为 MIG 实例）。训练中一般不这样，因为 GPU 计算和显存资源会被多进程争抢。
- 进程数等于总 GPU 数，直接决定了通信域的大小，进而影响扩展效率。

**Trade-off 5：初始化方法选择（env:// vs tcp://）**
- `env://` 依赖环境变量，适合所有主流启动器，简洁通用。
- `tcp://` 需手动指定 IP 和端口，灵活性高但配置复杂，常用于调试或特殊网络环境。
- `file://` 通过共享文件系统同步，很少用于训练。

**Trade-off 6：Rank 与并行策略的映射**
- 3D 并行中，TP、PP、DP 组的建立依赖于 rank 的代数拆分。例如，常见的排列顺序是 [TP, PP, DP]，即 rank 先按 TP 切，再按 PP 切，最后按 DP 切。这种映射决定了通信的局部性，直接影响性能。需要在初始化时精心设计 `mpu` 划分，确保高带宽通信域内为相邻 rank。

## 展开 17.2：Process Group（进程组）

---

### ① Formal Definition（形式化定义）

**Process Group（进程组）** 是分布式通信中定义通信范围的核心抽象。它是参与集合通信（Collective Communication）的一组进程（Rank）的子集，并赋予组内每个进程一个从 0 开始连续编号的**组内 Rank**（Group Rank）。所有集合通信操作（AllReduce、AllGather 等）都严格在一个 Process Group 的范围内执行，不同 Process Group 之间的通信完全隔离。

形式化定义：给定全局世界 $ \mathcal{W} $ 包含 $ N $ 个进程，全局 Rank 为 $ 0,1,\dots,N-1 $。一个 Process Group $ G $ 由 $ \mathcal{W} $ 的一个有序子集构成：

$$

G = (r_0, r_1, \dots, r_{k-1}),\quad k \leq N

$$

组内进程 $ r_i $ 的组内 Rank 为 $ i $。同一个进程可以同时属于多个 Process Group（例如，一个 GPU 既属于 TP 组，又属于 DP 组，还属于 PP 组）。每个 Process Group 在底层通信库（如 NCCL）中都会建立独立的通信域（communicator），管理连接、拓扑和算法选择。

核心特性：

- **隔离性**：不同 Process Group 内的集合通信互不干扰，可以并发执行（但共享物理带宽）。
- **局部性**：通常将具有高带宽链路的进程（如同一节点内的 GPU）划分为同一组，以最大化通信效率。
- **层次性**：可以构建多级组，对应混合并行中的 TP、PP、DP、EP 等维度，形成“组中组”的嵌套或交叉关系。

Process Group 是分布式训练框架实现混合并行的**核心组织机制**。

---

### ② System Design View（系统视角）

Process Group 位于 Runtime 层，连接 Rank 标识（17.1）与具体并行策略的通信需求。它是并行策略空间与物理进程空间的**映射桥梁**。

**在整个训练系统中的位置**：

```
进程初始化 (17.1) 确定全局 Rank
       │
       ▼
划分 Process Groups ────► 定义通信域 (TP组, PP组, DP组, ...)
       │
       ▼
并行模块 (模型层) 使用特定 group 调用通信原语
       │
       ▼
NCCL 根据 group 内的拓扑选择算法执行通信
```

**输入/输出/依赖**：
- **输入**：
  - 全局 World Size 和 Rank 分配（17.1）。
  - 并行策略配置：TP 大小 $ T $，PP 大小 $ P $，DP 大小 $ D $（通常 $ T \times P \times D = W $）。
  - 硬件拓扑信息（哪些 Rank 在同一节点，用于局部性优化）。
- **输出**：
  - 一组 Process Group 对象，分别代表 TP、PP、DP 等通信域。
  - 每个组内成员列表和组内 Rank。
- **依赖**：
  - 底层通信库（NCCL）支持创建多个 communicator。
  - 需要确保同一组内所有进程同时调用 `new_group()`，否则会死锁。

**设计目标**：
- **最小化跨慢速链路的通信**：将 TP 组限制在机内，DP 组可跨节点，PP 组通常也尽量节点内。
- **通信域并行的独立性**：不同组的通信操作可以重叠执行而不混淆。
- **简化上层逻辑**：上层模型代码只需向指定 group 发起通信，而无需关心物理拓扑。

**典型的 3D 并行分组方式**（Megatron 风格）：
设 GPU 总数为 $ W = T \times P \times D $。全局 Rank 按 `[TP, PP, DP]` 顺序交织。则：
- **TP 组**：连续 $ T $ 个 Rank 为一组，共 $ P \times D $ 个 TP 组。
- **PP 组**：跨步 $ T $ 选择 Rank，每 $ P $ 个构成一组，共 $ T \times D $ 个 PP 组。
- **DP 组**：跨步 $ T \times P $ 选择 Rank，每 $ D $ 个构成一组，共 $ T \times P $ 个 DP 组。

这种排列保证了 TP 组内 Rank 物理相邻（同节点），PP 组相邻 Rank 也在同节点，DP 组均匀跨节点。

### ③ Implementation Mapping（工程映射）

#### a) PyTorch 原生 Process Group 管理

PyTorch 通过 `torch.distributed` 提供 Process Group 的创建和使用。

**创建新 Process Group**：

```python
import torch.distributed as dist

# 创建包含指定 rank 的新组 (所有进程需同时调用，ranks 列表必须全局一致)
new_group = dist.new_group(ranks=[0, 1, 4, 5])

# 查询组信息
group_size = dist.get_world_size(group=new_group)
group_rank = dist.get_rank(group=new_group)
```

**在通信操作中使用**：

```python
dist.all_reduce(tensor, group=new_group)
dist.all_gather(gather_list, tensor, group=new_group)
```

**内置默认组**：
- `dist.group.WORLD`：包含所有进程，默认组。
- 若未指定 `group` 参数，所有集合操作在 WORLD 组上执行。

**DDP 指定 Process Group**：

```python
model = DDP(model, process_group=dp_group)
```

使得梯度同步仅在该 DP 组内进行。

#### b) Megatron-LM 的 Process Group 体系

Megatron 在 `megatron/core/parallel_state.py` 中实现了完整的组管理。核心步骤：

1. **初始化模型并行**：`mpu.initialize_model_parallel(tensor_model_parallel_size, pipeline_model_parallel_size)`
   根据 `torch.distributed.get_rank()` 和 `get_world_size()` 计算出每个 Rank 所属的 TP、PP、DP 组，并调用 `dist.new_group` 创建这些组。

2. **存储为全局变量**：
   - `_TENSOR_MODEL_PARALLEL_GROUP`
   - `_PIPELINE_MODEL_PARALLEL_GROUP`
   - `_DATA_PARALLEL_GROUP`
   - 以及相应的 `_MPU_TENSOR_MODEL_PARALLEL_WORLD_SIZE` 等。

3. **访问函数**：

   ```python
   from megatron.core import mpu
   tp_group = mpu.get_tensor_model_parallel_group()
   dp_group = mpu.get_data_parallel_group()
   ```

4. **通信操作封装**：Megatron 的 `communication.py` 中的函数（如 `_AllReduce`）内部会根据当前需要自动选择正确的 group（例如 TP 相关的 AllReduce 在 TP group 上执行）。

5. **混合并行中的 nested groups**：Megatron 还会创建如 `_PIPELINE_MODEL_PARALLEL_RANK` 等辅助变量。DP 组是在 TP+PP 子组之外的剩余维度上构建。

#### c) DeepSpeed 的 Process Group

DeepSpeed 利用 Megatron 的组管理或自行构建（如果未使用 Megatron）。在 ZeRO 初始化中，DeepSpeed 会创建 **ZeRO 优化所需的 DP 组** 或继承已有的 DP 组。此外，DeepSpeed 还管理 Expert Parallel Group（当使用 MoE 时）。

- 在 `deepspeed/runtime/engine.py` 初始化时，如果检测到模型并行，会调用 `deepspeed/utils/groups.py` 中的辅助函数创建组。
- `deepspeed.comm` 模块提供了类似 `dist` 的通信 API，但内部会自动选择正确的组（例如在 TP 组内执行 allreduce）。

#### d) 关键工程细节

- **创建 Process Group 的同步要求**：`dist.new_group()` 必须在**所有进程**上同时调用，并传入相同的 rank 列表（即使某个进程不在该组内，也必须调用但传入空列表或 `ranks=[]`，此时返回 `None`）。这是最容易出错的点。
- **组内通信与全局通信的隔离**：确保模型不同部分的通信发生在正确的组内，否则可能导致死锁或错误结果。
- **组的销毁**：通常不需要显式销毁，进程结束时清理。

### ④ Complexity Analysis（复杂度分析）

Process Group 本身是逻辑概念，其开销主要体现在通信库初始化和运行时选择。

**初始化开销**：
- 每创建一个 Process Group，NCCL 会在组内各 GPU 间建立连接和探测拓扑。组数量为 $O(\text{并行维度数})$，通常不超过 3~4 个（TP, PP, DP, EP），初始化时间很短（相对于总训练时间可忽略）。
- 但是，在极大的 World Size（如 10000+ GPU）下，多个 Process Group 的建立可能导致连接风暴，NCCL 需要精细管理。

**通信复杂度**：
- 通信操作的复杂度取决于组大小（组内 $k$ 个成员），而不是世界大小 $W$。例如，TP 组的 AllReduce 仅在 $T$ 个 GPU 上进行，步数为 $2(T-1)$，远小于 $W$。这通过分组有效遏制了通信延迟的爆炸。
- 不同组的通信如果共享相同的物理链路（例如同节点内的 NVLink 同时被 TP 和 DP 组使用），会产生竞争，需要调度（如 CUDA Stream 优先级、NCCL 的通道分配）来缓解。这增加了复杂度的间接影响。

**显存开销**：
- 每个 Process Group 需要 NCCL 维护通信缓冲区（用于环形传输的中间存储）。缓冲区大小与组大小和数据量有关，但通常由 NCCL 内部管理，开销相对固定（几 MB 到几十 MB）。对于大模型，可忽略不计。

**扩展性**：
- Process Group 机制使得并行扩展可以分层进行：在节点内增加 TP 度，组大小增大但带宽极高；在节点外增加 DP 度，组大小增大但 DP 组通信通过分层（15.3）优化。这比所有 GPU 同在一个扁平通信域中线性扩展性好得多。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：组的粒度与通信效率**
- **粗粒度组**（如只有一个 WORLD 组）：实现最简单，但所有通信都发生在全局，极易受跨节点带宽限制，扩展性差。
- **细粒度多组**（TP/PP/DP 分层）：隔离不同特性的通信，优化匹配硬件拓扑，但组的管理和通信调度复杂，容易引入 bug。

**Trade-off 2：组划分与硬件拓扑的绑定**
- 理想情况下，TP 组应严格限制在 NVSwitch 全互联的 8 GPU 内，PP 组跨节点但要避免频繁 P2P，DP 组可利用跨节点分层 AllReduce。
- 如果组划分与物理拓扑不匹配（例如 TP 组跨了节点），通信时间可能暴增，导致训练极慢甚至不可用。这要求启动脚本和调度器正确分配 Rank。

**Trade-off 3：组的静态定义 vs 动态重划分**
- 当前主流框架采用静态组（训练开始前确定），简单可靠。
- 动态组（如在训练过程中调整 TP 度或 DP 度）理论上可适应负载变化或弹性扩缩，但需要销毁旧组、创建新组，并重新分布参数和优化器状态，实现极其复杂，目前极少使用。

**Trade-off 4：Process Group 与 ZeRO 的通信**
- ZeRO-2/3 需要 ReduceScatter 和 AllGather，这些在 DP 组内进行。DP 组通常较大（跨节点），通信代价高。通过分层通信（节点内 ReduceScatter，节点间 AllReduce）可缓解，但这又依赖于 Process Group 内的层次划分（需要在组内再分 subgroup），增加了实现难度。DeepSpeed 通过 `sub_group_size` 等参数控制。

**Trade-off 5：组的数量与 GPU 资源利用**
- 不同组的通信可能并发，如果过多组同时通信，会争抢 NVLink 或 IB 带宽，降低有效带宽。因此，调度器（如 Megatron 的流水线调度）会错开通信高峰，避免过度竞争。

**Trade-off 6：调试与可观测性**
- 多 Process Group 增加了调试难度：需要明确当前错误来自哪个组，NCCL 的日志可能包含组 ID 但不易解析。工程师通常为每组设置不同的 `NCCL_DEBUG` 环境变量或使用带组信息的 wrapper。

## 展开 17.3：CUDA Stream

---

### ① Formal Definition（形式化定义）

**CUDA Stream** 是 NVIDIA CUDA 编程模型中用于管理 GPU 操作（Kernel 执行与内存拷贝）**并发性**的核心抽象。一个 CUDA Stream 表示一个**严格串行**的命令序列：在同一个 Stream 内部，所有提交的操作按先进先出（FIFO）顺序依次执行。不同 CUDA Stream 之间的操作则可能**并发执行**（concurrent execution），具体并发程度由 GPU 硬件资源（SM、内存带宽、拷贝引擎等）的动态调度决定。

形式化定义：设 GPU 可以同时维护多个 CUDA Stream $S_0, S_1, \dots, S_k$。每个 Stream $S_i$ 内部维护一个命令队列。当用户向不同 Stream 提交操作时：

- **串行约束**：$\forall op_a, op_b \in S_i$，且 $op_a$ 先于 $op_b$ 提交，则 $op_a$ 必定在 $op_b$ 开始前完成。
- **并发可能**：若 $op_a \in S_i, op_b \in S_j\ (i \neq j)$，则它们可能被 GPU 的多个硬件单元（如不同的 SM 分区、DMA 拷贝引擎）同时执行，也可能因资源不足而串行化。

**默认 Stream（Default Stream）**：
- 当用户不显式指定 Stream 时，所有操作提交到默认 Stream。
- 现代 CUDA（自 CUDA 7 起）的默认 Stream 是“每线程默认流”，不同宿主线程的默认流相互独立，可以并发。传统默认流（旧式 `cudaStreamLegacy`）则有隐式全局同步特性，但在 PyTorch 和现代库中通常不使用。

**关键同步操作**：
- `cudaStreamSynchronize(stream)`：阻塞调用线程，直到该 Stream 中所有已提交操作完成。
- `cudaEvent`：可以在 Stream 之间插入事件，实现精确的点到点依赖控制。例如，在 $S_1$ 中记录一个 Event，在 $S_2$ 中等待该 Event，保证 $S_2$ 的某些操作在 $S_1$ 的某点之后才开始。

CUDA Stream 是实现 **Compute-Communication Overlap（16.2）** 的硬件基础：将通信操作放入与计算不同的 Stream，使它们可以并行执行，从而隐藏通信延迟。

---

### ② System Design View（系统视角）

CUDA Stream 位于 Runtime 层的执行调度核心，是连接上层并行调度策略（如 DDP Reducer、Megatron Scheduler）与底层硬件（SM、拷贝引擎）的桥梁。

**在整个训练系统中的位置**：

```
并行策略 (DP/TP/PP) 产生通信需求
       │
       ▼
调度机制 (18.1 Hook, 18.2 Reducer, 18.3 Scheduler) 决定通信时机
       │
       ▼
CUDA Stream 管理 ──────► 分配计算/通信到不同 Stream
       │
       ▼
GPU 硬件 (SM 执行 Kernel, DMA 引擎执行拷贝/NCCL)
```

- 上层调度器通过将计算 Kernel 提交到主 Stream（计算流），将 NCCL 通信操作提交到辅助 Stream（通信流），实现并行执行。
- Stream 的并发能力直接决定了重叠效率：拷贝引擎（Copy Engine）和计算单元（SM）可以独立工作，当 SM 忙于计算时，拷贝引擎可同时执行数据传输。
- 依赖关系由 Event 精确控制，确保通信在梯度就绪后开始，优化器更新在通信完成后进行。

**输入/输出/依赖**：
- **输入**：计算任务（前向/反向 Kernel）和通信任务（AllReduce/AllGather 等 NCCL 操作）。
- **输出**：并发执行的时间线，减少 wall-clock 空闲时间。
- **依赖**：
  - CUDA 设备支持并发执行（具备独立 DMA 引擎，现代 GPU 均有）。
  - NCCL 操作与 Stream 异步（`ncclAllReduce` 接受 CUDA Stream 参数）。
  - Autograd Hook（18.1）提供了在计算图中插入通信操作的时机。

**设计目标**：
- 最大化 GPU 利用率：让 SM 和 DMA 引擎同时忙碌。
- 最小化同步开销：仅在必要的数据依赖点插入 Event 同步，避免不必要的阻塞。
- 管理显存：异步操作需要保证输入/输出缓冲区在操作完成前不被覆盖。

---

### ③ Implementation Mapping（工程映射）

#### a) PyTorch 中的 CUDA Stream API

PyTorch 对 CUDA Stream 提供了 Python 封装：

```python
import torch

# 获取当前默认 Stream
default_stream = torch.cuda.current_stream()

# 创建独立 Stream
comm_stream = torch.cuda.Stream()

# 在指定 Stream 上执行操作
with torch.cuda.stream(comm_stream):
    # 此 with 块内的 CUDA 操作均提交到 comm_stream
    dist.all_reduce(tensor)

# 主 Stream 继续执行计算
# ... (计算 Kernel 在 default_stream 上运行)

# 同步点：等待通信完成
comm_stream.synchronize()
```

**关键 API**：
- `torch.cuda.Stream()`：创建一个新 Stream。
- `torch.cuda.current_stream()`：获取当前线程的当前 Stream。
- `torch.cuda.stream(stream)`：上下文管理器，将内部操作重定向到指定 Stream。
- `stream.synchronize()`：CPU 端阻塞直到 Stream 中所有操作完成。
- `event = torch.cuda.Event()` + `event.record(stream)` + `event.wait(other_stream)`：跨 Stream 的事件同步。

#### b) DDP 中的 Stream 使用

PyTorch DDP 的 `Reducer` 内部创建了一个专用的**通信 Stream**，与主计算 Stream 分离：

1. 当某桶梯度就绪，`Reducer` 会将桶内梯度的展平副本**提交到通信 Stream** 执行 AllReduce。
2. 主计算 Stream 继续执行后续层的反向传播计算。
3. AllReduce 完成后，通信 Stream 上记录一个 Event，优化器步骤前在主 Stream 等待该 Event。

这样，反向计算与梯度通信实现了重叠。DDP 的实现细节封装在 C++ 层（`torch/csrc/distributed/c10d/reducer.cpp`），不直接暴露 Stream 给用户，但提供了 `DDP(..., gradient_as_bucket_view=True)` 等选项影响 Stream 内缓冲区的管理。

#### c) Megatron 的通信 Stream

Megatron-LM 在 `megatron/core/tensor_parallel/communication.py` 中为 TP 通信管理了独立的 CUDA Stream。例如，`RowParallelLinear` 的正向 AllReduce 和 Column Parallel 的反向梯度 AllReduce 可能被调度到通信流上，与 LayerNorm、残差加等计算重叠。

Megatron 还利用 Event 进行精确的跨 Stream 同步，确保数据依赖正确。

#### d) DeepSpeed 的 Stream 调度

DeepSpeed 在 ZeRO 实现中大量使用多 Stream 进行重叠：

- **参数预取**：后台 Stream 执行 AllGather 收集下一子层参数，当前 Stream 执行计算。
- **梯度 ReduceScatter**：在独立 Stream 上执行，与反向计算重叠。
- DeepSpeed 通过 `deepspeed/runtime/zero/stage3.py` 中的 `DeepSpeedZeroOptimizer_Stage3` 管理这些 Stream 和 Event。

#### e) 工程关键细节

- **默认 Stream 的陷阱**：PyTorch 使用“每线程默认流”，不同 Python 线程创建的 Tensor 操作可能在不同 Stream。但在典型训练中，所有 GPU 操作在主线程，使用同一默认 Stream，行为确定。显式多 Stream 管理需注意流切换开销和同步正确性。
- **显存复用与异步**：若某个 Tensor 在通信完成前被释放或修改，会导致数据竞争或错误结果。必须通过 Event 同步或 `stream.synchronize()` 保证生命周期。
- **NCCL 与 Stream**：所有 `torch.distributed` 的通信操作均异步于当前 Stream（在 PyTorch 中，通信操作提交到当前 Stream，不阻塞 CPU）。使用 `async_op=True` 可以返回一个 `Work` handle，控制同步粒度。

### ④ Complexity Analysis（复杂度分析）

CUDA Stream 本身不产生显存或计算开销，其核心复杂度在于**并发调度**和**同步管理**。

**硬件并发能力**：
- GPU 的 SM 可以同时执行来自不同 Stream 的 Kernel（通过线程块调度）。
- **拷贝引擎**（Copy Engine）与 SM 独立：在执行计算 Kernel 的同时，DMA 引擎可以传输数据（HBM ↔ 网络/NVLink）。这为 Compute-Communication Overlap 提供了物理基础。
- 但拷贝引擎数量有限（通常 1-2 个），如果多个 Stream 同时发起大量传输，它们会串行排队。此外，HBM 带宽被计算（load/store）和通信（DMA）共享，Memory Bound Kernel 与通信并发时可能互相拖慢。

**Stream 同步开销**：
- Event 记录和等待：每个 Event 的创建、记录和等待本身有微小 GPU 开销（几十 ns 到几 µs），但在大量短操作下频繁同步可能累积。
- CPU-GPU 同步（`synchronize`）会阻塞 CPU 线程，如果过早同步，会浪费 CPU 端的重叠机会。

**重叠效率分析**：
- 有效的重叠要求计算和通信在时间上重叠足够的区域。这取决于计算 Kernel 的类别（Compute Bound vs Memory Bound）和通信的消息大小。
- 对于 Compute Bound 的大矩阵乘，与通信重叠效果极佳，因为 SM 忙碌，带宽未被计算充分占用，通信可充分利用带宽。
- 对于 Memory Bound 的逐元素操作，计算已经与带宽竞争，再并发通信可能相互拖慢，重叠收益有限甚至为负。

**扩展性**：
- 随着 GPU 数量增加，通信时间占比上升，重叠的价值更大。但通信时间可能超过计算时间，此时即使完全重叠，总时间仍由通信主导，此时应优化通信本身而非仅依赖重叠。

---

### ⑤ Design Trade-offs（权衡）

**Trade-off 1：多 Stream 的收益 vs. 管理复杂度**
- 多 Stream 带来重叠机会，但增加了同步错误和资源竞争的风险。调试异步问题（如 race condition）非常困难。
- 通常仅在明确的通信热点（DDP AllReduce、ZeRO 预取）使用有限数量的附加 Stream（1-2 个），而非为每层创建。

**Trade-off 2：显存占用 vs. 重叠效果**
- 异步通信需要额外缓冲区：通信操作在其完成前，输入/输出张量不能被覆盖。DDP 的分桶视图（`gradient_as_bucket_view`）可避免复制，但如果不能使用视图，则需要为通信分配额外显存。
- 更长的重叠窗口需要更早启动通信（使用更大缓冲区或提前触发），可能增加峰值显存。

**Trade-off 3：Event 同步 vs. Stream 串行化**
- 使用 Event 细粒度同步可以最大限度并发，但出错可能导致数据竞争。
- 有些时候，简单地将所有操作放在同一 Stream（串行化）更安全，虽然无重叠，但避免了调试复杂的异步 bug。在大模型开发初期，先确保正确性，再逐步引入重叠是常见策略。

**Trade-off 4：默认 Stream 的隐式同步**
- 旧版 CUDA 的“传统默认流”会对所有其他 Stream 产生隐式同步（当默认流操作开始时，等待其他 Stream 完成），这可能意外打破并发。现代 PyTorch/CUDA 使用“每线程默认流”，无此问题，但仍需注意与其他库（如旧版 cuBLAS）的交互。

**Trade-off 5：计算与通信的硬件资源竞争**
- 如果计算 Kernel 大量使用 HBM 带宽（Memory Bound），并发通信会与之争夺带宽，导致计算和通信均变慢，重叠可能无收益。需根据 Kernel 特征（Roofline 分析，Chapter 9）决定是否启用重叠。
- 对于完全 Compute Bound 的 Kernel（如大 GEMM），通信几乎不影响计算，重叠效果最好。

**Trade-off 6：调度顺序与 Stream 优先级**
- CUDA Stream 可以设定优先级（`torch.cuda.Stream(priority=...)`），影响 GPU 线程块调度。将通信流设为较高优先级，可以确保它获得足够的 DMA 和 SM 资源。但在 PyTorch 中，优先级支持有限，通常通过调整操作顺序来隐式控制。
