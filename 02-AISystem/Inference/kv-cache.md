# PD

## 问题 1：两个阶段

大型语言模型（LLM）自回归生成文本时，分为 **预填充（Prefill）阶段** 和 **解码（Decode）阶段**。

- 预填充阶段：把完整的提示文本（如问题、故事开头）一次性输入模型，计算得到第一个输出 token（词/字）。
- 解码阶段：从第二个 token 开始，每次用“刚生成的 token”作为输入，迭代生成下一个 token，直到文本生成结束（如遇到终止符号）。

## 问题 2：各阶段性能瓶颈

- **预填充阶段**：属于“计算密集型”瓶颈。需要一次性处理整个提示文本的所有 token，模型要并行完成大量注意力、矩阵运算等，计算量随提示长度线性增长，对算力要求极高。
- **解码阶段**：属于“内存带宽 + 延迟密集型”瓶颈。因自回归特性（下一个 token 依赖前一个），只能**串行生成 token**，无法并行加速；且每次生成都要访问大模型的海量参数，内存带宽开销大，导致延迟高、速度慢。

## 问题 3：主流优化技术

### 针对预填充阶段

- **模型量化**：降低模型参数的精度（如从 32 位浮点转 16 位浮点、甚至 8 位整数），减少计算量和内存占用，让算力更高效。
- **算子优化**：对核心计算（如注意力机制、矩阵乘法）做算法优化，比如用 `FlashAttention` 算法，减少不必要的计算，提升并行效率。
- **硬件加速**：利用 GPU、TPU 等专用 AI 硬件的并行计算能力，优化计算调度，让大规模矩阵运算更快完成。

### 针对解码阶段

- **KV 缓存（Key-Value Cache）**：预填充阶段缓存好“提示文本每个 token 的注意力中间结果（Key 和 Value）”，解码阶段只需要用“新生成的 token”和缓存结果计算，避免重复计算提示文本的开销，大幅减少计算量。
- **批处理（Batching）**：同时处理多个生成请求（如多个用户的对话生成），把多个序列的解码过程“合并”，提升硬件整体利用率（虽然单个序列还是串行，但整体吞吐量更高）。
- **投机解码（Speculative Decoding）**：先让小模型快速生成几个候选 token，再用大模型验证“候选是否正确”；正确的保留，错误的回退修正。通过减少大模型的迭代次数，降低延迟。
- **模型结构优化**：采用更高效的结构，比如 `MoE（混合专家）` 架构（解码时只激活部分“专家”，减少每次计算量），或轻量化 Decoder 设计。
