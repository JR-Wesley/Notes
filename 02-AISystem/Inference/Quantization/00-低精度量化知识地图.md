# 数值量化与低精度表示：知识地图

本文面向希望从数值原理一路理解到 AI Infra 实现的读者。目标不是罗列量化工具，而是建立一套可以分析数值格式、量化算法、内存布局、Kernel、GPU 指令与分布式数据路径的共同语言。本主题沿“数值表示 → 量化数学模型 → 量化方案 → 现代低精度格式 → 模型量化算法 → Kernel / Runtime → GPU 硬件 → 分布式 AI Infra”展开。

## 从一个系统问题开始

量化的直接目标，是用更少的 bit 表示 Tensor，在可接受的数值和任务误差下，降低持久容量、数据搬运与计算成本。以一个 70B 参数模型为例，仅计算权重的理想容量：

| 权重格式 | 每参数字节 | 70B 权重理想容量 |
| --- | ---: | ---: |
| FP32 | 4 B | 280 GB |
| FP16 / BF16 | 2 B | 140 GB |
| FP8 / INT8 | 1 B | 70 GB |
| FP4 / INT4 | 0.5 B | 35 GB |

真实 checkpoint 和运行时显存不会严格等于表中数值，因为还存在 scale、zero-point、padding、layout、KV cache、workspace、allocator fragmentation，以及训练时的 master weights、gradients 和 optimizer states。位宽给出的是 data payload 下界，而不是完整系统容量。

在低 batch autoregressive decode 中，每生成一个 token 都要读取大量权重，时间常近似受 HBM 搬运约束：

$$
T_{\mathrm{decode}}\gtrsim
\frac{B_{\mathrm{weight}}+B_{\mathrm{KV}}+B_{\mathrm{metadata}}}
{BW_{\mathrm{HBM}}}.
$$

量化可以降低分子；若 GPU 还提供匹配的低精度矩阵指令，它也可能抬高 compute ceiling。用 Roofline 语言表示：

$$
P=\min(P_{\mathrm{compute}},\ AI\times BW_{\mathrm{memory}}),
\qquad
AI=\frac{\mathrm{operations}}{\mathrm{bytes\ moved}}.
$$

减少 operand bytes 会提高 arithmetic intensity，原生低精度 Tensor Core 又可能提高 $P_{\mathrm{compute}}$。但 quantize、pack、metadata load、unpack、dequantize、shape padding 和不匹配的 Kernel 都会增加成本，因此“从 BF16 变成 INT4”不等于端到端必然快 4 倍。

对初学者，可以先把量化记成六个相互连接的问题：

$$
\text{Quantization}
=\text{Data Format}
+\text{Scale Strategy}
+\text{Granularity}
+\text{Calibration/Algorithm}
+\text{Kernel}
+\text{Hardware/System}.
$$

这条入门公式强调学习层次；下文的统一分析框架则把它细化为可检查任意论文和实现的数据合同。

## 统一分析框架

后续笔记使用下面的抽象描述一个完整方案：

$$
\text{Quantization Scheme}
=
\text{Partition}
+\text{Statistics}
+\text{Codebook}
+\text{Mapping}
+\text{Granularity}
+\text{Metadata}
+\text{Encoding/Storage}
+\text{Compute Contract}.
$$

其中，**Partition / Granularity** 决定哪些元素共享量化参数；**Statistics** 描述如何估计有效范围；**Codebook** 是可重建值的集合；**Mapping** 决定原值如何选择码字，包括 clipping 与 rounding；**Metadata** 保存 scale、zero-point 或 shared exponent；**Encoding / Storage** 规定码字和元数据如何落入内存；**Compute Contract** 则说明硬件是在计算前反量化，还是直接执行原生低精度矩阵运算，以及采用何种累加精度。

统一数据路径为：

$$
X \rightarrow \text{partition} \rightarrow \text{statistics/range}
\rightarrow \text{metadata} \rightarrow \text{normalize}
\rightarrow \text{encode} \rightarrow Q \rightarrow \text{pack/store}
\rightarrow \text{load/unpack} \rightarrow \text{decode}
\rightarrow \text{compute} \rightarrow \text{accumulate/output}.
$$

学习具体格式时，不仅记录位宽，还要沿这条路径回答三个问题：误差在哪里引入，额外字节在哪里产生，硬件在哪里真正获得收益。教学用名称（如 `INT8_BLOCK128`）与标准或框架定义的正式类型必须明确区分。

## 分类维度

量化方案是多维设计空间，以下概念不能放在同一棵互斥分类树中。

| 分类轴 | 描述的问题 | 典型取值 |
| --- | --- | --- |
| Quantized object | 量化什么 | weight、activation、KV cache、gradient、optimizer state、communication buffer |
| Partition / granularity | 哪些元素共享参数 | per-tensor、per-channel、per-token、per-group、block |
| Statistics / calibration | 如何估计有效范围 | absmax、min-max、percentile、MSE、KL、运行时 amax |
| Codebook | 可以重建哪些值 | integer lattice、floating-point values、NF4 table、MX element format |
| Mapping | 如何选择码字 | uniform/non-uniform、nearest、stochastic rounding、clipping |
| Zero alignment | 数值零如何对齐 | symmetric、asymmetric、zero-point |
| Parameter timing | 参数何时产生 | static、dynamic、delayed scaling、online scaling |
| Metadata | 解码需要什么旁信息 | scale、zero-point、shared exponent、group shape、type tag |
| Storage | bits 如何落入内存 | byte-native、nibble packing、vector packing、scale interleave、alignment |
| Compute contract | 计算如何消费表示 | pre-dequantize、fused dequant-GEMM、native low-precision MMA、accumulator type |
| Optimization stage | 模型何时适应误差 | PTQ、QAT、quantization-aware fine-tuning |

因此，`INT4` 主要约束 element codebook 与 encoding，但不会自动说明对称性、group size 或 scale 类型；`per-block` 只说明参数共享范围，不说明 block 内采用整数、浮点还是查表码字；`static/dynamic` 说明统计量或量化参数的产生时机，不等同于 PTQ/QAT。MXFP4 则是一种由规范定义的复合表示：低精度 element format 与块级 shared scale 共同构成其数值语义，不能简化为“带 scale 的普通 INT4”。

## 分阶段学习与掌握标准

本系列按“先形成直觉，再建立形式模型，最后进入实现”的顺序使用，而不是一开始钻入 GPTQ 的矩阵推导。

| 阶段 | 阅读范围 | 应能完成的任务 | 暂不要求 |
| --- | --- | --- | --- |
| 入门直觉 | 00–02 | 解释位宽、scale、zero-point、rounding、clipping；手写 INT8/INT4 fake quantizer | 论文算法和 CUDA 优化 |
| 方案分类 | 03 | 从多个独立分类轴描述方案；计算 metadata overhead | 背诵框架枚举值 |
| 现代格式 | 04 | 区分 FP8、FP4、MXFP4、NVFP4 及 shared scale | 立即掌握 PTX layout |
| 对象策略 | 05 | 分析 W/A/KV/gradient 为什么采用不同策略 | 假定一个方案适用所有 Tensor |
| 算法理解 | 06 | 比较 RTN、SmoothQuant、GPTQ、AWQ、PTQ 与 QAT | 只记方法名称和排行榜 |
| 工程实现 | 07–09 | 追踪 pack/load/decode/MMA/accumulate 的实际数据路径 | 用理论位宽替代 benchmark |
| 系统综合 | 10–12 | 分析 serving、TP/EP 通信与前沿格式的端到端权衡 | 脱离硬件和 workload 下结论 |

完成 00–03 后，应能不查定义回答以下问题：为什么 INT4 不能直接表达任意小数；scale 与 zero-point 各自改变什么；symmetric/asymmetric 与 uniform/non-uniform 为什么不是同一分类轴；group size 变小为何通常改善局部表示却增加 metadata；W4A16 中哪些对象是 4 bit、16 bit 和 accumulator precision；为什么 checkpoint 缩小不保证等比例加速；为什么 weight-only 对低 batch decode 特别有吸引力；以及为什么 activation 的量化通常比静态 weight 更依赖数据分布。

整个学习过程保留一个共同实践原则：先以 RTN 和 reconstruction error 建立 baseline，再逐步加入 outlier、细粒度、算法补偿和 Kernel。复杂方法的价值应相对于简单 baseline 解释，而不是单独记忆。

## 来源策略

资料按“标准定义 → 厂商实现 → 框架／源码行为 → 研究方案 → 实验结果”分层使用。格式的数值语义优先引用标准；指令、数据类型和支持矩阵引用对应版本的厂商文档；算法机制引用论文；实际布局和融合路径以源码与可复现实验为准。厂商格式、OCP MX 标准与论文自定义格式即使名称相近，也不默认视为相同。

当前系列的初始一手来源包括 [OCP Microscaling Formats (MX) v1.0](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf)、[NVIDIA CUDA Math API](https://docs.nvidia.com/cuda/cuda-math-api/)、[NVIDIA CUDA Programming Guide](https://docs.nvidia.com/cuda/cuda-programming-guide/)、[SmoothQuant](https://arxiv.org/abs/2211.10438) 以及 [Post Training Quantization of Large Language Models with Microscaling Formats](https://arxiv.org/abs/2405.07135)。具体笔记只列实际用于支持正文的来源，并注明版本或适用硬件；不把研究结果写成标准要求，也不把 API 中存在某个 storage type 等同于所有 GPU 都能原生计算该格式。
