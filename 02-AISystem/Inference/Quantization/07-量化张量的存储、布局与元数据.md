# 量化张量的存储、布局与元数据

量化 Tensor 不是一个“换了 dtype 的普通数组”，而是一组必须共同解释的数据：

$$
\mathcal{T}_q=(B_Q,B_M,\Sigma),
$$

其中 $B_Q$ 是 quantized codes 的 bitstream，$B_M$ 是 scale、zero-point 或 codebook 等 metadata 的存储，$\Sigma$ 是描述 shape、partition、dtype、packing、layout、alignment 和版本的 schema。缺少其中任一部分，都可能无法把 bytes 唯一恢复为逻辑 Tensor。

本篇把 [[02-量化的统一数学模型]] 和 [[03-量化方案的分类维度与粒度]] 落到内存层：从 logical code 出发，经过 pack、padding、layout transform 和 serialization，到 Kernel load/unpack。重点不是背某个框架的字段名，而是建立一套能读 checkpoint、Tensor subclass 与 CUDA Kernel 的共同语言。

## 五种容易被统称为 layout 的对象

| 层次 | 描述对象 | 典型问题 |
| --- | --- | --- |
| Logical Tensor layout | Tensor 的逻辑 shape、axis 与索引语义 | $W[M,K]$ 中哪个轴是 output channel？ |
| Quantization layout | 哪些元素共享 metadata | 沿 K 每 128 个 weight 是否共享 scale？ |
| Bit packing layout | code bits 怎样组成 byte/word | INT4 的第一个 code 位于低 nibble 还是高 nibble？ |
| Runtime/prepacked layout | 为 load、warp 和 MMA 预先怎样重排 | 是否 tile、transpose、interleave、swizzle？ |
| Container layout | Tensor、metadata、offset 和 alignment 怎样写入文件 | checkpoint 能否 mmap、分片、版本化？ |

同一个逻辑矩阵可以拥有多个物理布局。一个 portable checkpoint 可以按 row-major 保存，加载时再 prepack 成某个 GPU Kernel 的专用布局；也可以直接保存 prepacked bytes，以减少启动时间但牺牲跨 backend 可移植性。讨论“layout”时必须标明所在层次。

## 从 Tensor 坐标到 byte address

普通 dense Tensor 用 shape、stride、storage offset 和 element size 将逻辑坐标映射到地址。对 row-major $W[M,K]$，若每元素正好占 $b$ byte，

$$
\operatorname{offset}(m,k)=mK+k,
\qquad
\operatorname{addr}=\operatorname{base}+b\,\operatorname{offset}.
$$

低于 8 bit 后，“每元素地址”不再总是整数 byte。更一般的做法是先计算 logical code index $i$，再映射到 storage unit 与 unit 内 bit position：

$$
u=\left\lfloor\frac{i}{P}\right\rfloor,
\qquad
r=i\bmod P,
$$

其中一个 storage unit 容纳 $P$ 个 code。对 4-bit code 和 8-bit byte，$P=2$；对把 8 个 INT4 装入 uint32 的实现，$P=8$。物理地址只定位 storage unit，$r$ 决定 shift 与 mask。

因此 sub-byte Tensor 的 logical stride 与 storage stride 必须分开。逻辑上的 K stride 是 1 element；物理上一行可能占 $\lceil K/2\rceil$ byte，也可能为了 vector load 被 padding 到 16、32 或 128 byte 对齐。

## INT4 packing：从有符号 code 到 nibble

### Signed value 与 4-bit pattern

Two's-complement signed INT4 的逻辑范围是 $[-8,7]$。编码为 unsigned nibble 时可写为

$$
u=q\bmod16,
\qquad u\in[0,15].
$$

解码时：

$$
q=
\begin{cases}
u,&u<8,\\
u-16,&u\ge8.
\end{cases}
$$

例如 $-2$ 的 nibble 是 1110，其 unsigned 解释为 14，但 signed decode 后为 $14-16=-2$。Bit extraction 只得到 $u$；signedness 是 schema 指定的解释规则。

### 两个 nibble 组成一个 byte

若约定第一个 code 放低 nibble，第二个放高 nibble，

$$
b=(u_0\mathbin{\&}0xF)
\;|\;
((u_1\mathbin{\&}0xF)\ll4).
$$

对逻辑序列

$$
[1,-2,5,7],
$$

nibble 依次为 [0x1, 0xE, 0x5, 0x7]，最终 bytes 为 [0xE1, 0x75]。若另一个格式采用 high-nibble-first，同一组数会产生不同 byte stream。二者的量化数学完全相同，却不是 binary-compatible。

解包 low-nibble-first byte 的逻辑过程是

$$
u_{2j}=b_j\mathbin{\&}0xF,
\qquad
u_{2j+1}=(b_j\gg4)\mathbin{\&}0xF,
$$

随后再做 signed decode。实际 Kernel 常一次加载 uint32、uint4 或更宽向量并并行提取多个 code，而不是逐 byte 循环；但 mask、shift、signed interpretation 的语义不变。

### Pack across rows 还是 pad each row

若 $W[M,K]$ 的 $K$ 为奇数，有两种合法合同：

1. 每行独立 packing，row bytes 为 $\lceil K/2\rceil$，最后一个高 nibble padding；
2. 把矩阵视为一条连续 code stream，下一行首元素可以占用上一行末 byte 的另一个 nibble。

第一种让 row address 简单且适合矩阵 tile，代价是每行最多浪费半个 byte；第二种 payload 更紧凑，却让行首可能不在 byte boundary。不能只从文件大小猜测合同，schema 必须记录 packing traversal 与 tail rule。

## Quantization group 与 packing group 相互独立

设权重沿 K 轴 group size 为 $G=128$。Quantization group 表示 128 个 code 共享一份 scale；packing group 可能只是每 2 个 code 一个 byte，或每 8 个 code 一个 uint32。于是一个 quantization group 可以对应 64 byte、16 个 uint32，但“128、64、16”分别属于不同层次。

若 group boundary 与 packing boundary 对齐，Kernel 可以在加载一段 packed data 时只使用一份 scale。若 $G$ 不是 packing width 的倍数，某个 storage unit 可能跨越两组，解码时需要额外 predicate 或规定禁止这种组合。因此很多实现限制 group size 为 32、64、128、256，并不表示数学上其他值不可量化，而是这些值更容易与 vector width、K tile 和 metadata reuse 对齐。

## Metadata 是 Tensor，不只是几个标量

### Metadata 的逻辑 shape

对 $W[M,K]$ 沿 K 每 $G$ 个元素分组，scale 的逻辑 shape 是

$$
[M,\lceil K/G\rceil].
$$

若采用 affine quantization，zero-point 通常有相同或可 broadcast 的 shape。若 scale 自身经过 double quantization，还需要 local scale codes、上一级 global scale，以及它们自己的 partition 描述。

一个可部署 schema 至少应回答：

| 字段 | 必须明确的内容 |
| --- | --- |
| Data code | bit width、signedness、codebook/FP variant |
| Logical shape | 原 Tensor shape 与 axis semantics |
| Partition | group axis、group/block shape、traversal、tail |
| Scale | dtype、shape、layout、数值方向（multiply 还是 reciprocal） |
| Zero-point | 是否存在、dtype、shape、packed 方式 |
| Packing | storage unit、codes/unit、bit order、byte order |
| Padding/alignment | row、tile、Tensor 与文件 offset 的规则 |
| Decoder | reconstruct 公式与特殊值处理 |
| Version | 格式或 quantization schema 版本 |

Scale 的“数值方向”经常被忽略。有的 API 保存 dequant scale $S$，恢复时乘 $S$；有的 Kernel 保存 reciprocal scale $S^{-1}$，quantize 时乘它；还有的系统分别保存 input scale、output scale 或 amax。相同 dtype 和 shape 不代表 metadata 语义相同。

### Structure of Arrays 与 Array of Structures

Codes 和 metadata 可以采用两种基本组织：

- Structure of Arrays（SoA）：所有 packed codes 连续存放，所有 scales 另存为 Tensor；
- Array of Structures（AoS）或 block-interleaved：每个 block 附近紧跟自己的 scale、zero-point 或辅助字段。

SoA 便于分别进行大块 vector load，也更接近 GPU GEMM 把 data operand 与 scale operand 分开的接口；interleaved block 便于流式 CPU decode 或让一个 cache line 同时带回 codes 与 metadata。哪种更快取决于消费方式，不能只按局部性直觉判断。

## 容量模型：payload 之外还有四类开销

对每组 $G$ 个 $b_q$ bit code、$b_s$ bit scale 和 $b_z$ bit zero-point，理想 payload 是

$$
B_{\mathrm{ideal}}
=
N b_q+
\left\lceil\frac{N}{G}\right\rceil(b_s+b_z).
$$

真实存储还需加入：

$$
B_{\mathrm{real}}
=
B_{\mathrm{ideal}}
+B_{\mathrm{tail}}
+B_{\mathrm{align}}
+B_{\mathrm{layout}}
+B_{\mathrm{container}}.
$$

$B_{\mathrm{tail}}$ 来自不完整 group 或 nibble；$B_{\mathrm{align}}$ 来自 row、Tensor 和文件 offset 对齐；$B_{\mathrm{layout}}$ 来自 tile padding、冗余副本或 swizzled scale slot；$B_{\mathrm{container}}$ 包含 Tensor 名称、shape、dtype、offset table 和模型元数据。

对于大矩阵，container header 往往可忽略；对于成千上万个小 Tensor，固定 header 和 alignment 可能显著。报告“4.125 bit/weight”时应说明这是 logical payload，还是实际 checkpoint/HBM allocation。

## Alignment、padding 与 tail 是格式的一部分

Alignment 的目的可能来自 SIMD/vector load、cache line、DMA、mmap 或硬件指令。若每行 logical payload 为 $R$ byte，要求 $A$ byte 对齐，则 physical row stride 可能是

$$
R_{\mathrm{phys}}
=
\left\lceil\frac{R}{A}\right\rceil A.
$$

Padding byte 不能随意包含可被误解为有效数值的 code。Decoder 必须通过 logical shape 或有效长度停止，Kernel 则通过 predicate、zero padding 或 shape restriction 处理尾部。对 GEMM reduction/K 维，错误的非零 padding 会直接污染 dot product；因此将 padding code 对应到实数零通常最安全，但 affine zero-point 或没有数值零的 metadata format 会使规则更复杂。

Tail 至少有三个层次：最后一个 quantization group 不满 $G$；最后一个 storage unit 不满 packing width；最后一个 Kernel tile 不满 MMA/CTA shape。它们可能同时发生，测试时应分别覆盖。

## Checkpoint layout 与 Kernel layout

### Portable checkpoint 优先表达语义

Portable format 通常按 Tensor 记录 name、shape、type、offset，并把数据段按全局 alignment 排列。GGUF 的目标包括自描述、可扩展、mmap 友好和包含加载模型所需的信息；其 general.quantization_version 与具体 Tensor quantization type 分离，说明“量化格式版本”和“Tensor scheme 名称”也是不同层次。

Container 能定位 bytes，不代表通用工具知道如何计算。Loader 还必须拥有该 quantized type 的 block schema 与 decoder。反过来，即使两个容器都能保存任意 byte blob，也不代表其中量化 Tensor 具有互操作性。

### Kernel prepacking 优先表达消费顺序

高性能 Kernel 希望 global load 合并、shared-memory bank conflict 少、解码结果直接进入目标 register fragment。为此，权重可能离线完成 transpose、tile、interleave 和 swizzle，scale 也按 warp 或 K tile 重排。

Marlin 的 FP16×INT4 路径会离线 reshuffle quantized weights 与 group scales，使运行时访问和反量化更适合 Tensor Core organization。这类 prepacking 不改变逻辑矩阵和 dequant formula，却改变

$$
(m,k)\longrightarrow\operatorname{physical\ offset}
$$

的映射。一个“GPTQ INT4 checkpoint”若尚未转换成 Marlin 期待的布局，不能只因为 bit width 与 group size 相同就直接交给 Marlin Kernel。

### Prepack 的三个时机

| 时机 | 优点 | 代价 |
| --- | --- | --- |
| 离线保存 | 启动快，无重复转换 | checkpoint 绑定 backend/architecture |
| 模型加载时 | portable source 可转换为当前设备布局 | 增加加载时间和临时内存 |
| 首次使用时 lazy pack | 只转换真正执行的层 | 首次请求抖动，缓存管理复杂 |

系统也可以同时保留 portable 与 prepacked 副本，以换取快速切换 backend，但会增加 host/GPU memory。Prepack cache 的 key 至少应包含源 Tensor identity、scheme version、Kernel/backend version、device architecture 和目标 layout。

## Scale layout：自然二维数组不一定能直接送入硬件

对 block-scaled operand $A[L,M,K]$，若每个 K 方向 $V$ 个元素共享 scale，自然 scale 元素数为

$$
L\,M\left\lceil\frac{K}{V}\right\rceil.
$$

自然 layout 可以理解为 [L,M,ceil(K/V)]。但 NVIDIA Blackwell block-scaled MMA 的特定 Swizzle32x4x4 合同要求 scale slot 数量为

$$
L\,
\operatorname{round\_up}(M,128)
\,
\operatorname{round\_up}
\!\left(
\left\lceil\frac{K}{V}\right\rceil,4
\right),
$$

并按 128×4 scale tile 交错排列以匹配 warp-group 消费方式。这里同时出现 row padding、K-block padding 和 swizzle。Quantizer/producer 必须生成正确布局；Kernel API 只知道按合同读取，并不会根据“数值看起来像 scale”自动重排。

这也解释了 metadata bandwidth 不能只用 scale 元素数估算。若 layout padding 很大、访问不能合并，或同一 scale 未在 tile 内充分复用，实际 load traffic 会高于逻辑 metadata 大小。

## Framework 中的 derived dtype

基础 dtype 只需 element bits 就能解释单个值；quantized Tensor 往往是 derived dtype：它由 raw data Tensor、scale/zero-point Tensor、block size 和 layout object 共同组成。torchao 将 quantization flow、quantized Tensor、primitive ops/efficient Kernel 和 basic dtype 分层，并把 packing format 作为 quantized Tensor 的独立维度。

这种设计避免为 per-row、per-group、per-block 的每种组合都发明一个互不兼容类，但也意味着打印出来的外层 dtype 名称未必足以描述物理表示。Serialization 必须保存或重建 derived Tensor 的全部组成部分，dispatch 则要根据 layout 选择正确 Kernel。

同样，框架中出现 int4、uint4 或 FP4 shell dtype 不保证普通算子都支持它。它可能只用于承载 bit pattern；真正可执行路径由 quantize/dequantize primitive、Tensor subclass dispatch、compiler lowering 或专用 GEMM 提供。

## Static weight 与 dynamic activation 的存储生命周期

Static quantized weight 通常在部署前生成，适合序列化、离线 prepack 并跨请求复用。Dynamic activation 则在当前输入到达后产生，其 logical codes、scales 和可选 workspace 都是短生命周期对象：

$$
X_{\mathrm{BF16}}
\rightarrow
(Q_X,S_X)
\rightarrow
\text{consumer GEMM}
\rightarrow
\text{release/reuse workspace}.
$$

若 quantize Kernel 将 $Q_X$ 写入 HBM，随后 GEMM 再读回，就产生额外 data pass。更高效的 pipeline 会尝试让 statistics、quantization、layout transform 与 consumer 更紧密融合，或至少复用预分配 workspace。是否值得保存动态 codes，取决于它会被多少消费者复用。

KV cache 处于两者之间：它运行时逐 token 生成，却会长期驻留并被反复读取。因此 KV 的 page/block layout、scale placement、append 粒度和 attention consumer 必须共同设计；不能把普通 weight checkpoint 的 packing 直接照搬。

## 完整示例一：BF16 权重到 INT4 K128

设 $W[M,K]$，目标是 signed symmetric INT4、沿 K 每 128 个元素一组、FP16 scale、low-nibble-first、每行独立 packing。完整路径如下：

| 阶段 | 结果 |
| --- | --- |
| Partition | $W_{m,g}=W[m,128g:128(g+1)]$，尾组按 logical K 截断 |
| Statistics | 每组计算 $a_{m,g}=\max|W_{m,g}|$ |
| Scale | $S_{m,g}=a_{m,g}/7$，保存为 FP16 |
| Encode | $q=\operatorname{clip}(\operatorname{round}(w/S),-8,7)$ |
| Signed bits | $u=q\bmod16$ |
| Pack | 每两个 K-adjacent code 装入一个 byte；第一个在低 nibble |
| Data shape | 逻辑 $[M,K]$；自然 packed bytes 为 $[M,\lceil K/2\rceil]$ |
| Scale shape | $[M,\lceil K/128\rceil]$ |
| Tail | 奇数 K 的高 nibble padding；不足 128 的最后一组只含有效元素 |
| Decode | extract → signed INT4 → FP conversion → multiply FP16 scale |
| Compute | materialize BF16/FP16，或在 register 中 fused dequant 后进入 GEMM |

若 Kernel 要求 K tile=64、向量加载 16 byte，则每次 load 覆盖 32 个 code，一个 quantization group 对应四次这样的 load。若 Kernel 还要求权重按 Tensor Core fragment 顺序预排，以上 natural packed layout 只是中间格式，需要再执行 prepack。

## 完整示例二：MXFP4 block-32 rowwise

对 $X[M,K]$ 的 OCP MXFP4 rowwise 表示：

| 阶段 | 结果 |
| --- | --- |
| Partition | 每行沿 K 每 32 个元素一个 block |
| Statistics/scale | 按 MX conversion 选择 E8M0 shared scale |
| Element codebook | FP4 E2M1 |
| Data payload | 每 block 32×4 bit = 16 byte |
| Metadata payload | 每 block 一个 8-bit E8M0 scale |
| Logical cost | $4+8/32=4.25$ bit/element，不含 padding/layout |
| Natural metadata shape | $[M,\lceil K/32\rceil]$ |
| Decode | E2M1 decode 后乘对应 E8M0 scale |
| Hardware path | 可能先转自然布局，也可能把 scale swizzle 成 block-scaled MMA 所需布局 |

这里 17 byte 是一个 block 的逻辑 payload，不代表文件或显存中一定把 16 byte codes 与 1 byte scale 紧邻保存。SoA、alignment 和硬件 swizzle 都可能改变实际占用。MX 数值规范与某个 GPU 的 scale layout 是两份合同。

## 正确性检查应逐层进行

### Byte-level round trip

构造覆盖边界值的 code：$-8,-7,-1,0,1,7$，以及奇数长度、尾 group、非连续 stride。验证 unpack(pack(q))=q，并固定预期 byte hex，避免 pack 与 unpack 以同一种错误相互抵消。

### Metadata association

为每个 group 使用容易识别的不同 scale，例如 1、2、4、8，验证 group boundary、axis 和 broadcast。对二维 Tensor 同时测试 row/column orientation；对 transpose 后的数据不能默认复用原 scale。

### Reference dequantization

使用最简单的 scalar/reference decoder 生成 $\hat{X}_{\mathrm{ref}}$，再与 vectorized、GPU 或 fused Kernel 的输出比较。测试必须覆盖 saturation、zero-point、subnormal/NaN（若格式支持）和 padding。

### Serialization round trip

保存后重新加载，检查 schema version、shape、code bytes、metadata dtype 与 values，而不只是比较最终模型输出。若存在 prepack cache，还要验证错误 architecture/version 不会复用旧布局。

### Kernel differential test

比较 fused quantized Kernel 与“reference dequantize + high-precision compute”，分别设置 accumulator/output tolerance。若差异超出 quantization 本身，问题可能来自 layout、解包、scale association、accumulator 或 epilogue，而不一定是量化算法。

## 小结

量化 Tensor 的完整表示是 codes、metadata 与 schema 的组合。Logical shape、quantization partition、bit packing、runtime prepack 和 file container 是不同层次；group size、packing width、vector width 和 MMA tile 也不是同一个 block size。

INT4 的关键工程步骤是 signed code 到 nibble、nibble 到 storage unit、storage unit 到 Kernel fragment；block-scaled FP/MX 还要求 scale Tensor 与 data Tensor 在正确 K block 上关联，并可能使用硬件指定的 swizzled scale layout。Checkpoint 变小只是 logical payload 的结果，真正的 HBM bytes 和速度还取决于 padding、metadata、转换与消费 Kernel。

## 来源与适用边界

- [ONNX QuantizeLinear](https://onnx.ai/onnx/operators/onnx__QuantizeLinear.html)：用于核对 per-tensor、per-axis、blocked quantization 的 scale/zero-point shape、axis 和 block size 接口语义；ONNX graph 语义不规定所有 backend 的物理 packing。
- [torchao Quantization Overview](https://docs.pytorch.org/ao/stable/contributing/quantization_overview.html)：用于区分 basic dtype、quantized/derived Tensor、packing format、primitive op 与 efficient Kernel。本文核查时页面标注 torchao 0.17；API 与支持状态会变化。
- [GGUF specification](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)：用于说明自描述 container、Tensor offset/alignment、mmap 目标以及 quantization version 与 Tensor type 的分层；具体 GGML quant block 应以对应源码版本为准。
- [Marlin repository](https://github.com/IST-DASLab/marlin)：用于说明 FP16×INT4 Kernel 会离线 reshuffle weight 与 group scale，使访问、dequantization 和 Tensor Core organization 配合；其布局和性能数字不外推到其他 Kernel/GPU。
- [NVIDIA CUTLASS Arguments and Operands](https://docs.nvidia.com/cutlass/latest/media/docs/operators/api_reference/arguments.html)：用于核对 natural scale ordering 与 Blackwell Swizzle32x4x4 scale slot 公式，以及 producer 负责生成正确 scale layout。
- [OCP Microscaling Formats (MX) Specification v1.0](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf)：用于 MXFP4 的 32-element block、E8M0 scale 与 E2M1 element 数值语义；硬件 swizzle 不属于 OCP 数值规范本身。

本文没有读取或改写具体模型 checkpoint，也没有运行 pack/unpack 程序、CUDA Kernel 或性能 benchmark。INT4 bytes 示例按正文约定手工推导；实际工程必须以目标格式版本、源码与 differential test 为准。
