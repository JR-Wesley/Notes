# 低精度格式与系统实现案例：从 BF16 Tensor 到可执行表示

前面的笔记分别建立了量化数学模型、现代低精度格式、物理存储、Kernel 和 GPU 执行机制。本篇把这些层次重新接成三条完整数据路径：同一个 BF16 矩阵如何变成教学方案 `INT8_BLOCK128`、教学方案 `FP8_BLOCK128`，以及标准格式 `MXFP4_BLOCK32_ROW`，最后怎样被 GEMM Kernel 消费。重点不是宣布哪一种格式“最好”，而是训练一种系统分析方法：任何低精度名称都要展开为数值合同、字节合同和计算合同。

本篇默认分析一个 Linear 权重矩阵 $W[M,K]$，以 $M=K=4096$ 作为容量示例。量化块均沿 $K$ 轴划分，因而每一行独立分组；这适合观察 weight storage 和 GEMM reduction 方向之间的关系。该选择不是所有 activation、KV cache 或通信 Tensor 的通用最优方案。

相关基础见 [[02-量化的统一数学模型]]、[[03-量化方案的分类维度与粒度]]、[[04-FP8、FP4与Microscaling格式]]、[[07-量化张量的存储、布局与元数据]]、[[08-低精度GEMM与Attention-Kernel]] 与 [[09-GPU低精度执行机制]]。本篇只在需要完成端到端推导时重述必要定义。

## 先固定名称：位宽标签不是可执行合同

`INT8_BLOCK128` 和 `FP8_BLOCK128` 不是标准中可以唯一解析的正式类型。为了使比较可复现，本篇给它们补全参数；换掉任一参数，就得到另一种 scheme。`MXFP4_BLOCK32_ROW` 则指向 OCP MX v1.0 的 MXFP4 数值语义，并额外声明 block 沿矩阵行的 $K$ 方向排列。

| 维度 | `INT8_BLOCK128` | `FP8_BLOCK128` | `MXFP4_BLOCK32_ROW` |
| --- | --- | --- | --- |
| 身份 | 本篇教学配置 | 本篇教学配置 | OCP MXFP4 + rowwise orientation |
| Partition | 每行沿 $K$ 每 128 个元素 | 每行沿 $K$ 每 128 个元素 | 每行沿 $K$ 每 32 个元素 |
| Element codebook | signed symmetric INT8，使用 $[-127,127]$ | OCP E4M3 / finite-only FP8，最大有限幅值 448 | E2M1，最大幅值 6 |
| Scale | 每块一个 FP16 dequant scale | 每块一个 FP16 dequant scale | 每块一个 E8M0 power-of-two scale |
| Zero-point | 无，等价于 $Z=0$ | 无显式 zero-point | 无显式 zero-point |
| Mapping | absmax、round-to-nearest-even、saturate | normalize、FP8 round-to-nearest-even、saturate | MX conversion、E2M1 round-to-nearest-even、saturate |
| Logical storage | 1 byte/code + scale Tensor | 1 byte/code + scale Tensor | 2 codes/byte + E8M0 scale Tensor |
| 典型 compute | fused dequant + FP16/BF16 MMA，或匹配时 INT8 MMA | native FP8 MMA 或 fused decode | native block-scaled MMA 或软件 decode |

这里特意让两个 8-bit 方案使用相同 block size 和 scale dtype，以隔离 integer lattice 与 floating-point codebook 的差别；让 MXFP4 使用规范固定的 32-element block，则保留其真实复合格式语义。这个比较因此不是控制所有变量的精度实验，而是一次数据合同对照。

完整对象仍用统一模型表示：

$$
\mathcal{S}
=
(\text{partition},\text{statistics},\text{codebook},\text{mapping},
\text{metadata},\text{storage},\text{compute contract}).
$$

仅保存 `dtype=int8` 或 `dtype=fp4` 无法恢复 $\mathcal{S}$。至少还要知道原始 shape、量化轴、block size、scale dtype 与方向、zero-point 语义、rounding/overflow policy、packing 顺序、物理 layout 和目标 Kernel 合同。

## 共同起点：BF16 矩阵与逻辑分块

设源矩阵为

$$
W\in\mathrm{BF16}^{M\times K},
\qquad M=K=4096.
$$

它包含 $N=16{,}777{,}216$ 个元素，理想 payload 为

$$
B_{\mathrm{BF16}}=N\times 2\ \mathrm{bytes}=32\ \mathrm{MiB}.
$$

对沿 $K$ 的 block size $G$，逻辑 block 可以写作

$$
W_{m,g}
=
\{W_{m,k}\mid gG\le k<\min((g+1)G,K)\},
$$

scale Tensor 的自然 shape 为

$$
[M,\lceil K/G\rceil].
$$

当 $K$ 不能整除 $G$ 时，最后一块需要显式有效长度、padding 或 tail policy。示例中的 4096 可被 128 和 32 整除，因此容量计算没有 tail；这不能推广到任意模型维度。

三条路径共享如下阶段：

$$
W_{\mathrm{BF16}}
\rightarrow \text{partition}
\rightarrow \text{block statistics}
\rightarrow \text{scale}
\rightarrow \text{normalize}
\rightarrow \text{encode}
\rightarrow (Q,S)
\rightarrow \text{pack/prepack}
\rightarrow \text{load}
\rightarrow \text{decode/scale}
\rightarrow \text{MMA}
\rightarrow \text{accumulate/epilogue}.
$$

区别在于每个箭头采用什么规则、产生什么 bytes，以及 scale 能否被推到 reduction 之外。

## 案例一：BF16 → `INT8_BLOCK128`

### 数学映射

本例采用 symmetric signed INT8，并故意不使用 $-128$，使正负最大码值对称。对 block $W_{m,g}$，令

$$
a_{m,g}=\max_{k\in g}|W_{m,k}|,
\qquad
S_{m,g}=\frac{a_{m,g}}{127}.
$$

若整块为零，需要约定 $S_{m,g}=1$ 或其他非零 sentinel，以避免除零；所有 code 仍写成 0。一般元素的 encode/decode 为

$$
q_{m,k}
=
\operatorname{clip}
\left(
\operatorname{RNE}\left(\frac{W_{m,k}}{S_{m,g}}\right),
-127,127
\right),
$$

$$
\widehat W_{m,k}=S_{m,g}q_{m,k}.
$$

这里的 codebook 是等间距 integer lattice，block 内绝对量化步长恒为 $S_{m,g}$。outlier 会增大整个 128-element block 的步长；减小 group size 可以改善局部拟合，却会增加 scale 数量和 Kernel 切换频率。

把 $S$ 存成 FP16 本身还会引入 metadata rounding。实际重建使用的是 $\widehat S=\operatorname{FP16}(S)$，因此总误差不仅是 integer rounding：

$$
W-\widehat S q
=
\underbrace{W-Sq}_{\text{element quantization}}
+
\underbrace{(S-\widehat S)q}_{\text{scale quantization}}.
$$

### 逻辑存储与 schema

每 128 个 INT8 code 占 128 byte，再加一个 2-byte FP16 scale，理想有效位宽为

$$
b_{\mathrm{eff}}
=8+\frac{16}{128}
=8.125\ \mathrm{bit/element}.
$$

对 $4096\times4096$ 矩阵，共有

$$
N_{\mathrm{block}}=4096\times\frac{4096}{128}=131{,}072
$$

个 block，所以 code 为 16 MiB，scale 为 0.25 MiB，逻辑 payload 合计 16.25 MiB。相对 32 MiB BF16 payload，理想压缩率约为 $1.97\times$，而不是忽略 metadata 后的精确 $2\times$。

可恢复该 Tensor 的 schema 至少要声明：`logical_shape=[4096,4096]`、`axis=K`、`block_size=128`、`code_dtype=int8`、`code_range=[-127,127]`、`scale_dtype=fp16`、`scale_semantics=dequant_multiplier`、`zero_point=0`、`rounding=RNE`、`overflow=saturate` 以及 code/scale 的 layout。ONNX `QuantizeLinear` 的 blocked quantization 可以用 scale shape 和 `axis/block_size` 表达逻辑广播关系，但 graph operator 不替 backend 规定 checkpoint container、Tensor Core prepack 或 shared-memory layout。

### 从字节到 GEMM

若 activation $A$ 保持 BF16/FP16，这是一条 W8A16 路径。Kernel 可以加载 INT8 weights，在寄存器或 shared memory 中 convert 并乘对应 FP16 scale，再送入 FP16/BF16 MMA。低精度收益主要来自 weight HBM/L2 traffic，乘法域不一定是 INT8。

若 activation 也量化成 INT8，并且 activation scale 与 weight scale 能在 dot product 外分离，Kernel 可以执行 INT8×INT8→INT32，再在 epilogue 乘 scale。可是本例的 weight scale 随 reduction 轴 $K$ 的 block 改变，完整输出应写成

$$
C_{ij}
=
\sum_g S^A_{i,g}S^W_{j,g}
\left(
\sum_{k\in g}q^A_{i,k}q^W_{j,k}
\right).
$$

因此不能在整个 $K$ reduction 完成后只乘一次单一 scale；每个 block 的 partial sum 必须先应用相应 $S^A_{i,g}S^W_{j,g}$ 再累加。这正是“同为 INT8”仍可能需要不同 Kernel mainloop 的原因。

零点也会改变计算合同。若改成 asymmetric INT8，

$$
(q^A-Z_A)(q^W-Z_W)
=q^Aq^W-Z_Wq^A-Z_Aq^W+Z_AZ_W,
$$

Kernel 需要额外 correction terms 或预计算 sums。`INT8_BLOCK128` 这个名称本身没有告诉我们是否存在这些项；本篇配置通过 $Z=0$ 明确排除了它们。

## 案例二：BF16 → `FP8_BLOCK128`

### Element exponent 与外部 scale 是两层范围

本例使用 OCP E4M3 finite-only codebook，每个 element 自带 sign、4-bit exponent 与 3-bit fraction；外部每块 FP16 scale 则把原始数值范围搬移到 E4M3 可用范围。令 $v_{\max}=448$，一种直接的 absmax recipe 是

$$
S_{m,g}=\frac{a_{m,g}}{448},
\qquad
q_{m,k}=\operatorname{FP8E4M3}
\left(\frac{W_{m,k}}{S_{m,g}}\right),
$$

$$
\widehat W_{m,k}=\widehat S_{m,g}\operatorname{decode}_{E4M3}(q_{m,k}).
$$

实际 recipe 还可能给 scale 留 margin、把 scale 限制为 power of two、使用历史 amax，或采用不同 saturation policy；这些都不是“FP8”两个字符自动规定的。本例明确采用当前 block 的 absmax、FP16 scale、round-to-nearest-even 与饱和转换。

当 block 全零时，$a_{m,g}/448$ 同样不能直接作为可用除数；实现需要指定非零 sentinel scale，并把所有 codes 写成 FP8 zero。这是量化器的边界合同，而不是由浮点除零行为决定。

与 INT8 的固定绝对 step 不同，E4M3 的相邻码字间距随 exponent 增大。它在不同数量级上大致维持有限的相对精度，但在某个窄区间内未必比把 255 个 integer levels 全部铺到该区间更精确。外部 block scale 缓解 block 间范围差异，element exponent 处理 block 内的数量级差异；两者解决的是不同层次的问题。

### 逻辑容量相同，数值语义不同

因为 code 仍是 1 byte、每 128 个 code 仍配一个 2-byte scale，`FP8_BLOCK128` 的逻辑容量也为 8.125 bit/element；对示例矩阵同样是 16 MiB codes + 0.25 MiB scales = 16.25 MiB。容量相同不意味着 bytes 可互换：INT8 byte 按二补数整数解释，FP8 byte 按 E4M3 sign/exponent/fraction 解释，rounding、特殊值和 saturation 也不同。

序列化时至少还要补充 `fp8_variant=OCP_E4M3`。现实 API 中还会遇到 `E4M3FN`、`E4M3FNUZ` 等名称；它们可能在 zero、NaN、bias 或有限值编码上不同，不能仅凭 E/M 位数把 bitstream 当作兼容。

### Native FP8 与 block-scaled FP8 不是同一条路径

硬件若支持 E4M3 MMA，只说明 FP8 codes 可以作为矩阵 operand；它不一定支持本例任意的“每 128 个 K 元素一个 FP16 scale”。可能的实现有三种：

1. load FP8，转换/缩放成 FP16 fragment，再执行 FP16 MMA；这是一条 fused decode 路径，节省存储带宽但不使用 FP8 multiply；
2. 让 FP8 codes 进入 native FP8 MMA，在每个 block 的 partial accumulator 上应用 scale；scale 处理仍由 Kernel 组织；
3. 使用硬件定义的 block-scaled MMA，但前提是 block size、scale dtype、scale vector orientation 和 layout 都与 instruction 合同匹配。本例的 FP16 scale 与 128-element block 不会因为 element 是 FP8 就自动变成 OCP MXFP8。

这一区分也解释了为什么 framework dtype、checkpoint dtype 与实际 SASS/PTX instruction 可能不一致。证明 native path 需要检查 library dispatch、Kernel 名称、目标 instruction 和 profiler，而不只是打印 Tensor dtype。

## 案例三：BF16 → `MXFP4_BLOCK32_ROW`

### MXFP4 是 element 与 shared scale 的复合格式

OCP MXFP4 把 32 个 E2M1 element 与一个 E8M0 shared scale 组成一个 block。E2M1 的非负幅值集合是

$$
\{0,0.5,1,1.5,2,3,4,6\},
$$

负值由 sign bit 给出。E8M0 没有 sign、fraction、zero 或 infinity；除保留的 NaN 编码外，它表示 $2^e$ 形式的 scale。于是一个重建值为

$$
\widehat W_{m,k}=X_{m,g}P_{m,k},
$$

其中 $X_{m,g}$ 是 E8M0 scale，$P_{m,k}$ 是 E2M1 element。32 个元素共享的是外部 power-of-two scale，不是彼此失去独立 exponent 的普通定点尾数。

OCP MX v1.0 要求实现提供一种最低限度的转换语义：先取 block amax 的最大不超过它的 power of two，再除以 element format 能表示的最大 power of two。对 E2M1，最大可表示 power of two 是 4，因此可写成

$$
X_{m,g}
=
\frac{2^{\lfloor\log_2 a_{m,g}\rfloor}}{4},
$$

再把 $W/X$ 以 round-to-nearest-even 转成 E2M1，并对超出范围的值饱和。规范允许实现支持其他 conversion algorithms，所以看到不同库采用接近 $a_{\max}/6$ 的 scale rule 时，必须记录具体 recipe，不能只记录输出 dtype。

全零 block 也是特殊情况：E8M0 没有数值零，因而实现应选择任意约定的有限非零 scale，并把 32 个 E2M1 elements 全部编码为零。只要 schema 固定该约定，重建结果仍唯一为零。

这也澄清一个容易混淆的细节：E2M1 的最大数值是 6，但“最大 power of two”是 4。MX v1.0 最低转换语义使用后者；scale 选择、element codebook 和 overflow policy必须一起阅读。

### Nibble packing 与逻辑容量

每个 32-element block 的 FP4 codes 占 $32\times4=128$ bit，即 16 byte；E8M0 scale 占 1 byte，所以逻辑 payload 为 17 byte：

$$
b_{\mathrm{eff}}
=4+\frac{8}{32}
=4.25\ \mathrm{bit/element}.
$$

示例矩阵共有

$$
4096\times\frac{4096}{32}=524{,}288
$$

个 block。codes 占 8 MiB，scales 占 0.5 MiB，总计 8.5 MiB；相对 BF16 的理想压缩率约为 $3.76\times$，而不是忽略 scale 后的 $4\times$。

两个 E2M1 code 可以 pack 到一个 byte，但还必须定义 high/low nibble 顺序。OCP MX 规定数值与 binary interchange 语义，却不要求 scale 必须紧邻本 block 的 16-byte code，也不替 GPU 规定矩阵 tile 的物理 prepack。逻辑上相同的 MXFP4 Tensor可以使用 SoA、block-interleaved 或硬件专用 layout。

### Rowwise orientation 进入数值语义

`ROW` 表示对 $W[M,K]$ 沿每一行的 $K$ 方向每 32 个连续元素共享 scale，自然 scale shape 是 $[M,K/32]$。若改成 columnwise，则 32-element block 沿 $M$ 方向形成；它会得到不同 amax、scale 和 codes。转置 rowwise 已量化 bytes 并不能得到从高精度 $W^T$ 独立生成的 rowwise MXFP4，因为共享集合已经改变。

训练的 forward/backward 或 GEMM 的不同 operand orientation 因而可能需要 rowwise 与 columnwise 两份量化表示。额外副本会增加 quantization bandwidth 和临时显存，这些开销不在 4.25 bit/element 的单份逻辑 payload 中。

### Native block-scaled MMA 的计算合同

若 A、B 都沿 GEMM 的 $K$ 方向采用 MX block，局部 dot product 的语义是

$$
C_{ij}
=
\sum_g X^A_{i,g}X^B_{j,g}
\left(
\sum_{k\in g}P^A_{i,k}P^B_{j,k}
\right).
$$

scale 随 $g$ 改变，因此必须在 K-block partial reduction 上生效。NVIDIA Blackwell `tcgen05.mma` 的 block-scaled路径把 element data 与 scale factors 作为不同 operand，并以更高精度 accumulator 完成这类运算。CUTLASS 的 MX 类型使用 UE8M0 scale 和 dense vector size 32，与 OCP MX 的 block size一致。

但自然 scale Tensor不能直接等同于硬件 operand layout。Blackwell CUTLASS 文档描述的 scale basic block包含 128 个 M/N 位置和沿 K 的 4 个 scale，并按硬件消费顺序交错。Producer或 quantizer 需要把自然 $[M,K/32]$ scales swizzle/prepack 成目标布局。对通信数据，Transformer Engine 的 MXFP8 实现甚至会在通信后、GEMM 前才做 swizzle，因为计算专用布局不适合作为跨设备交换表示。MXFP4 的一般系统原则相同：数值格式、交换布局和执行布局应分层处理。

## 一个小数值块：三种 codebook 实际保留什么

下面取一个 block 中的八个示意值：

$$
x=[-6,-3,-1,-0.3,0,0.75,2,5.2].
$$

它只用于观察 codebook，不代表完整 128/32-element block 的统计分布。INT8 令 $S=6/127$；FP8 为便于手算选一个合法的 power-of-two FP16 scale $S=1/64$，并使用 E4M3；MXFP4 的 $a_{\max}=6$，按上述 OCP 最低转换语义得到 $X=1$。

| 原值 | INT8 重建，$S=6/127$ | E4M3 重建，$S=1/64$ | MXFP4 重建，$X=1$ |
| ---: | ---: | ---: | ---: |
| -6 | -6.0000 | -6.0000 | -6 |
| -3 | -3.0236 | -3.0000 | -3 |
| -1 | -0.9921 | -1.0000 | -1 |
| -0.3 | -0.2835 | -0.3125 | -0.5 |
| 0 | 0 | 0 | 0 |
| 0.75 | 0.7559 | 0.7500 | 1.0 |
| 2 | 1.9843 | 2.0000 | 2 |
| 5.2 | 5.1969 | 5.0000 | 6 |

INT8 在整个 block 使用固定 $0.04724$ 左右的绝对步长；E4M3 在不同 exponent bin 使用不同步长；MXFP4 只有极稀疏的局部码字，但用更细的 32-element scale block适应局部分布。表中 RNE 把 E2M1 的 0.75 tie 选到 1.0。不能据此断言 FP8 总比 INT8好或 MXFP4 不可用，因为真实误差还由完整 block、scale rule、outlier、Tensor敏感度与模型补偿决定。

## 同一矩阵的容量与 metadata 对账

| 表示 | Code payload | Scale payload | 理想总量 | 有效位宽 | 相对 BF16 理想压缩率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BF16 | 32 MiB | 0 | 32 MiB | 16 | $1.00\times$ |
| `INT8_BLOCK128` | 16 MiB | 0.25 MiB | 16.25 MiB | 8.125 | $1.97\times$ |
| `FP8_BLOCK128` | 16 MiB | 0.25 MiB | 16.25 MiB | 8.125 | $1.97\times$ |
| `MXFP4_BLOCK32_ROW` | 8 MiB | 0.5 MiB | 8.5 MiB | 4.25 | $3.76\times$ |

这些数字只计算恰好整除时的 logical payload。实际 checkpoint 或显存还可能包含 row/tile padding、offset alignment、Tensor header、重复的 rowwise/columnwise表示、prepacked copy、scale swizzle padding 和 workspace。另一方面，若多个 block 的 scale 可按规范允许的方式压缩，文件容量也可能低于朴素 codes + scales；但 Kernel通常仍需要可直接寻址的 runtime表示。

容量分析必须同时报告三种数：logical bits/element、serialized bytes 和 runtime physical bytes。只报告第一种，无法预测显存；只报告 checkpoint 文件大小，又无法解释 Kernel traffic。

## 从 checkpoint 到 runtime：同一 scheme 的多种布局

一个可维护系统不应让“量化格式”同时承担所有布局职责。更稳妥的分层是：

| 层次 | 主要目标 | 代表内容 | 是否适合跨硬件复用 |
| --- | --- | --- | --- |
| Logical quantized Tensor | 唯一恢复数值 | codes、natural scales、axis、block size、dtype、rounding | 通常较高 |
| Serialized checkpoint | 稳定存储与装载 | Tensor table、offset、alignment、version、schema | 取决于容器与规范 |
| Runtime canonical layout | framework算子与通信 | contiguous codes、natural metadata、logical strides | 中等 |
| Kernel-prepacked layout | 合并load并匹配 fragment | transpose、interleave、tile、scale swizzle | 通常绑定 backend/architecture |

Static weight 可以在模型加载时一次 prepack 并跨请求复用；dynamic activation 每一步重新产生，通常要求 quantize 与 layout transform融合，否则额外读写会吞掉收益；KV cache 则持续 append 并重复读取，需要 page layout、scale placement 和 attention Kernel共同设计。

因此 checkpoint 最好携带足够的 logical schema，并把高度硬件专用的 prepack视为可重建 cache，除非部署环境固定且加载时间比可移植性更重要。把 SM100 的 swizzled scales 当作唯一权威表示，会使 CPU reference、跨 GPU 迁移、通信和版本升级都更困难。

## Kernel 选择：三种 scheme 分别把成本放在哪里

| 成本位置 | `INT8_BLOCK128` | `FP8_BLOCK128` | `MXFP4_BLOCK32_ROW` |
| --- | --- | --- | --- |
| Quantize | absmax、除法、RNE、clip | absmax、scale、FP8 conversion | 32值amax、E8M0 scale、E2M1 conversion |
| Decode辅助工作 | integer→FP、乘 FP16 scale，或 zero-free integer path | FP8 conversion/scale，或 native FP8 path | nibble unpack、scale association；native path需scale operand |
| Metadata traffic | 2 B / 128 values | 2 B / 128 values | 1 B / 32 values |
| Mainloop约束 | K-block scale可能要求 partial rescale | 是否原生取决于 scale合同 | block scale天然进入 K mainloop |
| Layout压力 | vector load、group边界、可选prepack | FP8 variant与scale layout | nibble packing、32-block orientation、硬件swizzle |
| 主要收益来源 | weight bandwidth或INT8 MMA | FP8 MMA与operand bandwidth | 极低operand bytes与native block-scaled MMA |

在低 batch decode 中，weight bytes 经常是主要成本，INT8/FP8/MXFP4 都可能先从 HBM traffic下降中受益。在大 batch prefill 或训练 GEMM 中，计算利用率更高，原生 matrix instruction、tile compatibility、accumulator吞吐和 conversion fusion的重要性上升。相同 checkpoint 在两个 workload 上可能需要不同 runtime表示或完全不同 Kernel。

还有一个关键边界：本篇三个例子都是 weight representation。若 activation 仍为 BF16，MXFP4×BF16 是否有原生 mixed-input instruction、library是否覆盖该 shape，以及是否需要先量化 activation，必须按硬件与库版本核查。格式可以存储，不等于任意 operand组合都有高性能 MMA。

## Graph IR、格式标准和硬件 ISA 各自保证什么

同一条数据路径会经过多个“合同层”，它们不能互相替代：

| 合同层 | 可以保证 | 不能单独保证 |
| --- | --- | --- |
| ONNX blocked quantization | scale shape、axis、block广播和算子数学 | nibble顺序、checkpoint容器、GPU prepack |
| OCP FP8/MX规范 | element/scale编码、MX block参数、基本转换与运算语义 | 某厂商scale swizzle、Kernel覆盖和性能 |
| Framework dtype/quantized Tensor | 程序中的对象类型、dispatch入口和逻辑metadata | 最终一定使用目标matrix instruction |
| CUTLASS/cuBLAS等library | 特定架构、layout和shape下的Kernel接口 | 任意模型shape无fallback、端到端质量 |
| PTX/ISA | operand、instruction、accumulator和layout底层合同 | framework必然选择该路径 |

如果部署失败，应先判断是数值合同不一致、schema缺失、layout不匹配、Kernel不可用，还是 workload根本没有落入低精度快路径。把所有问题统称为“量化精度不好”会掩盖真正故障层。

## 正确性验证：逐层定位，而不是只比较最终 logits

第一层验证 encode/decode。为每个 block构造 boundary values、ties、zero、最大有限值、overflow、underflow 和全零块，逐元素对照 reference；INT8 还要测试 $-128$ 是否禁用，FP8要固定 variant，MXFP4要测试 E8M0 scale 与 E2M1 saturation。

第二层验证 storage。用已知 nibble pattern 检查 high/low顺序，用不同 scale 序列检查 block association，并覆盖 K tail、row stride、transpose、alignment 与 serialization round-trip。逻辑 decode正确但 Kernel错误，常见原因就在这一层。

第三层验证 compute。比较“reference decode到 FP32/BF16 后 GEMM”与 fused/native低精度 Kernel，分别设置 accumulator和output tolerance。若差异超过单纯 quantization error，应继续检查 scale应用位置、K-block partial reduction、split-K中间 dtype 与 epilogue downcast。

第四层才验证模型质量与性能。质量应区分局部 reconstruction error、层输出误差、校准集指标和最终任务指标；性能应分别测量 quantize/prepack、冷启动、稳态 GEMM、端到端 latency/throughput、HBM bytes、metadata traffic 和 workspace。一个离线 weight prepack 很慢但能被数百万请求摊薄，可能仍是好设计；同样成本放在每 token activation上则可能不可接受。

## 选择方案时应回答的系统问题

面对新的低精度格式，可以按下面顺序收敛，而不是先按位宽排序：

1. **对象与生命周期**：是离线 weight、动态 activation、KV cache、gradient还是通信 buffer？量化成本能否复用？
2. **数值分布**：局部范围是否窄，是否有 outlier，绝对误差还是相对误差更重要？这决定 INT lattice、FP codebook与细粒度 scale的价值。
3. **完整 schema**：element variant、scale dtype、axis、group、zero-point、rounding、overflow和special values是否唯一确定？
4. **物理表示**：logical payload之外还有多少padding、副本、swizzle与workspace？
5. **消费路径**：目标 GPU与library能否执行匹配的 native/fused Kernel，还是要先 materialize高精度 Tensor？
6. **workload瓶颈**：当前受 HBM、片上decode、matrix unit、launch、shape还是network限制？降低位宽是否作用于真实瓶颈？
7. **验证证据**：reference、模型质量和 profiler是否分别证实数值正确、任务可接受和系统实际获益？

这套问题也解释了三种方案的典型定位。`INT8_BLOCK128` 简单、规则、容易建立 reference，适合做基础 baseline；`FP8_BLOCK128` 用 element exponent适应 block 内数量级，但其 scale recipe与硬件合同必须补全；`MXFP4_BLOCK32_ROW` 以更细 scale和复合格式换取极低 payload，对 layout、orientation和原生block-scaled Kernel依赖更强。它们不是一条只按位宽递进的直线，而是三组不同的数值—metadata—硬件折中。

## 小结

从 BF16 到低精度表示并不是一次 cast，而是一条包含 partition、statistics、scale、normalize、encode、pack、layout、decode和compute的完整数据路径。三种示例中，INT8与FP8虽然同为8-bit且逻辑容量相同，却分别使用uniform integer lattice与带element exponent的浮点codebook；MXFP4则把E2M1 element、32-element block和E8M0 scale绑定成标准复合格式，并让scale显式进入矩阵 datapath。

最重要的工程结论是：逻辑数值格式、序列化格式和Kernel执行布局必须分层。标准解决可解释的数值语义，framework/IR描述逻辑对象，library与ISA决定可执行布局；只有三层对齐，理论位宽才可能转化为正确且更快的系统实现。
