## THE CUDA C DEVELOPMENT PROCESS（CUDA C 开发流程）

CUDA 开发流程建立在既有软件生命周期概念之上，并利用对 GPU 内存/执行模型的抽象来掌控大规模并行环境。你的关注点始终是：

> "➤ Performance-oriented  ➤ Profile-driven  ➤ Guided with insights inspired by abstract models of GPU architecture"

即：**面向性能、由性能分析驱动、以 GPU 架构抽象模型为指导**。你只需聚焦高层域分解（domain decomposition）与存储层次管理，线程的创建/销毁这类簿记细节由 CUDA 接管。

### APOD 开发循环（APOD Development Cycle）

APOD 是 NVIDIA 为 CUDA 提出的**自定义迭代开发流程**，四个阶段（FIGURE 10-1）：

| 阶段 | 目标 | 关键活动 |
|---|---|---|
| **Assessment**（评估） | 找到瓶颈/热点 | 找出高计算强度的关键区，优先看数据并行循环；用分析工具找 hotspot；已有 OpenMP/pthreads 代码也是好目标 |
| **Parallelization**（并行化） | 把热点搬到 GPU | 三条路：CUDA 库 / OpenACC 等并行化编译器 / 手写 kernel；重构数据结构暴露并行性 |
| **Optimization**（优化） | 榨干性能 | grid-level（多 kernel 并发、流重叠传输）与 kernel-level（带宽/计算assets/延迟）优化 |
| **Deployment**（部署） | 产出可部署程序 | 检测 CUDA-capable GPU、适配硬件软件配置；**迭代**——含多个加速候选的应用会多次穿越 APOD |

**Assessment 要点**
- 优先评估含**显著计算的数据并行循环（data-parallel loop）**——这是 GPU 加速的最佳候选。
- 已有 OpenMP/pthreads 代码，只要并行段有足够并行度，也是好目标。

**Parallelization 要点**
- 最省力：直接换库（如 BLAS→cuBLAS，FFTW→cuFFT）。
- 次之：OpenACC 编译器指令（类似 OpenMP 的 `#pragma`，可移植、显式控制数据局部性）。
- 功能/性能超出现有库或编译器时，才手写 CUDA C kernel。
- **数据划分（data partitioning）**两类：
  - **Block partition（块划分）**：把连续数据块分给线程；kernel 性能对 block size 敏感。
  - **Cyclic partition（循环划分）**：每个线程每次处理一个元素，再跳过"线程数"个位置；先到先处理。

**Optimization 要点**
- 优化可落在两层次：**Grid-level**（整体 GPU 利用率，多 kernel 并发 + 流/事件重叠）与 **Kernel-level**（有效利用带宽/计算资源，隐藏指令与内存延迟）。
- kernel 三大性能限制因素：**Memory bandwidth / Compute resources / Instruction & memory latency**。
- 工具：Nsight Eclipse Edition、NVIDIA Visual Profiler (nvvp)、NVIDIA Command-line Profiler (nvprof)。

> "APOD is an iterative process that seeks to convert legacy applications to well-performing and stable CUDA applications."

### SPIRAL MODEL（螺旋模型）

APOD 的基本思路与软件工程的 **Spiral Model（螺旋模型）** 一致：分析→设计→实现 的连续细化迭代循环。APOD 只是把它套用到"把 legacy 应用变 CUDA 应用"这一场景。

## OPTIMIZATION OPPORTUNITIES（优化机会，按重要性排序）

一旦拿到正确程序，优化优先级如下：

> "➤ Exposing sufficient parallelism  ➤ Optimizing memory access  ➤ Optimizing instruction execution"

### 1. Exposing Sufficient Parallelism（暴露足够并行度）

目标：安排 GPU 上的并发工作，使**指令带宽与内存带宽都被喂饱**。两种方式：
- 在 SM 内保持更多并发 warp（occupancy）。
- 给每个线程/warp 分配更多独立工作。

> "However, a high degree of occupancy does not automatically correspond to higher performance."

高占用率 ≠ 高性能和——到达某阈值后再涨占用率也未必提速，但可从其它角度继续优化。两个层次：
- **Kernel-level**：寄存器在线程间划分、共享内存在块间划分 → 资源消耗会限制活跃 warp 数。
- **Grid-level**：用 `threads/block` 与 `blocks/grid` 两个参数控制线程如何分组、如何摊到各 SM。

### 2. Optimizing Memory Access（优化内存访问）

多数算法是 memory-bound。目标：**最大化内存带宽利用率**。聚焦两点：
- **内存访问模式**（让总线上的字节尽量被用上）。
- **充足的并发内存访问**（隐藏内存延迟）。

**Global Memory**
- warp 内 32 线程各给一个地址，硬件转成内存事务；设备访问粒度 **32 字节**。
- 两个指标之差 = 浪费的带宽：**程序请求的字节数** vs **硬件实际搬运的字节数**。
- 最佳访问模式：**aligned（首地址 32 字节对齐）+ coalesced（warp 内 32 线程访问连续块）**。
- Load 三类：**Cached**（默认，L1 开，粒度 128B 缓存行）/ **Un-cached**（L1 关，32B 段）/ **Read-only**（先命中独立 read-only cache，再 L2，再全局；Fermi 上全局 load 走 L1→L2→全局，Kepler 全局 load **跳过 L1**）。
- 不规则访问（misaligned/un-coalesced）下用短粒度（关 L1）反而提升带宽利用率；Fermi 上可用编译选项开关 L1，store 默认跳过 L1 并使对应缓存行失效。

**Shared Memory**
- 片上、高带宽低延迟，是"程序管理的缓存"。使用两大理由：① 显式缓存数据减少全局访问；② 重排数据布局避免非合并全局访问。
- 物理上线性排布、经 **32 个 bank** 访问；Fermi 默认 **4-byte bank mode**，Kepler 默认 **8-byte bank mode**。
- 同 warp 多线程访问同 bank 不同字 → **bank conflict**，多路冲突因 replay 很贵。
- 解法：**padding（填充）**——在合适位置加一个字，把访问摊到不同 bank，降低延迟、提升吞吐。
- 共享内存在所有驻留线程块间划分 → 关键资源，可能限制占用率。

### 3. Optimizing Instruction Execution（优化指令执行）

- 隐藏延迟：① 保持足够活跃 warp；② 给线程分配可流水化的独立工作。
- **Warp divergence（分支发散）**：
  > "When threads within a warp diverge, the warp must execute each branch path in sequence while disabling threads that did not take that execution path."
  发散时 warp 顺序执行各分支、关闭未走该路径的线程；若大量时间花在发散代码上，性能显著受损。
- **同步**：CUDA 提供 grid-level 与 thread-block-level 两种显式同步。
  > "Synchronizing threads inside potentially divergent code is dangerous and can cause unanticipated errors."
  在可能发散的代码里做同步很危险（须确保所有线程在 `__syncthreads` 屏障处汇聚）；同步本身有开销并限制调度器弹性。

### 4. CUDA Code Compilation（CUDA 代码编译）

CUDA 源文件分两类：常规 C 文件 + CUDA C 文件（内含 device function / host function）。编译分两段（FIGURE 10-2）：**nvcc 编译 device 代码**，**通用 C/C++ 编译器编译 host 代码**；编译后的 device 对象以 load image 形式嵌入 host 对象，链接阶段加 CUDA runtime 库。

**两种编译方式**
- **Whole-program compilation（整体编译）**：CUDA 5.0 之前，kernel 及其调用的全部 device 函数必须同文件；不能跨文件调用 device 函数/变量。
- **Separate compilation（分离编译，CUDA 5.0+）**：device 代码可跨文件引用。好处（FIGURE 10-3）：
  > "➤ Eases porting of legacy C code  ➤ Reduces build time with incremental library recompilation  ➤ Facilitates code reuse  ➤ Combine object files into static libraries  ➤ Link & call external device code  ➤ Create & use third-party libraries"

**分离编译三步**（Fermi, sm_20 例）

```bash
# 1) 生成含可重定位 device 代码的 .o（-dc）
nvcc -arch=sm_20 -dc a.cu b.cu
# 2) device linker 把所有 device 对象链成可交给 host linker 的 link.o（-dlink）
nvcc -arch=sm_20 -dlink a.o b.o -o link.o
# 3) host linker 生成可执行
g++ -c c.cpp -o c.o
g++ c.o link.o -o test -L<path> -lcudart
```

**Sample Makefile（Listing 10-1 要点）**
- `NVCC_FLAGS += -O3 -dc`（`-dc` 启用分离编译）、`CUDA_LINK_FLAGS := -dlink`、`GPU_CARD := -arch=sm_35`、链接 `-lcublas -lcufft -lcudart`，并 `-Xcompiler -fopenmp` 兼容 host OpenMP。

**把 CUDA 文件集成进 C 工程**
- CUDA 提供 C++ 约定接口与 C 约定接口两套 runtime API。从 `.c` 调 CUDA 需 `#include <cuda_runtime_api.h>`。
- device 源文件中用 `extern "C"` 包裹 kernel 启动包装函数，使其能被 C 链接（避免 C++ name mangling）：

```c
// 主机侧 .c 文件
#include <cuda_runtime_api.h>
...
// device 源文件，用 extern "C" 解析名字
extern "C" void launch_myKernel(...) {
    ...
    myKernel<<<grid, block>>>();
    ...
}
```

**CUDA Error Handling（错误处理）**
- 每个 CUDA API/库调用都返回错误码（成功或失败详情）。错误检查是异步的——返回的错误可能来自**更早的、仍在执行的异步调用**，需用 `cudaGetLastError`/`cudaPeekLastError`/`cudaGetErrorString` 处理。
- 三个检查函数：
  - `cudaGetLastError`：返回当前错误并**清空**内部状态为 `cudaSuccess`（多次调用返回不同错误 → 各不相同）。
  - `cudaPeekLastError`：同检查但**不清空**状态。
  - `cudaGetErrorString`：错误码 → 可读字符串。
- 生产代码一般用 `CHECK`/`CALL_CUDA` 宏，出错即打文件行号并退出：

```c
#define CHECK(call) { \
    cudaError_t err; \
    if ( (err = (call)) != cudaSuccess) { \
        fprintf(stderr, "Got error %s at %s:%d\n", cudaGetErrorString(err), \
                __FILE__, __LINE__); \
        exit(1); \
    } \
}
```

## PROFILE-DRIVEN OPTIMIZATION（性能驱动优化）

> "Profile-driven optimization is an iterative process to optimize your program based on profile information."

迭代流程：① 用 profiler 采集 → ② 找 hotspot → ③ 定位性能抑制因素 → ④ 优化 → ⑤ 重复至达标。kernel 最可能三类瓶颈：**Memory bandwidth / Instruction throughput / Latency**。

### Finding Optimization Opportunities Using nvprof

`nvprof [nvprof-options] <application> [application-arguments]`，默认 **Summary mode**。四类模式：

| 模式 | 启用选项 | 收集内容 |
|---|---|---|
| Summary（默认） | — | 汇总概览 |
| Trace | `--print-gpu-trace` / `--print-api-trace` | GPU 活动时间线 / 主机侧 CUDA API 调用时间线 |
| Event/Metric summary | `--events <names>` / `--metrics <names>` | 事件/指标的统计值（可 `--query-events`/`--query-metrics` 查全部） |
| Event/Metric trace | `--aggregate-mode off [events\|metrics]` | 每次 kernel 执行的事件/指标值（默认跨所有 SM 聚合） |

- **Profiling scope**：`--devices <device IDs>` 限定只采集指定设备（对 `--events`/`--metrics`/`--query-*` 生效）。
- **Events vs Metrics**：event 是硬件计数器（如全局内存访问次数、L1 命中次数）；metric 由 event 推导（如缓存利用率）。可自定义 metric。

**关键 metrics 速查**

| 关注点 | 推荐的 nvprof metrics / events |
|---|---|
| 全局内存访问模式（对齐+合并） | `gld_efficiency`、`gst_efficiency`（请求吞吐/必需吞吐之比）；`gld_transactions_per_request`、`gst_transactions_per_request`（单次请求平均事务数，越大越浪费）；`gld_transactions`、`gst_transactions`、`gld_throughput`、`gst_throughput` |
| 共享内存 bank 冲突 | `shared_load_transactions_per_request`、`shared_store_transactions_per_request`、`l1_shared_bank_conflict`（冲突次数）、`shared_load`、`shared_store`；replay 比 = `l1_shared_bank_conflict/(shared_load+shared_store)`；`shared_efficiency` |
| 寄存器溢出（spilling） | `l1_local_load_hit/miss`、`l1_local_store_hit/miss`；`local_load_hit_ratio`、`l1_cache_local_hit_rate`（低 = 严重溢出；Fermi 上限 63、Kepler 255 寄存器/线程） |
| 指令吞吐（串行化/发散） | `inst_executed`、`inst_issued`（含 replay，二者之差 = 串行化占比）；`branch_efficiency`（非发散分支/总分支）、`branch`、`divergent_branch` |

### Guiding Optimization Using nvvp

NVIDIA Visual Profiler 与 nvprof 的两点不同：**时间线可视化** + **自动性能分析建议**。它是独立应用 `nvvp`，也内嵌于 Nsight Eclipse Edition。六大视图：**Timeline / Analysis / Details / Properties / Console / Settings**。

- **Timeline view**：CPU/GPU 活动同屏时间线（前几章已用）。
- **Analysis view**：两种模式：
  - **Guided analysis（引导式）**：nvvp 分步带你走完——CUDA Application Analysis → Performance-Critical Kernels → Compute/Bandwidth/Latency Bound → Compute Resources。
  - **Unguided analysis（非引导式）**：每项旁有 `Run Analysis` 按钮，点按即跑该项分析，结果含说明与 `More...` 文档链接；选中单个 kernel 还会有 kernel 级专属分析项。

### NVIDIA Tools Extension（NVTX，标注关键代码段）

NVTX 用 C API 给应用打"事件/代码区间/资源"标签，nvvp 可捕获并可视化。两个核心服务：**CPU 事件与代码区间的 tracing** + **OS/CUDA 资源的命名**。用 `sumMatrixGPU.cu` 演示：

```c
#include <nvToolsExt.h>
#include <nvToolsExtCuda.h>
#include <nvToolsExtCudaRt.h>

nvtxEventAttributes_t eventAttrib = {0};
eventAttrib.version = NVTX_VERSION;
eventAttrib.size = NVTX_EVENT_ATTRIB_STRUCT_SIZE;
eventAttrib.colorType = NVTX_COLOR_ARGB;
eventAttrib.messageType = NVTX_MESSAGE_TYPE_ASCII;

eventAttrib.color = RED;  eventAttrib.message.ascii = "HostMalloc";
nvtxRangeId_t hostMalloc = nvtxRangeStartEx(&eventAttrib);   // 区间开始
// ... 主机内存分配 ...
nvtxRangeEnd(hostMalloc);                                    // 区间结束
```

编译链接扩展库：`nvcc -arch=sm_35 sumMatrixGPU_nvToolsExt.cu -o sumMatrixExt -lnvToolsExt`。nvvp 时间线会多出 "Markers and Ranges" 行，按指定颜色显示所有标注的主机侧事件。

## CUDA DEBUGGING（CUDA 调试）

调试分两类：**Kernel debugging**（检视 kernel 执行流与状态）与 **Memory debugging**（发现非法/冲突内存访问）。内存调试工具更自动化，适合先快速排错，再深入 kernel 调试。

### Kernel Debugging（内核调试）

三种手段：**cuda-gdb、printf、assert**。

**cuda-gdb**
- 与 gdb 几乎一致。编译需加 `-g -G`（嵌入 host+device 调试信息、关闭大部分优化）：

```bash
nvcc -g -G foo.cu -o foo
cuda-gdb foo
(cuda-gdb) run
```

- **CUDA Focus**：会话一次聚焦单个线程；可 `cuda thread lane warp block sm grid device kernel` 查看/切换焦点，如 `(cuda-gdb) cuda thread (128)`。
- 检视内存：`print scalar`、`print arr[0]`、`print *(@shared int*)0x4`（共享内存按 SM 局部，不同 focus 同地址可能不同值）。
- 环境信息：`info cuda devices/sms/warps/lanes/kernels/blocks/threads/...`。
- **Tunable 参数（Table 10-1 节选）**：`api_failures`(ignore)、`break_on_launch`(none)、`context_events`(on)、`defer_kernel_launch_notifications`(on)、`kernel_events`(none)、`launch_blocking`(off)、`memcheck`(off)、`ptx_cache`(on)、`single_stepping_optimizations`(CUDA 6.0 起 on)、`thread_selection`(logical)、`value_extrapolation`(off)。
- 实战（`debug-segfault.cu`）：捕获 `CUDA_EXCEPTION_10, Device Illegal Address`，定位到第 34 行对 `arr[tid][i]` 的多级解引用；`print arr[tid]` 显示 `(@global int* @global) 0x0`（NULL）→ 缺一次 `cudaMemcpy` 填充设备指针数组，补上即修。

**CUDA printf**
- CC ≥ 2.0 支持，接口同 C 的 `printf`（需 `stdio.h`）。
- 注意：① 线程间无打印顺序（除非显式同步）；② 用固定大小的**环形设备缓冲**暂存，产出快于显示会覆盖旧输出，缓冲大小由 `cudaGetDeviceLimit`/`cudaSetDeviceLimit` 取设；③ 缓冲在"kernel 启动 / 任何 host 同步 / 同步 `cudaMemcpy`"时回传主机。
- 用法：`printf("Hello from CUDA thread %d\n", tid);`——用索引限制打印线程数，避免上千线程冲爆缓冲。

**CUDA assert**
- CC ≥ 2.0 支持，需 `assert.h`。语义不同于 host：设备端 assert 失败时该线程**立即退出并保存信息**，但信息只在**下一个 CUDA 同步点**（如 `cudaDeviceSynchronize`）才显示到 stderr；若首次失败后又调 CUDA host API，返回 `cudaErrorAssert`。
- 配合 cuda-gdb 时控制权交给调试器检视状态；用 `NDEBUG` 宏可在 release 版关闭 assert 求值。

> "cuda-gdb is the most powerful ... printf is not interactive ... assert is great for inspecting application state when known issues arise."

### Memory Debugging（内存调试）

核心是 **cuda-memcheck**，比 cuda-gdb 更自动化、粗粒度，但给出更详细的内存错误统计。含两个工具：
- **memcheck**：查全局/本地/共享内存的越界与未对齐访问、硬件异常、malloc/free 误用、CUDA API 错误、`cudaMalloc` 泄漏、device heap 泄漏。
- **racecheck**：查共享内存的冲突访问（hazard，至少一个是写）。

**编译用于 cuda-memcheck**：不能用 `-g -G`（损害性能、影响错误可复现）。应加 **`-lineinfo`**（关联文件名/行号）、并加符号信息（`-Xcompiler -rdynamic` Linux / `-Xcompiler /Zi` Windows），既可读又可保性能。

**memcheck 例**（对 `debug-segfault`）：
```
========= Invalid __global__ write of size 4
=========     at 0x... in debug-segfault.cu:25:kernel(int**)
=========     by thread (0,0,0) in block (4,0,0)
=========     Address 0x00000000 is out of bounds
========= ERROR SUMMARY: 2 errors
```
给出方向（write）、空间（`__global__`）、大小（4B）、线程、越界地址——比 cuda-gdb 更精确省力；第二错是 `cudaMemcpy` 返回 CUDA error 4（驱动正在关闭，由前述内存错引发）。

**racecheck 例**（`debug-hazards.cu` 故意去掉 `__syncthreads`）：
```bash
nvcc -arch=sm_20 -lineinfo -Xcompiler -rdynamic -o debug-hazards debug-hazards.cu
cuda-memcheck --tool racecheck --save racecheck.dump ./debug-hazards > log
```
日志报 `WARN:(Warp Level Programming) Potential RAW hazard detected at __shared__ 0x7f in block (63,0,0)`，给出 Write Thread / Read Thread、指令地址、源码行、`Current Value`、host backtrace。先报 **RAW（读后写）** → 加 `__syncthreads` 后变 **WAR（写后读）** → 再加一处同步点 → `RACECHECK SUMMARY: 0 hazards displayed`。共享内存 hazard 只在**同一线程块内**发生。

## A CASE STUDY：移植 C 程序到 CUDA C（crypt）

用 APOD 把 legacy 的 IDEA 加解密程序 `crypt` 完整走一遍。程序分三块：main 初始化、generateEncrypt/DecryptKey 生成密钥、encrypt_decrypt 以 **8 字节块**加解密。

### Assessing crypt
- 用 **gprof**（免费、低开销）分析：生成 1GB 样本数据后跑 gprof，`encrypt_decrypt` 占 **87.03%** 总时间 → 并行化就该打它。
- 热点本身是"遍历 chunk 链表"的循环；但下一迭代依赖当前元素的指针 → **i+1 依赖 i**，需消除该依赖才能并行。

### Parallelizing crypt
两阶段：① 改控制流/数据结构使其易并行；② 把计算 kernel 移植到 CUDA C 并插入 CUDA API（cudaMalloc/cudaMemcpy）。
- **链表 → 数组**：消除 i+1↔i 依赖（用偏移索引取 chunk）；数组还能直接 `cudaMemcpy`，而链表含指针需改设备侧地址。
- 抽出核心计算 `doCrypt`（带输入/输出全局指针），`encrypt_decrypt` 标 `__global__`、把循环改成按线程 ID 处理相邻 chunk；新增 `encrypt_decrypt_driver` 负责**内存管理**（分配、传数据、释放）并按 chunk 数定 launch 配置。
- 结果：computation 主体已在 CUDA 上跑，但有明显优化空间。

### Optimizing crypt（性能驱动，迭代）

| 版本 | 性能 (KB/ms) | 关键优化 |
|---|---|---|
| Parallelized Implementation | 588.30 | 初版 CUDA，同步拷贝、未重叠 |
| Optimized with Overlap | 867.58 | 去掉无谓的 crypt 输出数组上行拷贝；分块 + `cudaMemcpyAsync` + 多流，实现计算/通信重叠（Table 10-2）|
| Optimized with Constant Memory | 1062.16 | `key` 放入 `__constant__`（广播优化，不再 warp 全阻塞读同一全局 4B），`cudaMemcpyToSymbolAsync` 传输（Table 10-3）|
| Optimized Thread Configurations | 1198.72 | 调 `threads/block`（见下，Table 10-5 累计值）|

- **Overlap**：`crypt` 中 `key` 是纯输出数组，上行拷贝无价值 → 去掉；按 `nBlocks` 分块，每块在独立流里做 `cudaMemcpyAsync`(H2D)→`encrypt_decrypt<<<...>>>`→`cudaMemcpyAsync`(D2H) + `cudaEventRecord`，实现流间重叠。
- **Constant Memory**：每线程同时读 `key` 同一位置 → warp 被阻塞读同一全局 4B，带宽利用率低；放入 constant memory 优化广播。
- **Thread Configuration（Table 10-4，单独调 block 大小）**：

  | Threads/Block | 性能 (KB/ms) |
  |---|---|
  | 32 | 725.54 |
  | 64 | 1165.65 |
  | **128** | **1268.07（最佳）** |
  | 256 | 1198.72 |
  | 512 | 1062.26 |
  | 1024 | 849.59 |

  默认 512 尚可，但 128 线程/块提升约 19%；原因是 512 时每线程分到的寄存器更少 → 更多 I/O 阻塞、计算利用率低。

- nvvp 还报过"全局带宽仅 12.5%"：因每个线程按 chunk 跨步、每次 load 单字节，缓存硬件把稀疏单字节 load 变成两次 128B 全局 load——实际 1/8 被用上；但后续引用会命中 L1/L2，**并非真问题**，需结合应用知识判断而非盲信 metric。

### Deploying Crypt（部署）
- **Multi-GPU**：`cuda.flexible.cu` 按 `cudaErrorNoDevice` 自动回退 host 执行；用 `cudaSetDevice(d)` 把工作切到所有可用 GPU；`doCrypt` 标 `__host__ __device__` 共享同一算法、减重复代码。
- **Hybrid OpenMP-CUDA**：CPU 与 GPU 并行协作两类：
  - **Data-parallel hybrid**：CPU 跑同数据并行计算（当"另一设备"），用 `__host__ __device__` 共用逻辑。
  - **Task-parallel hybrid**：CPU 跑更适 host 的、控制流复杂/访问不规则的任务。
  - `crypt.openmp.cu`：用 `#pragma omp parallel for` 标记 host 端 `h_encrypt_decrypt` 循环；新增 `cpu-percent` 参数切分 CPU/GPU 工作量；异步 CUDA 调用返回主机后启动 CPU 线程。
  - **Table 10-6（对 crypt，把工作放 CPU 从不利）**：0%CPU/100%GPU = 4387 KB/ms，随 CPU 占比升高性能单调下降（CPU 线程开销 + 计算慢）；但 HPL 基准等应用 hybrid 反而最优——示"CPU/GPU 协作对部分应用才有收益"。

## SUMMARY（本章总结）

- **APOD** 四步迭代（Assessment → Parallelization → Optimization → Deployment）是 NVIDIA 推荐的 CUDA 开发流程，本质是软件工程的螺旋模型，用于把 legacy 顺序 C 程序变为可生产部署的高性能 CUDA 程序。
- **优化优先级**：暴露足够并行度 > 优化内存访问（对齐合并、L1/L2、共享 bank/padding）> 优化指令执行（隐藏延迟、避免 warp 发散、谨慎同步）。
- **编译**：CUDA 5.0+ 支持分离编译（`-dc`/`-dlink`），便于移植 legacy C、增量编译、复用/产出库；C 工程通过 `extern "C"` 包装 kernel 启动接入；生产代码用 `CHECK` 宏做错误检查。
- **性能驱动优化工具**：`nvprof`（四种模式 + 关键 metrics：gld/gst_efficiency、bank conflict、register spilling、inst_issued vs inst_executed、branch_efficiency）、`nvvp`（六视图、guided/unguided 分析）、`NVTX`（标注主机侧区间供可视化）。
- **调试**：kernel 调试用 cuda-gdb / printf / assert；内存调试用 cuda-memcheck（memcheck 查越界/泄漏、racecheck 查共享内存 hazard）；编译时 `-lineinfo` + 符号信息。
- **案例 crypt** 走完 APOD：gprof 定位 87% 在 `encrypt_decrypt` → 链表改数组 + 手写 kernel → 重叠传输（868）/常量内存（1062）→ 调 block 配置（≈1198）→ 多 GPU/混合执行，性能相对初版 CUDA 实现**翻倍以上**。
