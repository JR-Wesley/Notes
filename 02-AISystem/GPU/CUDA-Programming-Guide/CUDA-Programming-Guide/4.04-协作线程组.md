## 4.4. Cooperative Groups（协作线程组）

来源：[CUDA Programming Guide — Cooperative Groups](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cooperative-groups.html)

### 4.4.1. Introduction（简介）

> Cooperative Groups are an extension to the CUDA programming model for organizing groups of collaborating threads. Cooperative Groups allow developers to control the granularity at which threads are collaborating, helping them to express richer, more efficient parallel decompositions. Cooperative Groups also provide implementations of common parallel primitives like scan and parallel `reduce`.

Cooperative Groups 是 CUDA programming model 的扩展，用于组织相互协作的线程组。它允许开发者控制线程协作的粒度，从而表达更丰富、更高效的并行任务划分，并提供 scan、parallel `reduce` 等常见并行原语的实现。

> Historically, the CUDA programming model has provided a single, simple construct for synchronizing cooperating threads: a barrier across all threads of a thread block, as implemented with the `__syncthreads()` intrinsic function. In an effort to express broader patterns of parallel interaction, many performance-oriented programmers have resorted to writing their own ad hoc and unsafe primitives for synchronizing threads within a single warp, or across sets of thread blocks running on a single GPU. Whilst the performance improvements achieved have often been valuable, this has resulted in an ever-growing collection of brittle code that is expensive to write, tune, and maintain over time and across GPU generations. Cooperative Groups provides a safe and future-proof mechanism for writing performant code.

过去，CUDA programming model 为协作线程提供的基本同步结构，是通过 `__syncthreads()` intrinsic 实现的、覆盖整个 thread block 的 barrier。为了表达更广泛的并行交互模式，许多追求性能的程序员自行编写临时且不安全的原语，用于单个 warp 内或同一 GPU 上多个 thread block 之间的同步。这些做法往往带来了有价值的性能提升，但也积累了大量脆弱代码，其编写、调优以及跨时间和 GPU 代际的维护成本很高。Cooperative Groups 为编写高性能代码提供了安全且面向未来兼容性的机制。

> The full Cooperative Groups API is available in the Cooperative Groups API.

完整接口见 Cooperative Groups API。

**解读：** Group handle 把“哪些线程必须一起参与”显式传给函数，便于写出可复用的并行算法。它不会替调用方修复参与线程缺失、错误分支或数据竞争；安全性仍依赖正确遵守 collective 的调用规则。

Cooperative Groups 通过 Cooperative Group Handle 管理。参与线程可以通过 handle 查询自己在 group 中的位置、group 大小及其他信息。下表列出部分成员函数。

> | `dim_threads()` | The 3D dimensions of the launched block in units of threads. |

| 访问器 | 返回值 |

完整成员函数列表见 Cooperative Groups API。

**解读：** `thread_rank()` 是 group 内的一维编号，`thread_index()` 是表中 thread block 的三维坐标。对 subgroup 应按其自身 rank 理解索引，不能默认它等于 `threadIdx.x`。不同 group 类型提供的成员函数也不完全相同，不能把这张选摘表当作所有类型的统一接口。参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

### 4.4.3. Default Behavior / Groupless Execution（默认行为与未显式分组的执行）

> Groups representing the grid and thread blocks are implicitly created based on the kernel launch configuration. These “implicit” groups provide a starting point that developers can explicitly decompose into finer grained groups. Implicit groups can be accessed using the following methods:

表示 grid 和 thread block 的 group 根据 kernel launch configuration 隐式创建。开发者可以从这些 implicit group 出发，显式划分出粒度更细的 group。通过以下方法访问 implicit group：

> **Table 11 Cooperative Groups Implicitly Created by CUDA Runtime**

**表 11 CUDA Runtime 隐式创建的 Cooperative Group**

> | Accessor | Group Scope |
> | --- | --- |
> | `this_thread_block()` | Returns the handle to a group containing all threads in current thread block. |
> | `this_grid()` | Returns the handle to a group containing all threads in the grid. |
> | `coalesced_threads()` [1] | Returns the handle to a group of currently active threads in a warp. |
> | `this_cluster()` [2] | Returns the handle to a group of threads in the current cluster. |

| 访问器 | Group 范围 |
| --- | --- |
| `this_thread_block()` | 包含当前 thread block 全部线程的 group handle。 |
| `this_grid()` | 包含整个 grid 全部线程的 group handle。 |
| `coalesced_threads()` [1] | 包含 warp 中当前 active 线程的 group handle。 |
| `this_cluster()` [2] | 包含当前 cluster 内线程的 group handle。 |

> **[1]** The `coalesced_threads()` operator returns the set of active threads at that point in time, and makes no guarantee about which threads are returned (as long as they are active) or that they will stay coalesced throughout execution.

**[1]** `coalesced_threads()` 返回调用时处于 active 状态的线程集合。除要求线程处于 active 状态外，它不保证具体返回哪些线程，也不保证这些线程在整个执行过程中始终保持 coalesced。

> **[2]** The `this_cluster()` assumes a 1x1x1 cluster when a non-cluster grid is launched. Requires Compute Capability 9.0 or greater.

**[2]** 当启动未配置 cluster 的 grid 时，`this_cluster()` 按 1×1×1 cluster 处理。此接口要求 Compute Capability 9.0 或更高。

> More information is available in the Cooperative Groups API.

更多信息见 Cooperative Groups API。

**解读：** `coalesced_threads()` 描述当前执行点的 active 线程，group 大小不保证为完整 warp。这里的 coalesced 指线程执行集合，不是“访存一定合并”。获取 grid handle 与具备 grid 同步能力也不同，后者还受 launch 方式限制。

#### 4.4.3.1. Create Implicit Group Handles As Early As Possible（尽早创建 Implicit Group Handle）

> For best performance it is recommended that you create a handle for the implicit group upfront (as early as possible, before any branching has occurred) and use that handle throughout the kernel.

为获得最佳性能，原文建议提前创建 implicit group 的 handle，即尽可能在任何分支发生前创建，并在整个 kernel 中持续使用该 handle。

#### 4.4.3.2. Only Pass Group Handles by Reference（只通过引用传递 Group Handle）

> It is recommended that you pass group handles by reference to functions when passing a group handle into a function. Group handles must be initialized at declaration time, as there is no default constructor. Copy-constructing group handles is discouraged.

将 group handle 传入函数时，原文建议按引用传递。Group handle 没有默认构造函数，必须在声明时初始化；不建议通过拷贝构造创建 group handle。

**解读：** 提前获取 block/grid 等稳定 scope 的 handle，能让后续函数共享明确的协作范围。但若算法就是要获得某个分支内当前 active 线程组成的 coalesced group，则应在那个执行点获取，不能把它提前到分支之前而改变参与集合。

### 4.4.4. Creating Cooperative Groups（创建 Cooperative Group）

> Groups are created by partitioning a parent group into subgroups. When a group is partitioned, a group handle is created to manage the resulting subgroup. The following partitioning operations are available to developers:

可以将 parent group 划分为 subgroup 来创建 group。划分时会创建 group handle，用于管理产生的 subgroup。可用的划分操作如下：

> **Table 12 Cooperative Group Partitioning Operations**

**表 12 Cooperative Group 划分操作**

> | Partition Type | Description |
> | --- | --- |
> | `tiled_partition` | Divides parent group into a series of fixed-size subgroups arranged in a one-dimensional, row-major format. |
> | `labeled_partition` | Divides parent group into one-dimensional subgroups based on a conditional label, which can be any integral type. |
> | `binary_partition` | Specialized form of labeled partitioning where label can only be “0” or “1”. |

| 划分类型 | 说明 |
| --- | --- |
| `tiled_partition` | 将 parent group 按一维、行优先顺序划分为一系列固定大小的 subgroup。 |
| `labeled_partition` | 根据条件 label 将 parent group 划分为一维 subgroup；label 可以是任意整数类型。 |
| `binary_partition` | Labeled partition 的特化形式，label 只能是 0 或 1。 |

> The following example shows how a tiled partition is created:

下面的示例展示如何创建 tiled partition：

```cpp
namespace cg = cooperative_groups;
// Obtain the current thread's cooperative group
cg::thread_block my_group = cg::this_thread_block();

// Partition the cooperative group into tiles of size 8
cg::thread_block_tile<8> my_subgroup = cg::tiled_partition<8>(my_group);

// do work as my_subgroup
```

> The best partitioning strategy to use depends on the context. More information is available in the Cooperative Groups API.

最合适的划分策略取决于具体场景。更多信息见 Cooperative Groups API。

**解读：** `tiled_partition<8>` 将父 group 的线程按线性顺序划成多个 8 线程 tile，每个线程拿到自己所属 tile 的 handle；它不会生成额外线程。尺寸和 parent 类型必须满足 partition API 的约束，不能从表中的概述推断任意 group 都可采用任意划分方式。

#### 4.4.4.1. Avoiding Group Creation Hazards（避免 Group 创建过程中的风险）

> Partitioning a group is a collective operation and all threads in the group must participate. If the group was created in a conditional branch that not all threads reach, this can lead to deadlocks or data corruption.

划分 group 是 collective operation，parent group 中的所有线程都必须参与。如果在并非所有线程都能到达的条件分支中创建 group，可能导致死锁或数据损坏。

**解读：** Collective 的参与要求以传入的 parent group 为准。若 parent 是整个 block，就不能只让一个分支中的部分线程调用 partition；应让全部 parent 成员共同划分，再以所得 subgroup 的范围协作。只把 handle 变量声明放进分支，并不会自动缩小 parent 的参与集合。

### 4.4.5. Synchronization（同步）

> Prior to the introduction of Cooperative Groups, the CUDA programming model only allowed synchronization between thread blocks at a kernel completion boundary. Cooperative groups allows developers to synchronize groups of cooperating threads at different granularities.

在 Cooperative Groups 引入之前，CUDA programming model 只允许在 kernel 完成边界进行 thread block 之间的同步。Cooperative Groups 使开发者能够在不同粒度上同步相互协作的线程组。

#### 4.4.5.1. Sync（Sync 同步）

> You can synchronize a group by calling the collective `sync()` function. Like `__syncthreads()`, the `sync()` function makes the following guarantees:

可以调用 collective `sync()` 函数同步一个 group。与 `__syncthreads()` 类似，`sync()` 提供以下保证：

- > All memory accesses (e.g., reads and writes) made by threads in the group before the synchronization point are visible to all threads in the group after the synchronization point.

  Group 中线程在同步点之前进行的全部内存访问，例如读写，在同步点之后对该 group 的所有线程可见。

- > All threads in the group reach the synchronization point before any thread is allowed to proceed beyond it.

  在任何线程获准越过同步点之前，group 中所有线程都必须到达该同步点。

> The following example shows a `cooperative_groups::sync()` that is equivalent to `__syncthreads()`.

下面的 `cooperative_groups::sync()` 与 `__syncthreads()` 等价。

```cpp
namespace cg = cooperative_groups;

cg::thread_block my_group = cg::this_thread_block();

// Synchronize threads in the block
cg::sync(my_group);
```

> Cooperative groups can be used to synchronize the entire grid. As of CUDA 13, cooperative groups can no longer be used for multi-device synchronization. For details see the Large Scale Groups section.

Cooperative Groups 可以同步整个 grid。自 CUDA 13 起，它不再支持 multi-device synchronization。详见 Large Scale Groups 一节。

> More information about synchronization is available in the Cooperative Groups API.

更多同步信息见 Cooperative Groups API。

**解读：** Sync 同时建立到达屏障与相应的内存可见性，但范围是指定 group。一个 tile 的 sync 不会等待其他 tile，一个 block 的 sync 也不会等待其他 block。CUDA 13 移除 multi-device 同步属于功能边界，因此保留这个版本条件。

#### 4.4.5.2. Barriers（Barrier 屏障）

> Cooperative Groups provides a barrier API similar to `cuda::barrier` that can be used for more advanced synchronization. Cooperative Groups barrier API differs from `cuda::barrier` in a few key ways:

Cooperative Groups 提供类似 `cuda::barrier` 的 barrier API，用于更高级的同步。它与 `cuda::barrier` 有以下主要区别：

- > Cooperative Groups barriers are automatically initialized

  Cooperative Groups barrier 会自动初始化。

- > All threads in the group must arrive and `wait` at the barrier once per phase.

  Group 中所有线程在每个 phase 都必须执行一次 arrive 和一次 `wait`。

- > `barrier_arrive` returns an `arrival_token` object that must be passed into the corresponding `barrier_wait`, where it is consumed and cannot be used again.

  `barrier_arrive` 返回 `arrival_token` 对象，必须将它传给对应的 `barrier_wait`。Token 在那里被消耗，之后不能再次使用。

> Programmers must take care to avoid hazards when using Cooperative Groups barriers:

使用 Cooperative Groups barrier 时，程序员必须避免以下风险：

- > No collective operations can be used by a group after calling `barrier_arrive` and before calling `barrier_wait`.

  Group 在调用 `barrier_arrive` 之后、`barrier_wait` 之前，不能执行 collective operation。

- > `barrier_wait` only guarantees that all threads in the group have called `barrier_arrive`. `barrier_wait` does NOT guarantee that all threads have called `barrier_wait`.

  `barrier_wait` 只保证 group 中所有线程都已调用 `barrier_arrive`，不保证所有线程都已调用 `barrier_wait`。

```cpp
namespace cg = cooperative_groups;

cg::thread_block my_group = this_block();
cg::cluster_group cluster = this_cluster();

auto token = cluster.barrier_arrive();

// Optional: Do some local processing to hide the synchronization latency
     local_processing(my_group);

// Make sure all other blocks in the cluster are running and initialized shared data before accessing dsmem
cluster.barrier_wait(std::move(token));
```

**解读与原文代码勘误：** Arrive 声明已到达本 phase，wait 再等待其他成员都 arrive；两者之间的工作必须不依赖尚未完成的同步，也不能在同一 group 上发起其他 collective。示例只定义了 namespace alias，`this_block()` 应改用 `cg::this_thread_block()`，`this_cluster()` 应写为 `cg::this_cluster()`；片段也省略了 shared data 的初始化。`local_processing(my_group)` 使用的是 block handle，不能据此认为允许在尚未 wait 的 cluster 上再执行 collective。

### 4.4.6. Collective Operations（Collective Operation）

> Cooperative Groups includes a set of collective operations that can be performed by a group of threads. These operations require participation of all threads in the specified group in order to complete the operation.

Cooperative Groups 提供一组由线程组共同执行的 collective operation。这些操作要求指定 group 中的所有线程参与，才能完成。

> All threads in the group must pass the same values for corresponding arguments to each collective call, unless different values are explicitly allowed in the Cooperative Groups API. Otherwise the behavior of the call is undefined.

除非 Cooperative Groups API 明确允许不同值，group 中所有线程在每次 collective 调用中，对应参数必须传入相同值；否则调用行为未定义。

**解读：** “参数一致”有明确例外，例如 reduce/scan 的输入值本来就可由各线程分别提供。相反，代表同一次集体操作的 group、复制范围等控制参数，不能未经 API 允许就随线程任意变化。

#### 4.4.6.1. Reduce（Reduce 归约）

> The `reduce` function is used to perform a parallel reduction on the data provided by each thread in the specified group. The type of reduction must be specified by providing one of the operators shown in the following table.

`reduce` 对指定 group 中每个线程提供的数据执行并行归约。必须通过下表中的某个 operator 指定归约类型。

> **Table 13 Cooperative Groups Reduction Operators**

**表 13 Cooperative Groups 归约 Operator**

> | Operator | Returns |
> | --- | --- |
> | `plus` | Sum of all values in group |
> | `less` | Minimum value |
> | `greater` | Maximum value |
> | `bit_and` | Bitwise AND reduction |
> | `bit_or` | Bitwise OR reduction |
> | `bit_xor` | Bitwise XOR reduction |

| Operator | 归约结果 |
| --- | --- |
| `plus` | Group 中所有值之和。 |
| `less` | 最小值。 |
| `greater` | 最大值。 |
| `bit_and` | 按位 AND 归约。 |
| `bit_or` | 按位 OR 归约。 |
| `bit_xor` | 按位 XOR 归约。 |

> Hardware acceleration is used for reductions when available (requires Compute Capability 8.0 or greater). A software fallback is available for older hardware where hardware acceleration is not available. Only 4B types are accelerated by hardware.

在可用时，归约会使用硬件加速，这要求 Compute Capability 8.0 或更高。较旧硬件没有该加速时，会采用软件回退实现。只有 4 字节类型可以获得硬件加速。

**解读：** 表中的 `less`、`greater` 返回较小值和较大值，不能按返回布尔值的比较器理解。“4 字节”也只是硬件归约的必要条件之一；例如 `float` 求和不会因为大小为 4 字节就自动使用整数归约指令。参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

> More information about reductions is available in the Cooperative Groups API.

更多归约信息见 Cooperative Groups API。

> The following example shows how to use `cooperative_groups::reduce()` to perform a block-wide sum reduction.

下面的示例展示使用 `cooperative_groups::reduce()` 进行 block 范围的求和归约。

```cpp
namespace cg = cooperative_groups;

cg::thread_block my_group = cg::this_thread_block();

int val = data[threadIdx.x];

int sum = cg::reduce(my_group, val, cg::plus<int>());

// Store the result from the reduction
if (my_group.thread_rank() == 0) {
   result[blockIdx.x] = sum;
}
```

**原文适用性说明：** API 参考为 `reduce` 列出的 group 类型是 `coalesced_group` 和 `thread_block_tile`，与此处直接传 `thread_block` 的示例不一致，不能把该代码视为已验证的 block-wide 实现。另外，`data[threadIdx.x]` 未包含 block 偏移，并隐含一维 block 的索引假设；扩展为各 block 处理不同数据时必须重新设计索引。原代码保留。参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

#### 4.4.6.2. Scans（Scan 扫描）

> Cooperative Groups includes implementations of `inclusive_scan` and `exclusive_scan` that can be used on arbitrary group sizes. The functions perform a scan operation on the data provided by each thread named in the specified group.

Cooperative Groups 提供 `inclusive_scan` 和 `exclusive_scan`。原文称它们可以用于任意 group 大小；这些函数对指定 group 中各线程提供的数据执行 scan。

> Programmers can optionally specify a reduction operator, as listed in Reduction Operators Table above.

程序员可以选择性地指定归约 operator，见上面的 Reduction Operators 表。

```cpp
namespace cg = cooperative_groups;

cg::thread_block my_group = cg::this_thread_block();

int val = data[my_group.thread_rank()];

int exclusive_sum = cg::exclusive_scan(my_group, val, cg::plus<int>());

result[my_group.thread_rank()] = exclusive_sum;
```

> More information about scans is available in the Cooperative Groups Scan API.

更多 scan 信息见 Cooperative Groups Scan API。

**解读与原文适用性说明：** 以按 rank 排列的输入 2、3、5、7 为例，求和 inclusive scan 得到 2、5、10、17，exclusive scan 得到 0、2、5、10。后者常用于根据各线程的输出数量计算写入起始位置。API 参考对 scan 同样列出 `coalesced_group` 和 `thread_block_tile`，所以“任意 group 大小”不能理解为支持所有 group 类型；此处 `thread_block` 示例也需核对。若多个 block 共用同一个 `result`，按 block 内 rank 直接写出还会发生地址重叠。参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

#### 4.4.6.3. Invoke One（Invoke One：由一个线程执行）

> Cooperative Groups provides an `invoke_one` function for use when a single thread must perform a serial portion of work on behalf of a group.

当需要一个线程代表整个 group 执行一段串行工作时，可以使用 Cooperative Groups 的 `invoke_one`。

- > `invoke_one` selects a single arbitrary thread from the calling group and uses that thread to call the supplied invocable function using the supplied arguments.

  `invoke_one` 从调用 group 中任意选择一个线程，让该线程使用所提供的参数调用指定的 invocable function。

- > `invoke_one_broadcast` is the same as `invoke_one` except the result of the call is also broadcast to all threads in the group.

  `invoke_one_broadcast` 与 `invoke_one` 相同，但还会将函数调用的返回结果广播给 group 中所有线程。

> The thread selection mechanism is not guaranteed to be deterministic.

线程选择机制不保证确定性。

> The following example shows basic `invoke_one` utilization.

下面的示例展示 `invoke_one` 的基本用法。

```cpp
namespace cg = cooperative_groups;
cg::thread_block my_group = cg::this_thread_block();

// Ensure only one thread in the thread block prints the message
cg::invoke_one(my_group, []() {
   printf("Hello from one thread in the block!");
});

// Synchronize to make sure all threads wait until the message is printed
cg::sync(my_group);
```

> Communication or synchronization within the calling group is not allowed inside the invocable function. Communication with threads outside of the calling group is allowed.

Invocable function 内不允许与调用 group 内的其他线程通信或同步；允许与调用 group 之外的线程通信。

**解读：** `invoke_one` 选择代表线程，但不保证选 rank 0，也不保证每次都选同一线程。只让代表线程执行的函数若再等待 group 内其他成员参与，就可能无法完成；示例把 `sync` 放在函数调用之后，让所有线程都能参与。`invoke_one_broadcast` 适合还需要把代表线程算出的返回值交给各成员的情况。

### 4.4.7. Asynchronous Data Movement（异步数据移动）

> Cooperative Groups `memcpy_async` functionality in CUDA provides a way to perform asynchronous memory copies between global memory and shared memory. `memcpy_async` is particularly useful for optimizing memory transfers and overlapping computation with data transfer to improve performance.

CUDA Cooperative Groups 的 `memcpy_async` 提供 global memory 与 shared memory 之间的异步内存复制功能，有助于优化内存传输，并通过计算与传输重叠提高性能。

> The `memcpy_async` function is used to start an asynchronous load from global memory to shared memory. `memcpy_async` is intended to be used like a “prefetch” where data is loaded before it is needed.

`memcpy_async` 用于发起从 global memory 到 shared memory 的异步加载。它的预期用法类似 prefetch，即在需要数据之前提前加载。

> The `wait` function forces all threads in a group to `wait` until the asynchronous memory transfer is completed. `wait` must be called by all threads in the group before the data can be accessed in shared memory.

`wait` 使 group 中所有线程等待异步内存传输完成。访问 shared memory 中的数据之前，group 中所有线程都必须调用 `wait`。

> The following example shows how to use `memcpy_async` and `wait` to prefetch data.

下面的示例展示通过 `memcpy_async` 和 `wait` 预取数据。

```cpp
namespace cg = cooperative_groups;

cg::thread_group my_group = cg::this_thread_block();

__shared__ int shared_data[];

// Perform an asynchronous copy from global memory to shared memory
cg::memcpy_async(my_group, shared_data + my_group.rank(), input + my_group.rank(), sizeof(int));

// Hide latency by doing work here. Cannot use shared_data

// Wait for the asynchronous copy to complete
cg::wait(my_group);

// Prefetched data is now available
```

**原文代码勘误：** `my_group.rank()` 应使用文档中的 `thread_rank()`。未给定长度的 shared 数组若表示动态 shared memory，应声明为 `extern __shared__ int shared_data[]` 并在 launch 时提供空间。更关键的是，这里每个线程给 group-wide `memcpy_async` 传入不同的源、目标指针，违反本节的 collective 参数一致要求；需要由 group 共同描述同一复制范围，不能照搬为“每个线程各复制一个 int”。原代码保持不改，参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

> See the Cooperative Groups API for more information.

更多信息见 Cooperative Groups API。

#### 4.4.7.1. Memcpy Async Alignment Requirements（Memcpy Async 的对齐要求）

> `memcpy_async` is only asynchronous if the source is global memory and the destination is shared memory and both are at least 4-byte aligned. For achieving best performance: an alignment of 16 bytes for both shared memory and global memory is recommended.

只有源位于 global memory、目标位于 shared memory，且两者都至少按 4 字节对齐时，`memcpy_async` 才能异步执行。为获得最佳性能，原文建议源和目标都按 16 字节对齐。

**解读：** 对齐正确还不够，硬件异步 global-to-shared 路径还要求 Compute Capability 8.0 及以上。等待之前的独立计算不能读取目标数据，也不能覆盖复制仍需读取的源数据；真正有收益的前提是存在可与传输重叠的工作。参见 [Cooperative Groups API](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html#cooperative-groups-api)。

### 4.4.8. Large Scale Groups（大范围线程组）

> Cooperative Groups allows for large groups that span the entire grid. All Cooperative Group functionality described previously is available to these large groups, with one notable exception: synchronizing the entire grid requires using the `cudaLaunchCooperativeKernel` runtime launch API.

Cooperative Groups 支持覆盖整个 grid 的大型 group。原文称前面介绍的全部功能都可用于这些大型 group，但有一个显著例外：同步整个 grid 必须使用 Runtime API `cudaLaunchCooperativeKernel` 启动。

> Multi-device launch APIs and related references for Cooperative Groups have been removed as of CUDA 13.

自 CUDA 13 起，Cooperative Groups 的 multi-device launch API 及相关引用已被移除。

**原文范围说明：** “前述全部功能都适用于大 group”的说法过宽：例如前文 reduce/scan 的 API 类型约束并未包含 `grid_group`。Grid 范围的 handle 和同步能力，不能用来推导所有 collective 都支持 grid。该句英文和对应译文均保留，使用时按具体 API 的 group 类型约束判断。

#### 4.4.8.1. When to use `cudaLaunchCooperativeKernel`（何时使用 `cudaLaunchCooperativeKernel`）

> `cudaLaunchCooperativeKernel` is a CUDA runtime API function used to launch a single-device kernel that employs cooperative groups, specifically designed for executing kernels that require inter-block synchronization. This function ensures that all threads in the kernel can synchronize and cooperate across the entire grid, which is not possible with traditional CUDA kernels that only allow synchronization within individual thread blocks. `cudaLaunchCooperativeKernel` ensures that the kernel launch is atomic, i.e. if the API call succeeds, then the provided number of thread blocks will launch on the specified device.

`cudaLaunchCooperativeKernel` 是用于启动单 device kernel 的 CUDA Runtime API，专门面向需要 block 间同步、使用 Cooperative Groups 的 kernel。它确保 kernel 中所有线程能够跨整个 grid 同步和协作，而传统 kernel 仅允许在单个 thread block 内同步。它还保证 kernel launch 是 atomic 的：如果调用成功，指定数量的 thread block 就会在指定 device 上启动。

> It is good practice to first ensure the device supports cooperative launches by querying the device attribute `cudaDevAttrCooperativeLaunch`:

应先查询 `cudaDevAttrCooperativeLaunch`，确认 device 支持 cooperative launch：

```cpp
int dev = 0;
int supportsCoopLaunch = 0;
cudaDeviceGetAttribute(&supportsCoopLaunch, cudaDevAttrCooperativeLaunch, dev);
```

> which will set supportsCoopLaunch to 1 if the property is supported on device 0. Only devices with compute capability of 6.0 and higher are supported. In addition, you need to be running on either of these:

如果 device 0 支持该属性，上述查询会将 supportsCoopLaunch 设为 1。只支持 compute capability 6.0 及以上的 device，并且还需要满足以下平台条件之一：

- > The Linux platform without MPS

  未启用 MPS 的 Linux 平台。

- > The Linux platform with MPS and on a device with compute capability 7.0 or higher

  启用 MPS 的 Linux 平台，且 device 的 compute capability 为 7.0 或更高。

- > The latest Windows platform

  最新的 Windows 平台。

**解读：** 仅查询到 cooperative launch 支持仍不够，grid 大小还受 kernel 的寄存器、shared memory 和 occupancy 限制。可用 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 结合 SM 数量估算可驻留的 block 上限；超限可能返回 `cudaErrorCooperativeLaunchTooLarge`。这里 launch 的 atomic 性不表示所有线程在同一时刻执行每条指令，也不使 kernel 内普通内存操作自动具有原子性。原文“最新 Windows”未给出明确版本，实际应结合设备属性与所用 Toolkit 的平台要求判断。参见 [Cooperative Kernel Launch API](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__EXECUTION.html)。本章代码仅作整理与静态核对，未编译或运行。
