## 3.3. The CUDA Driver API（CUDA 驱动 API）

> Previous sections of this guide have covered the CUDA runtime. As mentioned in CUDA Runtime API and CUDA Driver API, the CUDA runtime is written on top of the lower level CUDA driver API. This section covers some of the differences between the CUDA runtime and the driver APIs, as well has how to intermix them. Most applications can operate at full performance without ever needing to interact with the CUDA driver API. However, new interfaces are sometimes available in the driver API earlier than the runtime API, and some advanced interfaces, such as Virtual Memory Management, are only exposed in the driver API.

本指南前面的章节介绍了 CUDA Runtime。如 CUDA Runtime API and CUDA Driver API 一节所述，CUDA Runtime 构建在更底层的 CUDA Driver API 之上。本节介绍两者的一些差异，以及如何混合使用它们。大多数应用无需直接使用 Driver API，也能充分发挥性能。不过，一些新接口有时会先出现在 Driver API 中，之后才提供 Runtime API；某些高级接口，例如 Virtual Memory Management，则仅通过 Driver API 提供。

> The driver API is implemented in the cuda dynamic library (`cuda.dll` or `cuda.so`) which is copied on the system during the installation of the device driver. All its entry points are prefixed with cu.

Driver API 实现在 cuda 动态库中，原文列出的名称为 `cuda.dll` 或 `cuda.so`；安装 device driver 时，该库会被复制到系统中。所有 Driver API 入口点都以 `cu` 为前缀。

**解读（库名勘误）：** Windows 上的 Driver API 库通常是 `nvcuda.dll`，Linux 上是 `libcuda.so`（运行时常见 `libcuda.so.1`），不是原文所写的两个文件名。参见 [NVIDIA 官方库路径说明](https://docs.nvidia.com/cuda/nvidia-matmul-heuristics/api.html)。

> It is a handle-based, imperative API: Most objects are referenced by opaque handles that may be specified to functions to manipulate the objects.

它是一套基于 handle（句柄）的命令式 API：大多数对象通过 opaque handle（不透明句柄）引用，调用函数时传入这些 handle，以操作对应对象。

> The objects available in the driver API are summarized in Table 6.

Driver API 提供的对象汇总于表 6。

表 6：CUDA Driver API 提供的对象。

**解读（历史对象名称）：** 表中 `CUtexref` 对应 texture reference，而 texture object 的 handle 为 `CUtexObject`。这里保留原表，避免将两套接口混为一谈；texture/surface reference 属于旧接口体系。参见 [CUDA Driver 头文件中的类型与接口](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/cuda_8h_source.html)。

> The driver API must be initialized with `cuInit()` before any function from the driver API is called. A CUDA context must then be created that is attached to a specific device and made current to the calling host thread as detailed in Context.

调用 Driver API 的任何函数之前，必须先使用 `cuInit()` 初始化 Driver API。随后需要创建一个绑定到特定 device 的 CUDA context，并将其设为调用 host thread 的 current context，详见 Context 一节。

> Within a CUDA context, kernels are explicitly loaded as PTX or binary objects by the host code as described in Module. Kernels written in C++ must therefore be compiled separately into PTX or binary objects. Kernels are launched using API entry points as described in Kernel Execution.

在 CUDA context 内，host code 显式地以 PTX 或二进制对象形式加载 kernel，详见 Module 一节。因此，以 C++ 编写的 kernel 必须先单独编译成 PTX 或二进制对象。Kernel 通过 API 入口点启动，详见 Kernel Execution 一节。

> Any application that wants to run on future device architectures must load PTX, not binary code. This is because binary code is architecture-specific and therefore incompatible with future architectures, whereas PTX code is compiled to binary code at load time by the device driver.

希望在未来 device architecture 上运行的应用，必须加载 PTX，而不是仅加载二进制代码。原文的理由是：二进制代码针对特定架构，因此与未来架构不兼容；PTX 则在加载时由 device driver 编译成二进制代码。

**解读（兼容性限定）：** Cubin 并非对所有后续 GPU 都不兼容；例如，同一 compute capability 主版本内，存在面向相同或更高次版本的兼容规则。保留 PTX 是覆盖未来架构的重要途径，也可以与已编译 Cubin 共存。具体目标及特殊架构后缀仍须符合兼容条件。参见 [CUDA 平台的兼容性说明](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/cuda-platform.html)。

> Here is the host code of the sample from Kernels written using the driver API:

下面是 Kernels 一节示例改用 Driver API 编写的 host code：

```cpp
int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

    // Allocate input vectors h_A and h_B in host memory
    float* h_A = (float*)malloc(size);
    float* h_B = (float*)malloc(size);

    // Initialize input vectors
    ...

    // Initialize
    cuInit(0);

    // Get number of devices supporting CUDA
    int deviceCount = 0;
    cuDeviceGetCount(&deviceCount);
    if (deviceCount == 0) {
        printf("There is no device supporting CUDA.\n");
        exit (0);
    }

    // Get handle for device 0
    CUdevice cuDevice;
    cuDeviceGet(&cuDevice, 0);

    // Create context
    CUcontext cuContext;
    cuCtxCreate(&cuContext, 0, cuDevice);

    // Create module from binary file
    CUmodule cuModule;
    cuModuleLoad(&cuModule, "VecAdd.ptx");

    // Allocate vectors in device memory
    CUdeviceptr d_A;
    cuMemAlloc(&d_A, size);
    CUdeviceptr d_B;
    cuMemAlloc(&d_B, size);
    CUdeviceptr d_C;
    cuMemAlloc(&d_C, size);

    // Copy vectors from host memory to device memory
    cuMemcpyHtoD(d_A, h_A, size);
    cuMemcpyHtoD(d_B, h_B, size);

    // Get function handle from module
    CUfunction vecAdd;
    cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

    // Invoke kernel
    int threadsPerBlock = 256;
    int blocksPerGrid =
            (N + threadsPerBlock - 1) / threadsPerBlock;
    void* args[] = { &d_A, &d_B, &d_C, &N };
    cuLaunchKernel(vecAdd,
                   blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                   0, 0, args, 0);

    ...
}
```

**解读（示例边界）：** 这个片段显式完成初始化、选择 device、创建 context、加载 module、分配与复制数据、查找 kernel，再发起执行。`args` 中放的是 host 变量的地址，例如 `&d_A`，Driver 从该位置取出设备指针值作为 kernel 参数；不能直接把 `d_A` 当作参数值存储区。

原例包含 `...` 占位，未给出 `VecAdd.ptx`、结果取回、错误处理与清理逻辑。`VecAdd` 必须与 module 中实际导出的符号名匹配；C++ 名称修饰也要考虑。Grid 使用向上取整时，kernel 还需处理超过 N 的 thread。注释虽写 binary file，实际加载的是 PTX。

**解读（API 版本）：** 原例使用三参数 `cuCtxCreate`；所查新版签名增加了 `CUctxCreateParams*` 参数。应匹配所用 Toolkit 头文件及接口版本，不能将原调用直接套用到所有版本。参见 [Context Management](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__CTX.html)。

### 3.3.1. Context（上下文）

> A CUDA context is analogous to a CPU process. All resources and actions performed within the driver API are encapsulated inside a CUDA context, and the system automatically cleans up these resources when the context is destroyed. Besides objects such as modules and texture or surface references, each context has its own distinct address space. As a result, `CUdeviceptr` values from different contexts reference different memory locations.

CUDA context 类似于 CPU process。通过 Driver API 执行的资源管理和操作封装在 context 中，context 销毁时，系统会自动清理这些资源。除了 module、texture reference、surface reference 等对象，每个 context 还具有独立的地址空间。因此，来自不同 context 的 `CUdeviceptr` 值引用不同的内存位置。

**解读：** Context 与 CPU process 的对应是一种资源管理类比，并不意味着它是操作系统进程。指针或 handle 能否使用，要结合所属 context、映射关系和访问权限；仅将数值转换为另一种类型，不会转移资源所有权或自动取得跨 context 的访问权。

> A host thread may have only one device context current at a time. When a context is created with `cuCtxCreate()`, it is made current to the calling host thread. CUDA functions that operate in a context (most functions that do not involve device enumeration or context management) will return CUDA_ERROR_INVALID_CONTEXT if a valid context is not current to the thread.

一个 host thread 同一时刻只能有一个 current device context。使用 `cuCtxCreate()` 创建 context 时，它会成为调用 host thread 的 current context。需要在 context 中执行的 CUDA 函数，也就是大多数不属于 device 枚举或 context 管理的函数，在该 thread 没有有效 current context 时，会返回 CUDA_ERROR_INVALID_CONTEXT。

> Each host thread has a stack of current contexts. `cuCtxCreate()` pushes the new context onto the top of the stack. `cuCtxPopCurrent()` may be called to detach the context from the host thread. The context is then “floating” and may be pushed as the current context for any host thread. `cuCtxPopCurrent()` also restores the previous current context, if any.

每个 host thread 都有一个 current context stack。`cuCtxCreate()` 将新 context 压入栈顶。可以调用 `cuCtxPopCurrent()`，将 context 从 host thread 上解除绑定；它随后处于“游离”状态，可以被压入任意 host thread 的栈并成为 current context。`cuCtxPopCurrent()` 还会恢复此前的 current context（如果存在）。

> A usage count is also maintained for each context. `cuCtxCreate()` creates a context with a usage count of 1. `cuCtxAttach()` increments the usage count and `cuCtxDetach()` decrements it. A context is destroyed when the usage count goes to 0 when calling `cuCtxDetach()` or `cuCtxDestroy()`.

每个 context 还维护一个 usage count（使用计数）。`cuCtxCreate()` 创建 context 时，计数为 1；`cuCtxAttach()` 增加计数，`cuCtxDetach()` 减少计数。原文描述为：调用 `cuCtxDetach()` 或 `cuCtxDestroy()` 时，若使用计数降为 0，context 就被销毁。

**解读（旧接口限定）：** `cuCtxAttach`、`cuCtxDetach` 已被标记为 deprecated，原文的使用计数流程应作为历史机制阅读。当前 `cuCtxDestroy` 是销毁指定 context，不能理解为普通的引用计数减一操作。参见 [已弃用的 Context 接口](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__CTX__DEPRECATED.html)及 [cuCtxDestroy 语义](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__CTX.html)。

> The driver API is interoperable with the runtime and it is possible to access the primary context (see Runtime Initialization) managed by the runtime from the driver API via `cuDevicePrimaryCtxRetain()`.

Driver API 可以与 Runtime 互操作；通过 `cuDevicePrimaryCtxRetain()`，可以从 Driver API 访问 Runtime 管理的 primary context，参见 Runtime Initialization。

**解读：** Retain primary context 与把它设为当前 context 是两步；取得 handle 后，应按调用需要设置当前 context，并在不再持有时配对 `cuDevicePrimaryCtxRelease`。这套生命周期管理不能与旧 `cuCtxAttach/cuCtxDetach` 流程混用。参见 [Primary Context Management](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__PRIMARY__CTX.html)。

> Usage count facilitates interoperability between third party authored code operating in the same context. For example, if three libraries are loaded to use the same context, each library would call `cuCtxAttach()` to increment the usage count and `cuCtxDetach()` to decrement the usage count when the library is done using the context. For most libraries, it is expected that the application will have created a context before loading or initializing the library; that way, the application can create the context using its own heuristics, and the library simply operates on the context handed to it. Libraries that wish to create their own contexts - unbeknownst to their API clients who may or may not have created contexts of their own - would use `cuCtxPushCurrent()` and `cuCtxPopCurrent()` as illustrated in the following figure.

使用计数有助于在同一个 context 中工作的第三方代码相互协作。例如，若加载了三个使用同一 context 的库，每个库都可以调用 `cuCtxAttach()` 增加计数，并在用完 context 后调用 `cuCtxDetach()` 减少计数。对于大多数库，通常预期应用在加载或初始化库之前已创建 context：应用根据自己的策略创建 context，库则操作传入的 context。如果库希望自行创建 context，而不让可能已创建或尚未创建自有 context 的 API 调用方感知，则可以按下图所示使用 `cuCtxPushCurrent()` 与 `cuCtxPopCurrent()`。

### 3.3.2. Module（模块）

> Modules are dynamically loadable packages of device code and data, akin to DLLs in Windows, that are output by `nvcc` (see Compilation with NVCC). The names for all symbols, including functions, global variables, and texture or surface references, are maintained at module scope so that modules written by independent third parties may interoperate in the same CUDA context.

Module 是可以动态加载的 device code 与 data 包，由 `nvcc` 生成，类似于 Windows DLL，参见 Compilation with NVCC。包括 function、global variable、texture reference 和 surface reference 在内的所有符号，其名称都在 module scope 内管理，因此独立第三方编写的 module 可以在同一个 CUDA context 中协同工作。

> This code sample loads a module and retrieves a handle to some kernel:

以下代码加载一个 module，并取得其中某个 kernel 的 handle：

```cpp
CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");
```

**解读：** Module handle 标识加载的代码与数据包，function handle 标识其中可启动的 kernel。查找名称必须是 module 中实际存在的符号；仅成功加载文件，还不代表指定 kernel 名称一定存在。

> This code sample compiles and loads a new module from PTX code and parses compilation errors:

以下代码从 PTX 编译并加载一个新 module，并处理编译错误：

```cpp
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2]  = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
```

**解读（示例边界）：** `"some PTX code"` 是占位文本，不是有效 PTX；按现代 C++ 规则，字符串字面量也不应直接赋给可写 `char*`。应提供真实、有效且满足终止要求的 PTX 内容，并采用合适的类型。`values` 的解释随 JIT option 改变：有的项传 buffer 地址，有的项在指针槽位中编码数值，不能将所有项都机械改成“取变量地址”。日志 buffer 应初始化，错误路径也应检查 API 返回的 `CUresult`。

> This code sample compiles, links, and loads a new module from multiple PTX codes and parses link and compilation errors:

以下代码将多份 PTX 编译、链接并加载为新 module，同时处理链接与编译错误：

```cpp
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);
```

**解读（原文代码勘误）：** `cuModuleLoadData(cuModule, cubin)` 的第一个参数应为 `&cuModule`，因为该参数用于写回 module handle。`cuLinkCreate`、各次 `cuLinkAddData`、`cuLinkComplete` 和 module load 都需检查结果；某步失败后，不能仅打印日志便继续使用尚未成功生成的输出。参见 [Module Management 接口签名](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MODULE.html)。

这里先完成链接，再加载结果，最后销毁 link state。Link state 与已加载 module 是不同对象；销毁前者不等于卸载后者。几段示例重复使用同名变量，应分别理解，不能直接连贴成同一作用域的完整程序。

> It’s possible to accelerate some parts of the module linking/loading process by using multiple threads, including when loading a cubin. This code sample uses `CU_JIT_BINARY_LOADER_THREAD_COUNT` to speed up module loading.

可以使用多个 thread 加速 module 链接或加载过程的某些部分，包括加载 Cubin。以下代码通过 `CU_JIT_BINARY_LOADER_THREAD_COUNT` 加快 module 加载。

```cpp
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0]  = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1]  = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2]  = 0; // Use as many threads as CPUs on the machine
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
```

**解读：** 这里增加的是 host 侧 module 加载工作的并行度，不是 kernel 的 CUDA thread 数。`"some cubin code"` 同样只是占位文本，实际需要有效的 Cubin 二进制数据。加载加速应通过初始化阶段耗时衡量，而不能仅凭设置线程数就认定执行 kernel 会更快。

完整代码见 ptxjit CUDA sample。

### 3.3.3. Kernel Execution（Kernel 执行）

> `cuLaunchKernel()` launches a kernel with a given execution configuration.

`cuLaunchKernel()` 使用给定的执行配置启动 kernel。

> Parameters are passed either as an array of pointers (next to last parameter of `cuLaunchKernel()`) where the nth pointer corresponds to the nth parameter and points to a region of memory from which the parameter is copied, or as one of the extra options (last parameter of `cuLaunchKernel()`).

参数有两种传递方式：一是指针数组，即 `cuLaunchKernel()` 的倒数第二个参数，数组中第 n 个指针对应 kernel 的第 n 个参数，并指向用于复制该参数值的内存区域；二是作为 extra option 传递，即使用 `cuLaunchKernel()` 的最后一个参数。

> When parameters are passed as an extra option (the `CU_LAUNCH_PARAM_BUFFER_POINTER` option), they are passed as a pointer to a single buffer where parameters are assumed to be properly offset with respect to each other by matching the alignment requirement for each parameter type in device code.

通过 extra option，即 `CU_LAUNCH_PARAM_BUFFER_POINTER` 选项传递参数时，需要传入指向单个 buffer 的指针。该 buffer 内各参数的相对偏移，必须满足它们在 device code 中对应类型的对齐要求。

**解读：** `kernelParams` 方式让 Driver 根据 kernel 的参数信息取值；buffer 方式则要求应用自己正确打包所有字段。两种方式不能同时传入非空参数。参见 [cuLaunchKernel 参数规则](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__EXEC.html)。

> Alignment requirements in device code for the built-in vector types are listed in Table 43. For all other basic types, the alignment requirement in device code matches the alignment requirement in host code and can therefore be obtained using `__alignof()`. The only exception is when the host compiler aligns double and long long (and long on a 64-bit system) on a one-word boundary instead of a two-word boundary (for example, using gcc’s compilation flag -mno-align-double) since in device code these types are always aligned on a two-word boundary.

Built-in vector type 在 device code 中的对齐要求见表 43。对于其他基本类型，device code 与 host code 的对齐要求相同，因此可以用 `__alignof()` 获取。唯一的例外是 host 编译器将 `double`、`long long`，以及 64 位系统上的 `long` 对齐到一个 word，而不是两个 word 的边界，例如使用 GCC 的 `-mno-align-double` 选项时；在 device code 中，这些类型始终按两个 word 的边界对齐。

> `CUdeviceptr` is an integer, but represents a pointer, so its alignment requirement is `__alignof(void*)`.

`CUdeviceptr` 虽然是整数类型，但表示指针，因此它的对齐要求为 `__alignof(void*)`。

> The following code sample uses a macro (`ALIGN_UP()`) to adjust the offset of each parameter to meet its alignment requirement and another macro (`ADD_TO_PARAM_BUFFER()`) to add each parameter to the parameter buffer passed to the `CU_LAUNCH_PARAM_BUFFER_POINTER` option.

下面的代码使用 `ALIGN_UP()` 宏调整每个参数的偏移，以满足对齐要求；再使用 `ADD_TO_PARAM_BUFFER()` 宏，将各参数加入传给 `CU_LAUNCH_PARAM_BUFFER_POINTER` 的参数 buffer。

```cpp
#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                   \
    do {                                                        \
        paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
        memcpy(paramBuffer + paramBufferSize,                   \
               &(value), sizeof(value));                        \
        paramBufferSize += sizeof(value);                       \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4's alignment is 16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2's alignment is 8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);
```

**解读（参数打包示例问题）：** 原例需要注意以下几点，代码保持原样以便对照。

| 位置 | 问题与处理 |
| --- | --- |
| `cuLaunchKernel` 的维度参数 | API 要求先传 grid 的 x/y/z，再传 block 的 x/y/z；按变量名称理解，原例两组顺序写反了。 |
| `i`、`f4`、`c`、`f`、`devPtr`、`f2` | 原例未设置有效参数值；打包之前必须按目标 kernel 的参数声明初始化。 |
| `paramBuffer[1024]` | 写入前需确认对齐后的偏移加参数大小不超过容量。 |
| `ALIGN_UP` | 此位运算形式要求 alignment 为非零的 2 的幂。 |
| `__alignof(devPtr)` | 查询的是 host 上 `CUdeviceptr` 整数类型的对齐，不能在所有 ABI 下直接代替前文要求的 device pointer 对齐。 |
| 参数列表 | 顺序、大小、padding 和实际 kernel 声明必须一致；字节数相同本身不足以证明打包正确。 |

维度顺序和参数 buffer 规则参见 [cuLaunchKernel 官方定义](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__EXEC.html)。

> The alignment requirement of a structure is equal to the maximum of the alignment requirements of its fields. The alignment requirement of a structure that contains built-in vector types, `CUdeviceptr`, or non-aligned double and long long, might therefore differ between device code and host code. Such a structure might also be padded differently. The following structure, for example, is not padded at all in host code, but it is padded in device code with 12 bytes after field f since the alignment requirement for field f4 is 16.

结构体的对齐要求等于各字段对齐要求中的最大值。因此，包含 built-in vector type、`CUdeviceptr` 或未按同样方式对齐的 `double`、`long long` 的结构体，在 device code 和 host code 中可能具有不同的对齐要求，也可能采用不同的 padding。以下结构体就是原文给出的例子：原文称它在 host code 中没有 padding，而在 device code 中，字段 `f` 后会填充 12 字节，因为字段 `f4` 的对齐要求是 16 字节。

```cpp
typedef struct {
    float  f;
    float4 f4;
} myStruct;
```

**解读（布局限定）：** `float4` 需要 16 字节对齐，因此如果 `f` 位于偏移 0，`f4` 应位于偏移 16，二者之间有 12 字节 padding。原文所谓“host 完全没有 padding”依赖特定 ABI，不能推广到所有现代编译环境。应核对实际 host 的 `sizeof`、`alignof` 和 `offsetof`，并与 device 端要求对应，而不是仅从成员类型名称推断布局。

### 3.3.4. Interoperability between Runtime and Driver APIs（Runtime API 与 Driver API 的互操作）

> An application can mix runtime API code with driver API code.

应用可以混合使用 Runtime API 和 Driver API。

> If a context is created and made current via the driver API, subsequent runtime calls will use this context instead of creating a new one.

如果通过 Driver API 创建 context 并将其设为 current，后续 Runtime 调用就会使用该 context，而不是再创建一个新 context。

> If the runtime is initialized, `cuCtxGetCurrent()` can be used to retrieve the context created during initialization. This context can be used by subsequent driver API calls.

Runtime 初始化后，可以使用 `cuCtxGetCurrent()` 获取初始化期间创建的 context，并让后续 Driver API 调用使用它。

> The implicitly created context from the runtime is called the primary context (see Runtime Initialization). It can be managed from the driver API with the Primary Context Management functions.

Runtime 隐式创建的 context 称为 primary context，参见 Runtime Initialization。可以通过 Driver API 的 Primary Context Management 函数管理它。

**解读：** 混用两套 API 的关键是让它们操作预期的同一个 context，并明确谁负责生命周期。`cuCtxGetCurrent` 查询的是调用线程当前的 context；它不会替另一个 host thread 自动设置 current context。库调用也不应意外改变调用方后续使用的 context。

> Device memory can be allocated and freed using either API. `CUdeviceptr` can be cast to regular pointers and vice-versa:

Device memory 可以使用任意一套 API 分配和释放。`CUdeviceptr` 可以转换为普通指针，反向转换也可以：

```cpp
CUdeviceptr devPtr;
float* d_data;

// Allocation using driver API
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// Allocation using runtime API
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;
```

**解读（示例是两种方案）：** 两段分配代码分别展示 Driver 分配后转给 Runtime 风格指针，以及 Runtime 分配后转成 Driver handle。若原样连续执行，第二次分配会覆盖第一块内存的指针，且示例没有释放前一次分配。实际代码应分别保存和管理两块内存，或只采用其中一种方案。指针转换也不会把 device memory 变成可由 CPU 解引用的 host memory。

> In particular, this means that applications written using the driver API can invoke libraries written using the runtime API (such as `cuFFT`, `cuBLAS`, …).

具体而言，这意味着使用 Driver API 编写的应用，可以调用采用 Runtime API 编写的库，例如 `cuFFT` 和 `cuBLAS`。

> All functions from the device and version management sections of the reference manual can be used interchangeably.

参考手册中 device management 和 version management 部分的函数，可以在两套 API 之间交替使用。

**解读：** Runtime API 负责许多常见管理步骤，Driver API 则让应用显式控制 context、module 和启动参数。选择哪套接口，主要取决于控制需求与集成方式；使用更底层接口本身不会自动加速 kernel。本节示例仅做整理与静态核对，未编译或运行。
