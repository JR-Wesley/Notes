## 1.2. Programming Model

> This chapter introduces the CUDA programming model at a high level and separate from any language. The terminology and concepts introduced here apply to CUDA in any supported programming language. Later chapters will illustrate these concepts in C++.

本章从较高层次介绍 CUDA 编程模型，不依赖任何特定语言。这里引入的术语和概念适用于 CUDA 支持的所有编程语言；后续章节会用 C++ 展示这些概念。

### 1.2.1. Heterogeneous Systems

> The CUDA programming model assumes a heterogeneous computing system, which means a system that includes both GPUs and CPUs. The CPU and the memory directly connected to it are called the host and host memory, respectively. A GPU and the memory directly connected to it are referred to as the device and device memory, respectively. In some system-on-chip (SoC) systems, these may be part of a single package. In larger systems, there may be multiple CPUs or GPUs.

CUDA 编程模型以异构计算系统为前提，即系统同时包含 GPU 和 CPU。CPU 及其直接连接的内存分别称为 host 和 host memory；GPU 及其直接连接的内存分别称为 device 和 device memory。在某些片上系统（SoC）中，它们可能位于同一个封装内；更大的系统则可能包含多个 CPU 或 GPU。

> CUDA applications execute some part of their code on the GPU, but applications always start execution on the CPU. The host code, which is the code that runs on the CPU, can use CUDA APIs to copy data between the host memory and device memory, start code executing on the GPU, and wait for data copies or GPU code to complete. The CPU and GPU can both be executing code simultaneously, and best performance is usually found by maximizing utilization of both CPUs and GPUs.

CUDA 应用会在 GPU 上执行部分代码，但应用始终从 CPU 开始执行。运行在 CPU 上的 host code 可以调用 CUDA API，在 host memory 与 device memory 之间复制数据、启动 GPU 代码，并等待数据复制或 GPU 代码完成。CPU 和 GPU 可以同时执行代码；通常要充分利用两者，才能获得较好的性能。

> The code an application executes on the GPU is referred to as device code, and a function that is invoked for execution on the GPU is, for historical reasons, called a kernel. The act of starting a kernel running is called launching the kernel. A kernel launch can be thought of as starting many threads executing the kernel code in parallel on the GPU. GPU threads operate similarly to threads on CPUs, though there are some differences important to both correctness and performance that will be covered in later sections (see Section 3.2.2.1.1).

应用在 GPU 上执行的代码称为 device code；被调用并在 GPU 上执行的函数，由于历史原因称为 kernel。启动 kernel 的操作称为 kernel launch，可以把它理解为在 GPU 上启动大量并行执行该 kernel 代码的线程。GPU 线程与 CPU 线程的工作方式有相似之处，但也存在影响正确性和性能的重要差异，后续章节会进一步介绍（见 Section 3.2.2.1.1）。

**重点解读：** host 负责启动程序并通过 CUDA API 协调数据与计算，device 执行 GPU 代码。kernel launch 表示启动一批并行线程，而不是调用一次只执行一个线程的普通函数。CPU 与 GPU 可重叠工作，因此理解两侧的执行与数据流是后续优化的基础。

### 1.2.2. GPU Hardware Model

> Like any programming model, CUDA relies on a conceptual model of the underlying hardware. For the purposes of CUDA programming, the GPU can be considered to be a collection of Streaming Multiprocessors (SMs) which are organized into groups called Graphics Processing Clusters (GPCs). Each SM contains a local register file, a unified data cache, and a number of functional units that perform computations. The unified data cache provides the physical resources for shared memory and L1 cache. The allocation of the unified data cache to L1 and shared memory can be configured at runtime. The sizes of different types of memory and the number of functional units within an SM can vary across GPU architectures.

与其他编程模型一样，CUDA 依赖于对底层硬件的概念化描述。就 CUDA 编程而言，可以将 GPU 看作由多个 Streaming Multiprocessor（SM，流式多处理器）组成，而 SM 又被组织为 Graphics Processing Cluster（GPC，图形处理集群）。每个 SM 都包含本地寄存器文件、统一数据缓存和若干执行计算的功能单元。统一数据缓存为 shared memory 和 L1 cache 提供物理资源；两者的资源分配可以在运行时配置。不同 GPU 架构中，SM 内各类内存的容量和功能单元的数量可能不同。

> Note: The actual hardware layout of a GPU or the way it physically carries out the execution of the programming model may vary. These differences do not affect correctness of software written using the CUDA programming model.

注意：GPU 的实际硬件布局，以及硬件实现编程模型的具体执行方式，可能有所不同。这些差异不影响按照 CUDA 编程模型编写的软件的正确性。

> The CUDA programming model view of CPU and GPU components and connection

CUDA 编程模型中的 CPU、GPU 组件及其连接关系。

> Figure 2. A GPU has many streaming multiprocessors (SMs), each of which contains many functional units. Graphics processing clusters (GPCs) are collections of SMs. A GPU is a set of GPCs connected to the GPU memory. A CPU typically has several cores and a memory controller which connects to the system memory. A CPU and a GPU are connected by an interconnect such as PCIe or NVLINK.

图 2：GPU 包含多个 SM，每个 SM 含有多个功能单元；若干 SM 组成 GPC，多个 GPC 与 GPU 内存连接。CPU 通常包含多个核心和连接系统内存的内存控制器。CPU 与 GPU 通过 PCIe 或 NVLINK 等互连连接。

**重点解读：** SM 是理解线程执行和片上资源分配的关键层级；GPC 是组织多个 SM 的更高层级。图示是编程模型所需的抽象，不应把其中的数量或连接方式当作所有 GPU 的固定硬件规格。

#### 1.2.2.1. Thread Blocks and Grids

> When an application launches a kernel, it does so with many threads, often millions of threads. These threads are organized into blocks. A block of threads is referred to, perhaps unsurprisingly, as a thread block. Thread blocks are organized into a grid. All the thread blocks in a grid have the same size and dimensions. Figure 3 shows an illustration of a grid of thread blocks.

应用启动 kernel 时会启动大量线程，通常可达数百万个。这些线程被组织成 block，即 thread block（线程块）；thread block 再被组织成 grid（网格）。同一 grid 中所有 thread block 的大小和维度相同。图 3 展示了由 thread block 组成的 grid。

> Grid of Thread Blocks

线程块网格。

> Figure 3. Grid of Thread Blocks. Each arrow represents a thread (the number of arrows is not representative of actual number of threads).

图 3：线程块网格。每个箭头代表一个线程；图中的箭头数量不代表实际线程数。

> Thread blocks and grids may be 1, 2, or 3 dimensional. These dimensions can simplify mapping of individual threads to units of work or data items.

thread block 和 grid 可以是一维、二维或三维的。这些维度有助于把各个线程映射到工作单元或数据项。

> When a kernel is launched, it is launched using a specific execution configuration which specifies the grid and thread block dimensions. The execution configuration may also include optional parameters such as cluster size, stream, and SM configuration settings, which will be introduced in later sections.

启动 kernel 时需要指定执行配置，其中包括 grid 和 thread block 的维度。执行配置还可以包含 cluster 大小、stream 和 SM 配置等可选参数；后续章节会介绍这些参数。

> Using built-in variables, each thread executing the kernel can determine its location within its containing block and the location of its block within the containing grid. A thread can also use these built-in variables to determine the dimensions of the thread blocks and the grid on which the kernel was launched. This gives each thread a unique identity among all the threads running the kernel. This identity is frequently used to determine what data or operations a thread is responsible for.

执行 kernel 的每个线程都可以通过内置变量确定自己在所属 block 中的位置，以及该 block 在所属 grid 中的位置。线程还可以通过这些变量获知启动时 thread block 和 grid 的维度。由此，每个线程在该 kernel 的所有线程中都具有唯一身份；程序通常根据这一身份决定该线程负责的数据或操作。

> All threads of a thread block are executed in a single SM. This allows threads within a thread block to communicate and synchronize with each other efficiently. Threads within a thread block all have access to the on-chip shared memory, which can be used for exchanging information between threads of a thread block.

一个 thread block 中的所有线程都在同一个 SM 上执行，因此块内线程可以高效通信和同步。块内所有线程都能访问片上的 shared memory，并可借此交换信息。

> A grid may consist of millions of thread blocks, while the GPU executing the grid may have only tens or hundreds of SMs. All threads of a thread block are executed by a single SM and, in most cases [1], run to completion on that SM. There is no guarantee of scheduling between thread blocks, so a thread block cannot rely on results from other thread blocks, as they may not be able to be scheduled until that thread block has completed. Figure 4 shows an example of how thread blocks from a grid are assigned to an SM.

一个 grid 可能包含数百万个 thread block，而执行它的 GPU 可能只有几十或几百个 SM。一个 block 的所有线程由同一个 SM 执行，并且在大多数情况下会在该 SM 上运行至结束[1]。不同 block 之间没有调度顺序保证；某个 block 不能依赖其他 block 的结果，因为其他 block 可能要等它结束后才有机会被调度。图 4 展示了 grid 中的 thread block 分配到 SM 的示例。

> Thread blocks scheduled on SMs

调度到 SM 上的线程块。

> Figure 4. Each SM has one or more active thread blocks. In this example, each SM has three thread blocks scheduled simultaneously. There are no guarantees about the order in which thread blocks from a grid are assigned to SMs.

图 4：每个 SM 有一个或多个活动 thread block。本例中，每个 SM 同时调度了三个 block。grid 中各 block 被分配到 SM 的顺序没有保证。

> The CUDA programming model enables arbitrarily large grids to run on GPUs of any size, whether it has only one SM or thousands of SMs. To achieve this, the CUDA programming model, with some exceptions, requires that there be no data dependencies between threads in different thread blocks. That is, a thread should not depend on results from or synchronize with a thread in a different thread block of the same grid. All the threads within a thread block run on the same SM at the same time. Different thread blocks within the grid are scheduled among the available SMs and may be executed in any order. In short, the CUDA programming model requires that it be possible to execute thread blocks in any order, in parallel or in series.

CUDA 编程模型允许任意大的 grid 在不同规模的 GPU 上运行，无论设备只有一个 SM，还是有数千个 SM。为实现这一点，除少数例外，不同 thread block 中的线程之间不应存在数据依赖：同一 grid 中的线程不应依赖另一 block 中线程的结果，也不应与其同步。一个 block 的线程同时在同一个 SM 上运行；grid 中不同 block 则在可用 SM 间调度，并可能以任意顺序执行。简言之，程序必须允许 thread block 按任意顺序并行或串行执行。

**重点解读：** grid 提供大规模并行工作的集合，block 则是通常能够在同一个 SM 内通信和同步的基本单位。一般情况下，不能假定不同 block 的执行顺序；如果算法确实需要跨 block 协作，必须使用具备相应保证的专门机制。

##### 1.2.2.1.1. Thread Block Clusters

> In addition to thread blocks, GPUs with compute capability 9.0 and higher have an optional level of grouping called clusters. Clusters are a group of thread blocks which, like thread blocks and grids, can be laid out in 1, 2, or 3 dimensions. Figure 5 illustrates a grid of thread blocks that is also organized into clusters. Specifying clusters does not change the grid dimensions or the indices of a thread block within a grid.

除 thread block 之外，compute capability 9.0 及以上的 GPU 还提供可选的 cluster 分组层级。cluster 由多个 thread block 组成，与 block 和 grid 一样，可以按一维、二维或三维布局。图 5 展示了同时按 cluster 组织的 thread block grid。指定 cluster 不会改变 grid 的维度，也不会改变 block 在 grid 中的索引。

> Thread blocks scheduled on SMs

调度到 SM 上的线程块。

> Figure 5. When clusters are specified, thread blocks are in the same location in the grid but also have a position within the containing cluster.

图 5：指定 cluster 后，thread block 在 grid 中的位置保持不变，同时还拥有在所属 cluster 内的位置。

> Specifying clusters groups adjacent thread blocks into clusters and provides some additional opportunities for synchronization and communication at the cluster level. Specifically, all thread blocks in a cluster are executed in a single GPC. Figure 6 shows how thread blocks are scheduled to SMs in a GPC when clusters are specified. Because the thread blocks are scheduled simultaneously and within a single GPC, threads in different blocks but within the same cluster can communicate and synchronize with each other using software interfaces provided by Cooperative Groups. Threads in clusters can access the shared memory of all blocks in the cluster, which is referred to as distributed shared memory. The maximum size of a cluster is hardware dependent and varies between devices.

指定 cluster 会把相邻的 thread block 分组，从而提供在 cluster 层级进行同步和通信的额外机会。一个 cluster 中的所有 block 都在同一个 GPC 中执行。图 6 展示了指定 cluster 时，block 如何调度到该 GPC 内的 SM。由于这些 block 同时调度且位于同一个 GPC，同一 cluster 内不同 block 的线程可以通过 Cooperative Groups 提供的软件接口进行通信和同步。cluster 中的线程还能访问该 cluster 内所有 block 的 shared memory，这称为 distributed shared memory（分布式共享内存）。cluster 的最大规模取决于硬件，因设备而异。

> Figure 6 illustrates the how thread blocks within a cluster are scheduled simultaneously on SMs within a GPC. Thread blocks within a cluster are always adjacent to each other within the grid.

图 6 展示了同一 cluster 内的 thread block 如何同时调度到一个 GPC 中的 SM。cluster 内的 block 在 grid 中始终彼此相邻。

> Thread blocks scheduled in clusters on GPCs

以 cluster 为单位调度到 GPC 的线程块。

> Figure 6. When clusters are specified, the thread blocks in a cluster are arranged in their cluster shape within the grid. The thread blocks of a cluster are scheduled simultaneously on the SMs of a single GPC.

图 6：指定 cluster 后，其中的 thread block 在 grid 内按 cluster 形状排列，并同时调度到同一个 GPC 的各个 SM。

**重点解读：** cluster 为部分跨 block 协作提供明确的执行与通信范围：同一 cluster 的 block 会同时位于一个 GPC 内，并可通过 Cooperative Groups 与 distributed shared memory 协作。它是可选层级，且能否使用、可用规模都受设备能力约束。

#### 1.2.2.2. Warps and SIMT

> Within a thread block, threads are organized into groups of 32 threads called warps. A warp executes the kernel code in a Single-Instruction Multiple-Threads (SIMT) paradigm. In SIMT, all threads in the warp are executing the same kernel code, but each thread may follow different branches through the code. That is, though all threads of the program execute the same code, threads do not need to follow the same execution path.

在一个 thread block 内，线程按每组 32 个组织为 warp。warp 以 Single-Instruction Multiple-Threads（SIMT，单指令多线程）范式执行 kernel 代码。在 SIMT 中，同一 warp 的线程执行同一份 kernel 代码，但各线程可能走不同的分支；也就是说，执行同一程序并不要求所有线程走同一条控制流路径。

> When threads are executed by a warp, they are assigned a warp lane. Warp lanes are numbered 0 to 31 and threads from a thread block are assigned to warps in a predictable fashion detailed in Hardware Multithreading.

线程在 warp 中执行时会被分配一个 warp lane。lane 编号为 0 至 31；thread block 中的线程按可预测的方式分配到各 warp，具体规则见 Hardware Multithreading。

> All threads in the warp execute the same instruction simultaneously. If some threads within a warp follow a control flow branch in execution while others do not, the threads which do not follow the branch will be masked off while the threads which follow the branch are executed. For example, if a conditional is only true for half the threads in a warp, the other half of the warp would be masked off while the active threads execute those instructions. This situation is illustrated in Figure 7. When different threads in a warp follow different code paths, this is sometimes called warp divergence. It follows that utilization of the GPU is maximized when threads within a warp follow the same control flow path.

同一 warp 的线程同时执行相同指令。如果其中一些线程进入某个控制流分支，而另一些线程不进入，那么执行该分支时，后者会被屏蔽。例如，某个条件只对一半线程成立时，活动线程执行对应指令，另一半线程则被屏蔽。图 7 展示了这种情形。同一 warp 中不同线程走不同代码路径，有时称为 warp divergence（warp 分歧）。因此，同一 warp 的线程遵循相同控制流路径时，通常更有利于提高 GPU 利用率。

> Warp lanes are masked off when not active

不活动的 warp lane 会被屏蔽。

> Figure 7. In this example, only threads with even thread index execute the body of the if statement, the others are masked off while the body is executed.

图 7：本例只有索引为偶数的线程执行 `if` 语句体；执行期间，其余线程被屏蔽。

> In the SIMT model, all threads in a warp progress through the kernel in lock step. Hardware execution may differ. See the sections on Independent Thread Execution for more information on where this distinction is important. Exploiting knowledge of how warp execution is actually mapped to real hardware is discouraged. The CUDA programming model and SIMT say that all threads in a warp progress through the code together. Hardware may optimize masked lanes in ways that are transparent to the program so long as the programming model is followed. If the program violates this model, this can result in undefined behavior that can be different in different GPU hardware.

在 SIMT 模型中，同一 warp 的所有线程以锁步方式推进 kernel；实际硬件执行方式可能有所不同。有关这一差异在哪些情况下重要，可参见 Independent Thread Execution。指南不鼓励程序依赖 warp 执行与真实硬件之间的具体映射。CUDA 编程模型和 SIMT 抽象将同一 warp 的线程视为一起推进；只要程序遵循编程模型，硬件就可以以对程序透明的方式优化被屏蔽的 lane。若程序违反这一模型，可能出现未定义行为，而且在不同 GPU 硬件上的表现可能不同。

> While it is not necessary to consider warps when writing CUDA code, understanding the warp execution model is helpful in understanding concepts such as global memory coalescing and shared memory bank access patterns. Some advanced programming techniques use specialization of warps within a thread block to limit thread divergence and maximize utilization. This and other optimizations make use of the knowledge that threads are grouped into warps when executing.

编写 CUDA 代码时并非一定要显式考虑 warp，但理解 warp 执行模型有助于理解 global memory coalescing（全局内存合并访问）和 shared memory bank 访问模式等概念。一些高级编程技术会让 thread block 中不同 warp 承担专门任务，以减少线程分歧并提高利用率；这类优化利用了线程执行时按 warp 分组的事实。

> One implication of warp execution is that thread blocks are best specified to have a total number of threads which is a multiple of 32. It is legal to use any number of threads, but when the total is not a multiple of 32, the last warp of the thread block will have some lanes that are unused throughout execution. This will likely lead to suboptimal functional units utilization and memory access for that warp.

warp 执行方式的一个直接影响是：thread block 的线程总数最好是 32 的倍数。使用其他线程数量也是合法的，但若总数不是 32 的倍数，该 block 的最后一个 warp 就会有一些 lane 在整个执行过程中闲置，可能导致这个 warp 对功能单元和内存访问的利用不理想。

> SIMT is often compared to Single Instruction Multiple Data (SIMD) parallelism, but there are some important differences. In SIMD, execution follows a single control flow path, while in SIMT, each thread is allowed to follow its own control flow path. Because of this, SIMT does not have a fixed data-width like SIMD. A more detailed discussion of SIMT can be found in SIMT Execution Model.

SIMT 常与 Single Instruction Multiple Data（SIMD，单指令多数据）并行方式比较，但两者存在重要区别。SIMD 执行遵循一条控制流路径，而 SIMT 允许每个线程遵循自己的控制流路径。因此，SIMT 不像 SIMD 那样具有固定的数据宽度。关于 SIMT 的更多细节见 SIMT Execution Model。

**重点解读：** warp 是 32 个线程组成的执行分组。分支路径不一致时，不活动的 lane 会被屏蔽，降低该段代码的有效利用；但不能据此假定所有硬件细节都严格锁步。选择 32 的倍数作为 block 线程总数，主要是避免最后一个 warp 长期存在闲置 lane，而不是语法要求。

#### 1.2.2.3. Tile Programming in CUDA

> In addition to the SIMT model described in the preceding sections, CUDA supports a tile programming model. In tile programming, the programmer writes code at the level of an entire thread block, describing operations on multidimensional collections of data called tiles. The compiler maps these operations to the individual threads of the block.

除前述 SIMT 模型外，CUDA 还支持 tile 编程模型。在 tile 编程中，程序员以整个 thread block 为单位编写代码，描述对称为 tile 的多维数据集合所执行的操作；编译器再把这些操作映射到 block 内的各线程。

> Tile kernels are launched on a grid of blocks, as described in the Thread Blocks and Grids section. Each block executes the tile kernel and can query its position within the grid to determine which portion of the data it is responsible for. The programmer specifies only the grid dimensions; the number of threads per block is determined by the compiler based on the tile operations in the kernel (Figure 8).

与 Thread Blocks and Grids 一节所述相同，tile kernel 也在由 block 构成的 grid 上启动。每个 block 执行 tile kernel，并可根据自身在 grid 中的位置确定负责的数据区域。程序员只指定 grid 的维度；编译器根据 kernel 中的 tile 操作决定每个 block 的线程数（图 8）。

> Programmer's view in the SIMT and tile programming models

程序员视角下的 SIMT 与 tile 编程模型。

> Figure 8. Programmer’s view in the SIMT and tile programming models. In SIMT, the programmer writes per-thread code and controls how each thread accesses data. In tile programming, the programmer writes per-block code that operates on tiles; the compiler maps operations to the threads of the block.

图 8：SIMT 与 tile 编程模型的程序员视角。SIMT 中，程序员编写逐线程代码，并控制每个线程如何访问数据；tile 编程中，程序员编写逐 block 的 tile 操作代码，由编译器将操作映射到 block 的线程。

> Within a tile kernel, the block executes a single control flow. The programmer specifies operations on tiles, and the compiler distributes the work across the threads of the block. Standard control flow constructs such as conditionals and loops are supported, but because the block follows a single control flow, there is no concept of warp divergence. Scalar operations, such as computing an index or a loop bound, are executed by a single thread of the block. Tile operations, such as adding two tiles element by element, are collectively executed in parallel by all threads of the block.

在 tile kernel 内，一个 block 执行单一控制流。程序员指定 tile 操作，编译器将工作分配给 block 内的线程。条件和循环等标准控制流结构仍可使用，但由于整个 block 遵循同一控制流，因此不存在 warp divergence 的概念。计算索引或循环边界等标量操作由 block 中的一个线程执行；两个 tile 的逐元素加法等 tile 操作则由 block 的所有线程协同并行执行。

> It is important not to confuse blocks—units of execution—with tiles—units of data. A single block may create and operate on many tiles of different shapes and data types.

不要混淆作为执行单位的 block 与作为数据单位的 tile。一个 block 可以创建并操作许多形状、数据类型各不相同的 tile。

**重点解读：** tile 编程把逐线程工作分配交给编译器，程序员直接描述 block 级的数据操作。block 与 tile 分属执行和数据两个维度，一个 block 可以处理多个 tile；它仍使用 grid 与 block 的执行结构。

##### 1.2.2.3.1. Arrays and tiles

> Tile kernels work with two types of data: arrays and tiles. An array (or global array) is a multidimensional container of elements stored in device memory. Arrays are mutable: their contents can be modified by store operations within a kernel. An array has a shape and a data type.

tile kernel 使用两类数据：array 和 tile。array（或 global array）是存储在 device memory 中的多维元素容器，具有形状和数据类型。array 是可变的，kernel 内的 store 操作可以修改其内容。

> A tile is a multidimensional collection of values that exists only within tile code and is local to a single block. Tiles are immutable: every operation on a tile produces a new tile rather than modifying an existing one. Unlike an array, a tile does not necessarily have a representation in memory—the compiler decides how tile data is stored, and may use registers, shared memory, or other resources of the SM. Each dimension of a tile must be a power of two and must be known at compile time (that is, its value must be determinable before the kernel executes, rather than computed during execution). Tiles cannot be passed as kernel parameters; they are created and consumed entirely within tile code.

tile 是只存在于 tile 代码内部、归属于单个 block 的多维值集合。tile 不可变：对 tile 的每次操作都会生成新 tile，而不是修改原有 tile。与 array 不同，tile 不一定有固定的内存表示；编译器决定数据如何存放，可能使用寄存器、shared memory 或 SM 的其他资源。tile 的每个维度都必须是 2 的幂，并且必须在编译时已知，也就是在 kernel 执行前便能确定，而不是在执行过程中计算出来。tile 不能作为 kernel 参数传递，只能在 tile 代码内部创建和使用。

**重点解读：** array 是 device memory 中可修改的数据容器；tile 则是 block 内部使用的不可变值集合，具体存储位置由编译器决定。编译时已知的形状限制，使编译器能够提前规划 tile 操作的线程与资源映射。

##### 1.2.2.3.2. Tile space and data movement

> Data moves between arrays and tiles through load and store operations. These operations use a concept called the tile space, which is the result of conceptually partitioning an array into equally sized, non-overlapping tiles. For example, consider a two-dimensional array of shape (M, N). If a load operation specifies a tile shape of (tm, tn), the array is conceptually divided into ⌈M/tm⌉ rows and ⌈N/tn⌉ columns of tiles. An index into this tile space, such as (i, j), identifies which tile to load. The load returns a tile of shape (tm, tn) containing the corresponding elements from the array. When a tile extends beyond the boundaries of the array—for example, at the edges when the array dimensions are not exact multiples of the tile dimensions—the load specifies how out-of-bounds elements are handled, such as by filling them with zeros (Figure 9).

数据通过 load 和 store 操作在 array 与 tile 之间移动。这些操作使用 tile space（tile 空间）概念：在逻辑上把 array 划分为大小相等、互不重叠的 tile。例如，二维 array 的形状为 (M, N)，如果 load 指定的 tile 形状为 (tm, tn)，则在概念上会形成 ⌈M/tm⌉ 行、⌈N/tn⌉ 列 tile。tile space 中的索引 (i, j) 指定要加载的 tile；load 返回形状为 (tm, tn)、包含 array 相应元素的 tile。若 tile 延伸到 array 边界之外，例如 array 维度不是 tile 维度的整数倍时，load 会指定如何处理越界元素，例如填零（图 9）。

> Tile space and data movement

tile 空间与数据移动。

> Figure 9. Tile space and data movement. A two-dimensional array of shape (M, N) is conceptually partitioned into a grid of tiles with shape (tm, tn). A load at tile-space index (i, j) returns the corresponding tile. At the array boundary, elements that fall outside the array can be filled with zeros. A store writes a tile back to the array at a given tile-space index.

图 9：tile 空间与数据移动。形状为 (M, N) 的二维 array 在概念上被划分为形状为 (tm, tn) 的 tile 网格。在 tile-space 索引 (i, j) 处执行 load，会返回对应 tile；边界外的元素可以填零。store 则将 tile 写回 array 中指定的 tile-space 索引位置。

> A store operation performs the inverse: given a tile and an index into the tile space, it writes the tile’s elements to the corresponding region of the array. Any writes that fall outside the array boundaries are silently discarded. Tile programs also support gather and scatter operations, which load from or store to arbitrary positions in an array.

store 执行相反的操作：给定一个 tile 及其 tile-space 索引，将 tile 元素写入 array 的对应区域。落在 array 边界之外的写入会被静默丢弃。tile 程序还支持 gather 和 scatter，以从 array 中任意位置加载数据或向这些位置存储数据。

**重点解读：** tile space 的索引定位的是一块数据，而不是单个元素。load 可为边界外的位置提供填充值，store 则丢弃越界写入，因此处理非整除边界时需要分别理解读写行为。粘贴文本中的 tile 行数和列数公式缺失，这里依据 [NVIDIA 官方原文](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html#tile-space-and-data-movement) 补全为向上取整。

##### 1.2.2.3.3. Operations on tiles

> Tile programs provide a set of built-in operations that act on tiles, including elementwise arithmetic, matrix multiplication, reductions (such as sum and maximum) along one or more axes, shape manipulation (such as reshape and transpose), and type conversion. When two tiles of different shapes are combined in an operation, the smaller tile is automatically expanded to match the larger one before the operation is applied.

tile 程序提供一组作用于 tile 的内置操作，包括逐元素算术、矩阵乘法、沿一个或多个轴进行的归约（如求和、求最大值）、形状操作（如 reshape 和 transpose）以及类型转换。当形状不同的两个 tile 参与同一操作时，较小的 tile 会在操作前自动扩展，以匹配较大的 tile。

##### 1.2.2.3.4. Relationship to SIMT programming

> Tile programming and SIMT programming coexist within CUDA. An application may contain both SIMT and tile kernels, and both types of kernels can operate on the same data in device memory. The choice of programming model is a per-kernel decision. Tile programming does not replace SIMT programming. SIMT provides fine-grained control over individual threads, which remains necessary for some algorithms and optimization techniques. Tile programming provides a higher-level abstraction that can simplify kernel development. Because thread-level decisions are left to the compiler, the same tile kernel can run on different GPU architectures without requiring changes to the source. Both models are built on the same underlying hardware—SMs, thread blocks, and grids—described in the preceding sections. Both models also use the same device memory spaces, which are introduced in the following section.

tile 编程与 SIMT 编程在 CUDA 中并存。一个应用可以同时包含 SIMT kernel 和 tile kernel，两者也可以操作 device memory 中的同一份数据；选择哪种编程模型是逐 kernel 决定的。tile 编程并不取代 SIMT：SIMT 提供对单个线程的细粒度控制，某些算法和优化技术仍需要这种能力；tile 编程则通过更高层次的抽象简化 kernel 开发。由于逐线程决策交给编译器，同一 tile kernel 可以不修改源码就运行在不同 GPU 架构上。两种模型都建立在前述 SM、thread block 和 grid 等硬件结构之上，也都使用下一节介绍的 device memory 空间。

**重点解读：** SIMT 与 tile 是逐 kernel 选择的两种代码表达方式，可以在同一应用中共存。前者保留细粒度线程控制；后者把线程映射交给编译器，以换取更高层次的表达和跨架构的源码可移植性。

### 1.2.3. GPU Memory

> In modern computing systems, efficiently utilizing memory is just as important as maximizing the use of functional units performing computations. Heterogeneous systems have multiple memory spaces, and GPUs contain various types of programmable on-chip memory in addition to caches. The following sections introduce these memory spaces in more details.

在现代计算系统中，高效利用内存与充分利用执行计算的功能单元同样重要。异构系统具有多个内存空间；除缓存之外，GPU 还包含多种可编程的片上内存。下文将进一步介绍这些内存空间。

#### 1.2.3.1. DRAM Memory in Heterogeneous Systems

> GPUs and CPUs both have directly attached DRAM chips. In systems with more than one GPU, each GPU has its own memory. From the perspective of device code, the DRAM attached to the GPU is called global memory, because it is accessible to all SMs in the GPU. This terminology does not mean it is necessarily accessible everywhere within the system. The DRAM attached to the CPU(s) is called system memory or host memory.

GPU 和 CPU 都有直接连接的 DRAM 芯片。多 GPU 系统中，每个 GPU 都有自己的内存。从 device code 的视角看，GPU 直接连接的 DRAM 称为 global memory，因为 GPU 内所有 SM 都能访问它；这里的“global”并不表示系统中任何位置都必然能访问它。CPU 直接连接的 DRAM 称为 system memory 或 host memory。

> Like CPUs, GPUs use virtual memory addressing. On all currently-supported systems, the CPU and GPU use a single unified virtual memory space. This means that the virtual memory address range for each GPU in the system is unique and distinct from the CPU and every other GPU in the system. For a given virtual memory address, it is possible to determine whether that address is in GPU memory or system memory and, on systems with multiple GPUs, which GPU memory contains that address.

与 CPU 一样，GPU 使用虚拟内存寻址。在目前支持的所有系统上，CPU 与 GPU 使用统一的虚拟地址空间。这意味着系统中每个 GPU 的虚拟地址范围都是唯一的，与 CPU 和其他 GPU 的地址范围不同。给定一个虚拟地址，可以判断它位于 GPU 内存还是系统内存；在多 GPU 系统中，还可以判断它属于哪个 GPU 的内存。

> There are CUDA APIs to allocate GPU memory, CPU memory, and to copy between allocations on the CPU and GPU, within a GPU, or between GPUs in multi-GPU systems. The locality of data can be explicitly controlled when desired. Unified Memory, discussed below, allows the placement of memory to be handled automatically by the CUDA runtime or system hardware.

CUDA API 可用于分配 GPU 内存和 CPU 内存，也可在 CPU 与 GPU 的内存分配之间、同一 GPU 内部，或多 GPU 系统的 GPU 之间复制数据。需要时，程序可以显式控制数据的位置。下文介绍的 Unified Memory 则允许 CUDA runtime 或系统硬件自动处理内存放置。

**重点解读：** global memory 的“全局”范围是相对于该 GPU 内的 SM 而言，不能据此推断所有处理器都能直接、等价地访问它。统一虚拟地址空间使地址具有可区分的归属，但数据所在位置及访问代价仍需要单独考虑。

#### 1.2.3.2. Locality Domains

> A locality domain is a subset of a GPU’s memory and streaming multiprocessors (SMs). All GPUs have at least one locality domain. Larger GPUs may have more than one locality domain. On GPUs with more than one locality domain, performance of some kernels can be improved by using localized memory and compute. Localized memory is a memory allocation contained entirely within a single locality domain. Kernels using this memory can be scheduled on SMs within the same locality domain. Applications benefit from localization when memory and compute are divided between locality domains and work can be issued to each locality domain in parallel.

locality domain（局部性域）由 GPU 内存和 SM 的一个子集组成。所有 GPU 至少有一个 locality domain；较大的 GPU 可能有多个。对于具有多个 locality domain 的 GPU，某些 kernel 可以通过局部化的内存与计算提升性能。localized memory 是完全位于单个 locality domain 内的内存分配；使用这块内存的 kernel 可以调度到同一域内的 SM。当内存和计算被划分到不同域，并且能够向各域并行分配工作时，应用可以从局部化中受益。

> GPU memory which is allocated without specifying a locality domain is said to be unlocalized. Unlocalized memory allocations span across locality domains, except in the case of very small allocations.

分配 GPU 内存时若未指定 locality domain，该内存称为 unlocalized（未局部化）。除非常小的内存分配外，未局部化的内存分配会跨越多个 locality domain。

> On GPUs with only one locality domain, all GPU SMs and memory are part of that one locality domain.

对于只有一个 locality domain 的 GPU，所有 SM 和 GPU 内存都属于该域。

> Section 4.7 shows the mechanisms for localizing GPU memory and compute within a specific locality domain. Locality domains are a performance feature: CUDA code which does not localize memory or compute will still execute correctly.

Section 4.7 介绍了将 GPU 内存和计算局部化到特定 locality domain 的机制。locality domain 是一项性能特性；即使 CUDA 代码没有局部化内存或计算，仍然能够正确执行。

**重点解读：** locality domain 影响的是数据和计算在 GPU 内部的空间邻近关系。只有设备存在多个域，且工作能够相应划分、并行派发时，局部化才可能带来收益；它不改变程序正确性要求。

#### 1.2.3.3. On-Chip Memory in GPUs

> In addition to the global memory, each GPU has some on-chip memory. Each SM has its own register file and shared memory. These memories are part of the SM and can be accessed extremely quickly from threads executing within the SM.

除 global memory 外，GPU 还有片上内存。每个 SM 都有自己的寄存器文件和 shared memory；这些内存属于 SM，正在该 SM 内执行的线程能够以很低的延迟访问它们。

> The register file stores thread local variables which are usually allocated by the compiler. The shared memory is accessible by all threads within a thread block or cluster. Shared memory can be used for exchanging data between threads of a thread block or cluster.

寄存器文件保存线程局部变量，这些变量通常由编译器分配。一个 thread block 或 cluster 内的所有线程都可以访问相应的 shared memory；线程可借此在 block 或 cluster 内交换数据。

> The register file and unified data cache in an SM have finite sizes. The size of an SM’s register file, unified data cache, and how the unified data cache can be configured for L1 and shared memory balance can be found in Memory Information per Compute Capability. The register file, shared memory space, and L1 cache are shared among all threads in a thread block.

SM 中的寄存器文件和统一数据缓存容量有限。SM 寄存器文件、统一数据缓存的容量，以及如何在 L1 与 shared memory 之间配置统一数据缓存，可参见 Memory Information per Compute Capability。一个 thread block 的所有线程共同使用该 SM 的寄存器文件、shared memory 空间和 L1 cache 资源。

> To schedule a thread block to an SM, the total number of registers needed for each thread multiplied by the number of threads in the thread block must be less than or equal to the available registers in the SM. If the number of registers required for a thread block exceeds the size of the register file, the kernel is not launchable and the number of threads in the thread block must be decreased to make the thread block launchable.

要把一个 thread block 调度到 SM，每线程所需寄存器数乘以 block 中线程数，所得总量必须不超过该 SM 可用的寄存器数。如果一个 block 所需寄存器总量超过寄存器文件容量，kernel 就无法启动，需要减少该 block 的线程数，使其满足启动条件。

> Shared memory allocations are done at the thread block level. That is, unlike register allocations which are per thread, allocations of shared memory are common to the entire thread block.

shared memory 以 thread block 为单位分配。也就是说，它由整个 block 共同使用；寄存器则按线程分配。

**重点解读：** 寄存器和 shared memory 都是有限的片上资源，但分配粒度不同：寄存器用量随线程数累加，shared memory 用量按 block 计算。配置 block 大小时，必须同时考虑这些资源约束；寄存器总需求超过 SM 容量时，kernel 无法按该配置启动。

##### 1.2.3.3.1. Caches

> In addition to programmable memories, GPUs have both L1 and L2 caches. Each SM has an L1 cache which is part of the unified data cache. A larger L2 cache is shared by all SMs within a GPU. This can be seen in the GPU block diagram in Figure 2. Each SM also has a separate constant cache, which is used to cache values in global memory that have been declared to be constant over the life of a kernel. The compiler may place kernel parameters into constant memory as well. This can improve kernel performance by allowing kernel parameters to be cached in the SM separately from the L1 data cache.

除了可编程内存，GPU 还有 L1 和 L2 cache。每个 SM 的 L1 cache 是统一数据缓存的一部分；较大的 L2 cache 由 GPU 内所有 SM 共享，图 2 的 GPU 框图展示了这一结构。每个 SM 还具有独立的 constant cache，用于缓存 global memory 中被声明为在 kernel 生命周期内不变的值。编译器也可能把 kernel 参数放入 constant memory，让这些参数在 SM 中独立于 L1 data cache 被缓存，从而改善性能。

#### 1.2.3.4. Unified Memory

> When an application allocates memory explicitly on the GPU or CPU, that memory is only accessible to code running on that device. That is, CPU memory can only be accessed from CPU code, and GPU memory can only be accessed from kernels running on the GPU [2]. CUDA APIs for copying memory between the CPU and GPU are used to explicitly copy data to the correct memory at the right time.

应用在 GPU 或 CPU 上显式分配内存时，该内存只能由对应设备上运行的代码访问。也就是说，CPU 内存只能由 CPU 代码访问，GPU 内存只能由 GPU 上运行的 kernel 访问[2]。程序需使用 CUDA 的 CPU-GPU 内存复制 API，在适当时机显式地把数据复制到正确的内存中。

> A CUDA feature called unified memory allows applications to make memory allocations which can be accessed from CPU or GPU. The CUDA runtime or underlying hardware enables access or relocates the data to the correct place when needed. Even with unified memory, optimal performance is attained by keeping the migration of memory to a minimum and accessing data from the processor directly attached to the memory where it resides as much as possible.

CUDA 的 Unified Memory 特性允许应用分配可由 CPU 或 GPU 访问的内存。需要时，CUDA runtime 或底层硬件会提供访问能力，或将数据迁移到合适的位置。即使用了 Unified Memory，要获得较好性能，仍应尽量减少内存迁移，并尽可能由与数据所在内存直接连接的处理器访问数据。

> The hardware features of the system determine how access and exchange of data between memory spaces is achieved. Section Unified Memory introduces the different categories of unified memory systems. Section Unified Memory contains many more details about use and behavior of unified memory in all situations.

系统的硬件特性决定了不同内存空间之间如何访问和交换数据。Unified Memory 一节会介绍统一内存系统的不同类别，以及 Unified Memory 在各种情况下的使用方式与行为细节。

**重点解读：** Unified Memory 简化了 CPU 与 GPU 访问同一分配的编程方式，但没有消除数据位置和迁移成本。统一虚拟地址空间与 Unified Memory 也不是同一概念：前者描述地址空间的组织，后者提供跨处理器访问内存分配的能力。

#### Notes

> [1] In certain situations when using features such as CUDA Dynamic Parallelism, a thread block may be suspended to memory. This means the state of the SM is stored to a system-managed area of GPU memory and the SM is freed to execute other thread blocks. This is similar to context swapping on CPUs. This is not common.

[1] 在使用 CUDA Dynamic Parallelism 等特性的某些情况下，thread block 可能被挂起并将状态保存到内存。这意味着 SM 的状态被存入由系统管理的 GPU 内存区域，随后该 SM 可用于执行其他 block。其过程类似 CPU 的上下文切换，但并不常见。

> [2] An exception to this is mapped memory, which is CPU memory allocated with properties that enable it to be directly accessed from the GPU. However, mapped access occurs over the PCIe or NVLINK connection. The GPU is unable to hide the higher latency and lower bandwidth behind parallelism, so mapped memory is not a performant replacement to unified memory or placing data in the appropriate memory space.

[2] 一个例外是 mapped memory：这种 CPU 内存分配具有允许 GPU 直接访问的属性。但 mapped access 要经过 PCIe 或 NVLINK 连接；GPU 无法通过并行执行充分掩盖由此产生的较高延迟和较低带宽。因此，在性能方面，mapped memory 不能替代 Unified Memory 或将数据放在合适内存空间的做法。
