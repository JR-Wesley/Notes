## 4.19. Extended GPU Memory（扩展 GPU 内存）

来源：[CUDA Programming Guide — Extended GPU Memory](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/extended-gpu-memory.html)

> The Extended GPU Memory (EGM) feature, utilizing the high-bandwidth NVLink-C2C, facilitates efficient access to all system memory by GPUs, in both single-node and multi-node systems. EGM applies to integrated CPU-GPU NVIDIA systems by allowing physical memory allocation that can be accessed from any GPU thread within the setup. EGM ensures that all GPUs can access its resources at the speed of either GPU-GPU NVLink or NVLink-C2C.

Extended GPU Memory（EGM）利用高带宽 NVLink-C2C，使 GPU 能够在单节点和多节点系统中高效访问全部系统内存。EGM 适用于 NVIDIA 集成式 CPU-GPU 系统，允许分配能被该系统中任意 GPU 线程访问的物理内存。EGM 保证各 GPU 能够以 GPU-GPU NVLink 或 NVLink-C2C 链路的速度访问这些资源。

> **EGM**

**EGM**

**整理说明：** 粘贴内容在此仅有 “EGM” 图示标签，没有图片文件；标签保留，未补造原图。

> In this setup, memory accesses occur via the local high-bandwidth NVLink-C2C. For remote memory accesses, GPU NVLink and, in some cases, NVLink-C2C are used. With EGM, GPU threads gain the capability to access all available memory resources, including CPU attached memory and HBM3, over the NVSwitch fabric.

在这种系统配置中，本地内存访问通过高带宽 NVLink-C2C 完成。远程内存访问使用 GPU NVLink，某些情况下还会经过 NVLink-C2C。借助 EGM，GPU 线程可以通过 NVSwitch fabric 访问全部可用内存资源，包括 CPU 所连接的内存和 HBM3。

**解读：** EGM 扩展的是 GPU 可访问的内存范围及访问路径。CPU attached memory 仍然位于 CPU 侧，远程 HBM 仍然位于远端；“能够访问”不表示它们具有与本地 HBM 相同的延迟和带宽。这里的 NVLink/NVLink-C2C 速度描述的是所使用的互连路径，应用实际吞吐还取决于拓扑、共享链路负载和访问模式。

### 4.19.1. Preliminaries（预备知识）

> Before diving into API changes for EGM functionalities, we are going to cover currently supported topologies, identifier assignment, prerequisites for virtual memory management, and CUDA types for EGM.

在介绍 EGM 功能涉及的 API 变化之前，本节先说明当前支持的 topology、标识符分配、virtual memory management 的前提条件，以及 EGM 使用的 CUDA 类型。

#### 4.19.1.1. EGM Platforms: System topology（EGM 平台：系统拓扑）

> Currently, EGM can be enabled in several platforms:

当前，EGM 可在以下平台中启用：

1. > Single-Node, Single-GPU: Consists of an Arm-based CPU, CPU attached memory, and a GPU. Between the CPU and the GPU there is a high bandwidth C2C (Chip-to-Chip) interconnect.

   单节点、单 GPU：由一个 Arm CPU、CPU 所连接的内存以及一个 GPU 组成，CPU 与 GPU 之间通过高带宽 C2C（Chip-to-Chip）互连连接。

2. > Single-Node, Multi-GPU: Consists of ARM-based CPUs, each with attached memory, and multiple GPUs connected through an NVLink-based network.

   单节点、多 GPU：由多个 Arm CPU 及各自连接的内存，以及通过 NVLink 网络互连的多个 GPU 组成。

3. > Multi-Node, Multi-GPU: Two or more single-node systems, each as in (1) or (2) above, connected through an NVLink-based network.

   多节点、多 GPU：由两个或更多单节点系统组成，每个节点采用上述（1）或（2）的配置，节点间通过 NVLink 网络连接。

> **Note**
>
> Using `cgroups` to limit available devices will block routing over EGM and cause performance issues. Use `CUDA_VISIBLE_DEVICES` instead.

**注意：** 使用 `cgroups` 限制可用 device，会阻碍通过 EGM 的路由并引发性能问题。原文建议改用 `CUDA_VISIBLE_DEVICES`。

**解读：** 本节所说的 node 是系统或计算节点，后面的 NUMA node 是操作系统描述内存局部性的单位，两者不是同一层级。多节点 EGM 也要求文中描述的 NVLink 网络拓扑，不能仅因普通集群节点之间能够通过 TCP/IP 通信，就推断它们支持 EGM。

#### 4.19.1.2. Socket Identifiers: What are they? How to access them?（Socket 标识符：含义与获取方法）

> NUMA (Non-Uniform Memory Access) is a memory architecture used in multi-processor computer systems such that the memory is divided into multiple nodes. Each node has its own processors and memory. In such a system, NUMA divides the system into nodes and assigns a unique identifier (`numaID`) to every node.

NUMA（Non-Uniform Memory Access，非一致内存访问）是一种多处理器系统内存架构，将内存划分到多个 node。每个 node 拥有自己的处理器和内存。在这种系统中，NUMA 将系统划分为多个 node，并为每个 node 分配唯一标识符 `numaID`。

> EGM uses the NUMA node identifier which is assigned by the operating system. Note that, this identifier is different from the ordinal of a device and it is associated with the closest host node. In addition to the existing methods, the user can obtain the identifier of the host node (`numaID`) by calling `cuDeviceGetAttribute` with `CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID` attribute type as follows:

EGM 使用由操作系统分配的 NUMA node 标识符。注意，这个标识符不同于 device ordinal，它对应距离该 device 最近的 host node。除已有方法外，还可以调用 `cuDeviceGetAttribute`，查询 `CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID` 属性，获得 host node 的标识符 `numaID`：

```cpp
int numaId;
cuDeviceGetAttribute(&numaId, CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID, deviceOrdinal);
```

**解读：** `numaId` 用于选择 host memory 的放置位置，GPU device ordinal 用于选择或授权访问 GPU；二者即使数值碰巧相同，也不能互换。跨节点时还必须明确 ID 属于哪台机器，Node A 的 NUMA ID 不能直接当作 Node B 的本地 NUMA ID。

#### 4.19.1.3. Allocators and EGM support（Allocator 与 EGM 支持）

> Mapping system memory as EGM does not cause any performance issues. In fact, accessing a remote socket’s system memory mapped as EGM is going to be faster. Because, with EGM traffic is guaranteed to be routed over NVLinks. Currently, `cuMemCreate` and `cudaMemPoolCreate` allocators are supported with appropriate location type and NUMA identifiers.

将系统内存映射为 EGM 不会造成性能问题。原文进一步指出，访问映射为 EGM 的远程 socket 系统内存会更快，因为 EGM 保证流量经由 NVLink 路由。目前支持使用 `cuMemCreate` 和 `cudaMemPoolCreate`，并指定相应的 location type 与 NUMA 标识符。

**解读：** 原文关于“不会造成性能问题”和“远程访问会更快”的说法应结合其比较对象理解：它强调 EGM 将流量路由到 NVLink 的优势。不能据此推导所有工作负载都会加速，或远程内存访问等价于本地访问。

#### 4.19.1.4. Memory management extensions to current APIs（现有 API 的内存管理扩展）

> Currently, EGM memory can be mapped with Virtual Memory (`cuMemCreate`) or Stream Ordered Memory (`cudaMemPoolCreate`) allocators. The user is responsible for allocating physical memory and mapping it to a virtual memory address space on all sockets.

当前可以通过 Virtual Memory allocator（`cuMemCreate`）或 Stream Ordered Memory allocator（`cudaMemPoolCreate`）映射 EGM 内存。用户负责分配物理内存，并在所有相关 socket 的虚拟地址空间中建立映射。

> **Note**
>
> Multi-node, multi-GPU platforms require interprocess communication. Therefore we encourage the reader to see Chapter 4.16.

**注意：** 多节点、多 GPU 平台需要进程间通信，因此原文建议阅读第 4.16 章。

> **Note**
>
> We encourage readers to read CUDA Programming Guide’s Chapter 4.17 and Chapter 4.3 for a better understanding.

**注意：** 为更好地理解本节，原文建议阅读 CUDA Programming Guide 第 4.17 章和第 4.3 章。

> New CUDA property types have been added to APIs for allowing those approaches to understand allocation locations using NUMA-like node identifiers:

CUDA API 新增了以下属性类型，使上述方式能够通过类似 NUMA node 的标识符表达 allocation 的位置：

> | CUDA Type | Used with |
> | --- | --- |
> | `CU_MEM_LOCATION_TYPE_HOST_NUMA` | `CUmemAllocationProp` for `cuMemCreate` |
> | `cudaMemLocationTypeHostNuma` | `cudaMemPoolProps` for `cudaMemPoolCreate` |

| CUDA 类型 | 配合使用的属性与 API |
| --- | --- |
| `CU_MEM_LOCATION_TYPE_HOST_NUMA` | 用于 `cuMemCreate` 的 `CUmemAllocationProp`。 |
| `cudaMemLocationTypeHostNuma` | 用于 `cudaMemPoolCreate` 的 `cudaMemPoolProps`。 |

> **Note**
>
> Please see CUDA Driver API and CUDA Runtime Data Types to find more about NUMA specific CUDA types.

**注意：** 更多与 NUMA 相关的 CUDA 类型信息，参见 CUDA Driver API 和 CUDA Runtime Data Types。

**解读：** 两条路径使用不同层次的管理方式：VMM 显式拆分物理分配、地址保留、映射和权限设置；memory pool 则通过 pool 属性确定内存位置，通过 stream-ordered API 管理 allocation 生命周期。“映射全部 socket”不能理解为所有系统、进程自动共享一个相同指针。

### 4.19.2. Using the EGM Interface（使用 EGM 接口）

#### 4.19.2.1. Single-Node, Single-GPU（单节点、单 GPU）

> Any of the existing CUDA host allocators as well as system allocated memory can be used to benefit from high-bandwidth C2C. To the user, local access is what a host allocation is today.

现有 CUDA host allocator 分配的内存，以及系统分配的内存，都可以利用高带宽 C2C。对用户而言，本地访问的使用方式与现有 host allocation 一致。

> **Note**
>
> Refer to the tuning guide for more information about memory allocators and page sizes.

**注意：** 有关 memory allocator 和 page size 的更多信息，请参阅 tuning guide。

#### 4.19.2.2. Single-Node, Multi-GPU（单节点、多 GPU）

> In a multi-GPU system, the user has to provide host information for the placement. As we mentioned, a natural way to express that information would be by using NUMA node IDs and EGM follows this approach. Therefore, using the `cuDeviceGetAttribute` function the user should be able to learn the closest NUMA node id. (See Socket Identifiers: What are they? How to access them?). Then the user can allocate and manage EGM memory using VMM (Virtual Memory Management) API or CUDA Memory Pool.

在多 GPU 系统中，用户需要提供 host 信息以确定内存放置位置。NUMA node ID 是表达这种信息的自然方式，EGM 也采用该方式。因此，可以通过 `cuDeviceGetAttribute` 获取最近的 NUMA node ID，参见前面的 Socket Identifiers 一节，然后使用 VMM（Virtual Memory Management）API 或 CUDA Memory Pool 分配和管理 EGM 内存。

##### 4.19.2.2.1. Using VMM APIs（使用 VMM API）

> The first step in memory allocation using Virtual Memory Management APIs is to create a physical memory chunk that will provide a backing for the allocation. See CUDA Programming Guide’s Virtual Memory Management section for more details. In EGM allocations the user has to explicitly provide `CU_MEM_LOCATION_TYPE_HOST_NUMA` as the location type and `numaID` as the location identifier. Also in EGM, allocations must be aligned to appropriate granularity of the platform. The following code snippet shows allocating physical memory with `cuMemCreate`:

使用 Virtual Memory Management API 分配内存，第一步是创建为 allocation 提供实际存储的物理内存块。更多信息见 CUDA Programming Guide 的 Virtual Memory Management 一节。对于 EGM allocation，用户必须显式将 location type 设为 `CU_MEM_LOCATION_TYPE_HOST_NUMA`，并将 location identifier 设为 `numaID`。此外，EGM allocation 必须按照平台要求的 granularity 对齐。下面使用 `cuMemCreate` 分配物理内存：

```cpp
CUmemAllocationProp prop{};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
prop.location.id = numaId;
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop, MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
CUmemGenericAllocationHandle allocHandle;
cuMemCreate(&allocHandle, padded_size, &prop, 0);
```

**原文代码勘误：** `MEM_ALLOC_GRANULARITY_MINIMUM` 缺少 `CU_` 前缀，正式枚举是 `CU_MEM_ALLOC_GRANULARITY_MINIMUM`；本章后面的同名调用也有此问题。`ROUND_UP` 是示例依赖的辅助宏或函数，片段未提供定义。应依据查询结果对齐分配大小，而非跳过查询直接硬编码页大小。参见 [CUDA Driver VMM API](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__VA.html)。

> After physical memory allocation, we have to reserve an address space and map it to a pointer. These procedures do not have EGM-specific changes:

分配物理内存后，需要保留虚拟地址空间并将内存映射到一个指针。这两个步骤没有 EGM 特有的变化：

```cpp
CUdeviceptr dptr;
cuMemAddressReserve(&dptr, padded_size, 0, 0, 0);
cuMemMap(dptr, padded_size, 0, allocHandle, 0);
```

> Finally, the user has to explicitly protect mapped virtual address ranges. Otherwise access to the mapped space would result in a crash. Similar to the memory allocation, the user has to provide `CU_MEM_LOCATION_TYPE_HOST_NUMA` as the location type and `numaId` as the location identifier. Following code snippet create an access descriptors for the host node and the GPU to give read and write access for the mapped memory to both of them:

最后，用户必须显式设置已映射虚拟地址范围的访问保护，否则访问该范围会导致崩溃。与分配内存时类似，原文要求将 location type 设为 `CU_MEM_LOCATION_TYPE_HOST_NUMA`，将 location identifier 设为 `numaId`。下面为 host node 和 GPU 分别创建 access descriptor，授予两者对映射内存的读写权限：

```cpp
CUmemAccessDesc accessDesc[2]{{}};
accessDesc[0].location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
accessDesc[0].location.id = numaId;
accessDesc[0].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
accessDesc[1].location.type = CU_MEM_LOCATION_TYPE_DEVICE;
accessDesc[1].location.id = currentDev;
accessDesc[1].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
cuMemSetAccess(dptr, size, accessDesc, 2);
```

**解读与范围核对：** `allocHandle` 标识物理分配，`dptr` 是本进程保留并映射的虚拟地址，access descriptor 决定哪些访问方获准使用该地址。前面分配和映射的是 `padded_size`，这里传入的是 `size`；若要为整段映射授权，应统一核对范围，使用相应的已映射长度。另据当前 Driver API，`HOST_NUMA` access descriptor 中的 `id` 会被忽略，不能把它当成仅允许某个 CPU NUMA node 访问的隔离条件；分配属性中的 NUMA ID 则决定放置位置。参见 [CUDA Driver VMM API](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__VA.html)。

##### 4.19.2.2.2. Using CUDA Memory Pool（使用 CUDA Memory Pool）

> To define EGM, the user can create a memory pool on a node and give access to peers. In this case, the user has to explicitly define `cudaMemLocationTypeHostNuma` as the location type and `numaId` as the location identifier. The following code snippet shows creating a memory pool `cudaMemPoolCreate`:

用户可以在某个 node 上创建 memory pool，并允许 peer 访问，以定义 EGM。此时必须显式将 location type 设为 `cudaMemLocationTypeHostNuma`，将 location identifier 设为 `numaId`。下面通过 `cudaMemPoolCreate` 创建 memory pool：

```cpp
cudaSetDevice(homeDevice);
cudaMemPoolProps props{};
props.allocType = cudaMemAllocationTypePinned;
props.location.type = cudaMemLocationTypeHostNuma;
props.location.id = numaId;
cudaMemPoolCreate(&memPool, &props);
```

> Additionally, for direct connect peer access, it is also possible to use the existing peer access API, `cudaMemPoolSetAccess`. An example for an accessingDevice is shown in the following code snippet:

对于直接连接的 peer access，也可以使用已有的 `cudaMemPoolSetAccess` API。下面以 accessingDevice 为例：

```cpp
cudaMemAccessDesc desc{};
desc.flags = cudaMemAccessFlagsProtReadWrite;
desc.location.type = cudaMemLocationTypeDevice;
desc.location.id = accessingDevice;
cudaMemPoolSetAccess(memPool, &desc, 1);
```

**解读：** Pool 的 `props.location` 决定内存位于哪个 host NUMA node，`desc.location` 则描述访问它的 GPU。创建 Host NUMA pool 默认提供 host CPU 访问，GPU 访问仍需按要求设置。授予访问权限不会替代数据生产与消费之间的同步。参见 [CUDA Memory Pool API](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY__POOLS.html)。

> When the memory pool is created, and accesses are given, the user can set created memory pool to the residentDevice and start allocating memory using `cudaMallocAsync`:

创建 memory pool 并授予访问权限后，原文将该 pool 设置为 residentDevice 的当前 pool，再通过 `cudaMallocAsync` 开始分配内存：

```cpp
cudaDeviceSetMemPool(residentDevice, memPool);
cudaMallocAsync(&ptr, size, memPool, stream);
```

**原文 API 适用性说明：** 四参数 `cudaMallocAsync(&ptr, size, memPool, stream)` 是有效的 C++ 重载，等价于显式指定 pool 的 `cudaMallocFromPoolAsync`，并不依赖先设置 device current pool。`cudaDeviceSetMemPool` 要求 pool 位于指定 device 本地，不能把 Host NUMA pool 与 device pool 的 current 设置规则直接等同；此处第一行应结合所用 CUDA 版本核对。原代码保留。参见 [C++ cudaMallocAsync](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__HIGHLEVEL.html) 和 [cudaDeviceSetMemPool](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DEVICE.html)。

> **Note**
>
> EGM is mapped with 2MB pages. Therefore, users may encounter more TLB misses when accessing very large allocations.

**注意：** EGM 使用 2 MB page 进行映射。因此，访问非常大的 allocation 时，可能遇到更多 TLB miss。

**解读：** TLB 缓存虚拟页到物理页的转换；访问覆盖的页越多，越可能超过 TLB 覆盖能力。这里强调大 allocation 的地址转换压力，并不是说 2 MB 页本身比小页更容易 miss。数据布局、局部性和访问顺序都会影响实际表现。

#### 4.19.2.3. Multi-Node, Multi-GPU（多节点、多 GPU）

> Beyond memory allocation, remote peer access does not have EGM-specific modification and it follows CUDA inter process (IPC) protocol. See CUDA Programming Guide for more details in IPC.

除内存分配外，远程 peer access 不需要 EGM 特有的修改，而是遵循 CUDA 进程间通信（IPC）协议。更多 IPC 信息见 CUDA Programming Guide。

> The user should allocate memory using `cuMemCreate` and again the user has to explicitly provide `CU_MEM_LOCATION_TYPE_HOST_NUMA` as the location type and `numaID` as the location identifier. In addition `CU_MEM_HANDLE_TYPE_FABRIC` should be defined as the requested handle type. The following code snippet shows allocating physical memory on Node A:

用户应通过 `cuMemCreate` 分配内存，同样必须显式指定 `CU_MEM_LOCATION_TYPE_HOST_NUMA` 和 `numaID`，分别作为 location type 与 location identifier。另外，还要将 requested handle type 设为 `CU_MEM_HANDLE_TYPE_FABRIC`。下面演示在 Node A 上分配物理内存：

```cpp
CUmemAllocationProp prop{};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.requestedHandleTypes = CU_MEM_HANDLE_TYPE_FABRIC;
prop.location.type = CU_MEM_LOCATION_TYPE_HOST_NUMA;
prop.location.id = numaId;
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop,
                              MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
size_t page_size = ...;
assert(padded_size % page_size == 0);
CUmemGenericAllocationHandle allocHandle;
cuMemCreate(&allocHandle, padded_size, &prop, 0);
```

**解读与示例边界：** `CU_MEM_HANDLE_TYPE_FABRIC` 选择可跨 fabric 共享的 handle 类型；支持的系统还需要相应 IMEX 配置，不能只设置这个枚举就获得任意跨机访问能力。示例中的 `page_size = ...` 尚未补全，`assert` 只检查条件，不会替代码完成对齐，且不能代替 CUDA 返回值检查。参见 [VMM Fabric Handle 前提](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html)。

> After creating allocation handle using `cuMemCreate` the user can export that handle to the other node, Node B, calling `cuMemExportToShareableHandle`:

使用 `cuMemCreate` 创建 allocation handle 后，可以调用 `cuMemExportToShareableHandle`，将其导出供另一个节点 Node B 使用：

```cpp
cuMemExportToShareableHandle(&fabricHandle, allocHandle,
                             CU_MEM_HANDLE_TYPE_FABRIC, 0);
// At this point, fabricHandle should be sent to Node B via TCP/IP.
```

> On Node B, the handle can be imported using `cuMemImportFromShareableHandle` and treated as any other fabric handle

在 Node B 上，可以通过 `cuMemImportFromShareableHandle` 导入该 handle，并像其他 fabric handle 一样使用它。

```cpp
// At this point, fabricHandle should be received from Node A via TCP/IP.
CUmemGenericAllocationHandle allocHandle;
cuMemImportFromShareableHandle(&allocHandle, &fabricHandle,
                               CU_MEM_HANDLE_TYPE_FABRIC);
```

**解读：** 示例用 TCP/IP 传递的是 fabric handle 等控制信息，随后 GPU 对共享内存的访问走 NVLink fabric。导入的是同一底层 allocation 的引用，不是把 Node A 的内存内容复制到 Node B；两端建立的虚拟地址也不要求相同。

> When handle is imported at Node B, then the user can reserve an address space and map it locally in a regular fashion:

Node B 导入 handle 后，就可以按常规方式保留地址空间，并在本地建立映射：

```cpp
size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop,
                              MEM_ALLOC_GRANULARITY_MINIMUM);
size_t padded_size = ROUND_UP(size, granularity);
size_t page_size = ...;
assert(padded_size % page_size == 0);
CUdeviceptr dptr;
cuMemAddressReserve(&dptr, padded_size, 0, 0, 0);
cuMemMap(dptr, padded_size, 0, allocHandle, 0);
```

**原文上下文说明：** Node B 片段直接使用 `prop`、`size` 和未填写的 `page_size`，没有展示这些信息如何获得。接收方必须使用与导入 allocation 一致的属性和尺寸，不能用自身同编号的 NUMA node 擅自替换其来源。这里的 granularity 枚举同样遗漏 `CU_`；代码仅展示映射流程。

> As the final step, the user should give appropriate accesses to each of the local GPUs at Node B. An example code snippet that gives read and write access to eight local GPUs:

最后，用户需要为 Node B 上的各个本地 GPU 设置适当的访问权限。下面的代码为 8 个本地 GPU 授予读写权限：

```cpp
// Give all 8 local  GPUS access to exported EGM memory located on Node A.                                                               |
CUmemAccessDesc accessDesc[8];
for (int i = 0; i < 8; i++) {
   accessDesc[i].location.type = CU_MEM_LOCATION_TYPE_DEVICE;
   accessDesc[i].location.id = i;
   accessDesc[i].flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;
}
cuMemSetAccess(dptr, size, accessDesc, 8);
```

**解读：** `0..7` 是示例中的 Node B 本地 GPU 编号，实际程序应按本进程可见且需要访问的 GPU 构造 descriptor，不能假定总有 8 个。此处同样需要核对 `size` 与前面的 `padded_size`。获得读写权限后，跨节点的数据可见性、同步和 allocation 生命周期仍须由程序安排。

> **Note**
>
> The cross-node sharing shown here is address-centric: the imported allocation is mapped into the local virtual address space and accessed with ordinary loads and stores. For GPUs connected by an NVLink fabric, Compute fabric transport provides a resource-centric alternative that moves data with asynchronous fabric operations against a named logical endpoint rather than a mapped address. It reports an explicit per-operation completion status, so it suits large fabrics where fabric-error recovery is a concern.

**注意：** 这里展示的跨节点共享以地址为中心：将导入的 allocation 映射到本地虚拟地址空间，再通过普通 load/store 访问。对于通过 NVLink fabric 连接的 GPU，Compute Fabric Transport 提供了以资源为中心的另一种方式：对命名的 logical endpoint 发起异步 fabric 操作来移动数据，而不是通过映射地址访问。它为每次操作报告明确的完成状态，因此适合需要考虑 fabric 错误恢复的大规模 fabric。

**解读：** 最后一段比较的是两种使用共享资源的接口：EGM/VMM 将资源映射成地址，kernel 通过 load/store 访问；Compute Fabric Transport 通过命名 endpoint 提交显式异步操作，并逐次检查完成状态。后者适合围绕操作结果设计错误处理，但不表示软件无需实现恢复逻辑。本章保留全部原始代码，仅作整理与静态核对，未编译或运行。
