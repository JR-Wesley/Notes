## 3.4. Programming Systems with Multiple GPUs（多 GPU 系统编程）

来源：[CUDA Programming Guide — Programming Systems with Multiple GPUs](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html)。本节正文以用户提供的文本为准，缺失标题及代码换行按官方页面恢复。

> Multi-GPU programming allows an application to address problem sizes and achieve performance levels beyond what is possible with a single GPU by exploiting the larger aggregate arithmetic performance, memory capacity, and memory bandwidth provided by multi-GPU systems.

Multi-GPU 编程利用多 GPU 系统汇总后的算术运算能力、内存容量和内存带宽，使应用能够处理超出单个 GPU 能力的问题规模，并达到单 GPU 无法实现的性能水平。

**解读：** 多 GPU 提供的是可共同利用的资源总量，应用仍需划分工作并协调通信。能否缩短执行时间，取决于计算能否有效分摊，以及数据交换、同步和负载不均带来的开销；GPU 数量翻倍并不直接意味着速度翻倍。

> CUDA enables multi-GPU programming through host APIs, driver infrastructure, and supporting GPU hardware technologies:

CUDA 通过 host API、driver 基础设施及配套 GPU 硬件技术支持 Multi-GPU 编程：

> - Host thread CUDA context management
> - Unified memory addressing for all processors in the system
> - Peer-to-peer bulk memory transfers between GPUs
> - Fine-grained peer-to-peer GPU load/store memory access
> - Higher level abstractions and supporting system software such as CUDA interprocess communication, parallel reductions using [NCCL](https://developer.nvidia.com/nccl), and communication using NVLink and/or GPU-Direct RDMA with APIs such as [NVSHMEM](https://developer.nvidia.com/nvshmem) and MPI

- Host thread 的 CUDA context 管理
- 为系统内所有处理器提供统一的内存寻址
- GPU 之间的 peer-to-peer 批量内存传输
- 细粒度的 peer-to-peer GPU load/store 内存访问
- 更高层的抽象及配套系统软件，例如 CUDA interprocess communication、使用 [NCCL](https://developer.nvidia.com/nccl) 进行并行归约，以及借助 [NVSHMEM](https://developer.nvidia.com/nvshmem)、MPI 等 API，经由 NVLink 和／或 GPU-Direct RDMA 通信

> At the most basic level, multi-GPU programming requires the application to manage multiple active CUDA contexts concurrently, distribute data to the GPUs, launch kernels on the GPUs to complete their work, and to communicate or collect the results so that they can be acted upon by the application. The details of how this is done differ depending on the most effective mapping of an application’s algorithms, available parallelism, and existing code structure to a suitable multi-GPU programming approach. Some of the most common multi-GPU programming approaches include:

从最基本的层面看，Multi-GPU 编程要求应用同时管理多个活跃的 CUDA context，将数据分配给各 GPU，启动 kernel 完成各自的工作，再交换或收集结果，供应用进一步处理。具体做法取决于如何把应用算法、可用并行性及已有代码结构有效映射到合适的 Multi-GPU 编程方式。常见方式包括：

> - A single host thread driving multiple GPUs
> - Multiple host threads, each driving their own GPU
> - Multiple single-threaded host processes, each driving their own GPU
> - Multiple host processes containing multiple threads, each driving their own GPU
> - Multi-node NVLink-connected clusters, with GPUs driven by threads and processes running within multiple operating system instances across the cluster nodes

- 一个 host thread 驱动多个 GPU
- 多个 host thread，每个 thread 驱动自己的 GPU
- 多个单线程 host process，每个 process 驱动自己的 GPU
- 多个 host process，每个 process 包含多个 thread，各 thread 分别驱动自己的 GPU
- 通过 NVLink 互连的多节点集群：GPU 由分布在集群各节点的多个操作系统实例中的 thread 和 process 驱动

> GPUs can communicate with each other through memory transfers and peer accesses between device memories, covering each of the multi-device work distribution approaches listed above. High performance, low-latency GPU communications are supported by querying for and enabling the use of peer-to-peer GPU memory access, and leveraging NVLink to achieve high bandwidth transfers and finer-grained load/store operations between devices.

GPU 可以通过 device memory 之间的内存传输和 peer access 相互通信，覆盖上述各种多设备任务分配方式。通过查询并启用 peer-to-peer GPU memory access，以及利用 NVLink 在设备间进行高带宽传输和更细粒度的 load/store 操作，可以支持高性能、低延迟的 GPU 通信。

> CUDA unified virtual addressing permits communication between multiple GPUs within the same host process with minimal additional steps to query and enable the use of high performance peer-to-peer memory access and transfers, e.g., via NVLink.

CUDA unified virtual addressing（UVA，统一虚拟寻址）允许同一个 host process 内的多个 GPU 通信，只需少量额外步骤，查询并启用高性能 peer-to-peer memory access 与传输，例如通过 NVLink 进行通信。

**解读：** UVA 统一的是地址解释方式；它不会自动把多张 GPU 的显存合并为一块具有相同访问成本的本地内存。地址能否被另一张 GPU 使用，还取决于 peer capability、访问授权和同步。UVA 与 managed memory 也应分开理解：前者讨论寻址，后者还涉及数据的放置与访问管理。

> Communication between multiple GPUs managed by different host processes is supported through the use of interprocess communication (IPC) and Virtual memory Management (VMM) APIs. An introduction to high level IPC concepts and intra-node CUDA IPC APIs are discussed in the [Interprocess Communication](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/inter-process-communication.html#interprocess-communication) section. Advanced Virtual Memory Management (VMM) APIs support both intra-node and multi-node IPC, are usable on both Linux and Windows operating systems, and allow per-allocation granularity control over IPC sharing of memory buffers as described in [Virtual Memory Management](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html#virtual-memory-management).

对于由不同 host process 管理的多个 GPU，可以使用 interprocess communication（IPC，进程间通信）与 Virtual Memory Management（VMM，虚拟内存管理）API 支持通信。[Interprocess Communication](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/inter-process-communication.html#interprocess-communication) 一节介绍 IPC 的高层概念与节点内 CUDA IPC API。高级 VMM API 支持节点内及跨节点 IPC，可用于 Linux 和 Windows，并允许以单次内存分配为粒度，控制 memory buffer 的 IPC 共享，详见 [Virtual Memory Management](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html#virtual-memory-management)。

**解读：** 不同 process 具有各自的地址空间，因此仅把一个 process 中的指针数值发送给另一个 process，不足以共享 GPU allocation。IPC/VMM 的作用包括导出、导入资源并建立接收方可用的映射；具体跨节点能力仍受所用 handle 类型与系统支持限制。

> Compute fabric transport takes a different approach for GPUs on an NVLink fabric: rather than reaching a peer’s memory through a mapped virtual address, as the approaches above do, it names a group of resources using a logical endpoint id, a particular resource within that group via an offset, and accesses the resource with explicit, asynchronous fabric operations. See [Compute Fabric Transport](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-gpu-compute-fabric-transport) below.

对于 NVLink fabric 中的 GPU，Compute fabric transport 采用另一种方式：它用 logical endpoint ID 标识一组资源，用 offset 标识该组内的特定资源，再通过显式、异步的 fabric 操作访问资源；前述方式则通过映射后的虚拟地址访问 peer memory。参见下文 [Compute Fabric Transport](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-gpu-compute-fabric-transport)。

> CUDA itself provides the APIs needed to implement collective operations within a group of GPUs, potentially including the host, but it does not provide high level multi-GPU collective APIs itself. Multi-GPU collectives are provided by higher abstraction CUDA communication libraries such as [NCCL](https://developer.nvidia.com/nccl) and [NVSHMEM](https://developer.nvidia.com/nvshmem).

CUDA 本身提供在一组 GPU 之间实现 collective operation（集合通信操作）所需的 API，这组参与者也可能包括 host；但 CUDA 本身不直接提供高层 Multi-GPU collective API。这类集合通信由 [NCCL](https://developer.nvidia.com/nccl)、[NVSHMEM](https://developer.nvidia.com/nvshmem) 等更高抽象层的 CUDA 通信库提供。

### 3.4.1. Multi-Device Context and Execution Management（多设备 Context 与执行管理）

> The first steps that are required to for an application to use multiple GPUs are to enumerate the available GPU devices, select among the available devices as appropriate based on their hardware properties, CPU affinity, and connectivity to peers, and to create CUDA contexts for each device that the application will use.

应用使用多个 GPU 时，首先需要枚举可用的 GPU device，再根据硬件属性、CPU affinity（CPU 亲和性）及 peer 连接情况选择合适设备，并为应用将使用的每个 device 创建 CUDA context。

#### 3.4.1.1. Device Enumeration（设备枚举）

> The following code sample shows how to query number of CUDA-enabled devices, enumerate each of the devices, and query their properties.

以下代码展示如何查询支持 CUDA 的 device 数量、枚举各 device 并查询其属性。

```cpp
int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
           device, deviceProp.major, deviceProp.minor);
}
```

#### 3.4.1.2. Device Selection（设备选择）

> A host thread can set the device it is currently operating on at any time by calling `cudaSetDevice()`. Device memory allocations and kernel launches are made on the current device; streams and events are created in association with the currently set device. Until a call to `cudaSetDevice()` is made by the host thread, the current device defaults to device 0.

Host thread 随时可以调用 `cudaSetDevice()` 设置当前操作的 device。Device memory 分配与 kernel launch 均在 current device 上进行；stream 和 event 在创建时也与当时的 current device 关联。如果 host thread 尚未调用 `cudaSetDevice()`，current device 默认为 device 0。

> The following code sample illustrates how setting the current device affects subsequent memory allocation and kernel execution operations.

以下代码说明，设置 current device 会如何影响后续内存分配与 kernel 执行操作。

```cpp
size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // Set device 0 as current
float* p0;
cudaMalloc(&p0, size);       // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0); // Launch kernel on device 0

cudaSetDevice(1);            // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);       // Allocate memory on device 1
MyKernel<<<1000, 128>>>(p1); // Launch kernel on device 1
```

**解读（示例边界）：** `cudaSetDevice` 改变调用 host thread 后续操作的目标，不会把已有 `p0` 移到 device 1，也不会改变已有 stream 的归属。两段 kernel 的 host 提交顺序不等于它们在不同 GPU 上的完成顺序。示例只分配 1024 个 `float`，却启动了 128000 个 thread；是否越界取决于 `MyKernel` 的索引与边界判断，不能把这个片段直接当成完整可运行程序。

#### 3.4.1.3. Multi-Device Stream, Event, and Memory Copy Behavior（多设备 Stream、Event 与内存复制行为）

> A kernel launch will fail if it is issued to a stream that is not associated to the current device as illustrated in the following code sample.

如果将 kernel 提交到一个不属于 current device 的 stream，launch 就会失败，如以下代码所示。

```cpp
cudaSetDevice(0);               // Set device 0 as current
cudaStream_t s0;
cudaStreamCreate(&s0);          // Create stream s0 on device 0
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 0 in s0

cudaSetDevice(1);               // Set device 1 as current
cudaStream_t s1;
cudaStreamCreate(&s1);          // Create stream s1 on device 1
MyKernel<<<100, 64, 0, s1>>>(); // Launch kernel on device 1 in s1

// This kernel launch will fail, since stream s0 is not associated to device 1:
MyKernel<<<100, 64, 0, s0>>>(); // Launch kernel on device 1 in s0
```

> A memory copy will succeed even if it is issued to a stream that is not associated to the current device.

即使提交 memory copy 的 stream 不属于 current device，复制操作也可以成功。

> `cudaEventRecord()` will fail if the input event and input stream are associated to different devices.

如果输入 event 和输入 stream 分属不同 device，`cudaEventRecord()` 会失败。

> `cudaEventElapsedTime()` will fail if the two input events are associated to different devices.

如果两个输入 event 分属不同 device，`cudaEventElapsedTime()` 会失败。

> `cudaEventSynchronize()` and `cudaEventQuery()` will succeed even if the input event is associated to a device that is different from the current device.

即使输入 event 属于与 current device 不同的 device，`cudaEventSynchronize()` 和 `cudaEventQuery()` 也可以成功。

> `cudaStreamWaitEvent()` will succeed even if the input stream and input event are associated to different devices. `cudaStreamWaitEvent()` can therefore be used to synchronize multiple devices with each other.

即使输入 stream 和输入 event 分属不同 device，`cudaStreamWaitEvent()` 也可以成功。因此，可以使用 `cudaStreamWaitEvent()` 在多个 device 之间建立同步。

> Each device has its own [default stream](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html#async-execution-blocking-non-blocking-default-stream), so commands issued to the default stream of a device may execute out of order or concurrently with respect to commands issued to the default stream of any other device.

每个 device 都有自己的 [default stream](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html#async-execution-blocking-non-blocking-default-stream)，因此，提交到某个 device 的 default stream 的命令，相对于提交到其他 device 的 default stream 的命令，可以无序执行或并发执行。

**解读：** 上述规则可以按“对象归属”和“等待关系”区分：

| 操作 | 设备关联规则 | 含义 |
| --- | --- | --- |
| Kernel launch | Stream 必须属于 current device | 切换 device 不会迁移 stream |
| Memory copy | Stream 与 current device 不同，本身不构成失败条件 | 仍须满足指针、复制类型和其他 API 条件 |
| `cudaEventRecord` | Event 与记录它的 stream 必须属于同一 device | Event 记录该 stream 的执行进度 |
| `cudaEventElapsedTime` | 两个 event 必须属于同一 device | 不能直接用跨 GPU event 计算耗时 |
| `cudaEventSynchronize` / `cudaEventQuery` | Event 可以属于其他 device | 允许等待或查询该 event 的状态 |
| `cudaStreamWaitEvent` | Stream 可以等待其他 device 的 event | 可建立跨 GPU 的执行依赖 |

这里的“可以成功”指设备归属不匹配本身不会阻止调用；例如 `cudaEventQuery` 在 event 尚未完成时仍可返回 `cudaErrorNotReady`，参见 [Runtime 状态码说明](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__TYPES.html)。跨 GPU 的生产者—消费者关系应通过 event 或其他同步机制明确表达，不能依赖两张卡上的 default stream 名称相同。

### 3.4.2. Multi-Device Peer-to-Peer Transfers and Memory Access（多设备 P2P 传输与内存访问）

#### 3.4.2.1. Peer-to-Peer Memory Transfers（P2P 内存传输）

> CUDA can perform memory transfers between devices and will take advantage of dedicated copy engines and NVLink hardware to maximize performance when peer-to-peer memory access is possible.

CUDA 可以在 device 之间执行内存传输；当支持 peer-to-peer memory access 时，会利用专用 copy engine 和 NVLink 硬件尽可能提高性能。

> `cudaMemcpy` can be used with the copy type `cudaMemcpyDeviceToDevice` or `cudaMemcpyDefault`.

可以使用 `cudaMemcpy`，并将复制类型设为 `cudaMemcpyDeviceToDevice` 或 `cudaMemcpyDefault`。

> Otherwise, copies must be performed using `cudaMemcpyPeer()`, `cudaMemcpyPeerAsync()`, `cudaMemcpy3DPeer()`, or `cudaMemcpy3DPeerAsync()` as illustrated in the following code sample.

否则，必须使用 `cudaMemcpyPeer()`、`cudaMemcpyPeerAsync()`、`cudaMemcpy3DPeer()` 或 `cudaMemcpy3DPeerAsync()` 进行复制，如以下代码所示。

**解读：** `cudaMemcpyDefault` 依赖 UVA 推断指针所指的内存类型，参见 [Unified Addressing](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__UNIFIED.html)；显式 peer copy 接口则把源、目标 device 编号也作为参数。API 名称包含 Peer，并不单独证明传输走 NVLink；实际路径和带宽仍取决于设备能力与拓扑。

```cpp
cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0

cudaSetDevice(1);                   // Set device 1 as current
float* p1;
cudaMalloc(&p1, size);              // Allocate memory on device 1

cudaSetDevice(0);                   // Set device 0 as current
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaMemcpyPeer(p1, 1, p0, 0, size); // Copy p0 to p1
MyKernel<<<1000, 128>>>(p1);        // Launch kernel on device 1
```

> A copy (in the implicit `NULL` stream) between the memories of two different devices:

在两个不同 device 的内存之间，通过隐式 `NULL` stream 执行的复制：

> - does not start until all commands previously issued to either device have completed and
> - runs to completion before any commands (see [Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html#asynchronous-execution)) issued after the copy to either device can start.

- 必须等此前提交到任一 device 的所有命令完成后，才能开始；并且
- 必须执行完毕后，随后提交到任一 device 的命令才能开始，参见 [Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html#asynchronous-execution)。

> Consistent with the normal behavior of streams, an asynchronous copy between the memories of two devices may overlap with copies or kernels in another stream.

与 stream 的通常行为一致，两个 device 内存之间的异步复制，可以与另一个 stream 中的复制或 kernel 执行重叠。

> If peer-to-peer access is enabled between two devices, e.g., as described in [Peer-to-Peer Memory Access](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-gpu-peer-to-peer-memory-access), peer-to-peer memory copies between these two devices no longer need to be staged through the host and are therefore faster.

如果两个 device 之间已启用 peer-to-peer access，例如按 [Peer-to-Peer Memory Access](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/multi-gpu-systems.html#multi-gpu-peer-to-peer-memory-access) 一节所述启用，那么二者之间的 peer-to-peer memory copy 就不再需要经由 host 中转，因此更快。

**解读：** 此处 NULL stream 复制的强顺序保证，应与后文的异步复制、直接 peer load/store 区分。改成异步操作后，需要重新建立数据依赖并保证 buffer 生命周期；只有独立工作、硬件资源与依赖关系允许时，才可能实现传输与计算重叠。避免 host 中转能减少数据路径，但具体加速幅度仍需测量。

#### 3.4.2.2. Peer-to-Peer Memory Access（P2P 内存访问）

> Depending on the system properties, specifically the PCIe and/or NVLink topology, devices are able to address each other’s memory (i.e., a kernel executing on one device can dereference a pointer to the memory of the other device). Peer-to-peer memory access is supported between two devices if `cudaDeviceCanAccessPeer()` returns true for the specified devices.

根据系统属性，尤其是 PCIe 和／或 NVLink 拓扑，device 可以寻址彼此的内存，也就是在一个 device 上执行的 kernel 可以解引用指向另一个 device 内存的指针。原文表述为：若 `cudaDeviceCanAccessPeer()` 对指定的两个 device 返回 true，则二者支持 peer-to-peer memory access。

**解读（返回值勘误）：** `cudaDeviceCanAccessPeer(&canAccess, device, peerDevice)` 返回的是 `cudaError_t` 状态；是否能够访问由输出参数 `canAccess` 的 0/1 值表示。这里应检查 API 成功后再检查该输出值，不能把函数返回值直接当布尔能力结果。参见 [Peer Device Memory Access](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__PEER.html)。

> Peer-to-peer memory access must be enabled between two devices by calling `cudaDeviceEnablePeerAccess()` as illustrated in the following code sample. On non-NVSwitch enabled systems, each device can support a system-wide maximum of eight peer connections.

必须调用 `cudaDeviceEnablePeerAccess()`，才能在两个 device 之间启用 peer-to-peer memory access，如以下代码所示。在未启用 NVSwitch 的系统上，每个 device 在系统范围内最多支持 8 个 peer connection。

> A unified virtual address space is used for both devices (see [Unified Virtual Address Space](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html#memory-unified-virtual-address-space)), so the same pointer can be used to address memory from both devices as shown in the code sample below.

两个 device 使用统一的虚拟地址空间，参见 [Unified Virtual Address Space](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html#memory-unified-virtual-address-space)，因此可以从两个 device 使用同一个指针访问内存，如以下示例所示。

```cpp
cudaSetDevice(0);                   // Set device 0 as current
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // Allocate memory on device 0
MyKernel<<<1000, 128>>>(p0);        // Launch kernel on device 0

cudaSetDevice(1);                   // Set device 1 as current
cudaDeviceEnablePeerAccess(0, 0);   // Enable peer-to-peer access
                                   // with device 0

// Launch kernel on device 1
// This kernel launch can access memory on device 0 at address p0
MyKernel<<<1000, 128>>>(p0);
```

**解读（访问方向与同步）：** 当 current device 为 1 时，`cudaDeviceEnablePeerAccess(0, 0)` 允许 device 1 访问 device 0 的内存；它不会同时授权反方向的访问。双向访问需要分别查询并启用，参见 [Peer Access 的方向性](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__PEER.html)。

原例没有显式等待 device 0 的 kernel 完成。如果 device 1 的 kernel 读取或修改 device 0 正在写入的同一数据，就需要补充跨 device event 等同步；仅切换 device 或启用 peer access，不能作为数据就绪的依据。这里保留原例，以展示访问方式。

> **Note**

**注意：**

> The use of `cudaDeviceEnablePeerAccess()` to enable peer memory access operates globally on all previous and subsequent GPU memory allocations on the peer device. Enabling peer access to a device via `cudaDeviceEnablePeerAccess()` adds runtime cost to device memory allocation operations on that peer due to the need make the allocations immediately accessible to the current device and any other peers that also have access, adding multiplicative overhead that scales with the number of peer devices.

使用 `cudaDeviceEnablePeerAccess()` 启用 peer memory access，会全局作用于 peer device 上此前和此后进行的所有 GPU 内存分配。由于必须让这些分配立即对 current device 及其他已获准访问的 peer 可见，启用该功能会增加 peer device 上内存分配操作的运行时开销；这一额外开销会随着 peer device 数量增长而倍增。

> A more scalable alternative to enabling peer memory access for all device memory allocations is to make use of CUDA Virtual Memory Management APIs to explicitly allocate peer-accessible memory regions only as-needed, at allocation time. By requesting peer-accessibility explicitly during memory allocation, the runtime cost of memory allocations are unharmed for allocations not accessible to peers, and peer-accessible data structures are correctly scoped for improved software debugging and reliability (see [Virtual Memory Management](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html#virtual-memory-management)).

一种更具可扩展性的替代方式，是使用 CUDA VMM API，在分配时按需显式创建允许 peer 访问的内存区域，而不对所有 device memory allocation 统一启用 peer access。这样，不向 peer 开放的内存分配就不会承担这部分额外运行时开销；同时，可供 peer 访问的数据结构也具有明确的共享范围，有利于调试与可靠性，参见 [Virtual Memory Management](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html#virtual-memory-management)。

**解读：** 全局开启 peer access 方便使用，但会把映射维护成本扩展到许多本不需要共享的 allocation。VMM 让应用明确哪些区域向哪些 GPU 开放，适合对共享范围作细粒度控制。原文未解析的 `ref::virtual-memory-management` 交叉引用已整理为有效文档链接。

#### 3.4.2.3. Peer-to-Peer Memory Consistency（P2P 内存一致性）

> Synchronization operations must be used to enforce the ordering and correctness of memory accesses by concurrently executing threads in grids distributed across multiple devices. Threads synchronizing across devices operate at the `thread_scope_system` [synchronization scope](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#thread-scopes). Similarly, memory operations fall within the `thread_scope_system` [memory synchronization domain](https://docs.nvidia.com/cuda/cuda-c-programming-guide/#memory-synchronization-domains).

分布在多个 device 上的 grid，其 thread 并发执行时，必须通过同步操作保证内存访问的顺序与正确性。跨 device 同步的 thread 使用 `thread_scope_system` [同步作用域](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#thread-scopes)。原文还将此类内存操作描述为处于 `thread_scope_system` [memory synchronization domain](https://docs.nvidia.com/cuda/cuda-c-programming-guide/#memory-synchronization-domains) 中。

**解读（术语区分）：** `thread_scope_system` 是 thread scope，规定同步操作覆盖哪些线程；memory synchronization domain 则用于划分内存操作的排序与 fence 影响范围。两者相关，但不是同一个概念，也不存在用 `thread_scope_system` 命名的 domain 编号。参见 [Thread Scopes](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#thread-scopes) 与 [Memory Synchronization Domains](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/memory-sync-domains.html)。

> CUDA [Atomic Functions](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#atomic-functions) can perform read-modify-write operations on an object in peer device memory when only a single GPU is accessing that object. The requirements and limitations for peer atomicity are described in the CUDA memory model [atomicity requirements](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#atomicity) discussion.

当只有单个 GPU 访问某个对象时，CUDA [Atomic Functions](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#atomic-functions) 可以对位于 peer device memory 中的该对象执行 read-modify-write（读—改—写）操作。Peer atomicity 的要求和限制，见 CUDA memory model 中关于 [atomicity requirements](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#atomicity) 的讨论。

**解读（跨 GPU 原子性）：** 原文给出“仅一张 GPU 访问”的情况，并不意味着任何普通 atomic 都能安全协调多张 GPU。多 GPU 同时访问 peer GPU memory 中的原子对象时，需要适当的 system scope、内存顺序，以及每个访问源 GPU 到目标 GPU 的 native atomic 支持；该能力可通过 `cudaDeviceGetP2PAttribute` 查询 `cudaDevP2PAttrNativeAtomicSupported`。P2P 可读写不等于支持所需的跨 GPU 原子性。参见 [CUDA memory model 的 Atomicity 条件](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html#atomicity)。

#### 3.4.2.4. Multi-Device Managed Memory（多设备 Managed Memory）

> Managed memory can be used on multi-GPU systems with peer-to-peer support. The detailed requirements for concurrent multi-device managed memory access and APIs for GPU-exclusive access to managed memory are described in [Multi-GPU](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html#um-legacy-multi-gpu).

支持 peer-to-peer 的 Multi-GPU 系统可以使用 managed memory。多 device 并发访问 managed memory 的详细要求，以及允许 GPU 独占访问 managed memory 的 API，见 [Multi-GPU](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html#um-legacy-multi-gpu) 一节。

**解读：** Managed memory 可以简化访问接口，但不会消除跨 GPU 数据依赖。并发访问资格、数据放置和迁移行为，应结合该段链接中的设备能力条件理解；统一的指针写法不代表每次访问都有本地显存的成本。

#### 3.4.2.5. Host IOMMU Hardware, PCI Access Control Services, and VMs（Host IOMMU、PCI ACS 与虚拟机）

> On Linux specifically, CUDA and the display driver do not support IOMMU-enabled bare-metal PCIe peer-to-peer memory transfer. However, CUDA and the display driver do support IOMMU via virtual machine pass through. The IOMMU must be disabled when running Linux on a bare metal system to prevent silent device memory corruption. Conversely, the IOMMU should be enabled and the VFIO driver be used for PCIe pass through for virtual machines.

具体到 Linux，CUDA 和 display driver 不支持启用 IOMMU 的裸机 PCIe peer-to-peer 内存传输，但支持通过虚拟机直通方式使用 IOMMU。原文要求：在裸机 Linux 系统上运行时，必须禁用 IOMMU，以防止无明显报错的 device memory 数据损坏；相反，通过 PCIe passthrough 向虚拟机直通设备时，应启用 IOMMU 并使用 VFIO driver。

> On Windows the IOMMU limitation above does not exist.

Windows 不存在上述 IOMMU 限制。

> See also [Allocating DMA Buffers on 64-bit Platforms](https://download.nvidia.com/XFree86/Linux-x86_64/510.85.02/README/dma_issues.html).

另见 [Allocating DMA Buffers on 64-bit Platforms](https://download.nvidia.com/XFree86/Linux-x86_64/510.85.02/README/dma_issues.html)。

> Additionally, PCI Access Control Services (ACS) can be enabled on systems that support IOMMU. The PCI ACS feature redirects all PCI point-to-point traffic through the CPU root complex, which can cause significant performance loss due to the reduction in overall bisection bandwidth.

此外，在支持 IOMMU 的系统上还可以启用 PCI Access Control Services（ACS）。PCI ACS 功能会将 PCI 点对点流量重定向，经由 CPU root complex 转发；由于降低了整体 bisection bandwidth（对分带宽），这可能造成显著性能损失。

**解读（适用范围）：** 这里的 IOMMU 限制针对原文描述的 Linux 裸机 PCIe P2P 场景；虚拟机直通的条件不同，不应据此推导所有 CUDA 系统都要禁用 IOMMU。ACS 讨论的是路由路径及带宽：如果本可直接通信的设备必须经 root complex 转发，共享链路就可能成为瓶颈。本次仅整理文档，没有修改系统设置。

#### 3.4.2.6. Compute Fabric Transport（计算 Fabric 传输）

> Peer-to-peer memory access reaches a peer allocation through a virtual address that the issuing process has reserved and mapped. Compute fabric transport provides an alternative for large NVLink fabrics that names the peer by a logical endpoint id and the resource accessed by offset rather than a mapped address. It is intended for communication libraries and advanced applications and is described in [Compute Fabric Transport](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/compute-fabric-transport.html#compute-fabric-transport).

Peer-to-peer memory access 通过发起进程预留并映射的虚拟地址访问 peer allocation。对于大型 NVLink fabric，Compute fabric transport 提供了另一种方式：用 logical endpoint ID 标识 peer，以 offset 标识所访问的资源，而不是使用映射地址。它面向通信库和高级应用，详见 [Compute Fabric Transport](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/compute-fabric-transport.html#compute-fabric-transport)。

**解读：** Peer memory access 的访问入口是已映射的虚拟地址，Compute fabric transport 的访问入口是 endpoint ID 加资源 offset，并通过显式异步操作完成通信。两种模型对寻址和操作完成的表达方式不同，应根据通信库的接口约定管理资源与完成依赖。本节 5 段原始代码仅恢复排版并静态核对，未编译或运行。
