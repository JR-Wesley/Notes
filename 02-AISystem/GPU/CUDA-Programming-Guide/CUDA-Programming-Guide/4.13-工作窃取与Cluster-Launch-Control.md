## 4.13. Work Stealing with Cluster Launch Control（使用 Cluster Launch Control 实现工作窃取）

来源：[CUDA Programming Guide — Work Stealing with Cluster Launch Control](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cluster-launch-control.html)。按用户提供文本整理。

> Dealing with problems of variable data and computation sizes is essential when developing CUDA applications. Traditionally, CUDA developers have used two main approaches to determine the number of kernel thread blocks to launch: fixed work per thread block and fixed number of thread blocks. Both approaches have their advantages and disadvantages.

开发 CUDA 应用时，必须能够处理数据量和计算规模变化的问题。传统上，CUDA 开发者主要采用两种方式来确定 kernel 启动的 thread block 数量：固定每个 thread block 的工作量，或固定 thread block 的数量。两种方式各有优缺点。

> Fixed Work per Thread Block: In this approach, the number of thread blocks is determined by the problem size, while the amount of work done by each thread block remains constant.

**固定每个 thread block 的工作量：** 在这种方式中，thread block 数量由问题规模决定，而每个 thread block 执行的工作量保持不变。

> Key advantages of this approach:

这种方式的主要优点：

**Load balancing between SMs（SM 之间的负载均衡）**

> When thread block run-times exhibit variability and/or when the number of thread blocks is much larger than what the GPU can execute simultaneously (resulting in a low-tail effect), this approach allows the GPU scheduler to run more thread blocks on some SMs than others.

当各 thread block 的运行时间存在差异，和/或 thread block 数量远大于 GPU 能同时执行的数量时（从而减轻尾部效应），这种方式允许 GPU 调度器在某些 SM 上执行比其他 SM 更多的 thread block。

**Preemption（抢占）**

> The GPU scheduler can start executing a higher-priority kernel, even if it is launched after a lower-priority kernel has already begun executing, by scheduling its thread blocks as thread blocks of the lower-priority kernel complete. It can then resume execution of the lower-priority kernel once the higher-priority kernel has finished executing.

即使高优先级 kernel 在低优先级 kernel 已经开始执行之后才启动，GPU 调度器仍可以在低优先级 kernel 的 thread block 完成时，调度高优先级 kernel 的 thread block 开始执行。等高优先级 kernel 执行完毕，再继续执行低优先级 kernel。

**解读：** 这里的 preemption 描述在低优先级 block 完成、释放执行资源后，优先调度高优先级工作。不能据此推断正在运行的 block 会在任意指令处被中断。

> Fixed Number of Thread Blocks: In this approach, often implemented as a block-stride or grid-stride loop, the number of thread blocks does not depend on the problem size. Instead, the amount of work done by each thread block is a function of the problem size. Typically, the number of thread blocks is based on the number of SMs on the GPU where the kernel is executed and the desired occupancy.

**固定 thread block 数量：** 这种方式通常通过 block-stride 或 grid-stride loop 实现，thread block 数量不随问题规模变化，而每个 thread block 的工作量随问题规模变化。通常根据执行 kernel 的 GPU 所拥有的 SM 数量，以及期望的 occupancy，确定 thread block 数量。

> Key advantages of this approach:

这种方式的主要优点：

**Reduced thread block overheads（减少 thread block 开销）**

> This approach not only reduces amortized thread block launch latency but also minimizes the computational overhead associated with shared operations across all thread blocks. These overheads can be significantly higher than launch latency overheads.

这种方式不仅降低了摊销后的 thread block 启动延迟，也减少了所有 thread block 都要执行的公共操作所带来的计算开销。这些计算开销可能明显高于启动延迟开销。

> For example, in convolution kernels, a prologue for calculating convolution coefficients – independent of the thread block index – can be computed fewer times due to the fixed number of thread blocks, thus reducing redundant computations.

例如，在 convolution kernel 中，用于计算卷积系数的 prologue 与 thread block 索引无关。固定 thread block 数量可以减少这段准备计算的执行次数，从而减少重复计算。

**解读：** 固定 block 数量可以让同一批驻留线程反复处理数据，摊薄准备计算的成本；但静态的 grid-stride 分工对工作量不均衡的适应能力有限。CLC 保留按逻辑 block 划分任务的方式，让已运行的 block 动态接手后续任务。

> Cluster Launch Control is a feature introduced in the NVIDIA Blackwell GPU architecture (compute capability 10.0) that aims to combine the benefits of the previous two approaches. It provides developers with more control over thread block scheduling by allowing them to cancel thread blocks or thread block clusters. This mechanism enables work stealing. Work stealing is a dynamic load-balancing technique in parallel computing where idle processors actively “steal” tasks from the work queues of busy processors, rather than wait for work to be assigned.

Cluster Launch Control 是 NVIDIA Blackwell GPU 架构（compute capability 10.0）引入的功能，旨在结合上述两种方式的优点。它允许开发者取消 thread block 或 thread block cluster 的启动，从而对 thread block 调度施加更多控制。这种机制支持 work stealing（工作窃取）。Work stealing 是并行计算中的动态负载均衡技术：空闲处理器主动从繁忙处理器的工作队列中“取走”任务，而不是等待任务被分配给自己。

> Figure 54 Cluster Launch Control Flow

图 54：Cluster Launch Control 执行流程。

> With cluster launch control, a thread block attempts to cancel the launch of another thread block that has not started executing yet. If the cancellation request succeeds, it “steals” the other thread block’s work by using its index to perform the task. The cancellation will fail if there are no more thread block indices available or for other reasons, such as a higher-priority kernel being scheduled. In the latter case, if a thread block exits after a cancellation failure, the scheduler can start executing the higher-priority kernel, after which it will continue scheduling the remaining thread blocks of the current kernel for execution. The figure above presents the execution flow of this procedure.

使用 Cluster Launch Control 时，一个 thread block 会尝试取消另一个尚未开始执行的 thread block 的启动。如果取消请求成功，它就利用被取消 block 的索引执行对应任务，从而接手其工作。如果没有更多可用的 thread block 索引，或者由于其他原因（例如正在调度更高优先级的 kernel），取消请求会失败。在后一种情况下，如果当前 thread block 在取消失败后退出，调度器就可以开始执行更高优先级的 kernel；之后再继续调度当前 kernel 剩余的 thread block。上图展示了这一过程的执行流程。

**解读：** CLC 接手的是尚未启动的逻辑 block 所对应的任务，成功取消后，被取消的 block 不再单独启动。取消失败可能意味着有高优先级工作需要调度，因此失败不能简单等同于整个 grid 已经没有剩余工作。

下表总结了三种方式的优缺点：

> | --- | --- | --- | --- |
> | Reduced overheads | ✗ | ✓ | ✓ |
> | Preemption | ✓ | ✗ | ✓ |
> | Load balancing | ✓ | ✗ | ✓ |

| 优点 | 固定每个 thread block 的工作量 | 固定 thread block 数量 | Cluster Launch Control |
| --- | --- | --- | --- |
| 减少开销 | ✗ | ✓ | ✓ |
| 抢占 | ✓ | ✗ | ✓ |
| 负载均衡 | ✓ | ✗ | ✓ |

### 4.13.1. API Details（API 细节）

> Cancelling a thread block via the cluster launch control API is done asynchronously and synchronized using a shared memory barrier, following a programming pattern similar to asynchronous data copies.

通过 Cluster Launch Control API 取消 thread block 是异步操作，使用 shared memory barrier 进行同步，其编程模式与异步数据拷贝类似。

> The API, available through libcu++, provides:

该 API 通过 libcu++ 提供，包含：

> - A request instruction that writes encoded cancellation results to a `__shared__` variable.
> - Decoding instructions that extract success/failure status and the cancelled thread block index.

- 请求指令，将编码后的取消结果写入一个 `__shared__` 变量。
- 解码指令，从结果中提取成功或失败状态，以及被取消的 thread block 索引。

> Note that cluster launch control operations are modeled as async proxy operations (see Async Thread and Async Proxy).

注意，Cluster Launch Control 操作被建模为 async proxy 操作，参见 Async Thread and Async Proxy。

**解读：** 取消请求的提交与结果就绪是两件事。必须先通过 barrier 等待异步写入完成，再解码 `result`；由于操作跨越 async 与 generic proxy，还需要满足相应的可见性与顺序要求。

#### 4.13.1.1. Thread Block Cancellation（取消 Thread Block）

> The preferred way to use Cluster Launch Control is from a single thread, i.e., one request at a time.

推荐由单个线程使用 Cluster Launch Control，即一次发出一个请求。

> The cancellation process involves five steps:

取消过程包括五个步骤：

> - Setup Phase (Steps 1-2): Declare and initialize cancellation result and synchronization variables.
> - Work-Stealing Loop (Steps 3-5): Execute repeatedly to request, synchronize, and process cancellation results.

- **设置阶段（步骤 1–2）：** 声明并初始化取消结果和同步变量。
- **Work-stealing 循环（步骤 3–5）：** 重复执行请求、同步及取消结果处理。

> Declare variables for thread block cancellation:

**步骤 1：** 声明用于取消 thread block 的变量：

```cpp
__shared__ uint4 result; // Request result.
__shared__ uint64_t bar; // Synchronization barrier.
int phase = 0;           // Synchronization barrier phase.
```

> Initialize shared memory barrier with a single arrival count:

**步骤 2：** 初始化 shared memory barrier，将 arrival count 设为 1：

```cpp
if (cg::thread_block::thread_rank() == 0)
    ptx::mbarrier_init(&bar, 1);
__syncthreads();
```

> Submit asynchronous cancellation request by a single thread and set transaction count:

**步骤 3：** 由单个线程提交异步取消请求，并设置 transaction count：

```cpp
if (cg::thread_block::thread_rank() == 0) {
    cg::invoke_one(cg::coalesced_threads(), [&](){ptx::clusterlaunchcontrol_try_cancel(&result, &bar);});
    ptx::mbarrier_arrive_expect_tx(ptx::sem_relaxed, ptx::scope_cta, ptx::space_shared, &bar, sizeof(uint4));
}
```

**解读：** 本例 barrier 的 arrival count 为 1，对应单个提交线程的到达；期望的 transaction 字节数为 `sizeof(uint4)`，对应异步写入的结果大小。两者计量的对象不同，不能都理解为“线程数”。

**Note（注意）**

> Since thread block cancellation is a uniform instruction, it is recommended to submit it inside `invoke_one` thread selector. This allows the compiler to optimize out the peeling loop.

由于 thread block 取消指令是一条 uniform 指令，建议在 `invoke_one` 线程选择器中提交它。这样编译器可以优化掉 peeling loop。

> Synchronize (complete) asynchronous cancellation request:

**步骤 4：** 同步，等待异步取消请求完成：

```cpp
while (!ptx::mbarrier_try_wait_parity(&bar, phase))
{}
phase ^= 1;
```

**解读：** `phase` 记录当前等待的 barrier phase 奇偶性。每完成一轮等待后翻转一次，使下一轮等待对应下一次结果写入。

> Retrieve cancellation status and cancelled thread block index:

**步骤 5：** 获取取消状态和被取消的 thread block 索引：

```cpp
bool success = ptx::clusterlaunchcontrol_query_cancel_is_canceled(result);
if (success) {
    // Don't need all three for 1D/2D thread blocks:
    int bx = ptx::clusterlaunchcontrol_query_cancel_get_first_ctaid_x(result);
    int by = ptx::clusterlaunchcontrol_query_cancel_get_first_ctaid_y(result);
    int bz = ptx::clusterlaunchcontrol_query_cancel_get_first_ctaid_z(result);
}
```

> Ensure visibility of shared memory operations between async and generic proxies, and protect against data races between iterations of the work-stealing loop.

确保 shared memory 操作在 async proxy 与 generic proxy 之间的可见性，并防止 work-stealing 循环不同迭代之间发生数据竞争。

**解读：** 即使结果写入完成，也必须保证所有参与线程读完上一轮结果后，下一轮请求才能覆盖 `result`。后面的完整 kernel 通过线程组同步保护结果复用，并使用 proxy fence 表达跨 proxy 的访问顺序。

#### 4.13.1.2. Constraints on Thread Block Cancellation（Thread Block 取消的限制）

> The constraints are related to failed cancellation requests:

以下限制与失败的取消请求有关：

> Submitting another cancellation request after observing a previously failed request is undefined behavior.

在观察到前一个请求失败后，再提交另一个取消请求，会产生 undefined behavior（未定义行为）。

> In the two code examples below, assuming the first cancellation request fails, only the first example exhibits undefined behavior. The second example is correct because there is no observation between the cancellation requests:

下面两个代码示例都假设第一次取消请求失败。其中只有第一个示例存在未定义行为；第二个示例是正确的，因为两次取消请求之间没有观察第一次请求的结果。

**Invalid code:（无效代码）**

```cpp
// First request:
ptx::clusterlaunchcontrol_try_cancel(&result0, &bar0);

// First request query:
[Synchronize bar0 code here.]
bool success0 = ptx::clusterlaunchcontrol_query_cancel_is_canceled(result0);
assert(!success0); // Observed failure; second cancellation will be invalid.

// Second request - next line is Undefined Behavior:
ptx::clusterlaunchcontrol_try_cancel(&result1, &bar1);
```

**Valid code:（有效代码）**

```cpp
// First request:
ptx::clusterlaunchcontrol_try_cancel(&result0, &bar0);

// Second request:
ptx::clusterlaunchcontrol_try_cancel(&result1, &bar1);

// First request query:
[Synchronize bar0 code here.]
bool success0 = ptx::clusterlaunchcontrol_query_cancel_is_canceled(result0);
assert(!success0); // Observed failure; second cancellation was valid.
```

**解读：** 关键限制是“观察到失败之后”。第二段在查询第一次结果前已提交第二个请求，因此不触犯这条限制；它仍需正确管理各请求的结果存储和 barrier。两段中的 `[Synchronize bar0 code here.]` 都是占位说明，未提供完整可编译的同步代码。

> Retrieving the thread block index of a failed cancellation request is Undefined Behavior.

获取失败取消请求中的 thread block 索引，会产生未定义行为。

> Submitting a cancellation request from multiple threads is not recommended. It results in the cancellation of multiple thread blocks and requires careful handling, such as:

不建议由多个线程提交取消请求，因为这样会取消多个 thread block，且需要谨慎处理以下问题：

> - Each submitting thread must provide a unique `__shared__` result pointer to avoid data races.
> - If the same barrier is used for synchronization, the arrival and transaction counts must be adjusted accordingly.

- 每个提交请求的线程必须提供独立的 `__shared__` 结果指针，以避免数据竞争。
- 如果使用同一个 barrier 进行同步，必须相应调整 arrival count 和 transaction count。

**解读：** 推荐采用单请求循环：提交、等待、查询；成功才读取索引并继续，失败就结束循环。并发提交多个请求会增加结果缓冲和同步计数的管理复杂度。

### 4.13.2. Example: Vector-Scalar Multiplication（示例：向量与标量相乘）

> In the following subsections, we demonstrate work stealing through cluster launch control with a vector-scalar multiplication kernel. We show two variants of the same problem: one using thread blocks and one using thread block clusters.

接下来的小节通过一个向量与标量相乘的 kernel 展示如何使用 Cluster Launch Control 实现 work stealing。针对同一个问题，分别给出使用 thread block 和使用 thread block cluster 的两种变体。

#### 4.13.2.1. Use-case: Thread Blocks（使用场景：Thread Block）

> The three kernels below demonstrate the Fixed Work per Thread Block, Fixed Number of Thread Blocks, and Cluster Launch Control approaches for vector-scalar multiplication.

下面三个 kernel 分别展示向量与标量相乘的三种实现方式：固定每个 thread block 的工作量、固定 thread block 数量，以及 Cluster Launch Control。

**Fixed Work per Thread Block:（固定每个 thread block 的工作量）**

```cpp
__global__
void kernel_fixed_work (float* data, int n)
{
    // Prologue:
    float alpha = compute_scalar();

    // Computation:
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)
        data[i] *= alpha;
}

// Launch: kernel_fixed_work<<<(n + 1023) / 1024, 1024>>>(data, n);
```

**Fixed Number of Thread Blocks:（固定 thread block 数量）**

```cpp
__global__
void kernel_fixed_blocks (float* data, int n)
{
    // Prologue:
    float alpha = compute_scalar();

    // Computation:
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    while (i < n) {
        data[i] *= alpha;
        i += gridDim.x * blockDim.x;
    }
}

// Launch: kernel_fixed_blocks<<<SM_COUNT, 1024>>>(data, n);
```

**解读：** 前两个 kernel 分别把数据分配给随 `n` 增长的 grid，以及固定大小的 grid。`SM_COUNT` 的启动配置只是示例；合适的 block 数量还与 occupancy 和每个 block 的资源占用有关。`compute_scalar()` 在代码中由各线程执行，并不是每个 block 只调用一次。

**Cluster Launch Control:（Cluster Launch Control）**

```cpp
#include <cooperative_groups.h>
#include <cuda/ptx>

namespace cg = cooperative_groups;
namespace ptx = cuda::ptx;

__global__
void kernel_cluster_launch_control (float* data, int n)
{
    // Cluster launch control initialization:
    __shared__ uint4 result;
    __shared__ uint64_t bar;
    int phase = 0;

    if (cg::thread_block::thread_rank() == 0)
        ptx::mbarrier_init(&bar, 1);

    // Prologue:
    float alpha = compute_scalar(); // Device function not shown in this code snippet.

    // Work-stealing loop:
    int bx = blockIdx.x; // Assuming 1D x-axis thread blocks.

    while (true) {
        // Protect result from overwrite in the next iteration,
        // (also ensure barrier initialization at 1st iteration):
        __syncthreads();

        // Cancellation request:
        if (cg::thread_block::thread_rank() == 0) {
            // Acquire write of result in the async proxy:
            ptx::fence_proxy_async_generic_sync_restrict(ptx::sem_acquire, ptx::space_cluster, ptx::scope_cluster);

            cg::invoke_one(cg::coalesced_threads(), [&](){ptx::clusterlaunchcontrol_try_cancel(&result, &bar);});
            ptx::mbarrier_arrive_expect_tx(ptx::sem_relaxed, ptx::scope_cta, ptx::space_shared, &bar, sizeof(uint4));
        }

        // Computation:
        int i = bx * blockDim.x + threadIdx.x;
        if (i < n)
            data[i] *= alpha;

        // Cancellation request synchronization:
        while (!ptx::mbarrier_try_wait_parity(ptx::sem_acquire, ptx::scope_cta, &bar, phase))
        {}
        phase ^= 1;

        // Cancellation request decoding:
        bool success = ptx::clusterlaunchcontrol_query_cancel_is_canceled(result);
        if (!success)
            break;

        bx = ptx::clusterlaunchcontrol_query_cancel_get_first_ctaid_x<int>(result);

        // Release read of result to the async proxy:
        ptx::fence_proxy_async_generic_sync_restrict(ptx::sem_release, ptx::space_shared, ptx::scope_cluster);
    }
}

// Launch: kernel_cluster_launch_control<<<(n + 1023) / 1024, 1024>>>(data, n);
```

**解读：** 每轮先异步申请下一份工作，再计算当前 `bx` 对应的数据，以便请求与计算重叠。请求成功后用返回索引更新 `bx`，继续处理；失败则退出。内建 `blockIdx.x` 不会被修改，程序使用自己的 `bx` 代表接手的逻辑 block。`compute_scalar()` 放在循环外，能够被后续工作复用的前提是它不依赖被接手的 block 索引。

#### 4.13.2.2. Use-case: Thread Block Clusters（使用场景：Thread Block Cluster）

> In the case of a thread block clusters, the thread block cancellation steps are the same as in a non-cluster setting, with minor adjustments. As in the non-cluster case, submitting a cancellation request from multiple threads within a cluster is not recommended, as this will attempt to cancel multiple clusters.

对于 thread block cluster，取消步骤与不使用 cluster 时相同，仅需少量调整。与非 cluster 情况一样，不建议由 cluster 内多个线程提交取消请求，因为这会尝试取消多个 cluster。

> The cancellation is submitted by a single cluster thread.

由 cluster 内单个线程提交取消请求。

> The shared memory result of each cluster’s thread block will receive the same (encoded) value of the cancelled thread block index (i.e., the result value is multicasted). The result received by all thread blocks corresponds to the local block index {0, 0, 0} within a cluster. Therefore, thread blocks within the cluster need to add the local block index.

当前 cluster 中每个 thread block 的 shared memory 结果变量，都会收到相同的、经过编码的被取消 thread block 索引值，即结果会被 multicast（多播）。所有 thread block 收到的结果对应被取消 cluster 内局部 block 索引为 `{0, 0, 0}` 的 block。因此，当前 cluster 内的各 thread block 需要加上自己的局部 block 索引。

> Synchronization is performed by each cluster’s thread block using a local `__shared__` memory barrier. Barrier operations must be performed with the `ptx::scope_cluster` scope.

Cluster 中每个 thread block 都通过自己的局部 `__shared__` memory barrier 进行同步。Barrier 操作必须使用 `ptx::scope_cluster` scope。

> Cancelling in the cluster case requires all the thread blocks to exist. A user can guarantee that all thread blocks are running by using `cg::cluster_group::sync()` from sync API.

Cluster 情况下的取消操作要求所有 thread block 都已存在。用户可以使用 sync API 中的 `cg::cluster_group::sync()`，确保所有 thread block 都已经开始运行。

**解读：** Cluster 版把一次取消请求扩展到整个 cluster：单线程发起请求，各 block 接收相同结果并等待自己的 barrier。返回索引是被取消 cluster 的起始 block，各 block 加上自身局部偏移后才能分别处理正确的数据。

> The kernel below demonstrates the cluster launch control approach using thread block clusters.

下面的 kernel 展示了使用 thread block cluster 的 Cluster Launch Control 实现。

```cpp
#include <cooperative_groups.h>
#include <cuda/ptx>

namespace cg = cooperative_groups;
namespace ptx = cuda::ptx;

__global__ __cluster_dims__(2, 1, 1)
void kernel_cluster_launch_control (float* data, int n)
{
    // Cluster launch control initialization:
    __shared__ uint4 result;
    __shared__ uint64_t bar;
    int phase = 0;

    if (cg::thread_block::thread_rank() == 0) {
        ptx::mbarrier_init(&bar, 1);
        ptx::fence_mbarrier_init(ptx::sem_release, ptx::scope_cluster); // CGA-level fence.
    }

    // Prologue:
    float alpha = compute_scalar(); // Device function not shown in this code snippet.

    // Work-stealing loop:
    int bx = blockIdx.x; // Assuming 1D x-axis thread blocks.

    while (true) {
        // Protect result from overwrite in the next iteration,
        // (also ensure all thread blocks have started at 1st iteration):
        cg::cluster_group::sync();

        // Cancellation request by a single cluster thread:
        if (cg::cluster_group::thread_rank() == 0) {
            // Acquire write of result in the async proxy:
            ptx::fence_proxy_async_generic_sync_restrict(ptx::sem_acquire, ptx::space_cluster, ptx::scope_cluster);

            cg::invoke_one(cg::coalesced_threads(), [&](){ptx::clusterlaunchcontrol_try_cancel_multicast(&result, &bar);});
        }

        // Cancellation completion tracked by each thread block:
        if (cg::thread_block::thread_rank() == 0)
            ptx::mbarrier_arrive_expect_tx(ptx::sem_relaxed, ptx::scope_cluster, ptx::space_shared, &bar, sizeof(uint4));

        // Computation:
        int i = bx * blockDim.x + threadIdx.x;
        if (i < n)
            data[i] *= alpha;

        // Cancellation request synchronization:
        while (!ptx::mbarrier_try_wait_parity(ptx::sem_acquire, ptx::scope_cluster, &bar, phase))
        {}
        phase ^= 1;

        // Cancellation request decoding:
        bool success = ptx::clusterlaunchcontrol_query_cancel_is_canceled(result);
        if (!success)
            break;

        bx = ptx::clusterlaunchcontrol_query_cancel_get_first_ctaid_x<int>(result);
        bx += cg::cluster_group::block_index().x; // Add local offset.

        // Release read of result to the async proxy:
        ptx::fence_proxy_async_generic_sync_restrict(ptx::sem_release, ptx::space_shared, ptx::scope_cluster);
    }
}

// Launch: kernel_cluster_launch_control<<<(n + 1023) / 1024, 1024>>>(data, n);
```

**代码提示：** 示例声明了 `__cluster_dims__(2, 1, 1)`，因此 x 方向 grid 的 block 数需要能按两个一组划分。原启动式 `(n + 1023) / 1024` 对任意 `n` 不一定满足这一条件；使用时应将所得 block 数向上补齐为 2 的倍数，保留 `i < n` 边界判断。`compute_scalar()` 未在片段中提供定义；本节代码保持原样，仅作静态检查，未编译或运行。 Cluster 与 grid 维度约束参见[官方启动说明](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-host-programming.html#launching-with-clusters-using-cudalaunchkernelex)。
