## 4.11. Pipelines（流水线）

来源：[CUDA Programming Guide — Pipelines](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/pipelines.html)。按用户提供文本整理。

> Pipelines, introduced in Advanced Synchronization Primitives, are a mechanism for staging work and coordinating multi-buffer producer–consumer patterns, commonly used to overlap compute with asynchronous data copies.

Pipeline 在 Advanced Synchronization Primitives 中已有介绍，它是一种将工作组织为多个 stage、协调多缓冲 producer–consumer 模式的机制，常用于让计算与异步数据拷贝重叠执行。

> This section provides details on how to use pipelines mainly via the `cuda::pipeline` API (with pointers to primitives where applicable).

本节主要通过 `cuda::pipeline` API 详细介绍 pipeline 的使用方法，并在适当位置指向对应的底层 primitive。

### 4.11.1. Initialization（初始化）

> A `cuda::pipeline` can be created at different thread scopes. For a scope other than `cuda::thread_scope_thread`, a `cuda::pipeline_shared_state<scope, count>` object is required to coordinate the participating threads. This state encapsulates the finite resources that allow a pipeline to process up to count concurrent stages.

可以在不同的 thread scope 下创建 `cuda::pipeline`。当 scope 不是 `cuda::thread_scope_thread` 时，需要一个 `cuda::pipeline_shared_state<scope, count>` 对象来协调参与线程。这个共享状态封装了有限的资源，使 pipeline 最多可以同时处理 `count` 个 stage。

**解读：** `scope` 决定哪些线程参与协调，`count` 决定共享 pipeline 可同时保留多少个 stage。两者分别描述参与范围和流水线容量；实际数据 buffer 仍需由程序另行分配。

```cpp
// Create a pipeline at thread scope
constexpr auto scope = cuda::thread_scope_thread;
cuda::pipeline<scope> pipeline = cuda::make_pipeline();
```

```cpp
// Create a pipeline at block scope
constexpr auto scope = cuda::thread_scope_block;
constexpr auto stages_count = 2;
__shared__ cuda::pipeline_shared_state<scope, stages_count> shared_state;
auto pipeline = cuda::make_pipeline(group, &shared_state);
```

**解读：** 上面两个片段分别展示 thread scope 和 block scope 的创建方式，应作为独立示例阅读。Block-scope 片段中的 `group` 表示参与创建的线程组。

> Pipelines can be either unified or partitioned. In a unified pipeline, all the participating threads are both producers and consumers. In a partitioned pipeline, each participating thread is either a producer or a consumer and its role cannot change during the lifetime of the pipeline object. A thread-local pipeline cannot be partitioned. To create a partitioned pipeline, we need to provide either the number of producers or the role of the thread to `cuda::make_pipeline()`.

Pipeline 可以是 unified（统一参与）或 partitioned（角色分区）形式。在 unified pipeline 中，所有参与线程同时担任 producer 和 consumer。在 partitioned pipeline 中，每个参与线程只担任 producer 或 consumer 之一，并且在该 pipeline 对象的生命周期内不能改变角色。Thread-local pipeline 不能进行这种角色分区。要创建 partitioned pipeline，需要向 `cuda::make_pipeline()` 提供 producer 的数量，或当前线程的角色。

```cpp
// Create a partitioned pipeline at block scope where only thread 0 is a producer
constexpr auto scope = cuda::thread_scope_block;
constexpr auto stages_count = 2;
__shared__ cuda::pipeline_shared_state<scope, stages_count> shared_state;
auto thread_role = (group.thread_rank() == 0) ? cuda::pipeline_role::producer : cuda::pipeline_role::consumer;
auto pipeline = cuda::make_pipeline(group, &shared_state, thread_role);
```

> To support partitioning, a shared `cuda::pipeline` incurs additional overheads, including using a set of shared memory barriers per stage for synchronization. These are used even when the pipeline is unified and could use `__syncthreads()` instead. Thus, it is preferable to use thread-local pipelines which avoid these overheads when possible.

为了支持角色分区，共享的 `cuda::pipeline` 会产生额外开销，包括为每个 stage 使用一组 shared memory barrier 进行同步。即使 pipeline 是 unified 形式、原本可以改用 `__syncthreads()`，这些 barrier 仍然会被使用。因此，在可行时，优先使用 thread-local pipeline 可以避免这些额外开销。

**解读：** Unified 与 partitioned 描述线程角色；thread scope 与 block scope 描述协调范围。Thread-local pipeline 适合各线程跟踪自己的异步操作；如果消费者要使用其他线程复制的数据，仍需按访问关系安排线程间同步。

### 4.11.2. Submitting Work（提交工作）

> Committing work to a pipeline stage involves:

向 pipeline 的一个 stage 提交工作，需要执行以下步骤：

> - Collectively acquiring the pipeline head from a set of producer threads using `pipeline.producer_acquire()`.
> - Submitting asynchronous operations, e.g., memcpy_async, to the pipeline head.
> - Collectively committing (advancing) the pipeline head using `pipeline.producer_commit()`.

- 一组 producer 线程通过 `pipeline.producer_acquire()` 集体获取 pipeline 的 head。
- 向 pipeline head 提交异步操作，例如 `memcpy_async`。
- 通过 `pipeline.producer_commit()` 集体提交当前 head，并将 head 向前推进。

> If all resources are in use, `pipeline.producer_acquire()` blocks producer threads until the resources of the next pipeline stage are released by consumer threads.

如果所有资源都已被使用，`pipeline.producer_acquire()` 会阻塞 producer 线程，直到 consumer 线程释放下一个 pipeline stage 所需的资源。

**解读：** Acquire 获取可复用 stage，commit 提交该 stage 内积累的操作。容量用尽时 producer 等待 consumer 释放资源，这种反压防止 producer 抢先复用尚未消费完的缓冲区。程序也必须正确维护 stage 与实际 buffer 的对应关系。

### 4.11.3. Consuming Work（消费工作）

> Consuming work from a previously committed stage involves:

消费先前已经提交的 stage，需要执行以下步骤：

> - Collectively waiting for the stage to complete, e.g., using `pipeline.consumer_wait()` to wait on the tail (oldest) stage, from a set of consumer threads.
> - Collectively releasing the stage using `pipeline.consumer_release()`.

- 一组 consumer 线程集体等待该 stage 完成，例如使用 `pipeline.consumer_wait()` 等待 tail，即最旧的 stage。
- 通过 `pipeline.consumer_release()` 集体释放该 stage。

**解读：** Wait 确认该 stage 的异步操作完成，release 归还 stage 资源。若数据 buffer 会循环复用，应在数据使用结束后再释放，防止下一轮 producer 覆盖 consumer 仍在读取的数据。

> With `cuda::pipeline<cuda:thread_scope_thread>` one can also use the `cuda::pipeline_consumer_wait_prior<N>()` friend function to wait for all except the last N stages to complete, similar to `__pipeline_wait_prior(N)` in the primitives API.

对于 `cuda::pipeline<cuda:thread_scope_thread>`，还可以使用友元函数 `cuda::pipeline_consumer_wait_prior<N>()`，等待除最近 `N` 个 stage 之外的所有 stage 完成；它与 primitives API 中的 `__pipeline_wait_prior(N)` 类似。

**原文笔误：** `cuda::pipeline<cuda:thread_scope_thread>` 中的 `cuda:` 少了一个冒号；正确类型写法为 `cuda::pipeline<cuda::thread_scope_thread>`。上方保留原文，便于对照。

### 4.11.4. Warp Entanglement（Warp 内序列交织）

> The pipeline mechanism is shared among CUDA threads in the same warp. This sharing causes sequences of submitted operations to be entangled within a warp, which can impact performance under certain circumstances.

同一个 warp 中的 CUDA 线程共享 pipeline 机制。这种共享会使各线程提交的操作序列在 warp 内发生交织，在某些情况下影响性能。

> Commit. The commit operation is coalesced such that the pipeline’s sequence is incremented once for all converged threads that invoke the commit operation and their submitted operations are batched together. If the warp is fully converged, the sequence is incremented by one and all submitted operations will be batched in the same stage of the pipeline; if the warp is fully diverged, the sequence is incremented by 32 and all submitted operations will be spread to different stages.

**Commit。** Commit 操作会被合并：对于收敛执行该操作的所有线程，pipeline 序列只递增一次，它们提交的操作也会被归入同一批次。如果整个 warp 完全收敛，序列递增 1，所有提交的操作都会归入 pipeline 的同一个 stage；如果 warp 完全分歧，序列递增 32，提交的操作则会分散到不同 stage。

**解读：** 每个线程拥有自己的 C++ pipeline 对象，并不意味着底层批次提交序列完全独立。这里的 warp entanglement 解释了为什么线程分歧会让逻辑上的一次提交对应实际序列中的更多批次。

> Let PB be the warp-shared pipeline’s actual sequence of operations.

设 `PB` 为 warp 共享 pipeline 中实际的操作序列。

> `PB = {BP0, BP1, BP2, …, BPL}`

实际序列为 `PB = {BP0, BP1, BP2, …, BPL}`。

> Let TB be a thread’s perceived sequence of operations, as if the sequence were only incremented by this thread’s invocation of the commit operation.

设 `TB` 为某个线程感知到的操作序列，仿佛序列只因该线程自己调用 commit 而递增。

> `TB = {BT0, BT1, BT2, …, BTL}`

线程感知的序列为 `TB = {BT0, BT1, BT2, …, BTL}`。

> The `pipeline::producer_commit()` return value is from the thread’s perceived batch sequence.

`pipeline::producer_commit()` 的返回值来自当前线程感知的批次序列。

> An index in a thread’s perceived sequence always aligns to an equal or larger index in the actual warp-shared sequence. The sequences are equal only when all commit operations are invoked from fully converged threads.

线程感知序列中的一个索引，总是对应实际 warp 共享序列中一个相等或更大的索引。只有当所有 commit 都由完全收敛的线程调用时，这两个序列才相同。

> `BTn ≡ BPm where n <= m`

对应关系为 `BTn ≡ BPm`，其中 `n <= m`。

> For example, when a warp is fully diverged:

例如，当一个 warp 完全分歧时：

> The warp-shared pipeline’s actual sequence would be: PB = {0, 1, 2, 3, ..., 31} (PL=31).

Warp 共享 pipeline 的实际序列为 `PB = {0, 1, 2, 3, ..., 31}`，此时 `PL = 31`。

> The perceived sequence for each thread of this warp would be:

该 warp 中每个线程感知到的序列分别为：

> - Thread 0: TB = {0} (TL=0)
> - Thread 1: TB = {0} (TL=0)
> - …
> - Thread 31: TB = {0} (TL=0)

- 线程 0：`TB = {0}`，`TL = 0`。
- 线程 1：`TB = {0}`，`TL = 0`。
- ……
- 线程 31：`TB = {0}`，`TL = 0`。

> Wait. A CUDA thread invokes `pipeline::consumer_wait()` or `pipeline_consumer_wait_prior<N>()` to wait for batches in the perceived sequence TB to complete. Note that `pipeline::consumer_wait()` is equivalent to `pipeline_consumer_wait_prior<N>()`, where N = PL.

**Wait。** CUDA 线程调用 `pipeline::consumer_wait()` 或 `pipeline_consumer_wait_prior<N>()`，等待感知序列 `TB` 中的批次完成。原文指出，`pipeline::consumer_wait()` 等价于 `pipeline_consumer_wait_prior<N>()`，其中 `N = PL`。

> The wait prior variants wait for batches in the actual sequence at least up to and including PL-N. Since TL <= PL, waiting for batch up to and including PL-N includes waiting for batch TL-N. Thus, when TL < PL, the thread will unintentionally wait for additional, more recent batches. In the extreme fully-diverged warp example above, each thread could wait for all 32 batches.

Wait-prior 变体至少等待实际序列中直到 `PL-N`（含该批次）的所有批次。由于 `TL <= PL`，等待到 `PL-N` 也就包含了等待到 `TL-N`。因此，当 `TL < PL` 时，线程会无意中额外等待一些更新的批次。在上述 warp 完全分歧的极端例子中，每个线程可能等待全部 32 个批次。

**解读：** Over-wait 的根源是线程感知序列与 warp 实际序列的索引不一致。原文的 `N = PL` 等价表述应结合本段序列上下文阅读，不能直接当作任意时刻替换 `consumer_wait()` 的通用规则。编程时以“等待当前待消费 stage 完成”的接口语义为准；wait-prior 的 `N` 表示可保留的最近批次数。[CCCL pipeline API](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/synchronization_primitives/pipeline.html)

**Note（注意）**

> It is recommended that commit invocations are by converged threads to not over-wait, by keeping threads’ perceived sequence of batches aligned with the actual sequence.

建议由收敛的线程调用 commit，使线程感知的批次序列与实际序列保持一致，从而避免额外等待。

> When code preceding these operations diverges threads, then the warp should be re-converged, via `__syncwarp` before invoking commit operations.

如果这些操作之前的代码使线程发生分歧，应在调用 commit 之前通过 `__syncwarp` 让 warp 重新收敛。

**解读：** 应让参与同一轮 commit 的线程在分歧路径结束后收敛执行。使用 `__syncwarp` 时还需保证掩码所指定的线程实际参与同步；不能让已退出的线程继续被当作必到达的参与者。

### 4.11.5. Early Exit（提前退出）

> When a thread that is participating in a pipeline must exit early, that thread must explicitly drop out of participation before exiting using `cuda::pipeline::quit()`. The remaining participating threads can proceed normally with subsequent operations.

参与 pipeline 的线程如果必须提前退出，就必须在退出前显式调用 `cuda::pipeline::quit()`，退出对该 pipeline 的参与。其余参与线程随后可以正常继续执行后续操作。

**解读：** 提前返回会改变实际参与线程数。`quit()` 用于让 pipeline 知道该线程退出；它不能替代数据消费、buffer 生命周期管理或其他必要的同步。

### 4.11.6. Tracking Asynchronous Memory Operations（跟踪异步内存操作）

> The following example demonstrates how to collectively copy data from global to shared memory with asynchronous memory copies using a pipeline to keep track of the copy operations. Each thread uses its own pipeline to independently submit memory copies and then wait for them to complete and consume the data. For more details on asynchronous data copies, see Section 3.2.5.

下面的示例展示如何使用异步内存拷贝，将数据从 global memory 协同拷贝到 shared memory，并用 pipeline 跟踪拷贝操作。每个线程使用自己的 pipeline 独立提交内存拷贝，随后等待这些拷贝完成并消费数据。关于异步数据拷贝的更多细节，参见第 3.2.5 节。

**CUDA C++ `cuda::pipeline`**

CUDA C++ `cuda::pipeline` 示例

```cpp
#include <cuda/pipeline>

__global__ void example_kernel(const float *in)
{
    constexpr int block_size = 128;
    __shared__ __align__(sizeof(float)) float buffer[4 * block_size];

    // Create a unified pipeline per thread
    cuda::pipeline<cuda::thread_scope_thread> pipeline = cuda::make_pipeline();

    // First stage of memory copies
    pipeline.producer_acquire();
    // Every thread fetches one element of the first block
    cuda::memcpy_async(buffer, in, sizeof(float), pipeline);
    pipeline.producer_commit();

    // Second stage of memory copies
    pipeline.producer_acquire();
    // Every thread fetches one element of the second and third block
    cuda::memcpy_async(buffer + block_size, in + block_size, sizeof(float), pipeline);
    cuda::memcpy_async(buffer + 2 * block_size, in + 2 * block_size, sizeof(float), pipeline);
    pipeline.producer_commit();

    // Third stage of memory copies
    pipeline.producer_acquire();
    // Every thread fetches one element of the last block
    cuda::memcpy_async(buffer + 3 * block_size, in + 3 * block_size, sizeof(float), pipeline);
    pipeline.producer_commit();

    // Wait for the oldest stage (waits for first stage)
    pipeline.consumer_wait();
    pipeline.consumer_release();

    // __syncthreads();
    // Use data from the first stage

    // Wait for the oldest stage (waits for second stage)
    pipeline.consumer_wait();
    pipeline.consumer_release();

    // __syncthreads();
    // Use data from the second stage

    // Wait for the oldest stage (waits for third stage)
    pipeline.consumer_wait();
    pipeline.consumer_release();

    // __syncthreads();
    // Use data from the third stage
}
```

**代码解读：** 示例提交了三个 stage，其中第二个 stage 包含两次 `memcpy_async`，说明 stage 与拷贝操作并非一一对应。代码没有使用线程编号偏移 `buffer` 和 `in`，因此按原样执行时，各线程会对相同地址发起拷贝，无法实现注释所描述的“每线程读取一个元素”；应按实际数据布局给源、目标地址添加线程偏移。每个线程的等待也不能代替消费者所需的线程间同步。示例将 release 放在使用数据之前，但后面没有再次提交拷贝来复用这些 buffer；扩展为循环缓冲时，应先完成消费，再 release。这里保留原代码。

### 4.11.7. Producer-Consumer Pattern using Pipelines（使用 Pipeline 实现 Producer–Consumer 模式）

> In Section 4.10.7, we showed how a thread block can be spatially partitioned to implement a producer-consumer pattern using asynchronous barriers. With `cuda::pipeline`, this can be simplified using a single partitioned pipeline with one stage per data buffer instead of two asynchronous barriers per buffer.

第 4.10.7 节展示了如何在 thread block 内按线程角色进行空间划分，借助异步 barrier 实现 producer–consumer 模式。使用 `cuda::pipeline` 可以简化这一过程：为每个数据 buffer 分配一个 stage，使用单个 partitioned pipeline 协调工作，从而替代每个 buffer 所需的两个异步 barrier。

**CUDA C++ `cuda::pipeline`**

CUDA C++ `cuda::pipeline` 示例

```cpp
#include <cuda/pipeline>
#include <cooperative_groups.h>

#pragma nv_diag_suppress static_var_with_dynamic_init

using pipeline = cuda::pipeline<cuda::thread_scope_block>;

__device__ void produce(pipeline &pipe, int num_stages, int stage, int num_batches, int batch, float *buffer, int buffer_len, float *in, int N)
{
  if (batch < num_batches)
  {
    pipe.producer_acquire();
    /* copy data from in(batch) to buffer(stage) using asynchronous memory copies */
    pipe.producer_commit();
  }
}

__device__ void consume(pipeline &pipe, int num_stages, int stage, int num_batches, int batch, float *buffer, int buffer_len, float *out, int N)
{
  pipe.consumer_wait();
  /* consume buffer(stage) and update out(batch) */
  pipe.consumer_release();
}

__global__ void producer_consumer_pattern(float *in, float *out, int N, int buffer_len)
{
  auto block = cooperative_groups::this_thread_block();

  /* Shared memory buffer declared below is of size 2 * buffer_len
     so that we can alternatively work between two buffers.
     buffer_0 = buffer and buffer_1 = buffer + buffer_len */
  __shared__ extern float buffer[];

  const int num_batches = N / buffer_len;

  // Create a partitioned pipeline with 2 stages where half the threads are producers and the other half are consumers.
  constexpr auto scope = cuda::thread_scope_block;
  constexpr int num_stages = 2;
  cuda::std::size_t producer_count = block.size() / 2;
  __shared__ cuda::pipeline_shared_state<scope, num_stages> shared_state;
  pipeline pipe = cuda::make_pipeline(block, &shared_state, producer_count);

  // Fill the pipeline
  if (block.thread_rank() < producer_count)
  {
    for (int s = 0; s < num_stages; ++s)
    {
      produce(pipe, num_stages, s, num_batches, s, buffer, buffer_len, in, N);
    }
  }

  // Process the batches
  int stage = 0;
  for (size_t b = 0; b < num_batches; ++b)
  {
    if (block.thread_rank() < producer_count)
    {
      // Prefetch the next batch
      produce(pipe, num_stages, stage, num_batches, b + num_stages, buffer, buffer_len, in, N);
    }
    else
    {
      // Consume the oldest batch
      consume(pipe, num_stages, stage, num_batches, b, buffer, buffer_len, out, N);
    }
    stage = (stage + 1) % num_stages;
  }
}
```

> In this example, we use half of the threads in the thread block as producers and the other half as consumers. As a first step, we need to create a `cuda::pipeline` object. Since we want some threads to be producers and some to be consumers, we need to use a partitioned pipeline with `cuda::thread_scope_block`. Partitioned pipelines require a `cuda::pipeline_shared_state` to coordinate the participating threads. We initialize the state for a 2-stage pipeline in thread-block scope and then call `cuda::make_pipeline()`. Next, producer threads fill the pipeline by submitting asynchronous copies from in to buffer. At this point all data copies are in-flight. Finally, in the main loop, we go over all of the batches of data and depending on whether a thread is a producer or consumer, we either submit another asynchronous copy for a future batch or consume the current batch.

在这个例子中，thread block 内一半线程充当 producer，另一半充当 consumer。首先需要创建一个 `cuda::pipeline` 对象。由于需要让不同线程分别担任 producer 和 consumer，应使用 scope 为 `cuda::thread_scope_block` 的 partitioned pipeline。Partitioned pipeline 需要 `cuda::pipeline_shared_state` 来协调参与线程。我们在线程块作用域初始化一个包含两个 stage 的 pipeline 状态，随后调用 `cuda::make_pipeline()`。接着，producer 线程提交从 `in` 到 `buffer` 的异步拷贝，填充 pipeline；此时这些数据拷贝都已在进行中。最后，在主循环中遍历所有数据批次：根据当前线程的角色，或者为未来批次提交另一次异步拷贝，或者消费当前批次。

**解读：** 两个 stage 分别对应两个 buffer。Producer 先预取前两个批次，随后尝试向当前 stage 写入第 `b + 2` 批；如果该 stage 尚未释放，就在 acquire 处等待。Consumer 等待并处理第 `b` 批后释放 stage，双方再通过取模切换 buffer。`produce` 与 `consume` 中的拷贝、计算仍是注释占位，使用时需要补齐；kernel launch 还需分配 `2 * buffer_len * sizeof(float)` 字节动态 shared memory。`N / buffer_len` 使用整数除法，不能自动处理不足一个 buffer 的末尾数据。本节示例仅作原文整理和静态检查，未编译或运行。
