## 4.7. Locality Domains（局部性域）

来源：[CUDA Programming Guide — Locality Domains](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/locality-domains.html)。

> A locality domain is a portion of a GPU that contains streaming multiprocessors (SMs) and device memory. An application can allocate device memory in a locality domain and create a green context with SM resources in the same locality domain. Co-locating computation near the memory it accesses can improve performance on devices that have more than one locality domain. The compute localization API is described in Localizing Compute Resources and memory localization in Allocating Localized Device Memory.

Locality domain（局部性域）是 GPU 中包含 streaming multiprocessor（SM）与 device memory 的一部分。应用可以在某个 locality domain 中分配 device memory，并创建一个 SM 资源也位于同一 domain 的 green context。对于拥有多个 locality domain 的设备，让计算靠近它访问的内存，可能提高性能。计算资源的局部化 API 见 Localizing Compute Resources，内存局部化见 Allocating Localized Device Memory。

> CUDA identifies the locality domains of a device by zero-based locality domain IDs. A locality domain ID is meaningful only together with its device ID. The same ID is used when localizing SM resources and memory, allowing an application to request matching placement for both.

CUDA 用从零开始的 locality domain ID 标识设备中的各 domain。只有与 device ID 一起使用，locality domain ID 才具有确定含义。局部化 SM 资源与局部化内存时使用相同的 ID，因此应用可以要求两者匹配放置。

**解读：** locality domain ID 不是跨设备的全局编号。记录或复用放置配置时，应同时保存 device ID；性能收益取决于计算和所访问内存能否实际落在同一 domain。

### 4.7.1. Discovering Locality Domains（发现 Locality Domain）

> Use cudaDeviceGetAttribute with the following cudaDeviceAttr values:

使用 cudaDeviceGetAttribute 查询以下 cudaDeviceAttr 值：

> cudaDevAttrLocalityDomainCount returns the number of locality domains on the device.

cudaDevAttrLocalityDomainCount 返回设备上的 locality domain 数量。

> cudaDevAttrLocalityDomainMultiprocessorCount returns the number of SMs in each locality domain.

cudaDevAttrLocalityDomainMultiprocessorCount 返回每个 locality domain 中的 SM 数量。

> Applications should query these attributes rather than assume a particular topology. The number of locality domains available on a device is affected by the system configuration. The same device type may be presented with a different number of locality domains under different scenarios (Section 4.7.5.3). All devices, including those with a single locality domain available, can use the locality domain APIs. On devices with a single locality domain, these APIs are the same as targeting the full device. Use the device attributes to programmatically query the locality domain properties of the device:

应用应查询这些属性，而不要假定固定拓扑。设备可用的 locality domain 数量受系统配置影响；同一种设备在不同场景下可能呈现不同数量的 domain，见 4.7.5.3 节。所有设备都可以使用 locality domain API，包括只有一个 domain 的设备；此时它们的效果与选择整个设备相同。以下代码通过 device attribute 查询设备的 locality domain 属性：

```cpp
int localityDomainCount = 0;
int smsPerLocalityDomain = 0;

cudaDeviceGetAttribute(&localityDomainCount, cudaDevAttrLocalityDomainCount, device);
cudaDeviceGetAttribute(&smsPerLocalityDomain, cudaDevAttrLocalityDomainMultiprocessorCount, device);
```

**解读：** 先查询实际设备属性，再决定是否做局部化；只有一个 locality domain 时，局部性 API 的作用范围就是整个设备。示例省略了返回值检查，实际程序应检查两次查询是否成功。

### 4.7.2. Localizing Compute Resources（局部化计算资源）

> To localize SM resources to a specific locality domain, use the CUDA green context API. SMs placement is expressed through the green context resource APIs described in Section 4.6. The main steps to construct a localized SM partition are:

要把 SM 资源局部化到指定 locality domain，应使用 CUDA green context API。SM 的放置通过 4.6 节介绍的 green context resource API 表达。构造局部化 SM partition 的主要步骤如下：

> Obtain the device’s cudaDevResourceTypeSm resource with cudaDeviceGetDevResource.

使用 cudaDeviceGetDevResource 获取设备的 cudaDevResourceTypeSm 资源。

> Describe a localized SM group with cudaDevSmResourceGroupParams (details).

使用 cudaDevSmResourceGroupParams 描述局部化的 SM group（详见相关说明）。

> Pass the group parameters to cudaDevSmResourceSplit.

将 group 参数传给 cudaDevSmResourceSplit。

> Generate a resource descriptor with cudaDevResourceGenerateDesc, create a green context with cudaGreenCtxCreate, and finally create a stream via cudaExecutionCtxStreamCreate.

使用 cudaDevResourceGenerateDesc 生成资源描述符，通过 cudaGreenCtxCreate 创建 green context，再用 cudaExecutionCtxStreamCreate 创建 stream。

> Launch kernels on the stream.

在该 stream 上启动 kernel。

> Typical green context creation is described in Section 4.6.2. The additions necessary to localize SM resources are illustrated below:

普通 green context 的创建流程见 4.6.2 节。以下示例展示局部化 SM 资源所需的额外设置：

> To describe a localized SM group, set cudaDevSmResourceGroupLocalityDomainId in flags and set the ID in localityDomainId. Valid IDs are between 0 and cudaDevAttrLocalityDomainCount - 1.

要描述局部化 SM group，应在 flags 中设置 cudaDevSmResourceGroupLocalityDomainId，并将目标 ID 写入 localityDomainId。有效 ID 范围为 0 到 cudaDevAttrLocalityDomainCount - 1。

```cpp
cudaDevResource smResource;
cudaDeviceGetDevResource(device, &smResource, cudaDevResourceTypeSm);

{
    cudaDevSmResourceGroupParams params = {};
    // all fields in params must be zero-initialized
    params.flags = cudaDevSmResourceGroupLocalityDomainId;
    params.localityDomainId = localityDomainId;

    cudaDevResource result;
    cudaDevSmResourceSplit(&result, 1, &smResource, nullptr, 0, &params);
}
```

**解读：** `cudaDevSmResourceGroupLocalityDomainId` 用于提出目标 domain 约束。示例的 `cudaDevSmResourceSplit` 把 `remainder` 传为 `nullptr`，未分配进 `result` 的 SM 没有在此处保存；后续若要使用剩余 SM，应接收并管理 remainder。

> Multiple constraints may be specified in params in combination with requesting a locality domain. For example:

除请求 locality domain 外，还可以在 params 中组合指定多个约束。例如：

> The smCount constraint may be 0 (discovery mode) or positive. In discovery mode the API returns the number of SMs in the locality domain in params.smCount. On a full, un-partitioned, device resource, this value is the same as cudaDevAttrLocalityDomainMultiprocessorCount. When smCount is positive, the API will allocate up to the cudaDevAttrLocalityDomainMultiprocessorCount value. Larger smCount requests will fail.

smCount 约束可以是 0（发现模式）或正数。在发现模式下，API 通过 params.smCount 返回该 locality domain 的 SM 数量。如果输入资源是完整、未经分区的 device resource，此数值等于 cudaDevAttrLocalityDomainMultiprocessorCount。若 smCount 为正，API 最多分配该属性值对应数量的 SM；请求更大数值会失败。

> When coscheduledSmCount is 0 the API does not restrict SMs by coscheduled capability and the maximum number of localized SMs are available. The cluster capability of the partition can be dynamically queried later with cudaOccupancyMaxPotentialClusterSize. When coscheduledSmCount is nonzero, the the API will select only localized SMs satifsying the requested coscheduledSmCount.

coscheduledSmCount 为 0 时，API 不根据协同调度能力限制 SM，可用的局部化 SM 数量达到最大值。之后可以通过 cudaOccupancyMaxPotentialClusterSize 动态查询该 partition 的 cluster 能力。coscheduledSmCount 非零时，API 只选择满足所请求协同调度 SM 数量的局部化 SM。

> By default, all SMs in the result must satisfy the locality domain constraint and any additional constraints specified. To relax this behavior, add cudaDevSmResourceGroupBackfill to params.flags. With backfill, the API fills the group from the requested locality domain first, then from SMs not attributed to a locality domain, and finally from other locality domains. The call fails with cudaErrorInvalidResourceConfiguration if no SM can be found in the requested locality domain.

默认情况下，result 中所有 SM 都必须满足指定的 locality domain 与其他附加约束。若要放宽这一要求，可以将 cudaDevSmResourceGroupBackfill 加入 params.flags。启用 backfill 后，API 先从请求的 locality domain 填充 group，再使用未归属任何 locality domain 的 SM，最后使用其他 locality domain 的 SM。如果在请求的 locality domain 中一个 SM 都找不到，则调用返回 cudaErrorInvalidResourceConfiguration。

**解读：** `backfill` 允许在目标 domain 资源不足时从其他位置补足 SM，因此所得资源可能不再严格局部化。需要严格匹配计算与内存位置时，应核对返回资源的 `flags` 和 `localityDomainId`。

> Any unused SMs not returned in the result are returned in the API’s remainder parameter.

未包含在 result 中的剩余 SM，通过该 API 的 remainder 参数返回。

> The result’s cudaDevResource.sm.flags and cudaDevResource.sm.localityDomainId report the resource placement. When combining SM resources in one descriptor, the resources must have matching constraints, including flags and localityDomainId values.

result 中的 cudaDevResource.sm.flags 与 cudaDevResource.sm.localityDomainId 会报告资源的放置情况。将多个 SM resource 合并到一个 descriptor 时，它们必须具有匹配的约束，包括 flags 和 localityDomainId 的取值。

> The following code queries the number of locality domains, and constructs one stream per locality domain.

下面的代码查询 locality domain 数量，并为每个 domain 创建一个 stream。

```cpp
std::vector<cudaExecutionContext_t> contexts(localityDomainCount);
std::vector<cudaStream_t> streams(localityDomainCount);

{
    std::vector<cudaDevSmResourceGroupParams> params(localityDomainCount);
    std::vector<cudaDevResource> result(localityDomainCount);

    for (int i = 0; i < localityDomainCount; i++) {
        params[i] = {};
        params[i].flags = cudaDevSmResourceGroupLocalityDomainId;
        params[i].localityDomainId = i;
    }

    // A single split produces non-overlapping resources for all domains.
    cudaDevSmResourceSplit(result.data(), localityDomainCount, &smResource, nullptr, 0, params.data());

    for (int i = 0; i < localityDomainCount; i++) {
        cudaDevResourceDesc_t desc;
        cudaDevResourceGenerateDesc(&desc, &result[i], 1);
        cudaGreenCtxCreate(&contexts[i], desc, device, 0);
        cudaExecutionCtxStreamCreate(&streams[i], contexts[i], cudaStreamDefault, 0);
    }
}
```

**解读：** 这段代码为每个 domain 建立一个 green context 和一个 stream；kernel 要提交到对应 stream 才会使用该 context 的 SM 资源。结束时按原文顺序先销毁 stream，再销毁 context。示例着重展示流程，未包含错误处理。

> Each stream in streams executes on SMs from the locality domain with the corresponding index. Destroy the streams with cudaStreamDestroy and then destroy their contexts with cudaExecutionCtxDestroy when they are no longer needed.

streams 中的每个 stream 都在与其索引对应的 locality domain 的 SM 上执行。使用结束后，先用 cudaStreamDestroy 销毁 stream，再用 cudaExecutionCtxDestroy 销毁其 context。

### 4.7.3. Allocating Localized Device Memory（分配局部化 Device Memory）

> CUDA represents a localized memory location with a cudaMemLocation whose type is cudaMemLocationTypeDeviceLocalityDomain. For this location type, initialize both members of cudaMemLocation.localized:

CUDA 使用 cudaMemLocation 表示局部化的内存位置，其 type 为 cudaMemLocationTypeDeviceLocalityDomain。使用这一位置类型时，需要初始化 cudaMemLocation.localized 的两个成员：

> deviceId identifies the GPU.

deviceId 标识 GPU。

> localityDomainId identifies a locality domain on that GPU.

localityDomainId 标识该 GPU 上的 locality domain。

> The runtime API uses this location with stream-ordered memory pools (Section 4.3). The driver API additionally uses the corresponding CUmemLocation with virtual memory management allocations (Section 4.17).

Runtime API 将这种 location 用于按 stream 顺序执行的 memory pool，见 4.3 节。Driver API 还将相应的 CUmemLocation 用于 VMM allocation，见 4.17 节。

> Allocations created through other mechanisms, for example cudaMalloc or unified memory, can not be localized. MPS (Multi-Process Service) in MLOPart mode can be used to transparently localize applications that rely on cudaMalloc.

通过其他机制创建的 allocation，例如 cudaMalloc 或 unified memory，不能显式指定 locality domain。使用 MLOPart 模式的 MPS（Multi-Process Service，多进程服务）可以透明地局部化依赖 cudaMalloc 的应用。

**解读：** 普通 `cudaMalloc` 和 managed memory 无法通过这里的 location 参数显式指定 domain。需要控制分配位置时，使用局部化 memory pool 或 VMM；MPS 的透明局部化依赖原文所述的 MLOPart 模式。

#### 4.7.3.1. Creating a Localized Memory Pool（创建局部化 Memory Pool）

> To create a localized memory pool, set the location in cudaMemPoolProps and call cudaMemPoolCreate:

要创建局部化 memory pool，需设置 cudaMemPoolProps 的 location，并调用 cudaMemPoolCreate：

```cpp
cudaMemPool_t pool {};
cudaMemPoolProps props {};

props.allocType = cudaMemAllocationTypePinned;
props.location.type = cudaMemLocationTypeDeviceLocalityDomain;
props.location.localized.deviceId = device;
props.location.localized.localityDomainId = localityDomainId;

cudaMemPoolCreate(&pool, &props);
```

**解读：** pool 的 `location` 同时包含 device ID 与 locality domain ID。后续须从这个 pool 分配，才能把该放置选择作用于 allocation；创建 pool 本身不会迁移已有内存。

> Allocate from this pool with cudaMallocFromPoolAsync and release the allocation with cudaFreeAsync. The location can also be passed to cudaMemGetDefaultMemPool, cudaMemGetMemPool, and cudaMemSetMemPool when selecting the default or current pinned-memory pool for that locality domain. For the general memory-pool programming model, see Memory Pools.

通过 cudaMallocFromPoolAsync 从该 pool 分配内存，并使用 cudaFreeAsync 释放。选择该 locality domain 的默认或当前 pinned-memory pool 时，也可以将该 location 传给 cudaMemGetDefaultMemPool、cudaMemGetMemPool 和 cudaMemSetMemPool。一般 memory pool 编程模型见 Memory Pools。

#### 4.7.3.2. Creating a Localized VMM Allocation（创建局部化 VMM Allocation）

> The driver API can place physical memory created by cuMemCreate in a locality domain. Set CUmemAllocationProp::location.type to CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN and initialize location.localized.deviceId and location.localized.localityDomainId. The resulting physical allocation is reserved, mapped, and granted access in the same way as other VMM allocations. Access control set via cuMemSetAccess operates at full device granularity, not individual locality domains. See the localized VMM allocation section for the complete allocation sequence and granularity requirements.

Driver API 可以把 cuMemCreate 创建的物理内存放置在某个 locality domain。应将 CUmemAllocationProp::location.type 设为 CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN，并初始化 location.localized.deviceId 和 location.localized.localityDomainId。后续仍按一般 VMM allocation 的流程预留虚拟地址、映射并授予访问权限。由 cuMemSetAccess 设置的权限以整个 device 为粒度，而不是以各 locality domain 为粒度。完整分配流程及粒度要求见 localized VMM allocation 一节。

> Managed memory can not be localized: Requesting cudaMemAllocationTypeManaged with cudaMemLocationTypeDeviceLocalityDomain will return CUDA_ERROR_NOT_SUPPORTED. Similarly, cudaMemPrefetchAsync and cudaMemAdvise do not accept a device locality domain as a location and will return CUDA_ERROR_NOT_SUPPORTED.

Managed memory 不能局部化：将 cudaMemAllocationTypeManaged 与 cudaMemLocationTypeDeviceLocalityDomain 组合使用，会返回原文所写的 CUDA_ERROR_NOT_SUPPORTED。同样，cudaMemPrefetchAsync 与 cudaMemAdvise 不接受 device locality domain 作为 location，原文称其返回 CUDA_ERROR_NOT_SUPPORTED。

**解读：** 这里原文同时讨论 Runtime API 与 Driver API，却统一写作 `CUDA_ERROR_NOT_SUPPORTED`。查验返回值时应以具体函数的返回类型和相应错误码枚举为准；英文原句保留不改。

> See Locality Domains and Unified Memory for the relationship between locality domains and Unified Memory.

关于 locality domain 与 Unified Memory 的关系，见 Locality Domains and Unified Memory。

### 4.7.4. Querying Memory Placement（查询内存放置位置）

> Use cudaMemPoolGetAttribute with cudaMemPoolAttrLocalityDomainId to query a pool. It returns the locality domain ID for a localized pool and -1 for a pool that is not localized.

使用 cudaMemPoolGetAttribute 配合 cudaMemPoolAttrLocalityDomainId 查询 pool；局部化 pool 返回 locality domain ID，未局部化 pool 返回 -1。

> Use cudaPointerGetAttributes to query an allocation through its pointer. The returned cudaPointerAttributes.localityDomainOrdinal field contains the allocation’s locality domain ordinal, or -1 when the allocation is not localized:

使用 cudaPointerGetAttributes 通过指针查询 allocation。返回的 cudaPointerAttributes.localityDomainOrdinal 字段包含该 allocation 的 locality domain ordinal；未局部化时为 -1：

```cpp
cudaPointerAttributes attributes {};
cudaPointerGetAttributes(&attributes, ptr);
int localityDomainId = attributes.localityDomainOrdinal;
```

**解读：** `-1` 表示该 pool 或 allocation 未被报告为局部化，并不表示指针不可访问。查询结果可用于检查计算资源与内存是否选用了同一 domain。

### 4.7.5. Programming Guidance（编程建议）

> To localize a workload, launch kernels using compute resources from the same locality domain as their memory allocations.

要局部化一个 workload，应使用与其内存 allocation 相同 locality domain 中的计算资源来启动 kernel。

> Localizing only compute or only memory resources typically does not improve performance.

通常仅局部化计算资源或仅局部化内存，不会改善性能。

> If a kernel must use memory from several locality domains, measure whether compute localization is beneficial.

如果 kernel 必须访问多个 locality domain 的内存，应通过测量判断局部化计算资源是否有益。

**解读：** 局部性优化要让 kernel 的主要内存访问与 SM 所在 domain 对齐。若输入跨多个 domain，收益取决于实际访问模式，应按工作负载测量，而不能仅依据资源放置推断速度。

#### 4.7.5.1. Localized Kernels With Fork/Join Pattern（使用 Fork/Join 模式的局部化 Kernel）

> The fork/join pattern uses events and stream waits to express a parallel region. The application creates one stream from each localized green context by using cudaExecutionCtxStreamCreate. A separate main stream coordinates those localized streams. Create one fork event for the main stream and one join event per localized stream with cudaEventCreateWithFlags; timing should be disabled when the events are used only for ordering.

Fork/join 模式通过 event 与 stream wait 表达并行区域。应用通过 cudaExecutionCtxStreamCreate，为每个局部化 green context 创建一个 stream；另有单独的主 stream 协调这些局部化 stream。用 cudaEventCreateWithFlags 为主 stream 创建一个 fork event，并为每个局部化 stream 创建一个 join event；如果 event 仅用于排序，应禁用 timing。

> To fork, record one event on the parent stream and make every localized stream wait for that event. Work previously submitted to the parent is therefore ordered before the localized work. Submit independent work to the localized streams, using memory from their corresponding locality domains.

Fork 时，在 parent stream 上记录一个 event，让每个局部化 stream 等待该 event。这样，先前提交到 parent stream 的工作就会排在局部化工作之前。随后可将相互独立的工作提交到各局部化 stream，并使用对应 domain 的内存。

> To join, record one event on each localized stream after its work and make the parent stream wait for all of those events. Work subsequently submitted to the parent is then ordered after the localized work.

Join 时，在每个局部化 stream 完成工作后记录其 event，再让 parent stream 等待全部 event。此后提交到 parent stream 的工作便排在所有局部化工作之后。

```cpp
produceInputs<<<grid, block, 0, parentStream>>>(...);
cudaEventRecord(forkEvent, parentStream);

// localizedStreams[i] belongs to the green context for locality domain i.
for (int i = 0; i < localityDomainCount; i++) {
    cudaStreamWaitEvent(localizedStreams[i], forkEvent);
    processPartition<<<grid, block, 0, localizedStreams[i]>>>(...);
    cudaEventRecord(joinEvents[i], localizedStreams[i]);
}

for (int i = 0; i < localityDomainCount; i++) {
    cudaStreamWaitEvent(parentStream, joinEvents[i]);
}
consumeResults<<<grid, block, 0, parentStream>>>(...);
```

**解读：** 依赖顺序是 parent 产出输入 → 各局部化 stream 等待 fork event → 并行执行 → 各自记录 join event → parent 等待所有分支。用于依赖的 event 关闭 timing；代码中的 `...` 和未展示的变量声明表明这是流程示例。

#### 4.7.5.2. CUDA Graphs（CUDA Graph）

> CUDA Graphs (Section 4.2) support localization through stream capture and manual graph construction. For some applications, CUDA graphs may offer improved performance over stream-based programming.

CUDA Graph（见 4.2 节）可以通过 stream capture 或手动构建 graph 支持局部化。对某些应用而言，CUDA Graph 可能比基于 stream 的编程获得更好性能。

##### 4.7.5.2.1. Stream Capture（Stream Capture）

> A fork/join pattern can be captured to a CUDA graph. Begin capture on the parent stream, record the fork event, and wait on the fork event in each localized stream. Waiting on the fork event enrolls the localized streams in the same capture graph as the parent stream. Operations submitted to the localized streams become parallel graph branches. After launching all work on the localized streams, record the join event and wait on all the join events in the parent stream. These waits reconnect all branches to the parent stream. Every participating stream must be joined back to the origin stream before cudaStreamEndCapture is called.

Fork/join 模式可以 capture 成 CUDA Graph。在 parent stream 上开始 capture 并记录 fork event，让各局部化 stream 等待它；等待 fork event 会将这些局部化 stream 纳入与 parent stream 相同的 capture graph。提交给局部化 stream 的操作成为并行的 graph branch。所有局部化工作提交后，记录 join event，并让 parent stream 等待所有 join event。这些等待把各 branch 重新接回 parent stream。在调用 cudaStreamEndCapture 前，所有参与的 stream 都必须 join 回起始 stream。

```cpp
cudaStreamBeginCapture(parentStream, cudaStreamCaptureModeGlobal);

// Record forkEvent, submit work to each localized stream, record the
// joinEvents, and make parentStream wait as in the fork/join example above.

cudaGraph_t graph;
cudaStreamEndCapture(parentStream, &graph);
```

**解读：** stream capture 要在 `cudaStreamEndCapture` 前让所有从 parent stream 分叉的局部化 stream 经 join event 回到原 stream；否则 capture 不能形成完整的依赖图。示例省略了与前一段相同的 fork/join 具体提交步骤。

> The locality restriction of each child stream is retained by the captured kernel nodes. Graph replay uses the original localized SMs even when the executable graph is launched on a different stream. The graph launch stream supplies ordering but does not replace the execution resources recorded in the nodes.

各 child stream 的 locality 限制会保留在 capture 后的 kernel node 中。即使 executable graph 在另一 stream 上启动，replay 时仍使用原来的局部化 SM。Graph launch stream 只提供执行顺序，不会替换 node 中记录的执行资源。

**解读：** graph 中 kernel node 保留捕获时的局部化执行 context。replay 所用的 graph launch stream 负责与外部工作的顺序关系，不改变这些 node 的局部性选择。

##### 4.7.5.2.2. Graph Construction（显式构建 Graph）

> The same graph topology can be constructed explicitly. Add one kernel node for each locality domain, using the corresponding localized execution context in cudaKernelNodeParamsV2.ctx.

可以显式构建同样的 graph 拓扑。为每个 locality domain 添加一个 kernel node，并在 cudaKernelNodeParamsV2.ctx 中指定相应的局部化 execution context。

```cpp
cudaGraph_t graph = nullptr;
cudaGraphCreate(&graph, 0);

std::vector<cudaGraphNode_t> localizedNodes(localityDomainCount);
for (int i = 0; i < localityDomainCount; i++) {
    cudaGraphNodeParams params = { CU_GRAPH_NODE_TYPE_KERNEL };
    params.kernel.kern = kernel;
    params.kernel.gridDim = grid;
    params.kernel.blockDim = block;
    params.kernel.kernelParams = kernelArgs[i];
    params.kernel.ctx = localizedContexts[i];

    cudaGraphAddNode(&localizedNodes[i], graph, nullptr, nullptr, 0, &params);
}
```

**解读：** 示例只添加了按 domain 分配 context 的 kernel node；如需实现前述 fork/join 拓扑，还须显式添加相应的 graph 依赖边。`grid`、`block`、`kernelArgs` 等由调用方提供，示例未包含实例化、启动、销毁与错误处理。

#### 4.7.5.3. Compatibility Notes（兼容性说明）

> vGPU and MIG devices do not support localization and will report only 1 locality domain.

vGPU 和 MIG device 不支持局部化，只会报告 1 个 locality domain。

> CUDA on Windows does not support localization and will report only 1 locality domain.

Windows 上的 CUDA 不支持局部化，也只会报告 1 个 locality domain。

> CUDA Checkpoint does not guarantee that localized green contexts retain their localization properties when restored on a different device. The application may exhibit reduced performance after a restore.

CUDA Checkpoint 不保证局部化 green context 在另一设备上恢复后仍保有原局部化属性。恢复后应用性能可能下降。

> MPS (Multi-Process Service) in MLOPart mode presents each MLOPart device as a CUDA device with a single locality domain. MPS static partitioning treats the full device as a single locality domain.

MLOPart 模式下的 MPS（Multi-Process Service）将每个 MLOPart device 呈现为只有一个 locality domain 的 CUDA device。MPS 静态分区将完整 device 视为单个 locality domain。

**解读：** 可用 domain 数量受运行环境影响。尤其在 vGPU、MIG、Windows 或所列 MPS 模式下，查询可能只得到一个 domain；checkpoint 恢复到另一设备后，也应重新检查局部化资源的实际放置。
