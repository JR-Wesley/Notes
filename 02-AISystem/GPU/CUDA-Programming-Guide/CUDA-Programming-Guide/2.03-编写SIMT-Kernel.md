## 2.3. Writing SIMT Kernels（编写 SIMT kernel）

> CUDA kernels can largely be written in the same way that traditional CPU code would be written for a given problem. However, there are some unique features of the GPU that can be used to improve performance. Additionally, some understanding of how threads on the GPU are scheduled, how they access memory, and how their execution proceeds can help developers write kernels that maximize utilization of the available computing resources.

针对给定问题，CUDA kernel 的写法在很大程度上可以沿用传统 CPU 代码。不过，GPU 具有一些可以用来提高性能的独有特性。此外，理解 GPU 上线程如何调度、如何访问内存，以及执行过程如何推进，有助于开发者编写充分利用可用计算资源的 kernel。

> This chapter covers some more details of writing kernels using the SIMT programming model in both C++ and Python.

本章进一步介绍使用 C++ 和 Python，按照 SIMT 编程模型编写 kernel 的细节。

### 2.3.1. Basics of SIMT（SIMT 基础）

> From the developer’s perspective, the CUDA thread is the fundamental unit of parallelism. Section 1.2.2.2 describes the basic SIMT model of GPU execution and SIMT Execution Model provides additional details of the SIMT model. The SIMT model allows each thread to maintain its own state and control flow. From a functional perspective, each thread can execute a separate code path. However, substantial performance improvements can be realized by taking care that kernel code minimizes the situations where threads in the same warp take divergent code paths.

从开发者的角度看，CUDA thread 是并行执行的基本单位。第 1.2.2.2 节介绍了 GPU 执行所采用的基本 SIMT 模型，“SIMT Execution Model”一节则提供了更多细节。SIMT 模型允许每个线程维护自己的状态和控制流。从功能上说，每个线程可以执行不同的代码路径。不过，在编写 kernel 时尽量减少同一 warp 内线程沿不同路径执行的情况，可以显著改善性能。

**解读：** 每个线程在语义上可以独立选择分支，但同一 warp 内的不同分支会影响指令执行效率。优化时应关注同一 warp 内的路径一致性，而不是要求整个 grid 的线程都执行相同路径。

### 2.3.2. Thread Hierarchy（线程层次结构）

> Threads are organized into thread blocks, which are then organized into a grid. Grids may be 1, 2, or 3 dimensional and the size of the grid can be queried inside a kernel with the `gridDim` built-in variable. Thread blocks may also be 1, 2, or 3 dimensional. The size of the thread block can be queried inside a kernel with the `blockDim` built-in variable. The index of the thread block can be queried with the `blockIdx` built-in variable. Within a thread block, the index of the thread is obtained using the `threadIdx` built-in variable. These built-in variables are used to compute a unique global thread index for each thread, thereby enabling each thread to load/store specific data from global memory and execute a unique code path as needed.

线程被组织为 thread block，thread block 又被组织为 grid。Grid 可以是一维、二维或三维，在 kernel 内可以通过内建变量 `gridDim` 查询其大小。Thread block 同样可以是一维、二维或三维，其大小可以通过内建变量 `blockDim` 查询。Thread block 的索引可以通过 `blockIdx` 查询，block 内线程的索引则通过 `threadIdx` 获取。利用这些内建变量，可以为每个线程计算唯一的全局线程索引，从而使各线程能够读写 global memory 中的特定数据，并在需要时执行不同的代码路径。

- > `gridDim.[x|y|z]`: Size of the grid in the x, y and z dimension respectively. These values are the same for all threads and are part of the execution configuration set at kernel launch.

  `gridDim.[x|y|z]`：分别表示 grid 在 x、y、z 维度上的大小。所有线程看到的这些值都相同，它们属于 kernel 启动时设置的 execution configuration。

- > `blockDim.[x|y|z]`: Size of the block in the x, y and z dimension respectively. These values are the same for all threads and are part of the execution configuration set at kernel launch.

  `blockDim.[x|y|z]`：分别表示 block 在 x、y、z 维度上的大小。所有线程看到的这些值都相同，它们属于 kernel 启动时设置的 execution configuration。

- > `blockIdx.[x|y|z]`: Index of the block in the x, y and z dimension respectively. These values will differ among threads, to indicate which thread block is executing.

  `blockIdx.[x|y|z]`：分别表示 block 在 x、y、z 维度上的索引。不同线程看到的这些值可能不同，用于标识正在执行的线程所属的 thread block。

- > `threadIdx.[x|y|z]`: Index of the thread in the x, y and z dimension respectively. These values will differ among threads, to indicate which thread is executing.

  `threadIdx.[x|y|z]`：分别表示线程在 x、y、z 维度上的索引。不同线程看到的这些值不同，用于标识正在执行的线程。

> The use of multi-dimensional thread blocks and grids is for convenience only and does not affect performance. The threads of a block are linearized predictably: the first index x moves the fastest, followed by y and then z. This means that in the linearization of a thread indices, consecutive values of `threadIdx.x` indicate consecutive threads, `threadIdx.y` has a stride of `blockDim.x`, and `threadIdx.z` has a stride of `blockDim.x` * `blockDim.y`. This affects how threads are assigned to warps, as detailed in Hardware Multithreading.

使用多维 thread block 和 grid 只是为了方便，本身不会影响性能。Block 内的线程按照确定的规则线性化：第一个索引 x 变化最快，其次是 y，最后是 z。这意味着，在线程索引线性化后，连续的 `threadIdx.x` 对应连续线程；`threadIdx.y` 的步长为 `blockDim.x`；`threadIdx.z` 的步长为 `blockDim.x * blockDim.y`。这一规则会影响线程如何分配到 warp，详见“Hardware Multithreading”。

**解读：** Block 内的线性线程编号为 `threadIdx.x + blockDim.x * (threadIdx.y + blockDim.y * threadIdx.z)`。例如，`blockDim = (32, 8, 1)` 时，一个 warp 对应固定 y 下的 32 个 x；改成 `(16, 16, 1)` 后，一个 warp 会跨越两行。原文“维度不影响性能”指维度本身只是组织方式；维度改变后，线程到数据的映射以及 warp 内的访存模式仍可能改变性能。同一 block 的线程共享 `blockIdx`，不同 block 内可以有相同的 `threadIdx`。

#### 2.3.2.1. Thread Block Synchronization（Thread block 同步）

> In examples shown previously, there was not a need to synchronize threads within a thread block. When threads within a thread block cooperate or access the same memory addresses, especially in shared memory, described below, synchronization is necessary to avoid race conditions and memory hazards.

在前面的示例中，无须同步同一 thread block 内的线程。当 block 内的线程需要协作，或访问相同的内存地址时，尤其是在下文介绍的 shared memory 中，必须进行同步，以避免 race condition 和内存访问冲突。

> The most basic form of synchronization within a block is called syncthreads

Block 内最基本的同步形式称为 `syncthreads`。

#### 2.3.3.1. Global Memory（全局内存）

> Global memory (also called device memory) is the primary memory space for storing data that is accessible by all threads in a kernel. It is similar to RAM in a CPU system. Kernels running on the GPU have direct access to global memory in the same way code running on the CPU has access to system memory.

Global memory（也称 device memory）是存储 kernel 内所有线程都能访问的数据的主要内存空间，类似于 CPU 系统中的 RAM。GPU 上运行的 kernel 可以直接访问 global memory，就像 CPU 上运行的代码可以访问系统内存一样。

> Global memory is persistent. That is, an allocation made in global memory and the data stored in it persist until the allocation is freed or until the application is terminated. `cudaDeviceReset` also frees all allocations.

Global memory 具有持久性：在其中分配的内存及其保存的数据会持续存在，直到显式释放该分配，或者应用程序终止。`cudaDeviceReset` 也会释放所有分配。

> Global memory is allocated with CUDA API calls such as `cudaMalloc` and `cudaMallocManaged`. Data can be copied into global memory from CPU memory using CUDA runtime API calls such as `cudaMemcpy`. Global memory allocations made with CUDA APIs are freed using `cudaFree`.

通过 `cudaMalloc`、`cudaMallocManaged` 等 CUDA API 可以分配 global memory。通过 `cudaMemcpy` 等 CUDA Runtime API，可以将数据从 CPU 内存复制到 global memory。通过 CUDA API 分配的 global memory 使用 `cudaFree` 释放。

> Prior to a kernel launch, global memory is allocated and initialized by CUDA API calls. During kernel execution, data from global memory can be read by the CUDA threads, and the result from operations carried out by CUDA threads can be written back to global memory. Once a kernel has completed execution, the results it wrote to global memory can be copied back to the host or used by other kernels on the GPU.

在启动 kernel 之前，使用 CUDA API 分配并初始化 global memory。Kernel 执行期间，CUDA thread 可以从 global memory 读取数据，也可以将计算结果写回其中。Kernel 执行完成后，它写入 global memory 的结果可以复制回 host，也可以由 GPU 上的其他 kernel 使用。

> Because global memory is accessible by all threads in a grid, care must be taken to avoid data races between threads. Since CUDA kernels launched from the host have the return type void, the only way for numerical results computed by a kernel to be returned to the host is by writing those results to global memory.

由于 grid 内的所有线程都可以访问 global memory，因此必须避免线程之间发生 data race。从 host 启动的 CUDA kernel 的返回类型为 `void`，所以 kernel 计算得到的数值结果只能通过写入 global memory 的方式返回给 host。

> A simple example illustrating the use of global memory is the kernel shown below, where the three arrays A, B, and C are in global memory and are being accessed by this vector add kernel.

下面的 kernel 是使用 global memory 的简单示例：三个数组 `A`、`B`、`C` 都位于 global memory 中，由这个向量加法 kernel 访问。

```cpp
__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }
}
```

#### 2.3.3.2. Shared Memory（共享内存）

> Shared memory is a memory space that is accessible by all threads in a thread block. It is physically located on each SM and uses the same physical resource as the L1 cache, the unified data cache. The data in shared memory persists throughout the kernel execution. Shared memory can be considered a user-managed scratchpad for use during kernel execution. While small in size compared to global memory, because shared memory is located on each SM, the bandwidth is higher and the latency is lower than accessing global memory.

Shared memory 是同一 thread block 内所有线程都可以访问的内存空间。它在物理上位于各个 SM 内，与 L1 cache 共用统一数据缓存这一物理资源。Shared memory 中的数据在 kernel 执行期间保持有效，可以将其视为执行 kernel 时由用户管理的临时工作区（scratchpad）。虽然容量比 global memory 小，但由于它位于 SM 内，访问带宽更高、延迟更低。

> Since shared memory is accessible by all threads in a thread block, care must be taken to avoid data races between threads in the same thread block. Synchronization between threads in the same thread block can be achieved using the `__syncthreads()` function in C++. In Python, this same thread block synchronization is achieved using `cuda.syncthreads()`. This function blocks all threads in the thread block until all threads have reached the call to `__syncthreads()` or `cuda.syncthreads()`.

由于同一 thread block 内的所有线程都可以访问 shared memory，因此必须避免 block 内的线程发生 data race。C++ 使用 `__syncthreads()` 同步同一 block 内的线程；Python 中对应的函数是 `cuda.syncthreads()`。该函数会阻塞 block 内的线程，直到所有线程都到达 `__syncthreads()` 或 `cuda.syncthreads()` 调用。

```cpp
// assuming blockDim.x is 128
__global__ void example_syncthreads(int* input_data, int* output_data)
{
    __shared__ int shared_data[128];
    shared_data[threadIdx.x] = input_data[blockDim.x*blockIdx.x + threadIdx.x];

    // All threads synchronize, guaranteeing all writes to 'shared_data' are ordered
    // before any thread is unblocked from '__syncthreads()':
    __syncthreads();

    // A single thread safely reads 'shared_data':
    if (threadIdx.x == 0) {
        float sum = 0;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += shared_data[i];
        }
        output_data[blockIdx.x] = sum;
    }
}
```

**解读：** 这里的依赖顺序是“各线程写入自己的 shared memory 元素—全 block 同步—线程 0 读取全部元素”。不能把 `__syncthreads()` 移入只由线程 0 执行的分支。示例还假定一维 block 恰有 128 个线程、输入足够长、输出至少能容纳每个 block 的一个结果；其 `int` 输入使用 `float` 累加再转回 `int`，不适合作为任意整数数据的精确求和实现。

> The size of shared memory varies depending on the GPU architecture being used. Because shared memory and L1 cache share the same physical space, using shared memory reduces the size of the usable L1 cache for a kernel. Additionally, if no shared memory is used by the kernel, the entire physical space will be utilized by L1 cache. The CUDA runtime API provides functions to query the shared memory size on a per SM basis and a per thread block basis, using the `cudaGetDeviceProperties` function and investigating the `cudaDeviceProp.sharedMemPerMultiprocessor` and `cudaDeviceProp.sharedMemPerBlock` device properties.

Shared memory 的大小随 GPU 架构而变化。由于 shared memory 和 L1 cache 共用同一物理空间，使用 shared memory 会减少 kernel 可用的 L1 cache 容量。此外，如果 kernel 不使用 shared memory，那么全部物理空间都会用于 L1 cache。可以调用 CUDA Runtime API 的 `cudaGetDeviceProperties`，查询 `cudaDeviceProp.sharedMemPerMultiprocessor` 和 `cudaDeviceProp.sharedMemPerBlock` 属性，分别了解每个 SM 和每个 thread block 的 shared memory 大小。

> The CUDA runtime API provides a function `cudaFuncSetCacheConfig` to tell the runtime whether to allocate more space to shared memory, or more space to L1 cache. This function specifies a preference to the runtime, but is not guaranteed to be honored. The runtime is free to make decisions based on the available resources and the needs of the kernel.

CUDA Runtime API 提供 `cudaFuncSetCacheConfig`，用于告知 runtime 倾向于给 shared memory 分配更多空间，还是给 L1 cache 分配更多空间。该函数只是向 runtime 指定一种偏好，不能保证一定被采用。Runtime 可以根据可用资源和 kernel 的需求自行决定。

**解读：** Shared memory 与 L1 的容量分配由架构支持的配置以及驱动选择共同决定。原文“没有使用 shared memory 就一定把全部物理空间用于 L1”应视为简化描述，不能据此推算实际 L1 容量。Shared memory 是显式管理的存储区，L1 则是硬件缓存；两者共用物理资源，也不等于两者具有相同语义。参见 [L1/shared memory 配置说明](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)。

> Shared memory can be allocated both statically and dynamically.

Shared memory 既可以静态分配，也可以动态分配。

##### 2.3.3.2.1. Static Allocation of Shared Memory（Shared memory 的静态分配）

> To allocate shared memory statically, the programmer must declare a variable inside the kernel using the `__shared__` specifier in C++ or the `cuda.shared.array()` in Python. The array will be allocated in shared memory and will persist for the duration of the kernel execution. The size of the shared memory declared in this way must be specified at compile time. For example, the following code snippet, located in the body of the kernel, declares a shared memory array of type float with 1024 elements.

要静态分配 shared memory，程序员必须在 kernel 内声明变量：C++ 使用 `__shared__` 修饰符，Python 使用 `cuda.shared.array()`。数组将分配在 shared memory 中，并在 kernel 执行期间保持有效。采用这种方式声明的 shared memory，其大小必须在编译时确定。例如，下面位于 kernel 函数体内的代码声明了一个包含 1024 个 `float` 元素的 shared memory 数组。

```cpp
__shared__ float sharedArray[1024];
```

> After this declaration, all the threads in the thread block will have access to this shared memory array.

完成这一声明后，该 thread block 中的所有线程都可以访问这个 shared memory 数组。

##### 2.3.3.2.2. Dynamic Allocation of Shared Memory（Shared memory 的动态分配）

> To allocate shared memory dynamically in C++, the programmer can specify the desired amount of shared memory per thread block in bytes as the third (and optional) argument to the kernel launch in the triple chevron notation like this `functionName<<<grid, block, sharedMemoryBytes>>>()`. When this parameter is not specified, it defaults to 0.

在 C++ 中动态分配 shared memory 时，可以通过三尖括号 kernel 启动语法的第三个可选参数，指定每个 thread block 所需的 shared memory 字节数，例如 `functionName<<<grid, block, sharedMemoryBytes>>>()`。省略该参数时，默认值为 0。

> In Python, `cuda.core.launch()` must be used to launch the kernel. The `LaunchConfig` parameter takes a `cuda.core.LaunchConfig` object, which has a field called `shmem_size` which serves the same function as the 3rd argument in the triple chevron notation in C++.

在 Python 中，必须使用 `cuda.core.launch()` 启动 kernel。其 `LaunchConfig` 参数接收一个 `cuda.core.LaunchConfig` 对象，其中的 `shmem_size` 字段与 C++ 三尖括号语法中的第三个参数起相同作用。

**解读（原文勘误）：** Python 动态 shared memory 并不要求必须使用 `cuda.core.launch()`。Numba CUDA 也支持 `kernel[grid, block, stream, sharedmem](...)`，最后一个参数是动态 shared memory 的字节数；注意它的 `stream`、`sharedmem` 顺序与 C++ 相反。参见 [Numba kernel 启动配置](https://nvidia.github.io/numba-cuda/reference/kernel.html#dispatcher-objects)。

> Inside the kernel, the programmer can use the `extern __shared__` specifier with empty [] in C++ to declare a variable that will be allocated dynamically at kernel launch. In Python, the same `cuda.shared.array` method used to statically allocate shared memory is used with the `shape` argument set to 0.

在 kernel 内，C++ 可以使用 `extern __shared__` 修饰符和空的 `[]`，声明在 kernel 启动时动态分配的变量。Python 则使用与静态分配相同的 `cuda.shared.array` 方法，但将 `shape` 参数设为 0。

```cpp
extern __shared__ float sharedArray[];
```

> One caveat is that a kernel can have only one dynamically allocated shared array. If one wants multiple dynamically allocated shared memory arrays, a single dynamically allocated shared memory array which is large enough to contain all the desired arrays must be allocated and manually partitioned. In C++, for example, if one wants the equivalent of the following,

需要注意，一个 kernel 只能有一个动态分配的 shared memory 数组。如果需要多个动态 shared memory 数组，就必须分配一块足够容纳所有目标数组的动态 shared memory，并手动进行分区。例如，在 C++ 中，如果希望在动态 shared memory 中实现与下面这些数组等价的布局，

```cpp
short array0[128];
float array1[64];
int   array2[256];
```

> in dynamically allocated shared memory, one could declare and initialize the arrays in the following way:

就可以采用下面的方式声明并初始化这些数组：

```cpp
extern __shared__ float array[];

short* array0 = (short*)array;
float* array1 = (float*)&array0[128];
int*   array2 =   (int*)&array1[64];
```

> Note that pointers need to be aligned to the type they point to, so the following code, for example, does not work since array1 is not aligned to 4 bytes.

注意，指针必须满足其所指向类型的对齐要求。例如，下面的代码不可行，因为 `array1` 没有按 4 字节对齐。

```cpp
extern __shared__ float array[];
short* array0 = (short*)array;
float* array1 = (float*)&array0[127];
```

> In Python, since there are no pointers, this form of type punning is not available.

在 Python 中，由于没有指针，无法使用这种形式的 type punning（通过不同类型解释同一内存）。

**解读：** “只有一个动态数组”更准确地说是每个 block 只有一块动态 shared memory 分配，多个声明可以引用同一片底层存储，不能当成彼此独立的分配。示例三个数组占 `128 × 2 + 64 × 4 + 256 × 4 = 1536` 字节，偏移分别为 0、256、512；错误示例中 `127 × 2 = 254`，不满足 `float` 的 4 字节对齐。Python 无法直接照搬 C++ 指针转换语法，但 Numba 支持不同 dtype 的动态 shared array 引用同一底层内存，也支持通过互不重叠的 view 分区，见 [Numba Dynamic Shared Memory](https://nvidia.github.io/numba-cuda/user/memory.html#dynamic-shared-memory)。

#### 2.3.3.3. Registers（寄存器）

> Registers are located on the SM and have thread local scope. Register usage is managed by the compiler and registers are used for thread local storage during the execution of a kernel. The number of registers per SM and the number of registers per thread block can be queried using the `regsPerMultiprocessor` and `regsPerBlock` device properties of the GPU.

寄存器位于 SM 内，其作用域是单个线程。寄存器使用由编译器管理，用于在 kernel 执行期间保存线程私有的数据。可以通过 GPU 的 `regsPerMultiprocessor` 和 `regsPerBlock` 属性，分别查询每个 SM 和每个 thread block 的寄存器数量。

> When compiling C++ code, NVCC allows the developer to specify a maximum number of registers to be used by a kernel via the `-maxrregcount` option. Using this option to reduce the number of registers a kernel can use may result in more thread blocks being scheduled on the SM concurrently, but may also result in more register spilling. Register spilling means that values currently stored on-chip in registers must be written out to global memory and then read back later to make space for other values.

编译 C++ 代码时，NVCC 允许开发者通过 `-maxrregcount` 选项指定 kernel 可使用的寄存器数量上限。降低这一上限可能使更多 thread block 同时驻留在 SM 上，但也可能增加 register spilling。Register spilling 是指为了给其他值腾出寄存器空间，必须先将原本保存在片上寄存器中的值写入 global memory，之后再读回来。

**解读：** `--maxrregcount` 控制的是每个线程的寄存器使用上限。限制寄存器可能换来更多驻留线程，也可能造成额外的 local memory 读写，因此不能只看 occupancy 判断是否值得。相关单位见 [每线程寄存器上限](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#maximum-number-of-registers-per-thread)。

#### 2.3.3.4. Local Memory（局部内存）

> Local memory is thread local storage similar to registers and managed by NVCC, but the physical location of local memory is in the global memory space. The ‘local’ label refers to its logical scope, not its physical location. Local memory is used for thread local storage during the execution of a kernel. Automatic variables that the compiler is likely to place in local memory are:

Local memory 与寄存器类似，是由 NVCC 管理的线程私有存储，但它在物理上位于 global memory 空间中。“Local”指其逻辑作用域，而不是物理位置。它用于在 kernel 执行期间保存线程私有数据。编译器可能将下列自动变量放入 local memory：

- > Arrays for which it cannot determine that they are indexed with constant quantities,

  编译器无法确定其索引是否为常量的数组；

- > Large structures or arrays that would consume too much register space,

  会占用过多寄存器空间的大型结构体或数组；

- > Any variable if the kernel uses more registers than available, that is register spilling.

  当 kernel 所需寄存器超过可用数量时的任何变量，即发生 register spilling 的变量。

> Because the local memory space resides in device memory, local memory accesses have the same latency and bandwidth as global memory accesses and are subject to the same requirements for memory coalescing as described in Coalesced Global Memory Access. However, local memory is organized such that consecutive 32-bit words are accessed by consecutive thread IDs. Accesses are therefore fully coalesced as long as all threads in a warp access the same relative address, such as the same index in an array variable or the same member in a structure variable.

由于 local memory 位于 device memory 中，因此其访问具有与 global memory 相同的延迟和带宽特性，并且同样受“Coalesced Global Memory Access”中介绍的访存合并要求约束。不过，local memory 的组织方式使连续的 32 位字对应连续的线程 ID。因此，只要同一 warp 内的所有线程访问相同的相对地址，例如各自数组变量的同一下标，或各自结构体变量的同一成员，就可以实现完全合并的访问。

**解读：** 这里说的是不同线程各自的私有数组中“相同相对位置”的访问，例如 warp 内所有线程都读取自己的 `local_array[3]`，并非它们读取同一个共享对象。理解 local memory 时要分别判断私有性、物理位置和实际访问地址。

#### 2.3.3.5. Constant Memory（常量内存）

> Constant memory has grid scope and is accessible for the lifetime of the application. The constant memory resides on the device and is read-only to the kernel.

Constant memory 的访问范围覆盖整个 grid，并在应用程序的生命周期内可用。它位于 device 上，对 kernel 而言是只读的。

> In C++, variables or arrays are declared with the `__constant__` specifier outside any kernel or function.

在 C++ 中，使用 `__constant__` 修饰符，在任何 kernel 或函数之外声明变量或数组。

> In Python, the method `const_array = numba.cuda.const.array_like(ary)` is specified within the kernel code to create a constant memory array containing the data stored in the host array ary

在 Python 中，在 kernel 代码内使用 `const_array = numba.cuda.const.array_like(ary)`，创建一个 constant memory 数组，其中包含 host 数组 `ary` 中的数据。

> Constant memory means that a variable:

一个 constant memory 变量具有以下特性：

- > Resides in constant memory space,

  位于 constant memory space 中；

- > Has a distinct object per device,

  在每个 device 上都有独立的对象；

- > Is accessible from all the threads within the grid and from the host in C++ through the runtime library (`cudaGetSymbolAddress()` / `cudaGetSymbolSize()` / `cudaMemcpyToSymbol()` / `cudaMemcpyFromSymbol()`).

  Grid 内的所有线程都可以访问它；在 C++ 中，host 也可以通过 Runtime Library 的 `cudaGetSymbolAddress()`、`cudaGetSymbolSize()`、`cudaMemcpyToSymbol()` 和 `cudaMemcpyFromSymbol()` 访问它。

> In C++, constant memory has the lifetime of the context in which it was created. In Python, constant memory has the lifetime of the kernel in which it is declared.

在 C++ 中，constant memory 的生命周期与创建它的 context 相同。在 Python 中，constant memory 的生命周期与声明它的 kernel 相同。

**解读：** Python 段落中的“kernel 生命周期”不宜直接理解成“每次启动时由每个线程重新复制 host 数组”。`const.array_like` 表达的是 kernel 使用的常量数据；应将这一语义与运行时可写的 shared array 分开理解。参见 [Numba constant memory](https://nvidia.github.io/numba-cuda/user/memory.html#constant-memory)。

> The total amount of constant memory can be queried with the `totalConstMem` device property element.

可以通过 device property 中的 `totalConstMem` 字段查询 constant memory 的总容量。

> Constant memory is useful for small amounts of data that each thread will use in a read-only fashion. Constant memory is small relative to other memories, typically 64KB per device.

Constant memory 适合存放各线程以只读方式使用的少量数据。相较于其他内存，它的容量很小，通常每个 device 为 64 KB。

> An example snippet of declaring and using constant memory follows.

下面的片段展示了 constant memory 的声明和使用方式。

```cpp
// In your .cu file
__constant__ float coeffs[4];

__global__ void compute(float *out) {
    int idx = threadIdx.x;
    out[idx] = coeffs[0] * idx + coeffs[1];
}

// In your host code
float h_coeffs[4] = {1.0f, 2.0f, 3.0f, 4.0f};
cudaMemcpyToSymbol(coeffs, h_coeffs, sizeof(h_coeffs));
compute<<<1, 10>>>(device_out);
```

#### 2.3.3.6. Caches（缓存）

> GPU devices have a multi-level cache structure which includes L2 and L1 caches.

GPU device 具有多级缓存结构，包括 L2 cache 和 L1 cache。

> The L2 cache is located on the device and is shared among all the SMs. The size of the L2 cache can be queried with the `l2CacheSize` device property element from the function `cudaGetDeviceProperties`.

L2 cache 位于 device 上，由所有 SM 共享。可以通过 `cudaGetDeviceProperties` 返回的 `l2CacheSize` 属性查询其大小。

> As described above in Shared Memory, L1 cache is physically located on each SM and is the same physical space used by shared memory. If no shared memory is utilized by a kernel, the entire physical space will be utilized by the L1 cache.

如前文“Shared Memory”所述，L1 cache 在物理上位于各个 SM 内，并与 shared memory 使用同一物理空间。如果 kernel 不使用 shared memory，则整个物理空间都会用于 L1 cache。

> The L2 and L1 caches can be controlled via functions that allow the developer to specify various caching behaviors. The details of these functions are found in Configuring L1/Shared Memory Balance, L2 Cache Control, and Low-Level Load and Store Functions.

开发者可以通过相关函数控制 L2 和 L1 cache，指定不同的缓存行为。这些函数的详细说明见“Configuring L1/Shared Memory Balance”“L2 Cache Control”和“Low-Level Load and Store Functions”。

> If these hints are not used, the compiler and runtime will do their best to utilize the caches efficiently.

如果不提供这些提示，编译器和 runtime 会尽可能高效地利用缓存。

#### 2.3.3.7. Texture and Surface Memory（纹理内存与表面内存）

> Note: Some older CUDA code may use texture memory because, in older NVIDIA GPUs, doing so provided performance benefits in some scenarios. On all currently supported GPUs, these scenarios may be handled using direct load and store instructions, and use of texture and surface memory instructions no longer provides any performance benefit for non-texture loads.

注意：一些较早的 CUDA 代码可能会使用 texture memory，因为在较早的 NVIDIA GPU 上，这种方式在某些场景下能够提升性能。在当前支持的所有 GPU 上，这些场景都可以通过直接的 load/store 指令处理；对于非纹理数据读取，使用 texture memory 和 surface memory 指令已经不再具有性能优势。

> A GPU may have specialized instructions for loading data from an image to be used as textures in 3D rendering. CUDA exposes these instructions and the machinery to use them in the texture object API and the surface object API.

GPU 可能提供专用指令，用于从图像中读取数据，并将其作为三维渲染中的纹理。CUDA 通过 texture object API 和 surface object API 暴露这些指令及相应的使用机制。

> Texture and surface memory do not provide any performance advantage for non-graphics applications in CUDA on any currently supported NVIDIA GPU. These APIs are still useful when reading texture or surface data for rendering, such as writing hit shaders for NVIDIA OptiX, which uses CUDA as its shader language.

在当前支持的所有 NVIDIA GPU 上，texture memory 和 surface memory 都不会为 CUDA 非图形应用提供性能优势。不过，这些 API 对于读取用于渲染的纹理或 surface 数据仍然有用，例如为以 CUDA 作为 shader 语言的 NVIDIA OptiX 编写 hit shader。

对于需要维护现有代码、仍在使用这些 API 读取非纹理数据的开发者，可以在旧版 CUDA C++ Programming Guide 中找到相关 API 的说明。

#### 2.3.3.8. Distributed Shared Memory（分布式共享内存）

> Note: Distributed shared memory is a feature available when using thread block clusters. Thread block clusters make use of the `cooperative_groups` APIs, which are currently only available in C++.

注意：Distributed shared memory 是使用 thread block cluster 时可用的特性。Thread block cluster 使用 `cooperative_groups` API，而这些 API 目前仅在 C++ 中提供。

> Thread Block Clusters, introduced in compute capability 9.0 and facilitated by Cooperative Groups, provide the ability for threads in a thread block cluster to access shared memory of all the participating thread blocks in that cluster. This partitioned shared memory is called Distributed Shared Memory, and the corresponding address space is called Distributed Shared Memory address space. Threads that belong to a thread block cluster can read, write or perform atomics in the distributed address space, regardless of whether the address belongs to the local thread block or a remote thread block. Whether a kernel uses distributed shared memory or not, the shared memory size specifications, static or dynamic is still per thread block. The size of distributed shared memory is just the number of thread blocks per cluster multiplied by the size of shared memory per thread block.

Compute capability 9.0 引入了 thread block cluster，并通过 Cooperative Groups 提供支持，使 cluster 内的线程能够访问所有参与 block 的 shared memory。这种分区式共享内存称为 Distributed Shared Memory（分布式共享内存），相应地址空间称为 Distributed Shared Memory address space。Cluster 内的线程可以对该地址空间执行读取、写入或原子操作，无论目标地址属于本地 block 还是远端 block。无论 kernel 是否使用 distributed shared memory，静态或动态 shared memory 的大小仍然按每个 thread block 指定。Distributed shared memory 的总大小等于每个 cluster 的 block 数量乘以每个 block 的 shared memory 大小。

> Accessing data in distributed shared memory requires all the thread blocks to exist. A user can guarantee that all thread blocks have started executing using `cluster.sync()` from class `cluster_group`. The user also needs to ensure that all distributed shared memory operations happen before the exit of a thread block, e.g., if a remote thread block is trying to read a given thread block’s shared memory, the program needs to ensure that the shared memory read by the remote thread block is completed before it can exit.

访问 distributed shared memory 要求所有相关 thread block 都已经存在。可以使用 `cluster_group` 类的 `cluster.sync()`，保证所有 block 都已开始执行。同时，还必须保证所有 distributed shared memory 操作在线程块退出之前完成。例如，如果远端 block 正在读取某个 block 的 shared memory，程序必须保证这次远端读取完成后，被访问的 block 才能退出。

**解读：** Distributed shared memory 扩大了可访问范围，但没有把各 block 的 shared memory 变成独立持久的全局存储。下面第一次 `cluster.sync()` 保证各 block 已存在且清零完成；第二次保证远端更新完成，随后各 block 才读取并汇总自己的部分。

> Let’s look at a simple histogram computation and how to optimize it on the GPU using thread block clusters. A standard way of computing histograms is to perform the computation in the shared memory of each thread block and then perform global memory atomics. A limitation of this approach is the shared memory capacity. Once the histogram bins no longer fit in the shared memory, a user needs to directly compute histograms and hence the atomics in the global memory. With distributed shared memory, CUDA provides an intermediate step, where depending on the histogram bins size, the histogram can be computed in shared memory, distributed shared memory or global memory directly.

下面以简单的直方图计算为例，说明如何使用 thread block cluster 优化 GPU 上的计算。一种常见方法是在各 block 的 shared memory 中计算直方图，再使用 global memory 原子操作汇总。这种方法受到 shared memory 容量限制：当直方图的 bin 无法放入 shared memory 时，就需要直接在 global memory 中计算直方图并执行原子操作。Distributed shared memory 提供了一个中间层次：根据直方图各 bin 所需的存储容量，可以在 shared memory、distributed shared memory 或直接在 global memory 中计算直方图。

> The CUDA kernel example below shows how to compute histograms in shared memory or distributed shared memory, depending on the number of histogram bins.

下面的 CUDA kernel 根据直方图 bin 的数量，在 shared memory 或 distributed shared memory 中计算直方图。

```cpp
#include <cooperative_groups.h>

// Distributed Shared memory histogram kernel
__global__ void clusterHist_kernel(int *bins, const int nbins, const int bins_per_block, const int *__restrict__ input,
                                    size_t array_size)
{
    extern __shared__ int smem[];
    namespace cg = cooperative_groups;
    int tid = cg::this_grid().thread_rank();

    // Cluster initialization, size and calculating local bin offsets.
    cg::cluster_group cluster = cg::this_cluster();
    unsigned int clusterBlockRank = cluster.block_rank();
    int cluster_size = cluster.dim_blocks().x;

    for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
    {
    smem[i] = 0; //Initialize shared memory histogram to zeros
    }

    // cluster synchronization ensures that shared memory is initialized to zero in
    // all thread blocks in the cluster. It also ensures that all thread blocks
    // have started executing and they exist concurrently.
    cluster.sync();

    for (int i = tid; i < array_size; i += blockDim.x * gridDim.x)
    {
    int ldata = input[i];

    //Find the right histogram bin.
    int binid = ldata;
    if (ldata < 0)
        binid = 0;
    else if (ldata >= nbins)
        binid = nbins - 1;

    //Find destination block rank and offset for computing
    //distributed shared memory histogram
    int dst_block_rank = (int)(binid / bins_per_block);
    int dst_offset = binid % bins_per_block;

    //Pointer to target block shared memory
    int *dst_smem = cluster.map_shared_rank(smem, dst_block_rank);

    //Perform atomic update of the histogram bin
    atomicAdd(dst_smem + dst_offset, 1);
    }

    // cluster synchronization is required to ensure all distributed shared
    // memory operations are completed and no thread block exits while
    // other thread blocks are still accessing distributed shared memory
    cluster.sync();

    // Perform global memory histogram, using the local distributed memory histogram
    int *lbins = bins + cluster.block_rank() * bins_per_block;
    for (int i = threadIdx.x; i < bins_per_block; i += blockDim.x)
    {
    atomicAdd(&lbins[i], smem[i]);
    }
}
```

> The above kernel can be launched at runtime with a cluster size depending on the amount of distributed shared memory required. If the histogram is small enough to fit in shared memory of just one block, the user can launch the kernel with cluster size 1. The code snippet below shows how to launch a cluster kernel dynamically based on shared memory requirements.

上面的 kernel 可以在运行时根据所需 distributed shared memory 的容量，以不同 cluster size 启动。如果直方图足够小，一个 block 的 shared memory 就能容纳，则可以将 cluster size 设为 1。下面的片段展示如何根据 shared memory 需求动态启动 cluster kernel。

```cpp
// Launch via extensible launch
{
    cudaLaunchConfig_t config = {0};
    config.gridDim = array_size / threads_per_block;
    config.blockDim = threads_per_block;

    // cluster_size depends on the histogram size.
    // ( cluster_size == 1 ) implies no distributed shared memory, just thread block local shared memory
    int cluster_size = 2; // size 2 is an example here
    int nbins_per_block = nbins / cluster_size;

    //dynamic shared memory size is per block.
    //Distributed shared memory size =  cluster_size * nbins_per_block * sizeof(int)
    config.dynamicSmemBytes = nbins_per_block * sizeof(int);

    CUDA_CHECK(::cudaFuncSetAttribute((void *)clusterHist_kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, config.dynamicSmemBytes));

    cudaLaunchAttribute attribute[1];
    attribute[0].id = cudaLaunchAttributeClusterDimension;
    attribute[0].val.clusterDim.x = cluster_size;
    attribute[0].val.clusterDim.y = 1;
    attribute[0].val.clusterDim.z = 1;

    config.numAttrs = 1;
    config.attrs = attribute;

    cudaLaunchKernelEx(&config, clusterHist_kernel, bins, nbins, nbins_per_block, input, array_size);
}
```

**解读（示例前提）：** 这里按一维 block 和一维 cluster 编写，`nbins / cluster_size` 隐含要求 bin 数能整除 cluster size，否则最后一部分 bin 可能映射到不存在的 block。Grid 的 block 数还须与 cluster 维度兼容，不能把普通 kernel 的取整启动方式直接套用。`bins` 应在累加前初始化，申请的动态 shared memory 和 cluster size 也必须满足设备限制。代码中的 `CUDA_CHECK`、输入分配和这些检查均未在片段中定义。

### 2.3.4. Memory Performance（访存性能）

> Ensuring proper memory usage is key to achieving high performance in CUDA kernels. This section discusses some general principles and examples for achieving high memory throughput from global memory and shared memory in CUDA kernels. Global memory performance is a top performance consideration for most kernels. Shared memory is commonly used when threads operate on data they did not explicitly load or create, and so understanding performance-related characteristics of shared memory is also important.

正确使用内存是实现高性能 CUDA kernel 的关键。本节介绍一些通用原则和示例，说明如何在 kernel 中获得较高的 global memory 和 shared memory 吞吐量。对于大多数 kernel，global memory 性能是首要性能因素之一。在线程需要处理并非由自己显式加载或创建的数据时，通常会使用 shared memory，因此理解它与性能相关的特性同样重要。

> The following subsections will illustrate the important aspects of memory access by progressively improving access to both global and shared memory in a sample matrix transpose kernel.

下面各小节将围绕一个矩阵转置 kernel，逐步改善对 global memory 和 shared memory 的访问，以说明访存中的重要问题。

#### 2.3.4.1. Coalesced Global Memory Access（Global memory 合并访问）

> Global memory is accessed via 32-byte memory transactions. When a CUDA thread requests a word of data from global memory, the relevant warp coalesces the memory requests from all the threads in that warp into the number of memory transactions necessary to satisfy the request, depending on the size of the word accessed by each thread and the distribution of the memory addresses across the threads. For example, if a thread requests a 4-byte word, the actual memory transaction the warp will generate to global memory will be 32 bytes in total. To use the memory system most efficiently, the warp should use all the memory that is fetched in a single memory transaction. That is, if a thread is requesting a 4-byte word from global memory, and the transaction size is 32 bytes, if other threads in that warp can use other 4-byte words of data from that 32-byte request, this will result in the most efficient use of the memory system.

Global memory 通过 32 字节的 memory transaction（内存事务）访问。当某个 CUDA thread 请求从 global memory 读取一个字时，所属 warp 会根据各线程所访问字的大小和地址分布，将 warp 内所有线程的请求合并为满足这些请求所需的若干内存事务。例如，即使一个线程只请求一个 4 字节的字，warp 实际发起的 global memory 事务也会涉及总共 32 字节。为了最有效地利用内存系统，warp 应尽量使用单次事务取得的全部数据：如果某线程需要一个 4 字节的字，而事务大小为 32 字节，那么让同一 warp 的其他线程使用这 32 字节中的其他 4 字节数据，就能提高内存系统的利用效率。

> As a simple example, if consecutive threads in the warp request consecutive 4-byte words in memory, then the warp will request 128 bytes of memory total, and this 128 bytes required will be fetched in four 32-byte memory transactions. This results in 100% utilization of the memory transactions by threads in the warp. Figure 12 illustrates this example of perfectly coalesced memory access.

举一个简单例子：如果 warp 内连续线程请求内存中连续的 4 字节字，那么总共请求 128 字节，这些数据可以通过四次 32 字节事务取得。这样，事务传输的数据被 warp 内线程使用的比例为 100%。图 12 展示了这种完全合并的访存。

**解读：** 四次 32 字节事务还隐含起始地址按 32 字节对齐。连续 32 个 `float` 若跨越五个 32 字节段，就需要五次事务。因此，“连续”与“对齐”都要检查；这里计算的是 warp 一条访存指令涉及的段，不能直接等同于经过缓存后的实际 DRAM 流量。

> Figure 12 Coalesced memory access

图 12：合并访存。

> Conversely, the pathologically worst case scenario is when consecutive threads access data elements that are 32 bytes or more apart from each other in memory. In this case, the warp will be forced to issue a 32-byte memory transaction for each thread, and the total number of bytes of memory traffic will be 32 bytes times 32 threads/warp = 1024 bytes. However, the amount of memory used will be 128 bytes only (4 bytes for each thread in the warp), so the memory utilization will only be 128 / 1024 = 12.5%. This is a very inefficient use of the memory system. Figure 13 illustrates this example of uncoalesced memory access.

相反，极端的最差情况是连续线程访问的数据元素在内存中相距至少 32 字节。此时，warp 必须为每个线程发起一次 32 字节事务，总流量为 32 字节 × 每个 warp 的 32 个线程 = 1024 字节。但实际使用的数据只有 128 字节，即每个线程 4 字节，因此内存利用率仅为 128 / 1024 = 12.5%。这种内存使用方式非常低效，图 13 展示了这一非合并访存示例。

> Figure 13 Uncoalesced memory access

图 13：非合并访存。

> The most straightforward way to achieve coalesced memory access is for consecutive threads to access consecutive elements in memory. For example, for a kernel launched with 1d thread blocks, the previously shown vector add kernels will achieve coalesced memory access. Notice how a thread accesses the three arrays: and consecutive threads (indicated by consecutive values of `workIndex`) access consecutive elements in the arrays.

实现合并访存最直接的方式，是让连续线程访问内存中的连续元素。例如，以一维 thread block 启动前面给出的向量加法 kernel，就可以实现合并访存。观察线程访问三个数组的方式：连续线程由连续的 `workIndex` 表示，访问的也是数组中的连续元素。

```cpp
__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }
}
```

> There is no requirement that consecutive threads access consecutive elements of memory to achieve coalesced memory access, it is merely the typical way coalescing is achieved. Coalesced memory access occurs provided different threads in the warp access elements from the same 32-byte segments of memory in some linear or permuted way. Stated another way, the best way to achieve coalesced memory access is to maximize the ratio of bytes used to bytes transferred.

实现合并访存并不要求连续线程必须访问连续元素，这只是最常见的实现方式。只要 warp 内不同线程访问的是相同一组 32 字节内存段内的元素，无论按线性顺序还是按某种排列访问，都可以合并。换一种说法，实现高效合并访存的关键是尽量提高“实际使用字节数 / 传输字节数”的比例。

> An equivalent way to conceptualize global memory coalescing is to consider how many global memory transactions are required to satisfy the 32 addresses requested by a single load instruction from a single warp. In the best possible case, a single global memory transaction will be required to satisfy all loads. For perfectly coalesced access to 4-byte data elements, 4 global memory transactions will be required. In the worst case, 32 global memory transactions may be required to satisfy the addresses requested by a single load instruction from a single warp. In general, performance will be best when the number of global memory transactions required to satisfy a load is as small as possible.

理解 global memory 合并访问的另一种等价方式，是计算满足单个 warp 的一条 load 指令所请求的 32 个地址，需要多少次 global memory 事务。在最理想情况下，一次事务就可以满足全部读取。对于完全合并的 4 字节元素访问，需要四次事务。在最差情况下，单个 warp 的一条 load 指令可能需要 32 次事务才能满足所有地址请求。一般而言，满足一次 load 所需的事务越少，性能越好。

**解读：** “一次事务满足全部线程”可能对应多个线程访问同一 32 字节段中的数据，包括重复地址。32 个线程读取 32 个互不相同的 `float`，总共需要 128 字节，不可能只用一次 32 字节事务取得全部数据。

> Note: Ensuring proper coalescing of global memory accesses is one of the most important performance considerations for writing performant CUDA kernels. It is imperative that applications use the memory system as efficiently as possible.

注意：确保 global memory 访问得到正确合并，是编写高性能 CUDA kernel 最重要的性能考量之一。应用程序必须尽可能高效地使用内存系统。

##### 2.3.4.1.1. Matrix Transpose Example Using Global Memory（使用 global memory 的矩阵转置示例）

> As a simple example, consider an out-of-place matrix transpose kernel that transposes a 32 bit float square matrix of size N x N, from matrix a to matrix c. This example uses a 2d grid, and assumes a launch of 2d thread blocks of size 32 x 32 threads, that is, `blockDim.x` = 32 and `blockDim.y` = 32, so each 2d thread block will operate on a 32 x 32 tile of the matrix. Each thread operates on a unique element of the matrix, so no explicit synchronization of threads is necessary. Figure 14 illustrates this matrix transpose operation. The kernel source code follows the figure.

考虑一个简单的非原地矩阵转置 kernel：将大小为 N × N、元素类型为 32 位 `float` 的方阵，从矩阵 `a` 转置到矩阵 `c`。示例使用二维 grid，并假定以 32 × 32 个线程组成的二维 block 启动，即 `blockDim.x = 32`、`blockDim.y = 32`，每个 block 处理一个 32 × 32 的矩阵 tile。各线程处理不同的矩阵元素，因此无须显式线程同步。图 14 展示了这一转置操作，图后给出 kernel 源码。

> Figure 14 Matrix Transpose using Global memory

图 14：使用 global memory 的矩阵转置。

> The labels on the top and left of each matrix are the 2d thread block indices and also can be considered the tile indices, where each small square indicates a tile of the matrix that will be operated on by a 2d thread block. In this example, the tile size is 32 x 32 elements, so each of the small squares represents a 32 x 32 tile of the matrix. The green shaded square shows the location of an example tile before and after the transpose operation.

每个矩阵顶部和左侧的标签是二维 thread block 的索引，也可以视为 tile 索引。每个小方格表示由一个二维 block 处理的矩阵 tile。本例的 tile 大小为 32 × 32 个元素，因此每个小方格都代表一个 32 × 32 的矩阵子块。绿色阴影方格标出了一个示例 tile 在转置前后的位置。

```cpp
/* macro to index a 1D memory array with 2D indices in row-major order */
/* ld is the leading dimension, i.e. the number of columns in the matrix     */

#define INDX( row, col, ld ) ( ( (row) * (ld) ) + (col) )

/* CUDA kernel for matrix transpose */

__global__ void cuda_transpose(int m, float *a, float *c )
{
    int myCol = blockDim.x * blockIdx.x + threadIdx.x;
    int myRow = blockDim.y * blockIdx.y + threadIdx.y;

    if( myRow < m && myCol < m )
    {
        c[INDX( myCol, myRow, m )] = a[INDX( myRow, myCol, m )];
    } /* end if */
    return;
} /* end cuda_transpose */
```

> To determine whether this kernel is achieving coalesced memory access one needs to determine whether consecutive threads are accessing consecutive elements of memory. In a 2d thread block, the x index moves the fastest, so consecutive values of `threadIdx.x` should be accessing consecutive elements of memory. `threadIdx.x` appears in `myCol`, and one can observe that when `myCol` is the second argument to the `INDX` macro, consecutive threads are reading consecutive values of a, so the read of a is perfectly coalesced.

判断这个 kernel 是否实现合并访存，需要检查连续线程是否访问连续的内存元素。在二维 block 内，x 索引变化最快，因此连续的 `threadIdx.x` 应当对应连续内存元素。`threadIdx.x` 出现在 `myCol` 的计算中；当 `myCol` 作为 `INDX` 宏的第二个参数时，连续线程读取 `a` 中连续的值，因此对 `a` 的读取完全合并。

> However, the writing of c is not coalesced, because consecutive values of `threadIdx.x` (again examine `myCol`) are writing elements to c that are ld (leading dimension) elements apart from each other. This is observed because now `myCol` is the first argument to the `INDX` macro, and as the first argument to `INDX` increments by 1, the memory location changes by ld. When ld is larger than 32 (which occurs whenever the matrix sizes are larger than 32), this is equivalent to the pathological case shown in Figure 13.

但对 `c` 的写入没有合并，因为连续的 `threadIdx.x`——仍然观察 `myCol`——写入的是 `c` 中相距 `ld` 个元素的位置，`ld` 表示 leading dimension。这是因为此时 `myCol` 是 `INDX` 的第一个参数，第一个参数每增加 1，内存位置就移动 `ld` 个元素。当 `ld` 大于 32，也就是矩阵维度大于 32 时，这相当于图 13 中的极端情况。

> To alleviate these uncoalesced writes, the use of shared memory can be employed, which will be described in the next section.

可以使用 shared memory 改善这种非合并写入，下一节将介绍这种方法。

#### 2.3.4.2. Shared Memory Access Patterns（Shared memory 访问模式）

> Shared memory has 32 banks that are organized such that successive 32-bit words map to successive banks. Each bank has a bandwidth of 32 bits per clock cycle.

Shared memory 有 32 个 bank，连续的 32 位字依次映射到连续的 bank。每个 bank 的带宽为每个时钟周期 32 位。

> When multiple threads in the same warp attempt to access different elements in the same bank, a bank conflict occurs. In this case, the access to the data in that bank will be serialized until the data in that bank has been obtained by all the threads that have requested it. This serialization of access results in a performance penalty.

当同一 warp 内的多个线程访问同一 bank 中的不同元素时，就会发生 bank conflict。此时，对该 bank 的数据访问必须串行执行，直到所有请求线程都取得所需数据。这种串行化会造成性能损失。

> The two exceptions to this scenario happen when multiple threads in the same warp are accessing (either reading or writing) the same shared memory location. For read accesses, the word is broadcast to the requesting threads. For write accesses, each shared memory address is written by only one of the threads (which thread performs the write is undefined).

当 warp 内多个线程访问同一个 shared memory 位置时，存在两种例外情况。读取时，该字会广播给所有请求线程；写入时，每个 shared memory 地址只由其中一个线程写入，具体由哪个线程写入未定义。

**解读：** 同址读取可以广播；同址非原子写入即使没有 bank conflict，也不能保证多个更新都被保留。Bank conflict 是性能问题，data race 是正确性问题，消除前者并不自动解决后者。

图 15 展示了几种跨步访问。Bank 内的红框表示 shared memory 中的一个特定位置。

图 15：32 位 bank 大小模式下的跨步 shared memory 访问。

  左图：步长为一个 32 位字的线性寻址，无 bank conflict。

- > Middle: Linear addressing with a stride of two 32-bit words (two-way bank conflict).

  中图：步长为两个 32 位字的线性寻址，存在两路 bank conflict。

- > Right: Linear addressing with a stride of three 32-bit words (no bank conflict).

  右图：步长为三个 32 位字的线性寻址，无 bank conflict。

图 16 展示了涉及广播机制的几种读取访问。Bank 内的红框表示 shared memory 中的一个特定位置。如果多个箭头指向同一位置，该数据就会广播给所有请求它的线程。

  右图：无冲突的广播访问，线程访问同一 bank 内的同一个字。

**解读：** 对本节的 32 位访问，可用 `bank = word_index % 32` 理解映射。连续 32 个线程采用固定字步长 s 时，步长 1 覆盖 32 个 bank，步长 2 只覆盖 16 个 bank，步长 3 又覆盖全部 32 个 bank。这解释了图 15 中三种访问模式的差别。

##### 2.3.4.2.1. Matrix Transpose Example Using Shared Memory（使用 shared memory 的矩阵转置示例）

> In the previous example Matrix Transpose Example Using Global Memory, an implementation of matrix transpose was illustrated that was functionally correct, but not optimized for efficient use of global memory because the write of the c matrix was not coalesced properly. In this example, shared memory will be treated as a user-managed cache to stage loads and stores from global memory, resulting in coalesced global memory access of both reads and writes.

前面的“使用 global memory 的矩阵转置示例”在功能上是正确的，但由于对矩阵 `c` 的写入未能正确合并，global memory 使用效率并不理想。本例将 shared memory 作为用户管理的缓存，暂存从 global memory 读入的数据及随后要写出的数据，使 global memory 的读写都能够合并。

```cpp
#define THREADS_PER_BLOCK_X 32
#define THREADS_PER_BLOCK_Y 32

/* macro to index a 1D memory array with 2D indices in column-major order */
/* ld is the leading dimension, i.e. the number of rows in the matrix     */

#define INDX( row, col, ld ) ( ( (col) * (ld) ) + (row) )

/* CUDA kernel for shared memory matrix transpose */
__global__ void smem_transpose(int m,
                                    float *a,
                                    float *c )
{

    /* declare a statically allocated shared memory array */

    __shared__ float smemArray[THREADS_PER_BLOCK_X][THREADS_PER_BLOCK_Y];

    /* determine my row and column indices for the error checking code */

    const int myRow = blockDim.x * blockIdx.x + threadIdx.x;
    const int myCol = blockDim.y * blockIdx.y + threadIdx.y;

    /* determine my row tile and column tile index */

    const int tileX = blockDim.x * blockIdx.x;
    const int tileY = blockDim.y * blockIdx.y;

    if( myRow < m && myCol < m )
    {
        /* read from global memory into shared memory array */
        smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileX + threadIdx.x, tileY + threadIdx.y, m )];
    } /* end if */

    /* synchronize the threads in the thread block */
    __syncthreads();

    if( myRow < m && myCol < m )
    {
        /* write the result from shared memory to global memory */
        c[INDX( tileY + threadIdx.x, tileX + threadIdx.y, m )] = smemArray[threadIdx.y][threadIdx.x];
    } /* end if */
    return;

}
```

**解读（原文一致性与边界问题）：** 这段完整代码将 `INDX` 定义成列主序：`col * ld + row`，所以 `threadIdx.x` 位于第一个参数时，global memory 地址才连续。后文却改用 `tileRow`、`tileCol`，并按行主序解释第二个参数，二者不能直接拼接。这里保留原样，阅读时必须先确定正在使用哪一个 `INDX` 定义。

此外，完整代码写回时交换了 tile 坐标，却仍沿用读入阶段的边界条件。对于 m 不是 32 的整数倍的边缘 tile，这可能漏写、越界或读取尚未初始化的 shared memory。按这段列主序代码的约定，写回条件应检查 `tileY + threadIdx.x < m && tileX + threadIdx.y < m`；读入阶段保留原条件，block 内同步仍须由所有参与线程执行。这是对原代码的静态推导，未做 GPU 运行验证。

> The fundamental performance optimization illustrated in this example is to ensure that when accessing global memory, the memory accesses are coalesced properly. Prior to the execution of the copy, each thread computes its `tileRow` and `tileCol` indices. These are the indices for the specific tile that will be operated on, and these tile indices are based on which thread block is executing. Each thread in the same thread block has the same `tileRow` and `tileCol` values, so it can be thought of as the starting position of the tile that this specific thread block will operate on.

本例展示的核心优化，是确保访问 global memory 时能够正确合并请求。在复制之前，每个线程先计算 `tileRow` 和 `tileCol`，它们表示当前要处理的 tile 的位置，由正在执行的 thread block 决定。同一个 block 内的所有线程具有相同的 `tileRow` 和 `tileCol`，因此可以将其理解为该 block 所处理 tile 的起始位置。

> The kernel then proceeds with each thread block copying a 32 x 32 tile of the matrix from global memory to shared memory with the following statement. Since the size of a warp is 32 threads, this copy operation will be executed by 32 warps, with no guaranteed order between the warps.

随后，每个 thread block 使用下面的语句，将一个 32 × 32 的矩阵 tile 从 global memory 复制到 shared memory。由于每个 warp 包含 32 个线程，这次复制由 32 个 warp 执行，warp 之间的执行顺序没有保证。

```cpp
smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];
```

> Note that because `threadIdx.x` appears in the second argument to `INDX`, consecutive threads are accessing consecutive elements in memory, and the read of a is perfectly coalesced. In Python, this using `cuda.threadIdx.x` as the last index in the tuple has the same effect: access to a is perfectly coalesced.

注意，由于 `threadIdx.x` 出现在 `INDX` 的第二个参数中，连续线程访问连续的内存元素，对 `a` 的读取完全合并。在 Python 中，将 `cuda.threadIdx.x` 用作索引元组中的最后一个索引，也能使对 `a` 的访问完全合并。

**解读（对应关系）：** 这段叙述及紧邻的短代码片段采用的是行主序解释，对应本章前一个示例的 `row * ld + col`。它与本小节完整代码中的列主序宏不同；“第几个参数变化最快”取决于实际地址公式，不能脱离宏定义记忆。

> The next step in the kernel is the call to `__syncthreads()` / `cuda.syncthreads()`. This ensures that all threads in the thread block have completed their execution of the previous code before proceeding and therefore that the write of a into shared memory is completed before the next step. This is critically important because the next step will involve threads reading from shared memory. Without the `__syncthreads()`/ `cuda.syncthreads()` call, the read of a into shared memory is not guaranteed to be completed by all warps in the thread block before some warps advance to reading from the array in shared memory. When a thread processes or stores data it did not load, synchronization is necessary to ensure that the load operation for that element has completed before accessing it.

Kernel 的下一步是调用 `__syncthreads()` / `cuda.syncthreads()`。这保证 block 内所有线程都完成前面的代码之后才继续执行，因此从 `a` 读入 shared memory 的写入会在下一步开始前完成。这一点至关重要，因为下一步会从 shared memory 读取数据。如果没有这一同步调用，在部分 warp 已开始读取 shared memory 数组时，其他 warp 可能还没有完成从 `a` 到 shared memory 的加载。当线程处理或存储的数据并非由自己加载时，就需要同步，以保证访问该元素之前，其加载操作已经完成。

> At this point in the kernel, for each thread block, the shared memory array has a 32 x 32 tile of the matrix, arranged in the same order as the original matrix. To ensure that the elements within the tile are transposed properly, `threadIdx.x` and `threadIdx.y` are swapped when they read from `smemArray`. To ensure that the overall tile is placed in the correct place in c, the `tileRow` and `tileCol` indices are also swapped when they write to c. To ensure proper coalescing, `threadIdx.x` is used in the second argument to `INDX`, as shown by the statement below. In Python, this is again achieved by using `cuda.threadIdx.x` in the last index of the matrix index tuple.

此时，每个 block 的 shared memory 数组都保存了一个 32 × 32 的矩阵 tile，排列顺序与原矩阵相同。为正确转置 tile 内的元素，从 `smemArray` 读取时要交换 `threadIdx.x` 与 `threadIdx.y`；为将整个 tile 放到 `c` 中正确的位置，写入 `c` 时还要交换 `tileRow` 与 `tileCol`。为确保正确合并访存，`threadIdx.x` 放在 `INDX` 的第二个参数中，如下所示。Python 中同样通过将 `cuda.threadIdx.x` 用作矩阵索引元组的最后一个索引来实现。

```cpp
c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];
```

> This kernel illustrates two common uses of shared memory.

这个 kernel 展示了 shared memory 的两种常见用途。

- > Shared memory is used to stage data from global memory to ensure that reads from and writes to global memory are both coalesced properly.

  使用 shared memory 暂存 global memory 数据，使 global memory 的读取和写入都能正确合并。

- > Shared memory is used to allow threads in the same thread block to share data among themselves.

  使用 shared memory，使同一 thread block 内的线程能够彼此共享数据。

**解读：** 转置需要同时交换 tile 在大矩阵中的位置，以及 tile 内元素的位置。Shared memory 允许读入和写出由不同线程接手，从而重新安排 global memory 的访问顺序；同步负责保证接手读取发生在原线程写入之后。

##### 2.3.4.2.2. Shared Memory Bank Conflicts（共享内存 bank 冲突）

> In Section 2.3.4.2, the bank structure of shared memory was described. In the previous matrix transpose example, the proper coalesced memory access to/from global memory was achieved, but no consideration was given to whether shared memory bank conflicts were present. Consider the following 2d shared memory declaration,

第 2.3.4.2 节介绍了 shared memory 的 bank 结构。前面的矩阵转置示例已经实现了 global memory 读写的正确合并，但尚未考虑 shared memory 是否存在 bank conflict。考虑下面的二维 shared memory 声明：

```cpp
__shared__ float smemArray[32][32];
```

> Assume that the kernel is expected to be launched with a 2-d threadblock of 32 x 32 threads. Since a warp is 32 threads, each thread in a particular warp will have a fixed value for `threadIdx.y` and will have 0 <= `threadIdx.x` < 32.

假定 kernel 使用一个 32 × 32 个线程的二维 thread block 启动。每个 warp 有 32 个线程，因此同一 warp 中各线程的 `threadIdx.y` 固定，`threadIdx.x` 则满足 `0 <= threadIdx.x < 32`。

> The left panel of Figure 17 illustrates the situation when the threads in a warp access the data in a column of `smemArray`. Warp 0 is accessing memory locations `smemArray`[0][0] through `smemArray`[31][0] (`smemArray`[(0,0)] through `smemArray`[(31,0)] in Python). In both C++ and Python, multi-dimensional array ordering, the last index moves the fastest, so consecutive threads in warp 0 are accessing memory locations that are 32 elements apart. As illustrated in the figure, the colors denote the banks, and this access down the entire column by warp 0 results in a 32-way bank conflict.

图 17 左图展示了同一 warp 内线程访问 `smemArray` 同一列数据的情况。Warp 0 访问从 `smemArray[0][0]` 到 `smemArray[31][0]` 的位置；Python 中对应 `smemArray[(0,0)]` 到 `smemArray[(31,0)]`。在 C++ 和 Python 的多维数组排列中，最后一个索引变化最快，因此 warp 0 的连续线程访问的内存位置相距 32 个元素。图中颜色表示 bank，warp 0 沿整列访问会产生 32 路 bank conflict。

> The right panel of Figure 17 illustrates the situation when the threads in a warp access the data across a row of `smemArray`. Warp 0 is accessing memory locations `smemArray`[0][0] through `smemArray`[0][31] (`smemArray`[(0,0)] through `smemArray`[(0,31)] in Python). In this case, consecutive threads in warp 0 are accessing memory locations that are adjacent. As illustrated in the figure, the colors denote the banks, and this access across the entire row by warp 0 results in no bank conflicts. The ideal scenario is for each thread in a warp to access a shared memory location with a different color.

图 17 右图展示了同一 warp 内线程访问 `smemArray` 同一行数据的情况。Warp 0 访问从 `smemArray[0][0]` 到 `smemArray[0][31]` 的位置；Python 中对应 `smemArray[(0,0)]` 到 `smemArray[(0,31)]`。此时，连续线程访问相邻内存位置。图中颜色表示 bank，warp 0 沿整行访问不会产生 bank conflict。理想情况是每个线程访问一种不同颜色所代表的 shared memory 位置。

> Figure 17 Bank structure in a 32 x 32 shared memory array. The numbers in the boxes indicate the warp index. The colors indicate which bank is associated with that shared memory location.

图 17：32 × 32 的 shared memory 数组中的 bank 结构。方框中的数字表示 warp 索引，颜色表示该 shared memory 位置所属的 bank。

> Returning to the example from Section 2.3.4.2.1, one can examine the usage of shared memory to determine whether bank conflicts are present. The first usage of shared memory is when data from global memory is stored to shared memory:

回到第 2.3.4.2.1 节的示例，可以检查 shared memory 的使用是否存在 bank conflict。第一次使用 shared memory，是将 global memory 中的数据写入其中：

```cpp
smemArray[threadIdx.x][threadIdx.y] = a[INDX( tileRow + threadIdx.y, tileCol + threadIdx.x, m )];
```

> Because arrays are stored in row-major order, consecutive threads in the same warp, as indicated by consecutive values of `threadIdx.x`, will access `smemArray` with a stride of 32 elements, because `threadIdx.x` is the first index into the array. This results in a 32-way bank conflict and is illustrated by the left panel of Figure 17.

由于数组按 row-major order（行主序）存储，同一 warp 内由连续 `threadIdx.x` 表示的连续线程，会以 32 个元素为步长访问 `smemArray`，因为 `threadIdx.x` 是数组的第一个索引。这会造成 32 路 bank conflict，如图 17 左图所示。

> The second usage of shared memory is when data from shared memory is written back to global memory:

第二次使用 shared memory，是将其中的数据写回 global memory：

```cpp
c[INDX( tileCol + threadIdx.y, tileRow + threadIdx.x, m )] = smemArray[threadIdx.y][threadIdx.x];
```

> In this case, because `threadIdx.x` is the second index into the `smemArray` array, consecutive threads in the same warp will access `smemArray` with a stride of 1 element. This results in no bank conflicts and is illustrated by the right panel of Figure 17.

此时，`threadIdx.x` 是 `smemArray` 的第二个索引，同一 warp 内连续线程以一个元素为步长访问数组，因此没有 bank conflict，如图 17 右图所示。

> The matrix transpose kernel as illustrated in Section 2.3.4.2.1 has one access of shared memory that has no bank conflicts and one access that has a 32-way bank conflict. A common fix to avoid bank conflicts is to pad the shared memory by adding one to the column dimension of the array as follows:

第 2.3.4.2.1 节的矩阵转置 kernel 有一次 shared memory 访问没有 bank conflict，另一次则有 32 路 bank conflict。一种常见修复方法是在数组列维度上增加一个元素，给 shared memory 加入 padding：

```cpp
__shared__ float smemArray[THREADS_PER_BLOCK_X][THREADS_PER_BLOCK_Y+1];
```

> This minor adjustment to the declaration of `smemArray` will eliminate the bank conflicts. To illustrate this, consider Figure 18 where the shared memory array has been declared with a size of 32 x 33. One observes that whether the threads in the same warp access the shared memory array down an entire column or across an entire row, the bank conflicts have been eliminated, i.e., the threads in the same warp access locations with different colors.

对 `smemArray` 声明做出这一小改动，就可以消除 bank conflict。图 18 展示了声明为 32 × 33 的 shared memory 数组：无论同一 warp 内的线程沿整列还是整行访问，各线程所访问的位置都对应不同颜色，因此 bank conflict 被消除了。

**解读：** 在 C++ 二维数组的行主序布局下，`smemArray[x][y]` 的字偏移为 `x × leading_dimension + y`。宽度为 32 时，同一 warp 固定 y、连续 x，会反复命中同一个 bank；宽度改为 33 后，`(33x + y) % 32 = (x + y) % 32`，32 个线程分别落到不同 bank。空间从 4096 字节增加到 4224 字节，仅增加 128 字节。这个推导针对本例的 `float`、32 个 bank 和 32 × 32 block，不应不加检查地推广到其他元素大小或布局。

> Figure 18 Bank structure in a 32 x 33 shared memory array. The numbers in the boxes indicate the warp index. The colors indicate which bank is associated with that shared memory location.

图 18：32 × 33 的 shared memory 数组中的 bank 结构。方框中的数字表示 warp 索引，颜色表示该 shared memory 位置所属的 bank。

### 2.3.5. Atomics（原子操作）

> Performant CUDA kernels rely on expressing as much algorithmic parallelism as possible. The asynchronous nature of GPU kernel execution requires that threads operate as independently as possible. It’s not always possible to have complete independence of threads and as we saw in Shared Memory, there exists a mechanism for threads in the same thread block to exchange data and synchronize.

高性能 CUDA kernel 依赖于尽可能充分地表达算法中的并行性。GPU kernel 执行的异步特性要求线程尽量独立工作。不过，线程并不总能完全独立；正如“Shared Memory”一节所示，同一 thread block 内的线程可以通过相应机制交换数据并同步。

> On the level of an entire grid there is no such mechanism to synchronize all threads in a grid. There is however a mechanism to provide synchronous access to global memory locations via the use of atomic functions. Atomic functions allow a thread to obtain a lock on a global memory location and perform a read-modify-write operation on that location. No other thread can access the same location while the lock is held.

在整个 grid 的层次上，没有这样的机制来同步 grid 内的全部线程。不过，可以使用原子函数，为 global memory 中的位置提供同步访问。原子函数允许一个线程锁定某个 global memory 位置，并对它执行 read-modify-write（读—改—写）操作。持有该锁期间，其他线程都不能访问同一位置。

**解读（原文勘误）：** 这里的“锁住地址，其他线程无法访问”只是粗糙类比，不能当成原子操作的保证。Atomic 保证适用 thread scope 内对应操作的原子性；普通非原子访问不会因为它而自动获得互斥保护，对其他数据的可见性还取决于 memory order 和同步关系。原子加法也不是全 grid barrier。参见 [CUDA C++ memory model](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/memory_model.html)。原文“整个 grid 没有同步机制”应限定为普通 kernel 的常规启动语境；符合条件的 cooperative launch 可以支持 grid 同步，见后文解读。

#### 2.3.5.1. C++ std::atomic-like Atomics（C++ 中类似 std::atomic 的原子操作）

> In C++, CUDA provides similar syntax and behavior as the similarly-named C++ standard library atomics `cuda::std::atomic` and `cuda::std::atomic_ref`. CUDA also provides extended C++ atomics `cuda::atomic` and `cuda::atomic_ref` which allow the user to specify the thread scope of the atomic operation. The details of atomic functions are covered in Atomic Functions.

在 C++ 中，CUDA 提供了与同名 C++ 标准库原子类型具有相似语法和行为的 `cuda::std::atomic` 与 `cuda::std::atomic_ref`。此外还提供扩展原子类型 `cuda::atomic` 和 `cuda::atomic_ref`，允许用户指定原子操作的 thread scope。详细说明见“Atomic Functions”。

> An example usage of `cuda::atomic_ref` to perform a device-wide atomic addition is as follows, where array is an array of floats, and result is a float pointer to a location in global memory which is the location where the sum of the array will be stored.

下面展示使用 `cuda::atomic_ref` 执行 device 范围原子加法的示例。其中，`array` 是一个 `float` 数组，`result` 是指向 global memory 中某个位置的 `float` 指针，该位置用于保存数组元素的总和。

```cpp
__global__ void sumReduction(int n, float *array, float *result) {
...
tid = threadIdx.x + blockIdx.x * blockDim.x;

cuda::atomic_ref<float, cuda::thread_scope_device> result_ref(result);
result_ref.fetch_add(array[tid]);
...
}
```

**解读（原文勘误）：** `cuda::atomic_ref<float, ...>` 绑定的是已有的 `float` 对象，因此原代码 `result_ref(result)` 应为 `result_ref(*result)`；还需要包含 `<cuda/atomic>`。示例中的 `...` 表示代码省略，实际实现还需声明 `tid`、判断 `tid < n`，并在累加前将结果初始化为零。参见 [cuda::atomic_ref 官方示例](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/synchronization_primitives/atomic_ref.html)。

> Atomic functions should be used sparingly as they enforce thread synchronization that can impact performance.

应当节制地使用原子函数，因为它们施加的线程同步可能影响性能。

**解读：** 性能代价尤其取决于竞争程度：大量线程更新同一个结果地址容易成为瓶颈。先在 block 内求局部结果、再减少全局原子更新次数，通常是值得考虑的组织方式；原子操作本身并不意味着所有线程都会在某个同步点等待。

#### 2.3.5.2. Memory Atomics in Python（Python 中的内存原子操作）

> In Python, atomic memory operations are provided by functions available to GPU code in the `numba.cuda.atomic` namespace. Typical operations such as add, sub, max, min, and `compare_and_swap` are available. The full list of supported atomic operations is available in the Numba CUDA documentation.

在 Python 中，GPU 代码通过 `numba.cuda.atomic` 命名空间中的函数执行内存原子操作，支持 `add`、`sub`、`max`、`min`、`compare_and_swap` 等常见操作。完整列表参见 Numba CUDA 文档。

> The following code shows an example of a kernel using atomic memory access to compute the sum of all values in an array. Each thread block loads a slice of the array into shared memory. A single thread of each thread block computes a local sum and performs an atomic add to the result array, s. Because the data resides in shared memory, which is close to the compute resources of the SM, having a single thread perform the sum is usually still reasonably performant.

下面的 kernel 使用原子访问计算数组全部元素的总和。每个 thread block 先将数组的一个片段加载到 shared memory，再由 block 内的一个线程计算局部总和，并将它原子加到结果数组 `s` 中。由于数据位于靠近 SM 计算资源的 shared memory，即使由单个线程求和，通常也仍能获得尚可的性能。

```python
import numpy as np
from numba import cuda
import cupy as cp


@cuda.jit
def sum_reduce(a, s):
    ## create a shared array to support a block size up to 512 threads
    ## even though we'll use fewer in this example
    shared_staging = cuda.shared.array(shape=512, dtype=np.float32)

    ## Load values into shared memory and then synchronize to make sure all loads completed
    shared_staging[cuda.threadIdx.x] = a[cuda.blockIdx.x*cuda.blockDim.x + cuda.threadIdx.x]
    cuda.syncthreads()

    ## only thread 0 of each block does the local additions, followed by a single
    ## atomic operation per thread block
    local_sum = float(0.0)
    if cuda.threadIdx.x == 0:
        for i in range(cuda.blockDim.x):
            local_sum = local_sum + shared_staging[i]
        cuda.atomic.add(s, 0, local_sum)


array_length = 2**18

a = cp.ones(array_length)
s = cp.zeros(1, dtype=np.float32)

block_size = 256
grid_size = int(array_length/block_size)
sum_reduce[grid_size, block_size](a, s)

s_host = cp.asnumpy(s)
print(f"Sum is {int(s_host[0])}, expected {array_length}")
```

**解读：** 原例的 `2**18` 恰好能被 256 整除，所以这里的整除 grid 大小和无边界检查加载能够对应全部输入。推广到任意长度时，要向上取整 block 数、给无效线程的 shared memory 元素写入加法单位元 0，并让它们仍然参加同步；还要保证 block 大小不超过数组容量 512。由一个线程串行累加整个 block 主要便于展示原子操作，不能据此判断它是高吞吐 reduction 的最佳实现。

> In this simple example, the input array is all 1s, and so the correct sum is the same as the `array_length`.

在这个简单示例中，输入数组的元素全为 1，因此正确总和与 `array_length` 相同。

> If the line

如果将下面这一行

```python
cuda.atomic.add(s, 0, local_sum)
```

> were instead the non-atomic add

替换为以下非原子加法，

```python
s[0] = s[0] + local_sum
```

> access to `s[0]` would not be atomic and the final value of `s[0]` will be less than `array_length`. Further, that value may change from run to run and when run on GPUs with different numbers of SMs. This illustrates how atomic memory access is required for correctness in this code.

那么对 `s[0]` 的访问就不再具有原子性，`s[0]` 的最终值将小于 `array_length`。此外，多次运行之间，以及在不同 SM 数量的 GPU 上运行时，结果都可能变化。这说明在这段代码中，原子内存访问是保证正确性的必要条件。

**解读（原文表述限定）：** 非原子更新存在丢失累加的 data race，结果可能偏小，但不能保证每次都严格小于正确值；特定调度下也可能碰巧正确。测试偶然通过并不能证明不存在竞争。对于一般浮点输入，即便使用原子加法保证每次更新不丢失，不同累加顺序仍可能因舍入而产生不同结果。

> Note: This example, while functional, is not intended to illustrate how to write peak-performance reduction operations on the GPU. The CUDA Core Compute Libraries (CCCL) from NVIDIA provide high-performance primitives for many operations, including reductions. For both productivty and performance, developers should prefer to use these highly-tuned implementations over reimplementing the same algorithms whenever possible. These primitives are available in Python through the `cuda.coop` package.

注意：这个示例虽然能够完成任务，但目的并不是展示峰值性能的 GPU reduction 实现。NVIDIA 的 CUDA Core Compute Libraries（CCCL）为包括 reduction 在内的许多操作提供了高性能基础算法。为了兼顾开发效率和性能，只要可行，开发者都应优先使用这些经过充分优化的实现。Python 中可以通过 `cuda.coop` 包使用这些基础算法。

> Similar atomics are also available in C++, which are discussed in Section 5.4.5.1, but use of the `std::atomic-like` atomics is recommended and considered best practice in CUDA C++.

C++ 中也提供了类似的原子操作，详见第 5.4.5.1 节。不过，CUDA C++ 推荐采用类似 `std::atomic` 的原子操作形式，并将其视为最佳实践。

### 2.3.6. Cooperative Groups（协作组）

> Cooperative groups is a software tool available in CUDA C++ that allows applications to define groups of threads which can synchronize with each other, even if that group of threads spans multiple thread blocks, multiple grids on a single GPU, or even across multiple GPUs. The CUDA programming model in general allows threads within a thread block or thread block cluster to synchronize efficiently, but does not provide a mechanism for specifying thread groups smaller than a thread block or cluster. Similarly, the CUDA programming model does not provide mechanisms or guarantees that enable synchronization across thread blocks.

Cooperative Groups 是 CUDA C++ 中的软件工具，允许应用程序定义能够相互同步的线程组，即使线程组跨越多个 thread block、同一 GPU 上的多个 grid，甚至多个 GPU。通常，CUDA 编程模型允许同一 thread block 或 thread block cluster 内的线程高效同步，但没有提供指定小于 block 或 cluster 的线程组的机制。同样，一般的 CUDA 编程模型也没有提供跨 block 同步的机制或保证。

> Cooperative groups provide both of these capabilities through software. Cooperative groups allows the application to create thread groups that cross the boundary of thread blocks and clusters, though doing so comes with some semantic limitations and performance implications which are described in detail in the feature section covering cooperative groups.

Cooperative Groups 通过软件提供了上述两类能力，使应用程序可以创建跨越 block 和 cluster 边界的线程组。不过，这会伴随一定的语义限制和性能影响，详见介绍 Cooperative Groups 的特性章节。

**解读（适用范围）：** Cooperative Groups 可以细分 block，也可以在设备与启动方式满足条件时使用 grid 级协作；全 grid 同步需要 `cudaLaunchCooperativeKernel` 等相应启动支持，不能在任意普通启动中直接调用 grid barrier。原文“跨多个 GPU”的说法不适用于所有当前版本：CUDA 13 已移除 Cooperative Groups 的多设备 launch API 及相关 `multi_grid_group` 支持。这里保留这一版本条件，因为它直接影响代码是否可用。参见 [Cooperative Groups 的 Large Scale Groups](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cooperative-groups.html#large-scale-groups) 和 [CUDA 13.0 Cooperative Groups 变更](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#what-s-new-in-cooperative-groups)。

### 2.3.7. Kernel Launch and Occupancy（Kernel 启动与 occupancy）

> When a CUDA kernel is launched, CUDA threads are grouped into thread blocks and a grid based on the execution configuration specified at kernel launch. Once the kernel is launched, the scheduler assigns thread blocks to SMs. The details of which thread blocks are scheduled to execute on which SMs cannot be controlled or queried by the application and no ordering guarantees are made by the scheduler, so programs cannot rely on a specific scheduling order or scheme for correct execution.

CUDA kernel 启动时，线程按照启动时指定的 execution configuration 组成 thread block 和 grid。启动之后，调度器将 block 分配给 SM。应用程序无法控制或查询具体哪个 block 被调度到哪个 SM，调度器也不保证执行顺序，因此程序不能依赖特定调度顺序或调度方案来保证正确性。

> The number of blocks that can be scheduled on an SM depends on the hardware resources a given thread block requires, and the hardware resources available on the SM. When a kernel is first launched, the scheduler begins assigning thread blocks to SMs. As long as SMs have sufficient hardware resources unoccupied by other thread blocks, the scheduler will continue assigning thread blocks to SMs. If at some point no SM has the capacity to accept another thread block, the scheduler will wait until the SMs complete previously assigned thread blocks. Once this happens, SMs are free to accept more work, and the scheduler assigns thread blocks to them. This process continues until all thread blocks have been scheduled and executed.

一个 SM 能调度多少个 block，取决于每个 block 所需的硬件资源，以及 SM 上可用的资源。Kernel 刚启动时，调度器开始向 SM 分配 block；只要还有 SM 留有足够的、未被其他 block 占用的资源，分配就会继续。如果所有 SM 都无法再接纳一个 block，调度器就等待此前分配的 block 完成。资源释放后，SM 可以接收更多工作，调度器再为其分配 block。该过程持续到所有 block 都完成调度和执行。

> The `cudaGetDeviceProperties` function allows an application to query the limits of each SM via device properties. Note that there are limits per SM and per thread block.

应用程序可以通过 `cudaGetDeviceProperties` 返回的 device property，查询各个 SM 的资源限制。注意，这些限制既有以 SM 为单位的，也有以 thread block 为单位的。

- > `maxBlocksPerMultiProcessor`: The maximum number of resident blocks per SM.

  `maxBlocksPerMultiProcessor`：每个 SM 可同时驻留的 block 数量上限。

- > `sharedMemPerMultiprocessor`: The amount of shared memory available per SM in bytes.

  `sharedMemPerMultiprocessor`：每个 SM 可用的 shared memory 字节数。

- > `regsPerMultiprocessor`: The number of 32-bit registers available per SM.

  `regsPerMultiprocessor`：每个 SM 可用的 32 位寄存器数量。

- > `maxThreadsPerMultiProcessor`: The maximum number of resident threads per SM.

  `maxThreadsPerMultiProcessor`：每个 SM 可同时驻留的线程数量上限。

- > `sharedMemPerBlock`: The maximum amount of shared memory that can be allocated by a thread block in bytes.

  `sharedMemPerBlock`：单个 thread block 可以分配的 shared memory 字节数上限。

- > `regsPerBlock`: The maximum number of 32-bit registers that can be allocated by a thread block.

  `regsPerBlock`：单个 thread block 可以分配的 32 位寄存器数量上限。

- > `maxThreadsPerBlock`: The maximum number of threads per thread block.

  `maxThreadsPerBlock`：单个 thread block 的线程数量上限。

> The occupancy of a CUDA kernel is the ratio of the number of active warps to the maximum number of active warps supported by the SM. In general, it’s a good practice to have occupancy as high as possible which hides latency and increases performance.

CUDA kernel 的 occupancy（占用率），是活跃 warp 数量与 SM 所支持的最大活跃 warp 数量之比。一般而言，尽可能提高 occupancy 是一种良好实践，有助于隐藏延迟并提高性能。

**解读：** Occupancy 描述驻留 warp 数量的比例，不是算术单元利用率、访存带宽利用率，也不是性能分数。更多驻留 warp 有助于在某些 warp 等待时安排其他工作，但限制寄存器、缩小 tile 或增加 spilling 都可能抵消收益。下面的百分比是按给定资源条件计算的驻留上限，不能当成所有 SM 在整个 kernel 执行期间都达到的实测值。

> To calculate occupancy, one needs to know the resource limits of the SM, which were just described, and one needs to know what resources are required by the CUDA kernel in question. To determine resource usage on a per kernel basis, during program compilation one can use the `--resource-usage` option to nvcc, which will show the number of registers and shared memory required by the kernel.

计算 occupancy，需要知道前面介绍的 SM 资源上限，以及目标 kernel 的资源需求。编译时可以给 `nvcc` 添加 `--resource-usage` 选项，查看每个 kernel 所需的寄存器和 shared memory。

作为示例，考虑一个 compute capability 为 10.0 的 device，其属性如表 2 所列。

> If a kernel was launched as `testKernel<<<512, 768>>>()`, i.e., 768 threads per block, each SM would only be able to execute 2 thread blocks at a time. The scheduler cannot assign more than 2 thread blocks per SM because the `maxThreadsPerMultiProcessor` is 2048. So the occupancy would be (768 * 2) / 2048, or 75%.

如果以 `testKernel<<<512, 768>>>()` 启动 kernel，即每个 block 包含 768 个线程，那么每个 SM 同时只能执行两个 block。由于 `maxThreadsPerMultiProcessor` 为 2048，调度器不能在一个 SM 上再放入第三个 block。因此 occupancy 为 `(768 × 2) / 2048`，即 75%。

> If a kernel was launched as `testKernel<<<512, 32>>>()`, i.e., 32 threads per block, each SM would not run into a limit on `maxThreadsPerMultiProcessor`, but since the `maxBlocksPerMultiProcessor` is 32, the scheduler would only be able to assign 32 thread blocks to each SM. Since the number of threads in the block is 32, the total number of threads resident on the SM would be 32 blocks * 32 threads per block, or 1024 total threads. Since a compute capability 10.0 SM has a maximum value of 2048 resident threads per SM, the occupancy in this case is 1024 / 2048, or 50%.

如果以 `testKernel<<<512, 32>>>()` 启动 kernel，即每个 block 包含 32 个线程，那么每个 SM 尚未触及 `maxThreadsPerMultiProcessor` 限制，就会先触及 `maxBlocksPerMultiProcessor = 32` 的限制。因此，每个 SM 最多只能分配 32 个 block，驻留线程总数为 32 个 block × 每个 block 的 32 个线程 = 1024 个线程。Compute capability 10.0 的 SM 最多支持 2048 个驻留线程，因此此时 occupancy 为 `1024 / 2048`，即 50%。

**解读：** 这两个结果都假定寄存器、shared memory 等其他限制没有更早生效，并且有足够的 block 可供调度。通用思路是分别计算线程数、block 数、寄存器和 shared memory 允许的驻留 block 数，再取最严格的限制；实际还受资源分配粒度和各架构约束影响。

> The same analysis can be done with shared memory. If a kernel uses 100KB of shared memory, for example, the scheduler would only be able to assign 2 thread blocks to each SM, because the third thread block on that SM would require another 100KB of shared memory for a total of 300KB, which is more than the 233472 bytes available per SM.

也可以对 shared memory 做同样的分析。例如，如果每个 kernel block 使用 100 KB shared memory，调度器最多只能为每个 SM 分配两个 block，因为第三个 block 还需要另外 100 KB，使总需求达到 300 KB，超过每个 SM 可用的 233472 字节。

**解读（遗漏前提）：** 表 2 给出的 `sharedMemPerBlock = 49152` 是 48 KiB，而本例每 block 需要 100 KB，已经超过该值。要使这个示例成立，需要设备支持更大的 opt-in 上限，使用动态 shared memory，并通过 `cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, ...)` 显式申请相应额度；还应查询 `sharedMemPerBlockOptin`。不能只检查每 SM 总容量。参见 [大于 48 KB 的 shared memory 分配要求](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html)。

> Threads per block and shared memory usage per block are explicitly controlled by the programmer and can be adjusted to achieve the desired occupancy. The programmer has limited control over register usage as the compiler and runtime will attempt to optimize register usage. However the programmer can specify a maximum number of registers per thread block via the `--maxrregcount` option to nvcc. If the kernel needs more registers than this specified amount, the kernel is likely to spill to local memory, which will change the performance characteristics of the kernel. In some cases even though spilling occurs, limiting registers allows more thread blocks to be scheduled which in turn increases occupancy and may result in a net increase in performance.

每个 block 的线程数量和 shared memory 使用量由程序员显式控制，可以据此调整 occupancy。程序员对寄存器使用的控制较为有限，因为编译器和 runtime 会尝试优化寄存器使用。不过，可以通过 `nvcc` 的 `--maxrregcount` 选项，指定每个 thread block 的寄存器数量上限。如果 kernel 所需的寄存器超过指定值，就可能 spill 到 local memory，从而改变性能特征。在某些情况下，即使发生 spilling，限制寄存器仍能让更多 block 被调度，提高 occupancy，并最终带来净性能收益。

**解读（原文勘误）：** 本段将 `--maxrregcount` 写成“每个 thread block”的寄存器上限，单位有误，应为“每个线程”。每个 block 的总寄存器需求还与线程数及硬件分配粒度有关。可结合编译器资源报告和实测运行时间评估是否获益，不应只追求更高 occupancy。参见 [CUDA C++ 每线程寄存器上限说明](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#maximum-number-of-registers-per-thread)。
