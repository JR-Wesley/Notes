### 3.2.1. Using PTX（使用 PTX）

> Parallel Thread Execution (PTX), the virtual machine instruction set architecture (ISA) that CUDA uses to abstract hardware ISAs, was introduced in Section 1.3.3. Writing code in PTX directly is a highly advanced optimization technique that is not necessary for most developers and should be considered a tool of last resort. Nevertheless, there are situations where the fine-grained control enabled by writing PTX directly enables performance improvements in specific applications. These situations are typically in very performance-sensitive portions of an application where every fraction of a percent of performance improvement has significant benefits. All of the available PTX instructions are in the PTX ISA document.

第 1.3.3 节介绍了 Parallel Thread Execution（PTX），它是 CUDA 用于抽象硬件 ISA 的虚拟机指令集架构。直接编写 PTX 是一种高度进阶的优化技术，大多数开发者并不需要，应将它作为最后才考虑的手段。不过，在某些特定应用中，直接编写 PTX 所提供的精细控制确实能够改善性能。这通常发生在对性能极其敏感的代码部分，哪怕不到一个百分点的提升也具有显著收益。全部可用的 PTX 指令均收录于 PTX ISA 文档。

**`cuda::ptx` namespace（`cuda::ptx` 命名空间）**

> One way to use PTX directly in your code is to use the `cuda::ptx` namespace from libcu++. This namespace provides C++ functions that map directly to PTX instructions, simplifying their use within a C++ application. For more information, please refer to the `cuda::ptx` namespace documentation.

在代码中直接使用 PTX 的一种方式，是使用 libcu++ 的 `cuda::ptx` 命名空间。它提供直接映射到 PTX 指令的 C++ 函数，简化了在 C++ 应用中使用这些指令的过程。更多信息参见 `cuda::ptx` namespace 文档。

**Inline PTX（内联 PTX）**

> Another way to include PTX in your code is to use inline PTX. This method is described in detail in the corresponding documentation. This is very similar to writing assembly code on a CPU.

另一种方式是使用 inline PTX（内联 PTX），对应文档对此有详细说明。这种方法与在 CPU 上编写汇编代码非常相似。

**解读：** PTX 是虚拟 ISA。使用 `cuda::ptx` 或 inline PTX 增加了对指令表达的控制，但不自动保证更高性能；仍需结合目标架构、实际生成代码与测量结果判断。对大多数 kernel，应先明确瓶颈，再决定是否需要深入到指令层面。

### 3.2.2. Hardware Implementation（硬件实现）

> A streaming multiprocessor or SM (see GPU Hardware Model) is designed to execute hundreds of threads concurrently. To manage such a large number of threads, it employs a unique parallel computing model called Single-Instruction, Multiple-Thread, or SIMT, that is described in SIMT Execution Model. The instructions are pipelined, leveraging instruction-level parallelism within a single thread, as well as extensive thread-level parallelism through simultaneous hardware multithreading as detailed in Hardware Multithreading. Unlike CPU cores, SMs issue instructions in order and do not perform branch prediction or speculative execution.

Streaming Multiprocessor（SM，参见 GPU Hardware Model）的设计目标是并发执行数百个 thread。为管理如此多的 thread，它采用名为 Single-Instruction, Multiple-Thread（SIMT，单指令多线程）的并行计算模型，详见 SIMT Execution Model。指令采用流水线执行，既利用单个 thread 内的 instruction-level parallelism（指令级并行），也通过同时硬件多线程利用大量 thread-level parallelism（线程级并行），详见 Hardware Multithreading。与 CPU core 不同，SM 按顺序发射指令，不进行分支预测或推测执行。

> Sections SIMT Execution Model and Hardware Multithreading describe the architectural features of the SM that are common to all devices. Section Compute Capabilities provides the specifics for devices of different compute capabilities.

SIMT Execution Model 和 Hardware Multithreading 两节介绍所有设备共有的 SM 架构特征。Compute Capabilities 一节则给出不同 compute capability 设备的具体参数。

> The NVIDIA GPU architecture uses a little-endian representation.

NVIDIA GPU 架构采用 little-endian（小端）表示。

#### 3.2.2.1. SIMT Execution Model（SIMT 执行模型）

> Each SM creates, manages, schedules, and executes threads in groups of 32 parallel threads called warps. Individual threads composing a warp start together at the same program address, but they have their own instruction address counter and register state and are therefore free to branch and execute independently. The term warp originates from weaving, the first parallel thread technology. A half-warp is either the first or second half of a warp. A quarter-warp is either the first, second, third, or fourth quarter of a warp.

每个 SM 以 warp 为单位创建、管理、调度和执行 thread；一个 warp 包含 32 个并行 thread。组成 warp 的各个 thread 从相同的程序地址一起开始执行，但具有各自的指令地址计数器和 register 状态，因此可以独立选择分支并执行。Warp 一词来自织布，这被原文比喻为最早的并行“线程”技术。Half-warp 指 warp 的前半部分或后半部分；quarter-warp 则指 warp 的第一、第二、第三或第四个四分之一。

> A warp executes one common instruction at a time, so full efficiency is realized when all 32 threads of a warp agree on their execution path. If threads of a warp diverge via a data-dependent conditional branch, the warp executes each branch path taken, disabling threads that are not on that path. Branch divergence occurs only within a warp; different warps execute independently regardless of whether they are executing common or disjoint code paths.

Warp 一次执行一条共同指令，因此当其中全部 32 个 thread 采用相同执行路径时，执行效率最高。如果 warp 中的 thread 因依赖数据的条件分支而发生分歧，warp 会分别执行被选择的各条分支路径，并禁用不属于当前路径的 thread。Branch divergence（分支分歧）只发生在 warp 内部；不同 warp 无论执行相同还是不同的代码路径，都各自独立执行。

> The SIMT architecture is akin to SIMD (Single Instruction, Multiple Data) vector organizations in that a single instruction controls multiple processing elements. A key difference is that SIMD vector organizations expose the SIMD width to the software, whereas SIMT instructions specify the execution and branching behavior of a single thread. In contrast with SIMD vector machines, SIMT enables programmers to write thread-level parallel code for independent, scalar threads, as well as data-parallel code for coordinated threads. For the purposes of correctness, the programmer can essentially ignore the SIMT behavior; however, substantial performance improvements can be realized by taking care that the code seldom requires threads in a warp to diverge. In practice, this is analogous to the role of cache lines: the cache line size can be safely ignored when designing for correctness but must be considered in the code structure when designing for peak performance. Vector architectures, on the other hand, require the software to coalesce loads into vectors and manage divergence manually.

SIMT 架构类似于 SIMD（Single Instruction, Multiple Data，单指令多数据）向量组织方式，因为二者都由一条指令控制多个处理单元。关键区别在于，SIMD 向量组织会向软件暴露 SIMD 宽度，而 SIMT 指令描述的是单个 thread 的执行与分支行为。与 SIMD 向量机相比，SIMT 既允许程序员为独立的标量 thread 编写线程级并行代码，也允许为相互协作的 thread 编写数据并行代码。从正确性角度，程序员基本可以忽略 SIMT 行为；但在编写代码时尽量减少 warp 内 thread 的分歧，可以显著改善性能。这与 cache line 的作用类似：设计正确程序时可以不考虑 cache line 大小，但追求峰值性能时必须在代码结构中考虑它。相比之下，向量架构要求软件将 load 合并为向量，并手动处理分歧。

**解读：** SIMT 的便利在于以单个 thread 的逻辑编程，而 warp 是执行和性能分析的重要单位。分歧主要降低同一次指令执行中有效参与的 thread 比例；不同 warp 分别走不同路径，并不构成同一 warp 内的分歧。“可以忽略 SIMT”也不适用于依赖 warp 内隐式同步的通信代码，下一节正是在补充这一边界。

##### 3.2.2.1.1. Independent Thread Scheduling（独立线程调度）

> On GPUs with compute capability lower than 7.0, warps used a single program counter shared amongst all 32 threads in the warp together with an active mask specifying the active threads of the warp. As a result, threads from the same warp in divergent regions or different states of execution cannot signal each other or exchange data, and algorithms requiring fine-grained sharing of data guarded by locks or mutexes can lead to deadlock, depending on which warp the contending threads come from.

在 compute capability 低于 7.0 的 GPU 上，一个 warp 的 32 个 thread 共享同一个 program counter，并通过 active mask 指明活动 thread。因此，同一 warp 中处于分歧区域或不同执行状态的 thread 无法相互传递信号或交换数据。使用 lock 或 mutex 保护细粒度数据共享的算法，可能因参与竞争的 thread 属于哪些 warp 而发生死锁。

> In GPUs of compute capability 7.0 and later, independent thread scheduling allows full concurrency between threads, regardless of warp. With independent thread scheduling, the GPU maintains execution state per thread, including a program counter and call stack, and can yield execution at a per-thread granularity, either to make better use of execution resources or to allow one thread to wait for data to be produced by another. A schedule optimizer determines how to group active threads from the same warp together into SIMT units. This retains the high throughput of SIMT execution as in prior NVIDIA GPUs, but with much more flexibility: threads can now diverge and reconverge at sub-warp granularity.

在 compute capability 7.0 及更高的 GPU 上，Independent Thread Scheduling（独立线程调度）允许 thread 之间充分并发，不再受原有 warp 限制。GPU 为每个 thread 维护执行状态，包括 program counter 和 call stack，并且可以在线程粒度让出执行，以更好地利用执行资源，或让某个 thread 等待另一个 thread 产生数据。调度优化器决定如何把同一 warp 的活动 thread 组合成 SIMT 执行单元。这保留了此前 NVIDIA GPU 的 SIMT 高吞吐能力，同时提供更高灵活性：thread 可以在 sub-warp（小于 warp）粒度上发生分歧并重新汇合。

> Independent thread scheduling can break code that relies on implicit warp-synchronous behavior from previous GPU architectures. Warp-synchronous code assumes that threads in the same warp execute in lockstep at every instruction, but the ability for threads to diverge and reconverge at sub-warp granularity makes such assumptions invalid. This can lead to a different set of threads participating in the executed code than intended. Any warp-synchronous code developed for GPUs prior to CC 7.0 (such as synchronization-free intra-warp reductions) should be revisited to ensure compatibility. Developers should explicitly synchronize such code using `__syncwarp()` to ensure correct behavior across all GPU generations.

Independent Thread Scheduling 可能破坏依赖旧 GPU 架构隐式 warp-synchronous 行为的代码。这类代码假设同一 warp 的 thread 在每条指令上都同步推进，而 sub-warp 粒度的分歧与汇合使这一假设不再成立，可能导致实际参与执行的 thread 集合与预期不同。为 CC 7.0 之前 GPU 编写的 warp-synchronous 代码，例如不使用同步的 warp 内 reduction，都应重新检查兼容性。开发者应使用 `__syncwarp()` 显式同步，确保代码在不同 GPU 世代上的正确行为。

**解读：** Independent Thread Scheduling 改变的是调度和汇合的灵活性，并没有取消 warp，也没有把每个 CUDA thread 变成资源无限、执行进度独立保证的 CPU thread。同一 warp 中存在数据交换时，必须明确参与线程集合与同步点，不能以“它们应该一起执行”证明正确性。

> Note: The threads of a warp that are participating in the current instruction are called the active threads, whereas threads not on the current instruction are inactive (disabled). Threads can be inactive for a variety of reasons including having exited earlier than other threads of their warp, having taken a different branch path than the branch path currently executed by the warp, or being the last threads of a block whose number of threads is not a multiple of the warp size.

注意：Warp 中参与当前指令执行的 thread 称为 active thread；不参与当前指令的 thread 则处于 inactive（禁用）状态。原因包括比同一 warp 的其他 thread 更早退出、选择了不同于当前执行路径的分支，或 block 的 thread 数不是 warp 大小的整数倍，导致最后一个 warp 存在未使用的位置。

> If a non-atomic instruction executed by a warp writes to the same location in global or shared memory from more than one of the threads of the warp, the number of serialized writes that occur to that location may vary depending on the compute capability of the device. However, for all compute capabilities, which thread performs the final write is undefined.

如果 warp 中多个 thread 通过非原子指令写入 global memory 或 shared memory 的同一位置，那么该位置实际发生的串行写入次数可能因 compute capability 而异。但在所有 compute capability 下，最终由哪个 thread 完成最后一次写入都是未定义的。

> If an atomic instruction executed by a warp reads, modifies, and writes to the same location in global memory for more than one of the threads of the warp, each read/modify/write to that location occurs and they are all serialized, but the order in which they occur is undefined.

如果 warp 中多个 thread 通过原子指令对 global memory 的同一位置执行 read-modify-write，那么每个 read-modify-write 都会发生，且这些操作会串行化，但它们发生的先后顺序未定义。

**解读：** 多个非原子写入竞争同一地址，不能通过假定某个 lane 总是最后写入来获得确定结果。原子 read-modify-write 则保证每次更新都发生，但仍不保证 thread 的先后顺序；需要有序结果的算法必须另外建立顺序。

Thread Hierarchy describes how thread IDs relate to thread indices in the block.

> The execution context (program counters, registers, etc.) for each warp processed by an SM is maintained on-chip throughout the warp’s lifetime. Therefore, switching between warps incurs no cost. At each instruction issue cycle, a warp scheduler selects a warp with threads ready to execute its next instruction (the active threads of the warp) and issues the instruction to those threads.

SM 处理的每个 warp 的执行上下文，包括 program counter、register 等，在该 warp 的整个生命周期中都保存在芯片上。因此，在 warp 之间切换不产生上下文切换成本。每个指令发射周期，warp scheduler 会选择一个其 thread 已准备好执行下一条指令的 warp，并向这些 thread，即该 warp 的 active thread，发射指令。

> Each SM has a set of 32-bit registers that are partitioned among the warps, and a shared memory that is partitioned among the thread blocks. The number of blocks and warps that can reside and be processed concurrently on the SM for a given kernel depends on the amount of registers and shared memory used by the kernel, as well as the amount of registers and shared memory available on the SM. There are also a maximum number of resident blocks and warps per SM. These limits, as well the amount of registers and shared memory available on the SM, depend on the compute capability of the device and are specified in Compute Capabilities. If there are not enough resources available per SM to process at least one block, the kernel will fail to launch. The total number of registers and shared memory allocated for a block can be determined in several ways documented in the Occupancy section.

每个 SM 都具有一组 32 位 register，分配给各个 warp；还具有 shared memory，分配给各个 thread block。对某个 kernel 而言，能够同时驻留和被处理的 block、warp 数量，取决于 kernel 使用的 register 和 shared memory 数量，以及 SM 上这些资源的可用量。每个 SM 还具有 resident block 和 resident warp 数量上限。这些限制以及 register、shared memory 容量均取决于设备的 compute capability，具体见 Compute Capabilities。如果每个 SM 的可用资源连一个 block 都无法容纳，kernel 启动就会失败。Occupancy 一节说明了确定每个 block 分配的 register 和 shared memory 总量的多种方法。

**解读：** Warp 上下文常驻片上，省去的是像软件线程切换那样保存、恢复上下文的过程，不表示访存和调度没有延迟。隐藏延迟还需要有准备就绪的其他 warp。增加每个 block 的 register 或 shared memory 用量，可能减少可同时驻留的 block；因此 block 数、资源用量和延迟隐藏能力需要一起分析。

#### 3.2.2.3. Asynchronous Execution Features（异步执行功能）

> Recent NVIDIA GPU generations have included asynchronous execution capabilities to allow more overlap of data movement, computation, and synchronization within the GPU. These capabilities enable certain operations invoked from GPU code to execute asynchronously to other GPU code in the same thread block. This asynchronous execution should not be confused with asynchronous CUDA APIs discussed in Section 2.5, which enable GPU kernel launches or memory operations to operate asynchronously to each other or to the CPU.

近几代 NVIDIA GPU 加入了异步执行能力，以增加 GPU 内部数据移动、计算和同步之间的重叠。这些能力使 GPU 代码发起的某些操作，能够相对于同一 thread block 中的其他 GPU 代码异步执行。它不同于第 2.5 节介绍的异步 CUDA API；后者让 GPU kernel 启动或内存操作相对于彼此或 CPU 异步执行。

> Compute capability 8.0 (The NVIDIA Ampere GPU Architecture) introduced hardware-accelerated asynchronous data copies from global to shared memory and asynchronous barriers (see NVIDIA A100 Tensor Core GPU Architecture ).

Compute capability 8.0，即 NVIDIA Ampere GPU 架构，引入了硬件加速的 global-to-shared 异步数据复制和 asynchronous barrier，参见 NVIDIA A100 Tensor Core GPU Architecture。

> Compute capability 9.0 (The NVIDIA Hopper GPU architecture) extended the asynchronous execution features with the Tensor Memory Accelerator (TMA) unit, which can transfer large blocks of data and multidimensional tensors from global memory to shared memory and vice versa, asynchronous transaction barriers, and asynchronous matrix multiply-accumulate operations (see Hopper Architecture in Depth blog post for details.).

Compute capability 9.0，即 NVIDIA Hopper GPU 架构，进一步扩展了异步执行功能，包括 Tensor Memory Accelerator（TMA）单元、asynchronous transaction barrier，以及异步矩阵乘加操作。TMA 可以在 global memory 与 shared memory 之间双向传输大块数据和多维 tensor。更多细节参见 Hopper Architecture in Depth 博客文章。

> CUDA provides APIs which can be called by threads from device code to use these features. The asynchronous programming model defines the behavior of asynchronous operations with respect to CUDA threads.

CUDA 提供可以从 device code 中由 thread 调用的 API，以使用这些功能。Asynchronous programming model 定义了异步操作相对于 CUDA thread 的行为。

> An asynchronous operation is an operation initiated by a CUDA thread, but executed asynchronously as if by another thread, which we will refer to as an async thread. In a well-formed program, one or more CUDA threads synchronize with the asynchronous operation. The CUDA thread that initiated the asynchronous operation is not required to be among the synchronizing threads. The async thread is always associated with the CUDA thread that initiated the operation.

异步操作由一个 CUDA thread 发起，但其执行如同由另一个 thread 异步完成，这个假想 thread 称为 async thread。在结构正确的程序中，一个或多个 CUDA thread 会与该异步操作同步；发起异步操作的 CUDA thread 不必属于这些同步 thread。Async thread 始终与发起操作的 CUDA thread 相关联。

> An asynchronous operation uses a synchronization object to signal its completion, which could be a barrier or a pipeline. These synchronization objects are explained in detail in Advanced Synchronization Primitives, and their role in performing asynchronous memory operations is demonstrated in Asynchronous Data Copies.

异步操作通过 synchronization object 表示完成，该对象可以是 barrier 或 pipeline。Advanced Synchronization Primitives 一节详细介绍这些对象；Asynchronous Data Copies 一节则展示它们在异步内存操作中的作用。

**解读：** Async thread 是描述异步操作行为的模型，不表示程序员额外启动了一个普通 CUDA thread。发起操作的 thread、等待完成的 thread 和负责执行数据移动的硬件可以不同；关键是消费数据之前有正确的完成通知与同步。

##### 3.2.2.3.1. Async Thread and Async Proxy（Async Thread 与 Async Proxy）

> Asynchronous operations may access memory differently than regular operations. To distinguish between these different memory access methods, CUDA introduces the concepts of an async thread, a generic proxy, and an async proxy. Normal operations (loads and stores) go through the generic proxy. Some asynchronous instructions, such as LDGSTS and STAS/REDAS, are modeled using an async thread operating in the generic proxy. Other asynchronous instructions, such as bulk-asynchronous copies with TMA and some tensor core operations (`tcgen05.*`, `wgmma.mma_async.*`), are modeled using an async thread operating in the async proxy.

异步操作访问内存的方式可能与普通操作不同。为区分这些访问方式，CUDA 引入了 async thread、generic proxy 和 async proxy。普通 load、store 通过 generic proxy 访问内存。某些异步指令，例如 LDGSTS 和 STAS/REDAS，被建模为在 generic proxy 中执行的 async thread；另外一些异步指令，例如 TMA bulk-asynchronous copy 和部分 Tensor Core 操作（`tcgen05.*`、`wgmma.mma_async.*`），则被建模为在 async proxy 中执行的 async thread。

> Async thread operating in generic proxy. When an asynchronous operation is initiated, it is associated with an async thread, which is different from the CUDA thread that initiated the operation. Preceding generic proxy (normal) loads and stores to the same address are guaranteed to be ordered before the asynchronous operation. However, subsequent normal loads and stores to the same address are not guaranteed to maintain their ordering, potentially incurring a race condition until the async thread completes.

在 generic proxy 中执行的 async thread：异步操作发起后，会关联到一个不同于发起者 CUDA thread 的 async thread。此前对同一地址的 generic proxy 普通 load、store，保证排在该异步操作之前；但之后对同一地址的普通 load、store 不保证维持顺序，因此在 async thread 完成前可能产生 race condition（竞争条件）。

> Async thread operating in async proxy. When an asynchronous operation is initiated, it is associated with an async thread, which is different from the CUDA thread that initiated the operation. Prior and subsequent normal loads and stores to the same address are not guaranteed to maintain their ordering. A proxy fence is required to synchronize them across the different proxies to ensure proper memory ordering. Section Using the Tensor Memory Accelerator (TMA) demonstrates use of proxy fences to ensure correctness when performing asynchronous copies with TMA.

在 async proxy 中执行的 async thread：异步操作发起后，也会关联到不同于发起者的 async thread。此前和之后对同一地址的普通 load、store 都不保证维持顺序。需要使用 proxy fence 在不同 proxy 之间建立同步，确保正确的内存顺序。Using the Tensor Memory Accelerator（TMA）一节展示了如何在 TMA 异步复制中使用 proxy fence 保证正确性。

> For more details on these concepts, see the PTX ISA documentation.

关于这些概念的更多细节，参见 PTX ISA 文档。

**解读：** Async thread 描述“谁在异步推进”，proxy 描述“通过哪种内存访问机制观察数据”，两者不是同一概念。读写同一个地址时，程序文本中的先后关系未必能跨 proxy 建立所需顺序。完成等待与 proxy ordering 也应分别满足，不能仅凭发出了 proxy fence 就认定复制已完成。

### 3.2.3. Thread Scopes（线程作用域）

> CUDA threads form a Thread Hierarchy, and using this hierarchy is essential for writing both correct and performant CUDA kernels. Within this hierarchy, the visibility and synchronization scope of memory operations can vary. To account for this non-uniformity, the CUDA programming model introduces the concept of thread scopes. A thread scope defines which threads can observe a thread’s loads and stores and specifies which threads can synchronize with each other using synchronization primitives such as atomic operations and barriers. Each scope has an associated point of coherency in the memory hierarchy.

CUDA thread 构成 Thread Hierarchy（线程层级），利用这一层级是编写正确且高性能 kernel 的关键。不同层级中，内存操作的可见性和同步范围可能不同。为描述这种差异，CUDA programming model 引入 thread scope。Thread scope 定义哪些 thread 能观察到某个 thread 的 load、store，并规定哪些 thread 可以通过 atomic operation、barrier 等同步原语相互同步。每个 scope 在内存层级中都有对应的 point of coherency（一致性点）。

> Thread scopes are exposed in CUDA PTX and are also available as extensions in the libcu++ library. The following table defines the thread scopes available:

CUDA PTX 暴露了 thread scope，libcu++ 也通过扩展提供它们。下表定义了可用的 thread scope：

> | CUDA C++ Thread Scope | CUDA PTX Thread Scope | Description | Point of Coherency in Memory Hierarchy |
> | --- | --- | --- | --- |
> | `cuda::thread_scope_thread` |  | Memory operations are visible only to the local thread. | – |
> | `cuda::thread_scope_block` | `.cta` | Memory operations are visible to other threads in the same thread block. | L1 |
> |  | `.cluster` | Memory operations are visible to other threads in the same thread block cluster. | L2 |
> | `cuda::thread_scope_device` | `.gpu` | Memory operations are visible to other threads in the same GPU device. | L2 |
> | `cuda::thread_scope_system` | `.sys` | Memory operations are visible to other threads in the same system (CPU, other GPUs). | L2 + connected caches |

| CUDA C++ Thread Scope | CUDA PTX Thread Scope | 说明 | 内存层级中的一致性点 |
| --- | --- | --- | --- |
| `cuda::thread_scope_thread` |  | 内存操作仅对当前 thread 可见。 | – |
| `cuda::thread_scope_block` | `.cta` | 内存操作对同一 thread block 内的其他 thread 可见。 | L1 |
|  | `.cluster` | 内存操作对同一 thread block cluster 内的其他 thread 可见。 | L2 |
| `cuda::thread_scope_device` | `.gpu` | 内存操作对同一 GPU device 上的其他 thread 可见。 | L2 |
| `cuda::thread_scope_system` | `.sys` | 内存操作对同一系统的其他 thread 可见，包括 CPU 和其他 GPU。 | L2 + 相连的 cache |

**解读（表格边界）：** Scope 表示同步或原子保证涵盖哪些参与者，不会改变指针指向的地址空间，也不会把 block 的 shared memory 变成 CPU 可访问的内存。表中的 L1、L2 是概括性的硬件对应，不能据此把某个 scope 理解为“自动刷新所有缓存”。Cluster 的 C++ 单元格按原文留空；这不代表所有库版本都缺少该 scope，所查 [CCCL 文档](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/synchronization_primitives/atomic.html)已列出 `cuda::thread_scope_cluster`，实际使用应匹配安装版本。

> Sections Advanced Synchronization Primitives and Asynchronous Data Copies demonstrate use of thread scopes.

Advanced Synchronization Primitives 和 Asynchronous Data Copies 两节展示了 thread scope 的用法。

### 3.2.4. Advanced Synchronization Primitives（高级同步原语）

> This section introduces three families of synchronization primitives:

本节介绍三类同步原语：

- > Scoped Atomics, which pair C++ memory ordering with CUDA thread scopes to safely communicate across threads at block, cluster, device, or system scope (see Thread Scopes).

  Scoped Atomic：将 C++ memory ordering 与 CUDA thread scope 配合使用，在 block、cluster、device 或 system 范围内安全地进行线程间通信，参见 Thread Scopes。

- > Asynchronous Barriers, which split synchronization into arrival and wait phases, and can be used to track the progress of asynchronous operations.

  Asynchronous Barrier：将同步拆分为 arrival 和 wait 两个阶段，也可用于跟踪异步操作的进度。

- > Pipelines, which stage work and coordinate multi-buffer producer–consumer patterns, commonly used to overlap compute with asynchronous data copies.

  Pipeline：将工作划分为 stage，并协调使用多个 buffer 的 producer-consumer 模式，常用于让计算与异步数据复制重叠。

#### 3.2.4.1. Scoped Atomics（带作用域的原子操作）

> Section 5.4.5 gives an overview of atomic functions available in CUDA. In this section, we will focus on scoped atomics that support C++ standard atomic memory semantics, available through the libcu++ library or through compiler built-in functions. Scoped atomics provide the tools for efficient synchronization at the appropriate level of the CUDA thread hierarchy, enabling both correctness and performance in complex parallel algorithms.

第 5.4.5 节概述了 CUDA 提供的 atomic function。本节重点讨论支持 C++ 标准原子内存语义的 scoped atomic，它们可以通过 libcu++ 或编译器内建函数使用。Scoped atomic 使开发者能够在 CUDA 线程层级中的合适范围高效同步，兼顾复杂并行算法的正确性和性能。

##### 3.2.4.1.1. Thread Scope and Memory Ordering（线程作用域与内存顺序）

> Scoped atomics combine two key concepts:

Scoped atomic 结合了两个关键概念：

- > Thread Scope: defines which threads can observe the effect of the atomic operation (see Thread Scopes).

  Thread Scope：定义哪些 thread 能观察到原子操作的效果，参见 Thread Scopes。

- > Memory Ordering: defines the ordering constraints relative to other memory operations (see C++ standard atomic memory semantics).

  Memory Ordering：定义相对于其他内存操作的顺序约束，参见 C++ standard atomic memory semantics。

**解读：** Scope 回答“和哪些 thread 建立保证”，memory order 回答“本操作与其他读写之间有什么顺序保证”。扩大 scope 不会自动增强 ordering，使用 acquire/release 也不会自动扩大参与范围。本次仅提供了 `cuda::atomic` 实现，网页中其他代码标签已作为界面文字清理。

```cpp
#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // Shared atomic counter visible only within this block
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

    // Initialize counter (only one thread should do this)
    if (threadIdx.x == 0) {
        counter.store(0, cuda::memory_order_relaxed);
    }
    __syncthreads();

    // All threads in block atomically increment
    int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

    // Use old_value...
}
```

> This example implements a block-scoped atomic counter that demonstrates the fundamental concepts of scoped atomics:

本例实现了 block scope 的原子计数器，展示 scoped atomic 的基本概念：

- > Shared Variable: a single counter is shared among all threads in the block using `__shared__` memory.

  Shared Variable：通过 `__shared__` memory，让 block 内所有 thread 共享同一个计数器。

- > Atomic Type Declaration: `cuda::atomic<int, cuda::thread_scope_block>` creates an atomic integer with block-level visibility.

  Atomic Type Declaration：`cuda::atomic<int, cuda::thread_scope_block>` 创建一个具有 block 范围可见性的原子整数。

- > Single Initialization: only thread 0 initializes the counter to prevent race conditions during setup.

  Single Initialization：只有 thread 0 初始化计数器，避免初始化阶段的竞争。

- > Block Synchronization: `__syncthreads()` ensures all threads see the initialized counter before proceeding.

  Block Synchronization：`__syncthreads()` 确保所有 thread 在继续执行前都能看到初始化后的计数器。

- > Atomic Increment: each thread atomically increments the counter and receives the previous value.

  Atomic Increment：每个 thread 原子地递增计数器，并获得递增之前的值。

> `cuda::memory_order_relaxed` is chosen here because we only need atomicity (indivisible read-modify-write) without ordering constraints between different memory locations. Since this is a straightforward counting operation, the order of increments doesn’t matter for correctness.

这里选择 `cuda::memory_order_relaxed`，因为只需要 atomicity，即不可分割的 read-modify-write，而不需要对不同内存位置之间的访问施加顺序约束。由于这是简单计数操作，递增次序不影响正确性。

**解读（计数器示例）：** 在一维 block 且每个 thread 恰好递增一次的前提下，`old_value` 会分配出互不重复的计数值，但哪个 thread 得到哪个值不确定。`threadIdx.x == 0` 只在一维 block 中唯一；多维 block 应改用完整的唯一 thread 判定。这里 `relaxed` 适用于计数本身，不能据此发布与计数器无关的数据。若后面由某个 thread 汇总最终计数，还要保证所有递增已经完成。

> For producer-consumer patterns, acquire-release semantics ensure proper ordering:

对于 producer-consumer 模式，acquire-release 语义确保正确的顺序：

```cpp
__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

    if (threadIdx.x == 0) {
        // Producer: write data then signal ready
        data = 42;
        ready.store(true, cuda::memory_order_release);  // Release ensures data write is visible
    } else {
        // Consumer: wait for ready signal then read data
        while (!ready.load(cuda::memory_order_acquire)) {  // Acquire ensures data read sees the write
            // spin wait
        }
        int value = data;
        // Process value...
    }
}
```

**解读（原文示例缺口）：** 本例未显式初始化 `ready` 为 `false`，也没有在 producer/consumer 分流前建立初始化完成的 block 同步；不能把未说明的 shared atomic 初始状态当作有效的“尚未就绪”标志。应按所用库的对象初始化规则完成初始化，再让参与者进入通信过程。`threadIdx.x == 0` 的单 producer 假设同样要求一维 block，或改用唯一的 thread 判定。

在初始化和参与条件成立后，关键关系是：producer 先写 `data`，再 release-store `ready=true`；consumer 的 acquire-load 读到这次发布的值后，才读取 `data`。这种顺序连接起两个不同内存位置，单纯把 `ready` 做成原子变量但全部用 relaxed，并不能得到同样的发布保证。自旋等待还需考虑目标架构的调度与前进条件。

##### 3.2.4.1.2. Performance Considerations（性能考虑）

- > Use the narrowest scope possible: block-scoped atomics are much faster than system-scoped atomics.

  使用满足需求的最小 scope：block scope 原子操作比 system scope 原子操作快得多。

- > Prefer weaker orderings: use stronger orderings only when necessary for correctness.

  优先选择较弱的 ordering：只有正确性确实需要时才使用更强的 ordering。

- > Consider memory location: shared memory atomics are faster than global memory atomics.

  考虑内存位置：shared memory 原子操作比 global memory 原子操作更快。

**解读：** 三条建议都以正确性允许为前提，性能比较也依赖架构、竞争程度和访问模式。不能为了缩小 scope 排除真实参与者，也不能在需要发布其他数据时删除 acquire/release。Shared 与 global atomic 的速度关系应通过具体 workload 测量，不能理解为所有情况下的固定排序。

#### 3.2.4.2. Asynchronous Barriers（异步 Barrier）

> An asynchronous barrier differs from a typical single-stage barrier (`__syncthreads()`) in that the notification by a thread that it has reached the barrier (the “arrival”) is separated from the operation of waiting for other threads to arrive at the barrier (the “wait”). This separation increases execution efficiency by allowing a thread to perform additional operations unrelated to the barrier, making more efficient use of the wait time. Asynchronous barriers can be used to implement producer-consumer patterns with CUDA threads or enable asynchronous data copies within the memory hierarchy by having the copy operation signal (“arrive on”) a barrier upon completion.

Asynchronous barrier 与 `__syncthreads()` 这样的典型单阶段 barrier 不同：thread 通知自己已到达 barrier 的 arrival 操作，与等待其他 thread 到达的 wait 操作相互分离。这样，thread 可以在等待期间执行与 barrier 无关的其他操作，更有效地利用这段时间。Asynchronous barrier 可以实现 CUDA thread 之间的 producer-consumer 模式，也可以用于内存层级内的异步数据复制：复制完成时，由复制操作向 barrier 发出完成信号，即 arrive on barrier。

> Asynchronous barriers are available on devices of compute capability 7.0 or higher. Devices of compute capability 8.0 or higher provide hardware acceleration for asynchronous barriers in shared-memory and a significant advancement in synchronization granularity, by allowing hardware-accelerated synchronization of any subset of CUDA threads within the block. Previous architectures only accelerate synchronization at a whole-warp (`__syncwarp()`) or whole-block (`__syncthreads()`) level.

Compute capability 7.0 及更高的设备支持 asynchronous barrier。Compute capability 8.0 及更高的设备为 shared memory 中的 asynchronous barrier 提供硬件加速，并显著细化同步粒度：block 内任意 thread 子集都可以获得硬件加速的同步。此前架构仅在整个 warp（`__syncwarp()`）或整个 block（`__syncthreads()`）层级提供硬件加速同步。

> The CUDA programming model provides asynchronous barriers via `cuda::std::barrier`, an ISO C++-conforming barrier available in the libcu++ library. In addition to implementing `std::barrier`, the library offers CUDA-specific extensions to select a barrier’s thread scope to improve performance and exposes a lower-level `cuda::ptx` API. A `cuda::barrier` can interoperate with `cuda::ptx` by using the friend function `cuda::device::barrier_native_handle()` to retrieve the barrier’s native handle and pass it to `cuda::ptx` functions. CUDA also provides a primitives API for asynchronous barriers in shared memory at thread-block scope.

CUDA programming model 通过 libcu++ 中符合 ISO C++ 标准的 `cuda::std::barrier` 提供 asynchronous barrier。除了实现 `std::barrier`，库还提供 CUDA 专用扩展，允许选择 barrier 的 thread scope 来改善性能，并提供更底层的 `cuda::ptx` API。`cuda::barrier` 可以通过友元函数 `cuda::device::barrier_native_handle()` 获取 native handle，并将其传给 `cuda::ptx` 函数，从而与 `cuda::ptx` 互操作。CUDA 还为位于 shared memory、具有 thread block scope 的 asynchronous barrier 提供 primitives API。

> The following table gives an overview of asynchronous barriers available for synchronizing at different thread scopes.

下表概述了不同 thread scope 下可用于同步的 asynchronous barrier。

> | Thread Scope | Memory Location | Arrive on Barrier | Wait on Barrier | Hardware-accelerated | CUDA APIs |
> | --- | --- | --- | --- | --- | --- |
> | block | local shared memory | allowed | allowed | yes (8.0+) | `cuda::barrier`, `cuda::ptx`, primitives |
> | cluster | local shared memory | allowed | allowed | yes (9.0+) | `cuda::barrier`, `cuda::ptx` |
> | cluster | remote shared memory | allowed | not allowed | yes (9.0+) | `cuda::barrier`, `cuda::ptx` |
> | device | global memory | allowed | allowed | no | `cuda::barrier` |
> | system | global/unified memory | allowed | allowed | no | `cuda::barrier` |

| 线程作用域 | 内存位置 | 对 Barrier 执行 Arrive | 对 Barrier 执行 Wait | 硬件加速 | CUDA API |
| --- | --- | --- | --- | --- | --- |
| block | 本 block 的 shared memory | 允许 | 允许 | 支持（8.0+） | `cuda::barrier`、`cuda::ptx`、primitives |
| cluster | 本 block 的 shared memory | 允许 | 允许 | 支持（9.0+） | `cuda::barrier`、`cuda::ptx` |
| cluster | 远端 block 的 shared memory | 允许 | 不允许 | 支持（9.0+） | `cuda::barrier`、`cuda::ptx` |
| device | global memory | 允许 | 允许 | 不支持 | `cuda::barrier` |
| system | global/unified memory | 允许 | 允许 | 不支持 | `cuda::barrier` |

**解读：** 表中的 local/remote shared memory 以执行操作的 block 为参照。对 cluster 内远端 block 的 barrier 可以 arrive，不表示也能在远端地址上 wait；设计跨 block 协作时，必须把 signal 与 wait 各自放到允许的位置。Device/system scope 则描述参与范围，并不自动保证所有参与 thread 同时获得执行资源。

**Temporal Splitting of Synchronization（在时间上拆分同步）**

> Without the asynchronous arrive-wait barriers, synchronization within a thread block is achieved using `__syncthreads()` or `block.sync()` when using Cooperative Groups.

不使用异步 arrive-wait barrier 时，thread block 内的同步通过 `__syncthreads()` 实现，或者在使用 Cooperative Groups 时通过 `block.sync()` 实现。

```cpp
#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

    for (int i = 0; i < iteration_count; ++i) {
        /* code before arrive */

         // Wait for all threads to arrive here.
        block.sync();

        /* code after wait */
    }
}
```

> Threads are blocked at the synchronization point (`block.sync()`) until all threads have reached the synchronization point. In addition, memory updates that happened before the synchronization point are guaranteed to be visible to all threads in the block after the synchronization point.

Thread 会阻塞在同步点 `block.sync()`，直到所有 thread 都到达该点。此外，同步点之前发生的内存更新，保证在同步点之后对 block 内所有 thread 可见。

> This pattern has three stages:

这种模式分为三个阶段：

- > Code before the sync performs memory updates that will be read after the sync.

  同步之前的代码更新内存，这些更新将在同步之后被读取。

- > Synchronization point.

  同步点。

- > Code after the sync, with visibility of memory updates that happened before the sync.

  同步之后的代码可以看到同步之前发生的内存更新。

> Using asynchronous barriers instead, the temporally-split synchronization pattern is as follows.

改用 asynchronous barrier 后，在时间上拆分同步的模式如下。

```cpp
#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

  if (block.thread_rank() == 0)
  {
    // Initialize barrier with expected arrival count.
    init(&bar, block.size());
  }
  block.sync();

  for (int i = 0; i < iteration_count; ++i)
  {
    /* code before arrive */

    // This thread arrives. Arrival does not block a thread.
    barrier_t::arrival_token token = bar.arrive();

    compute(data, i);

    // Wait for all threads participating in the barrier to complete bar.arrive().
    bar.wait(std::move(token));

    /* code after wait */
  }
}
```

**解读（初始化与参与条件）：** `init(&bar, block.size())` 将预期到达次数设为 block 的 thread 数，随后的 `block.sync()` 确保其他 thread 使用 barrier 前初始化已完成。循环要求参与者按约定到达每个 phase；少到达或错误重复到达都会破坏协议。`compute` 只有声明，原文没有提供其实现，不能把这个片段视为独立可运行程序。

> In this pattern, the synchronization point is split into an arrive point (`bar.arrive()`) and a wait point (`bar.wait(std::move(token))`). A thread begins participating in a `cuda::barrier` with its first call to `bar.arrive()`. When a thread calls `bar.wait(std::move(token))` it will be blocked until participating threads have completed `bar.arrive()` the expected number of times, which is the expected arrival count argument passed to `init()`. Memory updates that happen before participating threads’ call to `bar.arrive()` are guaranteed to be visible to participating threads after their call to `bar.wait(std::move(token))`. Note that the call to `bar.arrive()` does not block a thread, it can proceed with other work that does not depend upon memory updates that happen before other participating threads’ call to `bar.arrive()`.

在这种模式中，同步点拆分为 arrive point，即 `bar.arrive()`，以及 wait point，即 `bar.wait(std::move(token))`。Thread 第一次调用 `bar.arrive()` 时开始参与 `cuda::barrier`。调用 `bar.wait(std::move(token))` 后，thread 会阻塞，直到参与者累计完成了预期次数的 `bar.arrive()`；这个次数由传给 `init()` 的 expected arrival count 决定。参与 thread 调用 `bar.arrive()` 之前发生的内存更新，保证在参与 thread 的 `bar.wait(std::move(token))` 返回后可见。注意，`bar.arrive()` 不会阻塞 thread，它可以继续做其他工作，只要这些工作不依赖其他参与者 arrive 之前的内存更新。

**解读：** `arrive()` 与 `wait()` 之间只能放不依赖本轮其他参与者发布数据的工作。`wait()` 等待的是相应 phase 的完成，不是要求其他 thread 都已经调用了 `wait()`。尤其要注意：其他 thread 在 arrive 之后执行的 `compute(data, i)`，不因本轮 wait 返回就自动全部完成；如果下一步依赖这些结果，还需要另一个正确的同步关系。

> The arrive and wait pattern has five stages:

Arrive-wait 模式分为五个阶段：

- > Code before the arrive performs memory updates that will be read after the wait.

  Arrive 之前的代码更新内存，这些更新将在 wait 之后被读取。

- > Arrive point with implicit memory fence (i.e., equivalent to `cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)`).

  带有隐式 memory fence 的 arrive point；原文称其等价于 `cuda::atomic_thread_fence(cuda::memory_order_seq_cst, cuda::thread_scope_block)`。

**解读（内存顺序限定）：** 原文将 arrive 类比为 `seq_cst` fence，不能因此推断所有 barrier 和独立原子操作之间建立了同一个全局顺序。严格推理应依据 barrier 的 phase、completion 和 happens-before 保证；独立的 fence 也不能替代到达计数及等待。参见 [C++ barrier 规范](https://eel.is/c++draft/thread.barrier.class)和 [cuda::barrier 语义](https://nvidia.github.io/cccl/unstable/libcudacxx/extended_api/synchronization_primitives/barrier.html)。

- > Code between arrive and wait.

  Arrive 与 wait 之间的代码。

- > Wait point.

  Wait point。

- > Code after the wait, with visibility of updates that were performed before the arrive.

  Wait 之后的代码可以看到 arrive 之前执行的内存更新。

> For a comprehensive guide on how to use asynchronous barriers, see Asynchronous Barriers.

关于 asynchronous barrier 的完整用法，参见 Asynchronous Barriers。

#### 3.2.4.3. Pipelines（Pipeline）

> The CUDA programming model provides the pipeline synchronization object as a coordination mechanism to sequence asynchronous memory copies into multiple stages, facilitating the implementation of double- or multi-buffering producer-consumer patterns. A pipeline is a double-ended queue with a head and a tail that processes work in a first-in first-out (FIFO) order. Producer threads commit work to the pipeline’s head, while consumer threads pull work from the pipeline’s tail.

CUDA programming model 提供 pipeline 同步对象，将异步内存复制组织为多个 stage，便于实现双 buffer 或多 buffer 的 producer-consumer 模式。Pipeline 是具有 head 和 tail 的双端队列，按 FIFO（先进先出）顺序处理工作。Producer thread 向 head 提交工作，consumer thread 从 tail 取出工作。

> Pipelines are exposed through the `cuda::pipeline` API in the libcu++ library, as well as through a primitives API. The following tables describe the main functionality of the two APIs.

Pipeline 可以通过 libcu++ 的 `cuda::pipeline` API 或 primitives API 使用。以下表格介绍这两套 API 的主要功能。

> | `cuda::pipeline` API | Description |
> | --- | --- |
> | `producer_acquire` | Acquires an available stage in the pipeline’s internal queue. |
> | `producer_commit` | Commits the asynchronous operations issued after the `producer_acquire` call on the currently acquired stage of the pipeline. |
> | `consumer_wait` | Waits for completion of asynchronous operations in the oldest stage of the pipeline. |
> | `consumer_release` | Releases the oldest stage of the pipeline to the pipeline object for reuse. The released stage can be then acquired by a producer. |

| `cuda::pipeline` API | 说明 |
| --- | --- |
| `producer_acquire` | 获取 pipeline 内部队列中一个可用的 stage。 |
| `producer_commit` | 提交当前已获取 stage 上，在 `producer_acquire` 之后发起的异步操作。 |
| `consumer_wait` | 等待 pipeline 中最早 stage 的异步操作完成。 |
| `consumer_release` | 将最早的 stage 释放回 pipeline 以供复用，producer 随后可以重新获取它。 |

**解读：** `producer_acquire` 表示 stage 可供生产者使用，`producer_commit` 提交工作；`consumer_wait` 表示消费者等待数据准备好，`consumer_release` 则表示消费者已用完这个 stage，可以复用。数据已经复制完成与 buffer 已经可以被覆盖，是两个不同的条件。

> | Primitives API | Description |
> | --- | --- |
> | `__pipeline_memcpy_async` | Request a memory copy from global to shared memory to be submitted for asynchronous evaluation. |
> | `__pipeline_commit` | Commits the asynchronous operations issued before the call on the current stage of the pipeline. |
> | `__pipeline_wait_prior(N)` | Waits for completion of asynchronous operations in all but the last N commits to the pipeline. |

| Primitives API | 说明 |
| --- | --- |
| `__pipeline_memcpy_async` | 请求提交从 global memory 到 shared memory 的复制，以异步方式执行。 |
| `__pipeline_commit` | 提交当前 pipeline stage 上在本调用之前发起的异步操作。 |
| `__pipeline_wait_prior(N)` | 等待除最近 N 次 commit 外，其余已提交异步操作全部完成。 |

**解读：** `__pipeline_wait_prior(N)` 等待较早的提交，仅允许最近 N 次提交仍在进行；N 不是“等待前 N 次”的意思。取 N=0 时，等待此前已提交的全部操作。Thread scope 的完成等待也不能直接替代其他 thread 消费共享数据时所需的协作同步。

> The `cuda::pipeline` API has a richer interface with less restrictions, while the primitives API only supports tracking asynchronous copies from global memory to shared memory with specific size and alignment requirements. The primitives API provides equivalent functionality to a `cuda::pipeline` object with `cuda::thread_scope_thread`.

`cuda::pipeline` API 的接口更丰富、限制更少；primitives API 则只支持跟踪满足特定大小和对齐要求的 global-to-shared 异步复制。Primitives API 的功能等价于具有 `cuda::thread_scope_thread` 的 `cuda::pipeline` 对象。

> For detailed usage patterns and examples, see Pipelines.

详细的使用模式和示例见 Pipelines。

### 3.2.5. Asynchronous Data Copies（异步数据复制）

> Efficient data movement within the memory hierarchy is fundamental to achieving high performance in GPU computing. Traditional synchronous memory operations force threads to wait idle during data transfers. GPUs inherently hide memory latency through parallelism. That is, the SM switches to execute another warp while memory operations complete. Even with this latency hiding through parallelism, it is still possible for memory latency to be a bottleneck on both memory bandwidth utilization and compute resource efficiency. To address these bottlenecks, modern GPU architectures provide hardware-accelerated asynchronous data copy mechanisms that allow memory transfers to proceed independently while threads continue executing other work.

在内存层级中高效移动数据，是 GPU 高性能计算的基础。传统同步内存操作会使 thread 在数据传输期间等待。GPU 本身可以借助并行隐藏内存延迟：等待内存操作完成期间，SM 切换去执行另一个 warp。即便如此，内存延迟仍可能限制内存带宽利用率和计算资源效率。为解决这些瓶颈，现代 GPU 提供硬件加速的异步数据复制，让内存传输独立进行，同时 thread 继续执行其他工作。

> Asynchronous data copies enable overlapping of computation with data movement, by decoupling the initiation of a memory transfer from waiting for its completion. This way, threads can perform useful work during memory latency periods, leading to improved overall throughput and resource utilization.

异步数据复制将“发起传输”与“等待完成”分离，使计算能够与数据移动重叠。Thread 可以在内存访问延迟期间执行有用工作，从而改善整体吞吐量和资源利用率。

> Note: While concepts and principles underlying this section are similar to those discussed in the earlier chapter on Asynchronous Execution, that chapter covered asynchronous execution of kernels and memory transfers such as those invoked by `cudaMemcpyAsync`. That can be considered asynchrony of different components of the application.

注意：本节的概念和原理与前面的 Asynchronous Execution 章节相似，但前者介绍的是 kernel 与内存传输操作之间的异步执行，例如通过 `cudaMemcpyAsync` 发起的操作，可以将它理解为应用不同组成部分之间的异步。

> The asynchrony described in this section refers to enabling transfer of data between the GPU’s DRAM, i.e. global memory, and on-SM memory such as shared memory or tensor memory without blocking the GPU threads. This is an asynchrony within the execution of a single kernel launch.

本节讨论的异步，是指在不阻塞 GPU thread 的情况下，在 GPU DRAM（即 global memory）与 SM 内存（例如 shared memory 或 tensor memory）之间传输数据，属于单次 kernel 执行内部的异步。

**解读：** 此处讨论 kernel 内部的数据移动，不是再调用一次 host 侧 `cudaMemcpyAsync`。具体可用的数据路径由指令和架构决定，不能把对 DRAM、shared memory、tensor memory 的概述理解为任意两种内存之间都支持直接异步复制。

> To understand how asynchronous copies can improve performance, it is helpful to examine a common GPU computing pattern. CUDA applications often employ a copy and compute pattern that:

要理解异步复制如何改善性能，可以先看一种常见 GPU 计算模式。CUDA 应用经常采用 copy-and-compute 模式：

- > fetches data from global memory,

  从 global memory 读取数据。

- > stores data to shared memory, and

  将数据存入 shared memory。

- > performs computations on shared memory data, and potentially writes results back to global memory.

  使用 shared memory 中的数据计算，并可能将结果写回 global memory。

> The copy phase of this pattern is typically expressed as `shared[local_idx] = global[global_idx]`. This global to shared memory copy is expanded by the compiler to a read from global memory into a register followed by a write to shared memory from the register.

该模式的复制阶段通常写成 `shared[local_idx] = global[global_idx]`。编译器将这种 global-to-shared 复制展开为：先从 global memory 读入 register，再将 register 中的值写入 shared memory。

> When this pattern occurs within an iterative algorithm, each thread block needs to synchronize after the `shared[local_idx] = global[global_idx]` assignment, to ensure all writes to shared memory have completed before the compute phase can begin. The thread block also needs to synchronize again after the compute phase, to prevent overwriting shared memory before all threads have completed their computations. This pattern is illustrated in the following code snippet.

在迭代算法中采用这种模式时，每个 thread block 都需要在 `shared[local_idx] = global[global_idx]` 赋值之后同步，确保所有 shared memory 写入完成后再开始计算。计算结束后也需要再次同步，防止其他 thread 尚未完成计算时就覆盖 shared memory。下面的代码片段展示了这一模式。

```cpp
#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;
    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

    // Wait for all copies to complete.
    block.sync();

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}
```

**解读（两次同步与示例前提）：** 第一次 `block.sync()` 保证数据已全部写入 shared memory，第二次保证所有消费者都用完当前 batch，之后才允许复用同一 buffer。两次同步分别保护“读之前写完”和“覆盖之前读完”。

原例通过 `block.group_index().x` 和 `threadIdx.x` 索引数据，隐含一维 grid/block；`grid.size()` 是 grid 中的总 thread 数，`batch_sz` 在这里是批次数。启动时还必须按注释提供 `block.size() * sizeof(int)` 字节的 dynamic shared memory。`compute` 为空实现，代码没有 host 启动部分，因而尚不执行实际计算。

> With asynchronous data copies, data movement from global memory to shared memory can be done asynchronously to enable more efficient use of the SM while waiting for data to arrive.

采用异步数据复制后，可以异步执行 global-to-shared 数据移动，让 SM 在等待数据到达时得到更有效的利用。

```cpp
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // Computes using all values of current batch from shared memory.
    // Stores this thread's result back to global memory.
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {
  auto grid = cooperative_groups::this_grid();
  auto block = cooperative_groups::this_thread_block();
  assert(size == batch_sz * grid.size()); // Exposition: input size fits batch_sz * grid_size

  extern __shared__ int shared[]; // block.size() * sizeof(int) bytes

  size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // Compute the index of the current batch for this block in global memory.
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // Whole thread-group cooperatively copies whole batch to shared memory.
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

    // Compute on different data while waiting.

    // Wait for all copies to complete.
    cooperative_groups::wait(block);

    // Compute and write result to global memory.
    compute(global_out + block_batch_idx, shared);

    // Wait for compute using shared memory to finish.
    block.sync();
  }
}
```

> The `cooperative_groups::memcpy_async` function copies `block.size()` elements from global memory to the shared data. This operation happens as-if performed by another thread, which synchronizes with the current thread’s call to `cooperative_groups::wait` after the copy has completed. Until the copy operation completes, modifying the global data or reading or writing the shared data introduces a data race.

`cooperative_groups::memcpy_async` 从 global memory 向 shared data 复制 `block.size()` 个元素。该操作如同由另一个 thread 执行，复制完成后，通过当前 thread 调用 `cooperative_groups::wait` 与之同步。在复制完成之前，修改 global data，或读取、写入 shared data，都会引入 data race。

**解读（原文代码勘误）：** 示例调用的是四参数 `cooperative_groups::memcpy_async(group, dst, src, shape)`，其 `shape` 单位是字节。因此，要复制 `block.size()` 个 `int`，最后一个参数应为 `sizeof(int) * block.size()`；原例只传 `block.size()`，与正文所称元素数量不符。使用 source/destination 两个 layout 的另一种重载才按元素计数。参见 [Cooperative Groups API 定义](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/device-callable-apis.html)。

保留原代码以便对照。修正长度后，`cooperative_groups::wait(block)` 用于等待复制完成，而末尾的 `block.sync()` 仍用于避免过早复用 buffer。示例中“等待时计算其他数据”仅有注释，尚未实现真正的重叠计算；两份示例中的同名 `compute` 定义也不应直接重复放进同一编译单元。

> This example illustrates the fundamental concept behind all asynchronous copy operations: they decouple memory transfer initiation from completion, allowing threads to perform other work while data moves in the background. The CUDA programming model provides several APIs to access these capabilities, including memcpy_async functions available in Cooperative Groups and the libcu++ library, as well as lower-level `cuda::ptx` and primitives APIs. These APIs share similar semantics: they copy objects from source to destination as-if performed by another thread which, on completion of the copy, can be synchronized using different completion mechanisms.

该示例展示了所有异步复制操作背后的基本思想：将内存传输的发起与完成分离，使 thread 能够在后台数据移动期间执行其他工作。CUDA 提供多种 API 使用这些能力，包括 Cooperative Groups 和 libcu++ 的 memcpy_async 函数，以及更底层的 `cuda::ptx` 和 primitives API。这些 API 具有相似语义：像由另一个 thread 完成一样，将对象从 source 复制到 destination，并在复制完成后通过不同的完成机制进行同步。

> Modern GPU architectures provide multiple hardware mechanisms for asynchronous data movement.

现代 GPU 架构为异步数据移动提供多种硬件机制。

- > LDGSTS (compute capability 8.0+) allows for efficient small-scale asynchronous transfers from global to shared memory.

  LDGSTS（compute capability 8.0+）支持高效的小规模 global-to-shared 异步传输。

- > The tensor memory accelerator (TMA, compute capability 9.0+) extends these capabilities, providing bulk-asynchronous copy operations optimized for large multi-dimensional data transfers

  Tensor Memory Accelerator（TMA，compute capability 9.0+）进一步扩展这些能力，提供针对大规模多维数据传输优化的 bulk-asynchronous copy。

- > STAS instructions (compute capability 9.0+) enable small-scale asynchronous transfers from registers to distributed shared memory within a cluster.

  STAS 指令（compute capability 9.0+）支持从 register 向同一 cluster 内 distributed shared memory 进行小规模异步传输。

> These mechanisms support different data paths, transfer sizes, and alignment requirements, allowing developers to choose the most appropriate approach for their specific data access patterns. The following table gives an overview of the supported data paths for asynchronous copies within the GPU.

这些机制支持不同的数据路径、传输大小和对齐要求，开发者可以根据具体访问模式选择合适的方法。下表概述了 GPU 内部异步复制支持的数据路径。

表 5：异步复制可采用的 source 和 destination memory space。空白单元格表示不支持对应的 source-destination 组合。

### 3.2.6. Configuring L1/Shared Memory Balance（配置 L1 与 Shared Memory 的容量平衡）

> As mentioned in L1 data cache, the L1 and shared memory on an SM use the same physical resource, known as the unified data cache. On most architectures, if a kernel uses little or no shared memory, the unified data cache can be configured to provide the maximal amount of L1 cache allowed by the architecture.

如 L1 data cache 一节所述，SM 上的 L1 与 shared memory 使用同一物理资源，称为 unified data cache。在大多数架构上，如果 kernel 很少或完全不使用 shared memory，可以配置 unified data cache，使 L1 cache 获得该架构允许的最大容量。

> The unified data cache reserved for shared memory is configurable on a per-kernel basis. An application can set the carveout, or preferred shared memory capacity, with the `cudaFuncSetAttribute` function called before the kernel is launched.

Unified data cache 中为 shared memory 保留的部分，可以按 kernel 配置。应用可以在启动 kernel 之前调用 `cudaFuncSetAttribute`，设置 carveout，即 preferred shared memory capacity（优选 shared memory 容量）。

```cpp
cudaFuncSetAttribute(kernel_name, cudaFuncAttributePreferredSharedMemoryCarveout, carveout);
```

> The application can set the carveout as an integer percentage of the maximum supported shared memory capacity of that architecture. In addition to an integer percentage, three convenience enums are provided as carveout values.

应用可以将 carveout 设为该架构最大受支持 shared memory 容量的整数百分比。除了整数百分比，还提供三个便利的枚举值：

- > `cudaSharedmemCarveoutDefault`

  `cudaSharedmemCarveoutDefault`：默认划分。

- > `cudaSharedmemCarveoutMaxL1`

  `cudaSharedmemCarveoutMaxL1`：优先使用最大的 L1 容量。

- > `cudaSharedmemCarveoutMaxShared`

  `cudaSharedmemCarveoutMaxShared`：优先使用最大的 shared memory 容量。

> The maximum supported shared memory and the supported carveout sizes vary by architecture; see Shared Memory Capacity per Compute Capability for details.

最大 shared memory 容量和支持的 carveout 大小因架构而异，详见 Shared Memory Capacity per Compute Capability。

> Where a chosen integer percentage carveout does not map exactly to a supported shared memory capacity, the next larger capacity is used. For example, for devices of compute capability 12.0, which have a maximum shared memory capacity of 100KB, setting the carveout to 50% will result in 64KB of shared memory, not 50KB, because devices of compute capability 12.0 support shared memory sizes of 0, 8, 16, 32, 64, and 100.

如果指定的整数百分比不能恰好对应某个支持的 shared memory 容量，就采用下一个更大的支持容量。例如，compute capability 12.0 设备的最大 shared memory 容量为 100 KB，将 carveout 设为 50% 后，实际对应 64 KB，而非 50 KB，因为该架构支持的 shared memory 容量档位为 0、8、16、32、64 和 100 KB。

> The function passed to `cudaFuncSetAttribute` must be declared with the `__global__` specifier. `cudaFuncSetAttribute` is interpreted by the driver as a hint, and the driver may choose a different carveout size if required to execute the kernel.

传给 `cudaFuncSetAttribute` 的函数必须用 `__global__` 限定符声明。驱动将这里的 `cudaFuncSetAttribute` 设置解释为 hint；如果执行 kernel 需要，驱动可以选择不同的 carveout 大小。

**解读：** Carveout 配置的是 SM 共享物理资源中 shared memory 与 L1 的容量划分偏好，不是给某个 block 分配的字节数。设置 50% 时还会落到架构支持的离散容量档位。后面设置 dynamic shared memory 上限以及启动时申请多少字节，是另两个相关但不同的步骤。

> Note: Another CUDA API, `cudaFuncSetCacheConfig`, also allows an application to adjust the balance between L1 and shared memory for a kernel. However, this API set a hard requirements on shared/L1 balance for kernel launch. As a result, interleaving kernels with different shared memory configurations would needlessly serialize launches behind shared memory reconfigurations. `cudaFuncSetAttribute` is preferred because driver may choose a different configuration if required to execute the function or to avoid thrashing.

注意：另一个 CUDA API `cudaFuncSetCacheConfig` 也允许应用调整某个 kernel 的 L1 与 shared memory 容量平衡。不过，原文称这个 API 对启动时的 shared/L1 配置施加硬性要求。因此，交错执行采用不同 shared memory 配置的 kernel，会因反复重新配置而不必要地使 launch 串行化。更推荐使用 `cudaFuncSetAttribute`，因为驱动可以在执行函数所需或为避免频繁切换配置时选择不同的配置。

**解读（原文限定）：** 当前 Runtime API 明确将 `cudaFuncSetCacheConfig` 定义为 preference，必要时可采用其他配置，并非绝对的硬性要求。不过，切换配置偏好确实可能插入 device 侧同步。这里保留原文，并以 [Runtime API 的明确语义](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__EXECUTION.html)补充限定。

> Kernels relying on shared memory allocations over 48 KB per block are architecture-specific. As such they must use dynamic shared memory rather than statically-sized arrays and require an explicit opt-in using `cudaFuncSetAttribute` as follows.

每个 block 依赖超过 48 KB shared memory 的 kernel 具有架构特定性。因此必须使用 dynamic shared memory，而非静态大小的数组，并按如下方式通过 `cudaFuncSetAttribute` 显式启用。

```cpp
// Device code
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// Host code
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);
MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
```

**解读：** `cudaFuncAttributeMaxDynamicSharedMemorySize` 用于显式设置 kernel 允许申请的 dynamic shared memory 上限；启动语法中的第三个参数才是本次每个 block 的实际申请量。设置成功仍取决于设备与 kernel 的资源限制，不能认为任意 GPU 都能使用 96 KB。原例包含 `...` 占位，需要补齐代码并检查 API、launch 返回情况。本次只整理与静态核对，未编译或运行 CUDA 示例。
