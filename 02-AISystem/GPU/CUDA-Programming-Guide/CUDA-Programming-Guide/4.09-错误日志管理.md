## 4.9. Error Log Management（错误日志管理）

来源：[CUDA Programming Guide — Error Log Management](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/error-log-management.html)。

> Error log management allows CUDA API errors to be reported in plain English, providing more information about the cause of an error than the API’s return value alone.

Error log management（错误日志管理）让 CUDA API 错误以易读的英文描述呈现，比单独查看 API 返回值提供更多关于错误原因的信息。

### 4.9.1. Background（背景）

> Traditionally, the only indication of a failed CUDA API call is a non-zero return code. Many CUDA error codes describe a category of failure without identifying which argument or requirement caused it. Error log management supplements those return codes with descriptive messages intended to help developers diagnose API usage errors.

传统上，CUDA API 调用失败仅通过非零返回码表示。许多 CUDA 错误码只说明失败类别，并不指出具体是哪个参数或哪项要求导致了错误。Error log management 在返回码之外提供描述性消息，帮助开发者诊断 API 使用错误。

**解读：** 错误码用于判断调用是否成功，描述性日志帮助定位失败原因。后文说明部分 API 尚未生成此类消息，因此日志应与返回码一起使用；没有日志并不能证明调用成功。

### 4.9.2. Activation（启用）

> Set the `CUDA_LOG_FILE` environment variable to `stdout`, `stderr`, or a path to a writable file. CUDA writes each generated log message to the selected destination.

将环境变量 `CUDA_LOG_FILE` 设为 `stdout`、`stderr` 或可写文件的路径。CUDA 会把每条生成的日志消息写入所选目标。

> CUDA also stores recent messages in an internal `buffer`. Applications can use the error log management APIs to register a callback or dump this `buffer` even if `CUDA_LOG_FILE` was not set before the application started. An error-free execution might not generate any messages.

CUDA 也会把近期消息保存在内部 buffer 中。即使应用启动前没有设置 `CUDA_LOG_FILE`，仍可通过错误日志管理 API 注册 callback，或导出该 buffer。没有发生错误的一次执行可能不会生成任何消息。

**解读：** `CUDA_LOG_FILE` 决定自动写出的目标；即使未设置它，应用仍可使用 callback 和内部 buffer 的 dump API。内部 buffer 只保留近期消息，需要查看较早日志时，不能把它当作完整执行记录。

### 4.9.3. Output（输出）

> Messages written to `CUDA_LOG_FILE` or returned by the dump APIs use the following format:

写入 `CUDA_LOG_FILE` 或由 dump API 返回的消息采用以下格式：

```text
[Time][TID][Source][Severity] Message
```

> For example, calling `cuLogsDumpToMemory` with a null `buffer` can generate messages similar to the following:

例如，向 `cuLogsDumpToMemory` 传入空 buffer 指针，可能生成类似下面的消息：

```text
[22:21:32.099][25642][CUDA][E] buffer cannot be NULL
[22:21:32.099][25642][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLogsDumpToMemory
```

> Without error log management, the call returns `CUDA_ERROR_INVALID_VALUE`. Calling `cuGetErrorString` provides the generic description invalid argument, but not which argument was invalid.

没有错误日志管理时，该调用返回 `CUDA_ERROR_INVALID_VALUE`。调用 `cuGetErrorString` 只能获得通用描述 `invalid argument`（无效参数），无法得知具体哪个参数无效。

**解读：** 示例中，`invalid argument` 只给出错误类别；日志中的 `buffer cannot be NULL` 则指出具体违反了 buffer 非空要求。`[Time]`、`[TID]`、`[Source]`、`[Severity]` 分别对应时间、线程 ID、来源与严重级别。

### 4.9.4. API description（API 说明）

> Error log management is available through both the CUDA Driver and Runtime APIs. The Runtime interface operates on messages generated by both the Runtime and Driver APIs; both interfaces use the same underlying log `buffer`.

CUDA Driver API 和 Runtime API 都提供错误日志管理功能。Runtime 接口可以处理 Runtime API 与 Driver API 生成的消息；两套接口使用同一个底层日志 buffer。

#### 4.9.4.1. Callback registration（注册 Callback）

> The Driver API callback type and registration functions are:

Driver API 的 callback 类型与注册函数如下：

```cpp
typedef void (CUDA_CB *CUlogsCallback)(
    void *data, CUlogLevel logLevel, char *message, size_t length);

CUresult CUDAAPI cuLogsRegisterCallback(
    CUlogsCallback callbackFunc,
    void *userData,
    CUlogsCallbackHandle *callback_out);

CUresult CUDAAPI cuLogsUnregisterCallback(
    CUlogsCallbackHandle callback);
```

> The corresponding Runtime API callback type and functions are:

对应的 Runtime API callback 类型与函数如下：

```cpp
typedef void (CUDART_CB *cudaLogsCallback_t)(
    void *data, cudaLogLevel logLevel, char *message, size_t length);

cudaError_t CUDARTAPI cudaLogsRegisterCallback(
    cudaLogsCallback_t callbackFunc,
    void *userData,
    cudaLogsCallbackHandle *callback_out);

cudaError_t CUDARTAPI cudaLogsUnregisterCallback(
    cudaLogsCallbackHandle callback);
```

> The Driver callback reports errors as `CU_LOG_LEVEL_ERROR` and warnings as `CU_LOG_LEVEL_WARNING`. The corresponding Runtime values are `cudaLogLevelError` and `cudaLogLevelWarning`. Formatted output represents these levels as E and W, respectively.

Driver callback 使用 `CU_LOG_LEVEL_ERROR` 表示错误、`CU_LOG_LEVEL_WARNING` 表示警告；对应的 Runtime 值分别为 `cudaLogLevelError` 和 `cudaLogLevelWarning`。格式化输出分别用 `E` 和 `W` 表示这两个级别。

> CUDA passes `userData` to the callback without modification. The `callback_out` argument is optional, but an application must retain the returned handle if it intends to unregister the callback.

CUDA 将 `userData` 原样传给 callback。`callback_out` 参数是可选的，但如果应用打算取消 callback 注册，就必须保存返回的 handle。

> The callback receives the message text and its explicit byte length. The message does not include the timestamp, thread ID, source, or severity prefix added to formatted file and dump output. Applications should not rely on a particular callback thread or invocation timing unless the API reference explicitly guarantees that behavior.

Callback 接收消息正文及其明确的字节长度。正文不包含格式化文件输出和 dump 输出附加的时间戳、线程 ID、来源或严重级别前缀。除非 API 参考文档明确保证，否则应用不应依赖 callback 在某个特定线程或特定时机被调用。

**解读：** Callback 收到的是消息正文和字节长度，处理时应使用 `length`，不要假设正文自带文件输出中的前缀。需要取消注册时应保留 handle；callback 的线程与调用时机也应按 API 文档的保证处理。

#### 4.9.4.2. Iterators and log dumps（Iterator 与日志导出）

> A log `iterator` identifies a position in the internal `buffer`. Calling `cuLogsCurrent` or `cudaLogsCurrent` sets an `iterator` to the current end of the `buffer`, so a later dump using that `iterator` returns only subsequently generated messages.

Log iterator 标识内部 buffer 中的一个位置。调用 `cuLogsCurrent` 或 `cudaLogsCurrent`，会把 iterator 设到 buffer 当前末尾；之后使用该 iterator 导出日志，只返回此后生成的消息。

> The Driver API functions are:

Driver API 函数如下：

```cpp
CUresult CUDAAPI cuLogsCurrent(
    CUlogIterator *iterator_out, unsigned int flags);

CUresult CUDAAPI cuLogsDumpToFile(
    CUlogIterator *iterator,
    const char *pathToFile,
    unsigned int flags);

CUresult CUDAAPI cuLogsDumpToMemory(
    CUlogIterator *iterator,
    char *buffer,
    size_t *size,
    unsigned int flags);
```

> The corresponding Runtime API functions are:

对应的 Runtime API 函数如下：

```cpp
cudaError_t CUDARTAPI cudaLogsCurrent(
    cudaLogIterator *iterator_out, unsigned int flags);

cudaError_t CUDARTAPI cudaLogsDumpToFile(
    cudaLogIterator *iterator,
    const char *pathToFile,
    unsigned int flags);

cudaError_t CUDARTAPI cudaLogsDumpToMemory(
    cudaLogIterator *iterator,
    char *buffer,
    size_t *size,
    unsigned int flags);
```

> The `flags` argument to all current and dump functions is reserved for future use and must be zero.

所有 current 和 dump 函数的 `flags` 参数均保留供未来使用，必须设为零。

> The following Runtime API example marks the current end of the log and later dumps only messages generated after that point:

下面的 Runtime API 示例先标记日志当前末尾，之后只导出该位置以后生成的消息：

```cpp
#include <cstdio>
#include <cuda_runtime_api.h>

cudaError_t printNewCudaLogs()
{
    cudaLogIterator iterator;
    cudaError_t status = cudaLogsCurrent(&iterator, 0);
    if (status != cudaSuccess) {
        return status;
    }

    int deviceCount;
    status = cudaGetDeviceCount(&deviceCount);
    cudaError_t deviceCountStatus = status;

    char buffer[25600];
    size_t size = sizeof(buffer);
    status = cudaLogsDumpToMemory(&iterator, buffer, &size, 0);
    if (status != cudaSuccess) {
        return status;
    }
    if (size != 0) {
        std::fwrite(buffer, 1, size, stderr);
    }
    return deviceCountStatus;
}
```

> The intervening CUDA call still requires normal return-code handling. This example demonstrates how the `iterator` selects a window of log messages; it does not require deliberately making an invalid CUDA call. The fixed-size array uses the maximum documented dump capacity of 25,600 bytes.

位于标记与导出操作之间的 CUDA 调用，仍须正常处理返回码。此示例展示 iterator 如何选择一段日志消息，并不要求故意执行无效的 CUDA 调用。固定大小数组采用文档规定的最大 dump 容量：25,600 字节。

**解读：** 示例先保存 `deviceCountStatus`，避免后续 dump 调用覆盖被诊断 API 的返回值。dump 成功时，`std::fwrite` 按返回的 `size` 输出日志正文，最后返回设备查询的状态；若 dump 自身失败，示例直接返回 dump 错误。Iterator 选择的是 buffer 中的一段消息，不能仅凭它将日志认定为某一次调用专属。

#### 4.9.4.3. Dump behavior（导出行为）

> If `iterator` is null, a dump requests all entries currently retained in the internal `buffer`. If an `iterator` is supplied, the dump begins at that position. After a successful dump, CUDA advances the supplied `iterator` to the current end of the log.

如果 `iterator` 是空指针，dump 会请求内部 buffer 当前保留的全部条目；如果提供了 iterator，则从该位置开始导出。成功导出后，CUDA 会把所提供的 iterator 推进到日志当前末尾。

> The internal `buffer` retains at most 100 entries. If requested messages have been overwritten and are no longer retained, CUDA adds a notice indicating that the output was truncated and returns the entries that remain available.

内部 buffer 最多保留 100 条日志。如果请求的消息已被覆盖、不再保留，CUDA 会添加一条说明输出被截断的通知，并返回仍然可用的条目。

**解读：** 传入空 iterator 表示读取当前仍保留的全部条目；传入有效 iterator 则可逐段读取新增日志。成功 dump 会推进该 iterator，但原文没有将此操作定义为清空整个 buffer。已被 100 条容量上限覆盖的历史消息无法通过扩大输出 buffer 找回。

> `cuLogsDumpToMemory` and `cudaLogsDumpToMemory` have these additional requirements:

`cuLogsDumpToMemory` 和 `cudaLogsDumpToMemory` 还具有以下要求：

> 1. `size` initially specifies the capacity of `buffer`.
> 2. CUDA null-terminates the `buffer`. Individual entries are separated by newline characters rather than null characters.
> 3. A 25,600-byte output `buffer` is sufficient to hold all retained log data.
> 4. On success, `size` contains the number of bytes written, excluding the terminating null character.
> 5. If there are no messages to dump, the function succeeds and sets `size` to zero.
> 6. If the `buffer` can hold some but not all requested messages, CUDA prepends a truncation notice, omits the oldest messages that do not fit, and retains the most recent message in the output.
> 7. If the `buffer` cannot hold any messages, the function returns `CUDA_ERROR_INVALID_VALUE` or `cudaErrorInvalidValue` and sets `size` to zero.

1. 调用前，`size` 指定 `buffer` 的容量。
2. CUDA 在 buffer 末尾添加空字符终止符。各条日志之间使用换行符分隔，而非空字符。
3. 25,600 字节的输出 buffer 足以容纳全部保留的日志数据。
4. 调用成功后，`size` 包含写入的字节数，不包括末尾的空字符终止符。
5. 如果没有消息可导出，函数调用成功，并将 `size` 设为零。
6. 如果 buffer 只能容纳部分请求的消息，CUDA 会在输出开头添加截断通知，省略放不下的最旧消息，并在输出中保留最新消息。
7. 如果 buffer 无法容纳任何消息，函数返回 `CUDA_ERROR_INVALID_VALUE` 或 `cudaErrorInvalidValue`，并将 `size` 设为零。

**解读：** 这里还有一类截断来自调用方输出 buffer 太小，与内部 buffer 覆盖旧条目不同。`size` 是输入输出参数，每次调用前应重新设置为可用容量；成功后它表示实际字节数。示例中的空 buffer 会报错，因此不能套用“先传空 buffer 查询所需长度”的常见用法。

### 4.9.5. Limitations and known issues（限制与已知问题）

> 1. When the 100-entry limit is reached, CUDA replaces the oldest entries.
> 2. Not all CUDA APIs generate descriptive messages yet. Coverage continues to expand.
> 3. CUDA does not validate a `CUDA_LOG_FILE` destination until a message is generated.
> 4. Log messages are not localized; CUDA provides them in US English.

1. 达到 100 条上限后，CUDA 会替换最旧的条目。
2. 目前并非所有 CUDA API 都会生成描述性消息，覆盖范围仍在扩大。
3. CUDA 只有在生成消息时，才会验证 `CUDA_LOG_FILE` 的输出目标。
4. 日志消息不提供本地化版本；CUDA 使用美式英语输出。

**解读：** 设置了 `CUDA_LOG_FILE` 却暂时没有输出，可能只是尚未生成消息；输出路径此时也可能尚未经过验证。诊断时仍应检查各 CUDA API 的返回值，并结合日志覆盖范围判断。
