CUDA C 编程里有两级并发：

> "Generally speaking, there are two levels of concurrency in CUDA C programming: Kernel level concurrency / Grid level concurrency"

- **Kernel-level（内核级）**：单个 kernel 由海量线程并行执行（Grid→Block→Thread），前几章已详述。
- **Grid-level（网格级）**：单个设备上**同时执行多个内核调用**（多个 stream 派发多个 kernel），通常提升设备利用率。

本章聚焦 **grid-level concurrency**，用 CUDA 流（stream）实现。流的本质：

> "A CUDA stream refers to a sequence of asynchronous CUDA operations that execute on a device in the order issued by the host code."

流是一串**异步 CUDA 操作**的队列，按主机下发顺序在设备上执行；同一流内严格有序、不同流之间无次序约束 → 多流并发即 grid-level concurrency。因为所有排队操作都是异步的，它们可与主机-设备系统中的其他操作重叠，从而**掩盖这些操作的时延**。典型 CUDA 三段式 `H2D → Kernel → D2H` 中，kernel 通常比传输慢，把 kernel 与传输放进不同流即可重叠、缩短总时长；流能在 **CUDA API 调用粒度**上实现流水线/双缓冲。

## 一、CUDA 流（Stream）

### 两类流：默认流 vs 非默认流

- **隐式流 / NULL 流（默认流）**：不显式指定流时，kernel 启动与数据传输都进默认流。前几章例子全用默认流。
- **显式流 / non-NULL 流**：显式创建与管理。**要做重叠，必须用 non-NULL 流。**

异步流可实现四类粗粒度并发：
- 重叠 主机计算 与 设备计算
- 重叠 主机计算 与 主机-设备数据传输
- 重叠 主机-设备数据传输 与 设备计算
- 并发的设备计算（多 kernel 同时跑）

默认流代码示例（全在默认流，按序执行）：

```c
cudaMemcpy(..., cudaMemcpyHostToDevice);   // 主机视角：同步，阻塞等待
kernel<<<grid, block>>>(...);              // 主机视角：异步，立即返回
cudaMemcpy(..., cudaMemcpyDeviceToHost);   // 同步
```

Kernel 启动默认异步 → 主机立即继续，天然可重叠设备与主机计算。

### 基础 API

```c
// 异步拷贝（第 5 参为流，默认 0=默认流）
cudaError_t cudaMemcpyAsync(void* dst, const void* src, size_t count,
                           cudaMemcpyKind kind, cudaStream_t stream = 0);
// 创建非默认流
cudaError_t cudaStreamCreate(cudaStream_t* pStream);
// 在指定流启动 kernel（第 4 参为流）
kernel_name<<<grid, block, sharedMemSize, stream>>>(argument list);
// 释放流（有未完成工作时立即返回，资源在全部完成后自动释放）
cudaError_t cudaStreamDestroy(cudaStream_t stream);
// 等待流中所有操作完成 / 非阻塞查询
cudaError_t cudaStreamSynchronize(cudaStream_t stream);
cudaError_t cudaStreamQuery(cudaStream_t stream);   // cudaSuccess 或 cudaErrorNotReady
```

⚠️ **异步函数可能返回之前已启动的异步操作的错误码**——报错的 API 调用不一定是引发错误的调用。

### 异步拷贝要求 Pinned Memory

异步传输必须使用**锁页（pinned / non-pageable）主机内存**，否则 OS 可能在传输途中物理移动数组 → 未定义行为：

```c
cudaError_t cudaMallocHost(void** ptr, size_t size);
cudaError_t cudaHostAlloc(void** pHost, size_t size, unsigned int flags);
```

### 多流并发代码模式

```c
for (int i = 0; i < nStreams; i++) {
    int offset = i * bytesPerStream;
    cudaMemcpyAsync(&d_a[offset], &a[offset], bytePerStream, streams[i]);
    kernel<<<grid, block, 0, streams[i]>>>(&d_a[offset]);
    cudaMemcpyAsync(&a[offset], &d_a[offset], bytesPerStream, streams[i]);
}
for (int i = 0; i < nStreams; i++) cudaStreamSynchronize(streams[i]);
```

> **Figure 6-1 启示**：即便在不同流里，H2D 数据传输也**不会并发**——因为它们争用同一个共享硬件资源：**PCIe 总线**。但**双向（duplex）PCIe 能重叠两个不同方向、不同流的传输**（一个流的 H2D 与另一流的 D2H 重叠）。

- 最大并发内核数因设备而异：**Fermi 支持 16-way，Kepler 支持 32-way**；并进一步受共享内存/寄存器等资源限制。

## 二、流调度：伪依赖、Hyper-Q、流优先级

### 伪依赖（False Dependencies，Fermi）

Fermi 虽支持 16-way 并发，但**所有流最终多路复用进单个硬件工作队列**。运行时从队首取任务、检查依赖、依赖满足才下发 SM。单个队列导致**伪依赖**：队列中被阻塞的任务会阻塞其后所有任务（即便属于不同流），只有"流边缘"处的任务对能并发（Figure 6-2）。

### Hyper-Q（Kepler）

> "Hyper-Q allows multiple CPU threads or processes to launch work on a single GPU simultaneously by maintaining multiple hardware-managed connections between the host and the device."

Kepler 用 **多个硬件工作队列（最多 32 个）** 消除伪依赖——每个流分配一个队列（>32 流时多流共享一队列才可能出现伪依赖）。受 Fermi 伪依赖拖累的旧程序**无需改代码即可显著提速**。Figure 6-3 展示三流三队列的完整流级并发。

### 流优先级（CC 3.5+）

```c
cudaError_t cudaStreamCreateWithPriority(cudaStream_t* pStream, unsigned int flags, int priority);
cudaError_t cudaDeviceGetStreamPriorityRange(int* leastPriority, int* greatestPriority);
```

- 高优先级流中的 grid 可**抢占**低优先级流中正在执行的 grid。
- **优先级只影响计算 kernel，不影响数据传输。**
- 整数越小优先级越高；超出范围自动 clamp。不支持时两参数返回 0。

## 三、CUDA 事件（Event）

事件 = 流中某点的标记（marker），用于：① 同步流执行；② 监控设备进度。事件在其**同流中前述所有操作完成后**才置为 satisfied；默认流上的事件对所有流的前述操作生效。

```c
cudaEvent_t event;
cudaEventCreate(&event);                       // 创建
cudaEventRecord(event, stream = 0);            // 在流中记录（异步）
cudaEventSynchronize(event);                   // 阻塞主机，等事件完成
cudaEventQuery(event);                         // 非阻塞查询
cudaEventElapsedTime(&ms, start, stop);        // 两事件间耗时（ms），可不同流
cudaEventDestroy(event);                       // 未完成时立即返回，完成后自动释放
```

⚠️ 若事件记录在 non-NULL 流，`cudaEventElapsedTime` 可能比预期大（记录本身是异步的，不保证只测两事件之间）。

**计时典型用法**（start/stop 默认放进 NULL 流，测 NULL 流首尾时间戳之差）：

```c
cudaEvent_t start, stop;
cudaEventCreate(&start); cudaEventCreate(&stop);
cudaEventRecord(start);
kernel<<<grid, block>>>(args);
cudaEventRecord(stop);
cudaEventSynchronize(stop);
float time; cudaEventElapsedTime(&time, start, stop);
cudaEventDestroy(start); cudaEventDestroy(stop);
```

## 四、流同步机制

### 阻塞流 vs 非阻塞流

- `cudaStreamCreate` 创建的是**阻塞流**：其操作可能被 NULL 流中更早的操作阻塞。
- NULL 流（隐式）与同一 CUDA context 内所有**阻塞流**同步：NULL 流的操作会等所有阻塞流先前操作完成；阻塞流的操作也会等 NULL 流先前操作完成。
- 例：`kernel_1`(stream_1) → `kernel_2`(NULL) → `kernel_3`(stream_2)：kernel_2 等 kernel_1，kernel_3 等 kernel_2（主机侧仍是异步非阻塞）。
- 用 `cudaStreamCreateWithFlags` 定制：`cudaStreamDefault`（阻塞）/ `cudaStreamNonBlocking`（非阻塞，禁用相对 NULL 流的阻塞行为）。

### 隐式同步 vs 显式同步

- **显式同步**：`cudaDeviceSynchronize` / `cudaStreamSynchronize` / `cudaEventSynchronize`——手动插入。
- **隐式同步**：函数主目的不是同步，但副作用会阻塞主机-设备。例如 `cudaMemcpy` 会等传输完成。

> ⚠️ 隐式同步尤其值得警惕：无意调用带隐式同步的函数会造成**非预期阻塞、性能下降**。

会**隐式阻塞当前设备所有先前操作**的函数包括：
- 锁页主机内存分配
- 设备内存分配
- 设备 memset
- 同一设备上两个地址间的内存拷贝
- 修改 L1/共享内存配置

### 显式同步的四种方式（grid 级）

| 粒度 | 函数 | 说明 |
|---|---|---|
| 设备 | `cudaDeviceSynchronize()` | 阻塞主机直到当前设备全部任务完成（重量级，少用） |
| 流 | `cudaStreamSynchronize` / `cudaStreamQuery` | 等流完成 / 非阻塞查询 |
| 事件 | `cudaEventSynchronize` / `cudaEventQuery` | 细粒度等事件 / 非阻塞查询 |
| 跨流 | `cudaStreamWaitEvent(stream, event)` | 让指定流等某事件后再执行后续操作（可跨流，Figure 6-4） |

### 可配置事件（cudaEventCreateWithFlags）

| flag | 含义 |
|---|---|
| `cudaEventDefault` | 默认 |
| `cudaEventBlockingSync` | 同步时**休眠让出 CPU 核**（默认是 spin 轮询，浪费 CPU 周期） |
| `cudaEventDisableTiming` | 仅用于同步、不记录计时 → 加速 `cudaStreamWaitEvent`/`cudaEventQuery` |
| `cudaEventInterprocess` | 可作进程间事件 |

## 五、并发内核执行（实战）

### 非默认流中的并发内核（simpleHyperq）

用 4 个 dummy kernel（含 `tan` 循环模拟算量）分别派发到 4 个 non-NULL 流（深度优先），用 start/stop 事件计时：
- **Tesla K40（Kepler, CC 3.5）**：0.079s，nvvp 显示 4 个 kernel 在 4 流中**并发**（Figure 6-5）。

### Fermi 上的伪依赖 + 广度优先救场

- 同一代码跑在 **Tesla M2090（Fermi，无 Hyper-Q）**：0.342s，并发受限。
- Figure 6-6：因共享单工作队列，4 流不能同时启动。深度优先（depth-first）使队列中相邻任务多属同流 → 仅流边缘可并发（Figure 6-7）。
- **广度优先（breadth-first）**：先派发所有流的 kernel_1，再所有 kernel_2……相邻任务均来自不同流 → 无伪依赖，全部并发（Figure 6-8）。

  ```c
  for (int i = 0; i < n_streams; i++) kernel_1<<<grid, block, 0, streams[i]>>>();
  for (int i = 0; i < n_streams; i++) kernel_2<<<grid, block, 0, streams[i]>>>();
  // ... kernel_3, kernel_4
  ```

- 实测 Fermi 上广度优先 0.105s，**比深度优先快约 3 倍**（Figure 6-9 全部流同时启动）。

### OpenMP 多线程派发

一个主机线程管一个流，用 `#pragma omp parallel` + `omp_get_thread_num()` 索引 streams 数组：
```c
omp_set_num_threads(n_streams);
#pragma omp parallel {
    int i = omp_get_thread_num();
    kernel_1<<<grid, block, 0, streams[i]>>>();
    // ...
}
```
编译：`nvcc -O3 -Xcompiler -fopenmp ... -lgomp`。当每流有额外主机工作要重叠时很有用；Kepler 上性能与单线程版相同。

### CUDA_DEVICE_MAX_CONNECTIONS 环境变量

Kepler 最多 32 个硬件队列，但**默认限制为 8**（省资源）。可调：
```bash
export CUDA_DEVICE_MAX_CONNECTIONS=32          # Bash
setenv CUDA_DEVICE_MAX_CONNECTIONS 32          # C-Shell
```
或在 C 中：`setenv("CUDA_DEVICE_MAX_CONNECTIONS", "32", 1);`

每流映射到一个连接；若流数 > 连接数，多流共享一队列 → 可能再现伪依赖。例：8 流 + 4 连接 + 深度优先 → 仅 4-way 并发且有伪依赖（Figure 6-10）；改广度优先即消除（Figure 6-11）。

### 限制并发的 GPU 资源

真实 kernel 用成百上千线程，共享内存/寄存器成为并发瓶颈。例：block(128)×grid(32)、NSTREAM=16 → 即便 32 连接也只达 **8-way 并发**（Figure 6-12）。

### 默认流的阻塞行为

深度优先循环里把 `kernel_3` 放进默认流 → 其后所有 non-NULL 流操作都被阻塞直到默认流完成（Figure 6-13）。

### 跨流依赖（cudaStreamWaitEvent）

复杂应用可有意引入跨流依赖。用 `cudaEventDisableTiming` 建同步专用事件，每流完成时记录，最后让末流等所有事件：

```c
cudaEvent_t* kernelEvent = (cudaEvent_t*)malloc(n_streams * sizeof(cudaEvent_t));
for (int i = 0; i < n_streams; i++)
    cudaEventCreateWithFlags(&kernelEvent[i], cudaEventDisableTiming);
for (int i = 0; i < n_streams; i++) {
    kernel_1<<<grid, block, 0, streams[i]>>>();
    // ... kernel_2..4
    cudaEventRecord(kernelEvent[i], streams[i]);
    cudaStreamWaitEvent(streams[n_streams-1], kernelEvent[i], 0);  // 末流等所有流
}
```

Figure 6-14：第 4 流（末流）等所有其它流完成才开始。

## 六、内核执行与数据传输重叠

Fermi/Kepler 有**两个 copy engine 队列**：一个 H2D、一个 D2H。因此**最多重叠两个数据传输，且仅当方向相反且在不同流**；否则全部串行。

两种情形：
- (a) kernel 消费数据 A → A 的传输必须在该 kernel 之前、**同一流**内。
- (b) kernel 不消费 A → kernel 与传输可放不同流（天然并发）。

### 深度优先重叠（simpleMultiAddDepth）

向量加法拆分为 M 个子集，各子集进独立流；需 pinned 内存（`cudaHostAlloc`），每流处理 `iElem = nElem/NSTREAM` 个元素：

```c
for (int i = 0; i < NSTREAM; ++i) {
    int ioffset = i * iElem;
    cudaMemcpyAsync(&d_A[ioffset], &h_A[ioffset], iBytes, cudaMemcpyHostToDevice, stream[i]);
    cudaMemcpyAsync(&d_B[ioffset], &h_B[ioffset], iBytes, cudaMemcpyHostToDevice, stream[i]);
    sumArrays<<<grid, block, 0, stream[i]>>>(&d_A[ioffset], &d_B[ioffset], &d_C[ioffset], iElem);
    cudaMemcpyAsync(&gpuRef[ioffset], &d_C[ioffset], iBytes, cudaMemcpyDeviceToHost, stream[i]);
}
```

- 相对默认流上的阻塞执行，**流式执行提速约 40%**（Figure 6-15）。
- 三类重叠：kernel 间重叠 / kernel 与其它流传输重叠 / 不同流不同方向传输重叠。
- 两类阻塞：同流 kernel 被前面传输阻塞 / 同方向 H2D 被前面 H2D 阻塞（即便 4 流也串行，因共用同一 copy engine 队列）。
- 把 K40 工作队列降到 1 → 与 Fermi 类似；但 Kepler 的 **GMU** 仍消除伪依赖。

### GMU（Grid Management Unit，网格管理单元）

> Kepler 引入 GMU：可暂停新 grid 下发、排队挂起 grid，支撑 Dynamic Parallelism。Fermi 的 grid 直接从流队列进 CWD；Kepler 的 grid 先进 GMU，由 GMU 管理与排序。

GMU 创建多个硬件工作队列以减少/消除伪依赖；**即使限制到单个硬件工作队列，GMU 的 grid 依赖分析仍能消除伪依赖**。

### 广度优先重叠（simpleMultiAddBreadth）

先派发所有 H2D，再所有 kernel，再所有 D2H：
- **Kepler（K40，单队列）**：与深度优先无显著差异——Kepler 双向调度机制已消除伪依赖。
- **Fermi**：广度优先反而**比深度优先更差**——H2D copy 队列争用使所有 kernel 要等全部 H2D 完成才能启动。

结论：**Kepler 通常不必纠结派发顺序；Fermi 需评估深度/广度优先选最优。**

## 七、GPU 与 CPU 执行重叠

因为 kernel 启动默认异步，launch 后直接在主机线程做有用工作即自动重叠（asyncAPI.cu）：

```c
cudaMemcpyAsync(d_a, h_a, nbytes, cudaMemcpyHostToDevice);
kernel<<<grid, block>>>(d_a, value);
cudaMemcpyAsync(h_a, d_a, nbytes, cudaMemcpyDeviceToHost);
cudaEventRecord(stop);
// 主机在等待 GPU 时可做其它工作
unsigned long int counter = 0;
while (cudaEventQuery(stop) == cudaErrorNotReady) counter++;
```

nvprof 实测：GPU 执行期间主机循环了 **14,606 次**迭代。

## 八、流回调（Stream Callback）

流回调是另一种可入队的操作：流中其前面所有操作完成后，**由运行时在主机侧调用一个应用提供的函数**。这是本书中**首个"GPU 操作反过来在主机上创建工作"**的例子。

```c
cudaError_t cudaStreamAddCallback(cudaStream_t stream,
    cudaStreamCallback_t callback, void* userData, unsigned int flags);

void CUDART_CB my_callback(cudaStream_t stream, cudaError_t status, void* data) {
    printf("callback from stream %d\n", *((int*)data));
}
// 每流末尾挂回调：该流全部完成后才在主机执行
cudaStreamAddCallback(streams[i], my_callback, (void*)(stream_ids + i), 0);
```

- 回调**每次注册只执行一次**，且会阻塞其后入队的工作直到回调完成。
- 回调在 NULL 流上时，所有流先前工作完成后才执行。
- **两个限制**：
  1. 回调内**不能调用任何 CUDA API 函数**。
  2. 回调内**不能做同步**。
- 不要假设回调之间或与其它 CUDA 操作的相对顺序（simpleCallback.cu 输出按流 0→3 顺序打印）。

## 本章核心结论（SUMMARY）

1. **流是 CUDA 编程模型的基础**，以粗粒度并发把高层操作排入独立执行流；异步 API + 流 = grid-level concurrency 的两大支柱。
2. **有依赖的操作必须放同一流**（如 kernel 必须在其消费的数据传输之后、同流）；无依赖的可随意分派。
3. 三种典型重叠：**并发多 kernel / kernel 与数据传输重叠 / CPU 与 GPU 执行重叠**。
4. 实战要点：
   - 平衡 kernel 资源需求与并发资源（太多任务→因资源等待而串行化；太少→设备欠利用）。
   - **尽量别用默认流跑异步操作**——默认流会阻塞其它 non-NULL 流。
   - **Fermi 上需权衡深度/广度优先**以消除共享工作队列的伪依赖；Kepler（Hyper-Q + GMU）基本免此顾虑。
   - 警惕**隐式同步**函数，避免无意的性能下降。
5. **nvvp** 是可视化多流行为、发现重叠机会的关键工具。
