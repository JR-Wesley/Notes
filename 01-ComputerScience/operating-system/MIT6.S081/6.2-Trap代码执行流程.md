# 6.2 Trap 代码执行流程

## 本页知识点

本页以 Shell 的 `write` 系统调用串起一次完整的用户态到内核态再返回的过程。用户代码看起来是在调用 C 函数 `write`，但系统调用包装代码会执行 RISC-V 的 `ecall`，使处理器进入 supervisor mode，并从事先设置的 trap 入口开始执行。课程把入口、处理和返回概括为以下顺序：

1. `ecall` 后先进入 `trampoline.S` 中的 `uservec` 汇编代码。此时仍使用用户页表，入口汇编保存用户寄存器，准备内核栈与内核页表，然后转入 C 函数 `usertrap`。
2. `trap.c` 中的 `usertrap` 判断 trap 原因。对于系统调用，它调用 `syscall`；`syscall` 根据系统调用编号找到对应的实现，本例是 `sys_write`。实现返回后，`syscall` 将结果留给用户态的返回值寄存器。
3. 控制权回到 `usertrap`，随后由 `usertrapret` 准备返回用户态所需的控制寄存器和状态，再进入 `trampoline.S` 中的 `userret`。后者在汇编中切换回用户页表、恢复用户寄存器，并通过 `sret` 回到用户程序。

原页问答还解释了 `vm.c` 中的函数为何能操作内存：它们是内核代码，在 supervisor mode 下运行，但访问仍以虚拟地址经过当前页表翻译。xv6 的内核页表提供了一些方便的直接映射，使内核虚拟地址对应到目标物理地址；在 `uservec` 切换页表之前，不能假定这些内核映射已经生效。

课程最后借 `read`、`write` 的切换开销引出内存映射文件（memory-mapped file）。文件内容映射到进程地址空间后，程序可通过普通内存访问读取或修改映射区域，某些访问场景可以减少反复调用 `read`、`write` 的成本。不过建立映射、缺页处理和持久化仍涉及内核工作，不能理解为完全绕开系统调用。

## 关键解读

**看清汇编与 C 代码的分工。** `uservec` 必须在尚未建立普通内核 C 运行环境时保存寄存器、换栈和换页表；`usertrap`、`syscall` 才能在准备好的环境中进行分派和处理。返回方向同理，`usertrapret` 先准备控制状态，`userret` 再完成需要汇编精确控制的页表切换与寄存器恢复。

**`syscall` 不直接调用 `usertrapret`。** 原页在流程说明中把这一步写进 `syscall`，但 2020 版 xv6 的实际控制流是 `syscall` 返回 `usertrap`，由 `usertrap` 调用 `usertrapret`。记住这一层返回关系，才能在调试器中正确理解调用栈。

**系统调用从 `ecall` 的下一条指令继续。** trap 时保存的 `sepc` 指向触发 trap 的 `ecall`；xv6 在系统调用路径将保存的用户程序计数器加 4，再为 `sret` 设置返回位置。若直接回到原 `ecall`，就会重复触发同一个系统调用。这是系统调用返回路径的具体要求，不可机械套用到所有异常和中断。
