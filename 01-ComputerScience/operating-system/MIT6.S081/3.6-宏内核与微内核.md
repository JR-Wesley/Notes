# 3.6 宏内核与微内核（Monolithic Kernel vs Microkernel）

> 来源：[MIT 6.S081 中文翻译：3.6 宏内核 vs 微内核](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec03-os-organization-and-system-calls/3.6-monolithic-kernel-vs-micro-kernel)。本节比较两种组织方式；文中的性能与安全讨论是设计上的权衡，不是对所有具体系统的实测结论。

## 本页知识点

内核执行受保护操作并检查来自用户程序的参数，因此它的正确性直接关系到隔离能否成立。页面用可信计算基（Trusted Computing Base，TCB）说明这一点，并提出设计问题：哪些操作系统服务应放在内核权限中运行？

| 维度 | 宏内核（monolithic kernel） | 微内核（microkernel） |
| --- | --- | --- |
| 服务的位置 | 文件系统、虚拟内存、进程管理等多数服务在内核态，xv6 采用这一结构。 | 内核态只保留少量基础机制，如进程间通信、基本地址空间和 CPU 复用；文件系统等服务可在用户态运行。 |
| 服务间协作 | 内核内模块可以直接、紧密地协作，较容易共享状态或缓存。 | 用户态服务通常经消息传递或 IPC 协作。 |
| 故障影响 | 更多代码带有内核权限，相关缺陷可能破坏整个系统的隔离。 | 把服务移出内核权限，可缩小具有最高权限的代码范围；服务间边界也增加协作成本。 |
| 性能挑战 | 紧密集成有利于减少跨边界通信，页面以 xv6、Linux 所属的设计类别举例。 | 一次服务请求可能需要额外的用户态／内核态切换；跨服务共享 page cache 等资源也更复杂。 |

页面以 Shell 请求文件系统服务为例说明微内核的通信路径：Shell 向内核中的 IPC 机制发送消息，消息被送往用户态文件系统服务；服务处理完再经 IPC 回复 Shell。与在内核内直接调用文件系统实现相比，这种组织方式增加了边界切换和通信工作。页面也明确指出其比较较为笼统，实际系统的性能与可靠性还取决于具体实现。

## 关键解读

**核心选择是特权代码的边界。** 宏内核把更多服务放入同一个特权地址空间，方便模块协作；微内核把尽可能多的服务放到用户态，以缩小内核态代码范围。不能只比较代码总量，还要看故障发生在哪个权限域，以及服务需要怎样互相通信。

**“微内核更安全”是设计动机，不是自动结论。** 减少内核态代码可降低某些缺陷直接取得内核权限的机会，但 IPC、用户态服务和接口检查本身仍要正确实现。类似地，页面指出微内核有额外切换与共享缓存的性能挑战，并不意味着每个微内核在每个负载下都必然慢于宏内核。

**跨边界调用是权衡的共同来源。** 前面学习的系统调用跨越用户／内核边界；微内核还把服务之间的交互也设计为显式通信。阅读具体设计时，应追踪一次文件操作经过哪些组件、发生几次通信、哪些状态需要共享，才能判断隔离收益与性能代价。
