# 8.4 Copy On Write Fork

> 原页面：[MIT 6.S081 中文翻译：8.4 Copy On Write Fork](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec08-page-faults-frans/8.4-copy-on-write-fork)。本节解释设计机制；具体实验实现还需要同步、错误回滚与 TLB 一致性等处理。

## 本页知识点

传统 `fork` 为子进程分配新的物理页，并复制父进程的整个用户地址空间。Shell 通常在 `fork` 后立刻让子进程执行 `exec`，而 `exec` 会丢弃刚复制的地址空间，因此大部分复制可能完全没有价值。Copy-on-write（COW）把复制推迟到某一方真正写入共享页时。

执行 COW fork 时，子进程的 PTE 暂时指向父进程已有的物理页；对于原本可写的页面，内核同时清除父、子 PTE 的写权限，并记录这是 COW 映射。父子进程可以继续只读访问同一份物理内容，但任一方执行 store 都会产生 page fault，防止修改直接泄露给另一个地址空间。

处理 COW 写故障时，内核验证故障地址及 PTE 的 COW 标记，分配新的物理页，把旧页内容复制过去，再把故障进程的 PTE 改为指向新页且可写，清除 COW 标记，并重新执行原 store。若旧物理页此后只剩一个映射，内核还可在确认该映射原本允许写入后恢复其写权限；存在更多共享者时则必须继续保持只读 COW 状态。

只读 PTE 不一定代表 COW。代码段或真正的只读数据被写入时应视为保护错误，不能复制后开放写权限。课程建议使用 RISC-V PTE 中保留给 supervisor software 的 RSW 位记录 COW，也可以维护独立元数据；无论采用哪种方式，故障处理程序都必须能区分 COW 页、零页、延迟分配空洞和真正非法的写访问。

共享物理页还改变了释放规则。父进程退出、子进程 `exec` 或某个 COW 故障完成私有化时，都只能减少旧物理页的引用计数；计数降到零后才能真正 `kfree`。引用计数通常按物理页保存，并在映射建立、复制、撤销和失败回滚时一致更新。

## 关键解读

**COW 同时修改父进程和子进程。** 如果只把子进程映射设为只读，而父进程仍可写共享物理页，父进程的修改会被子进程直接观察到，破坏 `fork` 的独立地址空间语义。双方都必须经过写故障路径后才能获得私有可写页。

**性能收益来自避免无用复制。** `fork` 只复制页表映射和增加引用计数，启动更快、瞬时内存占用更低；代价转移到首次写入，每个实际修改的共享页要承担 page fault、物理页分配和整页复制。`fork` 后迅速 `exec` 的工作负载收益最大。

**正确性依赖一套跨模块不变量。** 每个 COW 映射必须只读并带有可识别标记；引用计数必须等于仍持有该物理页的映射数量；修改 PTE 权限后还要按架构要求处理 TLB 中的旧翻译；内核通过 `copyout` 写用户页时也必须执行等价的 COW 处理，而不能绕过硬件写故障直接污染共享页面。
