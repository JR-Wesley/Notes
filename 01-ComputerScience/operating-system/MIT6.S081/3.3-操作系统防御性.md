# 3.3 操作系统防御性（Defensive）

> 来源：[MIT 6.S081 中文翻译：3.3 操作系统防御性](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec03-os-organization-and-system-calls/3.3-cao-zuo-xi-tong-fang-yu-xing-defensive)。本节从内核开发者视角说明为什么必须把用户程序视为不可信输入的来源。

## 本页知识点

操作系统要为多个应用持续提供服务，因此不能因为某个应用传入错误参数就崩溃。错误可能出于疏忽，也可能由攻击者故意构造。内核若处理不当，单个程序不仅可能使系统停止服务，还可能越过隔离边界、取得内核控制权；由于内核掌管硬件资源，这会影响整个系统。

由此，内核必须具备防御性：接受用户程序的请求时，不能默认参数正确或程序愿意遵守规则；需要在受保护的边界上检查请求，决定允许哪些操作。页面把应用与内核之间的这种边界比作一堵“墙”，并指出强隔离通常依赖两类硬件支持：用户态与内核态（RISC-V 中称 Supervisor mode）的权限区分，以及页表支撑的虚拟内存。具体机制留待后续小节展开。

## 关键解读

**防御的对象是整个系统的可用性与控制权。** 一个非法参数若仅使调用失败，影响通常局限于发起请求的进程；若使内核崩溃，其他进程也失去服务；若进一步让应用控制内核，隔离就被破坏。这三个结果的影响范围不同，说明为什么系统调用入口需要认真处理不可信参数。

**“有系统调用接口”不足以形成保护。** 接口使应用可以请求服务，但内核仍须验证请求的合法性，硬件也须阻止用户程序绕过接口直接执行特权操作或访问受保护内存。用户态／内核态与页表分别从执行权限和内存访问两方面支持这道边界；本页只概述两者，尚未说明它们在 xv6 中的具体实现。

**隔离是持续维护的性质。** 即使总体架构提供了强隔离，内核实现中的错误仍可能让恶意输入穿过边界。后续看系统调用实现时，可以反复检查：参数来自哪里、内核检查了什么、拒绝请求后是否仍保持系统状态可靠。
