# 8.2 Lazy Page Allocation

> 原页面：[MIT 6.S081 中文翻译：8.2 Lazy page allocation](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec08-page-faults-frans/8.2-lazy-page-allocation)。页面中的代码是课堂演示的最小修改，不是完整的 Lazy Lab 实现。

## 本页知识点

xv6 原本采用 eager allocation：进程调用 `sbrk(n)` 扩大地址空间时，内核立即分配物理页、清零并写入页表。应用程序常按最坏情况申请内存，却只使用其中一部分，因此这种做法会占用从未访问的物理内存。`sbrk` 的增量以字节计，而不是课程口头描述中的页数。

Lazy allocation 把“保留虚拟地址范围”和“分配物理页”分开。`sbrk` 增长时只更新进程记录的地址空间边界 `p->sz`，暂不创建 PTE 映射。进程首次读写该范围时产生 page fault，内核再根据故障地址按页分配物理内存、清零、建立带有用户读写权限的映射，然后保持原 `sepc` 返回，使失败的指令重新执行。

课堂演示修改 `sys_sbrk` 后，Shell 在 `malloc` 初始化新内存时产生 store page fault：`scause=15` 表示写页面异常，`stval=0x4008` 是访问地址，`sepc` 指向对应的 store 指令。处理程序把 `stval` 向下对齐到 `0x4000`，调用 `kalloc` 分配一页，清零后用 `mappages` 加入用户页表；如果物理内存耗尽，则无法兑现此前只在虚拟地址层面作出的分配，需要终止进程或采用更复杂的回收策略。

引入空洞映射后，原有代码的不变量也随之改变。未经修改的 xv6 假定 `p->sz` 范围内的用户页都已映射，所以 `uvmunmap` 遇到无效 PTE 会 panic；在延迟分配模型中，“属于地址空间但从未实际访问”的页面本来就没有映射，释放时应跳过这种合法空洞。类似假设还可能存在于 `fork`、用户与内核间复制以及地址空间缩减路径中，不能只修改 page fault 分支。

## 关键解读

**Lazy allocation 延迟的是物理资源承诺。** `sbrk` 成功只扩大进程可合法使用的虚拟范围，物理页在首次访问时才出现。这样节省内存并降低未使用页面的初始化成本，但错误可能从 `sbrk` 时刻推迟到后续访存时刻，例如首次触页时才发现 OOM。

**Page fault handler 必须先验证地址，再分配。** 仅检查 `stval < p->sz` 不足以构成完整实现；还要排除负向增长后已失效的范围、栈保护页、越界地址及错误访问类型，并处理页对齐、重复映射、分配失败和映射失败。未经验证就分配会把非法指针误当成合法缺页。

**改变分配策略会改变全局不变量。** 过去“地址空间范围内每页都有有效 PTE”成立，延迟分配后变成“范围内允许存在尚未触碰的空洞”。所有遍历、复制、回收和用户内存访问代码都必须按新不变量处理，这正是课堂中的两行核心修改仍不足以完成实验的原因。
