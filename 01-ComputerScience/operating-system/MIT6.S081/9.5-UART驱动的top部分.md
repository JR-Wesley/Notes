# 9.5 UART 驱动的 top 部分

> 章节入口：[MIT 6.S081 中文翻译：9.5 UART驱动的top部分](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec09-interrupts/9.5-uart-driver-top)。本次原站正文无法直接读取；以下依据对应课程内容的[转载整理](https://cloud.tencent.com/developer/article/2337456)与 [MIT 课程讲义](https://pdos.csail.mit.edu/6.828/2022/slides/6s081-lec-interrupts.pdf)归纳。下述 `uartputc()` 环形队列是课程所讲的 xv6 版本；当前 xv6 仓库的 `riscv` 分支可能采用不同实现。

## 本节知识点

本节以 Shell 输出提示符 `$ ` 为线索，追踪一次普通文件写入怎样走到 UART。启动阶段的 `init` 进程建立 console 设备文件，并让文件描述符 0、1、2 都指向 console。Shell 调用 `fprintf(2, "$ ")` 时，只看到文件描述符 2；它无需知道背后是串口设备。字符经过用户态输出函数触发 `write()`，进入内核后依次由 `sys_write()` 取得文件对象、`filewrite()` 判断它是设备文件，再通过设备操作表调用 `consolewrite()`。

`consolewrite()` 逐字节从调用者的地址空间取出字符，交给 `uartputc()`。这一段在发起写操作的进程的内核上下文中执行，属于课程所说的驱动 top half。它可以使用当前进程的信息读取用户缓冲区；当发送队列没有空间时，也可以让该进程睡眠等待。因此，这条路径不适合在中断处理程序中直接运行。

课程版本的 `uartputc()` 使用一个 32 字节的环形发送缓冲区，以及读指针 `uart_tx_r`、写指针 `uart_tx_w`。两指针相等表示队列空；写指针前进一步将追上读指针时表示队列满。为了区分空与满，这种判定方式会留出一个位置，所以 32 个数组槽位的可排队容量至多为 31 个字符。队列满时，写入进程等待读指针推进；有空间时，它把字符放入缓冲区、更新写指针并调用 `uartstart()`。

`uartstart()` 检查队列是否有待发送字符，以及 UART 的发送保持寄存器是否空闲。若都满足，就从队列取出一个字符，写入 UART 的 `THR` 寄存器，让设备开始发送；若设备仍忙，则返回，等后续中断再推进。字符交给设备后，`write()` 路径可以返回，UART 与 CPU 继续并行工作。将字节送入驱动或设备，并不等于字符已经出现在终端上。

## 关键解读

**设备文件把通用 I/O 接口接到具体驱动。** `filewrite()` 通过文件类型和设备操作表选择 `consolewrite()`，应用因而可以沿用文件描述符与 `write()`。抽象的边界在于：通用文件层负责分派，console 与 UART 代码负责实际设备协议。

**环形队列承担流量缓冲与背压。** Shell 产生字符的速度可能高于 UART 的发送速度；队列先吸收这段差异。若队列最终装满，top half 让进程等待，而不是覆盖尚未发出的数据。后续 bottom half 或其他推进发送的路径释放空间时，再唤醒等待者。

**返回时机要与发送完成区分。** `uartstart()` 只在硬件准备好时提交下一个字节，设备之后独立传输，并用中断告知内核可以继续。下一节的 bottom half 正是这条异步完成路径。
