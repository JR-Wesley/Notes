# 9.6 UART 驱动的 bottom 部分

> 章节来源：[MIT 6.S081 中文翻译：9.6 UART驱动的bottom部分](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec09-interrupts/9.6-uart-driver-bottom)；本次依据可读取的[原翻译仓库同名正文](https://github.com/huihongxiao/MIT6.S081/blob/master/lec09-interrupts/9.6-uart-driver-bottom.md)和 [2020 xv6 book，第 4、5 章](https://pdos.csail.mit.edu/6.828/2020/xv6/book-riscv-rev1.pdf)整理。以下函数和环形发送队列指课程所用 xv6 版本。

## 本节知识点

上一节的 top half 把 Shell 输出的字符交给 UART 后，进程可以继续执行，设备则独立发送。UART 准备好接收下一个输出字符，或者收到输入字符时，会产生中断。PLIC 把外部中断送到允许接收它的 CPU 核心；RISC-V 保存被打断的程序计数器等 trap 状态，转入 supervisor 模式并跳到 `stvec` 指定的入口。若中断发生在 Shell 的用户态执行期间，xv6 经 `uservec` 进入 `usertrap()`；若发生在内核态，则走内核对应的 trap 入口。

`usertrap()` 或 `kerneltrap()` 识别出设备中断后调用 `devintr()`。后者根据 `scause` 判定这是 supervisor 外部中断，再通过 `plic_claim()` 取得具体中断源编号。若编号对应 UART，就调用 `uartintr()`；设备处理结束后，`devintr()` 调用 `plic_complete()` 通知 PLIC 该中断已处理。`scause` 说明中断的类别，PLIC 返回的编号才指出是 UART 还是其他外设。

课程版本的 `uartintr()` 同时照顾串口输入与输出。它先尝试从 UART 的接收寄存器读出已有字符，有字符时交给 `consoleintr()`；随后持有发送队列的锁，调用 `uartstart()`。在本节讨论的 Shell 输出场景中，还没有键盘输入，因此接收路径没有字符可处理。`uartstart()` 检查 UART 是否可接收下一个字节；若发送队列里还有提示符后的空格，就从缓冲区取出它并写入 `THR`。队列读指针前进后，因队列满而睡眠的写入进程也可能被唤醒。

处理完成后，trap 返回路径恢复被打断的执行状态。中断发生时 CPU 正运行哪个进程，与此前是谁把字符放进 UART 队列并不必相同；bottom half 依靠设备状态与驱动共享队列继续工作，而不是依靠原写入进程仍在 CPU 上运行。

## 关键解读

**一次 UART 中断可能代表输入、输出或两者都有。** `uartintr()` 需要检查设备寄存器并分别推进相应路径，不能仅凭“来自 UART”就断定是键盘输入。课程讲解先提到读字符，再回到当前的输出例子，正是为说明这个分支。

**top half 与 bottom half 共享发送队列。** top half 生产字符，bottom half 在设备可继续发送时消费字符。二者可在不同 CPU 上接触同一份队列，因此课程版本用 `uart_tx_lock` 保护队列及指针；锁保证共享状态一致，而设备与 CPU 仍可并行运行。

**中断处理有两次不同的“确认”。** 驱动要按 UART 的寄存器协议处理设备事件，内核还要通过 `plic_complete()` 告诉 PLIC 已完成该中断源的处理。只完成驱动动作而不完成控制器侧确认，会使后续外部中断的分发出问题。

> 术语校正：原翻译描述硬件进入 trap 时“清除 SIE 寄存器相应的 bit”。RISC-V trap 机制在这里清除的是 `sstatus.SIE` 总使能位；`sie.SEIE` 是 supervisor 外部中断的分类使能位。两者应区分。
