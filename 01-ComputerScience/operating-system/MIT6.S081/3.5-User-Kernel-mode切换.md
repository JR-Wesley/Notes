# 3.5 User/Kernel mode 切换

> 来源：[MIT 6.S081 中文翻译：3.5 User/Kernel mode 切换](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec03-os-organization-and-system-calls/3.5-user-kernel-mode-switch)。本节建立系统调用跨越用户／内核边界的概念路径；完整 trap 入口细节留待后续课程。

## 本页知识点

用户程序在 User mode 执行，内核在具备更高权限的模式中执行。应用不能像调用自身函数那样直接跳到内核的 `fork` 或 `write` 实现，但必须能请求这些服务。RISC-V 为此提供 `ecall` 指令：用户程序通过系统调用封装代码发出请求，处理器把控制权交给内核控制的入口；内核依据系统调用编号识别请求，再分派到相应实现。页面以 `fork` 和 `write` 说明这条共同路径，而 xv6 中 `syscall.c` 的 `syscall` 函数负责按编号分派。

内核获得控制权之后，还要决定请求是否有效。页面以 `write` 为例：内核必须检查应用传入的缓冲区地址，避免被诱导去读取不属于该应用的内存。能执行 `ecall` 只是能提出请求，并不意味着请求必然获准执行。

系统调用也不是内核重新取得 CPU 的唯一场景。如果用户程序陷入死循环而不主动调用系统调用，硬件定时器到期仍可使控制权转入内核，供内核重新调度 CPU。页面在此只给出概念，未展开定时器中断的具体流程。

## 关键解读

**受控入口让“可请求服务”与“拥有内核权限”分开。** 用户程序选择要请求的系统调用，但不能选择任意内核指令地址以特权模式执行。处理器负责完成受控的控制权转移，内核再解释请求并验证参数，这延续了上一节讨论的防御性。

**系统调用编号与参数属于接口约定。** 页面把 `ecall` 与一个表示调用类型的数字联系起来。学习时应理解为：用户侧按约定准备编号和参数，`ecall` 触发进入内核，内核读取这些信息并分派；不要把它误解为普通函数直接调用内核实现。具体寄存器、trap 保存状态以及到达 `syscall` 函数前的步骤，后续章节会展开。

**主动请求与被动夺回控制权解决不同问题。** `ecall` 用于应用主动请求服务；定时器则让内核即使面对持续运行的用户程序，也有机会恢复控制并调度其他进程。二者都跨越 User/Kernel 边界，但触发原因不同。
