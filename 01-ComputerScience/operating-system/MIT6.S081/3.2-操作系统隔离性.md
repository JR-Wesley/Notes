# 3.2 操作系统隔离性（Isolation）

> 原页面：[MIT 6.S081 中文翻译：3.2 操作系统隔离性](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec03-os-organization-and-system-calls/3.2-cao-zuo-xi-tong-ge-li-xing-isolation)。本次原页面正文未能直接读取；以下结合[课堂笔记一](https://www.cnblogs.com/mlmz/p/16140685.html)与[课堂笔记二](https://www.cnblogs.com/looking-for-zihuatanejo/p/17620950.html)整理，并以前一节的课程框架限定范围。对机制的进一步解释已与可确认的章节要点区分。

## 本页知识点

隔离是操作系统组织结构的重要驱动力。多个应用共同使用一台计算机时，系统既要让它们得到 CPU、内存和文件等资源，又要限制一个应用对其他应用和内核的干扰。课程以较弱的、依赖应用自觉协作的方案作为思考起点，再引出由操作系统提供抽象和控制的必要性。

| 面向应用的抽象 | 隔离问题与作用 |
| --- | --- |
| 进程与 CPU 复用 | 应用以进程形式运行；操作系统决定何时让哪个进程使用 CPU，避免把处理器的控制权永久交给单个应用。 |
| 进程的内存空间 | 各进程通过自己的地址空间使用内存，阻止程序任意读写其他进程或内核的内存。虚拟内存的具体实现留待后续章节。 |
| 可执行文件与 `exec` | 程序的指令和初始数据保存在文件中；`exec` 按接口装入程序映像，而不是让应用随意操纵任意物理内存。 |
| 文件接口 | 应用通过文件名、描述符和读写调用访问持久数据，而非直接操作磁盘位置。文件的共享与权限仍需另行控制。 |

## 关键解读

**隔离首先是故障边界。** 如果一个程序计算错误或写错地址，它的影响应尽量局限在自身，而不应修改别的进程或内核。操作系统提供的进程和内存抽象，让应用能够使用资源，同时为资源访问建立边界。

**抽象并不自动等于强隔离。** 把 CPU 命名为“进程”、把磁盘命名为“文件”只是应用看到的接口；系统仍需要可靠的机制来执行访问限制。下一节将讨论面对不合作甚至恶意的应用时，为什么必须依靠更强的保护。这里不提前把具体的硬件权限位和页表实现归入本节已讲内容。

**隔离与共享要同时设计。** `fork` 后的文件描述符继承、通过文件交换数据等例子表明，进程之间并非完全断开。关键在于共享必须经过明确的接口与规则，而不是任意越过彼此的资源边界。后续阅读 xv6 时，应追踪每一种资源由谁拥有、怎样被共享、由谁检查访问权限。
