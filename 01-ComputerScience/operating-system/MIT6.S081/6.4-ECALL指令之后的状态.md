# 6.4 ECALL 指令之后的状态

> 原页面：[MIT 6.S081 中文翻译：6.4 ECALL 指令之后的状态](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec06-isolation-and-system-call-entry-exit-robert/6.4-ecall-zhi-ling-zhi-hou-de-zhuang-tai)。硬件状态的补充说明参照 [RISC-V 特权架构规范：Supervisor-Level ISA](https://docs.riscv.org/reference/isa/priv/supervisor.html)。

## 本页知识点

执行 `ecall` 后，程序计数器从低地址的用户指令跳到 `stvec` 指向的高地址，即 xv6 映射的 trampoline 页面；处理器已经进入 supervisor mode，但 `satp` 没有改变，当前仍是 Shell 的用户页表。trampoline 以相同虚拟地址映射进每个用户页表和内核页表，使入口代码既能在切换页表前开始运行，也能在切换后继续执行。

此刻绝大多数通用寄存器仍保存用户程序的数据。入口代码在保存它们之前不能随意覆盖任何寄存器，因此 `uservec` 的第一条关键指令使用 `csrrw` 交换 `a0` 与 `sscratch`：用户的 `a0` 暂存在 `sscratch`，而内核预先放入 `sscratch` 的 trapframe 地址进入 `a0`。这样入口代码获得一个可用的通用寄存器和保存其他状态的目标地址。

课程将 `ecall` 的核心效果概括为：进入 supervisor mode，把触发异常的用户程序计数器写入 `sepc`，并把程序计数器设置为 `stvec` 指定的入口。硬件没有保存全部通用寄存器，没有切换到内核页表，也没有设置内核栈，更没有直接调用内核 C 函数。这些工作随后由 `uservec` 完成。

这种最小硬件机制把策略留给操作系统：某些系统可让用户和内核共享页表，从而避免切换；某些快速路径可能只保存必要寄存器；简单处理也可能暂时不需要内核栈。xv6 选择完整保存用户状态、切换页表和内核栈，是其隔离模型与实现结构的选择。

## 关键解读

**“已进入内核态”不等于“内核运行环境已经就绪”。** `ecall` 后权限已经提高，执行位置也进入受保护的 trampoline，但页表、栈和通用寄存器仍延续用户态状态。只有入口汇编完成保存和切换后，才能安全地调用普通内核 C 代码。

**trampoline 同时解决可达性和隔离问题。** 因为硬件不切换 `satp`，`stvec` 指向的入口必须存在于当前用户页表；其 PTE 又不设置 `PTE_U`，用户态无法执行或修改这段监督模式代码。相同虚拟地址的双重映射保证切换页表时取指地址仍有效。

**原页的“三件事”是教学简化。** 按 RISC-V 特权规范，trap 进入 S-mode 时还会记录原因到 `scause`，按异常类型设置 `stval`，并更新 `sstatus` 中的 `SPP`、`SPIE`、`SIE` 等状态。因此应把原页表述理解为本段调试最关注的三项变化，而不是完整的硬件状态转移清单。
