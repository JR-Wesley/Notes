# 4.5 内核页表（Kernel Page Table）

> 原页面：[MIT 6.S081 中文翻译：4.5 Kernel Page Table](https://mit-public-courses-cn-translatio.gitbook.io/mit6-s081/lec04-page-tables-frans/4.5-kernel-page-table)。本次通过该页的搜索索引核对正文，并参照 [xv6 教材第 3 章](https://pdos.csail.mit.edu/6.S081/2020/xv6/book-riscv-rev1.pdf)确认 xv6 的内核映射。页面中的实体开发板与后续 QEMU 的设备地址不可直接混用。

## 本页知识点

本节把内核虚拟地址空间与机器的物理地址布局放在一起看。物理地址落到 DRAM、启动 ROM 还是设备寄存器，由具体主板或 QEMU 模拟的硬件平台决定。xv6 所用的 QEMU 配置将 RAM 放在从 `0x80000000` 开始的物理区域，并把 UART、磁盘、中断控制器等设备寄存器放在其他物理地址。内核对设备地址读写时，执行的是内存映射 I/O（MMIO），并非在普通 DRAM 中存取数据。

xv6 的内核页表把大量内核虚拟地址直接映射到数值相同的物理地址，包括内核代码和数据、可用物理内存以及部分设备寄存器。这种映射称为直接映射（direct mapping）：内核使用虚拟地址 `x`，转换后仍访问物理地址 `x`。它便于内核按已知地址使用内存和设备，但“虚拟地址等于物理地址”只是这些映射的选择，不是分页机制的必然规律。

内核栈展示了不同的映射方式。xv6 为每个进程准备内核栈，并在它下方留一个未映射的 guard page。若栈向下溢出到这页，访存会触发 page fault，帮助尽早发现越界。内核栈对应的物理页同时还落在内核的直接映射区域；实际使用栈时选用高虚拟地址的映射，才能利用相邻的 guard page。guard page 不需要为自己分配一个可用的物理数据页。

页表还设置访问权限：内核代码通常可读、可执行而不可写（`R-X`），内核数据通常可读、可写而不可执行（`RW-`）。权限错误会让意外的写代码或从数据区执行指令更早暴露。未映射、重复映射和权限控制，都是页表除地址转换之外的用途。

用户进程各有自己的用户页表；内核则有自己的页表。创建进程时，内核从可用物理内存中分配页来存放用户页表及代码、数据等。虚拟地址空间的理论范围很大，但通常只有小部分被映射；实际物理页耗尽时，分配及依赖分配的操作可能失败。

## 关键解读

**物理地址布局由平台定义，虚拟地址布局由页表定义。** 先确定硬件把某个物理地址交给 RAM 还是设备，再看内核页表把哪个虚拟地址映射过去。原页展示的实体开发板地址与 QEMU 下 xv6 的设备常量不完全相同，不能仅凭一个示意图推断所有平台的寄存器地址。

**直接映射只是内核布局中的主体。** 它让内核易于访问物理内存和 MMIO；高地址内核栈与未映射的 guard page 则说明内核仍可主动安排虚拟地址，获得额外保护。同一物理页可以有多个虚拟映射，但每个映射的访问路径及邻接关系可能不同。

**内核页表与用户页表承担不同职责。** 进程运行用户代码时，处理器使用该进程的页表；进入内核后需要能够访问内核代码、数据和设备的映射。用户地址空间与内核地址空间可具有相似的理论地址范围，却不意味着它们映射了相同的物理页，或都能实际占满整个范围。
